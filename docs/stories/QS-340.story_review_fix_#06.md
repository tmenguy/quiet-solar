## Findings to fix

### [must-fix] M1 — `test_leftover_dir_after_failed_remove_is_cleaned_on_retry` is platform-dependent
- File: `tests/qs/test_cleanup_worktree.py`
  (`test_leftover_dir_after_failed_remove_is_cleaned_on_retry`, ~line 777)
- Source: CI, Tests shard 1/4 (ubuntu):
  `assert work.exists() and (work / ".git").is_file()` → `(True and False)`
- Description: the test counts on `git worktree remove --force` failing
  partway because of a chmod-555 subdir, with the worktree's `.git` file
  surviving. The order git deletes things in depends on the platform and the
  git version. On macOS `.git` survives; on the Linux runner it is deleted
  before git hits the locked subdir.

  The production code is fine on both platforms. With no `.git` file there
  is no ownership proof, so the script refuses and deletes nothing.
- Proposed fix: build the leftover state deterministically instead of
  relying on git's partial-failure order.
  1. Create the real worktree (fixture) and save the content of its `.git`
     file.
  2. Run `git -C <main> worktree remove --force <work>` for real. This
     succeeds and removes both the admin dir and the directory.
  3. Recreate `<work>` containing the saved `.git` file plus a content file.
  4. Assert that `_registered_branch(main, work)[0] == "absent"` and that the
     admin dir no longer exists.
  5. Run `cleanup_worktree.py --work-dir <work> --issue 77 --force`. Assert
     `status == "removed"` and that `<work>` no longer exists.

  Keep the test's intent and name, or rename it to describe the
  deterministic setup. Drop the chmod/rmtree monkeypatching. Check that no
  other test in `tests/qs` relies on git's chmod partial-failure order. If
  one does, make it deterministic the same way.
