# QS-400 — Item worktrees: naming, creation and cleanup of work-item worktrees and branches; integration inside a deliverable

**Issue**: [#400](https://github.com/tmenguy/quiet-solar/issues/400) ·
**Lane of this task**: feature-factory · **Parent epic**: #369 (child 12) ·
**Sibling**: #399 (the Control Plane core, planned in parallel) ·
**Built on**: the frozen pipeline

Status: implemented — PR #402 (planned and finalized 2026-10-05 after 12 review rounds; implemented 2026-10-05)

## Problem

The second pipeline (epic #369) splits a **deliverable** (a GitHub issue
that ends in one PR, branch `QS_<N>`) into **work items** that run in
parallel, each in its own worktree and branch, and are integrated back into
the deliverable's branch very regularly. Today every tool knows only
`QS_<N>`:

| where | today | gap for items |
|---|---|---|
| `scripts/worktree-setup.sh` | numeric issue only (`:24-35`); branches from `origin/main` (`:271`); always `push -u origin` (`:535`) | no item name, wrong base, push not wanted |
| `scripts/qs/setup_task.py` | `branch = f"QS_{issue}"` (`:243`); fetches on main (`:256`); renders the agents and builds the launcher payload / pin | no item mode |
| `scripts/qs/utils.py` `get_worktree_dir` (`:104-108`) | `<repo>-worktrees/QS_{n}` | no item path |
| `scripts/qs/cleanup_worktree.py` | `branch_name = f"QS_{args.issue}"` (`:501`); safety counts `git log @{u}..HEAD` (`:54-60`) | an unpushed item has no upstream → count `-1` → every cleanup needs `--force`; and `--force --delete-branch` would delete the item's **only** copy |
| `scripts/qs/quality_gate.py` `_resolve_lane_issue` (`:1957-1978`) | `QS_<digits>` only | lane check skipped on an item branch |
| `scripts/qs/create_pr.py` (`:114-148`) | an unparsable branch gives `issue=None`, and the script still pushes and opens a PR | an item branch could be pushed and PR'd by mistake |

And nothing can integrate a work item into its deliverable's branch.

## Goal

1. Item worktrees and branches are **named, created and cleaned up** with
   the same tools as task worktrees, seeded the same way (venv, config,
   custom_components, caches).
2. Item branches stay **local** (D2); cleanup never deletes an item branch
   holding unintegrated commits without an explicit discard.
3. The frozen pipeline's `QS_<N>` path is **unchanged**, proven by
   regression tests.
4. A work item is **integrated** into its deliverable's branch:
   - serialised by #399's session-held `integration:QS_<N>` lock;
   - each merge in a scratch worktree, with conflicts resolved there by
     the integrating session;
   - `QS_<N>` moved only if the gate is green, by a compare-and-swap;
   - no push.
   #399 is on `main` (merged 2026-10-04), so this task builds on its real
   API: the lock, the fencing token, the `gates` cap, `allocate_item_k`, the
   `integrations` table and the `ToolSpec` registry.

## Decisions

Proposed by the assistant; the maintainer delegated the plan to
review-until-convergence (2026-10-03). ⚑ = to confirm at FINALIZE.

- **D1 — Naming.** An item branch is `QS_<N>_<k>`: `N` the deliverable's
  issue number (ASCII digits), `k` a positive integer without leading
  zeros, given by the caller (allocated by the Control Plane — §7). Its
  worktree is `<repo>-worktrees/QS_<N>_<k>`. `get_issue_from_branch` is
  **unchanged** and keeps returning `None` for `QS_<N>_<k>`. Consumers
  checked:
  - nothing lists `<repo>-worktrees/QS_*` by prefix (only
    `worktree-setup.sh` and `utils.py` build the path; `cleanup_worktree.py`
    takes it from `--work-dir`, as today);
  - `git worktree list` readers (`utils.get_main_worktree`,
    `cleanup_worktree.py`) match exact paths;
  - `get_issue_from_branch` callers: `context.py:150` (reports
    `issue: null`), `render_agents.py:193` (renders task-agnostic),
    `create_pr.py:115` (guarded, §6).
- **D2 — Item branches are never pushed.** Local only, no upstream:
  - CI runs only on PRs to `main`, so a pushed item gets no CI;
  - integration will read local refs;
  - there are no remote branches to clean.

  The cost is that in-flight item work has no off-machine copy. Frequent
  integration into the pushed `QS_<N>` mitigates it, and cleanup never
  drops unintegrated item work silently (D5).

  What enforces it here:
  - `worktree-setup.sh` sets no upstream and does not push;
  - `create_pr.py` refuses an item branch (D2 enforcement added by this
    plan, not required by #400; items only);
  - `cleanup_worktree.py` refuses `--push-first` for an item.

  **Repo-wide since #399:** its `pre-push` shim refuses
  `refs/heads/QS_<digits>_<digits>` in every worktree, with no DB needed.
  Only `git push --no-verify` bypasses it (a documented convention). The
  `create_pr.py` guard stays: it fails with a clear JSON error before any
  `gh` call or push attempt, rather than at the hook.
- **D3 — Creation.** `worktree-setup.sh <N> <k>` creates `QS_<N>_<k>` from
  the **local** `refs/heads/QS_<N>` (which must exist), with **no fetch**,
  **no upstream** (`--no-track`) and **no push**; the seeding is the same
  code as a task's. `setup_task.py <N> --item <k>` runs the existing
  declaration guards and the script.
- **D4 — Render without task facts, no pin (maintainer, 2026-10-03).**
  - `setup_task.py --item` renders the agents through Jinja, as for every
    worktree: harness frontmatter, model and effort from `models.py`, the
    shared partials. It uses `bound=False`, so **no task facts** are
    written into the files. This is the epic's rule for the new pipeline
    ("Jinja stays as a build step, with no task facts … the facts travel in
    the launch prompt and the Control Plane"). It is also what a later
    re-render on `QS_<N>_<k>` gives, since `get_issue_from_branch` resolves
    no issue there.
  - It writes **no pin**: nobody opens an item worktree by hand, the node
    (child 6b) is spawned with an explicit `--agent`, and a frozen phase
    agent pinned there would fail at its first `context.py` call.
  - The node's agent is child 6c's.
- **D5 — Item cleanup: two independent steps, each with its own proof.**
  `cleanup_worktree.py --issue <N> --item <k> --work-dir <wt>
  [--delete-branch [--discard-unintegrated]] [--force]` runs in a
  **separate function** `_cleanup_item`. The task path's functions are not
  edited.
  1. **Worktree step** (when `<wt>` exists):
     - it removes `<wt>` only if `<wt>` provably belongs to the item: the
       registration is on `QS_<N>_<k>`, or detached with directory name
       `QS_<N>_<k>`. Anything else (another branch, the `QS_<N>` worktree,
       the main checkout, an unregistered directory) is refused and nothing
       is touched, **with or without `--force`**;
     - it is safe when there are no uncommitted files and the worktree is
       on `QS_<N>_<k>` (not detached). Otherwise it returns
       `action_required` offering `--force`;
     - committed but unintegrated work does **not** block this step: it
       stays on the branch.
  2. **Branch step** (`--delete-branch`, without needing `--force`): it
     runs once the worktree step has removed the worktree, or when the
     directory is already gone (or is a stale unregistered leftover). An
     `error` or `action_required` from the worktree step stops the whole
     call:
     - it deletes `QS_<N>_<k>` only if it is fully integrated:
       `refs/heads/QS_<N>..refs/heads/QS_<N>_<k>` counts 0 commits, merges
       included;
     - otherwise the branch is kept with a machine-readable reason
       (`unintegrated`, `deliverable-missing` when `QS_<N>` is gone,
       `count-failed`), unless `--discard-unintegrated` is given, because
       an item branch is the only copy of its work (D2);
     - the delete uses `git branch -D` (the count, not git's
       `HEAD`/upstream rule, defines "merged"). git refuses a branch
       checked out elsewhere → `delete-failed`.

  `--push-first` is refused for an item. `--force` never deletes a branch:
  it only lets the worktree step discard uncommitted files or a detached
  `HEAD`'s commits, as for a task, after `action_required` reported them.
- **D6 — Integration is in this task, built on #399 as merged
  (maintainer, 2026-10-03: B, "tu vas attendre"; #399 merged
  2026-10-04).** There is a single phase and one PR, which closes #400.
  The split is #399's own contract with #400 (`docs/stories/QS-399.story.md`
  § "Contract with #400"):
  - **the git mechanics** live in scripts outside the Control Plane, like
    `setup_task.py` and `cleanup_worktree.py`;
  - **the locks, the fencing, the gate slot and the records** come from
    `ToolSpec`s that #400 registers in the Control Plane (§9).
- **D7 — Integration does not push.** It moves the local `QS_<N>`; the
  deliverable's node pushes through #399's `push` tool when it wants CI
  (child 6b).
- **D8 — Who calls the integration tools.** They accept a run token (the
  orchestrator) and a node token. With a node token, `tokens.require`
  limits the node to its own task, so it is the **item's own node**, which
  knows its change. #399 binds that node to its deliverable's branch for
  the lock. Which caller actually integrates, and when, is child 6b's.

## Design

### 1. Helpers — `scripts/qs/utils.py`

- `parse_task_branch(branch: str) -> tuple[int, int | None] | None` —
  `re.fullmatch(r"QS_([0-9]+)(?:_([1-9][0-9]*))?", branch)`.
  - `QS_400` → `(400, None)`; `QS_400_2` → `(400, 2)`.
  - `None` for `QS_400_0`, `QS_400_02`, `QS_400_x`, `QS_400_integration`,
    `QS_`, `QS_x2`, `QS_400\n`, `QS_400_2\n`, `main`, `""`.
- `task_branch_name(issue: int, item: int | None = None) -> str` — the one
  place in `scripts/qs/` (outside the Control Plane) where the name is
  spelled. `control_plane/items.py` spells it a second time, deliberately:
  the package may not import `utils` (§7); used by `setup_task.py` (output `branch`),
  `cleanup_worktree.py` (dry run, `_cleanup_item`) and the `create_pr.py`
  message.
- `get_worktree_dir(issue_number: int, item: int | None = None) -> Path` —
  `item=None` returns today's path unchanged (its only caller,
  `setup_task.py:278`, passes one positional argument).
- `get_integration_dir(issue_number: int, item: int) -> Path` →
  `<repo>-worktrees/QS_<N>_<k>_integration` (the item's integration
  scratch, §8).
- `positive_int(raw: str) -> int` — argparse `type` for `--item`: accepts
  only `re.fullmatch(r"[1-9][0-9]*", raw)` (the same grammar as `k` in D1
  and the shell), else raises `argparse.ArgumentTypeError`. The looser
  `context._issue_number` / `epic_doc._issue_number` copies are left
  unchanged.
- `get_issue_from_branch` — **untouched**.
- No logging (the scripts emit JSON); full type hints;
  `from __future__ import annotations`.

### 2. `scripts/worktree-setup.sh` — item mode

```text
worktree-setup.sh <N>                 # task (frozen path, unchanged)
worktree-setup.sh <N> <k>             # work item
worktree-setup.sh <N> <k> --integration   # integration scratch (§8)
```

- External commands used, unchanged: `git`, `ln`, `cp`, `rm`, `find`,
  `mktemp`, `mkdir`, `basename`, `sed`, `awk`, `grep` — no python, `gh` or
  sibling scripts.
- Bash 3.2 compatible (macOS `/bin/bash`): no `local -n`, `mapfile`,
  `readarray`, `declare -A`, `${v,,}`, `${v^^}`. The second argument is
  read as `${2:-}` (the script runs `set -u`). The usage header (`:5-6`)
  and the argument check (`:24-27`) accept 1, 2 or 3 arguments: `N` as today
  (`^[0-9]+$`), `k` (`^[1-9][0-9]*$`), and an optional third argument,
  the literal `--integration`; anything else is a usage error, exit 1. `MODE` is
  `task`, `item` or `integration`.
- One script, one linear flow; the item and integration modes only
  **skip or alter** steps.
  - The venv link (`:274-278`) and the QS-276 marker block (`:318-372`)
    are byte-unchanged, so `TestWorktreeSetupSeedsCaches` stays green
    untouched.
  - The config and custom_components seeding (`:280-316`) is wrapped in
    `if [ "$MODE" != integration ]; then … fi`.
- Task mode keeps today's order:
  1. recovery (`:75-252`);
  2. fetch (`:254-256`);
  3. `worktree add` (`:261-273`);
  4. seed (`:275-372`);
  5. HEAD check (`:374-392`);
  6. `ls-remote` / divergence (`:393-514`);
  7. push (`:516-544`).
- **Item mode** (`BRANCH=QS_<N>_<k>`):
  - **the deliverable check** — a function `_qs_require_deliverable`
    (item mode only):
    `git -C "$MAIN_DIR" show-ref --verify --quiet "refs/heads/QS_<N>"`,
    else print "Error: deliverable branch QS_<N> not found" and exit 1.
    It is called at **two** points so that every path reaching `worktree
    add` is covered (fresh setup, recovered setup, branch reuse), while a
    healthy item still reports "already set up" after its deliverable is
    gone:
    1. inside recovery, after the "already set up" early exit (`:131-135`)
       and before the destructive arms (`:230-251`), so nothing is torn
       down for a deliverable that is gone;
    2. before `mkdir -p "$WORKTREES_DIR"` (`:258-259`), for the fresh path
       (harmless repeat on the recovered path).
  - **recovery**
    - `ACTUAL_UPSTREAM` is still computed (`:130`), so `:232` stays safe
      under `set -u`.
    - The "already set up" test (`:131`) requires only `HEAD ==
      QS_<N>_<k>`, with its own message: "already set up on QS_<N>_<k>
      (local branch)".
    - The rest of recovery (cleanliness gate, tracked/stale removal) is
      unchanged and only ever touches this exact `WORKTREE_DIR`. It runs
      no `git worktree prune`, so a concurrent setup of another item is
      not affected.
  - **fetch:** skipped.
  - **`worktree add`:**
    - an existing `refs/heads/QS_<N>_<k>` is reused with `git worktree add
      <dir> QS_<N>_<k>` (as the task arm `:262-268` does). F17's "diverged
      from main" warning (`:263-266`) is skipped in item mode;
    - otherwise `git worktree add --no-track -b QS_<N>_<k> <dir>
      refs/heads/QS_<N>` (full ref as the start point, so a same-named tag
      cannot win);
    - a branch already checked out in another worktree makes git refuse,
      and the script exits non-zero with git's message, as for tasks
      today.
  - **seed and HEAD check:** unchanged.
  - **`ls-remote` / divergence and push:** the whole block (`:393-544`) is
    wrapped in `if [ "$MODE" = task ]`, so `REMOTE_TIP` is never read in
    item mode. The final message says "local branch, not published".
- **Integration mode** (`worktree-setup.sh <N> <k> --integration`;
  `MODE=integration`):
  - a `DIR_NAME` variable (`QS_<N>`, `QS_<N>_<k>` or
    `QS_<N>_<k>_integration`) now builds `WORKTREE_DIR` and
    `WORKTREE_DIR_CANON` (`:56-57`); `BRANCH` stays the branch name;
  - `_qs_require_deliverable` runs first;
  - an existing directory **or** registration (the same `grep -qxF -e
    "$WORKTREE_DIR" -e "$WORKTREE_DIR_CANON"` pipeline, run before `:75`)
    → "integration scratch already exists" and **exit 3**. The recovery
    block is skipped entirely, so nothing is touched;
  - no fetch;
  - the `worktree add` block tests the mode first: `if [ "$MODE" =
    integration ]; then git -C "$MAIN_DIR" worktree add --detach
    "$WORKTREE_DIR" "refs/heads/QS_${ISSUE}"; elif show-ref …` (otherwise
    the existing arm would try to check out `QS_<N>_<k>`, which the item
    worktree holds). `BRANCH` holds `QS_<N>_<k>` and is used in messages
    only. The third argument is read as `${3:-}`;
  - seeding of `venv` and the QS-276 caches only (no `config/` or
    `custom_components/` symlinks; §8);
  - the HEAD check (`:374-391`) is wrapped in `if [ "$MODE" !=
    integration ]` (detached by design);
  - no `ls-remote`, no push;
  - its own final message: "integration scratch, detached at QS_<N>".

### 3. `setup_task.py`

- New `--item K` (`type=positive_int`).
- `--item` with `--no-worktree` → JSON error, exit 1, checked right after
  argument parsing, before `check_declaration`: no `gh` call, no git work.
- `check_declaration`, `refuse_if_epic` and
  `refuse_decompose_epic_for_wrong_lane` run unchanged. With `--item`
  they are called with `next_cmd="/create-plan"` (`--next-cmd` is ignored
  for an item), so `refuse_if_epic` refuses **every** epic: an epic has no
  items, and `--next-cmd decompose-epic` cannot open a bypass. They are
  kept, at the cost of one `gh` call per item: no new code path, and an
  item is never cut for an undeclared or epic issue.
- Item path:
  - `fetch` on main skipped (`:256`);
  - `worktree-setup.sh N K` from the main checkout, as today
    (`:265-271`);
  - `work_dir = get_worktree_dir(N, item=K)`;
  - render with `render_agents.build_render_context(work_dir, bound=False)`
    + `render_all` (D4);
  - **no** launcher payload; `--next-cmd`, `--next-prompt` and `--title`
    are ignored for an item;
  - on a render failure, `_fail_render(..., item=True)` (new keyword,
    default `False` keeps today's text) names only `python
    scripts/qs/render_agents.py --work-dir <wt>` (no `next_step.py`);
  - output JSON: `issue_number`, `item`, `branch` (`QS_N_K`),
    `worktree_path`, `no_worktree: false`, `harness`.
- Without `--item`: code path and output unchanged.

### 4. `cleanup_worktree.py`

**Flags and routing in `main()`** (the task path is untouched)
- New flags: `--item K` (`type=positive_int`) and `--discard-unintegrated`.
  `--work-dir` stays required and is resolved as today (`Path(...).resolve()`,
  `:503`). `task_branch_name` and `positive_int` join the `utils` import (`:35`).
- Misuse refusals → `status: error`, between `:503` and the dry-run (`:505`):
  `--push-first` with `--item`; `--discard-unintegrated` without
  `--item --delete-branch`.
- Dry run: `would_delete_branch` = `task_branch_name(args.issue, args.item)`
  when `--delete-branch` is given (`:510`). It stays `QS_<N>` for a task, so
  `test_dry_run_announces_the_branch_deletion` is unaffected. The output
  gains `"item": K` only when given.
- After the dry run (between `:513` and `:515`): if `args.item` is set,
  `_cleanup_item(work_dir, args.issue, args.item, force=…, delete_branch=…,
  discard=…)`, then `return`. Everything below runs exactly as today, task
  messages included.
- Like the task path, the script exits 0 for every status; the outcome is in
  the JSON.

**`_cleanup_item`** — new, plus two new module-level helpers:
- `_unintegrated_count(git_dir, deliverable, item) -> int` = `git -C
  <git_dir> rev-list --count refs/heads/<deliverable>..refs/heads/<item>`, or
  `-1` on a missing ref or a git failure. It is module-level so tests can
  monkeypatch it.
- `_item_registration(main_wt, item_branch) -> Path | None` — the path of the
  worktree whose porcelain `branch` line is `refs/heads/<item_branch>`.

It also reuses, unchanged:
- `_main_worktree_or_fallback`;
- `_registered_branch` (`:224-254`: `("absent", None)` for an unregistered
  directory, `("unreadable", None)` when the listing fails);
- `_branch_exists`;
- `remove_worktree` (`:83-166`: it re-checks the main checkout and
  absent/unreadable registrations, but not the branch — hence ownership
  first);
- `_prune_worktrees`;
- `delete_local_branch` (`:172-189`: already `git branch -D`, with
  `cwd=main_wt`).

It emits one JSON object of its own, not through `_emit`.

Output: one dict, every key always present. Defaults:

```text
status, message, worktree_path,
worktree_removed: false, worktree_absent: false, worktree_remove_error: null,
stale_directory: null,
branch: "QS_<N>_<k>", branch_deleted: false, branch_absent: false,
branch_kept_reason: null, branch_delete_error: null,
unintegrated_commits: null, deleted_tip: null,
uncommitted_files: [], detached: false, options: {}
```

`status` is one of:
- `removed` — the worktree was removed or is absent; the branch was deleted,
  is absent, or was not requested;
- `removed-branch-kept`;
- `action_required`;
- `error`.

`error` and `action_required` **stop the whole call**: the branch step does
not run. A kept-branch message ends with "; branch kept".

**Order**
1. `main_wt = _main_worktree_or_fallback().resolve()`; on failure → `error`.
   `item_branch = "QS_<N>_<k>"`;
   `reg_path = _item_registration(main_wt, item_branch)`.
2. **Worktree step, when `work_dir` exists.** Ownership is checked first and
   is never bypassed:
   - `work_dir == main_wt` → `error`;
   - `kind, registered = _registered_branch(main_wt, work_dir)`;
   - **owned** when `kind == "branch" and registered == item_branch`, or
     `kind == "detached" and work_dir.name == item_branch`:
     - **safety**, unless `--force`:
       - `git -C <wt> status --porcelain`; a failing call → `error`;
       - uncommitted files or `kind == "detached"` → `action_required`,
         with `uncommitted_files`, `detached` and `options: {"--force":
         "discard uncommitted files / the detached HEAD's commits; the branch
         is never deleted by --force"}`; stop;
     - `wt_error = remove_worktree(work_dir)`:
       - `wt_error` and `work_dir.exists()` → `error`;
       - otherwise `worktree_removed: true`, `worktree_remove_error:
         wt_error`, and `_prune_worktrees(main_wt)` if `wt_error` (the task
         path's N2 rule);
   - **stale leftover**: `kind == "absent"`, `work_dir.name == item_branch`
     and `reg_path is None` → left on disk, reported as `stale_directory:
     <path>` ("remove it by hand, or `worktree-setup.sh <N> <k>` recovers
     it"); continue to step 4;
   - anything else (another branch, the `QS_<N>` worktree, a detached
     worktree with another name, `unreadable`, an unregistered directory
     with another name) → `error` naming the registration. Nothing is
     touched, whatever the flags.
3. **When `work_dir` does not exist:**
   - `reg_path` not `None` and `reg_path != work_dir` → `error` ("QS_<N>_<k>
     is checked out at <reg_path>"): a typo or stale `--work-dir` is never
     reported as removed;
   - otherwise `worktree_absent: true` and `_prune_worktrees(main_wt)`. That
     clears a registration whose directory was deleted by hand, so `git
     branch -D` is not refused. The task path already prunes, and `git
     worktree add` locks a worktree being created, so a concurrent item
     setup is not pruned. Continue.
4. **Branch step, only with `--delete-branch`.** It runs after step 2
   removed the worktree, after a stale leftover, and after step 3:
   - `refs/heads/QS_<N>_<k>` absent → `branch_absent: true`;
   - `deliverable_missing = not _branch_exists(main_wt, "QS_<N>")`;
     `n = _unintegrated_count(main_wt, "QS_<N>", item_branch)`;
     `unintegrated_commits = n` (when `n >= 0`);
   - kept, unless `discard`:
     - `deliverable_missing` → `deliverable-missing`;
     - `n > 0` → `unintegrated`;
     - `n == -1` with `QS_<N>` present → `count-failed`;
   - otherwise, or with `discard`: record `deleted_tip` (`rev-parse
     refs/heads/QS_<N>_<k>`, the undo point: `git branch QS_<N>_<k> <sha>`
     before gc), then `delete_local_branch(main_wt, item_branch)`. On
     failure (e.g. the branch is checked out elsewhere) the branch is kept,
     with `delete-failed` and git's error in `branch_delete_error`.
5. Check order, so that exactly one outcome wins: ownership / location
   (`error`) > safety (`action_required`) > the branch reasons in step 4's
   order.

### 5. `quality_gate.py` lane check

- `_resolve_lane_issue` uses `parse_task_branch`, imported from the sibling
  `utils` (stdlib-only imports, no cycle) next to `import targets`
  (`:92`), so there is one regex: `QS_<N>_<k>` → `(N, branch)`. The item
  is checked against its deliverable's declaration, and the cache stays
  keyed on `(issue, branch)`. The existing `.strip()` of git's output

### 7. What #399 provides, as merged (checked against the code)

Sources: `docs/workflow/control-plane.md`, the QS-399 story ("Contract with
#400", §8.4, §9.3), and `scripts/qs/control_plane/`.

- **`k`**: `cp.py task add --item-of <deliverable>` calls
  `tasks.allocate_item_k` (`tasks.py:102-107`), which never reuses a
  number.
  - The item row holds `deliverable_id` and `item_k`.
  - The deliverable row holds `issue_number`, plus `branch` (set by
    `worktree-create`, `tools.py:731-738`).
  - #400's tools read the rows, never a free `k` argument.
- **Caller identity**:
  - `tokens.require(task_id=…)` accepts a node token only on its own task
    (`tokens.py:140-142`), so the item's node may call tools on its item;
  - a run token works on any task of its run.
  - Inside a guard or probe, the caller is `ctx._call.who`, a
    `tokens.Principal` with `.subject` and `.session_id`. That is #399's
    own precedent (`tools.py:1430`); frozen `StepCtx` has no public field
    for it.
- **The lock**:
  - `cp.py lock acquire|release --name integration:<deliverable branch>`
    holds the lock for **the session**, across commands. A node token is
    bound to its task's deliverable branch (`locks.py:400-405`).
  - A tool whose `ToolSpec.locks` names it, called with the same token
    subject and session, **co-holds** it (`locks.py:250-265`), re-checked
    before every step.
  - If the lock is **free**, `hold()` silently takes a one-call,
    process-held lock (`locks.py:240-248`). If **another** session holds
    it, `hold()` waits up to 600 s and then returns `BUSY`. Hence #400's
    own session check (§9).
  - A tool never releases a session-held lock; the session runs `lock
    release`.
- **Fencing**: `run_recorded` checks the token before the claim and before
  every step (`locks.recheck`). A stale token also frees the session lock.
- **Keys**: a `succeeded` **or** `failed` call spends its key, and a replay
  returns the recorded result. Only `BUSY`, `POLICY_REFUSED`,
  `STALE_TOKEN`, `STOPPED` or `USAGE` **before any effect** release the
  claim (`control-plane.md` "Outcomes"). The retry rule is §9's "Keys and retries — the one rule".
- **Probe order**: `run()` calls the probe **before** the guard
  (`tools.py:456-463`), so a refusal that must touch nothing goes at the
  start of the probe (§9).
- **The gate slot**: `ToolSpec.cap = "gates"`. Co-holding a lock and
  taking a slot is supported (`locks.py:356-361`).
- **Records**: `tasks.record_integration(conn, clock, *, item_task_id,
  deliverable_id, item_tip, merge_commit, result, tool_call_key)`. Its
  arguments are keyword-only, `item_tip` is `NOT NULL`, and `result` is one
  of `ok`, `gate_red`, `conflict`, `noop`, `error`.
- **Task fields**: `tasks.update_fields` (`SETTABLE` includes `worktree`
  and `branch`).
- **`pre-push`**: refuses `refs/heads/QS_<digits>_<digits>` in every
  worktree (§10.3), so D2 is enforced repo-wide.
- **Registration**: `tools.register(ToolSpec)`, with `CONFLICT` on a
  duplicate. The CLI parser is built from `tools.REGISTRY`
  (`cli.py:814-821`), and `tools.reset()` drops every non-built-in tool
  (tests, `conftest.py:345`).
- **Package boundary**: `control_plane` modules import only from their own
  package (relative imports). `items.py` therefore spells the branch names
  itself (`f"QS_{n}_{k}"`), and reuses `tools`' internal helpers
  `_script_json`, `_python`, `_script` and `tail` (same package; not
  frozen API).

### 8. Integration mechanics — `scripts/qs/integrate_item.py` (no DB)

A plain script, like `setup_task.py`: git only, one JSON object on stdout.
**It takes no Control Plane lock.** It is called only by the §9 tools,
which hold the session lock, the gate slot and the fencing; its module
docstring says so. It sits outside `scripts/qs/control_plane/`, so it is
outside the CI coverage rule, and AC 10–11 (real git) are its whole proof.

**Exit codes**:
- 0 for every outcome below, the `status` field saying which;
- 1 with `{"error": "<code>", "detail": …}` for a refusal or a failure.
  `_script_json` then raises `StepFailed`.

**One scratch per item**: `<repo>-worktrees/QS_<N>_<k>_integration`
(`utils.get_integration_dir(N, k)`), created by `worktree-setup.sh <N> <k>
--integration` (§2). A per-item path means:
- a stale scratch of item *j* never blocks item *k*;
- a session that lost the lock and is still running can only write into
  its **own** item's scratch, never into another item's. This residual
  risk is limited to a superseded session of the same item, which #399
  ends at its next `cp.py` call;
- the path is the owner. The state file's `item` is only a cross-check.

**A per-item exclusive file lock**: every subcommand first takes a
non-blocking `fcntl.flock` on `<git common
dir>/qs-integration-QS_<N>_<k>.lock`. The common dir is absolute: `git -C
<main> rev-parse --path-format=absolute --git-common-dir`.
- It is held for the whole subcommand. For `gate`, it is also held by
  **the gate watchdog** (below), which inherits it. So the lock lasts as
  long as the watchdog, which outlives `integrate_item.py`, `cp.py` and
  the caller's shell, and exits only after the gate's process group is
  gone. A gate cannot be interrupted by `drop`: nothing removes a scratch
  under a running gate. The watchdog's own deadline guarantees the gate
  ends.
- On `scratch-busy`, the error carries `max_wait_s = GATE_TIMEOUT_S`, the
  longest a running gate can hold the lock. The caller waits, then retries
  with a new key. No side file is written, so nothing can go stale: the
  lock alone decides.
- `_gate-run` (below) is internal. It is exempt from the "every
  subcommand takes the flock" rule and never reopens the lock file: it
  holds the inherited descriptor.
- A second concurrent call fails with `scratch-busy`. This covers two calls
  from the same session, and a retry while the previous call still runs.
- The OS releases it when the process dies.

**Every subcommand is content-idempotent**: run again, it answers from the
git state and does nothing more. This, not the tool key, is what makes a
retry safe (§9 "Keys").

**State file**: `qs-integration.json`, in the scratch's own git dir (`git
-C <scratch> rev-parse --absolute-git-dir`): never tracked, and removed
with the worktree. Its fields:
- `issue`, `item`;
- `base` = the scratch's `HEAD` right after creation, which is also
  `QS_<N>`'s tip at that moment;
- `item_tip`;
- `phase`: `created`, then `merged` or `conflicts`;
- `conflicted_files`.

The scratch is seeded with `venv` and the caches only, not the
`config/` or `custom_components/` symlinks: the gate does not need them,
and a third-party component that is not in `.gitignore` would otherwise
make every scratch dirty.

**"Integrated" (used by `check`)**: the scratch's
merge commit `M` exists and is **an ancestor of `QS_<N>`**. In detail:
- phase `merged` or `conflicts`;
- `HEAD != base`;
- `item_tip` an ancestor of `HEAD`;
- `HEAD` an ancestor of (or equal to) `QS_<N>`;
- no operation in progress.

Being an ancestor, rather than equal, means a commit the deliverable node
made after the move does not hide it. `move` and `drop` use deliberately
simpler rules: `move` asks "is `new` an ancestor of `QS_<N>`"; `drop`'s
`integrated` asks "is the state's `item_tip` an ancestor of `QS_<N>`",
which needs no merge commit.

**The state is a hint; git decides.** Every subcommand except `drop`
answers `stale-scratch` for a scratch whose state is missing or unreadable,
whose `item` is not `K`, or whose `phase` git contradicts.

`prepare` repairs the two crash windows it can prove, both at phase
`created`, after the merge ran but before the state was rewritten:
- **(a)** `HEAD` is a merge whose parents are `base` and `item_tip` →
  rewrite the phase to `merged`;
- **(b)** `HEAD == base`, `MERGE_HEAD == item_tip` and unmerged paths
  remain → rewrite the phase to `conflicts`.

- **Same key** when the call got **no answer**: a crash, a kill, a timeout
  of the caller's own shell, or `BUSY` before any effect. #399 then skips
  the persisted steps. While the earlier call is still live, the replay
  answers `BUSY`: #399 refuses a same-key replay whose `started` row has a
  live holder.
- **New key** after any other answer: `succeeded`, `failed`, or a code
  raised after an effect.
- A session that receives `STALE_TOKEN` ends itself (#399); the next holder
  uses its own new keys.
- Because every step is content-idempotent, and the per-item file lock
  refuses a concurrent duplicate (`scratch-busy`), a new key is always
  safe. A caller that lost its counters picks a new suffix.
- Suggested keys:
  - `item:<task>:create:<n>`;
  - `item:<task>:cleanup:<n>`;
  - `item:<task>:start:<item tip>.<n>`;
  - `item:<task>:finish:<scratch HEAD>.<n>` (a flaky red gate is retried
    with `n + 1`);
  - `item:<task>:drop:<n>`.
- Callers branch on `.result.outcome`. A successful call means
  "integrated" only when `outcome == "ok"`.
- `refuse_when_stopped=True` (the default). No step sets `inject_token`
  (D7). `cli` is the only entry point that dispatches tools.

**Long gates**: the `gate` step's runner timeout is 3600 s, as #399's `gate`
tool. A full `gates` cap waits `GATE_WAIT_S` (1800 s), then `BUSY`, before
any effect (the same key is retried). During the step, the tool's process
group co-holds the session lock, so the lock stays held even if the
session dies (§8.4). A token superseded meanwhile fails at the next step
boundary (`STALE_TOKEN`); the new holder finishes the integration with a
new key.

**The integration flow** (child 6b wires it):

```text
cp.py lock acquire --name integration:QS_<N> --purpose "integrate item <k>" --token T
cp.py tool integrate-start  --task <item> --key item:<id>:start:<tip>.1    --token T
  outcome conflicts → resolve in <scratch>, git add, git commit
cp.py tool integrate-finish --task <item> --key item:<id>:finish:<head>.1  --token T
  outcome gate_red → fix in <scratch> and commit (new head), or retry a flaky gate (.2)
cp.py tool integrate-drop   --task <item> --key item:<id>:drop:1           --token T
cp.py lock release --name integration:QS_<N> --token T
```

- **A stale scratch** (`stale-scratch`; e.g. its holder died): the
  scratch belongs to this very item, so the holder runs `integrate-drop`,
  which reports the undo points, then `integrate-start` again. Another
  item's stale scratch never blocks this one.
- **Run `integrate-finish` in the background and wait for its answer**,
  not under a shell tool's timeout (Claude Code's Bash caps at 10 min). A
  dependency for child 6b, next to `--add-dir`.
- **`integrate-drop` vs `item-cleanup`**: `integrate-drop` is the node's
  own drop, which gives it `integrated` and the undo points.
  `item-cleanup` drops any scratch left behind, under the integration
  lock. A cleaned item keeps its `branch`.
- **`scratch-busy`**: a gate is still running, or a duplicate call is
  live. Wait up to the reported `max_wait_s`, then retry with a new key.
- **A terminal deliverable**: its session lock is dead for #399, so the
  `integrate-*` tools are not the cleanup path there. `item-cleanup` (a run
  token, no session lock) drops each item's scratch, item by item.
- **`deliverable-moved` / `deliverable-worktree-busy`**: `integrate-drop`
  (the undo points are reported), then `integrate-start` on the new tip.
  `prepare` refuses to resume a scratch whose `base` is no longer
  `QS_<N>`.
- **A dependency for child 6b**: while `integration:QS_<N>` is held, the
  deliverable's node must not commit on `QS_<N>`, and must keep its
  worktree clean when `move` runs. The lock does not enforce this.
- **A dependency on child 6b/6c**: the integrating node writes in the
  sibling directory `QS_<N>_<k>_integration`, so its session needs that path
  allowed (e.g. `--add-dir` at spawn).

### Implementation notes (as built, PR #402)

Where the code differs from, or adds to, §8–§9 above (review fix #01):
- **`drop`** also removes:
  - a registered scratch whose directory is gone, **even when locked**
    (`pruned: true`, via the unlock fallback);
  - an **unregistered** directory at the scratch path that holds no `.git`
    (one that does — a worktree moved by hand — is refused, `drop-failed`,
    "run `git worktree repair`"), reported as
    `not_a_worktree: true`. There is nothing to snapshot, and
    `worktree-setup.sh --integration` would otherwise exit 3 forever;
  - a registered scratch whose `.git` is **provably** not its worktree
    (`git_unreadable: true`): the file is missing (git would climb to an
    enclosing repository), its target is gone, or it points elsewhere. A
    valid-looking but unreadable scratch → `drop-failed`, nothing removed;
  - a scratch with a corrupt index: `status_unreadable: true`,
    `discarded_files: null`, and the snapshot is still taken (it uses its own
    temporary index).

  It uses `git worktree remove -f -f`, so a locked scratch goes too. A
  registration that survives the prune → `drop-failed`.
- **`check` at phase `created`** → `stale-scratch` (the merge never ran;
  replay `prepare`).
- **`item-cleanup` runs `cleanup` before `drop_scratch`** (AC 12 said
  "drop before cleanup"). A refused cleanup (`action_required` / `error`)
  then never destroys a live scratch. The two steps do not depend on each
  other. A retry with a new key is idempotent: worktree absent, branch
  absent. `discard_unintegrated` without `delete_branch` is `USAGE` before
  the claim.
- **Item cleanup.**
  - A detached worktree removed with `--force` reports `detached_head`, its
    undo point.
  - The branch step reads the tip **before** the count, and counts on that
    tip. The delete is a compare-and-swap on that tip (`update-ref -d <ref>
    <tip>`, review fix #02), made only when no worktree holds the branch. A
    branch that moved is kept as `delete-failed`.
- **Paths** are read NUL-separated (`-z`), so non-ASCII names are not quoted.
  The marker scan uses `:(literal)` pathspecs.
- **`merge-failed`** keeps its own detail when the scratch removal after it
  fails too (`cleanup_error`).
- **Output names** that are not UTF-8 are emitted as `\xNN` text, because the
  Control Plane stores outputs in sqlite. A relative-path worktree
  (`worktree.useRelativePaths`) is recognised by `drop` (review fix #03).
- **A registration of `QS_<N>` whose directory is gone** is ignored by
  `check` / `move`, so `move` falls back to `update-ref`.
- **`move` through `--ff-only`** re-reads `QS_<N>` afterwards: a descendant of
  the new head → `already-moved`, another commit → `deliverable-moved`, back
  at the old tip or gone → `move-failed`.
