## Findings to fix

### [must-fix] M1 — S1 episode bookkeeping does not run every cycle
- File: `custom_components/quiet_solar/ha_model/charger.py:5301-5303` (call site in `ensure_correct_state`), `:5174-5191` (`_update_no_power_episode`), `:888`/`:993`/`:5784` (only call chain), `:946-947`/`:879-886` (group loop early return / continue)
- Severity: must-fix
- Source: qs-review-edge-case-hunter
- Description: `QSChargerGeneric.ensure_correct_state` is only reached via
  group `ensure_correct_state` ← `dyn_handle` ← `constraint_update_value_callback_soc`
  (only while the constraint is unmet, and only while `is_load_active`). Once the
  constraint ends / is removed / is met, the latch is never cleared and the card
  shows NO_POWER until unplug — exactly the S1 scenario. In a multi-charger group,
  one member returning `res False` also starves the bookkeeping of every later
  member. The comment ("run every cycle") and the doc are wrong.
- Proposed fix: call `_update_no_power_episode(time)` from
  `check_load_activity_and_constraints` next to `_update_charger_fault_state`
  (~:3783), which runs every cycle via `update_loads_constraints` regardless of
  `is_load_active`; remove the call from `ensure_correct_state`. Treat a missing
  command object (`_inner_expected_charge_state is None`, e.g. after
  `_reset_state_machine()` from `execute_command` do_reset `:5974` or the OCPP
  comm-error handler `:6498`) as "not wanting charge" instead of an early return
  that pauses the clock (folds in edge-case nice-to-have). Fix the comment and doc.
  Tests: latch set → constraint removed (real `_constraints` emptied) → cycles via
  `check_load_activity_and_constraints` → latch clears after the window; and a
  two-charger group where member 1 returns `res False` does not stop member 2's
  latch from clearing.

### [should-fix] S1 — AC3 round-2 "no re-notify" pin is a test artifact; pick the S1 window from the real re-arm gap
- File: `tests/test_bug_379_zero_power_alert_arming.py:202-230` (the `t += timedelta(minutes=20)` jump), `charger.py:5174-5191`
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-acceptance-auditor (probe: driving the 20-min gap through cycles → `alerts=2`)
- Description: the test skips 20 min without cycles, so the episode clock never
  accrues. Production runs cycles in the gap; whether round 2 re-notifies then
  depends on how long the F2 re-arm → `apply_budgets` → `set(True)` gap really is.
- Proposed fix: determine from the code the realistic worst-case gap between the
  F2 re-arm (`set(False)` at ~REARM) and the group re-setting `True` (budget
  cadence / off→on spacing). Choose the S1 "not wanting charge" threshold so that
  gap keeps the latch in production (e.g. a dedicated constant such as
  `CHARGER_NO_POWER_EPISODE_END_S` ≥ that gap + margin, or reuse
  `CHARGER_START_RETRY_REARM_S` if it covers it); document the rationale next
  to the constant. Then rewrite AC3 round 2 to drive **every cycle** through the
  gap (via the real per-cycle path from M1) with a realistic gap, and add an
  explicit boundary pair: not-wanted for `< threshold` under cycles → latch kept,
  no re-notify; `> threshold` → cleared. Amend the story's AC3 wording ("as in
  `test_stuck_start_rearms_through_the_group`", which uses +20 min) accordingly.

### [should-fix] S2 — Status-sensor blips grant endless fresh fault grace
- File: `charger.py:5143-5147` (`_charger_fault_cleared_at` set), `:5159-5172` (`_was_faulted_within_power_window`), `:5729-5735` (skip branch), `:2432-2434` (`_unknown_state_vals`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: a one-cycle `unavailable`/`unknown` blip sets then clears
  `_charger_fault_since`, refreshing `_charger_fault_cleared_at` and granting a new
  600 s grace. Blips shorter than `CHARGER_FAULT_NOTIFY_DEBOUNCE_S` (120 s) never
  trigger the QS-346 alert either → a stuck charger with a flaky status entity is
  never alerted at all.
- Proposed fix: only record `_charger_fault_cleared_at` (grant the grace) when
  the fault held for at least `CHARGER_FAULT_NOTIFY_DEBOUNCE_S` (i.e. a "real"
  fault episode — equivalently when `_charger_fault_notified` was True or the
  duration check passes). In the skip branch, only skip on "currently faulted"
  (`_charger_fault_since` set) if that fault has already held for the debounce
  too — otherwise a single-cycle blip at check time still blocks; pick the
  simplest rule that satisfies: repeated sub-debounce blips do NOT postpone the
  zero-power alert, a real fault still gets the recovery grace. Test: blips every
  ~300 s during a stuck start → zero-power alert still fires on schedule; the
  existing long-fault test stays green.

### [should-fix] S3 — Fault grace re-arms to `time`, not to the recovery time
- File: `charger.py:5729-5735`
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-acceptance-auditor
- Description: re-arming `last_ping_time_success = time` at the first eligible
  check after a short fault pushes the next check to ~`cleared_at + 900 s`, which
  can land after REARM so the stuck round never alerts (alert slips a whole F2
  round).
- Proposed fix: re-arm to `max(last_ping_time_success, _charger_fault_cleared_at)`
  (when currently faulted, skip without moving the reference forward past the
  fault start — pick whatever keeps "exactly one window after recovery"). Doc:
  say "one full window after recovery" precisely. Test: short fault
  T0+100→T0+300 → alert on the first grid cycle past T0+300+WINDOW (tight
  bound, folds in blind's "S2 test has no tight upper bound" nice-to-have).

### [should-fix] S4 — N1 identity compare treats same-car refresh / ping-pong / generic→real as a swap
- File: `charger.py:4615-4622` (`attach_car` latch clear), `:3872-3885` (stale-object refresh), `:3492-3502` (cross-charger ping-pong), `:3464-3468` (`_default_generic_car`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter (+ blind nice-to-have on `==` vs `is`)
- Description: `_last_attached_car is not car` is True for a recreated `QSCar` of
  the same car (config reload), for A leaving to the generic fallback and coming
  back, and for generic→real identification after plug-in → the same stuck
  episode is notified again.
- Proposed fix: compare by car **name**, and ignore transitions to/from the
  default generic car (`_default_generic_car` / generic car flag) — they are not a
  real identity change. Clear the latch only when a real car is replaced by a
  different real car. On such a real swap also re-arm
  `_expected_charge_state.last_ping_time_success = time` (when not None) so the
  new car gets its own window (folds in edge-case nice-to-have). Tests: stale
  object refresh of same name keeps latch; generic→real keeps latch; real A→real
  B clears latch and re-arms the reference.

### [should-fix] S5 — `_no_charge_wanted_since` is never reset
- File: `charger.py:2393` (field), `:5188-5191`, latch set at `:5757`, `reset()` at `:2974`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: a stale timestamp from an earlier not-wanted period can clear a
  fresh latch on the very next `value is not True` observation, breaking AC3
  round 2.
- Proposed fix: set `self._no_charge_wanted_since = None` where the latch is set
  and in `reset()`. Once the threshold has passed and the latch is cleared, stop
  re-writing every cycle (folds in blind nice-to-have "clear once"). Test: stale
  `since` from before the latch → latch not cleared immediately.
