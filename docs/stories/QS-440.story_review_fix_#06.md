## Findings to fix

### [should-fix] A1 — If the node is reaped after a re-merge conflicts after a miss, the replay answers `finish`
- File: `scripts/qs/control_plane/catchup.py:682` and `:703-711` (`progress`), `docs/workflow/control-plane.md:716`
- Source: qs-review-edge-case-hunter (reproduced with two scratch tests)
- Description: after a "merge not committed" miss, intake resets `clean`
  to `None`. `progress` then re-merges, the merge conflicts, and the node
  is reaped at `catchup.after_merge`, before `clean=False` is written.
  The re-issued call skips intake. It sees `MERGE_HEAD` open, a non-empty
  `misses` and `clean is None`, and answers `finish`. The original call
  would have answered `resolve`.
  A second route ends in the same place: the recorded merge is reset
  away, the rewind sets `clean=None`, the re-merge conflicts, and the
  node is reaped at `after_merge`.
  This breaks the replay determinism that the doc claims.
- Proposed fix: before `self.git.merge()`, when `cu["misses"]` is
  non-empty and `cu["clean"] is not False`, set `cu["clean"] = False`
  in one `self.commit(state)`.
  - A clean merge overwrites `clean` with `True` at the record.
  - A reaped clean merge already resumes through the lookup with
    `clean=False`.
  - An untracked-files refusal leaves `clean=False` with no `MERGE_HEAD`,
    and no later path reads it.
  - The intended `finish` case is unchanged: the implementer returns with
    `MERGE_HEAD` open, intake resets `clean` to `None`, and no merge
    runs.

  Check whether this write needs its own fault point. Every state write
  is followed by a named fault point. If it does, add it to `FAULTS`,
  test it, and update the doc and PR body counts. Prefer to reuse the
  existing write path if one fits.
  Tests: `_crash("catchup.after_merge", …)` for both routes, each
  replaying to `resolve`.
  Make sure the doc's "so a replay agrees" stays true.

### [nice-to-have] A2 — A held lock is `TOOL_FAILED` when the worktree path contains an apostrophe
- File: `scripts/qs/control_plane/catchup.py:83-85` (`_REF_LOCK`)
- Source: qs-review-edge-case-hunter (reproduced with git 2.51, `LC_ALL=C`)
- Description: git prints the path unescaped inside `'…'`, so
  `[^'\n]*` stops at the apostrophe. This is a regression from fix #05.
- Proposed fix: in the first alternative only, let the path include
  `'`. The pattern becomes
  `r"Unable to create '[^\n]*\.lock': File exists|cannot lock ref '[^'\n]*': (?!Unable to create)"`.
  The literal `File exists` still keeps a full disk out. Add a
  parametrised row with `o'brien` in the path → BUSY, and a full-disk
  row with an apostrophe → TOOL_FAILED.
