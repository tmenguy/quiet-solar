## Findings to fix

### [should-fix] S1 — A timed-out / failed-to-start merge is read as "conflicts"; a stale `index.lock` is never detected
- File: `scripts/qs/control_plane/catchup.py:361-369` (`_Git.merge`), and the `MERGE_HEAD`-open branches of `progress` (:590-630), `count` and `after_merge`
- Severity: should-fix
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter
- Description: `merge()` treats any non-zero exit as conflicts whenever
  `MERGE_HEAD` exists. When the runner kills git on the deadline (exit
  124) or git failed to start (127), git may have written `MERGE_HEAD`
  and left a half-written index and a `.git/index.lock`. The tool then
  records `clean: False` and answers `implement resolve`, so the
  implementer gets a broken worktree.
- Proposed fix: in `merge()`, if `res.returncode in (124, 127)`, raise
  `self.fail(args, res)` before probing `MERGE_HEAD`. Wherever an open
  `MERGE_HEAD` leads to an `implement` answer, first check
  `git rev-parse --git-path index.lock`. If the file exists, answer
  `blocked(error, "a stale index.lock")`, which is the maintainer repair
  already listed in `control-plane.md`. Tests: a merge that times out
  (via the `_monotonic` / runner seam) → TOOL_FAILED with no
  `clean: False` record; an open merge plus an `index.lock` → the
  `error` block.

### [should-fix] S2 — `green` is recorded and `push` answered on a dirty worktree
- File: `catchup.py:524` (`intake`, where `green` is recorded) and `:650-654` (`after_merge`, the `push` answer)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `green = rev-parse HEAD` is recorded even when the
  implementer left its fix uncommitted (for example a commit hook
  refused the commit). Then `push` is answered for a head that was
  never gated, which breaks "nothing pushed until the gate is green".
  The leftover changes also make the next catch-up's merge fail after
  the count was already committed.
- Proposed fix: before recording `green`, and again before answering
  `push`, run `git status --porcelain --untracked-files=no`. If it prints
  anything, do not record green: count it as a miss (the same
  persisted `misses` path as a red gate) and answer `implement gate`.
  Tests: a green report on a dirty tree → no `green`, `misses`
  incremented, answer `implement`; a clean tree → unchanged behaviour.
  Document the new guard in the decision-order / repairs part of
  `docs/workflow/control-plane.md` ("The catch-up (#440)").

### [should-fix] S3 — `done()` loops when the task is already `ready_to_merge` or `done_report` is null
- File: `catchup.py:706-730` (`done`), and `scripts/qs/control_plane/tasks.py:23,61` (the forbidden `ready_to_merge → ready_to_merge` transition)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: when the converged check fails but the task is already
  `ready_to_merge`, `left` still contains `state`. `task state --to
  ready_to_merge` is then forbidden, so the node blocks `error`, gets
  the same answer after the unblock, and blocks again in a loop. This
  happens (a) after a maintainer deletes `catchup.json`
  (`done_report = null`, so no report ever counts), or (b) after a
  `blocked` report supersedes the converged one on the latest build
  round. In case (a) every resume also posts another converged report,
  because `done()` never records `done_report`.
- Proposed fix: when `task_state == "ready_to_merge"`, never include
  `state` in `left`. Leave out `report` when the latest build round
  already carries a `converged` report. When `done_report is None`, any
  converged report on the latest build round counts. Tests for (a) and
  (b), each asserting that `done` converges after at most one more
  call and that no second converged report is asked for.

### [should-fix] S4 — Re-issuing `step` on a `done` trigger re-runs `done_checks` and moves `done_report`
- File: `catchup.py:487` and `:663-685` (`done_checks`)
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: re-issuing `step` with the same trigger after
  `last.kind == "done"` runs `done_checks` again. That resets `catchups`
  and overwrites `done_report` with the current max report id. If the
  converged report was posted in between, `done` then sees "not
  converged" and asks for digest/report/state again.
- Proposed fix: when `last.kind == "done"` and the trigger matches the
  recorded one, replay the stored `done_answer(...)` without writing
  (`done_report` and `catchups` are left as they are). Test: step → done
  answer → post the converged report → re-issue step → `catchup done`
  converges.

### [should-fix] S5 — `done_report` takes the max over all phases, but `done()` compares it with build reports only
- File: `catchup.py:679` vs `:709-718`
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: the two sides use different rules. This is probably
  harmless while report ids are global and increasing, but it is
  fragile.
- Proposed fix: filter the `done_report` query on `phase = 'build'`
  (the latest build round), the same rule `done()` uses. Add a test with
  a later non-build report in between.

### [should-fix] S6 — `known()` treats every non-zero exit as "object missing"
- File: `catchup.py:337-342`
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: a real git failure (exit 128 "not a git repository", a
  corrupt repo) becomes `remote_state == "ahead"`, with the misleading
  message "the remote branch is ahead of HEAD".
- Proposed fix: use `git cat-file -e <sha>^{commit}` (or the current
  probe). Map only the "missing object" outcome to False: exit 1, or
  exit 128 when stderr names the bad object or revision. Any other exit
  goes to `self.fail(...)`, and 124/127 keep their existing handling.
  Test: a probe failure that is not a missing object → TOOL_FAILED.

### [should-fix] S7 — `branch()` maps exit 128 to "detached" and mis-reads an ambiguous short name
- File: `catchup.py:313-320` (`_Git.branch`)
- Severity: should-fix
- Source: qs-review-blind-hunter (should-fix), qs-review-edge-case-hunter (nice-to-have). Merged.
- Description: exit 128 also covers "not a git repository" and other
  fatal errors. `--short` prints `heads/QS_1` when a tag has the same
  name as the branch, which wrongly gives INVALID_STATE "detached or not
  on the branch".
- Proposed fix: run `git symbolic-ref -q HEAD` and compare the output
  with `f"refs/heads/{self.branch}"`. Exit 1 → detached. Any other
  non-zero exit → `self.fail(...)`. Tests: a tag with the branch's name
  → accepted; detached → INVALID_STATE; fatal → TOOL_FAILED.

### [should-fix] S9 — AC3: the per-fault invariants are asserted unevenly
- File: `tests/qs/control_plane/test_catchup.py:852-1035`
- Severity: should-fix
- Source: qs-review-acceptance-auditor
- Description: AC3 asks every fault test to assert both "no counter
  applied twice" and "at most one merge commit for the catch-up". The
  `_merge_count` check is missing from `after_adopt`,
  `after_reviewed`, `after_unblock`, `after_stale`,
  `after_merge_with_conflicts`, `after_conflict_record`,
  `after_push_write`, `after_fixes_write` and `after_done_write`. The
  `catchups` check is missing from `after_reviewed`, `after_record`,
  `after_lookup_record` and `after_fixes_write`.
- Proposed fix: add a helper
  `_invariants(w, *, catchups: int, merges: int)` that asserts both
  values, and call it at the end of every fault test with that test's
  expected values.

### [nice-to-have] N3 — A recorded merge sha missing from the object store gives TOOL_FAILED
