### [should-fix] SF-1 — Preserve the `blocking` contract across the OCPP fallback path
- File: `custom_components/quiet_solar/ha_model/charger.py:6431` (also `:6665`)
- Severity: should-fix
- Source: qs-review-coderabbit
- Description: When `blocking=True`, the fallback branch calls
  `_ocpp_set_charge_rate_fallback` without the requested mode. The helper always
  calls `ocpp.set_charge_rate` with `blocking=False`, then updates
  `_ocpp_last_fallback_amps` and returns `True` before the service handler
  completes — so a blocking caller receives an optimistic ack rather than the
  real outcome. The outer caller also fails to forward `blocking` at line 6665.
- Proposed fix: Thread `blocking` into `_ocpp_set_charge_rate_fallback`. When
  `blocking=True`, perform the `ocpp.set_charge_rate` service call with
  `blocking=True` and only update `_ocpp_last_fallback_amps` / return `True`
  after it completes; when the outer caller is non-blocking, keep today's
  schedule-and-return-optimistic behavior. Forward `blocking` at line 6665:
  `return await super().low_level_set_charging_current(current, time, blocking)`.
  Add/extend tests asserting the blocking caller sees the real outcome on the
  fallback path.

### [should-fix] SF-2 — Guard `NaN` offered value in the clip detector
- File: `custom_components/quiet_solar/ha_model/charger.py:6535` (`_ocpp_read_current_offered`), `:6583` (`check_amps_delivery`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `float(raw)` succeeds for a `NaN` reading (only `ValueError` /
  `TypeError` are caught), returning `nan`. In `check_amps_delivery` the reset
  guard `offered >= expected - OCPP_CLIP_TOLERANCE_A` is always `False` for
  `nan`, so a NaN reading is treated as a clip. If `sensor.<cpid>_current_offered`
  reports `NaN` continuously for ≥ `OCPP_CLIP_DETECT_WINDOW_S` (180 s) while
  Charging and the number ack matches the setpoint, a spurious "charger current
  limited" notification is sent. (`inf` is safe; only `NaN` produces the false
  positive.)
- Proposed fix: Add a `math.isfinite` (or `math.isnan`) guard in
  `_ocpp_read_current_offered` so a non-finite reading returns `None`
  (treated as "no reading", not a clip). Add a test feeding a `"nan"` reading
  across the window and asserting no notification fires.

### [should-fix] SF-3 — Wrap the `check_amps_delivery` call site so a raise cannot abort the cycle
- File: `custom_components/quiet_solar/ha_model/charger.py:3730` (in `check_load_activity_and_constraints`)
- Severity: should-fix
- Source: qs-review-blind-hunter (flagged as assumed without repo context)
- Description: `await self.check_amps_delivery(time)` is awaited with no
  surrounding try/except. The `QSChargerOCPP` override reads sensors
  (`_ocpp_read_current_offered`, `get_sensor_latest_possible_valid_value`);
  an unexpected raise there would abort the whole load-management cycle.
  `_notify_ocpp_clip` guards its notify channels, but the state-machine reads
  ahead of it are unguarded.
- Proposed fix: First confirm whether the surrounding QS-346 fault-machine
  block already wraps this call in a protecting try/except. If it does not,
  wrap the `check_amps_delivery` await in a defensive try/except that logs and
  swallows so the diagnostic clip detector can never abort load management.
  Add a test where the override raises and the cycle continues.

### [nice-to-have] NH-1 — Clip message rounds offered/requested amps to whole numbers
- File: `custom_components/quiet_solar/ha_model/charger.py:6597` (`_notify_ocpp_clip`)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: The message formats both values with `:.0f`, so an offered value
  like `15.6 A` rounds to `16 A` and can print "offers 16 A while 16 A were
  requested", contradicting the "clipped" premise.
- Proposed fix: Use `:.1f` (or floor the offered value) so the message never
  reads as offered == requested when a clip was detected.

### [nice-to-have] NH-4 — Move the fallback `current` clamp inside the guarded path
- File: `custom_components/quiet_solar/ha_model/charger.py:6500` (`_ocpp_set_charge_rate_fallback`)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: The clamp
  `int(min(float(self.charger_max_charge), max(float(self.charger_min_charge), float(current))))`
  sits outside the `try`, and only `HomeAssistantError` is caught around the
  service call. The generic base path performs the same `float(current)` inside
  a broad `except Exception`, so it swallows a bad value; the fallback does not.
  If `current` is `None`/non-numeric once latched into fallback mode,
  `float(None)` raises `TypeError` that propagates uncaught. Low-probability
  (amp callers always pass a numeric value) but the two paths diverge.
- Proposed fix: Bring the clamp inside the guarded path (or broaden the
  except to return `False` like the base path) so a bad `current` returns
  `False` instead of propagating.

### [nice-to-have] NH-5 — Guard `devid is None` in the clip notification text
- File: `custom_components/quiet_solar/ha_model/charger.py:6597` (`_notify_ocpp_clip`)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: The message interpolates `` `{self.devid}` `` for the manual
  `ocpp.clear_profile` instruction; the clip-detector path (unlike
  `_ocpp_set_charge_rate_fallback`) never guards `devid`. A device-less /
  partially-initialized `QSChargerOCPP` reaching the clip window tells the
  household to run the action "for `None`". Cosmetic (notification still fires)
  but the instruction becomes unusable.
- Proposed fix: Guard `self.devid` — skip the `clear_profile` instruction
  sentence (or the whole notification) when `devid` is `None`.
