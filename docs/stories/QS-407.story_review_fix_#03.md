## Findings to fix

### [should-fix] T1 — `_identify`: the latest listing must decide, not any earlier one
- File: `scripts/qs/control_plane/reviews.py:~663-679` (`_identify`, the `known = known or listing is not None` flag)
- Severity: should-fix
- Source: BH + EC (same finding)
- Description:
  - The first poll runs right after `claude --bg` returns, before the session can be registered. It normally returns a known listing (`[]`), so `known` is `True` at t≈0.
  - If every later poll returns `None`, the deadline raises a plain `StepFailed`, and `_guarded` fails a review whose session may be running. That is R1's case, reached by another path.
- Proposed fix: set `known = listing is not None` on every poll, so the last poll before the deadline decides. A `None` at the deadline → `Unidentified`; the review stays `launching`. Mirror the pilot, which decides on its own current listing. Update the docstring and the story / control-plane.md sentence if either says "any poll".
- Test: listings `[[], None, None, …]` → `Unidentified`; the review stays `launching`, with no `review_failed`. The opposite order `[None, …, []]` → `failed`, as today.

### [nice-to-have, kept] T2 — a timed-out launch gets only one identify poll
- File: `scripts/qs/control_plane/reviews.py` (`_identify` deadline; `_launch` exit 124)
- Source: EC
- Description: `spawn_bg` times out at 120 s, which is longer than `LAUNCH_SETTLE_S` (60 s) after `launch_at`. So `identify`'s first poll is already past its deadline.
- Proposed fix: when the launch step's output has `timeout: True`, use `deadline = max(launch_at + LAUNCH_SETTLE_S, identify_start + LAUNCH_SETTLE_S)`. If reading the previous step's output is awkward, set the deadline from `identify_start` when `launch_at + LAUNCH_SETTLE_S` is already past. Add a short comment that a genuine exit status of 124 is treated the same way (BH), at a cost of one settle window.
- Test: exit 124, session listed only on the second poll → `running`.
