## Findings to fix

### [should-fix] SF-1 — Only treat a `HomeAssistantError` as a candidate station-profile rejection
- File: `custom_components/quiet_solar/ha_model/charger.py:6452` (`QSChargerOCPP._on_amp_command_error`)
- Severity: should-fix
- Source: qs-review-coderabbit
- Description: `low_level_set_max_charging_current` forwards *every* exception
  from its `try` (including a `ValueError` from `float(current)` at
  `charger.py:6082`) to `_on_amp_command_error`. The hook decides whether the
  error is a station-profile rejection purely by substring:
  `OCPP_STATION_PROFILE_REJECTION_MARKER not in str(error)`. If the raw
  `current` is a string containing `"ChargePointMaxProfile"`, `float(current)`
  raises `ValueError: could not convert string to float:
  'ChargePointMaxProfile...'` — whose text contains the marker — so two such
  invalid-input calls would wrongly increment the streak, latch the sticky
  fallback, and suppress the real invalid-input warning. The marker only ever
  appears in the v0.12.0 `set_station_charge_rate` **`HomeAssistantError`**,
  so a non-HAE exception should never count.
- Proposed fix: In `QSChargerOCPP._on_amp_command_error`, return `False` for
  any `error` that is not a `HomeAssistantError` **before** the
  custom-profile and marker-text checks (so the caller logs the generic
  warning and the streak is untouched). Keep the existing
  `use_ocpp_custom_charging_profile` and marker-substring gates for genuine
  `HomeAssistantError`s. Add a test: a `ValueError("... ChargePointMaxProfile
  ...")` forwarded twice must NOT latch the fallback and must return `False`
  (generic-warning path), alongside the existing AC2/AC4 marker tests.
