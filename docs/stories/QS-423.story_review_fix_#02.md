### [should-fix] A stop that keeps failing (or exits 0 but leaves the session listed) is retried every tick for 7 days
- File: `scripts/qs/control_plane/reviewpilot.py` (`_State`, `stop_closed`); `docs/workflow/control-plane.md` (step 4, the constants table)
- Severity: should-fix (raised by two reviewers this round; fix plan #01 deferred it)
- Source: qs-review-edge-case-hunter (should-fix + nice-to-have "exit 0 but still listed"), qs-review-blind-hunter (should-fix "no cap/backoff", round-1 nice-to-have "attempts counted per stop")
- Description: `attempts` only orders the stops. A `claude stop` that hangs (exit 124) or always exits non-zero, or that exits 0 without ending the session, makes the 60 s "worst case" the steady state: a listing plus a stop on every `PILOT_EVERY_S` tick, for the whole `STOP_WINDOW_S`. Every tick then delays `hook_route`, `ci_watch` and `liveness_watchdog`. The exit-0 case is never logged.
- Proposed fix:
  1. `attempts[rid]` counts **ticks on which the review got at least one stop**, so it increments once per review per tick (only when `rid` is not yet in `sent`). A same-named fork no longer doubles it.
  2. New in-memory `_State.retry_at: dict[str, datetime]`, pruned to the window like the other fields. After a tick sends stops to `rid`, set `retry_at[rid] = clock.now() + timedelta(seconds=min(STOP_BACKOFF_MAX_S, PILOT_EVERY_S * 2 ** (attempts[rid] - 1)))`. New module constant `STOP_BACKOFF_MAX_S = 3600`.
  3. A candidate with `retry_at[rid] > clock.now()` is skipped for the whole tick: no stop, and it does not count toward needing a listing. If every non-stopped candidate is backing off, take no listing. Confirming such a review gone waits for its retry time. That is fine: after a successful stop the first retry delay is one `PILOT_EVERY_S`, so the next throttled tick still confirms it.
     - Watch for this: `stop_closed` is called directly in tests without the throttle. A test that expects "confirmed / retried next tick" now has to advance the fake clock by `PILOT_EVERY_S` between calls. Update the existing `TestStopClosed` tests that way. Keep their assertions otherwise (AC1, AC4a "retried next tick" hold in real time).
  4. When a candidate is matched on a listing, `attempts[rid] >= 1`, and none of its earlier stops failed (no `(rid, code)` with `code != 0` in `stop_logged`), log once per review: `[cp-review-pilot] review V<n>: claude stop exited 0 but the session is still listed`. Use the `(rid, 0)` key in `stop_logged` for the dedupe.
  5. Tests:
     - A stop that always exits 124: over ticks at `PILOT_EVERY_S` spacing it is sent at delays 30, 60, 120 s… capped at `STOP_BACKOFF_MAX_S`. A tick in between sends nothing and takes **no listing** when it is the only candidate.
     - The exit-0-still-listed line is logged exactly once.
     - A session plus a same-named fork increments `attempts` by 1 per tick.
     - The pruning of `retry_at` out of the window.
  6. Docs (step 4): describe the backoff. Change the worst case to: "about 60 s in one tick … ; a stop that keeps failing is retried with doubling delays up to `STOP_BACKOFF_MAX_S` (1 h), so it costs at most one such tick per hour". Mention the exit-0 log line. Add `STOP_BACKOFF_MAX_S` (3600) to the `reviewpilot` constants row. Update the module docstring step 4 to match.

### [should-fix] The doc's "resumed by hand … stopped on the pilot's next tick" claim is wrong both ways
- File: `docs/workflow/control-plane.md:961` (the "review-session stop window" Conventions bullet)
- Severity: should-fix (a doc inaccuracy that fix #01 introduced)
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter
- Description: once a review is confirmed gone (`_state.stopped`), it is no longer a candidate, so resuming its session by hand is **not** stopped on the next tick. After any daemon restart (a `code_version` restart follows every merge), the cold start lists again and stops that hand-resumed session, at an arbitrary moment, while it is still inside the window.
- Proposed fix (doc only): replace the sentence with the real behaviour. A closed review's session resumed by hand (`claude --resume <id>`) inside the window is stopped on the pilot's next tick if its stop is not yet confirmed. Otherwise it is stopped at the next daemon start (every merge restarts it), still within the window; the match ignores the listing's kind. To inspect a closed review's session safely, resume it after the window has passed.

### [nice-to-have] `word_tail`: a raw cut can start with whitespace, and its last fallback is unreachable
- File: `scripts/qs/control_plane/liveness.py:42-62` (`word_tail`)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter, qs-review-acceptance-auditor
- Description:
  - `word_tail("word" + " " * 10 + "end", 13)` returns `"          end"`. The cut starts inside a whitespace run longer than `limit // 2`, the character before the cut is not whitespace, and the raw cut is returned unstripped, so `bg_failure` writes `": " + "          end"`.
  - `return rest if rest.strip() else cut` can never take its `else` branch: `rest` is either empty, and then `gap.end() == limit > limit // 2` has already returned, or it starts with non-whitespace.
- Proposed fix:
  - When `cut[:1].isspace()`, handle it like the boundary case: `return cut.lstrip() or cut`. Put this right after the `text[-limit - 1].isspace()` branch.
  - Replace the last two lines with `return cut[gap.end() :]`, and drop the "and something but whitespace remains" clause from the docstring.
  - Add the parametrized case `("word" + " " * 10 + "end", 13, "end")`.
  - Every existing case keeps its expected value. Check `("alpha beta\n", 4, "eta\n")` and `("ab" + " " * 5, 3, "   ")` in particular: the latter takes the boundary branch first.
  - Keep the invariants: never over `limit`, never empty for a non-empty text and a positive limit.

### [nice-to-have] Step 4 still says a `finished` / `failed` review's session is always idle
- File: `docs/workflow/control-plane.md:578` (step 4 intro), plus the matching module docstring sentence in `reviewpilot.py`
- Severity: nice-to-have
- Source: qs-review-coderabbit (its round-1 comment, only partly addressed by fix #01)
- Description:
  - A `finished` review's session may still be finishing its last turn when the pilot's next tick comes, since `review finish` is followed by "then stop".
  - A `failed` review whose `claude --bg` ran (for example a launch that timed out) may still be busy.
  - "Idle and listed `done`" is the usual case, not a guarantee.
- Proposed fix (doc/docstring only): reword to "usually idle and listed `done` (L1) once its review is `finished`; a `failed` or `abandoned` review's session may still be busy (a launch that timed out, a `REVIEW_TTL_S` expiry), and the stop interrupts it on purpose, since its token is void".
