## Findings to fix

### [must-fix] M1 — a run-token key starting with `pilot:` stops the review pilot for good
- File: `scripts/qs/control_plane/reviews.py:465-479` (`_authorize`, run branch), `:155` / `:503` (`_reserve`); `scripts/qs/control_plane/reviewpilot.py:330-348` (`_split`, `retry_failed`), `drain`
- Severity: must-fix
- Source: BH + EC (same finding)
- Description: `_reserve` stores the caller's raw `ctx.key` as `review_triggers.tool_key`, and `KEY_RE` allows `pilot:foo`. SQLite `LIKE 'pilot:%'` ignores case, so `PILOT:x` matches too. `retry_failed` then runs `_split` → `int("foo")` → `ValueError` on every tick, before `drain`. From then on no cross-run review launches again. A key equal to a real pilot event key also hits the partial unique index `review_triggers_pilot` (an `IntegrityError` on each `discover`), and it takes the pilot launcher's `tool_calls` key (`CONFLICT` on replay).
- Proposed fix:
  1. In `_authorize`'s run branch, refuse with `USAGE` any key where `key.lower().startswith(PILOT_PREFIX)` ("the `pilot:` key prefix is reserved for the review pilot"). Import or share `PILOT_PREFIX` so there is one constant only.
  2. Make the pilot's scans exact and case-sensitive. Filter `retry_failed` / `drain` (and any other `LIKE 'pilot:%'` query) with `substr(tool_key, 1, length(?)) = ?`, or with `GLOB 'pilot:*'`, and add `AND actor = 'cp:review_pilot'` (or the pilot's actual actor constant) where the column exists.
  3. Make `_split` tolerant: when the attempt suffix is not `\d+`, return `None`. Callers then skip the row, so one bad row can never raise again.
- Tests: run token with keys `pilot:g1` and `PILOT:x` → `USAGE`, and no row is written. A hand-inserted malformed `pilot:` row → `retry_failed` and `drain` still work for the other events.

### [should-fix] S1 — `_SAFE_PATH` lets `,` through (it is the allowlist separator) and refuses non-ASCII paths
- File: `scripts/qs/control_plane/reviews.py:313` (and its uses at `:334-345`)
- Severity: should-fix
- Source: BH + EC
- Description: `--allowedTools=` is a `,`-joined value, so a path containing `,` splits one rule into two broken rules, and the session silently can do nothing. The pattern is also ASCII-only: a home such as `/Users/José/...` refuses every review at launch, and the review fails twice.
- Proposed fix: replace the pattern with a deny-list: no whitespace, no `,` and no shell metacharacter. For example, `re.compile(r"[^\s,'\"\\$`;&|<>(){}\[\]*?!#~]+")`. Keep whitespace refused. Document that limit in `docs/workflow/control-plane.md` (Conventions), next to the existing allowlist bullet.
- Tests: a comma path → `POLICY_REFUSED`. A non-ASCII path is accepted, and its rule string is exact. The existing whitespace-refused test still passes.

### [should-fix] S2 — a launcher that dies after a successful `claude --bg` fails a review whose session is running
- File: `scripts/qs/control_plane/reviewpilot.py:121-129` (`_launch_move`), `close_dead`
- Severity: should-fix
- Source: EC
- Description: `_launch` sets `launch_at` and spawns the session. If the launcher dies (OOM, SIGTERM, laptop sleep) before `identify` / `_on_success`, `_launch_move` moves the review to `failed` after `LAUNCH_SETTLE_S`. That voids the live session's token, so its work is lost and `STALE_TOKEN` follows. `retry_failed` then launches a duplicate session.
- Proposed fix: in `close_dead`, fetch the listing also when some `launching` row has `launch_at` set. If `liveness.find(listing, name=row["name"])` finds the session, adopt it with a guarded `UPDATE reviews SET state='running', session_id=?, short_id=?, updated_at=? WHERE id=? AND state='launching' AND launch_at IS NOT NULL` instead of failing it. If it is not listed (or the listing is unknown), keep the current behaviour. Under an unknown listing, keep the current TTL rule and do not fail early. Document the adoption in control-plane.md "Review sessions" (where the pilot closes dead reviews).
- Tests: a launching row with `launch_at` past the settle time whose name is listed → `running`, with `session_id` / `short_id` set and no `review_failed`. If not listed → `failed`, as today. Add a guard test: the row moves between the read and the write.

### [should-fix] S3 — `_identify` keeps polling a review that is already `finished`
- File: `scripts/qs/control_plane/reviews.py:623-636`
- Severity: should-fix
- Source: EC (+ BH nice-to-have: the loop never re-reads the state)
- Description: a quick session can call `review finish` and exit before `claude agents` lists it. `identify` then raises "never listed", and the call is recorded `TOOL_FAILED` for a review that succeeded. A replay returns the same failure.
- Proposed fix: re-read the row's state on each loop iteration. If it is `finished`, return `{"session_id": row["session_id"], "short_id": row["short_id"]}` (`None` values are fine, because `_on_success`'s CASE keeps `finished`). If it is `failed` / `abandoned`, raise `StepFailed` as at entry.
- Tests: the state flips to `finished` while the listing is `None` → the call succeeds, and the review stays `finished`. It flips to `abandoned` mid-loop → `StepFailed`.

### [should-fix] S4 — a diff larger than 256 KiB cannot be enumerated
- File: `scripts/qs/control_plane/gitread.py:27-37, 48-71`; `scripts/qs/agent_templates/_macros.md.j2` (`review_session` macro, the reading step)
- Severity: should-fix
- Source: EC
- Description: `diff` without `--path` is cut at `READ_MAX_BYTES`, and no op lists the changed files. The session cannot find the paths it did not see.
- Proposed fix: add an op `files` with required `base`, `head` (same sha checks): argv `git -C <main> diff --no-ext-diff --no-color --name-status <base> <head>` (with the same fixed options style as `diff`). Add one line to the macro: "If an answer has `truncated: true`, list the changed files with `review read --op files --base … --head …` and read them one by one with `--path`." Update control-plane.md's `review read` table and the `OPS` tuple. Update the render pins in `tests/qs/test_render_agents.py` if they pin the op list.
- Tests: the argv of `files`; refusal without `head`; a real-repo run via the CLI that lists the changed paths.

### [should-fix] S5 — the two sha checks disagree (7-40 vs 7-64, lowercase only)
- File: `scripts/qs/control_plane/gitread.py:31` (`_SHA`), `scripts/qs/control_plane/reviews.py:389` (`_HEX`)
- Severity: should-fix
- Source: BH (should-fix) + EC (nice-to-have)
- Description: `_heads` accepts 64-char (SHA-256) object names that `review read` then refuses. An uppercase `merge_sha` silently falls through to the branch path.
- Proposed fix: define one pattern, `[0-9a-f]{7,64}`, in `gitread`, and use it from `reviews` too. Lowercase a stored or captured sha before matching (in `_heads`, for `merge_sha`).
- Tests: a 64-hex rev is accepted by `review read`. An uppercase `merge_sha` is captured as the merge head (lowercased).

### [should-fix] S6 — `review finish` ignores the rowcount of its guarded `finished` UPDATE
- File: `scripts/qs/control_plane/reviews.py:798-802`
- Severity: should-fix (CR rated it trivial; kept because it is cheap and makes the contract explicit)
- Source: CR
- Description: if the row leaves `launching`/`running` anyway, outcomes are recorded and `review_done` is posted for a review that is not `finished`.
- Proposed fix: capture `cur = conn.execute(...)`. If `cur.rowcount != 1`, raise `CpError("STALE_TOKEN", f"review {rid} is no longer open", instructions=tokens.REVIEW_INSTRUCTIONS)` before any outcome or `review_done` write. The transaction rolls back.
- Tests: patch or simulate the state change between `tokens.require` and the UPDATE (e.g. a seam or a direct state flip inside the same connection) → `STALE_TOKEN`, with no outcome row and no `review_done`.

### [should-fix] S8 — one bad alert payload crashes the pilot on every tick
- File: `scripts/qs/control_plane/reviewpilot.py:246` (`_alert_events`)
- Severity: should-fix
- Source: BH
- Description: `json.loads(r["payload"]).get(...)` raises on a NULL payload, a non-JSON payload or a non-object payload. The hook then fails each tick on that row.
- Proposed fix: decode defensively. On `None`, a `json.JSONDecodeError`/`TypeError`, or a non-`dict` value, treat the payload as `{}` (no tasks). The group still exists, so its identity by alert ids stays the same.
- Tests: an alert with a NULL payload, one with `"[]"` and one with `"x"` → the tick does not raise, and the other events still fire.

## Triaged out (not fixed, with reason)
- CR: "Do not pass the launch grant in the command line" — invalid as a must/should-fix. This is the documented design choice in `docs/workflow/control-plane.md` Conventions ("A review's token is visible", #407): the session token is necessarily in the `claude --bg` argv, as a node's is. The threat model is agent mistakes, not adversarial sessions. Moving only the grant would not change the exposure.
- BH: the lock code may not handle a review principal — invalid. `tool review`'s spec holds no lock and no node cap (AC 1f; `reviews.py:690-698`).
- BH: `--model None` / `inherit` — invalid. `scripts/qs/models.py:38`: the resolver never returns `inherit`, and `None` raises → `StepFailed`.
- CR: "CodeRabbit unavailable" fallback — resolved. CodeRabbit delivered its review later.
- Deferred nice-to-haves (low value now; they can be follow-ups): the deadline wording; the per-tick scans growing with history; NULL `session_id` for a running review; the silent close when every run is closed; the node hook fragment on review sessions; the OpenCode `edit: deny`; `norm_path` on git paths; grep exit 128 mapped to `NOT_FOUND`, and `--pattern=-x`; stopping abandoned sessions; the unbounded `reviews` / `review_triggers` snapshot sections; the cap on finish text; quoting regex metacharacters under the allowlist (part of T13's live check); AA's coverage-by-claim note (CI enforces it).
