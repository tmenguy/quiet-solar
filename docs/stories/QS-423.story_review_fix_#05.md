## Findings to fix

### [should-fix] "After a successful stop the next tick still confirms the session gone" holds only for a first-attempt success
- File: `docs/workflow/control-plane.md:582` (step 4 "Backoff" bullet), plus the matching sentence in `scripts/qs/control_plane/reviewpilot.py`'s module docstring step 4, if it makes the same claim
- Severity: should-fix (the doc contradicts the code)
- Source: qs-review-blind-hunter
- Description: `retry_tick[rid] = tick + _backoff(rid)` is set whatever the exit code, and `_backoff` is `2 ** (attempts - 1)` ticks. A stop that exits 0 on attempt k ≥ 2 is confirmed gone only on the review's next **eligible** tick, after 2^(k−1) ticks (up to 120). The "exit 0 but still listed" line is delayed the same way. The code is right: resetting the backoff on exit 0 would bring back a stop on every tick for a stop that exits 0 but leaves the session running. The sentence is wrong.
- Proposed fix: replace the sentence with: "After a successful stop the review's next eligible tick confirms the session gone: the next pilot tick after a first attempt, later after a retry (its backoff applies whatever the exit code)."

### [nice-to-have] The "about 60 s" worst case is step 4's share, not the whole hook's
- File: `docs/workflow/control-plane.md:584` (step 4 "Worst case" bullet), plus the module docstring if it states the bound
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: the same pilot tick can also take step 2's listing (while a review runs) before step 4's own, so the hook as a whole can take about 80 s.
- Proposed fix: say "about 60 s of step 4 in one tick …", and add "(step 2's own listing, taken while a review runs, comes on top)".
