# QS-352 — Person-constraint target leaks into car `_next_charge_target` after the person constraint is removed

Lane: **bug × product** · Issue: [#352](https://github.com/tmenguy/quiet-solar/issues/352) · Split out of #351 (finding C) · Follow-up: [#353](https://github.com/tmenguy/quiet-solar/issues/353) (target provenance vs user-override snapshot).

## Symptom

A person-originated minimum-charge constraint is pushed on a plugged car
(Tesla M3, Magali, 41.63 % needed). Three minutes later the person is
re-allocated to another car and the person constraint is correctly
removed — but the car keeps **41 %** as its next-charge target: the
rebuilt best-effort filler targets 41 % instead of the car's 80 %
default, and the "next charge target" select shows 41 %. The state
persisted until a manual `qs_device_clean_and_reset`.

**Fingerprint 1 — the filler target is the integer `41`, not `41.63`.** The
person constraint keeps the float (07:05 line) and the local
`target_charge` at charger.py:4107/4134 is the float; the only `int()`
cast on this path is `set_next_charge_target_percent` (car.py:2679). An
int `41` at filler construction (charger.py:4243) can therefore only
come from `_next_charge_target` or from `_user_originated["charge_target_percent"]`
(fed by the same cast via the snapshot, see Amplifier). This narrows the
source to those two stores.

**Fingerprint 2 — `/3/3` and `replacing … (37.0/80.0/3/3)`.** The rebuilt
constraint is a plain FILLER (bump-solar would produce
`CONSTRAINT_TYPE_BEFORE_BATTERY_GREEN = 5`, const.py:378, at
charger.py:4197-4198), and it *replaces* the old filler: only the
removal path resets-then-re-pushes (load.py:2171-2179 →
charger.py:4248); the force and user-timed paths wipe the filler without
re-pushing it (charger.py:3826, 3923). So 07:08:04.613 is the
`do_remove_all_person_constraints` route with no force/timed/bump state
on the car.

**Discriminating between the two stores — log-verified (blocking check,
done).** For the 41 to have been promoted into `_user_originated`
between 07:05:04.44 and 07:08:04.54, `_on_user_originated_changed`
(car.py:306-322) must have run on the Tesla. Its callers on `QSCar`
(every `set_user_originated` site: car.py:423 person fixation, 501
person select, 2510 charge-time, 2537/2554 force, 2600/2602 target
select, 2772 bump-solar switch, 2807/2817 charger select, 2851
clean-constraints) mostly have **no dedicated log line** (the
conversion helpers `convert_auto_constraint_to_manual_if_needed` and
`user_add_default_charge_at_datetime` do not log; `load.py:238-243`
fires the hook even on an unchanged value). So the discriminator must be
**trigger-agnostic**, and it is:

- **Primary — the pin.** Every snapshot in that window runs car.py:319-322
  with `current_forecasted_person = Magali` and no prior `person_name`
  pin (the Tesla was in the Hungarian set at 07:05; Magali is authorized
  for it — the allocation rejects unauthorized pairs, home.py:2712), so
  it would have written `person_name = Magali`. The periodic 07:08
  allocation would then have taken the pin path (home.py:2601-2623:
  pinned when the person exists and the car is in `authorized_cars`) and
  printed `Tesla M3->Magali` at home.py:2734-2739. **It printed
  `Tesla M3->Thomas`.** Hence no snapshot ran on the Tesla in the window
  — whatever the trigger, logged or not.
- **Corroboration — cadence.** The only allocation lines are on the
  3-min cache cadence (`HOME_PERSON_CAR_ALLOCATION_CACHE_S = 3*60`,
  home.py:154; expiry observed at the next update tick, ≈181 s apart):
  07:02:03 → 07:05:04 → 07:08:04 → 07:11:04, each preceded by the four
  `_compute_person_next_need` lines of the periodic recompute, and
  07:08:04.539 is labelled `preferred-car assignment`, not a
  user-originated pin. A person-select that *differs* from the forecast
  forces an off-cadence allocation (car.py:519); none exists. (A pick
  equal to the forecast returns at car.py:505-508 after the snapshot
  with no allocation — that case is excluded by the pin argument, not by
  cadence.)
- **Corroboration — fingerprint 2.** `/3/3` excludes a bump-solar
  snapshot; `replacing (37.0/80.0/3/3)` excludes the force/timed paths.
- **Daily-notification fixation** (`PERSON_NOTIFY_REASON_DAILY_CHARGER_CONSTRAINTS`
  from charger.py:4257-4264 → person.py:565): the only notifications
  logged are `reason changed_car` from home.py:2820, which passes **no**
  `person_ct/force_ct/user_ct`, so person.py:565 cannot fire. No
  daily-reason line in the window. No restart in the window.

**Residual (stated, not closable from the log):** a user tap on the
Tesla in the 74 ms between 07:08:04.539 (Thomas becomes the forecasted
person) and 07:08:04.613 (charger cycle) would have pinned *Thomas* and
captured 41 without contradicting the allocation line. No system trigger
exists in that window (`changed_car` cannot fixate), so this is a
human-tap-in-74-ms residual; accepted as negligible.

Conclusion: at 07:08 the 41 lived **only** in `_next_charge_target`; the
incident took the **no-snapshot path**, which is exactly the path the fix
below closes.

Determinism: reproduced deterministically with a throwaway unit
scenario (below). The bare repro emits the same `37.0/41/3/3` filler and
the same `replacing` line shape; the replaced constraint differs
(`41.63/80.0` bare repro vs `37.0/80.0` incident) because the incident
had a pre-existing 37→80 filler that absorbed cycle N's push through
`eq_no_current` / `carry_info_from_other_constraint` (load.py:2465-2481).
The red test seeds that filler and asserts it survived step 1.

## Root cause

**One sentence:** `QSChargerGeneric.check_load_activity_and_constraints`
([charger.py:4137](../../custom_components/quiet_solar/ha_model/charger.py:4137))
persists the person's minimum target into the car-level
`QSCar._next_charge_target` via `QSCar.set_next_charge_target_percent`,
but the path that ends the person constraint's life —
`do_remove_all_person_constraints`
([charger.py:4169](../../custom_components/quiet_solar/ha_model/charger.py:4169))
— never restores that field, and the only other clearing site,
`QSHome.compute_and_set_best_persons_cars_allocations`
([home.py:2764-2773](../../custom_components/quiet_solar/ha_model/home.py:2764)),
clears it **only when it equals `car_default_charge`**, so a
person-derived value (41 ≠ 80) survives the person's departure.

Causal chain, confirmed against source:

1. Cycle N (Magali present, car not charged enough): charger.py:4107-4137
   sets local `target_charge = person_min_target_charge` **and** calls
   `self.car.set_next_charge_target_percent(target_charge)` →
   `_next_charge_target = int(41.63) = 41` (car.py:2679-2681). The value
   carries no provenance — it is indistinguishable from a default or a
   user value. Only `user_set_next_charge_target` marks
   `user_originated("charge_target_percent")`; this path does not.
2. Cycle N+1 (Tesla now Thomas's): `get_best_person_next_need` returns
   Thomas. The home-side "OK, it is already ready!" line is consistent
   with the charger-side `is_person_covered = True` (→ `person = None`,
   charger.py:4061-4062), and no charger WARNING "assigned to person
   Thomas … is_person_covered: False" appears at 07:08:04.5xx; the other
   route to the same branch is "need already met"
   (charger.py:4092-4103). **Either way** `do_remove_all_person_constraints = True`
   (4082) → Magali's constraint cleaned via the `ANY_PERSON_OF_ANY_NAME`
   sentinel (charger.py:4176; `_match_ct` load.py:2115-2125 removes every
   person-tagged constraint and keeps the untagged filler) — the
   `Constraint Reset device wallbox 1 maison` line. `_next_charge_target`
   untouched. Thomas is still notified at 4257 with `person_ct=None`
   (no fixation).
3. Same cycle, top of the car block (charger.py:3732):
   `target_charge = setup_car_charge_target_if_needed()` →
   `get_car_target_SOC()` → **41**. `user_target` resolves to `None`
   (charger.py:3752-3760: key absent), no force/user-timed/agenda
   constraint → `realized_charge_target is None` → filler block
   (charger.py:4184-4255): `intermediate = 20`,
   `max_target_charge = max(20, max(41, 37), 80) = 80`, but
   `37 + 1.5 >= 41` is false so the `elif` (charger.py:4223) that would
   lift the target to `max_target_charge` does not fire → **FILLER
   37 → 41**, replacing the pre-existing 37 → 80 filler. Exactly the
   logged `(Tesla M3 37.0/41/3/3) replacing … (37.0/80.0/3/3)`.
4. `compute_and_set_best_persons_cars_allocations` (home.py:2760-2784)
   runs with `current_forecasted_person = Thomas` → **person-present**
   branch (home.py:2764-2774): `41 == 80.0` is False → not cleared →
   `continue`. (Had the car been person-less, the no-person branch
   `if _next_charge_target is not None: continue` would have kept it
   too.) Either way the guard is designed to clear only the system
   default, so a person-derived value never matches.
5. The value stays until `_reset_charge_targets()`
   (`user_clean_and_reset` / `user_clean_constraints`, car.py:2840/2853).

Why the native car limit is unaffected: `adapt_max_charge_limit`
(car.py:2058-2061) clamps the requested value to **at least** the
default (`asked_percent <= car_default_charge → default`; it never lowers
below the default), so the leak only affects Quiet Solar's own
target/filler (as the issue already noted).

**Amplifier — system-originated promotion to user intent (tracked as #353,
not fixed here):** `QSCar._on_user_originated_changed` (car.py:306-310)
snapshots the *current* `_next_charge_target` into
`user_originated("charge_target_percent")` on **any** user-originated
change on the car. Two trigger classes exist while a person constraint is
live:

- **no user involved:** the end of every cycle calls
  `person_to_notify.notify_of_forecast_if_needed(..., person_ct=…)`
  (charger.py:4257-4264); at the person's daily notification time
  (`PERSON_NOTIFY_REASON_DAILY_CHARGER_CONSTRAINTS`, person.py:509-510)
  it fixates the person on the car
  (`_fix_user_selected_person_from_forecast`, person.py:565-567 →
  `set_user_originated("person_name", …)`, car.py:416-423) — which
  snapshots the 41 as `charge_target_percent`;
- **any user tap** on the car (bump solar, force charge, person select,
  target select, charger select, clean constraints — the full caller list
  above).

After promotion, charger.py:3752-3760 applies 41 as `user_target`, the
person is pinned, and the guard of the fix below is (correctly) blocked.
**The fix in this story closes the no-snapshot path only** — the path
this incident provably took (see Discriminating, above). The snapshot
path is #353's scope.

Hypotheses eliminated:

- *Allocation didn't actually change the car's person* — rejected:
  07:08:04.539 shows `Tesla M3->Thomas Menguy` and the charger removed
  Magali's constraint at 07:08:04.613.
- *User had set a 41 % target* — rejected by fingerprint 1 (int 41 from
  the person float) **and** by the pin argument (no snapshot on the Tesla
  in the window).
- *41 was already promoted into `_user_originated`* (any user tap, or
  daily fixation) — rejected by the pin argument (trigger-agnostic),
  corroborated by cadence and fingerprint 2; daily fixation excluded by
  the absence of any daily-reason notification. The 07:21 reset alone
  does not discriminate (it wipes both stores).
- *Force / user-timed / bump-solar state on the car* — rejected by
  fingerprint 2.

## Repro strategy

Unit test, deterministic, real `QSCar` + real `QSChargerGeneric`, built on
the public harness `tests/utils/charger_harness.py` (`make_hass`,
`make_home`, `create_charger`, `make_real_car`, `init_charger_states`,
`plug_car`) — the established import, see `tests/test_qs306_log_volume.py:47-56`.
A throwaway version (not committed) was run in-session and fails today
with `AssertionError: leaked target 41` / `assert 41 == 80.0`.

## Fix plan

Restore the car target where the person constraint's lifecycle ends —
inside the `do_remove_all_person_constraints` branch of
`QSChargerGeneric.check_load_activity_and_constraints`
(charger.py:4169-4182), symmetric with the write at 4137:

```python
if do_remove_all_person_constraints:
    ... existing clean_constraints_for_load_param_and_if_same_key_same_value_info(...) ...
    # QS-352: the person branch above persisted the person's target into the
    # car (set_next_charge_target_percent at the push site). No person
    # constraint is live anymore -> put the car back on its default unless the
    # user explicitly chose a target. `user_target` is the value resolved at
    # 3752-3760 (None when the key is absent OR present-but-None); it is read
    # once at 3874 and never reassigned before this point.
    if user_target is None and int(self.car.get_car_target_SOC()) != int(self.car.car_default_charge):
        _LOGGER.info(
            "check_load_activity_and_constraints: plugged car %s restoring default charge target %s%% (was %s%%) after person constraint removal",
            self.car.name, self.car.car_default_charge, self.car.get_car_target_SOC(),
        )
        await self.car.set_next_charge_target_percent(self.car.car_default_charge)
        target_charge = self.car.get_car_target_SOC()
```

- **Guard is `user_target is None`**, not `has_user_originated(...)`:
  the key can be present with value `None` (a snapshot taken after
  home.py:2773 cleared the field), which charger.py:3752-3760 already
  treats as "no user target". Using the same resolved variable keeps one
  semantics in the function (Test 3). `user_target` is written only at
  3752-3760 and read once at 3874; nothing reassigns it before 4169
  (verified).
- **Compare as `int`**: `set_next_charge_target_percent` int-casts
  (car.py:2679) while `car_default_charge` is a config float
  (`80.0`; the config selector is `step=1`, config_flow.py:1362-1369,
  so integral in practice). `int()` on both sides makes the "no churn"
  property hold even for a hand-edited fractional default; home.py:2769
  and car.py:2653 already rely on the same integral assumption.
  `car_default_charge` is non-`None` by construction (car.py:113 default
  `100.0`; config_flow.py:1359 `vol.Optional` omits the key rather than
  storing `None`) and is already dereferenced unguarded at
  charger.py:4185/4214.
- **`target_charge` refresh** uses `get_car_target_SOC()` (int 80) —
  exactly what charger.py:3732 will read next cycle — so the filler built
  in the *same* cycle (charger.py:4184+) equals the next-cycle filler;
  otherwise the `37.0/41` filler would still be pushed once and replaced
  a cycle later.
- `set_next_charge_target_percent` re-adapts the native car limit via
  `setup_car_charge_target_if_needed`: a no-op for person targets at or
  below the default (the clamp already held it there); for a person
  target **above** the default it issues one real `adapt_max_charge_limit`
  write lowering the car's native limit back to the default — the
  desired behaviour.
- Guarded by the `!=` so no-person cycles do not churn the field (and do
  not re-trigger home.py's INFO "setting default charge target" log
  every allocation). After the restore, home.py:2767-2773
  (person-present branch) will set the field to `None` on the next
  allocation; `get_car_target_SOC()` lazily re-materialises the default
  — harmless.
- **Not changed:** `home.py:2764-2773`. Its `== default_charge` check is
  the *person-assigned* branch's "clear the system default so the person
  forecast drives" — a different purpose from restoring after removal.
  In this incident it ran (Thomas assigned) and correctly refused to
  clear a non-default value it cannot attribute. With the charger-side

  considered and rejected: for a person target **above** the default the

## Iceberg check

**Local containment + tracked generic follow-up (decision (b), taken
in-session).** The observed defect is a missing symmetric reset: one
write site (4137) with no matching restore at the one removal site
(4169); the writer enumeration above shows the restore can only ever
touch a person-derived value. The fix is contained to the same function
and closes the path this incident provably took (log-verified
no-snapshot path).

**Generic cause, deliberately out of scope here →
[#353](https://github.com/tmenguy/quiet-solar/issues/353)
(`kind:feature,target:product,scale:task`):** `_next_charge_target` has
no provenance (system-default / person / user share one field), and the
user-override snapshot promotes whatever is in it to user intent — with
a **system-originated** trigger (daily person notification fixation)
that needs no user action. Through that path the leak recurs and the
containment guard is (correctly) blocked. Widening the fix here would
require either a provenance model or a value-equality heuristic that can
clobber a genuine user choice — a design change to the user-overrides
model, not a bug fix. This bug is **not** superseded: exit 1 (fix), with
#353 mandatory as the follow-up.
