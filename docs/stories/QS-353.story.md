# QS-353 — Car charge-target provenance: system hold instead of fake user intent

- **Issue**: [#353](https://github.com/tmenguy/quiet-solar/issues/353)
- **Branch**: `QS_353`
- **Lane**: feature × product (`scale:task`)
- **Back-links**: #352 (containment fix, diagnosis findings C2/C4), #351

## Problem

`QSCar._on_user_originated_changed` (`car.py:306-322`) is the car's
**freeze**: on *any* `set_user_originated(...)` call on the car it copies
the whole current car state — `_next_charge_target`,
`_next_charge_target_energy`, bump-solar, force-charge, charge-time, and
(only if absent and authorized) the forecasted person — into the
`_user_originated` store. That store is what the rest of the system reads
as "the user's choice" (charger.py `user_target` block at `3856-3865`;
home.py default-clear guard at `2797-2803`; allocation manual pin at
`home.py:2614`), and it is persisted across restarts (`load.py:583-586`).

The freeze is a **deliberate design** — "I saw the car's state and
tapped something, so that state is mine" (design decision D1 below). Three
things in the current code violate that design:

1. **A system action fires the freeze.** The daily person notification
   (`QSPerson.notify_of_forecast_if_needed`, `person.py:565-567`) calls
   `QSCar._fix_user_selected_person_from_forecast()` (`car.py:416-429`),
   which writes `set_user_originated("person_name", …)` to pin the
   allocation. No user is involved, yet the freeze runs and promotes the
   live person minimum (e.g. `41`) to `charge_target_percent`. From then on
   the charger applies `41` as `user_target`, the person is pinned until
   unplug/reset, and the #352 restore guard (`user_target is None`) never
   fires (#352 diagnosis, finding C2). The pin is also **never released**:
   the next day's notification returns early (`person_name` already set),
   so a prediction that has already come true or false keeps constraining
   allocation.
2. **The freeze stores `None`.** When home.py clears the field
   (`home.py:2803`, person assigned and value == default) a later freeze
   stores `charge_target_percent = None` — a key that is *present* but
   carries no intent (#352 finding C4). Worse, on a percent car
   `charge_target_energy` is **always** frozen as `None`, so after a single
   user tap both keys exist and the home.py default-clear guard
   (`not has_user_originated(...)` on **both** keys) is permanently
   disabled until `clear_all_user_originated`.
3. **Changing the person on a car does not reset what was validated under
   the previous person.** `user_set_person_for_car` (`car.py:498-517`)
   clears the *other* car's store when it takes a person away from it, but
   on the car being acted upon it only overwrites `person_name` — then the
   freeze re-stamps the previous person's minimum as the new person's user
   target.

### Design decisions (settled in DISCUSS)

- **D1 — the freeze stays.** A user action on the car validates the whole
  visible car state (target included, whoever wrote it). The issue's
  options 1 (provenance tag) and 2 (drop the target from the freeze) are
  **rejected**: they contradict D1. The issue's "Expected" sentence is
  superseded by this story (see "Issue re-scoping" below).
  **Accepted residual (review C-4):** a genuine user tap (bump solar,
  force charge, …) while a person minimum is displayed *does* stamp that
  minimum as the user target, and the #352 restore is then (correctly)
  blocked until unplug / reset / person change. This story closes the
  **no-tap** window only; the tap case is intended behaviour.
- **D2 — the notification does not create user intent; it creates a
  time-boxed system hold.** What the design wants is: "I announced a
  decision to the user; unless they touch it, the system must not
  second-guess that decision **until the prediction is proven true or
  false**" — i.e. until the announced leave time. The hold is *not*
  `_user_originated` state, so the freeze never runs for it. The hold is
  **persisted**, for parity with the pin it replaces: (a) the daily
  notification does **not** re-fire after a restart —
  `_last_forecast_notification_call_time` is in-memory only
  (`person.py:102`, set at `:628`), so the daily gate (`:484-493`) stays
  closed until the next `notification_dt_time`; (b) the save path is the
  same as the store's — `QSDeviceSensorData.async_update_callback`
  (`sensor.py:790-797`) serialises `update_to_be_saved_extra_device_info`
  on every update tick, and `_user_originated` rides in that very dict
  (`load.py:583`).
- **D3 — `until` = `QSPerson.predicted_leave_time` as announced.** The
  person constraint's `end_of_constraint` is *derived* from it
  (`update_person_forecast` → `car.get_best_person_next_need`
  `car.py:626-630` floors it to the previous 30-min boundary →
  `end_of_constraint = next_usage_time`, `charger.py:4270`/`4301`), and it
  is the time printed in the notification. A hold is set **only when a
  notification is actually being sent for an uncovered car**: the call
  sits in the `else` of `if self.predicted_mileage is None or
  self.predicted_leave_time is None` (`person.py:525`) **and** in the
  `else` of `if is_covered:` (`:545-552`) — a covered ("OK, already
  ready") car is not held, unchanged from today. Two consequences, both
  accepted: the hold outlives the person constraint's end by **up to 29
  min** (the floor) — during that window the person stays pinned exactly
  as a user pin would today, strictly shorter than today's until-unplug
  pin; and the hold is bound to the **announced** time — if the
  prediction moves later during the day (review C-19) the hold still
  expires at the announced time, allocation is free again and, the
  forecast still pointing at this car, normally re-picks the same person.
  No re-hold on forecast updates: only an announcement creates a hold.
- **D4 — user person change = reset, then freeze the new state.**
  Selecting a person (or "Force no person") on a car is the user rejecting
  the announced/validated situation **and** making a new choice. So the
  car's *person-bound* state is reset first — `person_name`, both target
  keys, the hold, `_next_charge_target` / `_next_charge_target_energy` —
  and `set_user_originated("person_name", …)` then fires the freeze, which
  validates the new person together with the current bump / force /
  charge-time. The target has no "new value" at that instant (the new
  person's minimum is computed on the charger's next cycle), so — via B —
  no target key is frozen; the new person's forecast or the car default
  drives it, and the user's next tap validates it. Freezing the car
  default as a user target here is deliberately avoided: it would make the
  `user_target is not None` branches in charger.py block the new person's
  constraint updates. **Not cleared by C (review P-3):** the user's manual
  charger selection (`USER_ORIGINATED_CHARGER_NAME`) and the charge-time
  `CHARGE_TIME_CONSTRAINTS_CLEARED` sentinel — neither is tied to the
  person, so C uses **targeted clears**, not `clear_all_user_originated()`
  (the freeze then re-stamps `charge_time` from the field, which preserves
  the sentinel — see "Facts").
- **D5 — a user pin and a hold never coexist (review C-16).** Whenever the
  store gains a `person_name`, the hold is cleared in the same step: by
  the freeze when it converts the forecasted (held) person into a user pin
  (`car.py:319-322`), and by C. Any site that drops a user pin therefore
  never uncovers a stale hold.

## Goal

A charge target written by the system or derived from a person is never
promoted to user intent by a **system** action; a system decision announced
to the user is held only until its leave time; `None` never enters the
user-originated store under the target keys; and a user person change
resets what was validated under the previous person. The #352 leak
scenario is closed on the **notification (no-tap) snapshot path**; the
user-tap path is accepted behaviour (D1).

## Design

### Facts the design relies on (verified against source, rounds 1-2)

- **Clears never fire the freeze.** `clear_user_originated` /
  `clear_all_user_originated` are plain dict pops (`load.py:256-260`);
  only `set_user_originated` calls `_on_user_originated_changed`
  (`load.py:238-245`), with a re-entrancy latch
  (`_in_user_originated_update`) so nested `set_`/`clear_` from inside the
  hook only touch the dict. `_stamp_user_target` (B) is therefore safe
  inside the hook.
- **The freeze writes `person_name` only if absent** (`car.py:319-322`:
  `not has_user_originated("person_name")` **and**
  `current_forecasted_person is not None` **and**
  `_is_person_authorized_for_car(...)` at `:321`) — it never writes
  `person_name = None`. Since `set_user_originated` stores the value
  *before* invoking the hook (`load.py:239`), the freeze triggered by C
  sees the new `person_name` already present and does not overwrite it.
- **The freeze and `charge_time`** (`car.py:313-317`): field set →
  isoformat; field `None` and stored value ≠ `CHARGE_TIME_CONSTRAINTS_CLEARED`
  → `None`; field `None` and stored value == sentinel → **untouched**. So
  a CLEARED sentinel survives C's freeze; `bump_solar` / `force_charge`
  are stamped from the fields `_qs_bump_solar_priority` (default `False`,
  `car.py:220`) / `do_force_next_charge`, never from the prior store.
- **`can_use_charge_percent_constraints()` is static per config**
  (`car.py:2558-2565`: invited → False; no/zero battery capacity → False;
  else True — no live SOC-sensor dependency since QS-243), so B's
  percent/energy dispatch cannot flip at runtime.
- **`predicted_leave_time` is always aware UTC** (assigned only at
  `person.py:293/310/319/371`, all `None` or `.astimezone(tz=pytz.UTC)`;
  the storage restore at `:417-420` is commented out; the serialiser at
  `:641` builds a *local copy* and does not mutate the attribute).
- **Notification call-site invariant.** `predicted_car` is the car whose
  `current_forecasted_person.name == self.name` (`person.py:495-499`,
  re-resolved after `update_person_forecast` at `:517-521`), so the held
  name (the car's forecasted person) and `until` (this person's leave time)
  always refer to the same person. The call sits inside `if do_notify:`
  (`:514`), after the `mobile_app is None` early return (`:472-473`), and
  in the not-covered branch (`:552`).
- **Allocation reads the pin once per recompute** (`home.py:2614`) and
  short-circuits the `FORCE_CAR_NO_PERSON_ATTACHED` sentinel at
  `:2619-2621` **before** `get_person_by_name`; the unauthorized branch is
  `:2625-2633`; there is no `else` for `p_per is None` (an unknown name
  falls through unpinned). `car.current_forecasted_person` is assigned
  from the allocation at `:2755-2760`; a cache hit (`:2771-2783`)
  re-applies the last allocation without re-reading the pin
  (`HOME_PERSON_CAR_ALLOCATION_CACHE_S = 3 * 60`, `home.py:156`).
- **`_reset_charge_targets()` exists** (`car.py:2567-2569`): sets both
  `_next_charge_target` and `_next_charge_target_energy` to `None`, no
  store access, no charger I/O; `get_car_target_SOC` lazily
  re-materialises `car_default_charge` **into the field**
  (`car.py:2708-2711`) — assert fields *before* calling it.
- **Other readers of the pin** (`get_user_originated("person_name")` in
  `custom_components/`, complete): `car.py:374-387` (boot validation of
  the *user* pin), `:467-468` (`get_car_person_option`), `:498/:513`
  (`user_set_person_for_car`), `:612` (`get_best_person_next_need`),
  `charger.py:3713` (log only), `home.py:2614` (allocation);
  `has_user_originated("person_name")` at `car.py:319`, `:418`. Only the
  allocation read changes; `:467` and `:612` fall back to
  `current_forecasted_person`, which allocation sets from the pin.
- **Keys are bare literals by car.py convention** (extra-device-info key
  `"current_forecasted_person_name_from_boot"` at `car.py:330/342`, store
  key `"bump_solar"` at `:311`); the new keys follow it — no `const.py`
  additions. Existing `const.py` names are used in test assertions
  (`USER_ORIGINATED_CHARGER_NAME`, `USER_ORIGINATED_CHARGE_TARGET_PERCENT`,
  `CHARGE_TIME_CONSTRAINTS_CLEARED`, `FORCE_CAR_NO_PERSON_ATTACHED`).
- **Test harness facts.** `tests/utils/charger_harness.py` `make_home()`
  (`:69-108`) is a `MagicMock` with
  `compute_and_set_best_persons_cars_allocations = AsyncMock()` (`:89`);
  `home.get_person_by_name(...)` therefore returns a `MagicMock`, and
  `self.name in person.authorized_cars` is **False** → any test needing
  authorization must stub `home.get_person_by_name` (pattern:
  `tests/test_user_overrides.py:316-319`). `_FakeCar.set_user_originated`
  (`tests/test_person_car_allocation.py:73-74`) is a plain dict write —
  the freeze never runs on `_FakeCar`. Allocation is a **min-cost**
  Hungarian on the Wh deficit (`home.py:2497-2508`, `home_utils.py:148-173`);
  `_FakeCar.get_adapt_target_percent_soc_to_reach_range_km` (`:88-98`)
  returns `deficit = (mileage - remaining_km) * 150`, so the person with
  the **smaller** deficit wins the single car; pass-2 tie-break threshold
  `PREFERRED_CAR_ENERGY_THRESHOLD_WH = 1000` (`const.py:533`).

### A′ — time-boxed system person hold (replaces notification fixation)

**New `QSCar` state** (`car.py`, next to
`_current_forecasted_person_name_from_boot`, `~235`):

```python
self._system_person_hold_name: str | None = None
self._system_person_hold_until: datetime | None = None   # aware UTC
```

**Shared helper** `QSCar._as_utc(dt: datetime) -> datetime`:
`dt.replace(tzinfo=pytz.UTC)` if `dt.tzinfo is None` else
`dt.astimezone(pytz.UTC)`. Used by both the setter and the restore so the
naive arm is covered once (AC 1).

**Persistence** (`update_to_be_saved_extra_device_info` /
`use_saved_extra_device_info`, `car.py:324-362`): two new keys
`system_person_hold_name` (str|None) and `system_person_hold_until`
(isoformat str|None). Restore, minimal `try` (project rule):

```python
name = stored_load_info.get("system_person_hold_name", None)
until_s = stored_load_info.get("system_person_hold_until", None)
until = None
if until_s is not None:
    try:
        until = datetime.fromisoformat(until_s)
    except (TypeError, ValueError):
        _LOGGER.warning("Car:%s ignoring persisted system person hold, invalid until %r", self.name, until_s)
if name is not None and until is not None:
    self._system_person_hold_name, self._system_person_hold_until = name, self._as_utc(until)
else:
    self._system_person_hold_name = self._system_person_hold_until = None   # absent / half / invalid → no hold, no log
```

Older stores (keys absent) → no hold, **no warning**. Expiry is checked
lazily by the resolver — no `device_post_home_init` change.

**Not in `QSCar.reset()`** (review P-7): `attach_car` (`charger.py:4536`)
calls `car.reset(keep_commands=True)` on every attach including boot
re-attach, which would drop a persisted hold. The unplug clear goes at the
explicit unplug site instead (below).

**Fixation → hold.** Rename `_fix_user_selected_person_from_forecast()` to
`hold_forecasted_person_until(until: datetime) -> None` (public: called
from `QSPerson`; docstring required; every test reference to the old name
is renamed in the same slice — `grep -rn _fix_user_selected_person
tests/`). Guards, in order, each a silent no-op that **leaves existing
hold fields untouched**: user pin present
(`get_user_originated("person_name") is not None`);
`current_forecasted_person is None`; not authorized
(`_is_person_authorized_for_car`, existing WARNING reworded to
`"Car:%s skipping system hold on Person:%s (not authorized)"`);
`until <= now` (review C-21 — a notification sent after the announced
leave time; DEBUG `"Car:%s not holding Person:%s, until %s already passed"`).
Otherwise set `_system_person_hold_name = current_forecasted_person.name`,
`_system_person_hold_until = self._as_utc(until)`, INFO
`"Car:%s holding Person:%s until %s (announced)"`. `now` is
`datetime.now(tz=pytz.UTC)` (the method has no `time` parameter; the
caller's `time` is the same clock).

Call site `person.py:565-567` — bind a local for mypy narrowing (review
D-8):

```python
leave_time = self.predicted_leave_time   # non-None here by construction (D3)
if leave_time is not None and (person_ct is not None or force_ct is not None or user_ct is not None):
    predicted_car.hold_forecasted_person_until(leave_time)
```

**Freeze converts hold → pin (D5).** In `_on_user_originated_changed`
(`car.py:319-322`), when the forecasted person is written as
`person_name`, also call `self.clear_system_person_hold()`.

**Resolver** `QSCar.get_pinned_person_name(time: datetime) -> str | None`
(docstring required; `time` is the aware-UTC home clock,
`home.py:2589/2593`; the resolver does **not** normalise `time` — tests
must pass aware UTC):

```text
user = get_user_originated("person_name")     # may be FORCE_CAR_NO_PERSON_ATTACHED
if user is not None: return user
if hold_name is not None and hold_until is not None and time < hold_until:
    return hold_name
if hold_name is not None:
    log INFO "Car:%s system hold on Person:%s expired at %s"
    clear_system_person_hold()
return None
```

`clear_system_person_hold()` sets both fields to `None`; silent (the
resolver owns the expiry log, emitted exactly once).

**Consumers of the pin** — one behavioural site changes:
`home.py:2614` `_person_name = car.get_user_originated("person_name")` →
`car.get_pinned_person_name(time)`. The held person is then treated by
allocation exactly like a manual pin (covered car/person,
`_last_persons_car_allocation`) — until expiry. The **unauthorized
branch** (`home.py:2625-2633`) becomes **source-aware** (review A-1/C-17/
D-19, same principle as D4/R4):

```python
if car.get_user_originated("person_name") is not None:
    car.clear_all_user_originated()          # existing behaviour for a user pin
car.clear_system_person_hold()               # always (no-op for a pin-only car, D5)
continue
```

so a hold-only car keeps its user store. **No unknown-person `else`**
(review S-10/C-18 — cut): a hold to a name `get_person_by_name` cannot
resolve is ignored (falls through unpinned, as today) and expires at
`until`; the pre-existing behaviour for an unknown *user* pin is out of
scope. Expiry is evaluated only on the recompute branch, so freedom
arrives at most 3 min after `until`, or immediately on `force_update`.

**Hold lifetime / clear sites** (all call `clear_system_person_hold()`):

| Event | Site |
| --- | --- |
| expiry (`time >= until`) | resolver, on first read (recompute branch) |
| freeze converts forecasted person → user pin | `car.py:319-322` (D5) |
| user person change on this car | `user_set_person_for_car` (slice A′ adds the hold clear; C adds the rest) |
| user takes the person onto another car | `car.py:513-517` loop, **two independent `if`s** (both may fire): `car.get_user_originated("person_name") == new_value` → `clear_all_user_originated()` (unchanged); `car._system_person_hold_name == new_value` → `clear_system_person_hold()`. Loop already skipped for `FORCE_CAR_NO_PERSON_ATTACHED` (`car.py:511`), and a car pinned to the sentinel never equals a real name. |
| physical unplug | `charger.py:3721`, next to `clear_all_user_originated()` (runs before `reset()` at `:3728`) |
| manual reset | `QSCar.user_clean_and_reset` (`car.py:2846`), after `super()` |
| unauthorized person | allocation branch above |

Not cleared on: constraint completion; next day's notification (which
*re-holds* with the new date — the old "returns early forever" behaviour
disappears because the guard is the user pin only).

**Behaviour after expiry:** allocation is free again. If the person really
left, the car is unplugged and everything is cleared anyway. If not, the
next allocation may reassign the person, the person constraint is removed,
and the #352 restore (`charger.py:4352-4373`, `user_target is None` now
true because nothing was promoted) brings the car default back.

### B — the freeze never stores `None` under the target keys

New private helper on `QSCar` (kept as a helper — review D-23: three
covered paths instead of four):

```python
def _stamp_user_target(self, key: str, value: int | float | None) -> None:
    """Store a target as user-originated; a None value stores nothing."""
    if value is not None:
        self.set_user_originated(key, value)
```

Used at `_on_user_originated_changed` (`car.py:309-310`): replace the two
unconditional `set_user_originated` lines with
`if self.can_use_charge_percent_constraints(): self._stamp_user_target("charge_target_percent", self._next_charge_target)`
`else: self._stamp_user_target("charge_target_energy", self._next_charge_target_energy)`.
A percent car therefore never grows a `charge_target_energy` key. An
existing test that asserts the full post-freeze store *including*
`charge_target_energy: None` is asserting the defect — update its
expected dict (review D-26).

Out of scope (review S-3, S-6): no legacy-`None` scrub (a persisted `None`
key is wiped by `clear_all_user_originated` at the next unplug / reset —
self-healing within one plug cycle); `user_set_next_charge_target`
(`car.py:2600-2602`) is **unchanged** — its invalid-value path is not
reachable from the select entity (options come from
`get_car_next_charge_values_options`). `charge_time` keeps its explicit
`None`/sentinel semantics (`car.py:313-317`). The consumer-side `None`
special cases (`charger.py:3858-3865`, home.py guard) are **left in
place** as defensive code; B makes the home.py guard *correct* again
without editing it.

### C — user person change resets the car's person-bound state

`user_set_person_for_car` (`car.py:498-501`), between the
`new_value == get_user_originated("person_name")` early return and
`set_user_originated("person_name", new_value)` — **fields first, then
store** (review C-2/D-1: robust even if a hook were ever added to clears):

```python
self._reset_charge_targets()                       # both target fields → None; no charger I/O
self.clear_system_person_hold()                    # (already added in slice A′)
self.clear_user_originated("person_name")
self.clear_user_originated("charge_target_percent")
self.clear_user_originated("charge_target_energy")
self.set_user_originated("person_name", new_value)  # fires the freeze
```

The freeze then stamps `bump_solar`, `force_charge`, `charge_time` from
the (untouched) fields, leaves the just-set `person_name`, and — via B —
writes no target key. `USER_ORIGINATED_CHARGER_NAME` and a
`CHARGE_TIME_CONSTRAINTS_CLEARED` sentinel already in the store are not
cleared by C and survive the freeze (Facts). The existing
`compute_and_set_best_persons_cars_allocations(force_update=True,
do_notify=True)` call re-allocates; the charger picks the new person's
minimum (or the default) on its next cycle, which also re-runs
`setup_car_charge_target_if_needed` for the native limit.

### Issue re-scoping

The issue's "Expected" ("a person- or system-derived charge target is
never persisted as user intent") is replaced by: *never by a **system**
action* (D1/D2). Options 1 and 2 are rejected. Suggested comment to paste
on #353 at FINALIZE (issue edits are outside this phase's edit scope):

> Plan (QS-353 story): the car freeze on user action is by design and
> stays — a genuine user tap (bump solar, force charge, …) validating the
> displayed person minimum as the user target is **intended**, not a
> defect. The fix is (A′) the daily notification no longer writes
> `person_name` as user-originated — it sets a system hold on the car until
> the announced `predicted_leave_time`, honoured by allocation and cleared
> on expiry / user person change / unplug / reset; (B) the freeze never
> stores `None` under the target keys and stamps only the key matching the
> car's percent capability; (C) a user person change resets the
> person-bound state (person, target keys, hold, target fields) before
> freezing the new choice. Options 1/2 in the issue body are superseded.

## Blast radius / observable behaviour change

- **Allocation**: after the announced leave time (+ ≤ 3 min cache), a car
  that was held is again a free allocation candidate (today: pinned until
  unplug/reset). Between the person constraint's end (floored) and `until`
  (≤ 29 min) the person stays pinned as today. A prediction that moves
  later after the announcement does **not** extend the hold (D3).
- **Charge target**: after a daily notification, the person's minimum is
  no longer reported as a *user* target (`user_target is None` in
  charger.py). Person constraints are unaffected (they are built from
  `person_min_target_charge`, not from the store). ASAP constraints with
  person info keep their person target (`charger.py:4013-4018` already
  keys on `user_target is not None`). **Residual (D1):** a user tap after
  the notification still stamps the displayed minimum as user target.
- **User person change (C/D4)**: a user-typed charge target (e.g. 90 %)
  set *before* picking a person is discarded — the field returns to the
  lazy default and the new person's forecast drives it. Manual charger
  selection and the charge-time CLEARED sentinel survive.
- **Unauthorized pin/hold in allocation**: a hold-only car now keeps its
  user store (today's branch is only reached by user pins, so no change
  for them).
- **UI**: the person select still shows the held person (via
  `current_forecasted_person`, set by allocation).
- **Persistence**: two new keys in the car's extra device info; older
  stores load with no hold and no log; a malformed `until` drops the hold
  with one warning.
- **Not changed**: the freeze on genuine user taps (D1); `charge_time`
  semantics; `user_set_next_charge_target`; the consumer-side `None`
  guards; the #352 restore/clear sites; `QSCar.reset()`; behaviour for an
  unknown *user* pin in allocation.
