## Findings to fix

### [should-fix] U1 — Snap-down doesn't respect the safety floor (`domain_min`)
- File: `custom_components/quiet_solar/ha_model/battery.py:229-237` (`_number_entity_target`, `snap_up=False` branch)
- Severity: should-fix
- Source: qs-review-edge-case-hunter + qs-review-acceptance-auditor (independent reproductions)
- Description: The restore snap-down re-clamps to `ent_min`/`ent_max`
  only; the domain clamp ran before the snap, so the snapped value can
  drop below the floor F. Reproduces when
  `F > floor(max_discharging_power / step) * step` (step doesn't divide
  the configured max and F sits in the last partial step): F=1100,
  configured max=1200, entity step=500, ent_max=6000 → restore request
  1200 → `floor(1200/500)` → landed **1000 < F=1100** — an outage while
  the restore value is pinned gives the house 1000 W instead of the
  guaranteed 1100. The story-legitimized `floor == max` case triggers it
  too: floor=max=5000, step 300 → restore lands 4800 while green-only
  lands 5100 (semantics invert). Write and probe agree (shared helper),
  so the shortfall is silent — this violates the one invariant the
  feature sells.
- Proposed fix: In the `snap_up=False` branch, after the snap + entity
  re-clamps, if the result dropped below the unit-converted
  `domain_min`, snap **up** instead (the safety floor outranks the
  never-raise-a-max preference; safe because `domain_min <= request` by
  the earlier domain clamp; a non-step-aligned write is already accepted
  for the `ent_min` case). Tests: stepped entity with
  `F > floor(max/step)*step` → restore lands >= F; the `floor == max`
  5000/step-300 case → restore and green-only land the same value >= F.

### [should-fix] U2 — Snap-up not capped at the user-configured `domain_max`
- File: `custom_components/quiet_solar/ha_model/battery.py:224-237` (`_number_entity_target`, ceil branch)
- Severity: should-fix (blind-hunter rated must-fix; edge-case-hunter
  bounded it to under one step — consolidated middle)
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter
- Description: The floor's ceil snap is re-clamped to the **entity's**
  `max` but never back to the domain max. Floor 4900 (or floor==max
  5000, explicitly allowed by R9), `max_discharging_power`=5000, entity
  step 300, ent_max 6000 → writes 5100 W > the 5000 W the user declared
  as the hardware limit — contradicting T3's own invariant ("never
  snapped up past the user-configured hardware limit"). The T8 warning
  stays silent (excess < one step).
- Proposed fix: Cap the ceil result at the unit-converted `domain_max`,
  allowing a non-step-aligned write (same posture as the `ent_min`
  case). Combined with U1 this yields the coherent priority order in the
  Summary. Test: floor within one step of configured max, loose
  `ent_max` → write lands <= configured max and >= floor.

### [should-fix] U3 — Silent under-delivery: no warning when landed < requested floor; ent_max-cap branch untested
- File: `custom_components/quiet_solar/ha_model/battery.py:244-257` (+ the cap at :234-235)
- Severity: should-fix
- Source: qs-review-blind-hunter + qs-review-acceptance-auditor
- Description: The T8 warning fires only when the landed value exceeds
  the request. When the entity's `max` forces the landed floor **below**
  the requested safety floor (ceil capped by `ent_max`: floor 4900,
  ent_max 5000, step 300 → capped 4800 < request) — arguably the more
  dangerous direction — nothing is logged. That cap branch
  (battery.py:234-235) is also exercised by no test where it is the
  binding operation.
- Proposed fix: Add the symmetric warning for
  `request_w - landed_w > snap step` (or landed < request at all on the
  snap-up path). One test where the ceil-cap is binding (floor 4900,
  ent_max 5000, step 300 → landed 4800, warning emitted) pins both the
  cap and the accepted under-delivery.

### [nice-to-have] U4 — Unavailable entity defaults the unit to W
- File: `custom_components/quiet_solar/ha_model/battery.py:~204-213` (`_number_entity_target` attribute read)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: When the number entity's state is `unknown`/`unavailable`,
  `attributes` is empty and the unit defaults to W — a momentarily
  unavailable kW entity would get a raw-W write (300 → 300 kW).
  Likely self-healing (the write fails on an unavailable entity and the
  probe recomputes the expected value with fresh attributes on each
  retry once it is back), but verify.
- Proposed fix: Verify the retry path; if a write can actually land with
  stale/empty attributes, skip (or defer) the write while the state is
  `unknown`/`unavailable`; otherwise add a comment documenting why the
  W-fallback is safe. Test only if a real hazard is confirmed.

### [nice-to-have] U5 — "Logged once" claim is false (docstring + concept doc); warning repeats every probe attempt
- File: `custom_components/quiet_solar/ha_model/battery.py:200, 251-257`; `docs/agents/concepts/ha-battery.md:37`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter + qs-review-coderabbit
- Description: The helper runs on every `execute_command` and every
  `check_commands` probe attempt, so a permanently-diverging entity
  (e.g. `min: 1000` vs floor 0) warns on each of the ~4 invocations per
  launch cycle indefinitely — but the docstring and ha-battery.md say
  "logged once".
- Proposed fix: Either dedupe the warning on `(entity_id, landed_w)`
  (one-shot pattern used elsewhere in the codebase) and keep the
  wording, or log only from the write path — and align both the
  docstring and ha-battery.md:37 with whichever behavior ships
  (CodeRabbit's proposed wording diff is in the PR thread).

### [nice-to-have] U7 — `step > ent_max` corner zeroes the floor
- File: `custom_components/quiet_solar/ha_model/battery.py:234-237`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: With `step > ent_max` and no `ent_min` (e.g. kW entity
  `max: 0.05, step: 0.1`, floor 300 W), the step-aligned cap
  `floor(ent_max/step)*step` evaluates to 0 and drags the ceil-snapped
  floor to a 0 write — violating R1's "never zeroed" in this corner,
  even though a raw `ent_max` write would be accepted by HA (core
  validates min/max, not step alignment).
- Proposed fix: On the snap-up path, when the step-aligned cap falls
  below the (converted) request, fall back to raw `ent_max` instead of
  the aligned cap. Test the `step > ent_max` shape.
