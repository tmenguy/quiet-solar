## Findings to fix

### [must-fix] M1 — `cleanup_worktree.py` can rmtree the main checkout or an arbitrary directory
- Files: `scripts/qs/cleanup_worktree.py` (`remove_worktree` ~80–108,
  `_cleanup_with_branch` ~425–453/496)
- Source: qs-review-edge-case-hunter (reproduced in throwaway repos)
- Description: ownership is proven with `rev-parse` *inside* `work_dir`. That
  answers for whatever repo contains the path. When it returns `QS_<N>`,
  `remove_worktree` runs. `git worktree remove` then fails ("is a main
  working tree" / "not a working tree"), and the **unconditional
  `shutil.rmtree(work_dir)` fallback deletes it anyway**. Reproduced cases:
  - Main checkout on `QS_9` with `--work-dir <main> --issue 9 --force
    --delete-branch`: the whole checkout, `.git` included, is deleted, then a
    `FileNotFoundError` traceback follows.
  - `--work-dir <wt>/sub`: `sub/` is deleted and the command reports success.

  The same fallback also sits under the task path when `{{worktree}}` equals
  the repo root.
- Proposed fix:
  - (a) In `remove_worktree`, before any action, refuse without touching
    anything when `work_dir.resolve() == main_wt.resolve()`, or when `work_dir`
    is not a registered **linked** worktree. Use the porcelain
    `_registered_branch(main_wt, work_dir)` and treat `"absent"` as
    not-registered. Return a clear error.
  - (b) Only fall back to `rmtree` after the path has been confirmed as a
    registered linked worktree (e.g. its registration exists, or it existed
    before a `git worktree remove` that partially ran).
  - (c) If the main worktree can't be determined, never rmtree. Return the
    error.
  - (d) In `_cleanup_with_branch`, use the porcelain registration as the
    **primary** ownership proof: kind `branch` equal to `QS_<N>`, or
    `detached` (keep the branch in that case). `rev-parse` is only a
    secondary cross-check.
  - (e) Tests, each asserting the directory still exists and the JSON status
    is `error`:
    - main checkout on `QS_N`;
    - a subdirectory of a linked worktree;
    - an unrelated clone on `QS_N`;
    - main worktree undeterminable.

    Existing removal tests must stay green.

### [should-fix] S1 — Retry path deletes an unrelated branch for a detached registration
- File: `scripts/qs/cleanup_worktree.py` (~296–299, `_retry_branch_delete`)
- Source: qs-review-blind-hunter + qs-review-acceptance-auditor +
  qs-review-edge-case-hunter (reproduced; deduplicated)
- Description: with the dir gone and the stale registration `detached`, the
  retry path prunes and then runs `branch -D QS_<issue>`. A detached
  registration proves nothing, so a mistyped `--issue` deletes an unrelated
  branch. This is inconsistent with the live path, which keeps the branch on
  a detached HEAD.
- Proposed fix: treat `kind == "detached"` like `absent`: prune, then
  `removed-branch-kept` with `branch_delete_error` "registration was
  detached; nothing proves it belonged to QS_<N>". Delete only when
  `kind == "branch" and registered == branch_name`. Add test
  `test_dir_gone_detached_registration_keeps_the_branch`.

### [should-fix] S2 — `sync_body` loses ownership after moving owned lines to a later anchor
- File: `scripts/qs/epic_doc.py` (~752–777, `sync_body`)
- Source: qs-review-edge-case-hunter (reproduced)
- Description: take body
  `"## Children\n\n- (not filed) B\n- (not filed) C\n\nWave 1:\n\n- [ ] #371 — A\n"`.
  - Run 1, with the table unchanged, still rewrites the issue body: it moves
    the owned lines under "Wave 1:".
  - Run 2, after B is filed as #380, has no block directly under the heading,
    so `owned=[]`. It then lists B as both filed and `(not filed)`, which
    never self-heals.
- Proposed fix: consider the section owned when any section block is
  `_owned_by_heading` **or** contains an `_OWNED_RE` line (only `sync_body`
  writes those). Also, when the regenerated owned lines would be identical,
  don't relocate them. An unchanged table must give an unchanged body.
  Prefer re-appending the regenerated `(not filed)` lines to the block that
  already held them, falling back to the anchor. Add a three-run test on the
  body above: no rewrite on run 1, correct lines after filing on run 2,
  no-op on run 3. Existing CRLF, byte-preserve and idempotence tests must
  stay green.

### [should-fix] S3 — Status probe can't show *what* would be lost when it isn't the doc
- Files: `scripts/qs/epic_doc.py` (`cmd_status` ~312–326),
  `scripts/qs/agent_templates/qs-finish-task.md.j2` (~111–115),
  `docs/workflow/lanes/epic-factory.md` (finish rule)
- Source: qs-review-edge-case-hunter
- Description: `safe_to_discard` is false whenever any path changed, but
  `local_modified` and `diff` cover the epic doc only. An uncommitted lane
  edit, an untracked note, or a local commit on another path therefore
  yields a force-delete prompt with nothing to show.
- Proposed fix: add `"changed": [...]` (the changed paths) and
  `"unpushed_commits": <int>` (`rev-list --count origin/main..HEAD`) to the
  status payload. The finish template and the lane doc list `changed` and
  `unpushed_commits` in the force-delete prompt. Add tests, and pin the
  template wording in `test_lane_steps_parity.py`.
