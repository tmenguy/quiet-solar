### [should-fix] R2-S1 — boot-guard store wipe can erase a user action made after the restart
- File: `custom_components/quiet_solar/ha_model/charger.py:3684-3688` (`_lift_boot_user_pin_if_car_unplugged`), `car.py:393` (`_on_user_originated_changed`), `charger.py:3644-3648` (guard disarm)
- Severity: should-fix (regression introduced by fix #01 S1)
- Source: qs-review-edge-case-hunter
- Description: the guard only disarms when this charger's own `USER_ORIGINATED_CAR_NAME`
  is written; a user action on the car pins only the charger it is attached to (and none
  while `car.charger is None`). The unplug proof needs recorder history and can land late
  in the boot window (~30 s + `CHARGER_BOOT_TIME_DATA_EXPIRATION_S`). When it lands, S1
  now wipes the whole car store — including a freeze, target %, force/timed charge or
  person pin the user set after the restart. Scenario: car X pinned on charger A, moved
  to charger B while HA was down; after boot X attaches to B; user sets 100 % on X's card
  (pins B, freezes X); A's guard still armed → proof lands → X's fresh store is wiped →
  person constraint pushed on B and the user's 100 % overwritten by the person need — the
  original QS-431 symptom. Same if the user acts on X in the first 30 s (no charger yet).
- Proposed fix: the store wipe must only erase pre-restart user state. Track a post-boot
  user action on the car (e.g. an in-memory, non-persisted flag or timestamp set in
  `QSCar._on_user_originated_changed` outside `_USER_REPLAY_FOR_INIT`); when the car had
  a genuine user action since boot, the guard falls back to the pre-S1 behaviour (lift
  only the pin keys it lifted before) and leaves the car store — and its freeze — intact.
  Red test: the scenario above (user action on X after boot, proof lands afterwards) →
  `is_user_frozen()` still True and the user's target marker kept; plus the existing S1
  test (no post-boot action) stays green.

### [should-fix] R2-S2 — a one-off plug-sensor flap now erases the user's whole car state
- File: `custom_components/quiet_solar/ha_model/charger.py:3684-3688`, `_car_unplugged_since` (~`charger.py:5321`); live path for comparison `charger.py:4352-4371`
- Severity: should-fix (regression introduced by fix #01 S1)
- Source: qs-review-edge-case-hunter
- Description: the boot proof is a single on→off transition of the car's plug sensor
  with no duration, whereas the live unplug branch S1 claims parity with is gated on the
  charger's debounced `is_not_plugged(time, for_duration=CHARGER_CHECK_STATE_WINDOW_S)`.
  Before S1 a spurious proof only lifted the charger pin (car usually re-selected); now
  it erases the freeze, target, force/timed charge and person pin. Scenario: the car
  stays plugged at A during the downtime but its car-API plug sensor flaps on → off → on
  (car asleep / API glitch) → boot proof fires → user state silently dropped, where the
  live path would have ignored the glitch.
- Proposed fix: gate the **car-store wipe** (not the pre-existing pin lift, whose QS-416
  contract stays unchanged) on a debounced unplug: the off state that follows the on→off
  transition must have lasted at least `CHARGER_CHECK_STATE_WINDOW_S` (same debounce as
  the live path), read from the same history `_car_unplugged_since` already uses. A
  shorter off span keeps the store (pin-lift only, as before S1). Red test: on → off
  (shorter than the window) → on during downtime → freeze and markers kept; the existing
  S1 test (sustained off) still unfreezes.

### [nice-to-have] R2-N1 — charger-card reset only half-mirrors the car-card reset
- File: `custom_components/quiet_solar/ha_model/charger.py:2691-2699` (`QSChargerGeneric.user_clean_and_reset`); reference `car.py:3050-3068` (`QSCar.user_clean_and_reset`)
- Severity: nice-to-have (raised by both qs-review-edge-case-hunter and qs-review-regression-proof — merged)
- Description: S2 clears the car's user store after `super().user_clean_and_reset()` has
  wiped the constraints, so `_clear_leaked_person_target_if_needed()` can no longer act,
  and it skips `clear_system_person_hold()`, `current_forecasted_person = None`,
  `_reset_charge_targets()` and the person allocation re-run that the car-card reset
  performs. Scenario: user pinned person P and set 100 %, presses the charger-card reset
  → car unfrozen and markers gone, but `_next_charge_target` stays 100 with no marker and
  `current_forecasted_person` is still P → next cycle pushes a person constraint for P.
- Proposed fix: before `super().user_clean_and_reset()`, call
  `self._clear_leaked_person_target_if_needed()` (constraints still present); after it,
  apply the car-side reset steps of `QSCar.user_clean_and_reset` that do not recurse
  into the charger (system-hold clear, forecasted-person clear, charge-target reset,
  allocation re-run). If that means sharing code with `QSCar.user_clean_and_reset`,
  extract the car-side steps into one small car helper called by both (justify in the
  progress note); do not call `car.user_clean_and_reset()` (it recurses). Extend
  `test_charger_card_reset_unfreezes_car` (or add a test) for the forecasted-person and
  charge-target outcome.

### [nice-to-have] R2-N2 — hysteresis lets the person target lag below the need
- File: `custom_components/quiet_solar/ha_model/charger.py:4945-4950`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: with "rounded % changes AND |Δ| >= 0.5" an in-place person target can sit
  up to ~1 % below the need (ct 80.4 vs need 80.6 → no rewrite); when the lagging ct is
  met it is acked, then re-pushed at the exact need — an extra met → ack → re-push round
  trip (and possibly a notification) instead of a quiet update.
- Proposed fix: asymmetric hysteresis — an **upward** move that changes the rounded %
  always rewrites; a **downward** move needs the rounded % to change and |Δ| >= 0.5.
  Jitter stays suppressed (at most one upward flip per boundary crossing). Red test:
  ct 80.4, need 80.6 → rewritten to 80.6; keep
  `test_person_target_rounding_jitter_does_not_rewrite` and
  `test_person_target_sub_percent_drift_does_not_rewrite` green (adjust the jitter
  fixture only if it relies on an upward flip being suppressed — justify in the note).
  Update the charger-budgeting doc sentence.
