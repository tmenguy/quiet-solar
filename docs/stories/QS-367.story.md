## Problem

QS-358 pinned the `deep` class to **Opus 4.8** on both harnesses (D3)
because Opus 5 over-reaches against our prompts, and deferred **Opus
5.5** (`claude-opus-5-5`, released 2026-09-22) in D21: Claude Code
2.1.278 rejects it, and nothing showed its scope discipline had
improved. The user now wants Opus 5.5 in the Claude harness (this
issue), and asked to revisit the whole table in its light.

### Research (2026-09-23)

- **Opus 5.5 ≈ Fable 5.1, at 40 % of the price.** Anthropic: *"performs
  at the level of Claude Fable 5.1 on most work"*; models overview:
  *"start with Claude Opus 5.5 … for most workloads"*, Fable 5.1 *"for
  demanding reasoning and long-horizon agentic work, or when your
  evals on Claude Opus 5.5 at higher effort still fall short"*. Price
  $4/$20 vs Fable $10/$50 per MTok; both 1M context. Anthropic's table
  has 5.5 ≥ Fable 5.1 on every row (Terminal-Bench 4.0 66.4 vs 55.8,
  FrontierCode 54.4 vs 50.3, HLE 67.7 vs 65.6 …), with the caveat that
  margins are *"a less reliable guide to real-world differences"*.
  ([overview](https://platform.claude.com/docs/en/about-claude/models/overview),
  [announcement](https://www.anthropic.com/claude-opus-5-5))
- **Code review is its strength — and it finds different bugs.**
  Anthropic: 72 % of known bugs vs Opus 5's 56 %, fewer false alarms.
  CodeRabbit (independent): 51/80 vs 49/80 baseline, 10/13 vs 5/13 on
  hard cases, same precision, and it *"finds a different mix of
  bugs"* — the basis for E4/E5's model mix (behavioural, not cosmetic,
  diversity).
  ([CodeRabbit](https://www.coderabbit.ai/blog/opus-5-5-model-review))
- **Scope discipline is *not* shown fixed.** Every: 5.5 wrote *"251
  lines across 17 files"* where the human fix was 171/14, and on a
  timed task built extras and never delivered the ask. No Anthropic
  statement on scope. This is D3's reason, still standing for
  implementers.
  ([Every](https://every.to/vibe-check/vibe-check-opus-5-5-is-pulling-our-codex-converts-back-to-claude))
- **Effort:** 5.5's default is `medium`, which *"matches or exceeds
  Claude Opus 5 at `high`"* on **coding** (migration guide). No evidence
  compares 5.5 `medium` to Opus 4.8 `high` on **review/critique** — so
  this story keeps `high` (E2).
- **OpenAI GPT-6 Sol / Luna** (2026-09-22): cheaper tiers under GPT-6
  Astra (Sol $2/$10 "everyday work", Luna $0.10/$0.50 "volume"). Listed
  by `opencode models` as `github-copilot/gpt-6-sol` /
  `github-copilot/gpt-6-luna`; Copilot rollout "gradual"; no
  code-review data. `github-copilot/claude-opus-5.5` is listed too;
  still no Fable on that provider.

### GUI model selection (observed while planning, 2026-09-23)

- The **GUI model picker decides the main session's model**. This
  planning session (pinned to `qs-create-plan`, frontmatter
  `claude-fable-5-1`) ran on **Opus 5.5** — the picker's choice. With
  `"model": "haiku"` added to `.claude/settings.local.json`, a **new**
  GUI session still did not switch. Neither frontmatter `model` nor a
  settings `model` key beats the picker. (The experiment's `model` key
  is removed by the user before implementation — it is local,
  gitignored state, not part of this change.)
- The pinned **`effortLevel` is honoured** by the GUI (it switches).
- Mechanism (the app's session records,
  `~/Library/Application Support/Claude/claude-code-sessions/*/*/local_*.json`):
  each session stores an explicit `model` (no inherited flag exists
  for it), while effort carries `effortInherited: true` — the app
  passes the picker's model explicitly, the GUI analogue of `--model`.
  No repo file can win (`.claude/settings.json` ranks below
  `settings.local.json`, which already lost). The app bundles Claude
  Code 2.1.280.
- **Sub-agents are unaffected:** from this GUI session (main on Opus
  5.5) a spawned `qs-plan-delta-auditor` reported `claude-sonnet-5` —
  its frontmatter. Only the **main session** of a GUI phase follows the
  picker, with no hint today of which model to pick.
- `docs/workflow/harness.md` claims full IDs in frontmatter work for
  "settings-pinned (GUI) sessions" — wrong for the desktop app.

## Goal

Re-cut the model table so each agent runs the model the evidence
favours for its role — Opus 5.5 where analysis and review dominate,
Opus 4.8 where patch footprint matters, Fable 5.1 where long-horizon
reasoning and reviewer diversity matter — on both harnesses; and make
the Claude GUI's manual model pick explicit at every handoff.

## Decisions

- **E1 — New class `build` = the implementer's model.** `qs-implement-task`,
  `qs-implement-setup-task` (and `qs-plan-dev-proxy`, E4) → `build`.
  Claude `claude-opus-4-8`, OpenCode `github-copilot/claude-opus-4.8`,
  effort `high` (today's implementer settings, unchanged). This is
  D21's pre-planned fallback ("split `deep` into an implement class
  (4.8) and a review class (5.5)"), taken now on the Every footprint
  evidence rather than after an A/B. Class vocabulary: `build` — *runs
  the implementer's model: contained, small-footprint code changes*
  (covers the implementers and their proxy).
- **E2 — `deep` → Opus 5.5 on both harnesses, effort stays `high`.**
  Claude `claude-opus-5-5`, OpenCode `github-copilot/claude-opus-5.5`
  (now on the provider, so no asymmetry). `CLASS_EFFORT["deep"]` is
  **unchanged** (`high`): the only effort evidence is 5.5 vs Opus 5 on
  coding, not vs 4.8 on review; lowering it later is one cell once 5.5
  has a track record here. `deep` keeps: `qs-plan-critic`,
  `qs-plan-concrete-planner`, `qs-diag-root-cause-skeptic`,
  `qs-review-blind-hunter`, `qs-review-edge-case-hunter`, and the
  bug-lane / no-lane planning orchestrators. Vocabulary: `deep` —
  *the best code-grounded analyst: critique, concrete planning,
  hunting, root cause*.
- **E3 — `opencode.json` follows `deep`** → `github-copilot/claude-opus-5.5`
  (the project default for agent-less sessions; Anthropic's "start with
  5.5 for most workloads"). The lockstep test keeps pinning it to the
  OpenCode `deep` row — no test change beyond the value.
- **E4 — Plan fan-out keeps three models (D2).** Moving both
  `frontier` plan reviewers to 5.5 would put all four global plan
  reviewers on one model. Instead:
  - `qs-plan-dev-proxy` `frontier` → **`build`** (Opus 4.8): it
    simulates the implementer, so it runs the implementer's model.
    A plausibility call, not measured — **revisitable** as one `_FLAT`
    row if its findings thin out;
  - `qs-plan-scope-guardian` stays `frontier` (Fable 5.1): pure
    reasoning lens, and the third model in the fan-out.
  - Resulting plan fan-out on Claude: critic 5.5 · concrete-planner
    5.5 · dev-proxy 4.8 · scope-guardian Fable · delta-auditor Sonnet 5.
- **E5 — `frontier` unchanged** (Fable 5.1 / `gpt-6-astra`, `high`):
  feature-lane planning orchestrator (the user's call), review/verify
  consolidators, `qs-diag-fix-minimalist`,
  `qs-review-acceptance-auditor`, `qs-review-regression-proof` — the
  latter two stay off 5.5 so the code-review fan-out also mixes models
  (hunters 5.5 · auditors Fable · CodeRabbit external), on the
  "different mix of bugs" evidence. Moving the consolidators to 5.5
  for cost is a possible later table change, not this story.
- **E6 — withdrawn (review round 1, K4).** With `deep` effort kept at
  `high`, every planning class still shares effort, the D16 tripwire
  (`test_planning_classes_share_effort`) stays green and untouched, and
  no pinned `effortLevel` changes anywhere.
- **E7 — The Claude GUI handoff names the model to pick.** The Claude
  launcher's `build_payload` already resolves the next phase's class
  (for the pinned effort); it now also emits **`phase_model`** =
  `models.model_for("claude", cls)`, unconditionally. Every `[Claude
  Code GUI]` block (7 orchestrator templates, 9 blocks) gains one
  bullet telling the user to select `{{phase_model}}` in the model
  picker. When `phase_agent_pinned` is `false` the whole GUI block is
  dropped (existing rule), so the key then simply has no reader — not
  specified or tested further. No `model` pin (dead config — observed
  above; D20). OpenCode/Codex launchers unchanged.
- **E8 — Claude Code ≥ 2.1.280 is a prerequisite for the smoke only.**
  The shell `claude` on `PATH` (the binary the implementer's Bash tool
  runs — not the app's bundled one) is 2.1.278 today. Tasks 1–6 are
  pure code/test/doc edits and proceed regardless. **Hard gate
  immediately before task 7**: parse `claude --version` (`X.Y.Z (Claude
  Code)`) as a version tuple; if < (2, 1, 280), stop, ask the user to
  upgrade, run no smoke, open no PR. Until upgraded, `deep` sub-agents
  spawned from a CLI session 400 — the reason for the gate.
- **E9 — GPT-6 Sol / Luna deferred.** One day old, gradual Copilot
  rollout, no review data, and using one as a cross-vendor OpenCode
  reviewer needs per-agent vendor mixing the class-per-harness policy
  does not express. Recorded here only; no follow-up issue is filed by
  this story (the user files one if/when wanted).
- **E10 — D21's A/B revisit is closed** by this story (prose record, no
  task): 5.5 is adopted for analysis/review on the research above; the
  implementer stays on 4.8, which is exactly the part the A/B would
  have tested.
