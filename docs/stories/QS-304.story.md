## What the user sees after this PR alone

Stated up front because it is narrower than the issue's symptom:

- one push notification when QS loses control of a load, and a `PROBLEM` binary
  sensor that stays on until control returns;
- ≈514 ERROR lines/hour/load eliminated while an incident lasts (9 557 across the three
  observed episodes; the largest single episode is 4 248);
- a retry every 300 s, forever, instead of silence after 17.5 min;
- **the load itself may still be ON.** Pool House needs #305 (its retries are
  no-ops against an already-`off` boolean); the Cumulus Enfants device refuses
  real `number.set_value(0)` calls and is out of scope by decision.

#305 is a co-requisite for the user-visible fix, not a follow-up.

## Problem

Two loads stayed physically ON for hours after their constraint was met and after
QS had decided to switch them off: **Cumulus Pool House**
(`switch.lhk_cumulus_pool_house_facade`, 100 % met at 15:00, still consuming at
19:02) and **Cumulus Enfants** (`switch.cumulus_enfants_boost`, stuck ON from the
early afternoon).

### Root cause

`AbstractDevice` (`home_model/load.py`) holds one in-flight command in
`running_command`. There is **no terminal state** for "the probe works and keeps
returning `False`" — the device answers, it just never reaches the target state:

| Where | Behaviour |
| --- | --- |
| `launch_command` (`load.py:625-636`) | early-returns and **stacks** whenever `running_command is not None` |
| `check_commands` (`load.py:730`) | promotes `_stacked_command` **only when `running_command is None`** |
| `check_commands` (`load.py:719`) | a give-up exists **only** for probe `None` (`NUM_MAX_INVALID_PROBES_COMMANDS`) |
| `QSHome.check_loads_commands` (`home.py:2871`) | ladder `wait_time > 50*(n+1)` while `n < 6`; at `n == 6` it **only logs ERROR** and never frees the slot |

`running_command` is cleared **only** by `_ack_command`. So once the 6-rung ladder
is spent the load is **permanently bricked**: every later command is silently
overwritten into `_stacked_command`, and no retry is ever attempted again. The only
exits are the device spontaneously complying, or an HA restart.

first load-management cycle after its deadline, and the cycle is ~7 s over 6 rungs.

## Goal

1. A load whose command never converges must **never** become uncommandable.
2. A newer desired command must **supersede** a stale in-flight one instead of
   starving behind it, without becoming a service-call storm.
3. When QS has lost control, **shout loudly**, through state that cannot get stuck.
4. Replace the per-cycle ERROR spam with one line in, one line out.

### Non-goals — deliberately not touched

- **Power accounting, group power subtraction, amp budgeting and consumption
  history.** A device misbehaving briefly must not perturb
  `home_non_controlled_consumption` or the persisted forecast. `is_load_command_set`
  is therefore **not modified**, and AC7 pins the absence of collateral damage.
- **User-override detection un-freezing → #307.** Deferred *because* it is not
  side-effect-free: opening that gate lets `external_user_initiated_state` be set,
  which flips `is_user_overridden()`, which is read by `device.py:881`,
  `dynamic_group.py:189/218/245` and `home.py:1723` — the same consumption
  computation this story must not move. It is also pre-existing: today's spent
  ladder already leaves `running_command` set forever.
- Making a disobedient device obey (#305 for Pool House; Enfants dropped).
- Solver code, `SOLVER_STEP_S`, constraint semantics.
- The `NUM_MAX_INVALID_PROBES_COMMANDS` (probe returns `None`) path — a different
  code path; left exactly as-is, including its `_ack_command(time, None)`.
- The pre-existing per-cycle `check command` / `force launch command` INFO lines
  (#306).

## Design

New members go on **`AbstractDevice`** (next to `is_load_command_set` at
`load.py:691`), except the `_notify_unresponsive` override which goes on
`AbstractLoad` (after `on_device_state_change` at `load.py:1153`). This matters
because `check_loads_commands` also drives `self.battery`
(`home.py:2856-2860`), and `QSBattery` is `AbstractDevice`-side.

### 1. The ladder saturates instead of terminating

Two constants, both keeping today's values, so nothing changes for a healthy
device:

```python
COMMAND_RELAUNCH_BASE_DELAY_S = 50   # was hardcoded 50 in home.py
NUM_MAX_COMMAND_RELAUNCH = 6         # was hardcoded 6, meaning "give up"
SUPERSEDE_MIN_INTERVAL_S = COMMAND_RELAUNCH_BASE_DELAY_S * NUM_MAX_COMMAND_RELAUNCH  # 300
```

```python
def command_relaunch_delay_s(self) -> float:
    """Linear backoff that saturates instead of running out: 50, 100, 150,
    200, 250, 300 for relaunch count 0..5, then 300 s forever."""
    return COMMAND_RELAUNCH_BASE_DELAY_S * min(
        self.running_command_num_relaunch + 1, NUM_MAX_COMMAND_RELAUNCH
    )
```

Callers must wrap it: `wait_time` is a `timedelta` (`check_commands` returns
`time - running_command_last_launch`, `load.py:727`), so the comparison is
`wait_time > timedelta(seconds=self.command_relaunch_delay_s())` — mirroring
today's `home.py:2871`. The 1050 s figure holds only because `wait_time` is
anchored on `running_command_last_launch`, not `first_launch`.

`NUM_MAX_COMMAND_RELAUNCH` stops meaning "give up" and starts meaning "the rung at
which the delay stops growing". Two distinct indices, deliberately named apart:
the **delay** stops growing at `n == 5`; the **uncontrollable threshold** is
`n >= 6` (cumulative 1050 s), and lives in `check_and_relaunch_command`.

### 2. One durable clock, and it cannot stick

```python
self.unresponsive_since: datetime | None = None   # init in AbstractDevice.__init__,
                                                  # immediately before load.py:165's
                                                  # _ack_command(None, None).
                                                  # NOT added to
                                                  # constraint_reset_and_reset_commands_if_needed.

@property
def is_uncontrollable(self) -> bool:
    """QS has given up on an in-flight command and is still retrying it."""
    return self.unresponsive_since is not None and self.running_command is not None
```

The `running_command is not None` conjunct is load-bearing, and it is the fix for a
hole an earlier draft had. Two reachable paths empty the slot with no successor:

- a superseding command that equals the preserved `current_command` hits the
  early-return at `load.py:654` — nothing is launched, nothing is in flight (this
  is exactly the Pool House 12:23 shape);
- `force_relaunch_command`'s override-suppression drop (`load.py:746-761`) sets
  `running_command = None` and returns.

In both, an `unresponsive_since`-only property would stay `True` forever with no
retry able to clear it — the sensor pinned on, the recovery edge unreachable.
Requiring something in flight makes "not stuck" structural rather than a list of
clear-conditions: if we are not waiting on anything, we are not uncontrollable.

There is a **third** path, and it is the one that matters: the
`NUM_MAX_INVALID_PROBES_COMMANDS` give-up calls `_ack_command(time, None)`, which
empties the slot while the guard below leaves `unresponsive_since` set. The probe
has gone *unavailable* — the device is failing harder, not recovering — so
clearing there would be a genuine false "recovery". The empty-slot clear therefore
runs **only when `current_command is not None`**, which that path has just nulled.
(The other two paths are legitimate clears: at `:654` the device already matches
the newly-desired command, and an override drop means the user took control.)

Clearing and logging live in one place — a private
`_clear_unresponsive(self, time, reason) -> None` on `AbstractDevice` that does
guard + clear + the single INFO. Both `_ack_command` (guarded on
`command is not None`, because `_ack_command(None, None)` is called from
`AbstractDevice.__init__` at `load.py:165`) and `check_and_relaunch_command` call
it, so AC9's "exactly one INFO" has one writer rather than two that can drift.

The empty-slot clear runs at the **very end** of `check_and_relaunch_command`,
after both `check_commands` and any `force_relaunch_command`. Position is
load-bearing: earlier, and it fires on a load that `check_commands` is about to
re-arm by promoting `_stacked_command` (`load.py:730`).

Its real purpose is **re-arming**, not logging: the entry guard is
`unresponsive_since is None`, so without the clear a load that loses control,
recovers via an empty-slot path, then loses control again would never notify a
second time. The INFO is the side effect.

**The empty slot must also reset the rung** (implementation finding). Alongside
the clear, `running_command_num_relaunch = 0` whenever
`check_and_relaunch_command` ends with `running_command is None`. The invariant is
**an empty command slot implies rung 0**: the rung counts relaunches *of the
in-flight command*, so with nothing in flight it describes a command that no
longer exists.

Without it there is a live bug. §3 has `abandon_running_command` preserve the
rung, which is right when a successor is launched in the same `launch_command`
call — but the two abandon paths with **no** successor (the `load.py:654`
equal-command early-return and `launch_command`'s override-suppression drop) leave
the rung at 6 with an empty slot. The clear then re-arms `unresponsive_since`, and
the *next*, unrelated command inherits rung 6: `_escalate_or_recover` declares lost
control on its **first cycle**, after zero relaunches, emitting a false
`"command off not confirmed after 6 relaunches"` ERROR and a spurious push. That
breaks AC9's one-push-per-episode and R5's ~1050 s bound.

Note the reset is placed outside the `current_command is not None` guard: the
unavailable-probe give-up deliberately keeps `unresponsive_since` (see above) but
must still not leave a poisoned rung behind. It is unconditional on the empty
slot, and a no-op on every other path (`_ack_command` and the
`force_relaunch_command` override drop already zero it).

This is why AC6's "clears the four named counters" must be read as §3 spells it out
— three fields plus `running_command`, with the rung preserved — and **not** as
"the rung is cleared on abandon". The rung is cleared one layer up, by the
empty-slot rule, only when nothing succeeded it. The consequence for the service
call rate is quantified in **R3**.

`_last_supersede_time: datetime | None = None` is initialised beside
`unresponsive_since` and **not** in `constraint_reset_and_reset_commands_if_needed`;
`None` means the first supersede is unthrottled. A *throttled* supersede must not
update it (or the window never opens), and `_clear_unresponsive` resets it, so a
stale timestamp cannot delay the first supersede of the next episode.

### 3. Abandon without faking an ack

```python
def abandon_running_command(self, time: datetime, reason: str) -> None:
```

Clears `running_command` and three of the four relaunch tracking fields —
`running_command_num_relaunch_after_invalid`, `running_command_first_launch`,
`running_command_last_launch`. **Preserves** `current_command`, `prev_command`,
`num_on_off`, `unresponsive_since`, `_last_supersede_time` and — critically —
**`running_command_num_relaunch`**.

Preserving the rung is not cosmetic. `command_relaunch_delay_s()` derives from
that counter, so zeroing it would restart the ladder at 50 s after every
supersede: relaunches at +50, +150, +300 s *inside* each 300 s throttle window,
≈4 service calls per window ≈1 150/day rather than R3's 288 steady-state floor.
That is the
same counter-reset trap §4 documents for the throttle, one layer down — four
reviewers found it independently. Preserving the rung keeps the saturated 300 s
cadence across supersession, which is what makes R3 and AC4 true as written.
`_ack_command` still resets the counter on a real ack, so a recovered device
starts a fresh ladder. It does **not** touch `_stacked_command` (see §4).
`reason` is used only in one lazy log line at DEBUG.

Preserving the rung is sound **only while a successor is launched in the same
`launch_command` call**, with no load-management cycle in between. The two abandon
paths that leave no successor are handled by §2's empty-slot rung reset — read the
two together; neither is correct alone.

`force_relaunch_command`'s override-suppression drop (`load.py:954-969`) **is** an
abandon and now calls this method instead of hand-rolling the same five
assignments, then explicitly zeroes the rung. The two drops differ in exactly that
one respect, and deliberately: a supersede protects the retry cadence, whereas an
override drop means the *user* took control, so the next command deserves a fresh
ladder rather than an inherited rung.

Preserving `current_command` is the crux: it means *last **confirmed** command*.
The `idle` was never confirmed, the device really is still `on`, so `on` is the
truth. `_ack_command(time, None)` would null it and additionally leak an on/off
transition out of the `num_max_on_off` budget (it sets `prev_command = current_command`,
so the next real ack sees `prev_command is None` and skips the count). The
override-suppression drop at `load.py:752-761` already preserves `current_command`
for the same reason and documents it.

### 4. Supersession — two cases, one throttle

| Incoming vs running | Load state | Action |
| --- | --- | --- |
| **equal** (`==`) | any | absorbed; `_stacked_command` cleared at `load.py:629`; no service call |
| **differs** | not uncontrollable | stacked — today's behaviour |
| **differs** | uncontrollable | supersede, **at most once per `SUPERSEDE_MIN_INTERVAL_S`**; inside the window the incoming command replaces `_stacked_command` (last-wins) and no service call is made |

An earlier draft exempted a change of command *kind* from the throttle, on the
argument that delaying `idle` → `on` by up to 300 s "would be a regression".
Measured against today that is false: today an uncontrollable load gets **nothing,
ever**, so a ≤300 s delay is a strict improvement. The exemption is dropped, which
also removes an `is_like`-based third case that was unsafe anyway — `is_like`
compares only the command string (`commands.py:48-51`), so `off` vs `idle` and a
charger's `auto_green` / `auto_green_cap` / `auto_consign` all count as different
"kinds" and would have been un-throttled.

**The throttle must not read the relaunch counter.** `command_relaunch_delay_s()`
derives from `running_command_num_relaunch`, which the empty-slot rule (§2) zeroes
— so anchoring the throttle there collapses the window to 50 s (~1 728 calls/day,
against R3's 288 steady-state floor). It uses a dedicated `_last_supersede_time`
compared against
the constant `SUPERSEDE_MIN_INTERVAL_S`. This is also why the invariant is stated
once and kept: **anything meaning "we have lost control" reads
`is_uncontrollable`, never the counter.**

Storm evidence: `LoadCommand.__eq__` correctly compares `power_consign`
(`commands.py:32`) — a consign change *is* a new command, and for a healthy load it
goes through immediately, exactly as today. But Cumulus Enfants received `on` at
**1761 → 521 → 534 → 536 W** on successive ~7 s cycles; each is unequal to the
last, so without the throttle an uncontrollable load would execute every cycle.

`launch_command`'s current block (`load.py:625-636`) `return`s on every branch, so
reaching the fall-through requires restructuring it. The replacement, so this can
be reviewed here rather than in the PR:

```python
if self.running_command is not None:
    if self.running_command == command:
        self.running_command = command
        self._stacked_command = None
        return
    if not self.is_uncontrollable:
        self._stacked_command = command
        return
    if (self._last_supersede_time is not None
            and (time - self._last_supersede_time).total_seconds() < SUPERSEDE_MIN_INTERVAL_S):
        self._stacked_command = command      # last-wins; retried next window
        return
    self._last_supersede_time = time
    self.abandon_running_command(time, reason="superseded")
    # fall through

self._stacked_command = None                 # existing load.py:639
```

`_stacked_command` clearing stays on the fall-through line and is not duplicated
inside `abandon_running_command`. Note the fall-through then reaches the existing
override check and the `current_command == command` early-return — so a supersede
whose incoming command equals the preserved `current_command` performs no service
call, which is correct (the device already matches what is now wanted) and is why
`is_uncontrollable` needs the in-flight conjunct.

No flicker or race: `abandon → fall-through → early-return/launch` contains **no
`await`**, so no other task can observe the momentarily-empty slot.

### 5. Perpetual retry from the pure layer

```python
async def check_and_relaunch_command(self, time: datetime) -> bool:
    """Probe, ack-or-relaunch, escalate. Returns command_acked_or_good for
    QSHome.check_loads_commands' all_ok aggregation."""
```

Relaunch whenever `wait_time > command_relaunch_delay_s()`, forever. The threshold
crossing, **after** awaiting `force_relaunch_command`:

```python
if (self.running_command is not None
        and self.running_command_num_relaunch >= NUM_MAX_COMMAND_RELAUNCH
        and self.unresponsive_since is None):
    self.unresponsive_since = time
    _LOGGER.error("Lost control of load %s: command %s not confirmed after %s relaunches",
                  self.name, self.running_command, self.running_command_num_relaunch)
    await self._notify_unresponsive(time, self.running_command)
```

The `unresponsive_since is None` guard is the once-only mechanism. `>=` not `==`,
because the counter is resettable.

- `check_commands` may run **twice** per invocation (once directly, once via
  `force_relaunch_command`'s `else` at `load.py:785`) — unchanged from today. The
  ladder counter is unaffected: `check_commands` increments only
  `running_command_num_relaunch_after_invalid` (`load.py:715`), while the ladder
  counter advances solely in `force_relaunch_command` (`load.py:766`). So the
  1050 s calibration holds.
- Non-re-entrancy of `check_and_relaunch_command` is guaranteed by the single
  load-management task, not by a lock.
- The counter already advances on an exception — `running_command_num_relaunch += 1`
  sits at `load.py:766` *before* the `try`, and `running_command_last_launch` is set
  outside the `except`. AC5 is a **regression guard** on that existing behaviour
  while the ladder moves, not a new fix. Use `try/finally` if restructuring, never a
  bare `except Exception` (project rule).
- Return contract: today's spent-ladder path returns whatever `check_commands`
  returned and only logs. AC8 pins that a permanently-uncontrollable load does not
  change off-grid behaviour; `test_finish_off_grid_switch_loads_not_ready` is in the
  affected set, so this path is live.

`ha_model/home.py:check_loads_commands` becomes a thin driver: call
`check_and_relaunch_command`, keep the `all_ok` aggregation and the per-load
`try/except`. The per-cycle `_LOGGER.error` is deleted.

### 6. Shout loudly

**Why `qs_enable_device` is not reused.** Its setter (`load.py:361-380`) calls
`self.reset()`, `home.remove_device(self)` and `home.add_disabled_device(self)`, and
the switch is a `QSSwitchEntityWithRestore` — **persisted**. Auto-flipping it would
stop QS probing the load entirely, so no ack could ever arrive and no evidence
could ever clear it: permanent and sticky, in the same field as a manual disable.

| | `qs_enable_device is False` | `is_uncontrollable` |
| --- | --- | --- |
| Origin | **manual only** — QS never writes it | automatic |
| Storage | persisted | derived, in-memory |
| Reset | user only, honoured forever | automatic, when control returns |
| Effect | load leaves the home | load stays in, keeps being retried |

`qs_enable_device` also remains the user's manual off-switch for the retries. Note
it calls `reset()`, which does not clear `unresponsive_since` — but disabling also
stops the retries, so `running_command` goes to `None` and `is_uncontrollable` is
`False` via the conjunct. No special case needed.

**Binary sensor.** `BINARY_SENSOR_LOAD_UNCONTROLLABLE = "qs_load_uncontrollable"`
in `const.py`, `device_class = BinarySensorDeviceClass.PROBLEM` (precedent
`binary_sensor.py:68`, and the class name lives in `binary_sensor.py` so `const.py`
stays HA-import-free). Needs a new `create_ha_binary_sensor_for_AbstractLoad`
helper plus `if isinstance(device, AbstractLoad): ret.extend(...)` in
`create_ha_binary_sensor` (`binary_sensor.py:136-152`) — there is no `AbstractLoad`
branch today — and `AbstractLoad` added to the `.home_model.load` import at
`binary_sensor.py:31`. It **must** pass an explicit
`value_fn=lambda d, key: d.is_uncontrollable`: `QSBaseBinarySensor.async_update_callback`
falls back to `getattr(device, key, False)` (`binary_sensor.py:219-222`) and `key`
is not the property name, so without it the entity is pinned `False`.
`isinstance(device, AbstractLoad)` (the bare form, per the `switch.py:105`
precedent) correctly excludes `QSHome`, `QSBattery`, `QSCar`, `QSSolar`,
`QSPerson` and `QSHeatPump` (`PilotedDevice`, hence `AbstractDevice`-side).
Conversely **every `QSChargerGeneric` and every `QSBiStateDuration` subclass gains
one extra binary sensor** — including the water boilers, pool and radiators, i.e.
exactly the population that hit this bug. Task 12 checks that against existing
entity-count and dashboard assertions.

**Notification.** One push on entry, via the existing
`AbstractLoad.on_device_state_change(time, DEVICE_STATUS_CHANGE_ERROR, message=...)`
(`load.py:1153-1156`, overridden by `HADeviceMixin` at `device.py:701-704`).
`DEVICE_STATUS_CHANGE_ERROR` (`const.py:379`) must be added to `load.py`'s
`..const` import list — it is not there today.

There is **no recovery push and no dismissal**: the channel is a fire-and-forget
mobile push (`Platform.NOTIFY`, `device.py:752-757`) with no notification id, and
it no-ops when `mobile_app` is unset. The binary sensor is the live state and
clears itself; recovery gets one INFO log. Sending an `ERROR`-status push to say
things are fine would also be wrong.

**Boundary.** `check_and_relaunch_command` lives on `AbstractDevice` but the
notify channel is on `AbstractLoad`, and the battery reaches the same driver. So
`async def _notify_unresponsive(self, time: datetime, command: LoadCommand) -> None:
return` is a documented no-op on `AbstractDevice`, overridden on `AbstractLoad`.
MRO is fine: `QSBiStateDuration(HADeviceMixin, AbstractLoad)` resolves the override
on `AbstractLoad` and `on_device_state_change` on `HADeviceMixin`. Accepted
product consequence: an uncontrollable **battery** gets the ERROR log but no push
and no sensor.

**Logs.** One ERROR on entry, one INFO on recovery, replacing ≈514 lines/hour/load.
No heartbeat. Both lazy `%s`, no trailing period.

## Acceptance criteria

1. **AC1** A load whose `probe_if_command_set` returns `False` forever remains
   commandable after the threshold: a differing command supersedes and executes
   (subject to AC4's throttle), rather than being stacked forever.
2. **AC2** `command_relaunch_delay_s()` returns 50/100/150/200/250/300 for
   `n = 0..5` and **300 for `n = 6, 7`** — the discriminating index is 6; a test at
   `n = 5` cannot distinguish the saturating formula from the old one.
3. **AC3** `is_uncontrollable` is `True` only while `unresponsive_since` is set
   **and** a command is in flight. It is `False` after the `load.py:654`

## Risks

- **R1** Task 7's current failure mode is *silent* — a `MagicMock` load's
  `TypeError` is swallowed at `home.py:2879`, so `all_ok` stays `True` and
  assertions never fire. A green gate proves nothing; the temporary-re-raise
  discovery step is mandatory. Converting to real `AbstractLoad` objects is what
  actually closes this.
- **R2** Supersession changes solver-visible command timing. `_stacked_command`
  stays single-slot, last-wins.
- **R3** The perpetual retry issues **~288 service calls/day as a steady-state
  floor** — not a ceiling — per uncontrollable load, indefinitely. Accepted: the
  cadence equals today's final rung, equal re-requests make no call, differing ones
  are throttled to the same interval anchored on `_last_supersede_time`, a relaunch
  that never acks never increments `num_on_off`, and `qs_enable_device` is the manual
  off-switch.

  **Floor, not ceiling (implementation finding — see §2's empty-slot rung reset).**
  288/day is the rate for a load that stays uncontrollable with the *same* command
  in flight: one relaunch per saturated 300 s window, 12/h. But the empty-slot
  re-arm resets `running_command_num_relaunch` to 0, so a genuinely **new** command
  launched after a re-arm gets a *fresh* 50/100/150/200/250/300 ladder: 1 launch + 6
  relaunches = **7 calls per 1050 s**. In the pathological alternation — solver asks
  for `X` (`== current_command`, absorbed by the `load.py:654` early-return, slot
  empties, re-arm), then for `Y` (`!= current_command`, launched, never acks, ladder
  climbs 1050 s, threshold re-crossed), then `X` again, forever — the period is
  ~1050 s, giving `86400 / 1050 ≈ 82` episodes/day × 7 calls ≈ **576 calls/day**,
  i.e. ~2× the floor.

  Accepted, and reviewers should **not** treat the excess as a regression:
  - Every one of those calls is for a command that genuinely **differs** from the
    last confirmed state. The `X` half of the alternation costs **zero** service
    calls (the early-return makes none). We only ever call when QS actually wants
    something else.
  - The alternative — inheriting a spent rung across a re-arm — is the bug this
    finding fixed: it declared lost-control on a new command's *first* cycle, with
    zero relaunches, logging a false "not confirmed after 6 relaunches". Correct
    escalation evidence is worth the call rate.
  - The push rate in this scenario is ~82/day/load, which is exactly what **R5**
    already states ("roughly one push per 1050 s of continued non-convergence"), so
    R3 and R5 are consistent rather than additive. If it proves noisy, R5's
    `_last_notify_time` floor damps the pushes without touching the call rate.
  - `qs_enable_device` remains the manual off-switch for both.
- **R4** After a restart, `unresponsive_since` is absent and the sensor stays
  `False` until the next failed command. Accepted — a restart is a fresh chance.
- **R5** The in-flight conjunct trades a stuck sensor for possible re-notification:
  an intermittently-obeying device can clear and re-cross the threshold, so the
  worst case is roughly one push per 1050 s of continued non-convergence per load.
  Accepted rather than damped, because a device that keeps losing control *should*
  keep saying so; if it proves noisy, add a `_last_notify_time` floor. AC9 pins one
  push per episode, not one ever.

## Implementation findings (v8)

Found while writing the code, after review round 4 closed. Recorded here so the
code-review phase starts from the corrected design rather than re-deriving it.

1. **The round-4 fix was half a fix — the preserved rung poisoned the next
   command.** Round 4 correctly made `abandon_running_command` preserve
   `running_command_num_relaunch` (finding 11). But that is only sound when a
   successor is launched in the same `launch_command` call. On the two abandon
   paths with no successor — the `load.py:654` equal-command early-return and
   `launch_command`'s override-suppression drop — the rung survived with an empty
   slot, `unresponsive_since` was re-armed, and the *next* unrelated command was
   declared uncontrollable on its **first cycle** after zero relaunches, logging a
   false `"not confirmed after 6 relaunches"` and firing a spurious push. Fixed by
   §2's **empty slot implies rung 0** invariant. Pinned by
   `test_re_arm_resets_the_ladder_rung_so_the_next_command_starts_fresh`.
   Consequence for the call rate quantified in the amended **R3**.
2. **R3's 288 calls/day is a floor, not a ceiling.** The rung reset means a new
   command after a re-arm gets a fresh 50 s ladder, so the pathological
   `X`/`Y` alternation reaches ~576/day. Accepted — see R3 for the arithmetic and
   the four reasons this is correct rather than a regression.
3. **The override-suppression drop was a duplicated abandon.**
   `force_relaunch_command` hand-rolled the same five assignments as
   `abandon_running_command`; it now calls it and zeroes the rung explicitly. See
   §3. Behaviour-preserving; verified against `tests/test_qs256_override_lifecycle.py`.
4. **AC5's justification only covered half the paths.** The story argues the rung
   advances on an exception because `running_command_num_relaunch += 1` sits before
   the `try` at `load.py:766` — true for `execute_command`, but `check_commands`
   calls `probe_if_command_set` **unguarded**, so a raising *probe* would propagate
   out and never advance the ladder. `check_and_relaunch_command` therefore uses two
   nested `try/finally` blocks (never a bare `except Exception`). The exception is
   deliberately not swallowed — `QSHome.check_loads_commands` keeps the per-load
   `try/except`. Both call sites now have their own double and assertion, per
   task 0.
5. **AC14b is contradictory as written** and was implemented to its intent. It asks
   that `check_loads_commands` "no longer contains the literals `50` or `6` **and**
   does call `command_relaunch_delay_s()`" — but §5 makes it a thin driver that
   delegates to `check_and_relaunch_command`, so it cannot call the delay helper.
   The test asserts the spirit and is strictly stronger where it matters: no `50`/`6`
   literals, no `force_relaunch_command`, `check_and_relaunch_command` present, and
   the delay derived from `command_relaunch_delay_s()` in the pure layer one call
   away.
6. **`tests/qs` is not a required supplement for this change set.** Task 14 asks for
   `--quick tests/qs` on the grounds that task 13 edits four `docs/agents/*.md`
   files. Those are not `tests/qs`-pinned — the pinned non-Python set is agent
   files, commands, workflow docs and `.claude/settings.json`, none of which this
   PR touches. `--quick tests/test_translations.py` and `--quick tests/ha_tests`
   were run and are green.
7. **The lost-control clock is ownerless after the invalid-probe give-up → split to
   [#308](https://github.com/tmenguy/quiet-solar/issues/308).** `_ack_command(time,
   None)` nulls `current_command` and empties the slot, but both clear-guards
   deliberately keep `unresponsive_since` — so the clock outlives the command it
   described and the next command inherits it, flipping `is_uncontrollable` `True`
   with zero relaunches of its own. No false ERROR and no false push (the once-only
   guard holds), so this is a diagnostic/robustness defect, not a functional one.

   Two obvious fixes were tried and **measured to be worse**, both recorded in #308:
   clearing the clock at the give-up drops the unreachable-device signal from
   **88% → 0%** of cycles (the give-up fires at ~70 s but the threshold needs
   1050 s, so the clock can never be re-earned); and preserving `current_command`
   via `abandon_running_command` bills **3000 W of phantom consumption** into
   `home_non_controlled_consumption` and the persisted forecast — squarely inside
   AC7's forbidden zone. `_ack_command(time, None)` must keep nulling
   `current_command`. #308's design hands the signal to a separate, owned

9. **Considered and REJECTED — do not re-propose: "absorb the incoming command
   when it equals `current_command`".** Recorded because it is superficially
   attractive and will occur to the next reader.

   The observation that motivates it is real: when the solver reverts to a command
   equal to `current_command` while a *differing* one is in flight on a **healthy**
   load, today's stacking forces the device through a full `on → idle → on` round
   trip, charging **2** transitions against the `num_max_on_off` daily budget and
   stamping `last_state_change_time`, which arms the 600 s
   `CHANGE_ON_OFF_STATE_HYSTERESIS_S` and can then block a *legitimate* transition
   for ten minutes.

   The tempting fix is to kill `running_command` and `_stacked_command` and absorb
   the incoming command instead. Two variants, both unsound:

   - **Trusting `current_command`** is unsound because a persisting
     `running_command` means the service call *already went out* (if the probe had
     said "already set" at launch, `launch_command` would have acked and emptied the
     slot). Between dispatch and ack, `current_command` is a stale belief.
   - **Probing first, then absorbing** is *also* unsound, and this is the decisive
     point: `probe_if_command_set` reads a **lagging observation**, not the future. A
     `True` probe means "the entity currently reports `on`" — it does not mean the
     in-flight `idle` will not land a moment later. **A dispatched service call is an
     un-retractable pending action; no amount of observing can cancel it.** So the
     probe can say `on`, we ack `on`, and the `idle` then takes effect — leaving QS
     believing `on` with nothing in flight and no probe scheduled to catch the
     divergence.

   Acking a command that was never executed also corrupts the switching-cost
   accounting in both directions: `_ack_command` sets `prev_command = current_command`
   and `current_command` to the phantom value, so the real transition goes uncounted
   while a later command against the phantom belief is charged one that never
   physically happens. Since `num_on_off` is the hardware wear-protection mechanism,
   corrupting the budget is strictly worse than spending it.

   **Therefore the round trip is not waste — it is accurate accounting of a
   transition that genuinely occurred**, and today's stacking is correct *because*
   it waits for the ack before applying the next command. There is nothing to
   optimise here. (AC4's "a differing one against a healthy load is stacked" is
   right on the merits, not merely for scope reasons.)

   The `load.py:654` early-return on the **uncontrollable** path is not the same
   thing and is safe: it does **not** call `_ack_command`, so no counter moves and no
   new belief is created — `current_command` merely keeps the value it already had —
   and it acts on a command that has demonstrably failed to take effect for 1050 s+,
   not one dispatched 7 s ago.
