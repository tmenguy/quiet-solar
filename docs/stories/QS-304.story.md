## The bug

`AbstractDevice` holds one in-flight command in `running_command`, cleared only by
`_ack_command`. The relaunch ladder gave up after 6 tries:

```python
# ha_model/home.py, before
if wait_time > timedelta(seconds=50 * (load.running_command_num_relaunch + 1)):
    if load.running_command_num_relaunch < 6:
        await load.force_relaunch_command(time)
    else:
        _LOGGER.error(...)          # ...and nothing else, ever
```

So after `50+100+150+200+250+300 = 1050 s` the load becomes **permanently
uncommandable**: `running_command` stays set forever, every later command is
silently overwritten into `_stacked_command`, and no retry is ever attempted again.
The only exits are the device spontaneously complying, or an HA restart.

Observed 2026-07-27 on **Cumulus Pool House**: `idle` dispatched 12:12, ladder spent
12:30, constraint met 15:00 — still physically ON at 19:06, with the 15:00 `idle`
sitting unexecuted in `_stacked_command`. Plus ≈514 ERROR lines/hour/load (9 557
across three episodes).

## The fix

1. **The ladder saturates instead of terminating.** `command_relaunch_delay_s()`
   returns 50/100/150/200/250/300 s for rungs 0-5 and then **300 s forever**.
   `NUM_MAX_COMMAND_RELAUNCH` stops meaning "give up" and means "the rung at which
   the delay stops growing". A load can never become uncommandable.
2. **A newer command supersedes a stale one** on a load QS has lost control of,
   instead of starving behind it — throttled to one service call per
   `SUPERSEDE_MIN_INTERVAL_S` (300 s), because the solver legitimately re-issues
   `on` at jittering power consigns every cycle. Inside the window the newest intent
   is parked in `_stacked_command` (last-wins).
3. **Say it once.** One ERROR and one mobile push when QS gives up
   (`DEVICE_STATUS_CHANGE_ERROR`), one INFO when control returns — replacing the
   per-cycle ERROR spam. No entity: the state is internal.
4. **The retry lifecycle moves to the pure layer.**
   `AbstractDevice.check_and_relaunch_command` owns probing, backoff and escalation;
   `QSHome.check_loads_commands` becomes a thin driver. The lifecycle is therefore
   provable without Home Assistant.

### Key mechanics

- `unresponsive_since` — the "we gave up" clock. Set once at the threshold;
  `_clear_unresponsive` is its only writer, so the one-line-in / one-line-out
  guarantee cannot drift between callers.
- `is_uncontrollable` = `unresponsive_since is not None and running_command is not
  None`. **Internal only, no entity.** It decides supersede-vs-stack and gates the
  one-shot escalation. The in-flight conjunct is what stops it sticking when a path
  empties the slot with no successor.
- `abandon_running_command(reason)` — drop the stale command without faking an ack.
  Preserves `current_command` (= last *confirmed* command; the device really is
  still in its old state) **and the ladder rung**, which keeps the 300 s cadence
  across supersession instead of restarting at 50 s.
- `_drop_running_command(reason)` — for the four paths that empty the slot with
  **no** successor (both override-suppression drops, the already-confirmed
  early-return, the disabled-device cleanup). Also zeroes the rung and releases the
  clock: with nothing in flight, neither describes anything.
- The supersede is committed **late**. `launch_command` decides to supersede but
  still has two gates to pass, so the abandon and the throttle stamp happen next to
  `self.running_command = command` — a supersede that issues no service call must
  neither burn the window nor leave a spent rung behind.
- `_seconds_since(time, anchor)` backs both clock comparisons and returns `None` for
  an anchor in the *future*, meaning "treat as elapsed". A backwards clock step
  otherwise freezes the ladder and the throttle for the duration of the jump.
- Exceptions: `launch_command` guards its probe as well as its execute, and
  `_finish_command_cycle` isolates the relaunch/escalation housekeeping so a
  secondary failure cannot mask the real device error.

### Non-goals

- Making a disobedient device obey — #305 for the Pool House facade; the Cumulus
  Enfants device refuses real `number.set_value(0)` calls and is out of scope.
- The pre-existing per-cycle INFO log volume → #306.
- Un-freezing user-override detection while a command is in flight → #307.
  Deliberately excluded: it would move `is_user_overridden()`, which feeds
  `home_non_controlled_consumption` and the *persisted* forecast.
- Power accounting. `is_load_command_set` is **not** modified (AC5).
- The `NUM_MAX_INVALID_PROBES_COMMANDS` (probe returns `None`) give-up keeps its own
  logic and still nulls `current_command` — preserving it there would bill phantom
  consumption into the persisted forecast. Consequence: the clock outlives its
  command on that path, so the next command inherits it. With no entity exposing the
  flag and the once-only guard holding, the only effect is supersede-vs-stack
  choice. Accepted.
- **A binary sensor, and clearing state on home-mode changes** — see the banner.

## Acceptance criteria

1. **AC1** A load whose `probe_if_command_set` returns `False` forever stays
   commandable: relaunches continue at 300 s indefinitely, and a differing command
   supersedes rather than being stacked forever.
2. **AC2** `command_relaunch_delay_s()` returns 50/100/150/200/250/300 for
   `n = 0..5` and **300 for `n = 6, 7`** — the discriminating index is 6.
3. **AC3** `is_uncontrollable` is `True` only while the clock is set **and** a
   command is in flight. `unresponsive_since` survives `abandon_running_command` and
   a `keep_commands=True` constraint reset; it is cleared only via
   `_clear_unresponsive`, from four callers — a real ack, the empty-slot re-arm,
   `_drop_running_command` (unconditionally), and a `keep_commands=False` wipe (that
   wipe destroys both `current_command` and `running_command`, i.e. the clock's
   subject).
4. **AC4** Supersession, given `running_command is not None`: an **equal**
   re-request makes no service call at any rung; a differing one against a
   **healthy** load is stacked; a differing one against an **uncontrollable** load
   executes at most once per `SUPERSEDE_MIN_INTERVAL_S`, asserted with the real
   jitter sequence (`on` at 1761 → 521 → 534 → 536 W) at a 7 s cadence, and
   asserted **again after a supersession has already occurred** to catch a
   rung-reset collapse to 50 s. `num_on_off` is not incremented by a relaunch that
   never acks.
5. **AC5 — no collateral damage.** `is_load_command_set`'s behaviour is unmodified
   (pinned by a truth table over its three inputs), and with override state held
   constant the power-accounting values for an uncontrollable load are identical
   before and after the threshold is crossed.
6. **AC6** An exception from `probe_if_command_set` *or* `execute_command` still
   advances the ladder, so a consistently-raising device reaches the threshold —
   including on the stacked-promotion path, where an unguarded probe once re-created
   the deadlock. The original device exception is never masked by a housekeeping
   failure.
7. **AC7** A load whose command cycle **raises** falsifies `all_ok`, so it blocks
   the off-grid switch like any other unconfirmed load. Deliberate change: the
   previous swallow left `all_ok` `True`.
8. **AC8** Entry emits exactly one new ERROR and exactly one push; the clear emits
   exactly one new INFO and **no** push. Superseding while uncontrollable does not
   re-notify, and neither does a permanently unreachable entity. If the push itself
   raises, a second ERROR is logged for the failed housekeeping — the once-only
   guard still holds.
9. **AC9** A disabled load never shouts: crossing the threshold while
   `qs_enable_device is False` emits no ERROR and no push. QS never writes
   `qs_enable_device` itself.
10. **AC10** A backwards clock step does not freeze the ladder or the throttle.
11. **AC11** Incident regression: constraint met → `idle` never acked → threshold
    crossed → the 12:23 `on` stacked while healthy → the 15:00 `idle` absorbed with
    **no** stale-`on` promotion → retries continue at 300 s, one push fired.
12. **AC12** The lifecycle is provable without Home Assistant — asserted in a test
    module containing no `homeassistant.*` import — and
    `QSHome.check_loads_commands` contains no ladder symbols.
13. **AC13** No `home_model/*.py` imports `homeassistant.*`.
14. **AC14** `python scripts/qs/quality_gate.py` (whole suite) passes: 100 %
    coverage, ruff, mypy, translations.

## Decided — do not re-open

Settled across three review rounds; re-litigating will not converge.

- **The binary sensor and the home-mode release machinery are out.** Removed as
  disproportionate to the bug. If the latch of an *internal* flag ever matters, it
  is a separate issue.
- **`launch_command`'s absorb branch must keep clearing `_stacked_command`.**
  Nothing can stack after `launch_command` is entered, so at absorb time the
  incoming command is the solver's newest word and anything stacked is obsolete.
  Keeping it resurrects the 12:23 `on` from the incident log, which AC11 forbids;
  `test_pool_house_incident_regression` pins it.
- **`abandon_running_command` preserves the ladder rung.** Zeroing it restarts the
  backoff at 50 s after every supersede (~4 calls per 300 s window instead of 1).
  The no-successor paths use `_drop_running_command` instead.
- **The supersede is an intent committed late**, not stamped up front. The
  alternative leaves the stale command in flight on both gate-return paths, so QS
  keeps retrying an `idle` the solver has already replaced with `on`.
- **Two independent anchors for the ladder and the throttle**, so "one service call
  per 300 s" holds per *command identity*, not per load — a relaunch followed by a
  superseding command can make two calls inside one window, bounded to one extra per
  episode. Coupling them would let a supersede delay the ladder, or a relaunch delay
  a newer intent.
- **`_notify_unresponsive` is a documented no-op on `AbstractDevice`.** The driver
  also runs against `QSBattery`, which has no notification channel. An
  uncontrollable battery gets the ERROR log but no push.

## Where the tests live

- `tests/test_bug_304_command_deadlock.py` — the whole lifecycle, pure layer, no

- `tests/qs304_helpers.py` — ladder timings derived from the production constants,

- `tests/factories.py` — `NeverAcksLoad` (the Pool House shape, with knobs for a
  complying / unreachable / raising device), `RaisingProbeLoad`,
  `RaisingExecuteLoad`, `RaisingCheckLoad`, `AlwaysReplansLoad`, `NeverAcksDevice`
  (the battery path), `attach_minimal_load_to_home`.

**Testing note that cost real time.** `QSHome.check_loads_commands` swallows
per-load exceptions, so a `MagicMock` load fails *silently* there — `all_ok` stays
`True` and assertions never fire. Twelve driver tests were exercising nothing. Use
`attach_minimal_load_to_home`; and if you suspect this class of bug, temporarily
re-raise from the swallowing `except` and run the suite — the failures are your
conversion list.
