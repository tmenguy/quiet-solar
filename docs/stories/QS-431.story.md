# QS-431 — Zoe charge constraint oscillates, triggering a notification storm

issue: 431
branch: "QS_431"
lane: bug-product
Status: implemented — PR #433; review fixes #01–#04 applied (verify round 5 pending)

## Symptom

On 2026-10-23, Thomas's phone received a notification storm from the Zoe
(wallbox 3 portail):

- **06:50 → 07:26**: one notification every ~7 min, always
  `Zoe (person:Thomas Menguy, originator:person): 43 % / 44 % today 07:30`. The
  text was sometimes identical from one notification to the next.
- **07:29:46 → 07:37:19**: ~8–9 notifications per minute, alternating every ~7 s
  between `Zoe (person:Thomas Menguy, originator:person): 44 % today 07:5x ASAP`
  and `Zoe: 100 % best effort`. It stopped when the user pressed the reset button
  on the Zoe (07:37:19).

User expectation: the Zoe had a **manual 25 %** target and **Thomas was manually
pinned to the Zoe** the evening before, so nothing should have oscillated.

## Evidence

Source: `/Users/tmenguy/Downloads/home-assistant.log` (2026-10-21 13:16 →
2026-10-23 11:10). Log times are local CEST = UTC+2.

### HA boot (2026-10-21 13:16:44): every car's user store is filled by the restore replay

At boot, entity restore replays `qs_bump_solar_charge_priority` (switch) and
`selected_next_charge_limit_for_car` (select) on every car, for example
`async_turn_off : qs_bump_solar_charge_priority on Zoe` and
`100% - Zoe default selected_next_charge_limit_for_car on Zoe` (log L248, L254).
The same lines appear for ID.buzz, Tesla M3 and Twingo.

These replays run under `user_replay_context(True)` (`car.py` L80-95) but still
go through `set_user_originated` → `QSCar._on_user_originated_changed`
(`car.py` L361-393). That hook snapshots the whole car state; only the
car↔charger pin is skipped during a replay (`car.py` L390-392).

**So `_user_originated` is non-empty on every car after every HA restart, with no
user action.** It also holds a `charge_target_percent` marker (here 100) from boot
onwards.

### Night

- 02:28:45: the SOC sensor stayed frozen at 20 % (Renault API, car asleep). The
  calculus estimated 25 % (`use calculus because sensor not growing … 25.0`), so
  the manual 25 % constraint was **COMPLETED** (notification
  `COMPLETED: Zoe (manual): 25 % today 10:00`).
- 02:28:52: with no user-timed constraint left, the person block pushed
  `Zoe {'person': 'Thomas Menguy'} 20.0/42.43/7/3`, ending 05:30 UTC (07:30

### 06:50 → 07:26: ~7-min cadence (secondary symptom)

- The Renault integration polls every **~7 min 12 s** (`renault_api` lines at
  06:28:55, 06:36:07, 06:43:19, …). This cadence is **not a quiet-solar constant**.
- Each poll updates SOC/range. `QSCar.get_adapt_target_percent_soc_to_reach_range_km`
  (`car.py` L2127) recomputes `km_per_percent`, so the person target drifts:
  42.43 → 43.08 → 43.55 → 43.64 → 44.00 → 44.04 → 44.055.
- The person block rewrites `car_charge_person.target_value` on any float
  difference (`charger.py` L4873). `LoadConstraint.stable_name` embeds the float
  (`constraints.py` L269-276), so the active-state hash changes and a notification
  goes out on every poll.
- Rounded, the series is 42 → 43 → 44 → 44 → 44 → 44 → 44. Of the 6 rewrites, only
  2 changed the displayed % (42→43, 43→44). The other 4 sent a notification with
  the same text.

### 07:29:46 → 07:37:19: ~7-s storm (primary symptom)

At the deadline (SOC 33 % < 44.05 %), `update_live_constraints` extends the person
constraint by ~21 min and switches it to type 9 (ASAP):
`pushed because mandatory and not met (#pushed 1)` →
`handled_constraint_force is now as fast as possible`. That part is by design.

After that, a **two-cycle (14-s) period** repeats. The hash changes at 07:29:46
ASAP / 07:29:53 filler / 07:30:00 ASAP / … The re-pushes are logged at
07:30:00.640, 07:30:14.643, 07:30:28.647, …

1. **Cycle A**: `check_load_activity_and_constraints … pushed usage minimum charge constraint … 33.0/44.055/7/3`.
   Its end is the past `next_usage_time` 05:30 UTC, so `update_live_constraints`
   promotes it to ASAP in the same cycle → hash `…/9/7)-Zoe-ASAP` → notification
   "44 % ASAP".
2. **Cycle B**: the ASAP block of `check_load_activity_and_constraints`
   (`charger.py` L4614-4630) finds the person ASAP. Because
   `user_target is not None` (marker 25), it rewrites `target_value` to 25. The
   car is at 33 %, so `set_live_constraints` silently filters the constraint out as
   met (`load.py` L2369). The hash falls back to `Zoe 100.0/3/3` → notification
   "100 % best effort". The next cycle is A again.

**Other removal paths are ruled out.** None of the drop paths that log anything
appears in the window: `skipped because met` (`load.py` L2539/L2621),
`stopped by callback`, `not met and pushed too many times`, or the WARNING
`removed … already-completed` (`load.py` L2387).

`do_remove_all_person_constraints` only logs at DEBUG, but it cannot run in cycle
B: the person block is skipped while `force_constraint` is set (`charger.py`
L4812). The in-session repro reproduced the same 2-cycle pattern on the real code
path.

The `update_value_callback … True/33.0 (33.0/25)` line at 07:29:53 is
*sensor 33 / calculus 25*, not the constraint target (`charger.py` L6573-6581).

**Precondition for the loop**: a `charge_target_percent` marker **at or below the
current SOC** (here 25 ≤ 33), with the person ASAP target above it. Without any
marker, the repro shows 0 hash changes.

### Person/car allocation (user question: "it was frozen, it should NEVER have changed")

The manual pin **held**: every allocation from 20:44:28 to 07:37 has
`Zoe->Thomas Menguy`, including the whole storm window. The later changes have
their own causes:

- 07:03:24 `unplugged connected car Twingo … clearing user_selected_person=Arthur Menguy`:
  the Twingo was physically unplugged, which drops its pin (QS-416, by design).
- 07:37:19 `qs_device_clean_and_reset on Zoe`: the user's reset cleared the
  Zoe→Thomas pin. Allocation then became `energy-optimal`.

### History

This is a residual path of **bug #48** (`9591a822`, March 2026,
`docs/stories/QS-legacy-bug-48-charger-constraint-oscillation.story.md`), with the
same symptom. #48 made person ASAP constraints keep their person target
**"unless the user explicitly overrode the charge target"**, implemented as
`user_target is not None`.

In the incident, the marker was genuine (25, set at 20:43:36), so the escape fired
as #48 designed it. The loop came from the person block re-pushing the need
(defect 1) and from the silent drop of a met constraint. The escape is a defect in
its own right because `user_target is not None` cannot tell a real user override
from a boot-replayed marker. The probe shows that a replayed marker of 25
reproduces the same loop on an unfrozen car.

## Product rule (decided with the user, 2026-10-23)

**A car frozen by a user action gets no person constraint.** Any *user* action on a
car freezes it. In practice, every non-replay caller of the car's
`set_user_originated` is a user entry point (verified in review round 2):

- the target % select;
- bump solar;
- "charge now" (`user_force_charge_now`);
- timed charge (`user_add_default_charge*`);
- "clean constraints" (button `qs_device_clean_command_and_constraints` →
  `QSCar.user_clean_constraints`, which writes the `CLEARED` sentinel);
- picking the person on the car card (`user_set_person_for_car`);
- picking the charger on the car card (`QSCar.user_set_selected_charger_by_name`).

**Explicit, user-accepted consequence:** pinning a person on a car freezes it. Once
Thomas is manually pinned on the Zoe, the Zoe never gets an automatic person-trip
constraint for Thomas until the freeze clears. Charging then follows only the
user's manual choices.

While frozen:

- the person need **must not be pushed** as a constraint;
- a live person constraint that is not ASAP yet is removed. The person block's
  removal branch runs through `_person_constraint_ends_this_cycle` returning True.
- a person constraint that is **already ASAP** when the freeze happens is *not*
  removed. The ASAP block runs first, finds it as `force_constraint`, and the
  person block (and so the removal branch) is skipped (`charger.py` L4812). It is
  retargeted to the user's target marker when one exists (Fix A′), runs to
  completion or ends as met, and is never re-pushed.

The freeze lasts until it is cleared: a physical unplug HA sees live **of the
attached car** (an unplug while HA is down is not detected, and a car detached
from its charger before the unplug keeps its freeze — documented limitations, see
Blast radius "Freeze lifetime"), the reset button
(`qs_device_clean_and_reset` → `user_clean_and_reset`, which clears the whole store,
unlike "clean constraints"), the person pin being taken by another car, or any other
`clear_all_user_originated` path (stale or unauthorised pin at boot or at
allocation). It survives HA restarts and lasts **even across
several days**; the user accepted this consequence explicitly.

Refinements, derived from the rule's own wording ("a *user* action on a car"):

- **An HA restart is not a user action.** The entity restore replay must not
  freeze a car (see Evidence: boot). The number and time platforms never write the
  car's store on restore (verified in review round 2).
- The QS-353 *system* person hold is not user-originated and does not freeze.
- Picking the *car on the charger card* (`QSChargerGeneric.user_set_selected_car_by_name`,
  `charger.py` L3993) writes the charger's store only, so it does not freeze the
  car. The boot re-attach writes the car's store directly (`charger.py` L4064) and
  must not freeze either. Picking the *charger on the car card* (above) does
  freeze.
- The person need is still **computed**: it keeps driving person↔car allocation
  and the "trip not covered" notifications. Only the constraint is suppressed.

## Root cause

**Two defects in `QSChargerGeneric.check_load_activity_and_constraints`
(`custom_components/quiet_solar/ha_model/charger.py`) combine:**

- **(1)** `_person_constraint_ends_this_cycle` (L4194) has no notion of a
  user-frozen car. So the person block pushed Thomas's 44 % need at 02:28:52 on a
  Zoe the user had taken manual control of at 20:43, and kept re-pushing it after
  every drop.
- **(2)** The #48 escape in the ASAP block (L4614-4630,
  `user_target is not None or not has_person_info`) lowers a person ASAP to any
  `charge_target_percent` marker, genuine or boot-replayed. When the marker is ≤
  the current SOC, the constraint becomes immediately met and is silently dropped
  by `AbstractLoad.set_live_constraints` (`home_model/load.py` L2369).

Together they give a 14-s push/drop loop. In the incident the marker was genuine
(25 ≤ 33).

Fixing (1) alone is not enough. A throwaway probe implemented the freeze as a
dedicated flag and kept the #48 escape. A car that is **not frozen** but carries a
**boot-replayed** marker of 25 still oscillated (7 hash changes in 10 cycles),
because the unfrozen person block keeps re-pushing. Fixing (2) alone leaves the
product rule unimplemented. Both are needed.

**Secondary (the ~7-min notifications, cars that are not frozen):** the person
block (L4873, `if car_charge_person.target_value != target_charge:`) rewrites the
constraint target on sub-percent float drift of the person need. That changes
`stable_name`, so `get_active_state_hash` changes and `do_probe_state_change`
notifies even when the displayed % is unchanged.

## Fix plan

**Fix C (product rule): a dedicated user-freeze flag.**

- `const.py`: add `USER_ORIGINATED_USER_FROZEN = "user_frozen"` next to the other
  `USER_ORIGINATED_*` keys.
- `car.py`, `QSCar._on_user_originated_changed` (L361): at the end, write
  `if not _USER_REPLAY_FOR_INIT.get(): self._user_originated[USER_ORIGINATED_USER_FROZEN] = True`.
  - Use a **direct dict write**. It simply skips a redundant guarded call: the
    re-entrancy guard of `set_user_originated` (`load.py` L238-245) would already
    prevent a second snapshot pass.
  - It is **not** gated on `key != USER_ORIGINATED_CHARGER_NAME`, unlike the L392
    pin. A charger pick on the car card freezes, per the rule.
  - The flag lives in the persisted store (`load.py` L587/L590), so it survives a
    restart.
  - It is cleared with the store by `clear_all_user_originated`: unplug edge, reset
    button, person pin taken by another car, unauthorised pin at allocation
    (`home.py` ~L2640), and the boot-time stale-pin clears in
    `QSCar.device_post_home_init` (`car.py` L478 pinned person gone, L486 not
    authorised).
  - `user_set_person_for_car` re-freezes after its targeted clears (L666-669).
  - Add a public `QSCar.is_user_frozen() -> bool` that returns
    `self.get_user_originated(USER_ORIGINATED_USER_FROZEN) is True`.
  - **Every charger call site compares `self.car.is_user_frozen() is True`.** Many
    older tests use `MagicMock` cars, whose mocked `is_user_frozen()` returns a
    truthy `MagicMock`. The explicit `is True` keeps them unfrozen.
- `charger.py`, `_person_constraint_ends_this_cycle` (L4194): add as the first test
  `if self.car.is_user_frozen() is True: return True`. No `None` guard: the method
  already dereferences `self.car` at L4221. It drives:
  - the person block's removal branch (`do_remove_all_person_constraints` → clean

**Blast radius:**

- **Fix C** changes behaviour only for cars **frozen by a genuine user action**.
  They lose automatic person-trip constraints until the freeze clears, which is the
  deliberate product decision.
  - Pinning a person on a car is such an action (user-accepted).
  - "Charge now" or a timed charge: the session itself is unchanged (same target,
    captured by D1). The visible change comes **after** the session completes: the
    person constraint is no longer re-pushed until unplug or reset. The
    `force_charge` / `charge_time` clears at L4640-4643 do not remove the flag.
  - Restart replays, the system hold, and charger-card car picks do not freeze.
- **Upgrade (both fixes):** user markers persisted *before* this change carry no
  flag, so already-frozen cars behave as unfrozen until the next user action.
  - For C, person constraints keep being pushed.
  - For A′, a person ASAP keeps its person target even if a genuine pre-upgrade
    user target exists.
  - Both are the safe direction (the trip is still covered), so no migration.
- **Fix A′** changes only person ASAP constraints on **unfrozen** cars that carry a
  marker. Today they are retargeted to the marker (looping when ≤ SOC, or raised to
  a replayed default); after the fix they keep the person need. Frozen cars with a
  marker behave as #48 intended. Frozen cars without a marker are unchanged.
- **Fix B** delays a person-target update by < 1 % until the rounded value changes.
  The solver energy delta is negligible.
- **Filler rule** (implement-time amendment, see "File-list amendments" 1): every
  car's filler notification / constraint name now reads
  `<car> (originator:filler): … best effort`; a legacy untagged filler is rebuilt
  once after the upgrade; an active energy-target filler loses its accumulated
  `current_value` when it is rebuilt; a filler is rebuilt only when the shape of the
  real chain changes (review fix #01, N1).
- **Freeze lifetime** (review fix #01 S2, #02 R2-N1, #03 R3-N3, #04 R4-M1/R4-N1):
  the freeze ends on an unplug HA sees live, a car-card or charger-card reset, the
  person pin taken by another car, or a stale / unauthorised pin. The charger-card
  reset clears the attached car's user store, system hold, forecasted person and
  charge targets and re-runs the notifying person allocation, as the car-card reset
  does (once, when the car-card reset drives it).
  **Documented limitation (review fix #04, user decision):** an unplug that happens
  while HA is down is not detected for the freeze. The QS-416 boot guard only lifts
  the pins (the charger's user car pin, the car's charger choice naming this
  charger, the boot car), exactly as on `main`, so the car stays frozen — no
  automatic person constraint — until the next live unplug or a reset. The
  boot-time car-store wipe tried by fixes #01–#03 is removed: it infers the

  really happen , document it , it is very hard to properly fix, so don't fix it"

- **Fix B hysteresis** (review fix #01 N2, #02 R2-N2, #04 R4-S1, #05 R5-N2): a
  live person target is rewritten when the rounded % changes, at once when it
  rises and only when the need fell by ≥ 0.5 % when it falls. Bound, at display
