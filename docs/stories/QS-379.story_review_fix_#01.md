## Findings to fix

### [should-fix] S1 — Zero-power latch can outlive the stuck episode
- File: `custom_components/quiet_solar/ha_model/charger.py:5673-5681` (latch), `:5180` (card), `:5350-5368` (F2 re-arm)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `possible_charge_error_start_time` is only cleared by a
  zero-power check that sees power (needs target `True`, ≥5 % SOC gap,
  trusted SOC sensor, SOC constraint) or by `reset()`. QS-379 makes every
  stuck start set it; after the F2 re-arm the target goes back to `False`
  and may never return to `True` (solar drops, constraint ends/changes to
  energy mode, target lowered within 5 %, SOC sensor distrusted). The card
  then stays `CAR_CHARGE_NO_POWER_ERROR` for the whole plug session and a
  second, genuine stuck start later in the session is never notified.
- Proposed fix: define the end of a no-power episode explicitly and clear
  the latch there. Suggested rule: the episode ends once the charger has
  **not wanted charge** (`_expected_charge_state.value is not True`) for
  longer than `CHARGER_CHECK_REAL_POWER_WINDOW_S` continuously — long
  enough that the AC3 round-2 re-arm (a few cycles after REARM) keeps the
  latch, short enough that "next morning" starts a fresh episode. Track the
  "not wanting charge since" timestamp in the per-cycle path that runs
  regardless of the SOC callback (e.g. `ensure_correct_state` /
  `check_load_activity_and_constraints`), not inside the SOC-gated block.
  The implementer may choose a different rule if it is simpler, but it
  must (a) keep AC3 round 2 intact, (b) guarantee the latch clears when QS
  stops wanting charge for a sustained period, (c) let a later stuck start
  in the same plug session notify again. Tests: one for "target stays
  False after re-arm → latch clears after the window, card no longer
  NO_POWER"; one for "second stuck start later in the session → second
  notification"; AC3 unchanged.

### [should-fix] S2 — Fault recovery triggers an immediate zero-power alert
- File: `custom_components/quiet_solar/ha_model/charger.py:361`, `:3768-3770` (QS-346 fault state machine), `:5650-5653` (zero-power check), `:5162-5169` (`is_load_active` fault gate)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: first launch at T0, charger faulted at T0+100 (callback
  gated off, `last_ping_time_success` frozen at T0), recovers at T0+900.
  On the first cycle after recovery `(t - T0) > 600` is already true, so
  the household gets the QS-346 fault alert followed immediately by a "no
  power being delivered" alert; the restarted charger never gets its own
  600 s. Contradicts the doc's "no double alert".
- Proposed fix: when a charger comes back from a fault, re-arm the
  zero-power reference: `_expected_charge_state.last_ping_time_success =
  <recovery time>` (only when it is not `None`). It must not depend on
  whether the SOC callback or `check_load_activity_and_constraints` runs
  first in the Home cycle. One robust option: record a
  `_charger_fault_cleared_at`/"was faulted" marker and, in the zero-power
  check itself, skip the check and re-arm the reference if the charger was
  faulted at any point within the window (e.g. `_charger_fault_since` still
  set from the previous cycle, or the fault cleared less than
  `CHARGER_CHECK_REAL_POWER_WINDOW_S` ago). Tests: fault from T0+100 to
  T0+900 then stuck → no zero-power alert before recovery+600, alert after;
  cover both call orders (callback first / fault-state machine first).

### [nice-to-have] N1 — Car swap without unplug inherits the previous car's no-power latch
- File: `custom_components/quiet_solar/ha_model/charger.py:4626-4650` (`detach_car`), latch at `:5673`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: `user_set_selected_car_by_name` calls `detach_car()` (not
  `reset()`), so car B inherits car A's `possible_charge_error_start_time`
  (card shows NO_POWER naming nobody relevant; B's real stuck start is not
  notified).
- Proposed fix: clear `possible_charge_error_start_time` when the attached
  car **identity changes**. Do NOT clear it on every `detach_car()` — that
  path runs on allocation churn and re-attaching the same car must not
  re-notify. E.g. clear in `attach_car` when the new car differs from
  `_last_attached_car`, or in the car-select handler. Test: car A latched →
  select car B → latch cleared; churn detach/attach of car A → latch kept.
