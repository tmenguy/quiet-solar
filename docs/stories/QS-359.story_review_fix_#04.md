## Findings to fix

### [should-fix] SF-1 — Don't latch the sticky fallback from a single rejection episode with concurrent in-flight setpoints
- File: `custom_components/quiet_solar/ha_model/charger.py:6457` (`QSChargerOCPP._on_amp_command_error`, the `self._ocpp_station_profile_rejection_streak += 1` path; non-blocking task spawn at ~6433 / `_ocpp_run_number_command`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: On the non-blocking amp path, each setpoint spawns its own
  `_ocpp_run_number_command` task doing `blocking=True`. If QS issues two amp
  changes within one charger command round-trip (comment cites 1–5 s; e.g.
  solar modulation changing the target faster than the charger acks), both
  in-flight tasks can fail with the `ChargePointMaxProfile` marker and each
  calls `_on_amp_command_error`. The streak then reaches
  `OCPP_STATION_PROFILE_REJECTIONS_TO_FALLBACK` (2) from what is effectively a
  single rejection episode, latching the sticky fallback (which persists until
  the integration reloads / HA restarts). This defeats the deliberate "a first
  rejection can be transient; wait for a second" tolerance the constant
  provides — a one-off transient hiccup can wrongly pin the charger into
  permanent fallback amp control.
- Proposed fix: Make the streak count *distinct* rejection episodes rather than
  concurrent in-flight task failures. Record the timestamp of the last
  *counted* marker rejection (e.g. `_ocpp_last_rejection_counted_time`) and
  only increment the streak when the incoming rejection is separated from the
  last counted one by at least the charger command round-trip window
  (introduce a small module constant, e.g.
  `OCPP_STATION_PROFILE_REJECTION_DEBOUNCE_S`, sized to cover the 1–5 s
  round-trip). Rejections that arrive inside that window collapse into the same
  episode (count once). Keep the existing reset-on-accepted-write behavior and
  the `use_ocpp_custom_charging_profile` / non-HAE / marker gates unchanged.
  Implementer may choose an equivalent mechanism (e.g. keying on the cycle
  `time`) provided it demonstrably collapses concurrent same-episode
  rejections. The `time` argument already threaded into `_on_amp_command_error`
  supplies the clock.
- Tests (TDD):
  - Two marker `HomeAssistantError`s delivered within the debounce window
    (same episode) → streak increments by 1 and does NOT latch; a WARNING is
    not emitted.
  - Two marker rejections in *distinct* episodes (separated by more than the
    debounce window, no accepted write in between) → streak reaches 2 and
    latches with exactly one warning (preserves AC2).
  - An accepted write between rejections still resets the streak to 0 (AC2
    regression guard).

### NH-1 — Note the HAE-only rejection-detection dependency
- File: `custom_components/quiet_solar/ha_model/charger.py:6456` (the
  `isinstance(error, HomeAssistantError)` guard)
- Source: qs-review-edge-case-hunter (nice-to-have)
- A genuine station-profile rejection that ever surfaces as a
  non-`HomeAssistantError` while still carrying the marker text (a
  hypothetical future HA/ocpp version raising a bare exception) would be
  silently dropped and fallback would never latch — a permanent false negative
  behind the single-line guard. This is accepted per the story's documented
  v0.12.0 contract assumption. Add a short inline comment recording the
  dependency so a future reader knows the guard intentionally trusts the
  HAE contract.

### NH-2 — Note the fallback's intentionally narrow exception surface
- File: `custom_components/quiet_solar/ha_model/charger.py:6512-6528`
  (`_ocpp_set_charge_rate_fallback`)
- Source: qs-review-edge-case-hunter (nice-to-have)
- The fallback catches `HomeAssistantError` and `(ValueError, TypeError)`
  only; a non-HAE runtime error from the `ocpp.set_charge_rate` handler (e.g.
  `asyncio.TimeoutError`, `ConnectionError`) would propagate, diverging from
  the base number path (which catches `Exception`). This is latent today: the
  fallback is only ever reached with `blocking=False` (the sole `blocking=True`
  amp caller routes to the number path), and a `blocking=False` `async_call`
  raises only HAE-family validation/registration errors. Add a short inline
  comment noting that the narrow surface is intentional today and must be
  revisited if a `blocking=True` caller is ever routed through the fallback.
