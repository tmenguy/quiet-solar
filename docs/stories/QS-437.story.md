maintainer**. It drives one real `qs-node` run on a throwaway factory issue,
guides the maintainer through the steps only a human can do, and records the

**Shell conventions.** The Bash tool's shell is zsh, and its state does not
persist between calls. So every call starts with this preamble:

```bash
setopt pipefail
export MAIN=/Users/tmenguy/Developer/homeassistant/quiet-solar L="$HOME/.local/state/quiet-solar/live-437" W="$HOME/.local/state/quiet-solar/live-437-wake" D="$HOME/.local/state/quiet-solar/live-437-dry"
CP() { "$MAIN/venv/bin/python" "$MAIN/scripts/qs/cp.py" "$@"; }
PY() { "$MAIN/venv/bin/python" "$@"; }
```

- `MAIN` is `git worktree list --porcelain | head -1`, checked at step 0.
- `CP` is a function, not a variable: zsh does not word-split `$CP`.
  `pipefail` keeps `CP`'s exit code through a `| PY "$L/tok.py" …` pipe.
- The build never calls the worktree's copy of `cp.py`.
- **The token rule.**
  - Every write takes `--token "$(cat "$L/run.token")"`. The commands below
    omit it for brevity, but it is always there.
  - **Except** `run open` and `run claim`, which take none. They mint the
    token, which `tok.py --run` saves (D9).
  - **Reads are scrubbed too.** Every `CP` call, reads included, is piped
    through `tok.py --scrub` at least. Nothing shows that `session status` or
    `ledger show` never echoes a token, so the rule does not rely on it.
  - The read and exempt commands take no token either: `version`, `ensure`,
    `session status`, `snapshot`, `task show`, `ledger show`.
  - `wait`, `msg pop` and `msg ack` are writes: they take `--token`.
  - **Every `CP` write's answer is piped through `tok.py`.** `--run` for
    `run open` / `run claim`, `--node` for `tool spawn` / `tool resume`, and
    `--scrub` for every other write. Its output is scrubbed, so an error that
    echoes the token never reaches the transcript. The commands below show the
    `--run` and `--node` pipes. **The `| PY "$L/tok.py" --scrub` pipe is
    omitted for brevity**, like `--token`, but it is always there.
  - `task show` and `snapshot` already drop nonces (`snapshot.py:16`); they
    are piped through `--scrub` anyway, as a safety net for their error paths.
  - **stderr is scrubbed too.** A plain `|` carries stdout only. `cp.py`
    writes its `[cp-*]` log lines (`wait.py:88`, `locks.py:372`, …) and any
    traceback raised before `main` (an import error after a pull) to stderr,
    and those would reach the transcript raw. An argparse error goes to
    **stdout**, as a `USAGE` answer whose `detail` echoes the argv, `--token`
    included (`cli.py:199-201`, `:1204-1205`), and the stdout scrub covers it.
    So:
    - a `--scrub` call is `CP … 2>&1 | PY "$L/tok.py" --scrub`;
    - a `--run` / `--node` call keeps stdout clean JSON with
      `2>"$L/err.txt"`, then `PY "$L/tok.py" --scrub < "$L/err.txt"`;
    - `view.py` and `wake.py` capture their subprocesses' stderr and scrub
      it before printing.
  - **`gh` reads are scrubbed too.** Every `gh` read of PR or issue text
    (the CodeRabbit evidence, the node's publications) is dumped to `$L` and
    read only through `tok.py --scrub`: a token the node put there would
    otherwise reach the transcript.
  - The bare word `sqlite3` in the build's own `--grep` patterns is safe. The
    DB-access hook matches only a segment naming `harness_state.db`
    (`hooks.py:229`).
  - The build **never prints `run.token`**. It is used only as
    `$(cat "$L/run.token")` inside a command, and its presence is checked with
    `test -s "$L/run.token"`.
- **Long calls:** every call that can run past 2 min (`wait`,
  `gh pr checks --watch`, a poll loop) sets the Bash tool timeout to
  600000 ms.
- **A Bash timeout on a `tool` call** counts as "started with no result":
  replay it with the same key and args, never a new key.
- **Every path is absolute.** That covers every `*_file`, `--args-file`,
  `--file`, `--input`, `--payload-file` and `--answer-file` (`tools._read_files`
  does not expand `~`). JSON args files hold the expanded path, and so does
  any `<MAIN>` in a prompt or message text.
- `$L`, `$W` and `$D` are created with `mkdir -p` then `chmod 700`.

## Design

### D1 — Who is the orchestrator, and how it wakes the node

The **build session** is the orchestrator. It opens the run under its own
session id (`$CLAUDE_CODE_SESSION_ID`, the `--session-id` default) and runs
every `CP` command itself. The maintainer watches, approves (D8), and does the
human-only steps (7.d).

**The session**, started from a terminal in the QS_437 worktree:

```bash
claude -n live-437 --permission-mode auto --add-dir "$HOME/.local/state/quiet-solar" --agent qs-implement-setup-task
```

`--add-dir` lets the session's Write/Edit tools reach `$L` and `$W` without a
prompt. The directory already exists and is trusted.

The name `live-437` is the run's name. `run open` binds it to this session,
and the watchdog's stalled-run messenger addresses the **run** name
(`watchdog.py:276`). So the session's name must equal the run's name for that
messenger to reach the orchestrator. Node names derive from it too
(`<run name>-T<n>-g<g>`, `tools.py:1207`). A message
that the watchdog injects into the build session is treated as a wake (drain
the queue, D4). It is **never** a maintainer approval.

**Waking the node.** `qs-implement-setup-task` has **no `SendMessage` tool**.
So the build wakes a node as the Control Plane's watchdog does: with a
one-shot messenger. Two things make the watchdog's messenger work, and the
hand-run one copies both (`watchdog.py:291-292`):

- it runs **outside every checkout**. Every worktree pins its phase agent in
  `.claude/settings.local.json`; QS_437 pins one with no `SendMessage`. A
  messenger started there would run as that agent;
- it runs with **the session's identity stripped from its environment**:
  `CLAUDE_CODE_SESSION_ID`, `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`,
  `CLAUDE_CODE_MESSAGING_*`, and also `QS_CP_TOKEN`.

The helper `PY "$L/wake.py" <target name> <k> [<message>]` (D9) does both.
It `chdir`s to `$W`, which is trusted by inheritance from
`~/.local/state/quiet-solar`, holds no token and pins no agent. Then it
launches, with the stripped environment and
`subprocess.run(argv, cwd=…, capture_output=True)` (`claude --bg` returns at
once), and scrubs both captured streams before printing them:

```text
claude --bg -n qs-wake-<base>-h<k> --model <fast> --permission-mode auto --tools=SendMessage --allowedTools=SendMessage "You are a one-shot messenger. Call the SendMessage tool exactly once, to the session named <target name>, with this message: <message> Do nothing else, then stop."
```

- `<base>` is the base name, `live-437` unless step 0.7 changed it. Step 0.7
  writes it to `$L/base.txt`. `wake.py` reads it, defaulting to `live-437`
  when the file is absent (the self-test runs before step 0.7).
- `<k>` counts 1, 2, … within the run (`0` and `0b` for the dry run).
- `<fast>` is read from `$L/fast.txt`, written at step 0.3 from `<MAIN>`'s
  `models.py`, which imports only `targets`:
  `PY -c 'import sys; sys.path.insert(0, "'"$MAIN"'/scripts/qs"); import models; print(models.model_for("claude", "fast"))' > "$L/fast.txt"`
  (today `claude-haiku-5-5`). `wake.py` refuses to run if the file is empty.
- `--tools=SendMessage` limits the messenger to that one tool, so it cannot
  read `$L`. `--allowedTools` only pre-approves a tool; it does not remove
  the others.
- **The `--no-tools` form.** The watchdog passes no `--tools`, and nothing in
  the repo has used `--tools` with `--bg`. So `wake.py --no-tools` drops it
  and uses the watchdog's exact argv (D1's dry run decides which form is
  used).
  - The residual risk of that form is bounded. The messenger's identity
    variables are stripped, it runs in `$W`, its prompt never names `$L`, and
    it is told to make one `SendMessage` call. It is recorded in the run log
    with that reasoning.
- **List-valued options.** `--tools`, `--allowedTools` and `--add-dir` take
  several values, until the next argument that looks like an option. So a
  prompt that directly follows one is swallowed as one more value (#424 L8).
  There are two safe forms:
  - the one-word `--opt=value`, which takes exactly one value;
  - the spaced form followed by another option, as in the dry run's
    `--tools "" --model …`.
- `wake.py` prints its final argv and writes it to `$L/wake-<k>.argv` (0600)
  before it launches. The file's first line is `cwd: <abs dir>`. The run log records the argv once per form: the dry
  run's try A or try B, and again only if the form changes. Each later wake's
  row keeps only `h<k>`, the messenger id and the result.
- `<message>` defaults to the fixed `<WAKE>`, which carries no token: "You
  have a message in your Control Plane queue. Run your start-up and go on with
  your protocol."
- After its turn, the build finds the messenger in `claude agents --json`
  (through `view.py agents`) by its name, logs its id, and runs
  `claude stop <id>`. A `--bg` session that **finished its turn** stays
  listed (L1). One that was `claude stop`ped is **absent** from the default
  listing (L3).
- A "Workspace not trusted" in its output is a precondition failure (the
  trust row), not a wrong wake design.

**Wake only when the node's turn is finished**: listed `idle` or `done`,
whichever of the two Claude Code reports for a finished `--bg` turn. The
dry run records which one, and D1, D4 and 7.a then use that same set. A node in its wait loop is
mid-turn and pops `node:T` itself every ≤ 60 s. A `SendMessage` to a busy
session queues a stray turn, which would spoil 7.a's `idle/done` evidence.
When the node is not idle, record "picked up by the node's wait loop, no wake".

**A wake succeeded** when, within 120 s, the node is listed `busy`/`working`
or its effect shows (a new ledger row, a drained `node:T` queue, a report).
Otherwise it is a `fail` (D6 failure path).

**The step-0 dry run** tests the real path: a messenger waking an idle `--bg`
session. It does not target the build itself, which is mid-turn and
interactive.

1. Start a disposable target in a **different** trusted directory,
   `$D` = `~/.local/state/quiet-solar/live-437-dry/` (0700, removed with `$L`
   and `$W`), with the stripped environment (`wake.py --target`, which
   `chdir`s to `$D`). The messenger stays in `$W`, so the dry run crosses
   directories as the real wake does (the node runs in `QS_<N>`):
   `claude --bg -n <base>-dry --tools "" --model <fast> "Reply with the single word ready, then end your turn."`
   (`""` gives it no tools. The single-value `--model` that follows ends
   `--tools`' list, so the prompt is not swallowed.)
2. Wait until `view.py agents` lists `<base>-dry` with a finished turn
   (`idle` or `done`; record which), up to 120 s. If it
   is not:
   1. Read its log. It holds no token.
   2. Record the cause, `claude stop` it, and restart it under a new name,
      `<base>-dry-r`, with `wake.py --target --no-tools` (no `--tools ""`;
      its prompt already limits it to one word). Tries A and B then address
      `<base>-dry-r`. A distinct name keeps the logs and the listing unambiguous.
   3. If it still does not start, that is a precondition failure (failure
      path), not a wake-design failure.
3. **Try A:** `PY "$L/wake.py" <base>-dry 0 "dry-run ping"`.
4. **Pass:** within 120 s, `<base>-dry` is listed `busy`/`working`, or
   `view.py logs <its id> --grep 'dry-run ping' --last 5` shows the message.
5. **If try A fails** for a reason other than trust:
   1. Read the messenger's own log. It holds no token, so
      `view.py logs <id> --grep . --first 40` may be read whole. Record the
      cause.
   2. `claude stop` the `h0` messenger, and wait until the target is listed
      `idle` again.
   3. **Try B:** `PY "$L/wake.py" --no-tools <base>-dry 0b "dry-run ping"`,
      judged the same way.
   4. If B passes, every later wake uses `--no-tools`, recorded with D1's
      bounded-risk reasoning.
6. `claude stop` every session of the dry run.

Only if try B fails too is the wake design wrong. Then stop, before anything
exists.

### D3 — The prompt file

`$L/prompt.md` holds what 6a would send:

- the issue and its title;
- the criteria, copied from `$L/criteria.txt`;
- "factory target: `qs-node-implementer` reads its scope from `task show`".

It must not start with `-` (`tools._launchable`). `tool spawn` appends the
Control Plane line and the token **to the argv, not to the file**
(`tools.py:1249`), so `prompt.md` holds no secret. The token does reach
`claude logs` (D9).

`prompt.md`, `resume-msg.txt`, the 7.d paste files, the `answer-<n>.md`
files and the comment and fix-task drafts may contain the DB's path, so they
are written with the **Write tool**, never with a Bash heredoc. The DB-access
hook could deny a build Bash call whose text names `harness_state.db`. Any
deny of the build's own calls is recorded as "build-side, not AC9 evidence".

**Posting.** Every comment and fix-task issue is posted from its checked
draft, with `gh issue comment <n> --body-file <draft>` or
`gh issue create … --body-file <draft>`, never with an inline `--body`. So
the text posted is exactly the text `leakcheck.py` checked.

**One probe line comes first**, for #424 AC9's hook check, since the real
node has no reason to run `sqlite3` on its own:

> probe-4: Before your protocol, run these two commands once each: `<MAIN>/venv/bin/python <MAIN>/scripts/qs/cp.py session status`, then `sqlite3 <MAIN>/harness_state.db 'select 1'`. Whatever the second one does (allowed, denied, refused, error), it is not a blocker: do not retry it, do not work around it, do not block or report on it. Then start your protocol. [probe-4 end]

**Markers.** Each probe message starts with a fixed marker and **ends with
an end marker**, neither carrying a token: `probe-4` … `[probe-4 end]` (this
line), `probe-7b` … `[probe-7b end]` (7.b), `probe-7d-term` …
`[probe-7d-term end]` and `probe-7d-app` … `[probe-7d-app end]` (7.d). The
reason text
`direct access to the Control Plane DB is refused (…); use cp.py`
(`hooks.py:231`) also appears in files the node may read: `hooks.py`, the
tests, `control-plane.md`. A plain count of that text can therefore rise
with no deny at all. So the check reads only the lines **after the probe's
marker**, and ties the deny to the call.

- **The hook-check rule**, the same at step 4, 7.b and 7.d. The build reads
  `view.py logs <sid> --join --after '\[<marker> end\]' --grep 'sqlite3|Control Plane DB is refused|refused|denied' --first 12`.
  That is the first lines after the **first** line matching the **end**
  marker. The probe text itself is always the end marker's first
  occurrence, so a node that later echoes the marker cannot move the
  anchor, and a probe text wrapped over several lines lies wholly before
  it. The build then classifies by reading those lines, never by a count:
  - a Bash tool call to `sqlite3`, whose tool result is the hook's reason
    text → `pass`;
  - a Bash call to `sqlite3` whose result is **not** a deny (e.g. a line
    `1`) → `fail`;
  - a refusal by the model or by `auto`'s classifier, with no `sqlite3` call
    → `not exercised (refused)`;
  - no `sqlite3` call after the marker → `not exercised (skipped)`;
  - the end marker itself is not in the log (`view.py` answers
    `marker not found`) → `not exercised (marker not in log)`. That is never
    `skipped`: first re-read with `--grep . --last 40` to see why.

  The probe text, including its wrapped continuation lines with
  `sqlite3 <MAIN>/…` and "(allowed, denied, refused, error)", ends at the end
  marker, so none of it is read.

  A `not exercised` at step 4 moves the hook check to 7.b and 7.d.

  A skip is a known risk, not a remote one: the node's template treats the
  orchestrator's prompt as context (`qs-node.md.j2:89-90`), and a resume
  message read at `step: done` may be treated the same way. 7.d, a
  maintainer instruction in an interactive session, is the backstop.
- **`session status` may race the spawn.** The node row gets its `session_id`
  only after the identify poll (`tools.py:1064-1078`, `:1283-1294`). An
  early `role: none` is recorded as that race, not as a failure. Cross-check
  it with `task show`'s `nodes[].session_id`. The race affects only
  `session status`: the DB-access deny is static and reads no role
  (`hooks.db_access_denial`, applied before any DB lookup).

This replaces #424's hand-written probe agent, which assumed `qs-node` had no
template. It has one now, so a hand-written `.claude/agents/qs-node.md` would
be overwritten at the next render. The real node covers AC9's three probe
steps:

- `session status`: the probe line;
- the `sqlite3` deny: the probe line;
- the plan report: the node's own round-1 plan report.

The #424 comment says this.

### D4 — The by-hand orchestrator acts

**The queue loop.** After every `wait`, the build drains the orchestrator
queue: `CP msg pop --run R --as orchestrator`, then `CP msg ack <id>
--receipt <receipt>`. It repeats until the pop answers `{"empty": true}` and
logs each message's `id` and `kind`.

The ack is needed because a popped, un-acked message is `in_flight` and
invisible for `VISIBILITY_S` (900 s). It then comes back as if it were new
(`messages.py:183-189`).

**Messages to expect, which are not failures:**
- `report`: one per node round.
- `task_without_node`: it fires once the task (`planning`, `contracted` or
  `building`) has no node in a live state (`spawning`, `running`, `idle`,
  `taken_over`), **and** its last state move or node launch is more than
  `ORPHAN_GRACE_S` = 600 s old (`detectors.py:40`, `:427-443`).
  - It is expected if worktree-create plus spawn take over 10 min.
  - Elsewhere it is a failure-path item. A reap mid-build can fire it at
    once.
  - 7.a–7.d (`ready_to_merge`) stay quiet.
- `node_dead`: only for the **current** generation once it is `reaped`
  (`watchdog._dead_nodes`; a replaced node is `superseded`, never `reaped`).
  It is expected only between the 7.a reap and the 7.b resume. It clears at
  the next watchdog tick after the row leaves `reaped`, which is the resume,
  or 7.c's `node stop` if 7.b is skipped. `msg pop` gives no creation time,
  so it is judged by **drain order**, not by when it is popped. The build
  drains just before and just after the resume (or the stop). A `node_dead`
  for the current generation (`payload.generation`) popped at or before the
  first drain after the resume or stop is expected, however late that drain
  is. One popped at a later drain, or at any other time, goes to the failure path.
- `orchestrator_not_listening` / `orchestrator_dead`: if the build session is
  not listed (step 0).
- `rotate` and question messages.
- `objection`: expected only from the race fallback below. Any other
  `objection` goes to the failure path (a D8 decision) and is recorded
  verbatim.

**`wait`:** `CP wait --run R --timeout <t>`, in the foreground, one call at a
time. The Bash tool timeout is set to 600000 ms. `<t>` is **120** from
`contracted` until the `fix` is sent, and **540** otherwise. On each answer:
- `{"pending": n}` → drain the queue.
- `{"timeout": true}` means no event → read `task show --task T`, then wait
  again.
- Exit 5 with `restart_wait` (the DB was migrated, or a daemon is restarting,
  e.g. after `main` moved) → `CP ensure`, then wait again, and log it.
- Exit 6 (`BUSY`, a lock on its token check) → wait about 5 s, then `wait`
  again, and log it.
- Exit 3 (`STALE_TOKEN`) → the failure path.

The build never polls `gh` in a loop.

**Each act:**

1. **Answer a `rotate`.** When: a `rotate` is popped. It is likely:
   `ROTATE_ROUNDS` = 4 over both loops, and 2 plan rounds plus 2 build rounds
   reach it.
   1. Ack the message.
   2. Wait until `view.py agents` lists the old session `idle`, up to 120 s,
      so that two sessions never work in one worktree at once (its git
      commands are not refused). If it never goes idle, take the failure path.

   maintainer gives the answer (D8). Then `question answer Q-<n> --answer-file $L/answer-<n>.md --reason "<why>"`, then wake (D1).

- `$L/fix-finding.json`:

  (all of these are `ledger._ITEM_KEYS`; `correctness` is a category).
- `$L/fix.json`: `{"finding_id": <id>, "level": "code", "what": "<the body above>"}`.

**Race fallback.** If the task reaches `ready_to_merge` before the fix is
sent, send the `fix` anyway. Record the `objection` it gets, which is the
protocol's answer to a fix after done, and mark "applies the fix"
`not exercised (race)`. If `finding open` itself refuses on a
`ready_to_merge` task, record the refusal, send nothing, and use the same
mark. Either way, the task stays `ready_to_merge`: a fix after done leaves
the finding open and the state unchanged. The node is idle at done, so the
`fix` is woken (D1): the node pops it, acks it, posts the `objection` and
drops it from `pending.json` (`qs-node.md.j2:767-771`), **before** 7.a.
**7.a starts only once** a queue drain after the wake has yielded the
`objection` for this `finding_id` **and** the node is then listed `idle`
again. A `claude stop` before that could cut the turn and leave the entry in
`pending.json`. If no objection arrives within the 120 s wake window plus
one `wait`, record that and go on: 7.b's non-empty `objections` branch
handles it. At 7.b's resume, nothing is then left to process.

A rotation and a question are **not forced**. If none comes, the result is
`not exercised`.

### D5 — Order of the run

The order follows from the code:

- `tool resume` accepts only a node already `reaped`. Its guard runs before
  any step and spends the key on a refusal (`tools.py:526`, `:1348-1353`).
  Its reserve step does call `nodes.refresh` (`tools.py:1310`), but only after
  that guard. So in effect `tool resume` does not reap. The daemon's
  `liveness_watchdog_hook` does (`nodes.refresh` every `LIVENESS_EVERY_S` =
  30 s). #424 AC9's "the next listing-taking call (`tool resume`'s reserve)"
  is wrong in that sense; the #424 comment says so, in these terms.
- `node stop` on a reaped node moves it to `stopped`, which cannot be resumed.
  So the stop is sent while the node is live.
- A bare `--resume` of a session that is still listed forks a copy (#424 L5).
  So the terminal and `/desktop` checks come after `claude stop`.

The order: spawn → plan loop → build loop (+ `fix`) → done → AC9 liveness and
`tool resume` → `stop` while live → `claude stop` → terminal → `/desktop` →
cleanup → record → `rm -rf $L $W $D`.

**Ids.** A `tool spawn` / `tool resume` answer has the node's token at the
**top level**. Its ids are under `result`: `session_id` (full), `short_id`,
`name`, `node_id`, `generation` (`tools.py:591-596`, `:1296-1302`). Every
step uses **the latest answer's** ids, as recorded in the run log. A
`tool resume` rewrites `short_id` (`tools.py:1286-1294`). So 7.c and later use
the resume answer's `short_id`, or the full id, which `claude stop` also
accepts. 7.b compares `session_id` with the one recorded just before the
resume.

| command | id |
|---|---|
| `claude stop` / `claude logs` | the latest `short_id`, or the full id |
| `claude --resume` | the **full** id (L4) |
| `SendMessage` / messenger | `name`: `<base>-T<n>-g<g>`, plus `-r<k>` after a relaunch |
| `view.py logs` for the 7.b and 7.d reads | the **full** `session_id`, which 7.b checks is unchanged (a resume rewrites `short_id`) |

**The stall rule.** A stall goes to the failure path.

| stage | stalled after |
|---|---|
| plan loop | 30 min with no new plan report or ledger round |
| build loop | 45 min with no new ledger row, report or PR push |
| CI | the node's own `blocked` report with `ci_wait` (`CI_WAIT_MAX_S` = 2700 s) |
| CodeRabbit | the node's `cr: skipped` in its report, or 40 min from the request (the node waits about 2 × `CR_WAIT_S` + a cap) |
| wake | 120 s (D1) |

### D9 — Token hygiene

Four helpers, written at step 0 into `$L` with the Write tool (D1's
`--add-dir` allows it; the fallback is a Bash heredoc), then
`chmod 600`. They are protected by `$L`'s 0700 mode and run with `PY`. The token forms are `run:R<n>.<epoch>.<32 hex>`,
`node:N<n>.<gen>.<32 hex>` and `review:V<n>.<0|1>.<32 hex>` (`tokens.py`):
the nonce is the last `.`-field.

- **`tok.py --run | --node | --scrub [--token-file F --nonces-file F]`**
  reads stdin. `--token-file` / `--nonces-file` are for the self-test only.
  - **`--scrub` is text-only and never parses.** It scrubs the whole input,
    which may be plain-text stderr lines and JSON mixed together. Empty input
    prints nothing. It always exits 0. With `run.token` absent (step 0, before
    `run open`), it applies the known nonces and the token shape only.
  - **`--run` / `--node` parse JSON**: their stdout is clean, with stderr sent
    to `$L/err.txt`. With no top-level `token` (an error answer, `BUSY`, …),
    they print the answer and write nothing. `pipefail` keeps `CP`'s exit
    code.
  - `--run` (`run open`, `run claim`): the **only** writer of
    `$L/run.token`. It writes the token atomically (a 0600 temp file, then
    rename), refuses an empty one, and prints the answer without it. If the
    answer is `ok: true` but no token can be parsed (a warning line, a partial
    write), it first writes the raw stdin to `$L/run-answer.raw` (0600), then
    exits non-zero. The failure path then recovers the token from that file
    by hand, or runs `run claim` with the maintainer's OK.
  - `--node` (every `tool spawn` / `tool resume`, whose answers carry the
    **node's** token at the top level): it appends the nonce to
    `$L/nonces.txt` (0600) and prints the answer without the token. It
    **never** touches `run.token`.
  - Every mode then applies `view.py`'s scrub to the **whole printed text**:
    every known nonce, whole and in 8-character windows, and the token
    shape `(run|node|review):[A-Z][0-9]+\.[0-9]+\.[^\s"',]+` → `<token>`. So
    a token echoed in a nested field, such as an error detail or a hint, is
    not printed either. The shape is narrow on purpose: an ordinary
    `"node:T"` field is left alone, so `result.session_id` and the other ids
    stay readable.
- **`view.py agents | logs <id> --grep RE [--first N | --last N] [--join] [--after RE2 | --before RE2] [--from-file F]`**
  is the only way `claude agents --json` and `claude logs` are read.
  - `--after RE2` keeps only the lines after the **first** line matching
    `RE2`, and `--before RE2` only the lines before the **first** one. These
    are the probe markers (D3).
    - `RE2` is matched on the joined text, so a marker split by a wrap still
      matches, then mapped back to its raw-line index.
    - If `RE2` matches nothing, `view.py` prints `marker not found` and exits
      non-zero, never an empty result. The step 4 banner read (`--before`)
      therefore never falls back to the whole log.
  - `--from-file` (self-test only) scrubs `F` instead of running `claude logs`.
  - `--join` folds wrapped and bordered lines before matching: it strips a
    leading or trailing `│` and joins each line to the next.
  - **Without N**, in any mode, it prints only the match count. `--join`'s
    line pairs can count one match twice. No step classifies by a count:
    the counts are context only.
  - `agents` keeps `sessionId`, `id`, `name`, `kind`, `status`, `state`,
    `cwd`, `pid`, `startedAt`, `model` and `agent` per entry, if present, and
    nothing else. The listing's fields are not documented, so the allowlist
    keeps out any argv or prompt field.
  - `logs` runs `claude logs <id>` and strips ANSI codes. On the **whole
    output, before it splits lines**, it removes every known nonce (the run's
    and those in `nonces.txt`), whole with whitespace allowed between
    characters, then in every 8-character window. It also replaces the token
    shape (`tok.py`'s pattern) with `<token>`, twice:
    - on the raw text;
    - on the text with its wraps **folded** (the borders stripped and the wrap
      newlines removed). So an unknown token, such as one the node mints for
      its reviewers, split by a wrap leaves no raw hex fragment on the next
      line.
    The window rule is the one `tools.py:1046-1055` uses: `claude logs` is a
    terminal replay that wraps lines, so a token can arrive split.
  - With N, it then prints the first or last N lines matching `RE` (cut to
    300 characters), plus a match count.
- **`leakcheck.py [--pre-token | --pattern-only] [--token-file F --nonces-file F] <files…>`**
  runs before every post and before every commit, on:
  - the run log (this story);
  - every draft under `$L` (the comments and fix tasks);
  - `$L/diff.patch` = `git diff $(git merge-base origin/main HEAD)` (the
    working tree, staged changes included, against the same base as the
    post-commit check, so a moved `main` adds no noise), of which **only the
    added (`+`) lines** are checked. A
    match on an unchanged context line is not this task's text: it is
    recorded, not treated as a leak.

  It runs **again after each commit and before its push**, on
  `git diff origin/main...HEAD` (added lines). It exits non-zero if:
  - `run.token` is missing or empty, so the check cannot run;
  - the run token, or any 8-character window of any known nonce, appears;
  - any `(run|node|review):[A-Z][0-9]+\.[0-9]+\.\S{8,}` appears.

  A missing or empty `nonces.txt` is fine in every mode: before the first
  spawn there are no nonces.

  **What the node publishes** is checked too, at step 6 (once `ready_to_merge`)
  and again at 8.4 before the close. The inputs, dumped to `$L`:
  - `gh pr view <pr> --json title,body,comments,reviews,commits`;
  - `gh api repos/{owner}/{repo}/pulls/<pr>/comments --paginate` (the inline
    review-thread comments);
  - `gh issue view <N> --json body,comments`;
  - the commits **as pushed**: `git -C <MAIN> fetch origin QS_<N>`, then
    `git -C <MAIN> log -p origin/main..origin/QS_<N>`.

  A hit is a `fail` (failure path): the node leaked a token.

  Its options:
  - `--pre-token`: before `run open`, only the nonces and the pattern are
    checked, since no run token exists yet.
  - `--pattern-only`: before task 9, the same pattern check through the
    helper. **After task 9**, once `$L` and the helper are gone, the review
    phase's commits use this self-contained command instead, which must print
    nothing:
    `git -C <abs QS_437> diff origin/main...HEAD | grep -E '^\+.*(run|node|review):[A-Z][0-9]+\.[0-9]+\.[^[:space:]]{8,}'`,
    plus the commit messages:
    `git -C <abs QS_437> log --format=%B origin/main..HEAD | grep -E '(run|node|review):[A-Z][0-9]+\.[0-9]+\.[^[:space:]]{8,}'`.
  - `--token-file` / `--nonces-file`: **self-test only**. They point at
    synthetic files in `$L/selftest/`, which sit outside `tok.py`'s
    only-writer rule.
- **`wake.py [--no-tools] [--fast-file F] <target> <k> [<message>]`** is
  D1's messenger launcher.
  - `wake.py --target [--no-tools] <name> <prompt>` starts the dry run's
    target the same way: with `--tools ""` unless `--no-tools` is given, and
    its argv written to `$L/wake-<name>.argv`.
  - It strips the environment and launches from `$W` (the plain form) or
    from `$D` (`--target`). It reads `$L/fast.txt` (or `F`, self-test only)
    and refuses if it is empty.
  - For the plain (non-`--target`) form, it writes its argv to
    `$L/wake-<k>.argv`, and names the messenger `qs-wake-<base>-h<k>` with
    `<base>` from `$L/base.txt`.
  - With `--tools=SendMessage`, the messenger cannot read `$L`.

**The self-test** (step 0.2). It records pass or fail per case, never a
synthetic string. Every synthetic value is **built at run time** inside
`$L/selftest/`; none is written in this story. The synthetic token is
`node:N1.1.` followed by 32 random hex characters. The cases:
- **`leakcheck.py`**, with `--token-file` / `--nonces-file` pointing at
  synthetic files:
  - exits 0 on a clean file and on this story: the positive control;
  - exits non-zero on a file holding an 8-character window of the synthetic
    nonce;
  - exits non-zero on the synthetic token;
  - exits non-zero with an empty token file;
  - with `--pre-token`, still exits non-zero on the synthetic token;
  - with no nonces file at all, still exits 0 on a clean file.
- **`view.py logs --from-file`**:
  - on a synthetic line with the nonce spaced out and wrapped across two
    lines, it prints `<token>` or nothing of it;
  - `--join` finds a synthetic hook line wrapped in the middle of
    `Control Plane DB is refused` and framed by `│`;
  - a synthetic **unknown** token (not in any nonces file) wrapped in the
    middle of its nonce leaves no hex fragment;
  - on a synthetic log whose only reason-text hit is a file read after the
    end marker, `--after '\[probe-x end\]' --grep 'sqlite3'` prints **no**
    `sqlite3` tool-call line (so the reader lands on `skipped`, not `pass`);
  - all the `--after` cases below run **with `--join`**, the mode D3 uses.
    `--after` anchors on raw-line indices: output starts at the first raw
    line after the one holding the end marker's closing `]`, so a joined pair
    cannot pull the marker line back in;
  - on a synthetic log where the node **echoes the marker** after its call,
    `--after` on the first end marker still prints the `sqlite3` call and its
    deny;
  - on a synthetic probe paragraph wrapped over 3 or more lines, `--after`
    prints none of it;
  - `--after` / `--before` keep exactly the lines after the first, and
    before the first, matching line.
- **`tok.py`**, with `--token-file` / `--nonces-file` pointing at synthetic
  files and its stdout captured to a file in `$L/selftest/`:
  - `--node` on a synthetic answer with a top-level `token` prints no token,
    appends the nonce to the synthetic nonces file, and leaves the real
    `run.token` and `nonces.txt` untouched;
  - on an answer whose token is also echoed in a nested field, it prints
    neither;
  - on a one-line answer with a top-level token **and** an ordinary
    `"node:T"` field, it still prints `result.session_id`;
  - `--scrub` on an answer echoing the token prints none of it, and writes
    nothing;
  - on an answer with no `token`, it prints the answer unchanged.
- **`wake.py --fast-file <empty file in $L/selftest/> <a target that does not exist> selftest`**
  refuses to run. It runs at step 0.2, before step 0.7, so the base is the
  `live-437` default and the messenger name would be
  `qs-wake-live-437-hselftest`; 8.2 stops it by that name. If it launches anyway, that is a self-test `fail`, and the
  messenger is `claude stop`ped.
- **stderr:** a synthetic command writes a known non-token marker line and
  the synthetic token to stderr, then JSON to stdout. Run as
  `… 2>&1 | PY "$L/tok.py" --scrub`, it passes only if `tok.py` exits 0,
  prints the marker line and the JSON, and prints no token.
- `tok.py --scrub` on an empty file exits 0 and prints nothing.
- `view.py --after` and `--before` with an **absent** marker print
  `marker not found` and exit non-zero.
- `view.py --after` on an end marker **split across a wrap** still anchors
  on it.
- (`wake.py --target`'s launch directory is checked at step 0.8, on the dry
  run's `$L/wake-<base>-dry.argv`, whose first line must be `cwd: $D`.)

**The self-test list is closed.** No further case is added unless a helper
gains a new behaviour.
- Then `rm -rf $L/selftest`.

These helpers guard the token, so all four are tested before use, even though
they are not repo code.

**7.d** moves the node's transcript, its stopped token included, into the
app. A stopped node's token is refused on every write (`STOPPED`), so this is
accepted. The run token never enters the node's transcript.

**`rm -rf $L $W $D` is the very last act** of the build, after commit D is
pushed and the PR is open: the leak check needs `$L` until then.
