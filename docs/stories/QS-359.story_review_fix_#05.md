### [should-fix] SF-1 — Catch non-HomeAssistantError failures from the fallback service call
- File: `custom_components/quiet_solar/ha_model/charger.py:6543` (`_ocpp_set_charge_rate_fallback` service call; branch order at `:6427`/`:6430`; stale comment at `:6549-6555`)
- Severity: should-fix
- Source: qs-review-coderabbit
- Description: In `QSChargerOCPP.low_level_set_max_charging_current`, the
  `if self._ocpp_station_profile_rejected:` fallback branch (`charger.py:6427`)
  is evaluated **before** the `if blocking:` branch (`charger.py:6430`) and
  forwards `blocking` into `_ocpp_set_charge_rate_fallback`. Therefore, once a
  charger has latched into fallback mode (the steady state this feature creates
  for chargers that reject `ChargePointMaxProfile`), a `blocking=True` amp
  caller reaches the fallback with `blocking=True`. A blocking
  `hass.services.async_call("ocpp", "set_charge_rate", …, blocking=True)`
  propagates the handler's exceptions, but the fallback's `except` clauses
  catch only `HomeAssistantError` and `(ValueError, TypeError)` (the latter for
  the clamp). A non-HAE runtime error from the service handler
  (`asyncio.TimeoutError`, `ConnectionError`, `RuntimeError`) escapes and
  aborts the load-management cycle instead of returning `False`. The in-code
  `NH-2` comment (`charger.py:6549-6555`) claiming the fallback "is only ever
  reached with `blocking=False`" is stale/incorrect given this branch order.
- Proposed fix: Separate the current-value clamp from the service call:
  - Keep computing `clamped` with its `(ValueError, TypeError)` → "bad current"
    handling (returns `False`, does not count as a service failure).
  - Wrap the `async_call` so that **any** exception from the service call
    (`HomeAssistantError` and other non-HAE runtime errors alike) returns
    `False` without propagating, reusing the existing warn-once-then-debug
    fallback-failure logging (`_ocpp_fallback_failure_logged`). Practically:
    keep `except HomeAssistantError` for the existing message, then add
    `except Exception` for the same warn-once-then-debug + `return False`
    behavior (or broaden the single clause) — implementer's choice, provided a
    non-HAE service-call error returns `False` and leaves the ack untouched.
  - Replace the now-incorrect `NH-2` comment with an accurate one: the fallback
    IS reachable with `blocking=True` whenever the station profile is latched,
    so its service-call exception surface must match the base number path
    (`except Exception`).
- Tests (TDD):
  - Fallback latched + `blocking=True` + `async_call` raises
    `asyncio.TimeoutError` (a non-HAE error) → `_ocpp_set_charge_rate_fallback`
    returns `False`, the exception does NOT propagate, and the fallback ack
    (`_ocpp_last_fallback_amps`) is untouched.
  - Preserve the existing AC5 fallback-failure (`HomeAssistantError`) and NH-4
    (`bad current`) tests unchanged.

### [nice-to-have] NH-1 — Document rejection *episodes*, not "twice in a row"
- File: `docs/agents/concepts/charger-budgeting.md:88`; `docs/stories/QS-359.story.md` (~line 125 "consecutive", ~line 661 "twice in a row", AC2 body ~539-546)
- Severity: nice-to-have
- Source: qs-review-coderabbit (also raised by qs-review-acceptance-auditor as AC2 text drift)
- Description: The concept doc and story still describe the fallback trigger as
  the charger rejecting `ChargePointMaxProfile` "twice in a row" /
  "consecutive" failures. Since review fix #04 the implementation counts marker
  rejections as distinct **episodes** — a new rejection counts only when it is
  at least `OCPP_STATION_PROFILE_REJECTION_DEBOUNCE_S` (10 s) after the
  previous *counted* rejection, and an accepted write resets both the streak
  and the debounce timestamp. Leaving the docs on the old wording keeps
  re-triggering this finding.
- Proposed fix: Documentation-only. Update `charger-budgeting.md` and the
  QS-359 story (design text + AC2 body) to describe the distinct-episode rule:
  two marker rejections in separate episodes (≥ debounce window apart, with no
  accepted write between) latch the fallback; concurrent/same-episode
  rejections collapse to one. Mention the constant, the
  `_ocpp_last_rejection_counted_time` gate, and the accepted-write reset.
  Preserve historical rationale as review-fix annotations.
