# QS-390 — Pool did not run 12h as expected today

- Issue: https://github.com/tmenguy/quiet-solar/issues/390
- Lane: bug × product (`kind:bug`, `target:product`, `scale:task`)
- Branch: `QS_390`
- Running versions: Home Assistant 2026.9.4, quiet_solar `v2026.09.28.0`
  (product code on this branch = `main`).
- Load: `Piscine` (`QSPool`, `pool` mode auto, target 12 h/day, finish time
  00:00 local, `num_max_on_off` = 8, ~1470 W, switch
  `switch.lhk_filtration_facade`). Home has a DC battery and an inverter limit.

## Symptom

1. On 2026-09-30 the pool ran **~58 min** (15:31 → 16:29 local), then
   quiet_solar announced `COMPLETED: 12h tomorrow 00:00` and turned it off.
2. This had already happened: every day that ended short of 12 h was followed
   by a day of ~1 h (table below).
3. The pump **cycles 5 min ON / 15 min OFF**, with up to **25 switch events in
   one day** against a configured max of 8. That is harmful to the pump motor.
   - At dawn, this happens on every full-cycle day in `history.csv` (09-22,
     09-23, 09-25, 09-26, 09-27, 09-29).
   - In the evening, it happens on days that still need run time after dark
     (09-22, 09-23, 09-25, 09-26, 09-27, 09-29 to varying degrees).

## Root cause

There are three defects. Defect 1 alone explains today. Defect 2, which defect 3
unmasks at night, causes both the harmful switching and the short days that
trigger defect 1.

**RC-1, carry-over from an expired constraint.**
`QSBiStateDuration.check_load_activity_and_constraints`
([bistate_duration.py:1098-1144](../../custom_components/quiet_solar/ha_model/bistate_duration.py))
has three steps involved:

- Detection (1101-1109) flags `mode_changed = True` whenever an existing
  non-override constraint's `end_of_constraint` is not among the new
  constraints' ends.
- `saved_runtime` (1117-1123) is the max `current_value` over all constraints.
- Seeding (1142-1144) is `initial_cv = min(saved_runtime, target)`.

Ordering makes it deterministic. `home.py` runs `update_loads_constraints`
(→ `check_load_activity_and_constraints`, ~2999) **before**
`update_live_constraints` (~3015), which is the step that would ack an expired
constraint as met. `TimeBasedSimplePowerLoadConstraint.is_constraint_met` is
true once `time >= end_of_constraint`, because `always_end_at_end_of_constraint`
is forced True for this type (constraints.py:2687, condition at
[constraints.py:2721](../../custom_components/quiet_solar/home_model/constraints.py)).
So on the first check after a constraint's end, an unmet expired constraint is
still in the list, is taken for a mode change, and its runtime seeds the next
constraint. For the pool the constraint's end is the local-midnight day change.

- The code came from `51b93548` (2026-04-05, "fix: preserve pool runtime on
  mode switch (force-on→default)", which introduced `saved_runtime`). Verified
  with `git show 51b93548`.
- It fires only when the previous constraint ended **unmet**.
- It affects every `QSBiStateDuration` subclass. It fires at the daily rollover
  in default/auto mode, and potentially between consecutive events in calendar
  modes (bistate_duration.py:660-692), where an unmet event that just ended
  seeds the next event.

**RC-2, a forced-ON hold slot is dropped by the power-headroom guard.**
In `MultiStepsPowerLoadConstraint.compute_best_period_repartition`:

1. The available-only loop
   ([constraints.py:2254-2261](../../custom_components/quiet_solar/home_model/constraints.py))
   calls `adapt_power_steps_budgeting(..., max_slot_power_headroom=slot_headroom)`
   and runs `continue` when the result is empty. This happens *before* the
   `forced_slot_commands` handling at 2285-2291 (`j = 0` for a forced ON).
2. So when the load is ON and inside its `CHANGE_ON_OFF_STATE_HYSTERESIS_S`
   (600 s) hold, `_get_forced_slot_commands` returns `{0: ON}`. Whenever the
   headroom (`_max_possible_production − _total_consumed_power`) is below
   1470 W, slot 0 is skipped. That means at night when RC-3 hides the battery,
   and at dawn when the PV surplus is below the pump's power.
3. Every later phase explicitly skips forced slots (green price optimiser ~2348,
   mandatory price fill ~2511). Slot 0 therefore ends `None`.
4. `_adapt_commands` then protects that empty first slot as a requested OFF
   (`protect_before != first_slot`, lines 958 and 1035-1045).
5. The pump is set `idle` 5 min after being turned ON.

The OFF hold is unaffected (`forced_cmd is None` → `j = -1`), so the 600 s hold
protects OFF but not ON.

The 5/15 rhythm follows from this:
- +5 min: the ON hold is dropped → OFF.
- +10 and +15 min: inside the OFF hold (ack + 600 s) → stays OFF.
- +20 min: free again. The phase that switched the pump ON in the first place
  switches it ON again: the mandatory reverse fill in the evening (needed =
  time left), and an undetermined phase at dawn (see Evidence).

`num_max_on_off` is only a planning budget, and it is defeated here because
the OFF is created before `_adapt_commands` runs and is then protected.

**RC-3, regression that unmasks RC-2 at night: the first allocation's headroom
ignores the battery.**
In `PeriodSolver.solve`
([solver.py:1260-1285](../../custom_components/quiet_solar/home_model/solver.py)),
`_bat_possible_disch` stays `None` and is passed to
`_compute_max_possible_production` under the comment "update
max_possible_production with battery info before first allocation".

- Commit `8e37209a` (QS-349 review fix #02, 2026-08-20, first shipped in
  `v2026.08.22.0`) replaced the tuple unpack with `_bcp.*` attribute reads and
  dropped `_bat_possible_disch = _bcp.battery_possible_discharge`. Verified with
  `git show 8e37209a`.
- As a result, the first-allocated constraint sees a PV-only headroom, which is
  negative at night. Constraints allocated later get battery discharge back in
  their headroom through `_allocate_constraints` (~1130).
- So at night, while the pool is the top-priority constraint, a charged battery
  no longer hides RC-2. The `Clim Rémi` constraint allocated before Piscine from
  22:51 restored battery discharge in Piscine's headroom, and the flapping
  stopped.
- RC-3's role at dawn is **undetermined**. SOC is not logged, and the battery
  was trickle-charging. If SOC was above the floor, RC-3 also hid battery
  discharge from the dawn headroom. F2 fixes the dawn OFF either way, and T2-dawn
  runs without a battery so it does not depend on RC-3.

**One-sentence cause:**

- *Today (RC-1):* `bistate_duration.check_load_activity_and_constraints` runs
  before `update_live_constraints` has acked the expired, unmet previous-day
  constraint. It takes that constraint for a mode change and seeds its runtime
  into the new day's constraint.
- *The short days and the harmful switching (RC-2, unmasked at night by RC-3):*
  `constraints.compute_best_period_repartition` drops the forced-ON hold slot
  whenever the headroom-limited command list is empty. At night that list is
  empty because `solver.solve` computes the first allocation's headroom without
  battery discharge. At dawn it is empty because the headroom is below the
  pump's power (RC-3's share there is undetermined).

## Fix plan (decided)

**F1, RC-1** —
[bistate_duration.py](../../custom_components/quiet_solar/ha_model/bistate_duration.py),
`check_load_activity_and_constraints`, mode-change block (1098-1144).
- Add a named module-level constant, `_CYCLE_END_MARGIN = timedelta(minutes=5)`
  (the margin is a user decision, 2026-09-30).
- Constraints whose `end_of_constraint <= time + _CYCLE_END_MARGIN` count as
  the finished previous cycle, whether already ended or ending within 5 min.
- The constant is consulted in exactly two places:
  1. the end-time `mode_changed` detection (1101-1109) skips them. This
     includes a not-yet-expired constraint inside the margin whose end is
     missing from the new ends, e.g. after a finish-time change (T1b-detect);
  2. the `saved_runtime` loop (1117-1123) skips them. This applies to **all**
     constraints there, user-override included, consistent with the accepted
     "last 5 min starts from 0" side effect.
- `_previous_bistate_mode` detection is unchanged.
- The two `push_live_constraint` carries (load.py:2444-2456 and 2469-2485)
  require equal end times, which is never the case across a rollover (`T` vs
  `T + 24h`). F1 alone therefore makes T1 green.
- **Cleanup path of the expired constraint:** it stays in `_constraints` until
  `update_live_constraints` (load.py:2530-2535, called from home.py:3015 on the
  same tick) acks it as met through `is_constraint_met`
  (`always_end_at_end_of_constraint` and `time >= end_of_constraint`,
  constraints.py:2687/2721) and removes it before the solve.
- That ack also sets `_last_completed_constraint` (lcc) to the short cycle
  (load.py:2202). Its two consumers stay safe, as T1c checks:
  - the `push_live_constraint` "same end as last completed" guard and carry
    (load.py:2427-2456) do not fire, because `T ≠ T + 24h`;
  - the metrics `lcc.end == today_utc` rule (bistate_duration.py:387-405) does
    not double count, because the new constraint is pushed on the same tick
    before the ack, so today content exists.
- Accepted side effect: this ack fires `DEVICE_STATUS_CHANGE_CONSTRAINT_COMPLETED`,
  i.e. a `COMPLETED: 12h` notification at midnight for a day that ended short.
  Today the mode-change block deletes it silently. **User accepted,
  2026-09-30.**
- Accepted side effect: a genuine mode switch in the last 5 min of a cycle
  starts from 0.

**F2, RC-2** —
[constraints.py](../../custom_components/quiet_solar/home_model/constraints.py),
`MultiStepsPowerLoadConstraint.compute_best_period_repartition`,
in the `for algo in allocate_available_algos` body (2244-2320, guard at
2254-2261). The change applies to both the `available_only` and the
`available_and_to_deplete` passes and is **not** gated on `algo`.
- When the headroom-limited `adapt_power_steps_budgeting` result is empty,
  `forced_slot_commands.get(i)` is a non-`None` command, **and**
  `not self.load.is_off_grid()`, recompute **without**
  `max_slot_power_headroom`. Amps and phase budgeting stay enforced.
- Off-grid, the production-headroom guard is the only physical ceiling (no grid
  to absorb an overshoot), so it keeps priority over the hold (T2-offgrid).
- Only `continue` if that is still empty, which means amps forbid it and is
  genuinely unsafe (T2-amps). The existing forced handling (2285-2291, `j = 0`) then
  places the command.
- The comment "stronger than the forced slots" keeps its meaning for the
  amps/phase limit only.

**F3, RC-3** —
[solver.py](../../custom_components/quiet_solar/home_model/solver.py),
`PeriodSolver.solve` (~1262).
- Restore `_bat_possible_disch = _bcp.battery_possible_discharge` inside

- Also correct the misleading comment at solver.py:163. It says "solar-only (no

    `_max_possible_production − _total_consumed_power`, i.e. draw from the grid
    or the battery.
  - `power_headroom[i]` goes negative for that slot (2310-2311), so constraints
    allocated later are refused in it.
  - For a non-mandatory or green-only load, `solver.py:1137-1146` may log
    "Non-mandatory load … causes total consumption to exceed production" for
    that slot. This is accepted as the cost of honouring the hold.
  - Behaviour is otherwise unchanged.
- **F3:** every home with a battery, first allocated constraint only. It
  restores pre-`v2026.08.22.0` behaviour, so more loads may legitimately be
  allowed on battery at night, as before the regression.

**Not in scope (decided)**
- **The as-fast-as-possible loop (constraints.py:2060-2094).** Its headroom is
  applied only when `do_use_available_power_only` is set (2064-2066), and it
  never forces `j = 0` for a forced ON. It would also need a change at
  2091-2094. The pool never takes this path (`always_end_at_end_of_constraint`
  blocks push → AFAP, load.py:2543). It is left untouched, and a separate issue
  can be opened if it ever shows up.
- **The just-in-time placement of mandatory time constraints** (reverse fill) is
  by design. It costs one extra OFF/ON pair (18:20 → 21:18) and leaves zero
  slack. After F1 a short day no longer contaminates the next one.
- **No hard command-level `num_max_on_off` cap** (user agreed, 2026-09-30). It
  could block a needed OFF (overrun) or a needed ON (unfiltered pool). No claim
  is made that the planning budget alone caps daily switch-ons at a given
  number.
- **Considered and dropped by the user (2026-09-30), no follow-up issue:**
  (M1) an end-of-window reserve for mandatory constraints, and (M2) keeping an
  already-ON load running instead of OFF → ON later at the same price.
- **The broader "one cycle accumulator per day" refactor** (option B, which
  would replace the three carry paths) was offered and set aside by the user.
