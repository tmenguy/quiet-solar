### [should-fix] S1 — degraded `gh` lookup prints the "add a label" STOP first
- File: `scripts/qs/agent_templates/_macros.md.j2:19-54` (`implement_routing`),
  `tests/qs/agents/test_handoff_macro.py` (`test_implement_variant_routes_by_declared_target`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: "For any other value (empty — no or ambiguous label, **or a
  degraded `gh` lookup**)" routes a failed lookup into the "no single
  target:* label … Label it with exactly one of …" STOP + add-label
  commands; the "lookup itself failed" paragraph only comes after. A user
  whose issue already carries `target:product` may follow the printed
  remedy and add `target:factory`, creating the both-labels state.
- Proposed fix:

    first: "If it exits non-zero / prints no JSON, or returns empty
    `labels` **and** `title`, the `gh` lookup failed: **STOP** and print
    `Cannot pick the implement variant: the issue lookup failed (gh) — retry, or tell me which variant to run.`
    Do **not** print the label message or commands below." (stable prefix kept).
  - Otherwise take `target`. Restrict the existing "For any other value"
    STOP to a successful lookup: "(empty — no or ambiguous `target:*` label)";
    drop "or a degraded `gh` lookup".
  - Delete the trailing "If `context.py` exits non-zero … lookup itself
    failed" paragraph (now handled up front).
  - Test: pin the lookup-failure message literal (with prefix), assert it
    appears **before** the label message, keep the "exits non-zero"
    assertion, assert "or a degraded `gh` lookup" absent — both harnesses,
    create-plan + review-task.
