## Findings to fix

### [must-fix] G1 — Restore: the overwrite and the fix-up are two commits, and the F4 handler misses `CpError`
- File: `restore.py:194-260` (`_restore_into`, `_fix_up`, `_carry`), `db.py:52-59` (`db.begin`)
- Severity: must-fix
- Source: qs-review-coderabbit (Major) and qs-review-edge-case-hunter
- Description:
  - `source.backup(conn)` commits the backup into the live DB before the
    `BEGIN IMMEDIATE` fix-up transaction runs (waiters, `daemon_lease`,
    carried selfcheck meta). Between the two commits, a concurrent hook can
    see the backup's raw state.
  - `db.begin` turns `OperationalError` into `CpError("BUSY"|"INTERNAL")`,
    which the new `except sqlite3.Error` does not catch. The user then gets
    a bare `BUSY` with no `replaced` pointer, and the lease is not cleared.
    This is exactly what F4 was meant to prevent.
  - The F4 hint says "retry the restore". A retry's `_carry` would read the
    already-restored (backup) waiters and meta, not the real pre-restore
    ones.
- Proposed fix: make the restore a single write to the live DB.
  1. Copy the chosen backup to a private staged file next to the live DB
     (0600, under the same private dir, a `.partial`-style name).
  2. Apply the whole fix-up to the staged copy in one transaction: carried
     waiters and selfcheck meta (captured from the live DB first), and the
     lease cleared.
  3. Do one `staged.backup(live_conn)` into the live DB.
  4. Unlink the staged copy (in `finally`).

  Error handling:
  - A fix-up failure now happens before the live DB is touched, so it is a
    plain refusal with nothing changed.
  - Catch `(sqlite3.Error, errors.CpError)` around the final copy. Keep the
    `replaced` pointer in its error.
  - Word every hint so it never presents a retry as lossless: the
    pre-restore data is in `<replaced>`.

  Tests:
  - an injected fix-up failure (including `db.begin` raising
    `CpError("BUSY")`) → the live DB is byte-identical and no staged file is
    left behind;
  - a failure of the final copy → the error names `replaced`;
  - the happy path is unchanged.

### [should-fix] G2 — F9 regression: a git timeout or a missing git now burns the whole overlap budget
- File: `detectors.py:155-179` (`_files`, `_conflicts`), `_Git.run` / `GitFailed`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `runner.run` returns 124 (timeout) or 127 (exec failure)
  instead of raising, and these become `GitFailed`. F9 now isolates those
  per branch and per pair. Up to `OVERLAP_MAX_CALLS` × `HOOK_SUBPROCESS_S`
  (about 400 s) can then be burned in one tick, starving the other hooks.
  With 127 the walk never completes. Failed results are not cached either,
  so a resumed walk re-runs them.
- Proposed fix:
  1. Carry the returncode on `GitFailed`. On 124 or 127, re-raise and abort
     the whole walk (the pre-F9 behaviour). Isolate only real git errors.
  2. Cache a failed diff or pair for the rest of the walk, so a resumed
     walk does not retry it.

  Test: a stub runner returning 124 for every `diff` → exactly one call,
  then the walk aborts.

### [should-fix] G3 — Watchdog: building the messenger args is outside the F1 guard
- File: `watchdog.py:274` (`_launch` → `messenger_args` → `_messenger_model`, lazy `import models`)
- Severity: should-fix
- Source: qs-review-blind-hunter and qs-review-edge-case-hunter
- Description: an `ImportError` or `KeyError` here escapes `_ladder`. It
  aborts the list comprehension (`watchdog.py:133`), so no run gets
  `orchestrator_not_listening` and the alert sync is skipped on every tick.
- Proposed fix: build `args` inside the same pre-claim `try` as the
  directory step. On failure, log once and `return False` (a failed launch,
  with nothing claimed).
  - Test: `_messenger_model` raises → no row, and
    `orchestrator_not_listening` is raised.

### [should-fix] G4 — Hook routing: a transient SQLite error now drops a routed alert for good (side effect of F2)
- File: `hookroute.py:81-100` (`route_locked`)
- Severity: should-fix (promoted: it is a regression from the round-1 fix)
- Source: qs-review-edge-case-hunter
- Description: the per-event SAVEPOINT treats every exception as a poisoned
  event, so a transient error (`SQLITE_FULL`, `IOERR`, `BUSY`) skips the
  event and moves the cursor past it.
- Proposed fix: re-raise `sqlite3.OperationalError` and
  `errors.CpError(code="BUSY")`, so the whole batch retries on the next
  tick. Isolate only data errors (`ValueError`, `UnicodeError`,
  `IntegrityError`, `CpError` USAGE…).
  - Test: an `OperationalError` on one event → the cursor does not move and
    the hook raises.

### [should-fix] G5 — Rotation: one malformed `.partial` name stops all pruning (side effect of F17)
- File: `backups.py:96-103` (`rotate`)
- Severity: should-fix (regression from the round-1 fix)
- Source: qs-review-edge-case-hunter
- Description: `PARTIAL` only checks for digits. A stamp like `20261399T…`
  makes `strptime` raise `ValueError`, which aborts `rotate` before the
  periodic pruning, and it keeps happening while that file exists.
- Proposed fix: `try/except ValueError: continue` for each partial file.
  - Test: an invalid-date partial plus prunable periodic copies → the
    periodic copies are still pruned.

### [should-fix] G9 — Restore: carried waiters whose run is not in the backup (verify)
