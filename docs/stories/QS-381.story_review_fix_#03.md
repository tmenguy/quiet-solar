## Findings to fix

### [must-fix] An unavailable phase switch blocks the group forever again (a regression from fix #02, item 3)
- File: `custom_components/quiet_solar/ha_model/charger.py:5369-5376` (the `_has_real_phase_reading()` gate in `_ensure_correct_state`), with the helper at `:2546-2557`
- Source: qs-review-edge-case-hunter (must-fix) + qs-review-acceptance-auditor (must-fix, reproduced: 45 min, `first_unblock=None`) + qs-review-blind-hunter (should-fix)
- Description: the gate sits in front of **every** phase branch: follow,
  normal launch and D1 adoption. It has no time bound. With the switch
  `unknown`/`unavailable`/missing and 1 phase expected:
  - `is_ok_to_launch` is never reached, so `_num_launched` never counts up
    and D1 (`not can_launch()`) can never fire;
  - `_ensure_correct_state` returns False forever, and the group returns
    `[]` forever.

  That is the A1 forever-block. The story explicitly lists "or it is
  unavailable (it then reads as 3 phases)" as a cause to bound, and argues
  that adopting the phantom 3 is safe. AC 4(a) uses `unavailable` as its
  fixture. The A4(a) test was switched to `off` in fix #02, which hides the
  regression.
- Proposed fix (story-aligned, route (a)):
  1. Narrow the `_has_real_phase_reading()` gate to the **follow branch
     only**. Inside the follow window with a phantom reading, skip the
     follow and fall through to the normal `is_ok_to_launch` / D1 adoption
     path. A launch on an unavailable entity is harmless:
     `low_level_set_charging_num_phases` catches the error, and
     `register_launch` still counts. Retry exhaustion then adopts the
     phantom 3 in bounded time (~196 s), which is conservative for
     per-phase current, as the story says.
  2. Keep setting `_phases_adopted_at` on every D1 adoption, including a
     phantom one. When the real reading returns inside the window, the
     follow branch (its reading is now real) follows it with no switch
     command. That also closes round-1 N1's needless extra switch.
  3. Reverse `test_unavailable_phase_switch_past_delay_is_not_adopted`.
     With the switch `unavailable` and 1 phase expected, 4 launches are
     followed by adoption of 3 at the same offsets as A1, and the group
     unblocks on the next cycle.
  4. Add a test: phantom adoption, then the switch returns to real `on`
     (1 phase) inside the window. It must be followed (expected → 1) with
     no `set_charging_num_phases` call and no reboot.
  5. Keep `test_unavailable_phase_switch_within_window_does_not_follow`,
     but make it assert the fall-through: no follow, the normal launch
     path is taken, and the group unblocks in bounded time.
  6. Restore AC 4(a)'s `unavailable` fixture in
     `test_start_stuck_with_phase_mismatch_rearms`. If the `off` variant
     adds value, keep it as a second parametrisation.
  7. Update the doc bullet (`docs/agents/concepts/charger-budgeting.md`,
     "Phase switch that never follows") and the story's fix-#02 note so
     that both say a phantom reading is never *followed* but can be
     *adopted* after the launch retries run out.

### [should-fix] The `apply_budgets` phase guard compares against the frozen snapshot, not the live expected value
- File: `charger.py:2343` (`new_num_phases != init_phase_num`)
- Source: qs-review-edge-case-hunter (nice-to-have) + qs-review-acceptance-auditor (nice-to-have #5: the replay-drop guard is not proven necessary by any test). Promoted because they compound.
- Description: `init_phase_num` is `cs.current_active_phase_number`, frozen
  when the snapshot was taken. Suppose a replay happens after the expected
  value changed underneath without an adoption marker, e.g. via the idle
  path at `:5998`. Then a budget with `budgeted == snapshot init != live
  expected` is skipped, and the charger gets amps budgeted for the other
  phase count.
- Proposed fix: compare against the live value
  (`new_num_phases != cs.charger._expected_num_active_phases.value`). The
  stale-replay drop (`:2258-2270`) becomes the real protection for the
  adopted case. Do **not** widen that drop to every mismatch: the legitimate
  3→1 split replay must still go through.
- Tests:
  - make `test_stale_replayed_budget_after_follow_does_not_revert_adoption`
    discriminate. Use a snapshot taken before the follow, with
    `budgeted 1 / current 3` or equivalent, so that only the drop guard
    stops the revert. Also assert that the early return skips the replay;
  - add the idle-path case: expected changed underneath with no marker,
    and the budget's phase count is still applied;
  - keep the 3→1 split replay test green.
