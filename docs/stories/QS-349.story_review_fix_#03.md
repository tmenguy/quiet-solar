## Findings to fix

### [must-fix] T1 — Charge-branch nearest-snap has no re-clamp → eternal retry on every battery command (regression)
- File: `custom_components/quiet_solar/ha_model/battery.py:195` (`_number_entity_target`, `snap_up=False` branch)
- Severity: must-fix
- Source: qs-review-edge-case-hunter
- Description: Fix #02's R1 re-clamped the ceil (discharge) branch to
  `ent_max` (lines 192-193), but the nearest-snap charge branch got no
  re-clamp on either side, so the snap can escape the entity range in
  both directions. (a) Charge entity `max: 5000, step: 300` — every
  battery command emits `max_charging_power = 5000` via
  `_command_to_values` → `round(5000/300)=17` → 5100 →
  `number.set_value(5100)` raises out-of-range (caught + logged), the
  value never lands, the probe expects the 5100-landed value → **eternal
  retry on every battery command**. (b) Charge entity
  `min: 100, step: 250` with `CMD_FORCE_CHARGE power_consign=100` →
  `round(0.4)=0` → write 0 < min → same eternal retry. This is a
  **regression**: pre-PR code (raw `int(clamped)` write, no step snap)
  landed 5000 fine on such entities.
- Proposed fix: After the nearest snap, re-clamp `write_value` to
  `[ent_min, ent_max]` (both sides — mirror the ceil branch's max
  re-clamp and add the min side; see also T5's step-aligned-cap note).
  Test: charge entity with `max` not divisible by `step` (5000/300 →
  lands 4800 or the entity max per chosen policy, in range, probe
  confirms) and the `min: 100, step: 250` case.

### [should-fix] T2 — Charge-leg probe expectation misses the domain clamp
- File: `custom_components/quiet_solar/ha_model/battery.py:143-145` (probe) vs `:343-344` (write)
- Severity: should-fix (CodeRabbit rated Major; repo-aware analysis shows
  pre-existing and latent — no production caller sets a consign on the
  battery, discharge leg immune by construction)
- Source: qs-review-coderabbit + qs-review-edge-case-hunter + qs-review-blind-hunter + qs-review-acceptance-auditor
- Description: `set_max_charging_power` clamps power to
  `[min_charging_power, max_charging_power]` before writing, but
  `probe_if_command_set` maps the **raw**
  `cmd_to_vals["max_charging_power"]` through `_charge_number_target`
  without that clamp. `execute_command(CMD_FORCE_CHARGE,
  power_consign=6000)` with `max_charging_power=5000` → entity lands
  5000, probe forever expects 6000 → the exact silent eternal-retry
  class R5 was fixing, on a public API path.
- Proposed fix: Apply the same `[min_charging_power,
  max_charging_power]` clamp to the probe expectation — preferably by
  moving the domain clamp inside `_charge_number_target` so write and
  probe share it. Test: consign-above-max → probe confirms the clamped
  landed value.

### [should-fix] T3 — Ceil snap-up also applies to the discharge restore write
- File: `custom_components/quiet_solar/ha_model/battery.py` (`_discharge_number_target` callers: `_command_to_values` restore value, `set_max_discharging_power`)
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: `CMD_GREEN_CHARGE_AND_DISCHARGE` restores
  `max_discharging_power` through the same `snap_up=True` path. On a
  stepped entity whose step doesn't divide the configured max (configured
  max 5000, `step: 300`, entity max >= 5100) the restore lands **5100 W —
  above the user-configured hardware discharge limit** by up to one
  step. Snap-up is only justified for the safety *floor* (a minimum must
  never be lowered); a *maximum* must never be raised.
- Proposed fix: Snap up only for the floor value; use nearest-snap
  (with T1's two-sided re-clamp) — or snap-down — for the restore/max
  value. Test: stepped entity, restore write lands <= configured max.

### [nice-to-have] T5 — FP-unsafe `ceil(x/step)` can overshoot on exact step multiples
- File: `custom_components/quiet_solar/ha_model/battery.py:191` (`_number_entity_target` ceil branch)
- Severity: nice-to-have
- Source: qs-review-blind-hunter (+ qs-review-edge-case-hunter: verified
  it can only overshoot, never lower the floor; write/probe agree so no
  retry loop)
- Description: A value that is an exact step multiple can divide to
  `n.000…01` and ceil to `n+1`, overshooting by a full step (common with
  kW entities using step 0.1). Related: re-capping the ceil result to
  `ent_max` can produce a non-step-aligned write when `ent_max` isn't a
  step multiple.
- Proposed fix: `math.ceil(write_value / step - 1e-9)`; when capping to
  `ent_max`, floor the cap to the nearest step multiple <= `ent_max`.
  Tests: exact-multiple floor stays exact; non-step-aligned `ent_max`.

### [nice-to-have] T6 — `_coerce_float` hardening gaps (negative, non-finite, charge max)
- File: `custom_components/quiet_solar/home_model/battery.py:18-28, 35, 55-57`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter
- Description: (a) A hand-edited `battery_max_discharge_power_value:
  -100` coerces fine and produces a **negative safety floor**
  (`min_discharging_power = -100`): green-only then emits -100
  (out-of-range → eternal retry) and the solver's cap
  `min(available_power, -100)` turns every demand slot into a forced
  100 W phantom charge. (b) A `"nan"` string coerces
  (`float("nan")` succeeds) and the NaN flows into `get_charger_power`,
  tripping the solver's NaN guard as a hard `ValueError` mid-solve.
  (c) `max_charging_power` (and capacity/SOC values) are not coerced at
  all — the same corrupt-entry scenario crashes later arithmetic.
- Proposed fix: Reject non-finite values in `_coerce_float`
  (`math.isfinite` → fallback), clamp the max-discharge operand to
  `max(0.0, ...)` before the floor clamp, and apply `_coerce_float` to
  `max_charging_power`. Tests: negative, `"nan"`, corrupt charge max.

### [nice-to-have] T7 — Non-numeric entity attributes crash every write and probe
- File: `custom_components/quiet_solar/ha_model/battery.py:178-187`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: `float(ent_min)` / `float(ent_max)` / `float(step)` on
  non-numeric attribute values raise `ValueError` with no guard, and the
  helper is called *outside* the service-call try/except in both
  `set_max_discharging_power` (line 261) and `probe_if_command_set`
  (line 133) — a single corrupt attribute (e.g. `step: "unknown"` from a
  custom integration) makes every write and probe raise instead of
  degrading. The docstring's "falls back to a raw W passthrough when the
  entity attributes are unreadable" is only honored for the state today.
- Proposed fix: Coerce the three attributes through the same tolerant
  `try/except (TypeError, ValueError)` → treat-as-absent pattern, plus a
  test with a non-numeric `step`.
