### [should-fix] R5-S1 — a `cr: trigger` can survive a catch-up push and be re-called for the catch-up head
- File: `scripts/qs/agent_templates/qs-node.md.j2`:
  - the catch-up push write, ~:372-374;
  - the catch-up parenthetical, ~:381-383;
  - the build step 2 moved-head sentence, ~:327-328;
  - the "Between loop calls" `cr: trigger` bullet, ~:573-575.

  Also `docs/workflow/control-plane.md:676`.
- Severity: should-fix
- Source: qs-review-blind-hunter and qs-review-edge-case-hunter, merged. Fix #04's catch-up wording introduced it.
- Description: the moved-head skip is stated only in build step 2, and the catch-up push write doesn't touch `cr`.
  The catch-up parenthetical then says the wait runs on "`cr` while it is `trigger` or `pending`", and "always re-call
  the tool first" applies. So after a `conflict` exit with `cr: trigger`, followed by a catch-up push, the node
  re-calls `tool coderabbit-trigger`. That posts `@coderabbitai review`, which reviews the **catch-up head**. This
  breaks "No CodeRabbit request is made for a catch-up head", uses up a `CR_MAX_REVIEWS` slot, and then waits a full
  `CR_WAIT_S` for a `cr_head` review that never comes.
- Proposed fix — use exactly this wording, where possible:
  1. Catch-up push write (~:372-374): "`round.json` gets, in one write, `head` = the new sha, `pushed_at` =
     `wait_from` = now, and a `cr: trigger` becomes `cr: skipped` ("head moved")."
  2. Catch-up parenthetical (~:382-383): "(and `cr` while it is `pending` for `cr_head`; `CAP` 180 then)".
  3. Build step 2 (~:327-328): keep the sentence and add "(the catch-up push writes it, step 7)".
  4. The "Between loop calls" `cr: trigger` bullet: "`cr: trigger` (only while `head` is `cr_head`; otherwise `cr:
     skipped`, "head moved", no re-call) → re-call `tool coderabbit-trigger` …".
  5. `control-plane.md:676`: "a moved head skips a `trigger` without a re-call (the catch-up push writes it; a
     `pending` review of `cr_head` keeps its window)".
- Tests (`tests/qs/test_render_agents.py`):
  - update `test_node_catch_up_polls_a_pending_review_by_the_same_rule`: the new parenthetical, and assert that
    "`trigger` or `pending` for" is gone;
  - add an assertion that the catch-up push write carries the "head moved" skip;
  - pin the bullet guard.
- After editing, re-read every `cr:` / `cr_head` / `cr_from` sentence in the template once and confirm there is a
  single rule.

### [should-fix] R5-S2 — a truncated Actions-suite page can read red
- File: `scripts/qs/control_plane/ciwatch.py` `_verdict` (~:162-170)
- Severity: should-fix
- Source: qs-review-coderabbit (Major on head `38dba8f6`). The blind hunter and edge-case hunter raised it as a
  nice-to-have in round 3. It is promoted now: four reviewers have raised it, and the fix is one line.
- Description: the `FAILURE` check runs before `hasNextPage` is consulted. A superseded failed suite on page 1, whose
  newer run is on page 2, gives a false `ci_red`.
- Proposed fix: after `latest = _latest_per_workflow(actions)`, if `suites["pageInfo"]["hasNextPage"]` is true,
  return `("PENDING", len(actions))` before the FAILURE check. Use a defensive `.get()`, matching the `nodes` guard.
  - Docs: "a truncated list always reads `pending`", in the module docstring and in the CI-watcher paragraph of
    `control-plane.md:278`.
  - Test: a truncated page with a visible failing suite → `PENDING`.
