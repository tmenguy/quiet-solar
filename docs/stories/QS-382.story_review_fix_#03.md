### [should-fix] Main-checkout lock — coverage, races, expiry (R-lock)
- File: `docs/epics/QS-369.md:371-378`, `docs/epics/QS-369.md:762-765`, `docs/epics/QS-369.md:755`, `docs/epics/QS-369.md:813-815`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: (1) The frozen pipeline's `finish-task` runs `git -C "$MAIN_DIR" fetch / checkout main / pull --ff-only` + `render_agents.py` on main (`scripts/qs/agent_templates/qs-finish-task.md.j2` l.307-311) and `setup-task` runs `setup_task.py` from main — neither takes a state-DB lock, and both pipelines run side by side (l.453-460). (3) No expiry: a holder archived/stopped mid-hold (R5, R9 did exactly this) blocks every later fast-forward and setup. (4) l.755 "a lock that serialises integrations" and the new lock sit side by side with no relation stated.
- Proposed fix: Apply **R-lock** from the summary in l.371-378; mirror in the child-5 pointer (l.762-765) and the child-7 pointer (l.813-815: "the frozen pipeline's main-checkout writes are unserialised — open point"); at l.755/765 one clause: "separate from the integration lock".
