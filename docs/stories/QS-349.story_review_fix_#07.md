## Findings to fix

### [should-fix] X1 — Zero-rule probe path untested
- File: `tests/test_ha_battery.py` (new test in `TestQSBatteryDischargeFloor`); rule at `custom_components/quiet_solar/ha_model/battery.py:198-207`
- Severity: should-fix
- Source: qs-review-acceptance-auditor
- Description: The zero rule is pinned solely by the pre-existing U7
  test through the write-skip path (verified empirically: disabling the
  rule fails exactly that one test of 98). The probe path — a zero
  reading strictly within one step of a non-zero, non-aligned expected
  value must NOT confirm (the exact false-confirm-of-a-zeroed-floor
  hazard the rule exists for) — has no test; moving the zero check after
  the step-window check would silently regress with everything green.
- Proposed fix: One probe test — floor 300, entity
  `{unit: kW, max: 0.05, step: 0.1}` (expected landed 50 W, step_w
  100 W), entity reading `"0"` → `probe_if_command_set(CMD_GREEN_CHARGE_ONLY)`
  is False.

### [should-fix] X2 — `OverflowError` escapes the W5-narrowed excepts
- File: `custom_components/quiet_solar/ha_model/battery.py:498, :530` (`get_max_discharging_power` / `get_max_charging_power`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `except (TypeError, ValueError)` covers non-numeric and
  NaN, but `int(round(float("inf")))` raises **OverflowError**
  (verified), which the replaced bare `except:` used to swallow. The
  getters are called unwrapped from `clamp_charge_power` (home.py:1683)
  and charger budgeting (charger.py:1430/1767/2712), where the exception
  now propagates instead of the documented "None on unparsable"
  contract. Reproduces with an entity state of `"inf"`/`"1e999"`.
- Proposed fix: Pass the parsed value through the shared
  `coerce_finite_float(...)` and return None on non-finite (matches
  `_entity_step`'s posture) — cleaner than widening the tuple. Test:
  entity state `"inf"` → getter returns None, no raise.

### [nice-to-have] X3 — Latch cleared against the read value instead of the expected landed value
- File: `custom_components/quiet_solar/ha_model/battery.py:170-173, :232-244`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: Under the W1 echo tolerance a probe can confirm with
  `read != expected landed`; `_clear_number_divergence_latch(ent, read)`
  then fails to drop the still-current entry keyed on the landed value —
  wait, inverse: it drops nothing for the landed key and the divergence
  is re-warned every execute/probe cycle. Repro: floor 500, entity
  `{min: 1150, step: 500}`, configured max 1200 → landed 1200 warned;
  quantizing device echoes 1000 → probe confirms via `|1000-1200| < 500`,
  clear misses the `1200` key → next execute re-warns. W3 tests cover
  only exact-read confirms.
- Proposed fix: Clear with the expected landed value
  (`expected_max_discharge` / `expected_max_charge`) instead of the
  read — identical behavior when read == expected (tests :1008/:1031
  unaffected). Test: echo-confirm scenario warns once, not per cycle.

### [nice-to-have] X4 — Unbounded latch growth under varying consigns
- File: `custom_components/quiet_solar/ha_model/battery.py:364-369`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter
- Description: The dedupe key includes `int(round(request_w))`; a
  permanently pinned entity (e.g. charge max 4000 < configured max)
  under solver-produced varying `CMD_FORCE_CHARGE.power_consign` values
  mints one new set entry + one WARNING per distinct consign, forever.
  Memory trivial, log spam and set growth unbounded.
- Proposed fix: Bucket the request in the key (round to the entity step
  or to landed_w) or cap the set (drop-oldest), keeping the tested
  per-distinct-request semantics for deliberate distinct writes.

### [nice-to-have] X5 — Exact-match fallback for invalid or oversized converted steps
- File: `custom_components/quiet_solar/ha_model/battery.py` (`_entity_step_w` / `_number_reading_matches`)
- Severity: nice-to-have
- Source: qs-review-coderabbit (+ edge-case-hunter's round-6 corrupt-step remark)
- Description: `_entity_step` rejects invalid raw steps, but the
  converted `step_w` is not validated or bounded — a corrupt huge finite
  step widens the echo-tolerance window arbitrarily, re-opening
  stale-reading false-confirms.
- Proposed fix: Use exact matching when either the raw step or the
  converted `step_w` is non-finite or outside a sane bound (e.g.
  step_w > the entity range or > domain max), preserving current
  behavior for valid bounded steps. Test: huge step attribute → exact
  match required.

### [nice-to-have] X6 — Absolute 1e-6 alignment tolerance is fp-fragile
- File: `custom_components/quiet_solar/ha_model/battery.py:~175` (alignment check)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: `abs(ratio - round(ratio)) <= 1e-6` on
  `write_value / step_u` misclassifies large values with tiny steps
  (10 000.3 W, step 0.1) as non-aligned, loosening the probe to the
  `< step_w` window.
- Proposed fix: Relative tolerance (`math.isclose` with rel_tol, or
  compare `abs(write_value - round(ratio)*step_u)` against an absolute
  epsilon in value units). Test: large-value/small-step aligned write
  classified aligned.

### [nice-to-have] X7 — `coerce_finite_float` accepts booleans
- File: `custom_components/quiet_solar/home_model/battery.py:~19`
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: `float(True) == 1.0`, so a corrupt `true` in a
  hand-edited entry silently becomes 1 W / 1 % instead of falling back
  to the default — the helper's own threat model.
- Proposed fix: Reject `bool` explicitly (`isinstance(value, bool)` →
  fallback), plus a test.

### [nice-to-have] X8 — Debug log on the write-skip for half-applied commands

- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: `set_charge_from_grid` is awaited before the

- Proposed fix: One `_LOGGER.debug` (or info) at the skip site naming
  the entity and the deferred value.

### [nice-to-have] X9 — De-overlap the write-skip wrong-value test leg
