## Findings to fix

### [should-fix] A 3→1 split replay undoes a D1 adoption that landed back on the snapshot's phase count
- File: `custom_components/quiet_solar/ha_model/charger.py:2711-2722` (`is_phase_snapshot_stale`), with the replay at `:2266-2276` and `:2349-2357`
- Source: qs-review-edge-case-hunter (reproduced with a scratch test)
- Description: the stale test only compares the snapshot's
  `current_active_phase_number` with the live expected value.
  Sequence:
  1. Two phase-switching chargers give `len(remaining_cs) > 1`. The first
     half applies the 3→1 `cs_copy`, so expected becomes 1.
  2. The switch stays `off`. After about 196 s D1 adopts 3 and sets the
     marker.
  3. The next healthy cycle replays the original `cs` (current 3,
     budget 1). It doesn't look stale, so
     `set_expected_num_active_phases(1)` runs: the marker is cleared, a
     5th+ switch command is sent, another ~196 s of group block follows,
     and the 30 min spacing is skipped.
- Proposed fix: while an adoption is live, a snapshot is also stale when
  its **budgeted** phase count differs from the live expected value:
  `adopted and (cs.current_active_phase_number != exp or cs.budgeted_num_phases != exp)`.
  This is only reached on the `check_charger_state=True` replay path, so a
  fresh budget is unaffected.
- Test: 3→1 split, D1 adoption back to 3, then replay. Expected stays 3,
  the marker is kept, no 5th switch call is sent, and the replay is
  dropped. The existing 1→3 / 3→1 split tests stay green.

### [should-fix] D1 re-adoption inside a live window restarts the window
- File: `charger.py` D1 adoption branch (`self._phases_adopted_at = time`, ~:5452)
- Source: qs-review-blind-hunter
- Description: after a follow, an unavailable reading falls through to
  launch, and 4 launches later D1 adopts again. That sets
  `_phases_adopted_at = time` again and opens a fresh 30 min window,
  escaping fix #02's rule that the window counts from the original
  adoption.
- Proposed fix: in D1, only stamp `_phases_adopted_at` when no adoption is
  live (`is None`). Otherwise keep the original stamp.
- Test: adopt, follow a real reading, go phantom, D1 re-adopts; assert
  `_phases_adopted_at` still equals the first adoption time.

### [should-fix] Coverage gap: the within-window phantom fall-through doesn't assert bounded unblock
- File: `tests/test_bug_381_non_converging_group.py:405-427` (`test_unavailable_phase_switch_within_window_falls_through_to_launch`)
- Source: qs-review-acceptance-auditor (fix #03 item 5, third clause missing)
- Proposed fix: extend the test (or add a sibling) to drive the group
  until `cs_healthy in actionable`. Bound it at
  `PHASE_ADOPT_OFFSET_S + 2*STEP` from the phantom's first cycle, and
  assert expected becomes 3.

### [should-fix, promoted] A dead switch repeats the adoption cycle every 30 min
- File: `charger.py:2848-2852` (`get_stable_dynamic_charge_status`, the `[1, 3]` phase offer)
- Source: qs-review-edge-case-hunter (nice-to-have). Promoted because it
  is a periodic group block on a dead switch, the issue's theme.
- Description: once the 30 min spacing expires, the solver can ask for
  1 phase again on a switch with no real reading. That means 4 launches,
  ~196 s of group block and a re-adoption, repeated every 30 min without
  end.
- Proposed fix: offer only `[current]` when `not self._has_real_phase_reading()`.
  Check that chargers without a phase switch are unaffected
  (`_has_real_phase_reading` returns True for them).
- Tests: a phantom reading offers only the current phase count; a real
  reading still offers `[1, 3]` once the spacing allows.
