## Findings to fix

### [should-fix] SF-1 — Latch the clip notification even when a notify channel raises a non-HomeAssistantError
- File: `custom_components/quiet_solar/ha_model/charger.py:6642` (`_notify_ocpp_clip`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: The two notification channels are each wrapped in
  `except HomeAssistantError`, but `_ocpp_clip_notified = True` is only set
  *after* both awaits. If a channel raises a non-`HomeAssistantError`
  (most concretely `self.home is None` → `AttributeError` on
  `self.home.async_notify_all_mobile_apps`, or any raise before the inner
  service-call try), the exception escapes `_notify_ocpp_clip`, is caught by
  the defensive wrapper at the call site, and `_ocpp_clip_notified` never
  latches. The next load-management cycle re-enters and re-fires the channel
  that had already succeeded, repeating the clip notification every cycle for
  the life of the clip — defeating "at most one clip notification per plug
  session" (story Goal 1d). The cited QS-346 precedent `_notify_charger_fault`
  deliberately uses `except Exception` on both channels for exactly this
  reason.
- Proposed fix: Broaden each per-channel guard from `except HomeAssistantError`
  to `except Exception` (matching the `_notify_charger_fault` precedent), OR
  set `_ocpp_clip_notified = True` before dispatching the channels so the latch
  holds regardless of channel outcome. Choose whichever preserves the "notify
  best-effort, latch once" contract. Add a test where a channel raises a
  non-HAE (e.g. `self.home is None`) and assert the notification does not
  re-fire on the next cycle.

### [nice-to-have] NH-1 — Clarify the optimistic-ack delta on the non-blocking OCPP path
- File: `custom_components/quiet_solar/ha_model/charger.py:6426` (`low_level_set_max_charging_current`)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: The non-blocking OCPP branch returns `True` before the scheduled
  `_ocpp_run_number_command` task runs, so the return value never reflects a
  rejection. This is a deliberate documented delta (story Goal 1a), not a bug,
  but a reader may misread it as a lost error.
- Proposed fix: Comment-only. Add a short inline comment at the non-blocking
  return making explicit that the `True` is an optimistic ack by design and the
  rejection surfaces asynchronously via the error hook.

### [nice-to-have] NH-2 — Document/guard the held-window case when the number state is unknown
- File: `custom_components/quiet_solar/ha_model/charger.py` (`check_amps_delivery`)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: When `get_max_charging_amp_per_phase()` returns `None` (number
  state unknown), `None != expected` is always True, so the clip window is held
  indefinitely and a real clip would never notify while the number stays
  unknown. Edge case, likely acceptable given the `Charging` gate.
- Proposed fix: Add a clarifying comment documenting that an unknown number
  state intentionally holds (does not notify on) the window. If cheap, treat an
  unknown ack as "no reading" consistently. No behavioral change required
  beyond documenting intent.

### [nice-to-have] NH-4 — Document the in-flight out-of-order number-write case as accepted
- File: `custom_components/quiet_solar/ha_model/charger.py:6442` (`low_level_set_max_charging_current` non-blocking branch)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: Two setpoints issued within the charger command round-trip
  (1–5 s) leave two number writes in flight that can complete out of order, so
  the last-applied amp value and the rejection-streak reset can momentarily
  reflect a stale setpoint. Self-corrects on the next cycle via the
  observation-driven ensure-state loop; impact is transient.
- Proposed fix: Document-as-accepted. Add a brief inline comment noting the
  transient out-of-order possibility and that the ensure-state loop self-corrects
  it next cycle. No re-architecture.

### [nice-to-have] NH-5 — Document the fast unplug+replug latch-carryover as accepted
- File: `custom_components/quiet_solar/ha_model/charger.py:6568` (`check_amps_delivery` per-plug-session reset)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: The per-plug-session reset only fires when
  `is_not_plugged(for_duration=CHARGER_CHECK_STATE_WINDOW_S)` is true. An
  unplug+replug faster than `CHARGER_CHECK_STATE_WINDOW_S` never trips the reset,
  so `_ocpp_clip_notified`/`_ocpp_clip_since` carry over into the new session and
  a genuine clip in the new session is not re-notified. Inherent to the shared
  `for_duration` primitive.
- Proposed fix: Document-as-accepted. Add a brief inline comment noting the
  latch relies on the shared `for_duration` reset and a sub-window replug will
  not re-arm. No re-architecture of the shared primitive.
