### [should-fix] A git operation in main resurrects an old version's halt
- File: `scripts/qs/control_plane/board.py` (`_code_version`, `_reset_for_tests`), story D5/D8, control-plane.md
- Severity: should-fix
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter, qs-review-acceptance-auditor (regression from fix #02)
- Description: `_code_version` returns `None` while `codever.git_busy(main)` is set,
  which switches `_halt` to the unknown-version rule — an old version's escalated
  failed record (or stale pending mark) then shows "halted: failed"/"stuck" and its
  copy block suggests `halt clear`. A conflicted merge/rebase left in main keeps it up
  for as long as it lasts.
- Proposed fix: keep a module-level last-known version per `main` (dict keyed by the
  resolved path), updated on every successful read and cleared by `_reset_for_tests`;
  while git is busy return the last-known value, and `None` only when none was ever
  read (cold start, the one-shot `cp.py board` process). Tests: known V2 then git
  busy with an old-version failed record → no halt; cold start + git busy → the
  unknown-version rule (today's behaviour); reset clears the cache. Fix the
  "never flickers the halt" wording in control-plane.md and story D8, and add the
  git-busy case to story D5 ("any failure giving `None`…").
