### [must-fix] #1 — Unplug clear is skipped exactly when needed; test enshrines the leak
- File: `custom_components/quiet_solar/ha_model/charger.py:3627`,
  test `tests/test_qs352_person_target_leak.py:410-411`
- Severity: must-fix
- Source: qs-review-coderabbit + qs-review-edge-case-hunter +
  qs-review-regression-proof (flagged independently by all three)
- Description: the guard
  `if not self.car.has_user_originated("charge_target_percent") and any(...)`
  skips the clear whenever a user target marker is present, but the very
  next line (`charger.py:3641`) `self.car.clear_all_user_originated()`
  wipes that marker anyway, and neither `reset(keep_commands=True)` →
  `detach_car()` nor `QSCar.reset` touches `_next_charge_target`. Result
  (probe on head, user target 60 + person leak 41 + unplug):
  `_next_charge_target=41, has_user_target=False, get_car_target_SOC=41`
  — the leaked person value survives the whole away period with no
  override left to justify it. Second variant: `has_user_originated` is
  also `True` for the key present-but-`None`, which contradicts the
  sibling restore branch that resolves present-but-`None` to "no user
  target" (`test_none_user_target_does_not_block_restore`). The shipped
  test `test_unplug_with_user_target_keeps_next_charge_target` asserts
  `car._next_charge_target == 41` — i.e. it pins the *person* leak, not
  the user's 60 — so it enshrines the bug.
- **Design decision (locked, may be revisited if the harness
  disproves it):** because `clear_all_user_originated()` runs
  immediately after and wipes any user marker, unplug already resets all
  user-originated state; preserving a user value in `_next_charge_target`
  on unplug is inconsistent with that. Adopt CodeRabbit's simpler
  design: **drop the `not has_user_originated(...)` guard entirely** and
  clear `_next_charge_target` (to `None`, the lazy default) whenever a
  live person constraint for this car exists. This also makes the
  present-but-`None` sub-case moot.
- Proposed fix:
  - Remove the `not self.car.has_user_originated("charge_target_percent") and`
    conjunct from the guard at `charger.py:3627`; keep the
    live-person-constraint `any(...)` predicate.
  - Rewrite `test_unplug_with_user_target_keeps_next_charge_target`:
    rename to `test_unplug_with_live_person_constraint_clears_target`,
    assert `car._next_charge_target is None` (lazy default) after unplug
    **even when a user target was set** — the field must not carry the
    person leak. Keep the existing positive test (no user target →
    cleared).
  - Add `test_unplug_no_person_constraint_preserves_target`: unplug with
    **no** live person constraint must NOT touch `_next_charge_target`
    (guard scope — pins finding #12's negative case).

### [must-fix] #2 — Agenda realign (#6) mutates a discarded duplicate — silent no-op
- File: `custom_components/quiet_solar/ha_model/charger.py:4250-4253`
- Severity: must-fix
- Source: qs-review-edge-case-hunter (must-fix) +
  qs-review-regression-proof (should-fix)
- Description: the realign mutates the local `car_charge_agenda`, but
  when an `eq_no_current`-equal agenda constraint is already live,
  `push_agenda_constraints` (`home_model/load.py:1971-1984`) sets
  `new_constraints[i] = None` and drops the freshly built object — so
  `car_charge_agenda` is an orphan and the mutation is a silent no-op.
  3-cycle probe (agenda event +30–40 h, person usage +4–7 h, SOC 37 %):
  `cycle3 next_charge_target=80 agenda targets=[41]` → self-heals only
  on cycle 4. The ~3 min window finding #6 claimed to close is still
  open, and `do_force_solve=True` fires for a state change that never
  lands. When the object *is* live, `requested_target_value` stays 41 —
  and `to_dict()["target_value"]` serializes `requested_target_value`
  (`home_model/constraints.py:467`), so a restart inside the window
  restores 41 and the next cycle destroys+recreates the constraint
  (`eq_no_current == False`).
- Proposed fix: resolve the **live** agenda constraint by identity and
  update both fields:
  ```python
  live_agenda = next(
      (c for c in self._constraints
       if c is not None and c.load_param == self.car.name
       and c.load_info is not None
       and c.load_info.get(CONSTRAINT_ORIGINATOR_KEY) == CONSTRAINT_ORIGINATOR_AGENDA
       and c.end_of_constraint == car_charge_agenda.end_of_constraint),
      None,
  ) if car_charge_agenda is not None else None
  if live_agenda is not None and live_agenda.target_value != target_charge:
      live_agenda.target_value = target_charge
      live_agenda.requested_target_value = target_charge
      self.set_live_constraints(time, self._constraints)
      do_force_solve = True
  ```
  Confirm the exact `CONSTRAINT_ORIGINATOR_KEY` / originator constant for
  agenda constraints against source before use.
- Test: add `test_agenda_live_constraint_realigned_after_person_removed`
  seeding a live agenda already carrying 41 before step 2 (the 3-cycle
  sequence), asserting the live agenda's `target_value` AND
  `requested_target_value` are both the default after the removal cycle
  (not next cycle). The existing freshly-pushed test stays.

### [should-fix] #4 — Force/timed constraint bypasses the restore for the whole forced session
- File: `custom_components/quiet_solar/ha_model/charger.py:4089`, `:4221`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: the restore is nested inside
  `if user_timed_constraint is None and force_constraint is None:`, so a
  live "charge now" (force) or user-timed constraint bypasses it. Probe:
  after a leak, pressing "charge now" builds the ASAP constraint with
  `target_value=41` (`{'originator': 'user_override'}`) instead of 80,
  and `_next_charge_target` stays 41 every cycle (the ASAP constraint is
  re-found by the force scan ~`charger.py:3893`, keeping the block
  unreachable) until the force session completes — hours, not minutes.
- Proposed fix: condition the restore on "no live person constraint for
  this car" (the same predicate the unplug clear now uses) rather than
  on the force/timed-null nesting, and evaluate it before
  `force_constraint`'s `target_charge` is consumed. If hoisting the
  block out of the `do_remove_all_person_constraints` nesting is too
  invasive for this round, gate a minimal restore just after
  `target_charge` is resolved (~`charger.py:3782`) when no person
  constraint is live. Add a regression test: leak 41 → re-allocate
  person away → user force-charge on the next cycle → assert the ASAP
  constraint and `_next_charge_target` are the default, not 41.
