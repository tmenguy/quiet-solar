## Findings to fix

### [should-fix] J1 — Overlap: a repo-wide git failure no longer fails the walk, and loops forever with more than `OVERLAP_MAX_CALLS` tasks (I4 regression)
- File: `detectors.py:230-262` (`_branch_tips`, `_walk`, `_main_base`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter (reproduced with the PR's own `FakeGit` fixtures)
- Description:
  - `_main_base(git)` runs only after a task's own tip has resolved. When
    every git call exits 128 (dubious ownership, a corrupt ref store, a
    moved checkout), every task's `rev-parse` fails. Each task is then
    marked unknown, and the H4 abort/backoff path is never taken.
  - A failed `rev-parse` is never cached, so each resumed walk pays for it
    again.
  - With 21 or more tasks, every tick burns its 20-call budget on the same
    failures, raises `OutOfBudget`, sets `walking=True`, and repeats.
    Overlap detection is then effectively off, with 20 git calls and 20
    heartbeat writes per tick.
  - The old whole-repo test was narrowed to fail only `refs/heads/main`, so
    this case is no longer covered.
- Proposed fix:
  1. Resolve the main base once **before** the row loop. A repo-wide
     failure then raises on main first and takes the H4 path (`GitFailed`,
     `last_at = now`, `last` kept). It is cached in `_overlap.refs`, so it
     costs nothing extra.
  2. Add `_overlap.failed_refs`, a set cleared in `_end_walk` just like
     `failed_diffs`. A per-branch ref that failed in this walk is not
     retried when the walk resumes.
  3. Tests:
     - `git.fail.add("rev-parse")` with more tasks than `OVERLAP_MAX_CALLS`
       → exactly one call, the walk aborts, and no further walk starts
       before `OVERLAP_EVERY_S`;
     - one broken deliverable ref with K ≥ 2 items → one failed call
       across a resumed walk;
     - keep the I4 per-branch test green.

### [nice-to-have] J2 — PreToolUse fallback: deny instead of ask, to match the unknown-mode rule
- File: `hooks.py:320-324`
- Source: qs-review-edge-case-hunter

  - Record the decision actually returned.
  - Update the I7 tests, control-plane.md and the "Review fix #04" note
    (add a #05 line).

### [nice-to-have] J3 — Hook routing: an out-of-range cursor

- Source: qs-review-edge-case-hunter

### [nice-to-have] J4 — Restore keep-guard: pick the hint from the SQLite error code
- File: `restore.py:282-288`
- Source: qs-review-edge-case-hunter
- Proposed fix: for a `sqlite3.OperationalError`, use
  `exc.sqlite_errorcode & 0xFF`:
  - `SQLITE_FULL` (13) / `SQLITE_CANTOPEN` (14) → the current "free space
    in (or fix) …" hint;
  - `SQLITE_BUSY` (5) / `SQLITE_LOCKED` (6) → a retry hint;
  - anything else → a generic "the live DB could not be copied; nothing
    was restored" hint, with no free-space claim.

  An `OSError` keeps the free-space hint. Tests: one for each branch.

### [nice-to-have] J6 — Restore brings back a stale `last_backup_error`
- File: `restore.py` `_fix_up` (staged copy)
- Source: qs-review-blind-hunter
- Description: a periodic copy taken right after a failed attempt contains
  `meta.last_backup_error`. Restoring that copy raises `backup_failed`
  again.
- Proposed fix: in `_fix_up`, `DELETE FROM meta WHERE key =
  'last_backup_error'` on the staged copy. The live value is not carried
  either, because a restore starts a fresh backup cycle.
  - Test: restore a backup that holds the key → the key is absent and no
    `backup_failed` is raised by the next hook.
