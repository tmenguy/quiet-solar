# QS-372 — Extract launcher/handoff plumbing from phase templates and route implement variant by lane

- Issue: #372 · Branch: `QS_372` · Lane: `feature-factory`
- Parent epic: #369 (autonomous implement/review build loop) — child 2,
  prerequisite for the build orchestrator (children 3+).

## Problem

1. **Handoff plumbing dominates the phase templates.** Every phase that
   hands off embeds the same launcher block: the `next_step.py` call,
   JSON parsing, the GUI-pin instructions (`phase_agent_pinned`,
   `phase_model`, the stale-pin hazard, the five GUI bullets), the
   OpenCode `session_created` success contract and its failure-mode
   list. There are **8 handoff sites** across the six templates
   (closed list in §3); each costs ~45 rendered lines on Claude and ~40
   on OpenCode, interleaved paragraph-by-paragraph in the source and
   drifting in wording from site to site. In `qs-review-task.md.j2` the
   plumbing is ≈290 of 560 lines. It is paid in context on every
   invocation, and two of its rules are LLM judgment calls on JSON
   fields ("drop the GUI block when `phase_agent_pinned` is false",
   "omit the existing-session block when `existing_session_prompt` is
   null").
2. **Path-based routing survives.** `qs-create-plan` ("Determine
   NEXT_PHASE") and `qs-review-task` step 6 pick `implement-task` vs
   `implement-setup-task` from a hardcoded path list (`scripts/`,
   `.claude/`, `.opencode/`, `legacy/`, `docs/`, `.github/`, top-level
   config). QS-321 settled that target is **declared, never inferred**;
   `context.py` already returns the declared `target`. The same rule is
   copied into `phase-protocols.md` and the five lane files that are
   byte-identical to it (inlined into the bound rendered prompts, so
   they would contradict the templates), `overview.md` and
   `.claude/commands/review-task.md`.

A pure Jinja macro fixes the *source* duplication but not the
*rendered* context cost: it expands to the same text at every site. So
the Claude user-facing text moves into code. **The context saving is
Claude-only**: the OpenCode agent must itself execute `spawn_session`
and check its result, so its contract stays prose — written once in the
macro. That satisfies the issue's "write the handoff block once … on
both harnesses", which asks for one written block, not reduced OpenCode
context.

## Goal

- The handoff is written **once**: the Claude user-facing block is
  produced by the launcher as a ready-to-print `handoff_text` payload
  field; the per-harness agent instructions live in **one** macro in
  `_macros.md.j2`, called from all 8 handoff sites.
- The implement variant is chosen from the **declared target**
  (`context.py` → `target`), never a path list — in templates and in
  the docs that restate the rule.
- Same launcher commands, same GUI instructions, same OpenCode contract
  (clauses and order); the only user-visible deltas are listed in AC6.

## Decisions

- **D1 — Hybrid (code + macro).** `launchers/claude.py::build_payload`
  emits `handoff_text`; `_macros.md.j2` gains `handoff(...)`. Macro-only
  was rejected: it leaves rendered context unchanged.
- **D2 — `qs-setup-task` is out of scope.** It keeps its inline block
  and its rendered GUI pins. `handoff_text` is built **only when
  `caller == "next_step"`**, so setup-task's payload gains no unread
  field (the `gui_context` precedent, `test_claude_launcher.py:569-575`).
- **D3 — Unusable target → STOP and ask.** No default variant. The
  agent prints a literal, stable message (§4) and waits for the user.
- **D4 — Runtime resolution only.** The agent re-runs `context.py` at
  the routing step and reads `target` (`context.py:223`: `"factory"`,
  `"product"`, or `""` when the label is missing *or* ambiguous —
  `targets.py:118,129` — *or* when `gh` fails, since `context.py`
  degrades every `gh` failure to empty fields, never an exception,
  `context.py:63-96`). No render-time literal (it could go stale
  after a relabel), no new render-context field, no new `targets.py`
  helper: `parse_axes` stays the single owner of the axis mapping.
  Epic lanes never reach an implement phase, so need no row. The
  two-site routing paragraph is a macro (`implement_routing`) so the
  target→variant mapping has one owner in the templates too.
- **D5 — Only the implement variant is re-routed.** implement-task's
  review/verify choice, setup-task's create-plan/diagnose choice and
  diagnose/verify's fixed `implement-task` stay as they are. No prose
  outside the extracted blocks changes, except the harness-split tail
  of implement-task's resolution paragraph
  (`qs-implement-task.md.j2:245-254`), which today refers to "the
  fallback line, which carries both branches" / "the success-contract's
  agent pair". It becomes one harness-neutral sentence:

  > `lane` from `context.py` is `bug-product` (i.e. routes to
  > `/verify-task` instead of `/review-task`), and substitute that
  > value everywhere below.

  It still carries `/review-task`, `/verify-task`, `bug-product` and
  "Resolve the next phase from the lane" on both harnesses
  (`test_shared_orchestrator_carries_both_lane_branches`).
- **D6 — No `--format text`.** Bash output is not reliably shown to the
  user, so the agent must re-emit the text anyway; the guard is the
  "print verbatim" instruction plus the golden tests (AC1). Markdown
  bold inside the ```text fence is kept — it is there today.
- **D7 — OpenCode wording is canonicalised, not byte-preserved.** Today
  the 8 OpenCode sites differ in wrapping, agent-name parentheticals,
  "Before running" phrasing, and suffixes (e.g. "(review-fix #01 S9)").
  The macro renders **one canonical wording** with the same clauses in
  the same order; the contract is pinned clause-by-clause (AC3), not
  byte-for-byte.
- **D8 — No unknown-harness guard.** `render_all` renders exactly
  `_HARNESSES = ("claude", "opencode")` (`render_agents.py:97`); the
  macro uses `[% if harness == "claude" %]…[% else %]…` like every
  template today.

## Design

### 0. Capture the "before" (Task 0 — implementer check, not a deliverable)

Render both harnesses into the scratchpad
(`render_all(..., out_root=<scratch>/before)`) and extract the 8 Claude
text-fence blocks and the 8 OpenCode handoff sections. The Claude
blocks differ in phase/banner/trailer, the existing-session block
(sites 6 and 8), wrapping at sites 1–2, and implement-task's dual
fallback line. **The Task-0 extract of review-task step 6 is
authoritative** for the `handoff_text` wording; §1 below is a
transcription. The AC1 golden strings are **literal templates checked into
the test file**, copied from that extract, filled only with
`payload["new_context"]`, the test's `work_dir`, the issue number and
`payload["phase_model"]` (so they depend on neither the machine's temp
dir nor the model policy table). The OpenCode extracts feed the
Task-8 review diff.

### 1. `scripts/qs/launchers/claude.py` — `handoff_text`

### 2. `scripts/qs/agent_templates/_macros.md.j2` — `handoff(...)`

```jinja
[%- macro handoff(next_cmd, fix_plan=false, rerun="") -%]
```

`harness` reaches the macro through the context: all six templates
already `[% import "_macros.md.j2" as m with context %]` (as
`lane_paragraph` relies on today); keep that import form.

Called as:

```jinja
[% call(prefix) m.handoff("finish-task") %]
[[ prefix ]] Adversarial review complete. No blocking findings.
[% endcall %]
```

- `next_cmd`: bare literal (`finish-task`, `review-task`,
  `implement-task`) or placeholder (`{{NEXT_PHASE}}`,
  `{{next_implement}}` — always the bare form).
- `fix_plan` (sites 6, 8): adds `--fix-plan-path "{{fix_plan_path}}"`
  and `--pr-number {{pr_number}}`; the substitution sentence names
  them. On OpenCode it also renders (a) the `existing_session_prompt`
  rule ("a paste-into-already-running-session prompt — it is NOT a
  session-spawn command. Do NOT execute it."; omit the block when
  missing or null), (b) the `Already running an implementation
  session? / Paste this prompt into it: / {{existing_session_prompt}}`
  lines inside the `[OK]` report, and (c) the "(Omit the "Already
  running an implementation session?" block when
  `existing_session_prompt` is missing or null.)" note **after** the
  report fence (where it sits today, `qs-review-task.md.j2:514-517`,
  `qs-verify-task.md.j2:528-531`).
- `rerun` (sites 6, 8: `review-task` / `verify-task`): the trailer line
  at the end of the report fence — Claude: "Then re-run /<rerun> (or
  open a fresh `claude --agent qs-<rerun>` session) to verify.";
  OpenCode: "Then re-activate `qs-<rerun>` (or open a fresh session
  bound to it) to verify." (today's wording, `qs-review-task.md.j2:508-513`,
  `qs-verify-task.md.j2:522-527`). On Claude it is preceded by one
  blank line after `handoff_text`, as today.
- Call body: banner lines only, each starting with `[[ prefix ]]`.
  At sites 1–2 the banner line is wrapped in
  `[% if harness == "claude" %]` inside the body (OpenCode has no
  banner there today). Claude renders `[[ caller("✅") | trim ]]`;
  OpenCode renders `[[ caller("[OK]") | trim | indent(2, first=true) ]]`
  (the report is indented 2 spaces inside a list item); either is
  skipped, with its trailing blank line, when empty.
- The OpenCode "Launch surfaces for the Claude harness" pointer quote
  is **not** part of the macro: the six existing pointer blocks (one
  per template, before the first site's lead prose) stay where they
  are. Five are standalone `[% if harness == "opencode" %]` blocks;
  implement-setup's (`:270-276`) shares an `[% else %]` with the
  "Before running" sentence being deleted (`:281-283`) — move the
  pointer into its own `[% if harness == "opencode" %]` block.
- The "Before running" sentence is generated by the macro (both
  harnesses): "**Before running** — substitute `{{worktree}}`,
  `{{issue}}`, `{{title}}`[, `{{fix_plan_path}}`, `{{pr_number}}`]
  with the values you captured earlier[; substitute `<next_cmd>` with
  the value you resolved above]." The last clause renders **only when
  `next_cmd` starts with `{{`** (sites 1, 2, 3, 6). The existing
  per-site sentences are therefore deleted (§3).

**Claude branch** — exact rendered skeleton (column 0):

````text
**Before running** — substitute … (generated sentence).

```bash
python scripts/qs/next_step.py \
    --next-cmd "<next_cmd>" \
    --work-dir "{{worktree}}" \
    --issue {{issue}} \
    --title "{{title}}" \
    [--fix-plan-path "{{fix_plan_path}}" \
    --pr-number {{pr_number}} \]
    --harness claude-code
```

Parse the JSON. If it contains an `error` key, STOP and print the raw
JSON. Otherwise print the report below, replacing `<handoff_text>` with
the payload's `handoff_text` **verbatim** (do not rephrase, reorder or
drop any part of it):

```text
<rendered caller("✅") banner lines>

<handoff_text>

<rerun trailer line, if rerun>
```
````

This reproduces today's fence layout (banner → blank → "Next phase: …"
→ Preferred → … → GUI → trailer).

**OpenCode branch** — the canonical contract, clauses in this order:
the generated "Before running" sentence; the `--harness opencode`
block; "Parse the JSON output of `next_step.py`."; the `error`-key
STOP; "Otherwise capture the `new_context` string" (+ the fix-plan
rule (a) when `fix_plan`); "**Run `new_context` via the Bash tool**"
+ the `spawn_session.py` / "Do NOT extract only the prompt" / "Do NOT
strip `--agent qs-<phase>`" / `prompt_async` warning; the
Bash-tool-error STOP; "The success contract is **binary**:";
`status == "session_created"` AND `agent` equals `qs-` followed by the
phase name passed to `--next-cmd` (here: `qs-<next_cmd>`) → success,
report (indented 2 spaces, in a ```text fence): the `caller("[OK]")`
banner lines, `[OK] Next phase session created: qs-<next_cmd>`,
"(visible in the OpenCode session list on the left)", the
`Already running…` lines (b) when `fix_plan`, then the `rerun` line;
the omit-when-null note (c) when `fix_plan`; "**Anything else** … →
STOP" with the 7 failure modes (`agent_file_missing`,
`agent_file_unreadable`, `agent_file_empty`, `worktree_invalid`,
`fallback_cli`, `fallback_unavailable`, `session_orphaned`) and the
`scripts/qs/spawn_session.py` reference.

Mandatory canonical strings (pinned by
`test_opencode_execute_contract.py:48-59`, which must pass unchanged):
``Run `new_context` via the Bash tool``, `status == "session_created"`,
``If the `next_step.py` JSON contains an `error` key``,
`If the Bash tool returns an error before producing any JSON output`,
`**Before running** — substitute`, and text matching
``equals\s+`qs-`\s+followed\s+by\s+the\s+phase\s+name``.

### 4. Implement-variant routing — macro `implement_routing(var)`

In `_macros.md.j2`, used by `qs-create-plan` ("Determine NEXT_PHASE",
replacing :229-233, heading kept) and `qs-review-task` step 6
(replacing :298-316, incl. the closing `[% endif %]`):

> Route by the **declared target** (QS-321 — never inferred from the
> files you touch): re-run `python scripts/qs/context.py` and take
> `target`. `factory` → `<var> = implement-setup-task`; `product` →
> `<var> = implement-task`. For any other value (empty — no or
> ambiguous label, or a degraded `gh` lookup), **STOP** and print:
> `Cannot pick the implement variant: issue #{{issue}} has no single target:* label. Add one (gh issue edit {{issue}} --add-label target:factory or target:product) or tell me which variant to run.`
> Then wait for the user: if they report adding a label, re-run
> `context.py` and route again; if they name a variant, use it.

Harness-neutral; `<var>` is `NEXT_PHASE` or `{{next_implement}}`,
always assigned the bare phase name (never a slash form). The stable
prefix `Cannot pick the implement variant:` is what child 3 of #369
can detect.

## Acceptance criteria

1. **AC1 — `handoff_text`.** Golden literal strings (checked into the
   test) for, via `build_payload(caller="next_step")`: pinned true ×
   no fix plan; pinned true × fix plan + PR (existing-session block
   present, multi-line prompt fully indented); pinned false × no fix
   plan (no GUI bullets, stale-pin line present). Via `_handoff_text`
   directly: an empty-string `existing_session_prompt` omits the block.
   With `caller="setup_task"` the key is absent.
2. **AC2 — One macro, 8 sites.** In each of the six rendered Claude
   agents: the "`handoff_text` **verbatim**" instruction appears
   exactly as many times as its sites in §3 (1,1,1,1,2,2); each site's
   `--next-cmd` value matches the §3 column (both harnesses); every
   site carries the generated "Before running" sentence naming all its
   placeholders, with the "substitute `<next_cmd>`" clause present at
   sites 1, 2, 3, 6 and absent at 4, 5, 7, 8; neither `[Claude Code GUI]` nor "On `false` the
   worktree may still carry" appears; every bash fence is at column 0.
3. **AC3 — OpenCode contract.** For each of the 8 OpenCode sites, a
   test slices the handoff section and asserts the §2 OpenCode clauses
   appear **in order** (incl. all 7 failure modes; for sites 6 and 8
   also "Do NOT execute it", the `Already running…` report lines and
   the omit-when-null note after the fence);
   `test_opencode_execute_contract.py` passes unchanged; the four
   relocated LSP sections are present; the six pointer blocks are
   unchanged (`test_counterpart_agents_point_at_harness_doc`).
4. **AC4 — Target routing.** Rendered create-plan and review-task
   (both harnesses) contain the §4 target rule, the re-run-on-label
   instruction, and the STOP message with its stable prefix
   `Cannot pick the implement variant:` (path-list absence is AC5's
   job).
5. **AC5 — No path-list routing phrase** in any rendered orchestrator
   (both harnesses, **both** the unbound and the bound render —
   `tests/qs/agents/_rendered.py:38-53` — so the inlined lane text is
   covered) or `.claude/commands/*.md`, matched after whitespace
   normalisation (`" ".join(body.split())`, as
   `test_lane_steps_parity.py:111` does — the phrases wrap across
   lines): `If **all** are in`, `if all touched files are in`,
   `If **every** touched file is under`, `chosen by file scope`,
   `chosen by the file scope`, `based on the file paths in its task
   breakdown`, `Inspect the file paths your task breakdown will touch`.
   Edit-scope descriptions listing the same paths are legitimate and
   not matched.
6. **AC6 — Behaviour.** Launcher commands and GUI wording unchanged;
   the only user-visible deltas: (1) fallback lines name the resolved
   phase (implement-task's is `/review-task` *or* `/verify-task`, no
   longer both); (2) the variant follows the declared target — a
   `*-product` task whose fix touches only `scripts/` now routes to
   `implement-task` (the QS-321 intent); (3) a pinned-false handoff
   shows the one-line stale-pin notice instead of nothing; (4) a
   launcher failure now makes the Claude agent STOP and print it —
   widened by fix #01 S1 beyond an `error` key to also cover a non-zero
   exit, no JSON, or a missing `handoff_text`, and fix #02 S1 mirrored
   the same widening on OpenCode (non-zero exit / no JSON / missing
   `new_context`), so this parity is now exact; (5) cosmetic:
   line-wrapping inside the Claude report at sites 1–2 follows the
   canonical text (words unchanged). This list is closed — no other line
   enters `handoff_text` at implement time.
7. **AC7 — Gates.** `tests/qs` pins updated per the Task 1 table;
   `python scripts/qs/quality_gate.py --impacted` and

## Risks

- **LLM paraphrasing `handoff_text`.** Mitigation: explicit
  "verbatim, do not rephrase/reorder/drop" + the text is produced
  deterministically and golden-tested (D6).
- **Pin-test churn hides a regression.** The AC1 goldens assert the full
  text, a superset of every removed per-token assertion; AC3 guards the
  OpenCode clauses; Task 8 reviews every OpenCode hunk.
- **Stale worktree render.** A worktree rendered before this change
  keeps the old inline block — harmless, the payload only *adds* a key.
- **`target` unusable at run time** (unlabelled legacy task, two target
  labels, or `gh` failure): D3 STOP — never a silent default.
- **D3 STOP vs the autonomous build loop (epic #369).** The STOP is
  interactive; the non-interactive behaviour belongs to child 3. The
  STOP message is a stable literal (AC4) so the orchestrator can detect
  it.
- **Placeholders inside macro args** (`{{NEXT_PHASE}}` in a
  `[[ ]]`-delimited env) are literal text; covered by the AC2/AC4
  render tests. `caller()` output needs `| trim` (trim_blocks does not
  apply to `[[ ]]`) to avoid doubled blank lines.
