### [must-fix] M1 — F = 0 flip-debit divergence breaks the stated no-op invariant
- File: `custom_components/quiet_solar/home_model/solver.py:463-473`
- Severity: must-fix
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter + qs-review-acceptance-auditor
- Description: The flip branch in `_battery_get_charging_power` debits the
  per-price budget **pre-clamp**: `new_limit_discharge = max(0.0,
  limit_discharge + min(charged_energy + leak_energy, 0.0))` computed
  before the flip clamp zeroes the bucket on every flipped slot. The old
  code updated `limited_discharge_per_price` with the *post-clamp*
  `charged_energy`, so a flipped slot consumed **zero** budget and the
  residual stayed available for later same-price slots. At F = 0 (the
  default for every existing install) this changes real behavior: budget
  5000 Wh, first slot wants 6000 Wh → flip; pre-PR later same-price slots
  could still discharge up to 5000 Wh; post-PR they are all flipped to
  `CMD_GREEN_CHARGE_ONLY`, so the battery holds charge and the home
  imports up to the lost residual from the grid at that price. This
  contradicts the in-code comment, `docs/agents/concepts/solver.md` ("At
  F = 0 ... reduces to the pre-QS-349 behaviour"), and the story's F = 0
  regression guarantee. Root cause is a story-internal contradiction:
  Design §4 mandates the pre-clamp formula *and* claims the F = 0 no-op —
  both cannot be true.
- Proposed fix:
  1. On the flip branch, debit **post-clamp**: only the discharge that
     actually survives the flip, i.e. `new_limit_discharge = max(0.0,
     limit_discharge + min(0.0, charged_energy_post_flip + leak_energy))`
     computed after the clamp — this reduces exactly to the pre-QS-349
     behavior at F = 0 (flip debits nothing when the slot's surviving
     discharge is the leak only, which is 0 at F = 0).
  2. Add the explicit F = 0 flip-site regression test AC 3 requires:
     budget-limited scenario (residual budget > 0 but smaller than one
     slot's discharge) followed by later same-price discharging slots;
     assert the residual is preserved and later slots still discharge.
  3. Amend `docs/stories/QS-349.story.md` Design §4 and
     `docs/agents/concepts/solver.md` so the documented debit formula and
     the F = 0 invariant agree with the implemented (post-clamp)
     semantics.
  4. Update `tests/test_solver_discharge_floor.py::test_flip_keeps_leak_and_debits_only_compressible_budget`
     (line ~165, "compressible budget fully consumed on this flip") to
     the corrected debit semantics for F > 0.

### [should-fix] S1 — Battery restore failure aborts load shedding permanently
- File: `custom_components/quiet_solar/ha_model/home.py:1057-1063`
- Severity: should-fix
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter + qs-review-coderabbit
- Description: Fix B makes the awaited `battery.launch_command(...)` a
  prerequisite of the load-shed loop with no error isolation. An exception
  escaping it skips shedding all loads, skips `_switch_to_off_grid_launched`,
  and skips `force_next_solve()`; since `qs_home_is_off_grid` is committed
  *before* the work and the listener's log-only `except`
  (home.py:1246-1249) swallows the error, later
  `_compute_and_apply_off_grid_state` calls see `do_reset == False` and
  never retry — loads stay running off-grid.
- Proposed fix: Wrap the `CMD_GREEN_CHARGE_AND_DISCHARGE` `launch_command`
  call in its own log-only `try/except Exception` with
  `_LOGGER.error(..., exc_info=True)` (matching the failure-isolation
  pattern in `_notify_charger_fault` in `ha_model/charger.py`) so a
  raising battery command cannot cancel load shedding and the gate. Add a
  test: raising battery `launch_command` → loads still shed, gate still
  set.

### [should-fix] S2 — Floor write not validated against the number entity's unit/step/range → eternal retry
- File: `custom_components/quiet_solar/ha_model/battery.py:74,80,178-186`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: The read path converts the entity value to W
  (`convert_power_to_w`, line ~214) but the write path sends the raw W
  integer, and `probe_if_command_set` compares the W-converted read
  against the emitted floor. A kW-denominated `max_discharge_number`
  entity (write of `300` lands as 300 kW → probe reads 300000 W ≠ 300), a
  step that doesn't divide the floor (entity snaps 330 → 300), or an
  entity min/max range excluding the floor (`number.set_value` raises
  out-of-range, caught and logged, value never lands) all cause
  `probe_if_command_set` to never confirm → retry forever. Writing 0 was
  unit-/step-/range-invariant so this class was dormant; a 300 W floor is
  not.
- Proposed fix: Convert the written value to the entity's unit
  symmetrically with the read path, and clamp/round to the entity's
  min/max/step (available from the state attributes) before writing and
  before the probe comparison. Add tests for the kW-unit and
  non-dividing-step cases.

### [should-fix] S3 — Full-solve tests can pass vacuously
- File: `tests/test_solver_discharge_floor.py:239-247, 290-297`
- Severity: should-fix
- Source: qs-review-acceptance-auditor + qs-review-coderabbit

  `assert any(cmd.is_like(CMD_GREEN_CHARGE_ONLY) and cmd.power_consign < 0
  for cmd in per_slot)`).

### [should-fix] S5 — Two concept-doc wording errors
- File: `docs/agents/concepts/ha-battery.md:20-23`,
  `docs/agents/concepts/home-model-battery.md:54-56`
- Severity: should-fix
- Source: qs-review-coderabbit
- Description: (a) ha-battery.md describes the floor as driving "the

  compares the raw expected value from `_command_to_values` — init
  normalization is what aligns them.
- Proposed fix: (a) Replace with "For discharge-limiting commands,
  `_command_to_values` emits the outage safety floor
  (`min_discharging_power`, default `0`; QS-349) as the HA
  `max_discharging_power` value —". (b) Reword to "and
  integer-normalized (`float(int(...))`) so the write/read casts and the
  raw expected value used by `probe_if_command_set` agree; a non-integer
  floor would otherwise never confirm in `probe_if_command_set` (eternal
  retry)."
