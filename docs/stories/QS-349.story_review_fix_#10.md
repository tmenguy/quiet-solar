## Findings to fix

### [should-fix] AA1 — Fold `_is_discharge_floor_command` into `_command_to_values`
- File: `custom_components/quiet_solar/ha_model/battery.py:81`
  (`_command_to_values`), `:304` (`_is_discharge_floor_command`),
  consumers at `:123` (write path) and `:153` (probe path)
- Severity: should-fix (design coherence; no behavior change)
- Source: user (author review of the final diff)
- Description: `_command_to_values` is the single authority mapping a
  command to entity values, yet the snap semantics of the discharge
  value — "is this the safety floor (snap up) or a restore/max (snap
  down)?" — is re-derived at both consumers via a separate static
  predicate. A future command added to `_command_to_values` could
  silently get the wrong snap direction, and nothing structurally forces
  write and probe to agree.
- Proposed fix: `_command_to_values` emits the snap semantics alongside
  the value (e.g. `"max_discharging_power_snap_up": bool`, or a
  value+flag pair — whichever reads cleanest). Both consumers read the
  flag from the dict; delete `_is_discharge_floor_command`. The public
  setter keeps its `snap_up` parameter (external callers default False,
  unchanged). NOTE: this mapping is battery command semantics — it stays
  in battery.py, NOT in the AA2 utility.
- Tests: one new test pinning the emitted flag per command
  (CMD_GREEN_CHARGE_ONLY / CMD_FORCE_CHARGE -> snap up;
  CMD_GREEN_CHARGE_AND_DISCHARGE -> snap down).

### [should-fix] AA2 — Extract the number-entity machinery into `ha_model/ha_utils.py`; battery becomes a thin consumer
- File: NEW `custom_components/quiet_solar/ha_model/ha_utils.py`;
  source material in `custom_components/quiet_solar/ha_model/battery.py`
  (`_number_entity_target`, `_number_reading_matches`, `_entity_step`,
  `_safe_float`, the snap/clamp/alignment/landed logic, and the
  divergence-warning latch machinery incl.
  `_NUMBER_DIVERGENCE_LATCH_MAX`, `_warn_number_divergence`,
  `_clear_number_divergence_latch`)
- Severity: should-fix (design placement; no behavior change)
- Source: user (author review of the final diff)
- Description: The "write a value to a third-party number entity
  correctly" machinery (unit conversion, domain clamp, step snap with
  direction, landed-value prediction, tolerant read-back comparison,
  once-per-divergence warning) is generic, not battery-specific. The
  same problem class already has two OTHER hand-rolled partial
  implementations in the repo: `charger.py:5809`
  (`low_level_set_max_charging_current` — ad-hoc clamp + int, no
  unit/step handling) and `car.py:2063` (bisect snap-up to allowed
  steps + read-back compare). Battery's version is the most complete;
  it should be the shared one.
- Proposed fix: Create `custom_components/quiet_solar/ha_model/ha_utils.py`
  holding the generic machinery. Design freedom for the implementer,
  with these requirements:
  - The API must be reusable beyond power/W (the car case is percent):
    at minimum parameterize entity id, hass, requested value in domain
    units, domain min/max, snap direction, unit-conversion hooks (W
    conversion stays the default path), and warn context. A small
    stateful helper class owning the divergence latch (one instance per
    consumer device) is acceptable and probably cleanest; module-level
    functions with explicit state are also fine.
  - battery.py keeps only thin wrappers (`_discharge_number_target` /
    `_charge_number_target` or direct calls) and its command semantics
    (see AA1); target: the number-machinery block in battery.py shrinks
    to glue.
  - Migration of charger.py / car.py to the utility is OUT OF SCOPE for
    this PR — record it as a candidate follow-up task in the story's
    ledger, do not touch those files.
  - `coerce_finite_float` stays in home_model/battery.py (layering:
    ha_model may import home_model, not vice versa) — ha_utils may
    import it.
- Tests: existing tests keep passing with zero expected-value edits;
  mechanical retargeting of import/monkeypatch paths to ha_utils is
  allowed and expected. Direct-call unit tests of the moved helpers may
  move alongside them (same assertions).
- Docs: update `docs/agents/concepts/ha-battery.md` (now describes the
  thin consumer + points to the utility). Run
  `python scripts/qs/check_doc_drift.py` and satisfy it for the new
  module (add `ha_utils.py` to an existing concept doc's covers —
  ha-battery.md is acceptable — or a small new concept doc if the
  checker requires one).
