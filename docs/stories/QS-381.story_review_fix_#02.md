## Findings to fix

### [should-fix] A stale replayed budget in `apply_budgets` clears the adoption marker
- File: `custom_components/quiet_solar/ha_model/charger.py:2324-2325` (with ~989-995 and ~2234, `remaining_budget_to_apply` replay)
- Source: qs-review-edge-case-hunter
- Description: `apply_budgets` calls
  `set_expected_num_active_phases(cs.budgeted_num_phases, ...)` every time,
  even when the budget did not change phases. `remaining_budget_to_apply`
  keeps old `QSChargerStatus` snapshots across cycles where the group returns
  `[]`, and those snapshots still carry the phase count from before a follow.
  Replaying one after a follow looks like a new request: it clears
  `_phases_adopted_at`, and `_ensure_correct_state` re-drives the switch.
  That is the revert fix #01 was meant to stop, and it also skips the
  30 min spacing.
  Sequence: multi-charger group, cycle N splits the budget into decrease and
  increase. Charger A (adopted 3, target 1) is in the increasing set with
  `budgeted_num_phases=3`. In cycle N+1, A's switch flips late, the follow
  sets expected=1, and the group returns `[]` with the remaining budget kept.
  In cycle N+2 the `check_charger_state=True` replay calls
  `set_expected_num_active_phases(3)`: marker cleared, `turn_off` sent.
- Proposed fix:
  1. In `apply_budgets`, only treat the phase count as a request when the
     budget actually asks for a phase change
     (`cs.budgeted_num_phases != cs.current_active_phase_number`, i.e. the
     existing `new_num_phases != init_phase_num` notion). Otherwise don't
     touch the expected phases.
  2. In the `check_charger_state` replay block, drop the stale remaining
     budget (`do_apply = False` / clear it) when a replayed
     `cs.current_active_phase_number != cs.charger._expected_num_active_phases.value`.
  The implementer should check both changes against existing
  `apply_budgets` / `dyn_handle` tests and keep normal phase-change
  budgeting unchanged.
- Test: drive `dyn_handle` / `apply_budgets` through the split sequence above
  (not only direct `set_expected_num_active_phases` calls) and assert no phase
  re-drive after the follow. Also add a positive test: a real budget phase
  change through `apply_budgets` after adoption still launches.

### [should-fix] A flapping switch keeps the follow window open forever
- File: `charger.py:~5337` (follow branch, `self._phases_adopted_at = time`)
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter
- Description: every follow refreshes the marker, so the 30 min window never
  expires for a flapping entity. The group is blocked one cycle per flap.
  This is the "blocks the group forever" pattern the issue is about.
- Proposed fix: do not refresh `_phases_adopted_at` in the follow branch. The
  window counts from the original adoption. A test pins that a flip after
  adoption + 30 min goes back to the normal launch path.

### [should-fix] Adoption and follow act on unknown/unavailable phase switch readings
- File: `charger.py:5319-5365` (follow + D1 adoption branches), with `current_num_phases` ~2507-2518
- Source: qs-review-edge-case-hunter (round 1 N1 + round 2)
- Description: when the 3-to-1 switch entity is missing, `unknown` or
  `unavailable`, `current_num_phases` returns a hard-coded 3. The follow
  branch takes that as a real flip at once (and follows back when the entity
  returns). D1 adoption can also lock in the default 3.
- Proposed fix: only adopt or follow when the phase switch has a real
  reading. For a switch-based charger that means the state is `on`/`off`;
  keep the existing behaviour for chargers whose phase count comes from
  elsewhere. Otherwise fall through to the existing "NOT OK TO LAUNCH" debug
  branch. Add a helper (e.g. `_has_real_phase_reading()`) if that's cleaner.
- Tests: switch `unavailable` within the window → no follow, no launch.
  Switch `unavailable` past the adoption delay → no adoption.

### [should-fix] Pin the follow window edges
- File: `tests/test_bug_381_non_converging_group.py`
- Source: qs-review-edge-case-hunter + qs-review-acceptance-auditor
- Proposed fix: add tests for a flip at adoption + 30 min − 1 step

  re-driven). Add a one-line note on post-window behaviour in
  `docs/agents/concepts/charger-budgeting.md` (the "Phase switch that never
  follows" bullet).
