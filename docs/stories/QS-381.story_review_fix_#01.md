### [should-fix] Late phase switch after adoption is reverted
- File: `custom_components/quiet_solar/ha_model/charger.py:5311-5330` (`_ensure_correct_state`, D1 adoption branch)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: Adoption fires ~196 s after the first phase launch and calls
  `self._expected_num_active_phases.set(current_active_phases, time)`, which
  resets the launch counter. If the requested switch lands *after* adoption
  (target 1 phase, observed 3 at adoption, the switch entity then flips `on`),
  `current_num_phases` (1) no longer matches the adopted value (3).
  `is_ok_to_launch(3)` passes on the fresh counter and
  `set_charging_num_phases(3)` switches the charger back, which registers a
  reboot if `do_reboot_on_phase_switch` is on. The budget then can't ask for
  1 phase for 30 min: one intended switch ends up as 5+ real ones.
- Proposed fix: once the charger is adopted, a later mismatch must follow the
  observed value, not re-drive the switch. The adopted value is not a budget
  request. Suggested mechanism: store an adoption marker (e.g.
  `self._phases_adopted_at: datetime | None`) when the D1 branch fires. On a
  later phase mismatch, while the marker is set and younger than
  `TIME_OK_BETWEEN_CHANGING_CHARGER_PHASES`, and no new budget request has come
  in since, re-adopt the observed value (`set(current, time)` + `success`, one
  WARNING/INFO log) instead of launching. Clear the marker when the budget
  issues a new phase request. Cover every path that sets
  `_expected_num_active_phases` from the budget/constraint side, so a real new
  request still launches normally. The implementer may choose an equivalent
  mechanism if it is simpler, as long as:
  - a late flip after adoption never triggers `set_charging_num_phases`
    (or a reboot);
  - a genuine new budget phase request after adoption still launches as
    before;
  - the D1 bound (group unblocks at adoption) is unchanged.
- Tests (new, in `tests/test_bug_381_non_converging_group.py`):
  - the switch entity flips to the requested phase one STEP after adoption:
    no further `turn_on`/`turn_off` phase call and no `reboot()`. The expected
    value follows the observed one and the group stays unblocked;
  - after an adoption, a new budget phase request still triggers the phase
    switch launch.
