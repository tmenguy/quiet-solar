## Findings to fix

### [should-fix] T1 — An unfinished catch-up survives the node's error-block re-entry; every later `catchup base` is refused
- File: `catchup.py:737-738` (`base`), `:522-527` (adopt), `:674-693` (`after_merge`); `scripts/qs/agent_templates/qs-node.md.j2` (Blocking, the re-entry rule)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: on re-entry, the node sees remote = HEAD ≠ round.json's
  head. It writes `catchup = null` and `step: wait` itself, but nothing
  tells Python. So `catchup.json` keeps the old catch-up with its
  `merge`. If step 6 then routes to a build round (red CI on the
  catch-up head, blocking findings, or open `catchup fixes`), that
  round's `catchup base` raises INVALID_STATE "a catch-up merge is not
  pushed yet" forever. Only a hand edit gets out. It reproduces when:
  (1) `tool push` succeeded but the next `catchup step` failed twice,
  then the node blocked and got `info`; or (2) after a mid-catch-up
  "the remote branch is ahead of HEAD", the maintainer pulled, pushed
  and sent `info`.
- Proposed fix: make Python the one that ends the catch-up.
  - Preferred: on re-entry, before the node drops the trigger, it
    re-runs `catchup step` with the same trigger, so Python finishes
    the push write (`after_merge` sees the merge in HEAD and pushed)
    and answers `wait`. The node drops the trigger only if the call
    still gives the same `error`.
  - Check that this also resolves case (2). If it does not, add a
    small write op (`catchup end`) for the re-entry. It clears
    `catchup` and records `base_merge = {merge, head: HEAD}` when the
    recorded merge is in HEAD and pushed.
  - Either way, update the template and `control-plane.md` (Blocking /
    repairs).
  - Tests: case 1 and case 2, each followed by red CI or a pending fix
    → `catchup base` does not raise and returns the merge.
  - The adopt-with-a-different-`head` dead end (ECH nice-to-have) must
    also end up resolved by this.

### [should-fix] T2 — The merge lookup accepts one of main's own merges after a rebase or reset
- File: `catchup.py:386-388` (`lookup`), used at `:551-555` (`intake`) and `:661-666` (`progress`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter (reproduced in a scratch repo)
- Description: `git log -1 --first-parent --merges <head>..HEAD` returns
  main's latest "Merge pull request" commit after `git rebase
  origin/main`. Its `^2` is in origin/main, so the foreign-merge check
  passes. That merge is then recorded with `clean: false`, which
  triggers a huge irrelevant review diff, a misleading "remote ahead",
  and a repair loop that never ends.
- Proposed fix: at both lookup sites, accept the found merge only if
  `self.git.ancestor(cu["head"], found)`. Otherwise answer
  `_error("the catch-up head is no longer in HEAD")` and write nothing.
  Add a repair line to `control-plane.md`. Test: main has merge
  commits, and the implementer aborts and rebases → the error.

### [should-fix] T3 — A replayed `done` skips the push checks
- File: `catchup.py:516-517` (the `done` replay → `resume_done`)
- Severity: should-fix
- Source: qs-review-acceptance-auditor
- Description: since fix #01's S4, a re-issued `step` after a `done`
  goes straight to `resume_done` and skips D4 step 5's push checks. A
  bot push between the `done` answer and the node's `step: done` write
  is then answered `done`, and the task goes `ready_to_merge` with the
  remote ahead.
- Proposed fix: in the replay branch, run `remote_state(HEAD)` first.
  This read is read-only, so S4's no-write rule still holds.
  `ahead` → `_error("the remote branch is ahead of HEAD")`, not
  pushed → `_error("HEAD is not pushed")`, then `resume_done`. Tests:
  the replay after a second clone pushes to the branch → the error; an
  unpushed local commit → "HEAD is not pushed".

### [should-fix] T4 — A killed merge without `MERGE_HEAD` leaves an `index.lock` nobody detects; a dirty tree is not a start guard
- File: `catchup.py:499-501` (`resolve` / `index_locked`), `:650` (the `git.merge()` call in `progress`), `:579-584` (`count` start guards)
- Severity: should-fix
- Source: qs-review-blind-hunter (index.lock), qs-review-edge-case-hunter (dirty start guard, raised to should-fix because the count is spent before the merge fails)
- Description: a merge killed while it updates the index has most
  likely not written `MERGE_HEAD` yet, so `resolve()` is never reached.
  The next call merges again, fails on the lock, and the result is a
  vague TOOL_FAILED. Separately, leftover tracked changes pass the
  start guards, `catchups` is incremented and written, and then
  `git merge` refuses the merge.
- Proposed fix:
  - Check `index_locked()` before every `git.merge()` call, and at the
    top of the `cu["merge"] is None` branch. If the lock is there,
    answer `_error("a stale index.lock")`.
  - Add `self.git.dirty()` and `index_locked()` to the start guards in
    `count`, before anything is written:
    `_error("uncommitted changes outside a catch-up")` and the
    index.lock error.
  - Add a repair line in `control-plane.md` for the new detail.
  - Tests: an `index.lock` with no MERGE_HEAD on a catch-up → the
    error; a dirty tree when a trigger arrives → the error, with
    `catchups` unchanged and no state written.

### [should-fix] T5 — The git env contract is not pinned
- File: `catchup.py:310-317` (`_Git.call`), `tests/qs/control_plane/test_catchup.py:713`
- Severity: should-fix
- Source: qs-review-acceptance-auditor
- Description: D4 specifies `env_remove=gitread.ENV_REMOVED`,
  `env_extra={"GIT_TERMINAL_PROMPT": "0"}` and
  `decode_errors="surrogateescape"`, but no test asserts them. If one
  regressed, a fetch could hang on a credential prompt.
- Proposed fix: add a test over `wrap.calls`. Every git call has
  `cwd == repo.wt`, `env_remove == gitread.ENV_REMOVED`,
  `env_extra == {"GIT_TERMINAL_PROMPT": "0"}` and
  `decode_errors == "surrogateescape"`.

### [should-fix] T6 — `_REF_LOCK` matches any "Unable to create"
- File: `catchup.py:80`
- Severity: should-fix (raised from nice-to-have because a wrong `BUSY` costs 6 × 60 s of replays before the block)
- Source: qs-review-blind-hunter
- Description: a non-lock fatal error such as a full disk is read as a
  ref lock and answered `BUSY`.
- Proposed fix: match the lock only, i.e. `"Unable to create '"`
  together with `".lock'"` (or `".lock': File exists"`). Test: a fetch
  failing with "Unable to create '…/tmpfile': No space left" →
  TOOL_FAILED, not BUSY.
