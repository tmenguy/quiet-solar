### [should-fix] Z1 — Residual `OverflowError`: corrupt-huge finite kW entity bound at the landed conversion
- File: `custom_components/quiet_solar/ha_model/battery.py:388` (`landed_w = int(round(_to_w(write_value)))`)
- Severity: should-fix
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter (cross-confirmed)
- Description: A corrupt-but-finite kW entity `min` (e.g. `1e306` kW,
  any finite > ~1.8e305 kW) passes `coerce_finite_float`, wins the hard
  ent_min re-clamp at :385 after the domain clamp, then
  `_to_w(write_value)` overflows silently to `inf` (verified against
  `PowerConverter.convert`) and `int(round(inf))` raises — escaping
  `set_max_discharging_power` / `probe_if_command_set` /
  `execute_command`. Same crash class as accepted X2/Y2 — this is the
  third non-finite site; Y2 guarded both `ratio` divisions but not the
  landed conversion, and Y2's test uses a W-unit entity where `_to_w`
  is identity, dodging the crash its title claims to pin.
- Proposed fix: Compute `landed_to_w = _to_w(write_value)`; if
  non-finite, treat the corrupt bound as absent for the landed
  expectation (fall back to the domain-clamped `request_w`). Add the
  kW-variant test (`{unit: kW, min: 1e306}` → write/probe do not raise,
  landed falls back sanely) alongside the existing W-unit Y2 test.

### [nice-to-have] Z2 — Latch wipe when the expected value is None
- File: `custom_components/quiet_solar/ha_model/battery.py` (`probe_if_command_set` latch-clear calls)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: `_clear_number_divergence_latch(entity, expected)` called
  with `expected = None` (a command carrying no charge/discharge value)
  matches no `int` key, and the current implementation then wipes the
  entity's entire latch — re-arming warnings for still-current
  divergences. Unreachable today (`_command_to_values` always sets both
  values) but the `int | None` signature invites it.
- Proposed fix: Early-return (no clear) when the expected value is None,
  in both legs; small test.

### [nice-to-have] Z3 — Pass the domain max into `_entity_step` explicitly
- File: `custom_components/quiet_solar/ha_model/battery.py:241-243` (`_step_sanity_bound_w` entity-id dispatch)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: When the user configures the SAME number entity for both
  `max_charge_number` and `max_discharge_number` (config flow does not
  forbid it), the `entity_id == self.max_charge_number` branch wins and
  the discharge leg gets the charge domain max as its step sanity bound
  — an entity step between the two maxima then survives X5 on the
  discharge leg, widening its echo window (e.g. ±2000 W around a
  <=100 W expectation). Degenerate config (both writes fight over one
  entity anyway), but a current caller receives the wrong bound.
- Proposed fix: Pass the correct domain max down from
  `_number_entity_target` / `_number_reading_matches` (which know the
  leg) instead of re-deriving it from the entity id inside
  `_step_sanity_bound_w`; test the shared-entity shape on the discharge
  leg.
