# QS-453 — Review pipeline: finding verification, finding ledger, less churn

- Issue: #453 · Lane: feature-factory · Target: factory → `implement-setup-task`
- Status: plan v4 + review fix plans #01–#07 (PR #454; changes recorded inline as "fix #NN F-xxx")

## Problem

Evidence from the 273 review fix plans in `docs/stories` (84 of 148 stories
have at least one; 3.3 rounds on average, up to 10). Of ~2,000 accepted
findings only ~8% are must-fix and ~52% are nice-to-have.

Re-count done during planning (1,758 findings with a parseable
`Severity:` + `Source:` line):

| Source | must-fix | should-fix | nice-to-have |
|---|---|---|---|
| `qs-review-blind-hunter` | 33 | 246 | 443 |
| all other reviewers | 116 | 459 | 460 |

Of the blind-hunter's 33 must-fix, 18 are co-sourced with another
reviewer and ~15 are unique to it (e.g. QS-195 M1 silent override flip,
QS-178 `_battery_get_charging_power`, QS-288 CLAUDE.md `+ ` bullet,
QS-332 #04 epic worktree, QS-210 where edge-case-hunter mis-read the
code). Its noise is the nice-to-have bucket (61% of its output), plus
checklist items (TODO/FIXME, style/lint) that ruff/mypy already cover.

Structural gaps:

1. `qs-review-task` / `qs-verify-task` are forbidden to read code, so no
   one checks that a finding is real, or that its severity is earned,
   before the user triages it.
2. Code-review decisions are not recorded anywhere except "to fix" items
   in fix plans. Skipped/rejected findings resurface every round, and
   reviewers **flip-flop** (round N asks to undo what round N-1 fixed, or
   re-raises what the user rejected).
3. Every round re-reviews the whole PR, so each fix round produces a new
   crop of findings on unchanged code.
4. The Claude `frontier` class row is `claude-fable-5-1`, which needs
   usage credits (a plan reviewer died on HTTP 429 during this planning
   session).

## Goal

Cut low-value review churn in **both** code-review orchestrators
(`qs-review-task` and `qs-verify-task`) while keeping the must-fix yield:

- (a) a **finding-verification pass** between consolidation and triage;
- (b) a durable **finding ledger** (findings + decisions + state
  history), written by a deterministic script, used to dedupe and to
  catch flip-flops;
- (c) triage **defaults to must-fix + should-fix**; nice-to-have is
  opt-in and recorded as rejected when not picked;
- (d) **muzzle** `qs-review-blind-hunter` (keep its independent
  diff-only lens, drop its noise);
- (e) **2 full rounds, then delta rounds**;
- (f) **model row**: the Claude `frontier` row runs `claude-opus-5-5`
  until Fable credits are back. No agent changes class.

User-approved in DISCUSS/TRIAGE (beyond the issue's literal text):
everything applies to both orchestrators; blind-hunter muzzled, not
removed — which also drops its nice-to-have output and requires a
scenario per finding; a deterministic ledger script with stable IDs;
flip-flop detection; delta rounds; verify-task keeps its PR comments; the
verifier may promote a nice-to-have; (f).

## Out of scope

- **`/code-review` (Claude Code built-in) as a reviewer.** Rejected on
  harness parity alone: it is Claude-only, while both harnesses render the
  same reviewer roster. Whether a sub-agent can invoke a skill was
  therefore not tested — it would not change the outcome. Its useful
  ideas (CONFIRMED/PLAUSIBLE verdicts, a concrete failure scenario per
  finding) are reproduced by (a). The rationale is recorded in
  `docs/workflow/adversarial-review.md` (task 7).
- The plan-review pipeline (`qs-create-plan` and its reviewers).
- A DB / cross-task ledger, ledger stats (`show --stats`) — YAGNI. The
  script has exactly one storage seam (`load()` / `save()`); **no**
  storage interface, backend registry or abstraction beyond it.
- **Re-deciding a closed finding** (e.g. "actually fix F-003, which I
  rejected") without a reviewer re-raising it. The user can ask for it in
  the next implement session; the ledger catches up when a reviewer
  re-raises it.
- Bumping Fable to 5.2 (the user will do it when upgrading) and any
  agent class change.
- Implement phases never *write* the ledger (single writer). Their only
  change is excluding it from their `git add` (D8).
- Migration: a PR already in review when this ships has no ledger → it
  restarts at round 1 (two more full rounds). Accepted.

## Design

### D1 — New sub-agent `qs-review-finding-verifier`

- Template `scripts/qs/agent_templates/qs-review-finding-verifier.md.j2`,
  both harnesses. Hidden sub-agent, **read-only by tool list**: Claude
  `tools: Read, Grep, Glob, LSP` (compared as a set); OpenCode
  `edit: deny`, `bash: {"*": deny}`. No git: the orchestrator passes the
  diff text and the ledger in the prompt.
- Model class `deep` (`scripts/qs/models.py`); in the LSP-include list.
- Spawned **once, after** the parallel reviewer fan-out and the
  consolidation, **before** triage — a sequential post-pass, not a
  reviewer. The "parallel, never serial" rule covers the reviewer fan-out
  only (doc lines to amend: tasks 5 and 7).
- **Input** (prompt): PR number, worktree path, head SHA; the diff
  reviewed this round (full or delta) — above 3,000 lines, only the
  changed-file list plus the hunks of files cited by findings, and the
  verifier `Read`s the rest; the consolidated findings (key `C-1…`,
  source, severity, where, title, body); the ledger from
  `review_ledger.py show --format json --head <sha>` (which includes, per
  decided finding, `file_changed` and the `diff_since_decision` hunks of
  its file — D2 `show`).
- **Output**: exactly one fenced ```` ```json ```` block holding one
  object (key table below); the orchestrator pastes the block's **inner**
  JSON into `review_ledger.py add`:

  ```json
  {"mode": "verified",
   "checks": [{"ref": "F-001", "status": "RESOLVED", "evidence": "charger.py:2480"}],
   "findings": [{"key": "C-1", "source": "qs-review-edge-case-hunter",
                 "severity": "must-fix", "where": "charger.py:2471", "title": "...",
                 "verdict": "CONFIRMED", "evidence": "charger.py:2471",
                 "reproduces_when": "stopped car, phases [1,3], reset pass",
                 "severity_action": "keep",
                 "relation": {"kind": "NEW", "ref": null}, "note": null}]}
  ```

  | key | required | nullable | values |
  |---|---|---|---|
  | `mode` | yes | no | `verified` (verifier) · `fallback` (orchestrator, D4 step 4) |
  | `checks[].ref` / `.status` | yes | no | an `accepted` F-ID · `RESOLVED`/`STILL-PRESENT` |
  | `checks[].evidence` | yes | no | `file:line` |
  | `findings[].key`, `source`, `severity`, `where`, `title` | yes | no | copied from input; severity `must-fix`/`should-fix`/`nice-to-have` |
  | `findings[].verdict` | yes | yes | `CONFIRMED`/`PLAUSIBLE`/`REFUTED`; `null` = not verified |
  | `findings[].evidence` | yes | yes | `file:line`; non-null iff `verdict` non-null |
  | `findings[].reproduces_when` | yes | yes | concrete input/state; `null` = none |
  | `findings[].severity_action` | yes | no | `keep`/`demote`/`promote` |
  | `findings[].relation` | yes | no | `{"kind": NEW\|DUPLICATE\|REOPENS\|FLIP-FLOP, "ref": F-ID or null}` |
  | `findings[].note` | yes | yes | free text shown at triage |

  No other key is allowed (no `body`).
- **Verdict rules**: must-fix and should-fix always get a verdict.
  Nice-to-have: `verdict: null` unless the verifier, reading its text,
  sees a concrete runtime scenario and verifies it — only then
  `severity_action: promote` (→ should-fix). `orchestrator:doc-maintenance`
  is never verified (`verdict: null`, deterministic). `demote`
  (must/should → nice-to-have) is required for a verified finding with
  `reproduces_when: null`, except for the scenario-exempt sources
  `qs-review-acceptance-auditor`, `qs-review-regression-proof`,
  `orchestrator:doc-maintenance`.
- **`checks`**: one per ledger finding in state `accepted` — all of them.
- **Relations** (judged against the ledger as shown, i.e. the state at the
  start of the round):
  - `NEW` — not in the ledger;
  - `DUPLICATE` — restates F-x, nothing new: F-x `rejected` and the cited
    region unchanged since the decision (judged from
    `diff_since_decision`), or F-x `resolved`/`superseded`/`accepted`;
  - `REOPENS` — F-x `accepted`/`resolved` whose fix is missing, broken or
    regressed;
  - `FLIP-FLOP` — (a) asks to undo the fix of an `accepted`/`resolved`
    F-x, or (b) re-raises an F-x the **user** rejected
    (`rejected_by: user`) in a region that changed since the decision.
    Re-raises of `default-skip`/`verifier` rejections are `DUPLICATE`
    (region unchanged) or `NEW` (changed) — never FLIP-FLOP;
  - a `REFUTED` finding relates only `NEW` or `DUPLICATE` — refuting
    a claim never reopens or flips a ledger finding (fix #02 F-022);
  - several matches → the most recent non-`superseded` F-x;
    `file_changed: null` means "unknown", never "unchanged".
- Hard rules: never edit; never invent new findings (`promote` only
  re-ranks a reported one); every `REFUTED` carries refuting evidence;
  output is the single JSON block only.

### D2 — `scripts/qs/review_ledger.py` (deterministic ledger)

**Location and root.** Ledger path =
`<root>/docs/stories/QS-<N>.review_ledger.json` (built from `root`, never
from an absolute constant), outside the `*_review_fix_*` glob. Imports
follow the scripts' convention
(`from utils import get_repo_root  # type: ignore[import-not-found]`,
as `render_agents.py:41` imports from `utils`). Root = `--root PATH` if
given, else `get_repo_root()`; either way normalised with
`git -C <root> rev-parse --show-toplevel`; `CalledProcessError`/`OSError`
→ exit 1 ("not a git repo"). Otherwise stdlib only (`argparse`, `json`,
`pathlib`, `subprocess` for git with `cwd=root`);
`main(argv: list[str] | None = None) -> int`;
`if __name__ == "__main__": raise SystemExit(main())`. Plain write.

**Round lifecycle = git.** The ledger is committed only when a round
ends (D4 step 8); implement phases never stage it (D8). So:
*finished* round = ledger clean vs `HEAD`; *started* round = ledger dirty
vs `HEAD` (or untracked) with at least one round.

**Schema (version 1):**

```json
{
  "version": 1,
  "rounds": [{"n": 1, "head": "<sha>", "added": true}],
  "findings": [
    {
      "id": "F-001", "round": 1, "source": "qs-review-edge-case-hunter",
      "reported_severity": "must-fix", "severity_action": "keep",
      "severity": "must-fix",
      "where": "path/file.py:42", "title": "...", "note": null,
      "verdict": "CONFIRMED", "evidence": "path/file.py:42",
      "reproduces_when": "...", "relation": null,
      "state": "accepted", "rejected_by": null, "decided_round": 1,
      "history": [
        {"round": 1, "from": null, "to": "open", "note": "added"},
        {"round": 1, "from": "open", "to": "accepted", "note": "user: fix"}
      ]
    }
  ]
}
```

- `severity` = `reported_severity` after `severity_action`.
- IDs: `F-` + (max existing + 1), zero-padded to 3 digits, wider past 999.
- `decided_round` is set by `set`; the decision SHA is the head of the
  round whose `n == decided_round`.
- History "note" entries (no state change) have `from == to`.
- `rejected_by` is cleared when a finding leaves `rejected`.
- `relation` is `null` for NEW; `{"kind", "ref"}` otherwise; a downgraded
  relation is stored as `null` with history note
  `"relation-invalid: <kind> <ref>: <why>"`.
- When a report re-targets an existing F-x (`reopened`, `challenged`),
  F-x takes the new report's `reported_severity`, `severity_action`,
  `severity`, `where`, `verdict`, `evidence`, `reproduces_when`, `note`;
  the previous values go into the history note.
- `version` missing or ≠ 1, or invalid JSON → exit 2 (corrupt).

**States and transitions** (enforced by `set` and by `add`'s
reconciliation; `set` outside the table → exit 1):

| from | to | trigger |
|---|---|---|
| — | `open` | `add`: `NEW`, or `FLIP-FLOP` (a) → a new F-y with `relation {FLIP-FLOP, F-x}` |
| `open` | `accepted` | `set --to accepted` |
| `open` | `rejected` | `set --to rejected --by user\|default-skip\|verifier` |
| `accepted` | `resolved` | `add`: check `RESOLVED` |
| `accepted` | `open` | `add`: check `STILL-PRESENT`, or `REOPENS` |
| `resolved` | `open` | `add`: `REOPENS` (regression) |
| `rejected` | `open` | `add`: `FLIP-FLOP` (b) — only `rejected_by: user` ("challenged") |
| `accepted`/`resolved`/`open` | `superseded` | automatic, when the FLIP-FLOP F-y that refs it is `set --to accepted` (no-op if already `superseded`); `open` covers an F-x reopened in the same round, so the order of the two decisions does not matter (fix #01 F-001) |

**CLI** — every subcommand takes `--issue N [--root PATH]`. Exit 0 ok;
1 invalid input / transition / unknown ID / not a repo / wrong lifecycle
state (argparse usage errors too — `ArgumentParser.error` overridden);
2 corrupt ledger. Missing file → empty ledger. JSON on stdout except
`show --format md`; on exit 1/2 a JSON `{"error": "...", ...}` naming the
bad key/ID.

- **`start-round --head <sha> [--force-full]`**, in order:
  1. Ledger dirty vs `HEAD` (or untracked) → restore it from `HEAD`
     (`git checkout HEAD -- <path>`; `git rm --cached` + delete if absent
     from `HEAD`); `discarded: true`. A failed restore, or a ledger still
     dirty after it, → exit 1 `"could not discard the unfinished round"`
     (fix #01 F-004). Exception: when the ledger at `HEAD` is a
     committed-unfinished round, the dirty copy holds recovery decisions
     and is **not** discarded — exit 1 with its `round` and `open` IDs
     (fix #02 F-029) — but only when it loads and its `rounds` equal the
     committed ones; a deleted, corrupt or rounds-less copy is restored
     from `HEAD` as usual (fix #03 F-035 / F-036). `docs/stories/QS-<N>.story_review_fix_*` files absent from
     `HEAD` (untracked, or staged by a failed commit) are listed in
     `stale_fix_plans` (not deleted — fix #02 F-028).
  2. The committed last round has a finding in state `open` → exit 1
     (`"error": "round N committed unfinished"`, listing the IDs, with a
     `hint`). Recovery stays in the CLI: `set` also works on that
     committed round (fix #01 F-003); then `check-round`, and the round
     finishes like step 8 (`round` is in the error): any finding accepted
     with that `decided_round` → fix plan + implement handoff; none →
     ledger-only commit, then `changed_since_round` (in the error: the
     step-4 diff of that round's head vs `--head`) → `start-round` again,
     else step 8's all-skip finish (fix #03 F-037, fix #04 F-043 / F-044,
     fix #05 F-050, fix #06 F-050 / F-053 / F-054).
  3. No rounds → round 1, `full`.
  4. Same content as the last round's head: `git diff --quiet <last_head>
     <head> -- . ':(exclude)docs/stories/QS-<N>.review_ledger.json'
     ':(exclude)docs/stories/QS-<N>.story_review_fix_*'` exits 0 (1 or
     128 = changed). Then, unless `--force-full` → `status: "no-change"`,
     nothing appended. (The story file is **not** excluded: a story-only
     fix is a change.)
  5. Else append `{"n": last+1, "head": <sha>, "added": false}`,
     `status: "new"`. Mode: rounds 1–2 → `full`, `reason: null`;
     `--force-full` → `full`, `reason: "forced"`; round ≥ 3 → `delta`
     with `base` = last head, unless `git merge-base --is-ancestor`
     exits 1 → `full`, `"base not an ancestor"`; exits 128 → `full`,
     `"base unknown"`; `git rev-list --merges <base>..<head>` non-empty →
     `full`, `"merge commit since base"`.
  - Output: `{"status": "new"|"no-change", "discarded": bool,
    "stale_fix_plans": [...], "round": n, "mode": "full"|"delta"|null,
    "base": sha|null, "reason": str|null}` (`mode`/`base` null on
    `no-change`; `base` null on `full`).
- **`add --keys C-1,C-2,…`** — one JSON object on stdin (the D1 object;
  invoked as `python scripts/qs/review_ledger.py add --issue N --keys …
  <<'QS_LEDGER'`, like `qs-decompose-epic.md.j2:206`). `--keys` is
  required: the consolidated keys, and the object's `findings` key set
  must equal them (exit 1 naming `missing` / `extra` — fix #02 F-015). Requires a started round whose
  `added` is false (else exit 1); sets `added: true`.
  **Validation** (any failure → exit 1, nothing written): not JSON;
  missing/unknown/duplicate key; bad enum; `ref` missing when
  `kind != NEW`; a `checks[].ref` that is not an `accepted` F-ID;
  `evidence` null with a non-null `verdict` or vice versa; `promote` on a
  non-nice-to-have, with `verdict: null` / `REFUTED`, or with
  `reproduces_when: null` (fix #01 F-007); `demote` on a nice-to-have;
  a non-string `checks[].ref` (fix #01 F-006).
  A `REFUTED` finding with relation `REOPENS` / `FLIP-FLOP` (fix #02
  F-022). In `mode: fallback` also: non-empty `checks`, or a finding
  with `severity_action != keep` or relation `!= NEW` (fix #02 F-021).
  In `mode: verified` also: a must/should with `verdict: null` (unless
  source `orchestrator:doc-maintenance`); a verified must/should from a
  non-exempt source with `reproduces_when: null` and `severity_action !=
  demote`; `checks` refs ≠ the set of `accepted` IDs.
  **Reconciliation** — all preconditions are evaluated against the
  **snapshot at the start of `add`** (what the verifier saw):
  1. Resolve each element's relation against the snapshot:
     - unknown ref → `NEW` (downgraded);
     - ref `superseded`: `DUPLICATE` stays; `REOPENS`/`FLIP-FLOP` are
       **redirected** to `FLIP-FLOP` (a) against the live head of its
       supersede chain — each hop the newest accepted FLIP-FLOP that refs
       the previous one (the cycle "fix A → undo A → A again" is a
       flip-flop; fix #01 F-002). No live head (dead end, cycle) → `NEW`
       (downgraded);
     - `DUPLICATE`: any decided state (not `open`). Exception: the
       report's effective severity (after its `severity_action`) higher
       than F-x's `severity` → `NEW` (downgraded, note `"severity
       escalated"`) — a re-demoted repeat stays a duplicate (fix #01
       F-005);
     - `REOPENS`: ref `accepted`/`resolved`; else `NEW` (downgraded);
     - `FLIP-FLOP`: ref `accepted`/`resolved` → (a) new F-y; ref
       `rejected` with `rejected_by: user` → (b) challenge F-x; else
       `NEW` (downgraded).
  2. Create every new finding (`NEW`, downgraded, FLIP-FLOP (a) F-y) in
     state `open`.
  3. For each existing F-x, collect its effects (its check + every
     element targeting it) and apply **one** transition, by precedence:
     `REOPENS` > `FLIP-FLOP (b)` > check `STILL-PRESENT` > check
     `RESOLVED`; `DUPLICATE` never transitions. The others become history
     notes and are reported as `merged`.
  - Output: `{"findings": {"C-1": {"id": "F-004", "effect":
    "new|new-downgraded|duplicate|reopened|challenged|flip-flop|merged"}},
    "checks": {"F-001": "resolved|reopened|merged"}}`.
- **`set --id F-x --to accepted|rejected [--by user|default-skip|verifier] [--note "..."]`**
  — requires a started round with `added: true` (or a committed
  unfinished round, for recovery — fix #01 F-003); only from `open`;
  `--by` required for `rejected`, forbidden for `accepted`; stamps
  `decided_round` = latest round; accepting a FLIP-FLOP F-y supersedes its
  ref (no-op if already superseded).
- **`check-round`** — writes nothing. Exit 1 if the last round has
  `added: false` (fix #02 F-030) or if any finding is `open`
  (`{"open": [IDs]}`); else exit 0 with `{"accepted_unchecked": [IDs]}`
  — `accepted` findings decided before this round and not checked in it
  (only possible in `fallback` mode).
- **`show [--format json|md] [--head <sha>]`** — `json`: the whole ledger;
  with `--head` (resolved like `start-round --head`: an unknown commit →
  exit 1, fix #01 F-008), each decided finding also gets `file_changed`
  (`where` must match `^(?P<path>[^\s:]+)(:\d+(-\d+)?)?$`, else `null`;
  a path present at neither revision → `null`, never "unchanged" — a bare
  basename would otherwise read as unchanged (fix #01 F-010);
  `git diff --quiet <decision sha> <head> -- <path>` → 0 `false`,
  1 `true`, 128 `null`) and `diff_since_decision` (that diff's text,
  capped at 200 lines, `null` when `file_changed` is not `true`). `md`: a
  table `ID | Round | Source | Sev | Where | Title | State | By | Relation`.

### D3 — Single writer, fix-plan format

Only the orchestrator calls mutating subcommands. Fix plans name findings
by ID in the heading only: `### [must-fix] F-003 — <title>`; the
`File/Severity/Source/Description/Proposed fix` lines stay. No test or
script parses fix-plan headings. Fix plans are written **after**
`check-round` passes (D4 step 8).

### D4 — Orchestrator protocol (both `qs-review-task` and `qs-verify-task`)

Headings are contract-test anchors (task 3); all `###` headings and
fences at column 0. Runtime placeholders: `{{pr_number}}`, `{{branch}}`,
`{{issue}}` as today; `{{round}}` = `round` from the `start-round` JSON;
`{{fix_plan_path}}` = the `next_review_fix_path` output (step 8).

1. **`### 1. Fetch the PR diff and open the round`** — context;
   `git fetch origin {{branch}}`; PR head =
   `gh pr view {{pr_number}} --json headRefOid --jq .headRefOid`; local =
   `git log -1 --format=%H`. Equal → go on. Local ahead of the PR head
   (a failed push) → `git push origin {{branch}}`, re-read the PR head.
   Local behind → STOP ("pull first"). Diverged → STOP (ask the user).
   The worktree must equal the head (the verifier and the repo-reading
   reviewers read it): `git status --porcelain` showing anything besides
   the ledger and fix plans → STOP (fix #02 F-016). Only after the heads
   are synced, `gh pr view` / `gh pr diff` (fix #02 F-019).
   Then `python scripts/qs/review_ledger.py start-round --issue {{issue}}
   --head <head>` (`--force-full` when the user asked for a full review).
   Report `discarded` ("round N was not finished — redoing it"),
   `stale_fix_plans` (ask the user whether to delete them), and a `full`
   `reason`. Exit 1 "committed unfinished" → STOP, show the IDs; the user
   decides them with `set` (fix #01 F-003) and the round finishes like
   step 8 — accepted ones get a fix plan and an implement handoff, all
   skipped → ledger-only commit, then restart only when the error's
   `changed_since_round` is true (new code needs a round) or the user
   asked for a full review (`--force-full` — fix #07 F-055), else step 8's
   all-skip finish with its banner / PR comment (fix #03 F-037; fix #05 /
   #06 F-050, F-053; the branch is on every finding accepted in that
   round — fix #04 F-044). `no-change` → say nothing changed since round N and offer
   a forced full re-review (`--force-full`), else stop. Otherwise, if the
   ledger has findings, print `show --format md`.
2. **Parallel fan-out** (heading unchanged per orchestrator). Every
   reviewer is told to ignore `docs/stories/QS-{{issue}}.review_ledger.json`
   and `docs/stories/QS-{{issue}}.story_review_fix_*`. Delta mode:

   | orchestrator | gets the delta | always full |
   |---|---|---|
   | `qs-review-task` | blind-hunter (orchestrator pastes the delta diff **text**), edge-case-hunter (`base` + exclude pathspec) | acceptance-auditor, coderabbit |
   | `qs-verify-task` | edge-case-hunter | coderabbit, regression-proof |

   Delta diff = `git diff <base>..<head> -- .
   ':(exclude)docs/stories/QS-{{issue}}.review_ledger.json'
   ':(exclude)docs/stories/QS-{{issue}}.story_review_fix_*'`. The
   coderabbit wrapper re-reads CodeRabbit's comments each round; repeats
   become `DUPLICATE`s.
3. **`### 3. Consolidate findings`** — dedupe across reviewers
   (unchanged). Drop as invalid any finding whose `where` is the ledger
   or a fix plan. The "CodeRabbit unavailable" meta-finding is an info
   line, never added. Doc-maintenance audit unchanged; its finding gets
   source `orchestrator:doc-maintenance`.
4. **`### 4. Verify findings`** — spawn `qs-review-finding-verifier`
   with the D1 inputs. **Fallback** (crash, no JSON block, or a second
   `add` exit 1 at step 5): the orchestrator builds the object itself —
   `mode: fallback`, `checks: []`, every finding `verdict: null`,
   `evidence: null`, `reproduces_when: null`, `severity_action: keep`,
   `relation {NEW, null}`, `note: "unverified"`. Fallback findings are
   never REFUTED; accepted entries stay `accepted`.
5. **`### 5. Record findings`** — paste the inner JSON into
   `review_ledger.py add --keys <consolidated keys>` (`<<'QS_LEDGER'`;
   `--keys ""` when there are none — fix #02 F-015, fix #03 F-032). Exit 2 → HALT. Exit 1 on the
   verifier's object → show the error, re-ask the verifier once with it,
   then fall back (step 4). Exit 1 on the fallback object, or a lifecycle
   error → HALT with the error (the orchestrator never edits findings).
6. **`### 6. Zero-blocking fast path`** — only in `verified` mode with no
   `accepted_unchecked`: if every `open` finding falls in
   `Dropped by verifier` or `Nice-to-have` (step 7), `set` the former
   `--to rejected --by verifier` and the latter `--by default-skip`, list
   them in the completion message (`qs-verify-task` also keeps posting the
   nice-to-have PR comment), `check-round`, commit (ledger-only fence,
   step 8), hand off to finish-task (existing `m.handoff`).
7. **`### 7. Interactive triage`** — each `open` finding is in exactly one
   bucket, the first row that matches:

   | # | bucket label | content | default |
   |---|---|---|---|
   | 1 | `FLIP-FLOP` | effects `flip-flop` / `challenged`, shown with F-x history | **none — explicit decision** |
   | 2 | `Reopened` | effect / check `reopened` | fix |
   | 3 | `Unverified` | `mode: fallback` must/should | **none — explicit decision** |
   | 4 | `Dropped by verifier` | verdict `REFUTED` or `severity_action: demote`, with evidence + note | reject (overridable) |
   | 5 | `Blocking` | must/should, verdict `CONFIRMED`, `PLAUSIBLE` (marked `?`), or doc-maintenance (marked `deterministic`); promoted marked `↑` | fix — "fix all" covers rows 2 + 5 |
   | 6 | `Nice-to-have` | the rest, collapsed | reject (opt-in) |

   Info lines (not buckets): "N repeats of decided findings, suppressed"
   (`duplicate`), every `merged` and `new-downgraded` effect with its
   note, and `accepted_unchecked` IDs.
8. **`### 8. Record decisions, fix plan, commit`** — `set` every decision
   (FLIP-FLOP decisions first; a later `set` refused because its finding
   is now `superseded` is expected, and that finding drops out of the
   fix plan, which lists exactly the findings accepted this round — fix
   #02 F-027)

   `{{fix_plan_path}}`, write the fix plan (D3), and commit with:

   ```bash
   git add "docs/stories/QS-{{issue}}.review_ledger.json" "{{fix_plan_path}}"
   git commit -m "QS-{{issue}}: review round {{round}}, fix plan" -- "docs/stories/QS-{{issue}}.review_ledger.json" "{{fix_plan_path}}"
   git push origin {{branch}}
   ```

   If all skipped: no fix plan; `qs-verify-task` keeps posting its

   ```bash
   git add "docs/stories/QS-{{issue}}.review_ledger.json"
   git commit -m "QS-{{issue}}: review round {{round}}" -- "docs/stories/QS-{{issue}}.review_ledger.json"
   ```

## Risks

- **Fuzzy matching.** Relations are the verifier's judgement (helped by
  `diff_since_decision`); the script enforces preconditions on the
  snapshot, downgrades invalid ones to NEW, and shows every downgrade and
  merge. FLIP-FLOP and Unverified never auto-decide. The script does not
  enforce the region judgement itself.
- **Delta rounds miss regressions** caused by a fix in unchanged code.
  Mitigation: rounds 1–2 full; edge-case-hunter reads around the delta;
  whole-PR reviewers stay full; merges force full; CI full gate;
  `--force-full`.
- **Verifier cost/latency** — one extra agent per round; bounded by the
  3,000-line cap and by verifying must/should only.
- **Muzzled blind-hunter may still drop some unique must-fix** —
  accepted; measurable later from the ledger.
- **Claude `frontier` = `deep`** until Fable is back: planning and
  judgment reviewers share Opus 5.5 with the hunters on Claude.
- Each ledger push re-runs CI.
- v4 folds round-3 findings without a round-4 review (user choice);

  rule-combination bugs.
