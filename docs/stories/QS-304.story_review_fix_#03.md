### [must-fix] 1 — the OFF / SENSORS_ONLY release is unreachable in production
- File: `custom_components/quiet_solar/ha_model/home.py:2856-2869`
  (call site `:2868`); early return at `:2912-2916`
- Severity: must-fix
- Source: qs-review-edge-case-hunter **and**
  qs-review-acceptance-auditor (independently, same conclusion)
- Description: `_release_unmanaged_loads_lost_control_state()` is called
  from inside `check_loads_commands`' own early-return branch, but
  `check_loads_commands` has only two production callers —
  `home.py:2940` and `finish_off_grid_switch` (`:2836`, invoked at
  `:2922`) — and **both are downstream of `update_loads`' identical early
  return at `:2912-2916`** for `home_mode is None` / `HOME_MODE_OFF` /
  `HOME_MODE_SENSORS_ONLY`. So in exactly the two modes round-#02
  finding 5 named first, the release can never execute. Only the
  `HOME_MODE_CHARGER_ONLY` arm (`:2881-2884`) is reachable. The
  `finish_setup(time) is False` path (`:2871`, `:2918`) is likewise
  unreleased.

  Mode by mode:
  - **SENSORS_ONLY** is worse than a stale latch: `update_all_states`
    (`:2796-2799`, excludes only OFF) keeps running
    `HADeviceMixin.update_states` → `async_update_callback`
    (`ha_model/device.py:1141-1142`), so `is_uncontrollable is True` is
    *actively re-asserted* into `binary_sensor.qs_load_uncontrollable`
    every state loop.
  - **OFF**: the entity retains its last PROBLEM state and nothing can
    clear it — no `launch_command`, no ack, `running_command` stays set,
    and the `home_mode` select is a plain attribute write with no
    `reset()`.
- Why the test did not catch it: the pin
  (`tests/ha_tests/test_bug_304_uncontrollable_load.py:531`, `:542`)
  calls `home.check_loads_commands(T0)` directly and never
  `home.update_loads`, bypassing the unreachable path. Coverage cannot
  see this class of defect.
- Proposed fix: release from a site that actually runs in these modes.
  Options, in preference order: (a) at the top of `update_loads`, before
  its early return; (b) on the `home_mode` transition itself. Whichever
  is chosen, the release must also cover the `finish_setup is False`
  path. **Pin by driving `home.update_loads(...)`** and asserting the
  sensor clears in OFF and in SENSORS_ONLY. Move the three places that
  currently document the false behaviour along with the code:
  `home_model/load.py:735-752` (the `release_lost_control_state`
  docstring, whose "one site that already owns the managed-set decision
  is narrower and testable" premise is what failed),
  `docs/agents/concepts/qs-home-orchestrator.md:78-85`, and the story's
  disposition 2 / AC3 clearer 5.

### [must-fix] 2 — `release_lost_control_state` keeps the slot and the spent rung → push spam
- File: `custom_components/quiet_solar/home_model/load.py:735-754`
- Severity: must-fix
- Source: qs-review-edge-case-hunter (filed by
  qs-review-acceptance-auditor as should-fix; higher severity taken)
- Description: the method releases the clock (`_clear_unresponsive`) but
  leaves `running_command_num_relaunch` at its saturated value **and**
  leaves the slot occupied. So the first managed cycle after the load
  returns re-crosses the threshold immediately and emits a second ERROR
  *and* a second mobile push with zero fresh evidence. It is the only
  clock-releasing path that does not reset the rung —
  `_drop_running_command` (`:869`) and the `keep_commands=False` wipe
  (`:371`) both zero it, which is exactly what forces a fresh 1050 s
  before the next shout. Verified in the pure layer: after
  `drive_until_uncontrollable` (rung 6, 1 push), each
  `release_lost_control_state(...)` + one `check_and_relaunch_command(...)`
  adds one more `"Lost control of load"` ERROR and one more
  `DEVICE_STATUS_CHANGE_ERROR` push — **1 → 2 → 3 → 4** over three round
  trips.
- Reachable today via a CHARGER_ONLY ↔ ON toggle with an uncontrollable
  non-charger present (the one live release arm). **Fixing must-fix 1
  arms it for the OFF/ON toggle too** — i.e. the user's own remediation
  becomes a notification-spam loop, and an automation that flaps home
  mode pushes once per flap. This is why must-fix 1 and 2 must land
  together.
- Breaks AC9's one-line-in guarantee *across episodes*;
  `tests/ha_tests/test_bug_304_uncontrollable_load.py:242` only checks
  within a single episode. Note
  `tests/test_bug_304_command_deadlock.py:828` already uses this exact
  mechanism deliberately (`load.unresponsive_since = None  # re-arm so
  the notify is reached again`) to re-trigger a push, so the behaviour is
  demonstrated in-tree — just not as a defect.
- Proposed fix: zero `running_command_num_relaunch` alongside the clock,
  so a returning load needs a fresh full ladder before it can shout
  again. Consider whether the slot should also be emptied — align with
  whichever sibling (`_drop_running_command`) is the closer analogue, and
  state the choice in the docstring. Pin with a mode round-trip test
  asserting the push count stays at 1 across at least three round trips.

### [should-fix] 3 — CHARGER_ONLY disarms detection on loads QS still commands
- File: `custom_components/quiet_solar/ha_model/home.py:2881-2884` vs
  `update_loads:3019`
- Severity: should-fix (orchestrator note: the most consequential item on
  the should-fix list — it silently reinstates the original QS-304
  symptom)
- Source: qs-review-edge-case-hunter
- Description: the release asserts "the load is no longer managed by QS",
  but `update_loads`' dispatch loop iterates `self._commands`
  **unfiltered** by `all_loads`, so QS keeps issuing `launch_command` at
  non-chargers from the previous solve's queue while their lost-control
  detection is disarmed on **every** cycle (`_clear_unresponsive` wipes
  both `unresponsive_since` and `_last_supersede_time` at `:727`/`:732`).
  With `is_uncontrollable` forced False each cycle, `launch_command` takes
  the `not self.is_uncontrollable` stack branch (`:896-900`), and
  `_relaunch_stale_command`'s promotion branch (`:1142-1147`) can never
  fire, while the ladder never runs because the load is not swept. The
  stale command stays in flight, every new intent is stacked and
  overwritten, with no ERROR and no PROBLEM sensor — **the original
  QS-304 symptom, reinstated silently.** Window lasts until the queue
  drains or the next solve replaces `_commands` (up to 5 min per
  `:2959`), and `check_loads_commands` at `:2940` runs *before* that solve
  on every cycle.
- Proposed fix: make "managed" mean the same thing in both places. Either
  filter the `update_loads` dispatch loop by the same managed set the
  release uses, or do not release a load that still has queued commands.
  This is the finding that most argues for treating the release as one
  mechanism (constraint 2 above) rather than four patches.
