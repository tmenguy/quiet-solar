### [must-fix] M1 — `head_state` ignores CodeRabbit's check run (CodeRabbit no longer posts a commit status)
- File: `scripts/qs/control_plane/coderabbit.py:197-213` (`head_state`), used by `_trigger` (:235) and `_ingest` (:272)
- Severity: must-fix
- Source: qs-review-edge-case-hunter (confirmed live by the orchestrator; the qs-review-coderabbit wrapper hit the same thing)
- Description: Since 2026-10-27 (PR #433 head `1696d233` onward) `commits/{sha}/statuses` holds no `CodeRabbit`
  status. CodeRabbit reports through a **check run** named `CodeRabbit` from app `coderabbitai`. Live on PR #435's
  head `01fc582e`, the check run went from `status: in_progress`, title "Review in progress", to
  `status: completed`, `conclusion: success` (title "Finished" per the edge-case hunter). So `head_state` always
  answers `not_requested`:
  - the trigger never answers `already`: it posts a duplicate `@coderabbitai review` that counts toward `CR_MAX_REVIEWS`;
  - a clean review that posts no review object never settles: ingest stays `BUSY` until `CR_WAIT_S` (900 s), then
    the node writes the wrong label "CodeRabbit skipped: no review in time".
- Proposed fix:
  - In `head_state`, also read `repos/{owner}/{repo}/commits/{head}/check-runs?check_name=CodeRabbit`. The answer is
    an object `{total_count, check_runs: [...]}`, not a list, so `_pages` as written does not fit; add a small
    helper, or flatten `check_runs` across `--paginate --slurp` pages. Keep entries whose `app.slug == "coderabbitai"`.
  - Map the latest check run:
    - `queued` / `in_progress` → `in_progress`, stamped `started_at`;
    - `completed` + `conclusion == "success"` → `completed`, stamped `completed_at`, unless its `output.title` /
      `output.summary` says "rate limited" or "skipped", which map to `not_requested` (the same meaning as the
      status descriptions);
    - any other conclusion → `not_requested`.
  - When both a status and a check run exist, take the newer of the two.
  - Unexpected or unparseable answers → `BUSY`, as for statuses.
  - Make the latest-entry choice deterministic: key `(timestamp, id)`. This also covers the edge-case hunter's
    nice-to-have about ties.
  - Add check-run fixtures captured live from PR #435's head (`gh api
    "repos/tmenguy/quiet-solar/commits/01fc582ec3466626338a79348a9f2c25397836f6/check-runs?check_name=CodeRabbit"`)
    for completed, plus a hand-made in-progress one.
  - Add tests:
    - trigger answers `already` on a check-run `in_progress` / `completed` head;
    - ingest settles `reviewed, ids: []` after `CR_SETTLE_S` on a completed check run with no review object;
    - "the newer of status vs check run" wins;
    - check-runs gh failure or unparseable answer → `BUSY`;
    - stay at 100% coverage.
  - Update the `head_state` docstring and the CodeRabbit paragraphs of `docs/workflow/control-plane.md` (node
    protocol: what counts as "reviewed" / "in progress"). Add a short implementation note in the story that the
    signal moved to a check run.

### [should-fix] S1 — a head with no GitHub Actions suite keeps the CI watcher on fast polling forever
- File: `scripts/qs/control_plane/ciwatch.py:124-125` (`_verdict`), `:276` (the `fast` decision)
- Severity: should-fix
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter (merged)
- Description: No `github-actions` suite → `PENDING`, so `fast = True` and the PR is polled every `CI_FAST_S` (30 s)
  for as long as it is watched. This happens on a PR that conflicts with main, on `[skip ci]`, with Actions down,
  or with a task parked `blocked` on such a PR. The pre-#425 code polled such a head slowly.
- Proposed fix: keep the verdict `PENDING`, because suites may simply not be created yet after a push. But poll fast
  only when the head moved (`sha != row["ci_sha"]`) or at least one Actions suite exists and is incomplete; a head
  with no Actions suite at all is polled at `CI_SLOW_S`. To do this, carry the fact on `PrCi` (e.g. a `suites: int`
  count of Actions suites, or a boolean) and update the `PrCi` field-order test. Add a test: no suite, same sha →
  slow poll; no suite, new sha → fast. Update the CI watcher section of `control-plane.md` in one sentence.

### [should-fix] S2 — a stale failed Actions suite on the same head keeps the verdict FAILURE forever
- File: `scripts/qs/control_plane/ciwatch.py:66-70` (`_PR_FIELDS`), `:117-130` (`_verdict`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: GitHub creates one check suite per workflow run. If a failing head gets a second run of the same
  workflow on the same SHA (`pr-quality.yml` runs on `reopened`; a close/reopen without a push), the old
  `COMPLETED/FAILURE` suite stays next to the new passing one, and `any(...)` keeps `FAILURE`. The old rollup kept
  the latest run per check name, so this is a regression.
- Proposed fix: add `workflowRun{ databaseId workflow{ databaseId } }` to the `checkSuites` node selection. In
  `_verdict`, keep only the latest suite per workflow (highest `workflowRun.databaseId`) before deciding; suites with
  no `workflowRun` yet are kept as they are. Add tests: an old failed plus a newer passing suite of the same
  workflow → `SUCCESS`; an old passing plus a newer failing one → `FAILURE`; two different workflows are each
  counted. Document it in the CI watcher section.

### [should-fix] S3 — `cr: trigger` has no wait bound; the wait-loop end condition is circular
- File: `scripts/qs/agent_templates/qs-node.md.j2:306-315` (build step 2) and `:564-566` ("The wait ends…")
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: Only `cr: pending` is bounded by `CR_WAIT_S` from `cr_from`, and `cr_from` is set only on
  `triggered` / `already`. The template says the wait ends when `cr` is neither `pending` nor `trigger`, then says an
  unanswered `trigger` "then becomes `skipped`". That is circular, so a trigger that keeps answering `BUSY` can hold
  the wait until `ci_wait` blocks the node.
- Proposed fix:
  - Set `cr_from` = now when entering `cr: trigger` too, so `CR_WAIT_S` bounds `trigger` and `pending` together.
  - In "Between loop calls", add: `cr: trigger` past [[ crwait ]] s since `cr_from` → `cr: skipped` ("CodeRabbit
    trigger failed").
  - Rephrase the end condition: "The wait ends when CI is terminal and `cr` is no longer `pending`; once CI is
    terminal, a `cr: trigger` still unanswered becomes `cr: skipped` ("CodeRabbit trigger failed")".
  - Update the `cr_from` description at :182, and `control-plane.md` if it restates this.
  - Keep the rendered-text tests green; extend one if they pin the wording.

### [should-fix] S4 — `qs-node-plan-concrete` flags every file the plan will create as `must_fix`
- File: `scripts/qs/agent_templates/qs-node-plan-concrete.md.j2:60-61`
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: "A file the plan references and you cannot find: `must_fix`" also matches files the plan says it
  will create, which gives false must-fix findings on most plans.
- Proposed fix: limit it to files the plan says it modifies or reads, and say explicitly that files the plan
  creates are expected to be missing. Only a create-target whose parent directory or module path is wrong is a
  finding.
