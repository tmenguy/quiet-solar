## Findings to fix

### [should-fix] R2-1 — `_user_replay_for_init` instance flag leaks across awaits (regression from fix #01 S2)
- File: `custom_components/quiet_solar/ha_model/car.py:~212`, `:~2738-2746` (`user_set_next_charge_target`), `:~2937-2957` (`set_qs_bump_solar_charge_priority`), `:~359-366` (D3 hook)
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-edge-case-hunter, qs-review-acceptance-auditor
- Description: the flag is set on the car instance and held across real `await`s (`convert_auto_constraint_to_manual_if_needed`, `setup_car_charge_target_if_needed`, `charger.update_charger_for_user_change()`). (a) A genuine user action on the same car during a replay skips its pin; (b) two interleaved calls (replay True + user False) save/restore in the wrong order and leave the flag stuck at True for the process lifetime → that car's user actions never pin again.
- Proposed fix: remove the instance flag. Use a module-level `contextvars.ContextVar[bool]` (per asyncio task, default False) set with a token and reset in `finally` (`var.reset(token)`), read by the D3 hook — or thread `for_init` explicitly to every `set_user_originated` call site on the replay path. Prefer the ContextVar if threading touches many signatures. Test: interleave a `for_init=True` replay blocked on an awaited `asyncio.Event` with a concurrent `for_init=False` user call on the same attached car → the user call pins; after both finish, a new user action still pins (flag not stuck).

### [should-fix] R2-2 — persisted pin survives a car swap during HA downtime even when the old car reports `off`
- File: `custom_components/quiet_solar/ha_model/charger.py` (`device_post_home_init` ~3886-3958, `attach_car` / `_restore_boot_attached_car_best_score` ~5001-5056, `update_to_be_saved_extra_device_info` ~2567), `const.py`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: the floor restore correctly refuses on a valid `off` since `saved_at`, but `USER_ORIGINATED_CAR_NAME` is persisted with the charger's user-originated data and becomes `_boot_car`; the user-selection branch then returns the old car every cycle. Since any user action now pins, the story's scenario row "A unplugged and B plugged while HA is down, A's API reports `off` → normal rules" breaks for any pair the user touched.
- Proposed fix:
  - Persist a pin reference time: in `update_to_be_saved_extra_device_info(data, time)`, write a new key `STORAGE_KEY_USER_PIN_SAVED_AT` (in `const.py`, next to the floor keys) = `time.isoformat()` when `USER_ORIGINATED_CAR_NAME` holds a real car name, else `None`. Read/validate it in `use_saved_extra_device_info` (tz-aware, parseable; malformed → None), hand it to the boot slot in `device_post_home_init` like the floor.
  - Apply the same positive-evidence guard as the floor, factored into one helper (e.g. `_car_unplugged_since(car, since, time) -> bool`, reusing the `saved_at > time` refusal semantics): at the first boot decision that would honour the persisted pin (in `device_post_home_init` once cars are known, or in `_compute_best_car` / `attach_car` during the boot window — pick the earliest point where the pinned car's `car_plugged` history is readable), if the pinned car has a valid `off` since the pin's saved time → clear the charger's `USER_ORIGINATED_CAR_NAME` and the car's `USER_ORIGINATED_CHARGER_NAME` if it names this charger, drop `_boot_car` if it is that car, log INFO. No `off` (including holes / no sensor / no saved time) → pin honoured as today.
  - Tests: A pinned on W1, save, restart, B plugged, A reports `off` after the save → pin cleared, B attaches to W1; A reports `on`/hole → pin kept; missing/invalid pin saved_at → pin kept.
  - Story: update the scenario table / AC7d-or-AC6 text and Risks accordingly; `docs/agents/concepts/user-override.md`.

### [should-fix] R2-3 — disabling a pinned charger keeps its pin
- File: `custom_components/quiet_solar/ha_model/charger.py` (disable edge), `home_model/load.py:~473-490` (`qs_enable_device` setter), `ha_model/home.py:~2093-2103`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: disable → `reset()` + `home.remove_device()` detaches the car and removes the charger from `home._chargers` but keeps `USER_ORIGINATED_CAR_NAME`; the S1c loop can't reach it. On re-enable the stale pin pulls the car back from its new charger.
- Proposed fix: clear `USER_ORIGINATED_CAR_NAME` on the charger's disable edge (a `QSChargerGeneric` override/hook invoked when `qs_enable_device` goes False). Test: pin, disable, re-enable → no pin; the car stays on W2.

### [should-fix] R2-4 — `pinned_elsewhere` protects stale pins
- File: `custom_components/quiet_solar/ha_model/charger.py:~3653-3664` (`_compute_best_car`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter
- Description: the S1b filter skips a car pinned on any enabled inactive charger, even when that charger does not hold the car (pin persisted before the boot attach, car-card pick never attached, charger offline with status `None` for hours) → the car can be blocked everywhere indefinitely.
- Proposed fix: add `charger.car is not None and charger.car.name == pinned` to the comprehension (keeps exactly the S1b case: W1 holds X while inactive). Log at INFO (not DEBUG) when a car is skipped for this reason, once per (charger, car) episode. No time bound. Test: W1 pinned to X with `W1.car is None`, W1 inactive → W2 wins X; existing S1b rows still pass.
