# QS-381 — Other non-converging chargers still block the whole budgeting group forever

- Issue: https://github.com/tmenguy/quiet-solar/issues/381
- Lane: feature × product (`area:charger`, `area:solver`, `kind:feature`, `scale:task`, `target:product`)
- Branch: `QS_381`
- Follow-up 3 of QS-376 (#376, PR #378) — see `docs/stories/QS-376.story.md`
  ("Decisions" → Follow-ups, "Iceberg check") and review fix #01 EC9.

## Problem

`QSChargerGroup.ensure_correct_state` (charger.py:857) returns `[], None`
(no actionable charger, so `dyn_handle` budgets nobody) as soon as one member
returns `res is False` from `ensure_correct_state`. QS-376 contained the
start-stuck case with isolation plus amp reservation, and a re-arm through the
group. The member's `_ensure_correct_state` (charger.py:5251) still has other
checks that can keep `one_bad = True` with no time bound.

"Blocked" means the others are not re-budgeted. They keep their last amps, but
none of them can start, stop or change amps, and no new charger can start.

## Analysis (per case)

Code facts used below (all in `ha_model/charger.py`):

- `QSStateCmd` (L262) retries a command up to `STATE_CMD_RETRY_NUMBER + 1` = 4
  launches. `can_launch()` is `False` after the 4th.
- `is_ok_to_launch` launches when `_num_launched == 0`, or when
  `last_time_set is None`, or when `time - last_time_set > command_retries_s`
  (strict). After the 4th launch it returns `False` for as long as the value
  does not change.
- `_num_launched` only grows through `register_launch`, and only three places
  call it:
  - `start_charge` / `stop_charge` (L4689/4700), charge state,
    `command_retries_s = 90`;
  - `set_charging_num_phases` (L5011/5026), phases,
    `command_retries_s = STATE_CMD_TIME_BETWEEN_RETRY_S = 42`;
  - `set_max_charging_current` (L4971), only when not
    `for_default_when_unplugged`. Its one caller (L3817) passes `True`, so the
    **amps counter never grows in production**.
- **This is by design (maintainer, 2026-09-30):** amps changes have no retry
  limit. Changing a set-point does not wear the charger, unlike an on/off cycle
  (charge-state commands are capped) or a phase switch. The code does not say
  this anywhere today, so this story adds a comment and a doc line (Design, D0).
- Timings below are on the 7 s test grid (as in QS-376), not the production
  cadence.

### A1 — phase switch retries exhausted (L5269-5289): unbounded, fixed here

- `current_num_phases` (L2500) reads the 3→1 phase switch: `on` is 1 phase,
  anything else (including `unknown` / `unavailable`) is 3.
- A mismatch with `_expected_num_active_phases.value` sets `one_bad`. After 4
  `set_charging_num_phases` launches, on the grid at 0 / 49 / 98 / 147 s,
  nothing is sent again and the group is blocked **forever**.
- Causes: the switch refuses or ignores the command, or it is unavailable (it
  then reads as 3 phases).
- Budgeting uses the **expected** phase count as the member's current count
  (`cs.current_active_phase_number = _expected_num_active_phases.value`, L2675).
- Why adopting the observed count is safe:
  - The idle probe already adopts it (`_expected_num_active_phases.set(self.current_num_phases, time)`,
    L5859).
  - Blocking lowers no current; it only freezes the others.
  - An unavailable switch reads 3 phases. If the charger is really on 1 phase,
    the 3-phase budget over-counts, which is safe.
  - A switch that reads `on` while the charger is really on 3 phases would break
    every other QS phase decision too. It is not a case this fix can or should
    handle.
- **Bound:** adopt the observed phase count once the retries are exhausted and
  the last launch has had its 42 s retry delay.

### A2 — amps mismatch while charging (L5381-5419): blocks by design, no code

- `currently_charging and want_charge` with `get_charging_current() !=
  _expected_amperage.value` keeps the group blocked for as long as the mismatch
  lasts.
- Amps changes have no retry limit, by design (see Code facts above). So QS is
  **not** silent: it re-sends the set-point on every `_ensure_correct_state`
  call, from the group cycle and from `apply_budgets` (L2324). It does not stop
  after 4 tries, as the issue assumed.
  - `set_charging_current` only calls the service when the reported value
    differs (L4991).
  - The block ends on the first cycle where the charger follows.
- Reported **above** expected, or unknown (`None`): the charger may draw more
  than its budget, so the group **must keep blocking**. That matches the issue's
  circuit-safety constraint. No change.
- Reported **below** expected: this is safe (it draws less than budgeted).
  Adopting the reported value would unblock the group, but the next budget asks
  for the higher value again (`get_stable_dynamic_charge_status` offers the full
  `min_charge..max_charge` range, L2769). The member then blocks again on every
  round. A useful fix needs a learned per-charger amp cap with a hold-off. That
  is a new design, not a bound → **follow-up** #387 (D-c).
- **Conclusion:** A2 is already contained. It keeps blocking, it keeps retrying,
  and it recovers as soon as the charger follows. No code.

### A2' — the stop direction (L5304-5341): found in this analysis, follow-up

This is `currently_charging and not want_charge`. It is not in the issue, and
it has two sub-cases:

- (i) The amps before the stop never reach the target. The fallback "stop
  despite amps not confirmed after retries"
  (`amps_retries_exhausted = not _expected_amperage.can_launch()`, L5308) never
  runs in production, because amps retries are unlimited by design. So the stop
  waits for the amps for as long as the set-point differs, and the member blocks
  the group while charging. The follow-up has to decide whether that wait needs
  a time bound (time since the amps target was set), rather than a count bound.
- (ii) Amps confirmed, 4 stop launches, the charger keeps charging. The stop
  counter *is* counted, so it is never re-sent, and the group is blocked
  **forever**.

Both must keep blocking (the charger draws current nobody budgeted). Fixing them
means changing the amps retry accounting, which is a broader change → **follow-up
issue** #386 (D-a).

### A3 — a requested reboot that never happens (L5260-5266, L3730): not reachable today, fixed for correctness

- `reboot()` (L5032) only arms the wait (`_asked_for_reboot_at_time`) when
  `can_reboot()` holds, which needs `charger_reboot_button`. That attribute
  comes only from the `CONF_CHARGER_REBOOT_BUTTON` kwarg (L2347). No config flow
  sets it, and the OCPP discovery line is commented out (L6278). So **no charger
  can arm a reboot wait today**, and the OCPP notification triggers (L6403,
  L6434) are gated on `can_reboot()` as well.
- Latent bug: `check_if_reboot_happened` is `async` (L5044) but
  `_ensure_correct_state` calls it **without `await`** (L5261). The coroutine is
  truthy, so the "reboot happened" branch would always run on the first call, and
  Python would log "coroutine … was never awaited".
- With the `await` fixed, the check returns:
  - `False` for the first `minimum_reboot_duration_s` (120 s);
  - for chargers with rebooting status values (OCPP, Wallbox), `False` until a
    rebooting status has been seen for ≥ 2 × refresh interval (28 s).
- A reboot that never happens would then block **forever**, in two places:
  - the group, via `res is False`;
  - the load itself: `check_load_activity_and_constraints` returns `False` early
    while `_asked_for_reboot_at_time` is set (L3730). That also happens with no
    car plugged, where `_ensure_correct_state` is never reached.
- **Bound:** fix the `await`, and stop waiting after
  `CHARGER_REBOOT_WAIT_TIMEOUT_S` (10 min), in both places. The production blast
  radius today is nil. This makes the path correct before anyone wires a reboot
  button (D-b).

### A4 — a start-stuck charger that also fails an earlier check (QS-376 EC9): bounded by A1 + A3

- `is_start_stuck` (L5087) only looks at the charge-state command. So the group
  isolates the member, with its amps reserved, even when `_ensure_correct_state`
  stops at the reboot or phase check. The F2 re-arm is in the start branch,
  after those checks, so it is never reached, and the member stays isolated and
  reserved **forever**.
- The phase and reboot checks run before the start branch. So a member only gets
  there if the mismatch or the reboot shows up **after** its 4 start launches:
  for example, the phase switch going `unavailable` while the member is
  isolated.
- The group still calls `charger.ensure_correct_state` for an isolated member on
  every cycle (L876, before the isolation test at L898). Once A1 and A3 are
  bounded, the earlier check clears in bounded time, and F2 re-arms on the first
  start-branch cycle after its own threshold (4th start launch + 15 min).
- **Bound:** re-arm at the first cycle after both the F2 threshold and the
  earlier check's bound. No new code; tests pin it.

## Goal

Two bounds, and one case that stays blocked:

- A phase switch that never follows blocks the group for about 3:16 per round
  (A1).
- A reboot that never happens blocks it for at most 10 min (A3).
- A start-stuck member behind either one no longer stays isolated forever (A4).
- An amps mismatch while charging stays blocked, as circuit safety requires, and
  keeps retrying (A2, documented).

## Design

All in `custom_components/quiet_solar/ha_model/charger.py`. `QSStateCmd` is
defined there too, and it is not changed.

- **D0 — record the unlimited amps retries (A2).** Comment only, no behaviour
  change.
  - Where: in `set_charging_current` (L4978), plus a one-line pointer at the
    `amps_retries_exhausted` line (L5308).
  - Text: amps changes are deliberately not counted with `register_launch`, so
    `_expected_amperage` never runs out of retries and the set-point is re-sent
    on every ensure cycle. A set-point change does not wear the charger, unlike
    an on/off cycle or a phase switch. As a result, the `amps_retries_exhausted`
    fallback in the stop path only fires if a caller counts launches (today only
    `set_max_charging_current` outside the unplugged default, which no production
    path does).
- **New constant** `CHARGER_REBOOT_WAIT_TIMEOUT_S = 10 * 60`, next to
  `CHARGER_START_RETRY_REARM_S`, with a QS-381 comment: the longest wait for a
  requested reboot.
- **D1 — phase adoption (A1).** Superseded in part by review fixes #01–#04, see
  Implementation notes. Put this in the phase-mismatch block, in the
  `else` (NOT OK TO LAUNCH) of
  `self._expected_num_active_phases.is_ok_to_launch(...)`, inside the existing
  `if probe_only is False:` (a probe never changes a target).
  - Condition: `not self._expected_num_active_phases.can_launch()` and
    `self._expected_num_active_phases.last_time_set is not None` and
    `(time - self._expected_num_active_phases.last_time_set).total_seconds() > self._expected_num_active_phases.command_retries_s`.
    The strict `>` matches `is_ok_to_launch`.
  - Action:
    - log WARNING `"Ensure State:%s phase switch never converged after %d
      launches: adopting the observed %s phases (expected %s)"`;
    - then `self._expected_num_active_phases.set(current_active_phases, time)`
      (the existing local, L5270);
    - then `await self._expected_num_active_phases.success(time=time)`.
  - `set` goes first: a different value resets the command, which drops any
    registered reboot-on-success callback, so no reboot fires for a switch that
    did not happen.
  - `one_bad` stays `True` for this call. The next call finds the phases
    matching.
  - The existing `else` DEBUG log stays for the not-yet-due case.
  - Cadence: adoption at the first cycle > 147 + 42 s, i.e. 196 s (3:16) after
    the first phase launch on the 7 s grid. The `set` also restarts the 30 min
    `TIME_OK_BETWEEN_CHANGING_CHARGER_PHASES` spacing that gates the
    **non-consign** phase offer (L2764), so there, a broken switch costs at most
    one 3:16 block per 30 min.
  - Known limit: consign commands (`CMD_AUTO_FROM_CONSIGN`, `CMD_AUTO_GREEN_CAP`
    with a consign) pick phases in `get_consign_amps_values` (L561) without that
    gate. When the consign cannot be met on the adopted phases, the next budget
    asks for the switch again. That is 3:16 blocked out of every ~4 min: bounded,
    but not good. Gating it changes consign semantics → **follow-up** #388 (D-d).
- **D4 — reboot wait (A3).**
  - Pure predicate `QSChargerGeneric._is_reboot_wait_expired(time) -> bool`:
    `self._asked_for_reboot_at_time is not None and (time - self._asked_for_reboot_at_time).total_seconds() >= CHARGER_REBOOT_WAIT_TIMEOUT_S`.
  - One action `QSChargerGeneric._give_up_reboot_wait(time) -> None`: log
    WARNING `"%s: reboot asked at %s never happened, giving up the wait"`, then
    `self._asked_for_reboot_at_time = None`.
  - `_ensure_correct_state`: `is_reboot_done = await self.check_if_reboot_happened(...)`.
    In the not-done branch: if `self._is_reboot_wait_expired(time)`, call
    `self._give_up_reboot_wait(time)` and go on as if the reboot had happened
    (the done branch only clears the field too, so nothing else is skipped).
    Otherwise keep today's INFO log and `one_bad = True`. Like today's done
    branch, this also runs in probe mode, since clearing a stale wait is not a
    command.
  - `check_load_activity_and_constraints` (L3730):
    `if self._asked_for_reboot_at_time is not None:` → if
    `self._is_reboot_wait_expired(time)`, call `self._give_up_reboot_wait(time)`
    and continue; otherwise `return False`.
  - Whichever caller runs first clears the field, and the other one then sees
    `None`. Both outcomes are the same.
  - A new `reboot()` during a wait restarts it (it sets the time again). Each
    request is bounded, and no production caller can reach this today.

## Blast radius

- **D1:** only chargers with a 3→1 phase switch that never follows. The budget
  then runs on the observed phase count. For non-consign commands, at most one
  phase-change round per 30 min.
- **D4:** nil in production today (no charger can arm a reboot wait). Once a
  reboot button is wired, the wait becomes real, bounded at 10 min.
- **Temporarily-unavailable switch (review fixes #04–#05):** the phase-offer gates
  only ever *withhold* a phase change from a charger whose switch is broken or dead
  — the non-consign offer (`get_stable_dynamic_charge_status`, fix #04-4), the
  consign offer (`get_consign_amps_values`, fix #05), and the `apply_budgets`
  live-expected compare. They never widen the offer for a healthy charger. The
  TIME-based stale-replay drop (fix #05) narrows to genuinely stale snapshots only,
  so a fresh post-adoption split budget — and any unrelated charger sharing that
  replay — is no longer starved.
- No change to the solver, constraints, amps / stop paths, the QS-346 fault path
  or the QS-376 isolation / reservation.

## Follow-ups (opened 2026-09-30)

- #386: a charger that refuses to stop blocks its whole budgeting group (A2' i + ii).
  Includes the maintainer's point: a stopped charger should block nothing. Amps
  are already skipped when stopped, but the phase and reboot checks still run.
  Also includes the maintainer's point that a charger refusing to stop should be
  frozen with its amps reserved (QS-376 style), and the catch that the
  reservation release is not safe for a charger that is really drawing current.
- #387: a charger that refuses an amps raise blocks its whole budgeting group
  (A2 below-expected). Includes the maintainer's brainstorm: accept the old
  value after several refusals, retry later, `is_amps_expected_fine()`.
- #388: a consign re-asks a failed phase switch right after the adoption (D1
  known limit).
