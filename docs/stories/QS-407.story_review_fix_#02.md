### [should-fix] R1: a launched review is still failed early when the session listing is unknown
- Files:
  - `scripts/qs/control_plane/reviews.py`: `_identify` (~:640-658), `_guarded` (~:542-556) and `_launch` (~:629)
  - `scripts/qs/control_plane/reviewpilot.py`: `_launch_move` (~:120-150) and `close_dead` (~:180-205)
- Severity: should-fix
- Source: BH + EC (the same finding)
- Description: S2 of fix plan #01 says "an unknown listing never fails a launched review early: only the TTL". Today that holds only for the dead-holder branch of `close_dead`. Three paths still void a live session's token (STALE_TOKEN on its findings and its finish) and make `retry_failed` launch a duplicate:
  1. `try_agents()` returns `None` on every `_identify` poll until `LAUNCH_SETTLE_S`. `_identify` then raises "was never listed", and `_guarded` moves the `launching` row to `failed` at once.
  2. The `call_state == 'failed'` branch of `_launch_move` fails a launched row (`launch_at` set) even when `listing is None`.
  3. `claude --bg` times out (the runner's exit 124). `_launch` raises `StepFailed`, but the background session may already have forked.
- Proposed fix (one rule: **a launched review fails early only when a known listing does not show it; under an unknown listing only `REQUEST_TTL_S` fails it**):
  1. `_identify`: remember whether any poll returned a listing that is not `None`. If none did by the deadline, raise a distinct failure. That can be a `StepFailed` subclass such as `Unidentified`, or a flag on `StepFailed`. `_guarded` catches it, re-raises it and does **not** close the review. The tool call still fails, and the row stays `launching` with `launch_at` set.
  2. `reviewpilot._launch_move` / `close_dead`, for a `_launched(row)`:
     - With `listing is None`, skip both the `call_state == 'failed'` branch and the dead-holder branch. Only the `REQUEST_TTL_S` move applies.
     - With a known listing, adoption by name keeps priority (as today). Otherwise the failed-call or dead-holder move applies, as today.
  3. `_launch`: on `res.returncode == 124` (timeout), do not raise. Return `{"launched": True, "timeout": True}` (or similar) and let `identify` decide by name. Every other non-zero exit still raises `StepFailed`.
  4. Update `docs/workflow/control-plane.md` ("Review sessions", where `identify` and the pilot's closing of dead reviews are described) and the story's D7 / D12 so the rule above is stated once.
- Tests:
  - A listing that is `None` on every identify poll → the call fails, but the review stays `launching`, with no `review_failed`.
  - A later `close_dead` tick with the session listed → adopted (`running`).
  - With the listing still unknown → failed only at `REQUEST_TTL_S`.
  - A launched row with `call_state = 'failed'` under `listing None` → not moved before the TTL.
  - The same row under a known listing that does not show it → `failed`, as today.
  - `claude --bg` exit 124 → `identify` runs, and a listed session → `running`.

### [should-fix] R2: the S8 payload fix is incomplete, so `payload["tasks"]` is iterated without a type check
- File: `scripts/qs/control_plane/reviewpilot.py:~282` (`_alert_events`)
- Severity: should-fix
- Source: EC (confirmed by running it)
- Description: with `{"tasks": null}` or `{"tasks": 5}` the loop raises `TypeError` inside `discover`'s `db.write`, on every tick. `retry_failed` and `drain` then never run. With `{"tasks": "T12"}` the loop adds the tasks `"T"`, `"1"` and `"2"`.
- Proposed fix: do what `_overlap_partners` does:
  ```python
  tasks = payload.get("tasks")
  if isinstance(tasks, list):
      group["tasks"].update(t for t in tasks if isinstance(t, str))
  ```
- Tests: payloads `{"tasks": null}`, `{"tasks": 5}` and `{"tasks": "T12"}` → no raise, no per-character tasks, and the other events still drain.
