### [must-fix] R1 — Step-snap in `_discharge_number_target` can silently zero the safety floor (and escape the entity range)
- File: `custom_components/quiet_solar/ha_model/battery.py:168-178`
- Severity: must-fix
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter + qs-review-acceptance-auditor
- Description: The round-1 S2 fix snaps to the **nearest** step after
  the min/max clamp. Two reproductions: (a) a kW-denominated entity with
  `step: 1`: floor 300 W → 0.3 kW → `round(0.3/1)*1 = 0` → writes
  **0 kW**, and because the probe expectation shares the same helper it
  *confirms* the zeroed floor — the system believes the outage floor is
  set while the hardware holds a hard 0, silently, with no log. This is
  exactly the hazard QS-349 exists to prevent. (b) The snap is applied
  after the min/max clamp, so it can escape the entity range: entity
  `min: 100, step: 250`, floor 100 W → clamp 100 → `round(0.4)*250 = 0`
  → `number.set_value(0)` raises out-of-range (caught + logged), the
  value never lands, probe never confirms → eternal retry, the exact
  class S2 was fixing. Banker's rounding also means the floor can snap
  *down* in general (`floor=100, step=200 → 0`).
- Author note (triage): in practice the max-discharge entity is
  W-denominated, not kW — the W path is the primary one. Nearest
  rounding is a bad idea regardless of unit; do the simple safe thing.
- Proposed fix: For the discharge-limit target, snap **up**:
  `math.ceil(write_value / step) * step` (a safety *minimum* must never
  be lowered by snapping), then re-clamp to `ent_max` (ceil cannot
  undershoot `ent_min` since the pre-snap value is already >= `ent_min`).
  The probe expectation follows automatically via the shared
  `_discharge_number_target` helper. Tests: (1) kW entity with `step: 1`
  → floor 300 W lands at 1 kW (>= floor, never 0) and probe confirms;
  (2) W entity `min: 100, step: 250`, floor 100 → snapped value stays in
  range, no out-of-range write, probe confirms; (3) plain W entity with
  integer step (the practical case) → floor unchanged.

### [should-fix] R2 — Load-shed loop has no per-load isolation
- File: `custom_components/quiet_solar/ha_model/home.py:1073-1091`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: The round-1 S1 guard isolates only the battery restore. A
  raising `load.launch_command` (awaited probe + service call, can raise
  `HomeAssistantError`) at load *k* escapes `async_set_off_grid_mode`, is
  swallowed by the listener's log-only catch (home.py:1248-1251), and
  aborts shedding of loads *k+1..n*, skips `_switch_to_off_grid_launched`
  (line 1085) and `force_next_solve()` (line 1091). Since
  `qs_home_is_off_grid` is committed at line 1048, later
  `_compute_and_apply_off_grid_state` calls see `do_reset == False` and
  never retry: the remaining loads stay running off-grid with the gate
  never armed.
- Proposed fix: Wrap each iteration's
  `reset_override_state_and_set_reset_ask_time` + `launch_command` in the
  same log-only `try/except Exception ... exc_info=True` pattern as the
  battery guard. Test: first load raises → second load still shed, gate
  set, `force_next_solve` called.
