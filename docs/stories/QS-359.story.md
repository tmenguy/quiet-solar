# QS-359 — OCPP integration v0.11.4 → v0.12.0: compatibility analysis and hardening

- Issue: https://github.com/tmenguy/quiet-solar/issues/359
- Lane: feature × product (`area:charger`, `scale:task`)
- Branch: `QS_359`
- Upstream: https://github.com/lbbrhzn/ocpp (`v0.11.4` → `v0.12.0`, released 2026-09-20)

## Problem

The `lbbrhzn/ocpp` Home Assistant integration shipped v0.12.0 with a
declared breaking change. Quiet Solar's `QSChargerOCPP` drives chargers
exclusively through that integration's entities and actions, so the
change set had to be mapped onto every QS touch point to decide whether
QS breaks, and how QS should behave on chargers that *do* lose a
capability with this release.

Production reference: Thomas's Wallbox Pulsar Plus (OCPP 1.6J, single
connector) on v0.11.4, working. v0.12.0 has **not** been run in
production yet; the conclusions below come from the upstream diff plus
a v0.11.4 debug log (see Verdict), and the Upgrade checklist is the
runtime confirmation.

## Analysis (v0.11.4 → v0.12.0, 12 commits, 8 functional)

### QS touch points in the OCPP integration

| QS usage ([charger.py `QSChargerOCPP`](../../custom_components/quiet_solar/ha_model/charger.py)) | v0.12.0 status |
| --- | --- |
| `switch.<cpid>_charge_control` — start/stop via `switch.turn_on/off`, non-blocking | entity id unchanged; **availability semantics changed** (transaction-bound, see below) |
| `number.<cpid>_maximum_current` — the only amp-control path (`use_ocpp_custom_charging_profile=False`), via `number.set_value`, non-blocking; the number's state is read back as the amp ack (`get_max_charging_amp_per_phase`) | entity id and registry identity unchanged; **send behavior changed** (see below) |
| `sensor.<cpid>_status_connector` — plug/charge state through `QSOCPPv16v201ChargePointStatus` | unchanged (no enum or sensor change) |
| `sensor.<cpid>_power_active_import` — secondary power probe | unchanged |
| `ocpp.trigger_custom_message` (`MeterValues`, `devid`) — data refresh | unchanged (`services.yaml` identical between tags) |
| `call_service` bus listener on persistent notifications → `handle_ocpp_notification` | returns immediately (dead code) — irrelevant |

Entity discovery is substring-based (`_find_charger_entity_id`,
`suffix in entity_id`). The new `number.<cpid>_session_current_limit`
does not collide with `_maximum_current`.

### Version-independent finding (upstream #2148)

`_resolve_charge_rate` re-reads `ChargeProfileMaxStackLevel` on every
limit write and falls back to `stack_level = 1` on any exception —
unchanged in v0.12.0. One transient `GetConfiguration` failure installs
the next `ChargePointMaxProfile` at level 1 where the previously
installed level-10 profile out-ranks it; the charger silently stays
clipped at the old ceiling (asymmetric: lower values apply, higher ones
don't) until `ocpp.clear_profile`. Reporter: Pulsar Plus fw 6.7.41,
driven by a PV-surplus EMS with a few hundred writes/day — QS's exact
profile. QS is blind to it today because its amp ack reads the number
entity (optimistic), not what the EVSE offers.

### Verdict

- No code change is *required* for the Pulsar Plus on v0.12.0.
- Two hardening items are worth shipping because QS now has evidence
  they matter, both gated so the Pulsar path is unchanged unless a
  guard trips.

## Goal

1. On a charger whose `maximum_current` number accepts the command (the
   Pulsar Plus), keep QS's observable behavior on both OCPP integration
   versions: same `number.set_value` payload, same ack source (the
   number), no `ocpp.set_charge_rate` call, no fallback-mode warning.
   Known, accepted deltas: (a) the number call runs one task hop later
   (Block 1); (b) non-marker number errors (e.g. a timeout) now log the
   generic QS warning instead of landing in HA's task logger; (c) one
   extra probable entity (`current_offered`) when the sensor exists;
   (d) at most one clip notification per plug session per HA run when a
   real clip occurs.
2. Restore amp control on OCPP chargers that reject
   `ChargePointMaxProfile` — the population that v0.12.0's #2131
   breaks — by falling back to the `ocpp.set_charge_rate` action,
   which still runs the pre-v0.12.0 chain.
3. Make a stack-level clip (#2148) visible: detect "EVSE offers less
   than commanded while the number claims the command is applied" and
   notify the household once per plug session with the manual
   workaround and its consequence. **Never** write `ocpp.clear_profile`
   from QS.
4. Fix the `QSChargerOCPP` bullet in
   `docs/agents/concepts/charger-budgeting.md` (the one doc the drift
   checker pins to `charger.py`) and record the fallback/detector
   behavior there in two sentences.

## Design

All product changes live in `QSChargerOCPP` plus two small hooks in
`QSChargerGeneric`. Principle: **fail-open to today's behavior** —
nothing new runs unless a detector fires; every detector has a
tolerance, a window and a cap.

### Constants (module-level in `ha_model/charger.py`)

`project-context.md` says constants live in `const.py`; the established
precedent for **charger runtime tunables** is `charger.py` (e.g.
`CHARGER_CHECK_STATE_WINDOW_S`, `STATE_CMD_RETRY_NUMBER`,
`CHARGER_FAULT_NOTIFY_DEBOUNCE_S` ~line 216), and this story follows the
precedent. Add after `CHARGER_FAULT_NOTIFY_DEBOUNCE_S`, in a `# QS-359`
comment block shaped like the QS-346 one:

- `OCPP_CLIP_DETECT_WINDOW_S = 180` — how long a clip must hold
  continuously before the household is alerted (absorbs the 60 s
  `MeterValueSampleInterval` lag after an increase).
- `OCPP_CLIP_TOLERANCE_A = 1.0`
- `OCPP_STATION_PROFILE_REJECTION_MARKER = "ChargePointMaxProfile"` —
  substring of the `HomeAssistantError` text raised by
  lbbrhzn/ocpp v0.12.0 `ocppv16.py::set_station_charge_rate`
  (`Failed to set variable: ChargePointMaxProfile: Rejected|NotSupported`);
  the comment carries the upstream version and function name. v0.11.4
  never raises for this because it falls back itself.
- `OCPP_STATION_PROFILE_REJECTIONS_TO_FALLBACK = 2` — marker rejections
  in distinct episodes (no accepted number write in between) before the
  fallback mode latches; one rejection can be transient (a profile
  write racing a transaction start). Fix #04: a rejection counts as a
  new episode only when it lands at least
  `OCPP_STATION_PROFILE_REJECTION_DEBOUNCE_S` (10 s) after the last
  counted one (`_ocpp_last_rejection_counted_time`); concurrent
  same-episode rejections collapse to one, and an accepted write resets
  both the streak and the debounce timestamp.
- `OCPP_FALLBACK_CONN_ID = 1` — single-connector chargers only
  (multi-connector is out of scope).

The service domain / service name / attribute keys (`"ocpp"`,
`"set_charge_rate"`, `"devid"`, `"limit_amps"`, `"conn_id"`) and the
discovery suffix `"_current_offered"` are written **inline**, exactly
like the neighbouring `low_level_update_data_request` call
(`"ocpp"`, `"trigger_custom_message"`, `"devid"`) — one convention per
class, not two.

### New `QSChargerOCPP` attributes

Declared with types **before** the `if self.charger_device_ocpp is not None and hass is not None:`
guard in `__init__` (next to `charger_ocpp_current_import` /
`charger_ocpp_power_active_import`, ~lines 6129-6130), because four test
files construct `QSChargerOCPP` directly without a device:

- `self.devid: str | None = None` and
  `self.charger_ocpp_transaction_id: str | None = None` (today both are
  only assigned inside the guard; `get_probable_entities` already reads
  the latter unguarded)
- `self.charger_ocpp_current_offered: str | None = None`
- `self._ocpp_station_profile_rejected: bool = False`
- `self._ocpp_station_profile_rejection_streak: int = 0`
- `self._ocpp_last_fallback_amps: int | None = None`
- `self._ocpp_fallback_failure_logged: bool = False`
- `self._ocpp_clip_since: datetime | None = None`
- `self._ocpp_clip_notified: bool = False`

### Block 0 — optional entity discovery

`_find_charger_entity_id(device, entries, prefix, suffix)` fabricates
`prefix + slugify(device_name) + suffix` when nothing matches. Correct
for required entities, wrong for optional ones. Add
`optional: bool = False`; when `optional=True` and nothing matches on
the **computed-fallback exit** (device present), log at debug and
`return None`. The `device is None` exit is unreachable from the only
`optional=True` call site (inside the device guard) and is left
unchanged. The "multiple found → longest" rule and `optional=False`
behavior are unchanged.

Inside the guard, in the **non-custom-profile branch only**
(`else:` of `if self.use_ocpp_custom_charging_profile`, ~lines
6161-6165 — the custom branch already binds `_current_offered` as
`CONF_CHARGER_CHARGING_CURRENT_SENSOR`):

- `self.charger_ocpp_current_offered = self._find_charger_entity_id(device, entries, "sensor.", "_current_offered", optional=True)`

`get_probable_entities()` appends it when not `None`, so the probe cache
tracks it like the status sensor. Absent → the clip detector stays
dormant.

### Block 1 — capture the outcome of the amp command

Today `QSChargerGeneric.low_level_set_max_charging_current` (~6039)
swallows every exception (`_LOGGER.warning(...)`, `done = False`) and
QS calls it with `blocking=False`, so a `HomeAssistantError` raised by
the number entity lands in HA's background-task logger and QS reports
`done=True`. The number payload today is
`{ATTR_ENTITY_ID: self.charger_max_charging_current_number, number.ATTR_VALUE: int(min(charger_max_charge, max(charger_min_charge, float(current))))}`
on `number.DOMAIN` / `number.SERVICE_SET_VALUE`.

- `QSChargerGeneric` gains
  `async def _on_amp_command_error(self, error: Exception, current: float, time: datetime) -> bool`
  returning `False` (not handled). It receives the **raw** `current`
  (the clamped value is computed inside the `try` and may not exist).
  Contract in the docstring: **must not raise** — it runs inside an
  `except` branch. The existing `except Exception as e:` branch (a
  pre-existing broad catch at a service-call boundary, not new code)
  becomes:

  ```python
  handled = await self._on_amp_command_error(e, current, time)
  if not handled:
      _LOGGER.warning("low_level_set_max_charging_current: Error %s", e, exc_info=True, stack_info=True)
  done = False
  ```

- `QSChargerOCPP.low_level_set_max_charging_current(current, time, blocking=False)` — branch order:
  1. `if self.use_ocpp_custom_charging_profile: return await self.low_level_set_charging_current(current, time, blocking)` — unchanged behavior.
  2. `if self._ocpp_station_profile_rejected: return await self._ocpp_set_charge_rate_fallback(current, time, blocking)`.
     (Revised in review fix #01: `blocking` is forwarded so a blocking
     caller on the fallback path gets the real outcome. Originally
     specified as `_ocpp_set_charge_rate_fallback(current, time)`.)
  3. `if blocking: return await self._ocpp_run_number_command(current, time)` — an explicit blocking caller keeps a real outcome.
  4. `self.hass.async_create_task(self._ocpp_run_number_command(current, time))`; `return True`.
- `_ocpp_run_number_command(current, time) -> bool`:
  `ok = await super().low_level_set_max_charging_current(current, time, blocking=True)`;
  `if ok: self._ocpp_station_profile_rejection_streak = 0`; `return ok`.
  `blocking=True` inside a task surfaces the number's
  `HomeAssistantError` to `_on_amp_command_error` without stalling the
  load-management cycle (charger round trip 1–5 s). This is the one
  mechanical change on the accepted path: the service call happens one
  task hop later; the return value was already `True`. An
  `unavailable` number entity is filtered by HA (`entity_service_call`)
  and raises nothing — unchanged. On the OCPP path the hook is only
  ever reached inside this task (or a blocking caller's await).

### Item 2 — fallback mode for chargers that reject `ChargePointMaxProfile`

- `QSChargerOCPP._on_amp_command_error(error, current, time) -> bool`:
  - `if not isinstance(error, HomeAssistantError): return False`
    (Added in review fix #03, SF-1: the marker only ever appears in the
    v0.12.0 `set_station_charge_rate` `HomeAssistantError`, but the
    caller forwards *every* exception from its `try` — including a
    `ValueError` from `float(current)` when `current` is a string that
    happens to contain "ChargePointMaxProfile". Rejecting any non-HAE
    error before the marker check keeps such invalid input on the
    generic-warning path and out of the streak.)
  - `if self.use_ocpp_custom_charging_profile: return False`
  - `if OCPP_STATION_PROFILE_REJECTION_MARKER not in str(error): return False`
    (transient timeouts and other errors never count).
  - `self._ocpp_station_profile_rejection_streak += 1`.
  - `if not self._ocpp_station_profile_rejected and streak >= OCPP_STATION_PROFILE_REJECTIONS_TO_FALLBACK:`
    set `_ocpp_station_profile_rejected = True` and log **one** warning
    naming the charger ("station profile rejected N times by <name>;
    switching amp control to `ocpp.set_charge_rate` until the
    integration is reloaded or HA restarts"). A first rejection logs at
    debug; rejections after the latch (tasks created before the flip)
    log nothing.
  - **No replay.** The next load-management cycle re-issues the
    setpoint through branch 2 — the ensure-state loop already retries
    on observation, so a replay here would only duplicate it and
    reintroduce an in-flight ordering question.
  - `return True` (QS owns the diagnosis; the generic warning is
    suppressed for marker errors). Nothing in this method can raise.
- The mode is **sticky until the integration is reloaded or HA
  restarts** (no re-probe, no persistence). Rejecting
  `ChargePointMaxProfile` is a charger property; a firmware fix is
  picked up at the next restart.
- `_ocpp_set_charge_rate_fallback(current, time, blocking=False) -> bool`:
  - `if self.devid is None: return False` (device-less construction;
    log at debug).
  - clamp `clamped = int(min(float(self.charger_max_charge), max(float(self.charger_min_charge), float(current))))`
    — the **same** expression (truncating `int`) the generic path uses.
    A bad `current` (`ValueError`/`TypeError`) is caught and returns
    False rather than propagating out of the load-management cycle.
  - `try: await self.hass.services.async_call("ocpp", "set_charge_rate", {"devid": self.devid, "limit_amps": clamped, "conn_id": OCPP_FALLBACK_CONN_ID}, blocking=blocking)`
    (Revised in review fix #01: `blocking` is forwarded so a blocking
    caller receives the real outcome — the service handler raises on
    refusal — instead of the optimistic ack. Originally specified as
    `blocking=False`.)
    `except HomeAssistantError as e:` (covers `ServiceNotFound`) → log
    at **warning the first time**, then debug while
    `_ocpp_fallback_failure_logged` is set; `return False`. A separate
    `except (ValueError, TypeError)` guards the clamp against a bad
    `current` (logs a warning, returns False). **No** bare
    `except Exception` — this runs in the load-management cycle.
  - On success: `self._ocpp_last_fallback_amps = clamped`,
    `_ocpp_fallback_failure_logged = False`, `return True`. The ack is
    assigned **after** a call that returned without raising, so a
    missing/failed service leaves the previous ack and the ensure-state
    loop keeps retrying (throttled by `is_ok_to_launch`). Residual, stated
    in the code comment: the action's handler swallows the chain's
    boolean ("reports success either way"), so a charger that also
    rejects `TxProfile`/`TxDefaultProfile` is invisible on this path —
    exactly what the v0.11.4 slider did for that population.
  - Code comment (required by the user, American English):
    `ocpp.set_charge_rate` keeps the pre-v0.12.0 chain
    (`ChargePointMaxProfile` on connector 0 → `TxProfile` on the running
    transaction → `TxDefaultProfile` on `conn_id`) on both integration
    versions; `conn_id` only selects the Tx target connector, the
    station profile is always tried first (and is expected to be
    rejected here). The `TxDefaultProfile` it writes persists on the
    charger at the last fallback amps beyond the mode — same as the
    v0.11.4 slider did for these chargers. The cleaner alternative on
    v0.12.0+ is `number.<cpid>_session_current_limit` (a `TxProfile`
    bound to the displayed transaction, session-scoped, no persistent
    `TxDefaultProfile`), not used here because it is v0.12.0-only, needs
    a displayed transaction id, and its value goes `unknown` at every
    transaction end, which fights QS's ack loop.
- Ack source in fallback mode — override
  `QSChargerOCPP.get_max_charging_amp_per_phase() -> float | None`:
  `if self._ocpp_station_profile_rejected: return None if self._ocpp_last_fallback_amps is None else float(self._ocpp_last_fallback_amps)`;
  else `return super().get_max_charging_amp_per_phase()`. Same
  optimistic semantics as today's number; `None` here means "not yet
  acked", exactly like an `unknown` number state today (comment at the
  override). `current_offered` is **not** used as an ack: it lags a
  MeterValues interval, is a non-integer measurement compared by `==`
  in the ensure-state loop, and is exactly the quantity that may
  legitimately sit below the command.
- `can_set_amps_when_not_charging()` stays `False`: amps are still only
  written while charging, on both paths.

### Item 1 — stack-level clip detector (#2148): detect and tell, never write

- `QSChargerGeneric` gains `async def check_amps_delivery(self, time: datetime) -> None` (no-op), awaited in
  `check_load_activity_and_constraints` right after the QS-346 fault
  state machine (the block ending with `self._charger_fault_notified = True`,
  ~line 3704) and before `if self.is_not_plugged(time, for_duration=CHARGER_CHECK_STATE_WINDOW_S):`
  (~line 3706). Reachability: identical to the QS-346 machine it sits
  next to — both run every cycle before any plug-state branch, which is
  what lets the per-session reset below observe the unplug.
- `QSChargerOCPP.check_amps_delivery(time)` — per-cycle state machine
  mirroring QS-346 (plain state, not a rising-edge fire):
  1. return immediately when `self.charger_ocpp_current_offered is None`
     or `self._ocpp_station_profile_rejected` (the detector is
     **number-path only**: in fallback mode the number reverts and the
     ack is optimistic, so the comparison below is meaningless).
  2. if `self.is_not_plugged(time, for_duration=CHARGER_CHECK_STATE_WINDOW_S)` →
     `_ocpp_clip_since = None`, `_ocpp_clip_notified = False` (per
     plug-session reset) and return. Not persisted: an HA restart during
     a clipped session may re-notify once (accepted).
  3. read the inputs:
     - `charging = self.is_charge_enabled(time) is True and self.get_sensor_latest_possible_valid_value(self.charger_status_sensor_unfiltered, time=time) == QSOCPPv16v201ChargePointStatus.charging`
       (`QSOCPPv16v201ChargePointStatus` is a `StrEnum`, so the raw
       `"Charging"` string compares equal). SuspendedEV/SuspendedEVSE
       are excluded on purpose: upstream `_zero_flow_measurands` does
       **not** zero `Current.Offered` (checked in `ocppv16.py`), but a
       paused car may still read `Current.Offered = 0` on some chargers.
     - `expected = self._expected_amperage.value`; valid when not `None`
       and `expected > self.charger_min_charge` (strict: at the minimum
       a clip is indistinguishable from the charger's own floor, and QS
       drives to the minimum before every stop).
     - `offered = self._ocpp_read_current_offered(time)`:
       `self.get_sensor_latest_possible_valid_value(self.charger_ocpp_current_offered, time=time)`
       — the **same probe-cache primitive** as the status gate — converted
       with `float()` under `except (ValueError, TypeError)` → `None`
       (also `None` for a missing/`unknown`/`unavailable` value). No
       freshness check: the `Charging` gate implies the charger is online
       and QS's ensure-state loop triggers `MeterValues` periodically while
       charging.
  4. transitions:
     - `not charging` or `expected` invalid or `offered is None` →
       `_ocpp_clip_since = None`; return.
     - `self.get_max_charging_amp_per_phase() != expected` (the number has
       not acknowledged the current setpoint — a routine amp change is in
       flight) → **skip this tick, hold `_ocpp_clip_since`**; return.
       Resetting here would let solar modulation restart the window on
       every setpoint change and hide a real clip.
     - `offered >= expected - OCPP_CLIP_TOLERANCE_A` → `_ocpp_clip_since = None`; return.
     - else (clipped): `if _ocpp_clip_since is None: _ocpp_clip_since = time`;
       `elif not _ocpp_clip_notified and (time - _ocpp_clip_since).total_seconds() >= OCPP_CLIP_DETECT_WINDOW_S`
       (inclusive) → `await self._notify_ocpp_clip(time, expected, offered)`;
       `_ocpp_clip_notified = True`.
- `_notify_ocpp_clip(time, expected, offered)`:
  - `car = self.car or (self._last_attached_car if self._last_attached_car is not None and self._last_attached_car.charger is None else None)`
    — the same expression `_notify_charger_fault` uses.
  - message (second person, backticks, honest about the consequence and
    the legitimate alternative cause). `offered` is printed with
    `math.floor(offered)` (Revised in review fix #01, NH-1: flooring —
    not `:.0f` rounding — avoids "offers 16 A while 16 A were requested"
    when `offered` is e.g. 15.6, which would contradict the clip

### Rejected alternatives

- **Automatic `ocpp.clear_profile` + immediate re-set** (first draft of
  item 1). Rejected on the reporter's warning and on QS's own
  constraints: clearing drops the charger to installation max
  (32 A × 3 phases ≈ 22 kW on a Socket Pro) until a new profile lands;
  the car ramps in seconds and the reporter saw minutes. Doing it
  while unplugged only moves the spike to the next session start —
  today QS drives amps to `charger_min` *before* stopping so the
  persisted ceiling at the next start is 6 A; after a clear there is no
  ceiling, and QS deliberately refuses to write amps while idle on OCPP
  (`can_set_amps_when_not_charging=False`, Pulsar jumps to 32 A on an
  idle amp command — #1684). No write-based escape exists either: the
  clip is the Pulsar keeping the level-10 profile alongside the level-1
  one, and QS does not control the stack level the integration uses.
  The fix belongs upstream (#2148: cache / last-known-good stack
  level). The manual workaround in the notification carries the same
  consequence and says so.
- **`number.<cpid>_session_current_limit` as the fallback** — see the
  code comment in Item 2 and Follow-ups.
- **Observation-based fallback entry** (round 2, N8: enter fallback
  when the ensure-state loop exhausts `STATE_CMD_RETRY_NUMBER` with the
  number never acking; leaves the send path byte-identical, no task
  hop, no hook). Rejected by the user: it loses the
  `ChargePointMaxProfile` marker, so a transient timeout could move the
  Pulsar into fallback mode — the false-positive direction "without
  hurting my current setup" forbids. Block 1 kept, with the
  2-rejection streak as the tolerance.
- **Latching on a single rejection** (round 2) — zero tolerance;
  replaced by the distinct-episode rejection streak (fix #04: rejections
  count once per debounce window, reset on an accepted write).
- **Replaying the setpoint inside the error hook** (round 2) —
  duplicates the ensure-state retry and creates in-flight ordering
  questions; the next cycle re-issues.
- **`current_offered` as the amp ack in fallback mode** (round 1) —
  lags a MeterValues interval, non-integer vs `==`, may read 0 while
  suspended → retry exhaustion on the population being rescued.
  Optimistic ack instead.
- **Time-based re-probe of the number path (6 h)** (round 1) —
  invented requirement with an ack/mode race window while the flag was
  cleared before the outcome was known. Sticky until reload/restart.
- **`last_reported` freshness gate on `current_offered`** (round
  1) — redundant with the 180 s hold + `Charging` gate; dragged a
  conftest change. Dropped.
- **Unit-of-measurement gate on `current_offered`** (round 2) — OCPP
  defines the `Current.Offered` measurand in amperes and the
  integration passes the charger's unit through; a unit gate would
  silently disable the detector wherever attributes are missing.
- **Extracting `_dispatch_charger_alert` from `_notify_charger_fault`**
  (round 1) — touches QS-346 code for no user need. Channels called
  directly.
- **Only returning `False` from `low_level_*` when the target entity is
  `unavailable`** — nothing consumes those return values;
  `start_charge`/`stop_charge` ignore them and the ensure-state loop is
  observation-driven. No observable change → not done.
- **Feeding `current_offered` into budgeting as the effective max while
  clipped** — safe planning-only mitigation, deferred (touches
  `QSChargerStatus` amp bounds; user chose notification-only).
- **Splitting the detector into its own story / making it opt-in** —
  user decided a single story and notification-only; a false positive
  costs one notification per plug session.
