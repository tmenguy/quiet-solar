## Findings to fix

### [should-fix] S1 — `sync_body` ownership rule is only half implemented (#03 S2)
- File: `scripts/qs/epic_doc.py` (~767)
- Source: qs-review-edge-case-hunter + qs-review-acceptance-auditor (both
  reproduced; deduplicated)
- Description: `is_owned` checks only `_owned_by_heading`. When a prose line
  (e.g. a wave label) sits between `## Children` and the list blocks, filing
  a child lists it as both filed and `(not filed)`, and this never corrects
  itself.
- Proposed fix:
  ```python
  is_owned = any(
      _owned_by_heading(content, s)
      or any(_OWNED_RE.match(content[k]) for k in range(s, e))
      for s, e in section_blocks
  )
  ```
  Add three-run tests (run 1 unchanged, run 2 after filing strips the
  `(not filed)` line, run 3 no-op) for each of these bodies:
  - `"## Children\n\nWave 1:\n\n- [ ] #371 — A\n\nWave 2:\n\n- (not filed) B\n"`
  - `"## Children\n\nRemaining:\n\n- (not filed) B\n\n- [ ] #371 — A\n"`
  - `"## Children\n\nWave 1 (filed first):\n\n- (not filed) B\n- [ ] #371 — A\n"`

  The legacy #369-shaped body (no owned lines) must keep producing no owned
  lines.

### [should-fix] S2 — "re-run from the main checkout" retry hint can't succeed after a live-path kept branch
- Files: `scripts/qs/agent_templates/qs-finish-task.md.j2` (~130–133),
  `docs/workflow/lanes/epic-factory.md` (~247 mirror)
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter (reproduced;
  deduplicated)
- Description: after a live-path `removed-branch-kept` the registration is
  already gone, so a re-run always ends in `absent` → kept again.
- Proposed fix: reword the `removed-branch-kept` bullet. A re-run only helps
  if the worktree directory was deleted out-of-band while still registered.
  Otherwise the agent reports the kept branch and its `branch_delete_error`:
  - If the error is a transient git error, e.g. a ref lock, the user clears
    the cause and runs `git -C <main checkout> branch -D QS_{{issue}}`
    themselves.
  - If the branch was kept because HEAD was detached or unknown, the agent
    leaves the decision to the user.

  Make the lane doc mirror say the same. Update the parity pins in
  `test_lane_steps_parity.py`.

### [should-fix] S3 — A detached registration removes the worktree without an `--issue` check
- File: `scripts/qs/cleanup_worktree.py` (`_cleanup_with_branch` ~555–576)
- Source: qs-review-blind-hunter
- Description: a mismatch in the `branch` case is refused, but a `detached`
  registration is accepted as ownership proof for removal. With a wrong
  `--issue`, another task's detached worktree gets force-removed. That breaks
  the template's "on a refusal nothing was touched" promise.
- Proposed fix: when the registration is `detached`, proceed with removal
  only if `work_dir.name == f"QS_{issue}"` (the worktree naming convention of
  `worktree-setup.sh`). Otherwise refuse with `status: "error"` and touch
  nothing. Keep the existing behaviour of keeping the branch on a detached
  HEAD. Add tests for both a matching and a mismatching dir name.

### [should-fix] S4 — Leftover dir from a partially failed `git worktree remove` can never be cleaned (M1 regression)
- File: `scripts/qs/cleanup_worktree.py` (`remove_worktree` ~108–116)
- Source: qs-review-edge-case-hunter (reproduced with a chmod 555 subdir)
- Description: git drops the registration, then fails to delete the dir. A
  re-run finds the registration `absent` and refuses forever. Before M1, the
  rmtree fallback cleaned this up.
- Proposed fix: when the registration is `absent`, accept a second ownership
  proof. `<work_dir>/.git` must be a **file** whose `gitdir:` line resolves
  (the target may no longer exist) to
  `<git-common-dir of main_wt>/worktrees/<id>`. Only then run `rmtree`, with
  no `git worktree remove`. Anything else keeps refusing. That covers a
  missing `.git`, a `.git` directory (a clone or main checkout), and a gitdir
  pointing at another repo. Add a test that reproduces the case: a real
  worktree, `git worktree remove` failing via a chmod 555 subdirectory, then
  chmod back and re-run → `removed`. Skip the test when running as root. Add
  a negative test where the gitdir points elsewhere → refused, dir intact.

### [should-fix] S5 — New `cleanup_worktree.py` branches have no test
- File: `tests/qs/test_cleanup_worktree.py`
- Source: qs-review-acceptance-auditor
- Description: these new lines are never hit:
  - ~126: a real `git worktree remove` failure with the dir still present.
  - ~209: `git worktree list --porcelain` failing → `"unreadable"`.
  - ~332/336/340: retry path with a proven `branch` registration ending in
    `branch-checked-out-elsewhere` / `removed-branch-kept`.
- Proposed fix:
  - Monkeypatch `subprocess.run` for the `worktree remove` and
    `worktree list` commands (pattern:
    `test_main_worktree_or_fallback_reraises_when_both_fail`).
  - Add a retry-path test: rmtree the first worktree, add a second worktree
    on `QS_77` (`git worktree add --force`), re-run with
    `--force --delete-branch`, and assert `branch-checked-out-elsewhere`.
  - Add a retry-path test where `branch -D` fails → `removed-branch-kept`.
