## Findings to fix

### [should-fix] Fork rotation assumes a stable listing order; duplicate entries are stopped twice
- File: `scripts/qs/control_plane/reviewpilot.py:547-554` (`_matches`), `:591-594` (`_rotated`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter (should-fix + the "duplicates not deduped" nice-to-have)
- Description:
  - `_rotated` indexes `attempts % len(found)` into `matches[rid]`, which keeps `claude agents --json`'s order. That order is not sorted (`ClaudeCli.agents`), so if the CLI reorders entries between ticks, the hanging target can land first every time. The "a target whose stop hangs never starves its sibling fork" promise then fails.
  - Two listing entries with the same target get two `claude stop` calls in one tick. That also skews the rotation.
- Proposed fix: have `_matches` return the matches **deduplicated by target** (`a.id or a.session_id`) and **sorted by target**, so the rotation runs over a deterministic order. Update `_matches`' docstring.
- Tests:
  - A listing permuted between ticks (`[A, B]` then `[B, A]`), where A's stop hangs: over two eligible ticks, both A and B get a stop.
  - A listing with the same target twice: one `claude stop` for it in the tick.

### [nice-to-have] `stopped_ok` misses a session whose stop target changes between listings
- File: `scripts/qs/control_plane/reviewpilot.py:~623-624, ~639-640`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: suppose tick 1 lists `agent("S-1", id=None)`, so the stop goes to `S-1` and exits 0, and tick 2 lists the same session with `id="short-1"`. The lookup uses `a.id`, misses, and the "exited 0 but still listed" line is never logged.
- Proposed fix: after an exit-0 stop, record both `found.id` and `found.session_id` (the non-empty ones) in `stopped_ok[rid]`. Check `a.id in ok or a.session_id in ok`. Test the scenario above: one line is logged.

### [nice-to-have] `_backoff`'s cap has no guard
- File: `scripts/qs/control_plane/reviewpilot.py:~585-588` (`_backoff`)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter
- Description: `int(STOP_BACKOFF_MAX_S // PILOT_EVERY_S)` gives a cap of 0 (no backoff at all) when `PILOT_EVERY_S > STOP_BACKOFF_MAX_S`. Today's constants (3600 / 30) are fine.
- Proposed fix: `cap = max(1, int(STOP_BACKOFF_MAX_S // PILOT_EVERY_S))`. Do not guard against `PILOT_EVERY_S = 0`, which is not a valid throttle.
- Test: with `PILOT_EVERY_S` monkeypatched above `STOP_BACKOFF_MAX_S`, the backoff is 1 tick.

### [nice-to-have] Module docstring: a 191-character line and "once per exit code"
- File: `scripts/qs/control_plane/reviewpilot.py:~28-30` (the module docstring, step 4)
- Severity: nice-to-have
- Source: qs-review-blind-hunter, qs-review-acceptance-auditor
- Description: fix #03 appended text without rewrapping, leaving one 191-character line (the repo's line length is 120; the formatter does not rewrap docstrings). The sentence also says "a failed stop is logged once per exit code", but the code and the docs log once per review and exit code.
- Proposed fix: rewrap step 4 of the docstring at ≤ 120 columns and say "once per review and exit code". While there, rename the stop loop's per-agent variable `found` (it also names the list of matches elsewhere, e.g. `_rotated(found, …)`) to `target_agent`, or similar.

### [nice-to-have] Worst case: a closed review with no `session_id` forces a listing every tick for up to `REQUEST_TTL_S`
- File: `docs/workflow/control-plane.md:~584` (the step 4 "Worst case" bullet)
- Severity: nice-to-have
- Source: qs-review-blind-hunter
- Description: a closed review with no `session_id`, still within `REQUEST_TTL_S` of its launch, stays a candidate. No stop is sent while it is unlisted, so it never backs off, and it costs a listing (up to `HOOK_SUBPROCESS_S`) on every pilot tick for up to 10 minutes. The worst-case bullet says the cost occurs only while closed sessions are listed.
- Proposed fix (doc only; the cost is bounded and accepted): add one clause to the worst case. "a closed review never identified (no `session_id`) costs one listing per tick until its `launch_at` is `REQUEST_TTL_S` (10 min) old". Mirror it briefly in the module docstring if that fits.

### [nice-to-have] Test gaps: the long stderr tail of `_log_stop_failure`, and a hard-coded cap
- File: `tests/qs/control_plane/test_reviewpilot.py:~925` (near `test_a_failed_stop_with_an_empty_stderr`), `:~1034` (`test_the_backoff_never_overflows`)
- Severity: nice-to-have
- Source: qs-review-acceptance-auditor
- Description: no test feeds `_log_stop_failure` a stderr over `STOP_TAIL`. Separately, `test_the_backoff_never_overflows` hard-codes `+ 120`.
- Proposed fix:
  - Add a case with a ~300-character multi-word stderr. The logged tail is ≤ `STOP_TAIL`, starts on a word, and is a suffix of the stderr.
  - Derive the expected cap as `int(reviewpilot.STOP_BACKOFF_MAX_S // reviewpilot.PILOT_EVERY_S)`.
