### [should-fix] S4 — No runtime guard for Claude Code CLI ≥ 2.1.280
- File: `scripts/qs/next_step.py` (payload build path), `scripts/qs/setup_task.py`
  (launcher emission path); reference `scripts/qs/models.py:~47`,
  `docs/workflow/harness.md:~408`
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-edge-case-hunter
- Description: `deep` → `claude-opus-5-5` requires Claude Code ≥ 2.1.280;
  older builds 400. The only check is the story's one-off manual gate (E8).
  On any other machine / fresh clone with an older CLI every `deep` agent
  fails mid-fan-out with an opaque error.
- Proposed fix: add a small pure helper in `scripts/qs/launchers/claude.py`
  (e.g. `check_cli_floor(version_text: str, floor=(2, 1, 280)) -> str | None`)
  that parses `claude --version` output (`"2.1.278 (Claude Code)"`) into a
  tuple and returns a warning string when below the floor, `None`
  otherwise (unparseable → `None`, never raise). Call it best-effort from
  the Claude launcher's payload build (`subprocess.run(["claude",
  "--version"], …)` with a short timeout; any `OSError` / timeout →
  skip), printing the warning to **stderr** only — never block or alter the
  payload, matching how render warnings behave. Add the floor as a named
  constant next to the `claude` row in `models.py` and reference it from
  the helper so the two cannot drift. Tests: helper is pure — parametrize
  below / equal / above / garbage; one launcher test with `claude` mocked
  to an old version asserts the stderr warning and an unchanged payload;
  one with a missing binary asserts silence. Document the guard in one
  sentence in `docs/workflow/harness.md` next to the existing 2.1.280
  note.
