### [must-fix] 1 — fix #01/7 re-opened the deadlock on the stacked-preferring path
- File: `custom_components/quiet_solar/home_model/load.py:1081-1093` →
  `:927` (unguarded probe), contrast `:931-939` (guarded execute)
- Severity: must-fix
- Source: qs-review-edge-case-hunter
- Description: `launch_command` wraps `execute_command` in
  `try/except` but **not** `probe_if_command_set`. On the new
  stacked-preferring path introduced by review fix #01/7 the ordering is:

  ```text
  _stacked_command = None            (:887)
  _last_supersede_time = time        (:918)
  abandon_running_command(...)       (:919)
  running_command = command
  running_command_last_launch = time (:921-923)
  probe_if_command_set(...)          (:927)  <-- UNGUARDED
  ```

  A raising probe therefore consumes the newest intent, stamps both the
  300 s supersede window and the staleness clock, and returns **without
  ever issuing a service call**. The rung is not incremented either
  (`launch_command` never touches `running_command_num_relaunch`).
  Because `SUPERSEDE_MIN_INTERVAL_S == COMMAND_RELAUNCH_BASE_DELAY_S *
  NUM_MAX_COMMAND_RELAUNCH`, the throttle window and the ladder delay
  expire on the same instant, so this path is re-entered on *every*
  300 s window for as long as a differing stacked intent exists.
  Net result: `execute_command` is never called again — **the exact
  deadlock this PR exists to fix, re-created on a path the PR added.**
  Reproduces when an uncontrollable load's `probe_if_command_set` raises
  every cycle (the AC5 device) *and* the solver keeps producing a
  differing `power_consign` (the jitter case the throttle exists for, so
  `_stacked_command` is always non-None and `!= running_command`).
  This also defeats fix #01/3's stated intent — "don't burn the 300 s
  window on a supersede that issued no service call" — for the
  raise-after-stamp case.
- Why the existing test misses it:
  `tests/test_bug_304_command_deadlock.py:811`
  (`test_raising_probe_still_reaches_the_threshold`) exercises this only
  with `_stacked_command is None`, so it routes through
  `force_relaunch_command`, which **is** exception-safe.
- Proposed fix: guard `probe_if_command_set` in `launch_command` the same
  way `execute_command` already is, and make the stamp-and-abandon
  ordering robust to it — a probe that raises must not consume the intent
  *and* burn the window *and* skip the rung. Prefer: probe inside the
  same `try` as the execute, and on exception ensure either the rung
  advances or the throttle stamp is rolled back, so the next cycle can
  still make progress. Pin with a test that is the existing AC5 test
  **plus a non-empty differing `_stacked_command`**, asserting that
  `execute_command` is eventually called and the ladder still reaches the
  threshold.

### [should-fix] 3 — backwards clock step freezes the ladder (primary comparison left unguarded)
- File: `custom_components/quiet_solar/home_model/load.py:1069`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `time - self.running_command_last_launch <= timedelta(...)`
  returns early on a **negative** delta, so the ladder stops advancing
  entirely for the whole duration of a backwards clock jump. For a load
  that is not *yet* uncontrollable, `launch_command` then takes the
  `not self.is_uncontrollable` branch (`:859-863`) and stacks every
  solver command, and the rung can never grow to reach the escalation
  threshold — i.e. the command slot is deadlocked **silently**, with no
  ERROR and no PROBLEM sensor. Reproduces when a command is launched at
  T, NTP or a manual correction moves the clock to T−1 h, and the device
  does not ack: for one hour no relaunch is issued and every new command
  is stacked.
- Note the inconsistency: review fix #01/26 hardened the *sibling*
  comparison in `_is_supersede_throttled` (`:807-812`) against exactly
  this, so the two clock comparisons now disagree about a rewound clock.
- Proposed fix: apply the same future-anchor guard to the primary driver
  comparison. Factor the "anchor in the future ⇒ treat as elapsed" rule
  into one helper used by both sites so they cannot drift again. Pin with
  a rewound-clock test asserting the ladder still advances.

### [should-fix] 4 — `unresponsive_since` stranded when `current_command is None`
- File: `custom_components/quiet_solar/home_model/load.py:830-831`
  (`_drop_running_command`), `:1135-1142` (`_escalate_or_recover`),
  also `:900-903` and `:1159-1160`
- Severity: should-fix
- Source: qs-review-edge-case-hunter (merged with qs-review-blind-hunter's
  two ownerless-clock items)
- Scope note: this finding is **deliberately scoped to the newly
  reachable shapes only**. The invalid-probe give-up shape
  (`_ack_command(time, None)` after `NUM_MAX_INVALID_PROBES_COMMANDS`) is
  the pre-existing defect already tracked in **#308** and is explicitly
  *out of scope here* — do not pull #308 into this PR.
- Description: both clears are gated on `current_command is not None`,
  but a load that has **never had a confirmed command** can cross the
  threshold: `current_command` is `None` after `__init__` or any
  `keep_commands=False` reset, and stays `None` until the first
  `_ack_command`. Path: config-entry reload (or a fresh bistate load such
  as the Pool House switch) → first command launched → never acked →
  1050 s → `unresponsive_since` set with `current_command` still `None` →
  user flips the switch by hand → `force_relaunch_command` →
  `is_command_suppressed_by_override` True → `_drop_running_command` →
  slot empty, rung 0, **clock kept**. Consequences on the next command:
  - `is_uncontrollable` True on its very first cycle with zero relaunches
    — the PROBLEM sensor lit right after the user's own remediation,
    which is the exact symptom fix #01/4 set out to kill;
  - rung is 0, so `command_relaunch_delay_s()` is **50 s while flagged
    uncontrollable**, breaking the "never more than one service call per
    300 s" invariant asserted at `load.py:25-29`;
  - the first differing solver command supersedes immediately instead of
    stacking.

  Same stranding reachable via the `launch_command` override branch
  (`:900-903`) and the disabled-device slot clear (`:1159-1160` →
  `:1135`).
- Proposed fix: make the re-arm unconditional on the emptied-slot paths
  rather than gated on `current_command is not None` — an empty slot with
  no successor has no owner for the clock regardless of whether a
  confirmed command ever existed. Keep the invalid-probe give-up path
  excluded (that gate is #308's subject), and say so in the code comment
  so the two are not conflated. Then correct the `is_uncontrollable`
  docstring at `:682-688`: its claim *"Exactly one shape now produces
  that mismatch"* is inaccurate.

### [should-fix] 5 — `is_uncontrollable` never self-clears when the driver stops running
- File: `custom_components/quiet_solar/home_model/load.py:670-696`,
  `custom_components/quiet_solar/ha_model/home.py:2846-2863`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `check_loads_commands` returns early for `home_mode`
  `None` / `HOME_MODE_OFF` / `HOME_MODE_SENSORS_ONLY` (`:2846-2850`) and
  replaces the load list with `self._chargers` in
  `HOME_MODE_CHARGER_ONLY` (`:2862-2863`); `finish_setup(time) is False`
  returns early too. `home_mode` is a live select entity
  (`select.py:165-172`), so no reload or reset intervenes. Meanwhile the
  binary sensor keeps being refreshed by the independent state loop
  (`binary_sensor.py:237-248`) and stays *available* (only
  `qs_enable_device is False` marks it unavailable), so it reports PROBLEM
  forever. Triggered by the *natural* user reaction to the notification:
  setting home mode to "off", or to "charger only" for a non-charger
  load. The story's stated design — "the `qs_load_uncontrollable` binary
  sensor is the live state that clears itself"
  (`load.py:1543-1548`) — does not hold in these modes.
- Proposed fix: decide and document one of: (a) make
  `is_uncontrollable` additionally require that the driver is actually
  running for this load, so the sensor reads False when QS is not
  managing it; or (b) release the clock when a load leaves the managed
  set. (a) is preferred — it keeps the property derived and needs no new
  write site. Pin with a test that flags a load, switches home mode to
  off, and asserts the sensor clears.

### [should-fix] 6 — AC8 is violated for a load whose cycle raises
- File: `custom_components/quiet_solar/ha_model/home.py:2872-2879`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `check_and_relaunch_command` deliberately propagates the
  device exception, and the per-load `except` logs it **without** setting
  `all_ok = False`. So `finish_off_grid_switch` (`:2836-2840`) sees
  `all_load_ok` True and completes the off-grid switch while that load's
  command was never confirmed — violating AC8 ("a permanently
  uncontrollable load still blocks the off-grid switch") for precisely
  the AC5 device. The `except` shape is pre-existing, but the AC and the
  `all_ok` aggregation contract are new in this PR, and
  `test_permanently_uncontrollable_load_still_blocks_off_grid_switch`
  (`tests/ha_tests/test_bug_304_uncontrollable_load.py:196`) only covers
  the non-raising `NeverAck` load.
- Proposed fix: set `all_ok = False` in the per-load `except`. A load
  whose probe raises is by definition not confirmed-good, so treating it
  as OK is unsound in both directions. Note the interaction with must-fix
  1 in the same area. Extend the AC8 test with a raising load.
