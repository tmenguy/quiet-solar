## Findings to fix

### [should-fix] W1 — Step-aware comparison semantics: false-confirm window + write-skip churn
- File: `custom_components/quiet_solar/ha_model/battery.py:168-199`
  (`_number_reading_matches` / `_entity_step_w`), `:180-182` (the
  inclusive tolerance), plus the write-skip equality checks in
  `set_max_discharging_power` / `set_max_charging_power`
- Severity: should-fix
- Source: qs-review-edge-case-hunter + qs-review-acceptance-auditor + qs-review-blind-hunter (three independent facets)
- Description:
  (a) **False-confirm window (edge-case-hunter, primary):** the probe
  tolerance is `abs(read - expected) <= step_w` unconditionally — one
  full inclusive step even when the expected landed value is
  **step-aligned**, where a quantizing device echoing our write can only
  read back exactly equal; any non-equal reading is provably
  stale/foreign. No-corruption repro: floor=1000 W, max=1500 W, entity
  `{step: 500}` (all aligned). Battery sits at the green-only landed
  1000; off-grid restore commands CMD_GREEN_CHARGE_AND_DISCHARGE →
  expected 1500; the `number.set_value` fails and is swallowed
  (battery.py:421-428), entity stays at 1000 → `|1000-1500| = 500 <=
  500` → **restore falsely confirmed**: no retry, no lost-control
  escalation, battery capped at 1000 W during the outage. Mirror image
  defeats the green-only discharge lock. A corrupt huge `step` widens
  the window arbitrarily.
  (b) **Inclusive boundary (acceptance-auditor):** even for non-aligned
  expected values, a genuine step-echo is always strictly < one step
  away (both step-neighbours of a non-aligned value), so `<=` admits
  only illegitimate readings (e.g. step 1 kW, expected 1000 W, device
  pinned at 0 → confirms a floor that never landed — the latched-at-0
  hazard).
  (c) **Write-skip churn (blind-hunter):** the write-skip check in the
  setters requires exact equality (`expected_w ==
  get_max_discharging_power()`) while the probe tolerates the echo — a
  quantizing device confirms in the probe but fails the skip check, so
  every `execute_command` re-issues the same write (write/re-quantize
  churn).
- Proposed fix (write policy untouched — comparison only): one shared
  step-aware comparison used by BOTH the probe and the write-skip
  checks: if the expected landed value is step-aligned (fp-tolerant
  alignment check, preferably on the entity-unit `write_value` the
  helper already returns), require exact equality; otherwise accept
  strictly `< step_w`. This still satisfies V1's original repro
  (expected 1200 non-aligned, echo 1000, |200| < 500). Tests:
  (1) stale-aligned reject — the restore repro above must NOT confirm
  (and must keep retrying); (2) boundary reject — read exactly one step
  below a non-aligned expected → not confirmed; (3) V1's original
  echo-accept test still passes; (4) write-skip uses the same
  comparison — a quantized echo does not re-issue the write on the next
  execute_command (no churn), while a genuinely wrong value does.

### [nice-to-have] W2 — V2 warning threshold shares the inclusive-boundary flaw
- File: `custom_components/quiet_solar/ha_model/battery.py:300-307`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: A legitimate step snap moves the value strictly less than
  one step, but the divergence warning fires only at `> tol` with
  `tol = step_w`, so an external bound diverging by exactly one step is
  absorbed as if it were quantization: green-only floor 500 W
  (aligned, ceil no-op), entity `{min: 1000, step: 500}` → landed 1000,
  delta == 500 == tol → no warning although the +500 came from
  `ent_min`, not the snap.
- Proposed fix: Warn at `>= step_w` in the snap direction (a real snap
  can never reach a full step) — or compute the actual snap delta and
  warn on any divergence beyond it. Test: the 500/min-1000/step-500
  shape warns.

### [nice-to-have] W3 — Divergence-latch semantics under W1 (fix/test together)
- File: `custom_components/quiet_solar/ha_model/battery.py:162-165` (clear-on-confirm), warn dedupe key
- Severity: nice-to-have
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter
- Description: (a) Clearing the whole `_number_divergence_warned` latch
  on every confirmed probe makes a permanently-diverging entity re-warn
  on every command transition (one WARNING per green-only↔restore
  cycle) rather than once per recurrence; the dedupe key also omits the
  request value, so two different requests landing on the same
  value/direction are silently deduped. (b) The V5-reset × V1-tolerance
  interaction (false confirm resets the latch → warn/clear/warn
  alternation) collapses to a non-issue once W1 lands — verify rather
  than separately fix.
- Proposed fix: Clear only the confirmed entity's entries (not the whole
  set), include the request value in the dedupe key, and re-check the
  alternation scenario after W1; adjust the U5 dedupe test accordingly.
