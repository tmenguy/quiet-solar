# QS-407 — The global and cross-run reviews: agents, the review-session tool, the cross-run pilot, `blast_radius`

Child 15 of epic [#369](../epics/QS-369.md). Lane `feature-factory`,
`target:factory` → `implement-setup-task`. Built on the frozen pipeline.
Dependencies all merged: #399, #400, #375 (ledger, v2), #405 (6c: rows +
resolver), #406 (child 14: tick hooks, alerts, v3). **This child's migration
is v4.**

## Problem

The second pipeline replaces a permanent "coherence checker" with two
one-shot LLM sessions (maintainer, 2026-10-02):

- the **global review of a run**: every task of **one run** read together
  (do they fit together, does each fit the global plan, what is each
  deliverable's blast radius). It is not the per-task review: that one is
  the node's own build loop (focused reviewers + CodeRabbit, 6b);
- the **cross-run coherence review**: tasks of **several runs** that collide
  (same code, same task twice).

Nothing can launch them today:

- `tool spawn` needs a task with a worktree; a review is a session over a
  *set* of tasks, possibly across runs.
- A token is a run's or a node's. A node token is bound to its own task,
  and `ledger.writer` / `msg post` stay inside the token's run: a cross-run
  review could write nothing.
- The daemon (child 14) has a tick-hook point and cross-run alert kinds, but
  nothing acts on them, and the daemon holds no token.
- `blast_radius` has a head sha, but no review's **outcome per task and per
  head** is stored, which child 7's merge conditions need.
- `qs-global-review` / `qs-cross-run-review` have model rows (6c) but no
  template.

## Goal

1. A **review session** model on the Control Plane: `reviews`,
   `review_tasks`, `review_triggers` (schema v4); a **review-scoped token**
   minted at launch; two write paths for it (`finding open` on its scope,
   the `review finish` hand-back); a read-only `review read` for code.
2. **`cp.py tool review`**: launches one review session (`claude --bg`) in a
   private directory, with the model from 6c's resolver and a pinned
   `dontAsk` allowlist; coalesces close triggers and defers the ones a
   running review cannot cover; idempotent on a key (a replayed key never
   launches), recorded in `tool_calls`. 6a calls it for the global review;
   child 13 reuses it for the final review.
3. **The review pilot**: a tick hook on child 14's point that launches the
   cross-run review on its rules, always through a **separate detached
   `cp.py tool review` process**, retries from its own queue, and closes
   reviews that died (DB-only).
4. Each review's **outcome per task with the head sha it reviewed**, a
   minimal reader for child 7, and the global review's `blast_radius` with
   the same sha.
5. The two agent templates, rendered and pinned.

**D1 — A review is a row, not a node.** `reviews` (one row per review),
`review_tasks` (its scope: one row per task, the base and head it reviewed,
its outcome), `review_triggers` (every trigger: created, joined, queued
or skipped — the pilot's queue, D11). Migration `Migration(4, "review sessions
(#407)", schema_reviews.STATEMENTS)`. Not `nodes`: a review has no task, no
worktree, no node cap, no resume.

**D2 — The principal: a review-scoped token, plus a hand-back command.**
Token `review:V<n>.<e>.<nonce>`, a third kind in `tokens`:

- **`e = 1` is the session token** (`reviews.nonce`), minted when the row
  becomes `launching` (the run-token path inserts it so; the grant path's
  `requested → launching` mints it), and passed in the launch prompt. Valid
  while the review is `launching` or `running` and the nonce matches.
- **`e = 0` is the launch grant** (`reviews.grant_nonce`, minted by the
  pilot's request, D10). Valid while the review is not `failed` /
  `abandoned` and the nonce matches — so the launcher's per-step recheck
  and `succeed()` still pass after the session already finished or the row
  went `running` (C2-3, P2-2). It is **bound to its call**: `tool review`'s
  `authorize` (D7) requires `reviews.tool_key == f"review/{key}"`, `key`
  being the call's raw `--key` (C2-9, D3-1).
- **Grammar** (C3-8): `review:V[1-9][0-9]*\.[01]\.[0-9a-f]{32}`, checked
  with `re.fullmatch` (a trailing newline is refused, C4-2); anything else
  is `USAGE`. A `NULL` or empty stored nonce (the session
  `nonce` of a `requested` row, the `grant_nonce` of a run-token row) is
  `STALE_TOKEN` before any comparison.
- **Distinguishing them** (P7): `tokens.require` maps a `review` token with
  `e = 0` to the effective kind `review_grant`, `e = 1` to `review`, and
  checks the effective kind against `kinds`. `tool review` has
  `token_kinds = {"run", "review_grant"}`; `finding open` and `review
  finish` accept `review`. Every other command that takes a token has
  neither in its `kinds`: `CONFLICT`.
- **The reads take no token** (V2-6, C2-17): `snapshot`, `task show`,
  `ledger show` and `review read` are tokenless, as for everyone; only
  `finding open` and `review finish` get `--token`.
- **Expiry is by state**, not by clock (`require` has no clock, P6): the
  pilot moves a dead or expired review to `failed` / `abandoned` (D12);
  outside its valid states a token is `STALE_TOKEN` with
  `REVIEW_INSTRUCTIONS` ("this review is closed or superseded: stop now,
  take no further action"). Review nonces are compared with
  `hmac.compare_digest`.
- **`Principal`** gains `review_id: str | None = None`, `review_kind: str |
  None = None`, `scope: frozenset[str] = frozenset()`; `run_id` is the
  review's `home_run_id` or `""` (cross-run), and `_Call.claim` stores
  `who.run_id or None` in `tool_calls.run_id` (P3). `actor` is
  `review:V<n>`.
- **`require(task_id=…)` with a review token**: the task must be in
  `scope` (`CONFLICT` otherwise, any run); the run check is skipped.
- Where the session token writes, and nowhere else:
  - `finding open` on a scope task, `--source` required and equal to the
    review's source (`global_review` / `cross_run_review`, already in
    `schema_ledger.REVIEWER_SOURCES`; another is `CONFLICT`). Each item's
    `reviewer` is set to `review:V<n>` (a given one is replaced), so an
    exact re-raise across reviews is a new row, matched and flagged by
    #375's matching — never a replay of another review's row. A terminal
    scope task (a merged one, D3) is accepted: the ledger checks no task
    state. `relates_to` keeps #375's run scoping (the task's run).
  - **`review finish`** (D4).
- So a review never calls `finding state` / `classify`, `blast-radius set`,
  `msg post` or any tool.
- **Threat model** (Q2): unchanged — the Control Plane guards against agent
  mistakes, not adversarial sessions. The Control Plane writes the session
  token to **no file of its own**; it is in the `claude --bg` argv (visible
  in `ps`, as a node's is) and in Claude Code's own session transcripts
  (C2-12). Mitigations: error text recorded by the tool is redacted
  (`review:V<n>.<e>.<redacted>`), a test asserts `launcher.log` never holds
  a nonce, and `snapshot` strips both nonces (`nonce` is already in
  `SECRET_COLUMNS`; `grant_nonce` is added).

**D3 — Scope, base and head.**

- **Global** (`kind = global`, requested with a **run token** of that run):
  every task of the run that is a deliverable (`is_deliverable = 1`) or a
  work item (`deliverable_id IS NOT NULL`) and is not terminal (state not in
  `tokens.TERMINAL_TASK_STATES`: `dropped`, `merged`, `validated`). A run
  token asking for `cross_run`, or for another run, is `CONFLICT`.
- **No global review for fewer than 2 tasks** (maintainer): the count is
  every scope task, work items included (a deliverable split into 3 items
  is 4 tasks). 0 or 1 task → the call **succeeds** with `{"skipped":
  "single_task", "tasks": [...]}`, nothing in `reviews` or
  `review_triggers`; the `tool_calls` row is `succeeded`, so a replayed key
  returns the same answer. 6a's triggers never fail on it.
- **Cross-run** (`kind = cross_run`, requested by the pilot only): the
  event's tasks (D11), **filtered at every request** (re-filtered on each
  re-request, C3-10): tasks of closed runs dropped, except a merge event's
  merged task, always kept even if its run just closed (C3-7). Skipped
  when what is left holds no non-terminal task, or (alert event) spans
  fewer than 2 open runs, or (merge event) has no open run other than the
  merged task's. A skip writes no `reviews` row; the pilot's trigger row is
  marked `skipped` (D11). The coalesce key is built on the kept set
  (V2-11).
- **The base and head reviewed**, per scope task, captured **once** in
  `prepare` (through `ctx.runner`, timed, in `<MAIN>`), never recaptured
  (`prepare` writes only rows still pending, C2-8). The first row that
  applies wins:

  | the task | `head_sha` | `base_sha` | `head_state` |
  |---|---|---|---|
  | `merge_sha` set **and present locally** (`git cat-file -e <merge_sha>^{commit}`) | `merge_sha` | `rev-parse <merge_sha>^1` | `merged` |
  | a branch that resolves (`rev-parse --verify refs/heads/<branch>^{commit}`) | the tip | a work item: `merge-base refs/heads/<its deliverable's branch> <head>` when that branch resolves (P3-2); otherwise `merge-base <main base> <head>` | `branch` |
  | a branch that does not resolve | `NULL` | `NULL` | `unresolved` |
  | no branch | `NULL` | `NULL` | `plan` (the review covers its plan) |

  **`<main base>`** (P3-1) follows child 14's overlap rule
  (`detectors._main_base`, reimplemented on `ctx.runner`, not imported): the
  newer of `refs/heads/main` and `refs/remotes/origin/main` (`merge-base
  --is-ancestor`), `origin/main` when they diverged — task branches are cut
  from `origin/main` and nothing in the Control Plane fetches. A merge
  commit not yet fetched falls through to the branch rows; `prepare` never
  fails on it (P3-3). **Exit codes** (P4-1): only `0` means present or
  resolved; a runner timeout or exec failure (`124` / `127`, child 14's
  `ABORT_CODES`) fails the step (`StepFailed`, the review `failed`, so it is
  retried rather than recorded `unresolved`); any other code (`128` for a
  missing object or ref) means absent. `base_sha..head_sha` is then the task's own change,
  whatever `main` did since (C2-6, P2-7, V2-8). Outcomes on a `NULL` head are **advisory**: the
  reader (D13) never returns them, so child 7 cannot gate on them.

**D4 — `review finish`: the hand-back.** `cp.py review finish --input F
--token <session>`. Input:

```json
{"summary": "…",
 "tasks": {"T3": {"outcome": "pass", "blast_radius": "ok", "reason": "…"},
           "T7": {"outcome": "fail", "reason": "…"}}}
```

- **Order of checks** (P2-10): read the file and parse the JSON (duplicate
  keys and non-JSON → `USAGE`); then `tokens.require` (`CONFLICT` /
  `STALE_TOKEN`); then the shape and the scope.
- Every scope task appears exactly once (`USAGE` otherwise; a task outside
  the scope is `CONFLICT`). `outcome` is `pass | fail`; `reason` is
  required for `fail`. Nothing cross-checks `outcome` against the findings
  (the ledger records, it does not refuse).
- `blast_radius` (`ok | doubt | too_large`): **global reviews only**
  (`USAGE` in a cross-run review); **required** for every scope deliverable
  with a non-`NULL` head; allowed on any scope task with one; `USAGE` on a
  `NULL` head. Appended to #375's `blast_radius` (which already has the
  free-text `review` column) through a shared helper
  `ledger.append_blast_radius_locked`, with `head_sha` = the reviewed head,
  `review` = `V<n>`, actor `review:V<n>`. `blast-radius set` stays run-only,
  unchanged.
- One transaction: a guarded `UPDATE reviews SET state = 'finished' … WHERE
  id = ? AND state IN ('launching', 'running')` (a finish while the launcher
  is still identifying is fine, C10); `review_tasks.outcome / reason /
  blast_radius_id / recorded_at`; one **`review_done`** message per **open**
  run of the scope (`messages.post_locked`, recipient `orchestrator`,
  sender `review:V<n>`, `dedupe_key = review:V<n>` — `messages` is
  `UNIQUE (run_id, dedupe_key)`, so each run gets its own, C2-5), payload
  `{review_id, kind, summary, tasks: [{task_id, base_sha, head_sha,
  head_state, outcome, reason, blast_radius, finding_ids}] (that run's
  tasks), other_runs: [...]}`; `finding_ids` are the task's findings whose
  actor is `review:V<n>`.
- **No replay** (S5): afterwards the session token is void, so a second
  call is `STALE_TOKEN` with `REVIEW_INSTRUCTIONS` — the session stops; the
  data is already written.

**D5 — Where a review runs** (confirmed). In a **private directory outside
every checkout**: `QS_CP_REVIEW_DIR` (default
`~/.local/state/quiet-solar/cp-reviews/`), then
`<root>/<sha256(str(paths.select_db().resolve()))[:8]>/V<n>/`. One helper,
`reviews.review_dir(review_id, create=True)`, applies
`paths.ensure_private_dir` to the root, the hash level, `V<n>` and its
`in/` (P2-9; a directory inside a checkout or linked worktree is
`POLICY_REFUSED`, as `QS_CP_MESSENGER_DIR`); the pilot and `prepare` both
call it.

- **Layout** (C2-10): `in/` (the session's own input files — the only
  place it can read or write), `.claude/agents/<stem>.md` (the agent copy),
  `args.json` (the pilot's launcher args), `launcher.log`.
- The agent file is **copied** at `prepare` from
  `<MAIN>/.claude/agents/<stem>.md` (stdlib; the Control Plane never
  renders). Missing → the review `failed`, the step `StepFailed` "render
  the agents on main".
- The session gets **no `--add-dir`**: it reads code only through `cp.py
  review read` (D6a) at the reviewed shas, and state through `snapshot`
  (whose `alerts` key **is** child 14's alert read path, with each alert's
  payload `tasks`, S2-3), `task show`, `ledger show`.
- **The DB** (V2-2, C2-15, S3-1): the launch's `--settings` JSON always
  carries `"env": {"QS_CP_DB": "<str(paths.select_db().resolve())>"}`, so the
  session's `cp.py` calls open the same DB as the launcher (the live one in
  production, identical behaviour). The detached launcher inherits the daemon's
  environment (`daemon.strip_env` removes only the token and session
  identity, so `QS_CP_DB` stays; pinned, V2-10).
- **Retention:** review directories are kept (they are small); delete old
  ones by hand, as the `v<N>` backups. Noted in "Conventions".

**D6 — Permission mode: `dontAsk` with a pinned allowlist** (confirmed;
`auto` is the fallback). `reviews.REVIEW_PERMISSION_MODE = "dontAsk"`;
`reviews.launch_args` builds both forms, both pinned by tests (V9):

- `dontAsk`: `--permission-mode dontAsk --allowedTools=<list>` (one word:
  #406 T1's variadic trap), `<list>` = `reviews.allowed_tools(main, python,
  review_dir)`, exact strings pinned:
  - `Read(/<in>/**)` and `Write(/<in>/**)`, where `<in>` is the absolute
    `…/V<n>/in` path, so the rule starts with `//` (Claude Code's
    absolute-path form). Worked example: `in` = `/x/V1/in` →
    `Read(//x/V1/in/**)`, `Write(//x/V1/in/**)` (V2-9);
  - `Bash(<python> <MAIN>/scripts/qs/cp.py <cmd>:*)` for exactly `snapshot`,
    `task show`, `ledger show`, `review read`, `finding open`, `review
    finish`, with `<python>` the D10 rule (`<MAIN>/venv/bin/python`, else
    `sys.executable`), shared with the prompt's `cp.py` prefix.
  - `allowed_tools` refuses (`POLICY_REFUSED`, so the review `failed`) a
    `<MAIN>`, `<python>` or directory path holding whitespace or a shell
    metacharacter: the unquoted pinned form would stop matching (C2-11).
- `auto` (fallback): `--permission-mode auto
  --disallowedTools=Edit,NotebookEdit`.
- **The command form** the template pins (V13/C12): one command per Bash
  call, no pipe, no `&&`, no `;`, no redirect, no `$(…)`, no env prefix, no
  heredoc; always `<python> <cp.py> <cmd words> …`, with `--token` (only on
  `finding open` and `review finish`) after the command words.
- `--settings` is `hooks_settings("node", main)` — the hook fragment, whose
  `PreToolUse` DB-access deny applies to **any** session — plus the
  policy's `effortLevel` and D5's `env`. The deny rules for
  *registered* sessions (`gh pr merge`, a superseded `SendMessage`) key on
  `runs.session_status`, which knows only nodes and orchestrators; a review
  session is neither, so they do not apply — and are not needed: neither
  tool is allowed (D2-2).

**D6a — `cp.py review read`: git, read-only, fixed argv** (Q1). **One
exempt command** (no DB, no token), `review read <op> …` with a positional
`op` (`choices = ("diff", "show", "grep", "ls-tree")`, P2-12; `log` dropped,
S2-1), that runs a fixed `git` invocation in `paths.main()` and prints
`{"ok": true, "output": …, "truncated": bool, "lossy": bool}`:

| op | arguments | runs |
|---|---|---|
| `diff` | `--base SHA --head SHA [--path P]` | `git diff --no-ext-diff --no-textconv --no-color <base> <head> [-- P]` |
| `show` | `--rev SHA --path P` | `git cat-file blob <rev>:<P>` |
| `grep` | `--rev SHA --pattern X [--path P]` | `git grep -n --no-color -e <X> <rev> [-- P]` |
| `ls-tree` | `--rev SHA [--path P]` | `git ls-tree -r --name-only <rev> [-- P]` |

- Every call: `-c core.pager=cat -c diff.external=`, environment
  `GIT_CONFIG_NOSYSTEM=1`, `GIT_PAGER=cat`, `GIT_EXTERNAL_DIFF` unset, a
  timeout.
- `SHA` is a 7–40 hex sha only (S2-2): the prompt gives every `base_sha` /
  `head_sha`, so no moving ref is needed; anything else (a ref, a leading
  `-`) is `USAGE`. `P` goes through `ledger.norm_path`. `X` is passed after
  `-e`.
- Output is decoded through a new `decode_errors` keyword of `Runner.run`
  (forwarded by `tools._StepRunner.run`, P3-4) and `FakeRunner.run` (P2-6),
  with `"surrogateescape"` (P3-6): `lossy` is true when a lone surrogate is
  present; the byte count is `len(out.encode("utf-8", "surrogateescape"))`
  and truncation at `READ_MAX_BYTES` (256 KiB) cuts on those bytes; the
  result is then re-decoded with `errors="replace"` before printing.
- No other git option can be passed, so `-O`, `--output`, `--ext-diff`,
  `--textconv`, `--filters`, `--write-tree` are unreachable; tests pin each
  op's argv and the refusals.

**D7 — `tool review`, a task-less tool.**

- **Two additive `ToolSpec` fields**, appended last in this order and
  pinned in `test_tools.py`'s field list (P11, P2-1):
  - `task_bound: bool = True`. `cp.py tool <name>`: `--task` is optional at
    parse; the handler requires it for a bound tool and refuses it for an
    unbound one, both `USAGE` (exit 2, as `_Parser.error`).
    `run_recorded(task: str | None)`, `invoke(task_id: str | None)`;
    `_Call.task()` returns `cast(TaskRow, None)` for an unbound spec, so the
    declared types stay `TaskRow` and no existing tool changes (P2). An
    unbound spec never reads `ctx.task` nor uses `task_state_guard` /
    `non_terminal`.
  - `authorize: Callable[[sqlite3.Connection, tokens.Principal, Mapping[str,
    Any], str], None] | None = None` (connection, principal, args, key),
    called by `run_recorded` inside its first `db.write`, right after
    `call.require()` and before `replay()`: a refusal there is a clean
    `CONFLICT`, before any claim (no `tool_calls` row, nothing spent).
- **`locks`** (P1): `Held` gets `kinds` (default `{"run", "node"}`);
  `_Call.run` passes `self.spec.token_kinds` to `locks.hold`, which uses it
  in `recheck`, `_take_lock` and `_take_slot`. `tool review` itself takes
  **no lock and no slot** (C2-16), but `recheck` runs before every step.
- **Args and the matrix** (V21, checked by `authorize`):

  | token | args | answer |
  |---|---|---|
  | run of R1 | `{kind: global, run: R1, trigger?}` | launch, join, defer or skip |
  | run of R2 | `{kind: global, run: R1}` | `CONFLICT` |
  | run | `{kind: cross_run, …}` or `{review: …}` | `CONFLICT` |
  | grant of V7, `reviews.tool_key == "review/" + key` | `{review: V7}` | launch |
  | grant of V7, another key | any | `CONFLICT` |
  | grant of V7 | `{review: V8}` or `{kind: …}` | `CONFLICT` |
  | session token, node token | any | `CONFLICT` (kind not accepted) |

- **`reviews.request_locked`** (V2-14), shared with the pilot (D10):
  `request_locked(conn, clock, *, kind, run_id=None, tasks=None, trigger,
  actor, tool_key, grant, trigger_row_id=None) -> Skipped | Joined |
  Deferred | Created`. It computes the scope (D3), applies D8, and on
  `Created` inserts the row — `launching` with a `nonce` (run token,
  `grant=False`) or `requested` with a `grant_nonce` (pilot, `grant=True`)
  — and its `review_tasks` (base and head pending). Its trigger row: with
  `trigger_row_id` (the pilot's queue row, D11) it **updates** that row
  (`review_id`, `outcome`); without it (the run-token path) it inserts one,
  except on `Skipped` / `Deferred` (V3-1, C3-4). `reviews.tool_key` is
  `review/<key>` (the spawn precedent `"<tool>/<key>"`, P2-13);
  `review_triggers.tool_key` is the raw key. Ids come from
  `db.next_id(conn, "review", "V")`.
- **Steps** (new code in `reviews.py`; only `liveness.find`,
  `nodes.LAUNCH_SETTLE_S` and `tools.IDENTIFY_POLL_S` are reused from
  `spawn`, P8). **Each step re-reads the review and checks its own
  precondition** (C2-8, V2-4, C3-3): `reserve` — none on the run-token path,
  `requested` (or `launching` under the same key: a takeover) on the grant
  path; `prepare` and `launch` — `launching`, else the step fails; steps
  2–4 — a noop when `reserve` recorded a skip or a join; `identify` and
  `on_success` — any state but `failed` / `abandoned` (a `finish` while
  identifying is fine, C10):
  1. `reserve` (one transaction) — run token: `request_locked`; `Skipped`
     records `{"skipped": …}`, `Joined` records `{"coalesced_into":
     "V<n>"}`, **`Deferred` raises `BUSY`** "a review of this key (V<n>) is
     running; replay this key after it closes" (released before any
     effect, so the same key works later, D8); `Created` records
     `{"review_id"}`. Grant: a guarded `requested → launching` that mints
     the session `nonce`; a row already `launching` under the same key is a
     takeover and **re-mints nothing** (the launched session keeps its
     token, C3-11).
  2. `prepare`: first, in its own transaction, stamps `reviews.heads_at`
     (the capture marker, set **before** git runs, so D8 defers from that
     instant, C3-1) with a guarded `UPDATE … SET heads_at = ? WHERE id = ?
     AND state = 'launching' AND heads_at IS NULL`: no row changed and the
     row not `launching` → the step fails; still `launching` with
     `heads_at` set → a takeover, it proceeds (C4-4); then base and head (D3, rows still pending only), the
     model `Ctx.resolve_model(stem, None)` (reached as
     `ctx._call.ctx.resolve_model`, as spawn does; `None` → `StepFailed` "no
     model resolver", the review `failed`, P4-3) → `(model, effort)` (no lane: a review spans lanes; "the default class"
     is the row's own class — `frontier` / `deep` today, whatever 6c's row
     says), `review_dir(create=True)` and the agent copy.
  3. `launch`: stamps `launch_at`, then `claude --bg --agent <stem> -n
     <name> --model M <D6 permission args> --settings '<D6 settings>'
     "<prompt>"`, cwd = the review dir, `QS_CP_TOKEN` and the session
     identity removed (`daemon.stripped_names`). The prompt carries the
     facts: review id and kind, the scope (task, run, title, branch,
     `base_sha`, `head_sha`, `head_state`), the exact `cp.py` prefix, the
     `in/` directory, the token, the deadline.
  4. `identify`: the listing by name until `launch_at + LAUNCH_SETTLE_S`.
  - Steps 2–4 are noops after a skip or a join; `on_success` returns the
    short answer (P17).
  - **Failures** (S2): any failure of `prepare`, `launch` or `identify`
    (never listed) first moves the review to `failed` with a **guarded**
    `UPDATE … WHERE id = ? AND state IN ('requested', 'launching')` (with
    `error`, its own transaction, C2-2) and, in that transaction when one
    row changed, posts `review_failed` to each open run of the scope (C3-2,
    V3-2: the joined triggers and 6a's deferred callers learn it); then it
    raises `StepFailed`: the key
    is spent, the coalesce key is free, the session token is void (a late
    session gets `STALE_TOKEN` at its first write). **A replayed key never
    launches again**: the probe reports `launch` done whenever `launch_at`
    is set, and a takeover of a dead holder only finishes `identify`
    against the original deadline.
  - `on_success`: guarded `UPDATE … SET state = 'running' WHERE id = ? AND
    state = 'launching'`; on a row already `finished` it records only
    `session_id` / `short_id` and the answer carries the actual state (V4). The answer: `{review_id, kind, name,
    session_id, state, tasks: [{task_id, run_id, base_sha, head_sha,
    head_state}]}` — no token.
- **Replay and `NULL` columns** (V2-7): `tool_calls`' key is its primary
  key `(tool, key)`, and its `task_id` / `run_id` are nullable since v1, so
  a task-less, run-less call replays by key like any other; tested.
- **Registration:** `reviews.register_review_tool()`, idempotent, called by
  `cli` at import and in `main`; `reviews.TOOL_NAME = "review"`;
  `selfcheck._expected_tools()` adds it (P22).

**D8 — Coalescing and deferral** (Q6, maintainer 2026-10-16: "6a"). The
coalesce key is `global:<run>` or `cross_run:<sorted kept task ids joined by
"|">` ("the sorted set of tasks touched"; a superset is a different key,
C16 rejected). When the key has a review in flight (`requested`,
`launching` or `running`):

- **its capture has not started** (`heads_at IS NULL`: it is `requested`,
  or `launching` before `prepare`'s first transaction) **and**, for a
  global review, the newly computed scope equals its `review_tasks` set
  (a task added or split meanwhile defers, C3-5) → the request **joins**
  it: one trigger row (`outcome = 'joined'`), no launch, the answer
  `coalesced_into: V<n>`;
- **otherwise** → the request is **deferred**: it would be
  absorbed by a review that never sees the new commits. `tool review`
  answers `BUSY` with the running review's id (released, nothing written:
  6a replays the **same key** after `review_done` / `review_failed`); a key
  whose call ended (a launch, a join, a failure) is spent: after a
  `review_failed` for its own review or one it joined, 6a uses a **new key**
  (`task:<R>:global:<n+1>`, C4-1); the pilot
  keeps the event in its queue (D11) and retries on a later tick.

So after a running review closes, **one** new review of the latest heads
starts, and the triggers that arrive in its first seconds join it. A partial
unique index on `reviews(coalesce_key) WHERE state IN ('requested',
'launching', 'running')` makes two in-flight reviews of one key impossible.

**D9 — No budget and no cap** (maintainer; see "Deviations"). `tool
review` limits neither the number of reviews per run nor the sessions
running at once, and never counts against the node cap (`locks.admit_node`
counts only `nodes` rows). Every review and trigger is recorded.

**D10 — The pilot's authority: the launch grant.** The daemon holds no
token. The pilot, in-process, calls `reviews.request_locked(…, grant=True,
tool_key="pilot:<event>:<attempt>")` (the **same** scope, coalescing and
deferral as `tool review`). On `Created`, outside the transaction, it calls
`review_dir(create=True)`, writes `args.json` (`{"review": "V<n>"}`) and
starts:

```text
<MAIN>/venv/bin/python <MAIN>/scripts/qs/cp.py tool review \
    --key pilot:<event>:<attempt> --args-file <dir>/args.json --token review:V<n>.0.<grant>
```

through `seams.popen(argv, cwd=<MAIN>, start_new_session=True,
stdin=DEVNULL, stdout=log, stderr=log, env=daemon.strip_env(os.environ))`,
`log` = `<dir>/launcher.log` opened by the pilot and closed right after the
call. Any exception in the directory, the file or the `Popen` moves the
review to `failed` (guarded) with its alert (C2-14). It never waits: the
identify wait (up to 60 s, past `STALE_AFTER_S`) never holds the tick. **No
zombies** (C4): the pilot keeps each `Popen` in a module list and `poll()`s
it every tick, dropping the finished ones. A missing
`<MAIN>/venv/bin/python` falls back to `sys.executable` (the watchdog's
rule). With `Seams.popen is None` the pilot skips its step 3 entirely (no
request, no trigger row), logging once (P3-8, C3-11).

**D11 — The trigger rules and the pilot's queue** (rules confirmed).

- **Alerts:** `PILOT_KINDS = {overlap_cross_run, duplicate_task_cross_run}`
  (not `dependency_cycle_cross_run`: a dependency edit, already alerted to
  every run). Open `alerts` rows of those kinds, grouped by `(kind,
  subject)`; scope = the payload's `tasks`. **One occurrence, one event**
  (C2-13): an open group whose alert ids intersect the `alert_ids` stored in
  an earlier trigger row of that `(kind, subject)` is that same event; a
  group with no shared id (a recurrence: new rows) is a new event, keyed
  `alert:<kind>:<sha256(subject)[:16]>:<lowest alert id at first sight>`.
  A partial clear keeps the event. A recurrence always has new ids: child
  14's `alerts._raise` inserts a new row per occurrence (counter `n`), it
  never reopens a cleared one (C3-9).
- **A merge that touches another run:** a task that reached `merged`
  (`task_history`, after `meta.review_pilot_cursor`) for which **any**
  `overlap_cross_run` row (open or cleared) names it with a task still
  non-terminal in another open run. Scope = the merged task plus those
  tasks. Event key `merge:<task>:<history id>`. DB-only. **Limit:** an
  overlap the detector never saw is not caught (the node's catch-up with
  `main` still meets it).
- **The queue is `review_triggers`** (C2-4, V2-5, C3-4): every new event is
  written at first sight as a trigger row `tool_key = pilot:<event>:1`,
  `outcome = 'queued'` (unique partial index `ON review_triggers(tool_key)
  WHERE tool_key LIKE 'pilot:%'`), whose `trigger` JSON carries the event,
  its raw task ids and its `alert_ids`; a merge row is written **in the
  same transaction** that advances the cursor past it (C21). The request
  (`request_locked(…, trigger_row_id=…)`) sets `outcome` to `created`,
  `joined` or `skipped`, or leaves it `queued` when `Deferred`. Each tick
  re-requests, re-filtering the stored task ids (D3):
  - the rows still `queued` — an alert event none of whose stored
    `alert_ids` is still open is marked `skipped` instead (the collision is
    gone, C4-3); merge events are not affected;
  - **Q7 (maintainer, 2026-10-16: "7a"):** an event whose latest attempt's
    review ended **`failed`** (the launch failed: nothing ran) gets attempt
    `n + 1` as a **new** row `pilot:<event>:<n+1>`, while `n <
    PILOT_ATTEMPTS` (2). A review that ended **`abandoned`** (it ran, then
    died or expired) is **not** retried: its `review_failed` alert tells the
    orchestrators and the maintainer, who decide.

  So a crash between the request's commit and the `Popen`, or a launcher
  that never started, is retried once, for merge events too; a `skipped`
  row leaves the queue for good (S3-3).

**D12 — The pilot hook: `review_pilot`.** In `activeloop._builtin()` **and**
`activeloop.BUILTIN_NAMES`, from its own module `reviewpilot.py`, after
`detectors` and before `hook_route`. Every `PILOT_EVERY_S` (30 s,
`ticks.Throttle`):

1. **Reap** finished launcher processes (`poll()`).
2. **Close dead reviews** (read, probe, beat, write — no subprocess in a
   `db.write`). Every move is a **guarded** `UPDATE … WHERE id = ? AND state
   = <the state read> AND <its condition, re-evaluated in SQL>`, and posts
   its alert only when one row changed (C2-2). With `since =
   COALESCE(launch_at, updated_at)` (V2-4, C2-1, P2-3, D2-1):
   - `requested` with no `tool_calls` row `PILOT_RETRY_S` (60 s) after
     `created_at` (the launcher never started) → `failed`;
   - `requested` / `launching` whose `tool_calls` row is `failed`, or
     `started` with a dead holder (`seams.probe.holder_alive`, the check
     `tools` uses) and `since` older than `LAUNCH_SETTLE_S` → `failed`;
   - `requested` / `launching` with `since` older than `REQUEST_TTL_S`
     (600 s) → `failed`: the backstop for a launcher alive but hung, which
     the dead-holder rule cannot see (S2-4);
   - `running` whose `session_id` is absent from `LIVENESS_CONFIRM` (2)
     consecutive successful listings → `abandoned` (C3-6). The listing
     (`seams.claude.try_agents(timeout=HOOK_SUBPROCESS_S)`, a beat after) is
     taken only while a review is `running`; the sighting counter lives in
     memory and starts cold (a new daemon needs 2 fresh sightings); a failed
     listing changes nothing;
   - `running` with `launch_at` older than `REVIEW_TTL_S`
     (3600 s) → `abandoned`;
   - (review fix #01, S2) a `launching` review with `launch_at` set whose
     session the listing shows by name is adopted (`running`, guarded)
     instead of failed; under a failed listing only `REQUEST_TTL_S` fails it.

   A review's `tool_calls` row is found with `(t.tool || '/' || t.key) =
   r.tool_key`, as `locks` does for spawn (P3-7).

   Each move posts one `review_failed` event (`alerts.event_locked`,
   subject `review:V<n>:<state>`, per open run of the scope — alerts are
   per run, `UNIQUE (run_id, fingerprint)`), payload `{review_id, kind,
   state, error, finding_ids}` (the findings it opened before dying, C17).
   No `claude stop`: a dead or late session's token is void.
3. **The queue and the rules** (D11) → `request_locked` → the launcher
   (D10).

Seams (P2-4, P2-5): `Seams.popen: Callable[..., Any] | None = None`
(`make_seams` passes `subprocess.Popen` at call time; the existing
`Seams(...)` calls in `test_watchdog.py` and `test_ciwatch.py` stay valid;
the pilot logs and launches nothing when it is `None`); the test
`make_seams` passes `deps.popen`, so the no-real-subprocess guard still
catches it (P10); `FakePopen` returns a `FakeProc` with a scriptable
`poll()` / `returncode` and a `pid` (`daemon.ensure` ignores the return
value). Pilot rows' actor is `cp:review_pilot`.

- `review_tasks`: `review_id`, `task_id`, `run_id`, `base_sha`,

- `review_triggers`: `id`, `review_id` (nullable: a queued or skipped

- `schema_reviews.STATEMENTS` ends with the cursor seed (v3's precedent,

- **The reader** (minimal, S11): `reviews.outcome(conn, task_id, *, kind,

- **`snapshot`** gains `reviews`, `review_tasks`, `review_triggers`

  cross-run launcher in flight (`tool_calls.run_id NULL`) is not in a
  run-filtered `tool_calls_in_flight`; its `reviews` row is. `task show`
  and the export are unchanged.
- `alerts.REVIEW_FAILED = "review_failed"` in `alerts.KINDS` (daemon-owned:
  a hook cannot pose as it). Message kind `review_done` (`messages` checks
  only its 1–32 characters, V3-3).

**D14 — The agents.** `qs-global-review.md.j2` and
`qs-cross-run-review.md.j2`, each extending `_base.md.j2`:

- Claude frontmatter: `name`, `description`, `tools: Bash, Read, Write`,
  `model: [[ model ]]` (6c's rows). OpenCode frontmatter mirrors
  `qs-plan-critic.md.j2` (`description`, `mode: subagent`, `color`,
  `hidden: true`, the model line, `permission` with `edit: deny`, P16).
  Both stems go into `LSP_EXCLUDE_AGENTS` (P4).
- The body (the facts come from the prompt):
  1. read `snapshot --run R` for each run of the scope (`runs.global_plan`,
     decisions, reports, `alerts`), then `task show --task T` per scope
     task (digest body, criteria, ledger, convergence) — no `--token`;
  2. read `ledger show --task T --family --state
     open,rejected,settled,deferred` and **raise nothing already there**
     (`relates_to` instead);
  3. read the code **only** with `review read`, at the shas of its prompt:
     `diff --base <base_sha> --head <head_sha>` for the task's change,
     `show --rev <head_sha> --path …`, `grep --rev <head_sha> --pattern …`,
     `ls-tree --rev <head_sha>`; never assume a working tree;
  4. the lens — global: does each task fit the global plan, do the tasks
     fit together, each deliverable's blast radius; cross-run: do the runs'
     tasks conflict (same code, same feature twice, contradictory
     decisions), what must each run know;
  5. write a JSON file in its `in/` directory, then `finding open --task T
     --phase <build if head_state is branch or merged, else plan> --source
     <its source> --input <file> --token …`, one call per task (a cross-run
     finding is opened on each task it touches);
  6. write the finish file in `in/`, call `review finish` once, then stop.
- **Errors:** `USAGE` from `finding open` / `review finish` → fix the input
  and retry, at most twice; `CONFLICT` → do not retry that item, mention it
  in the summary; `STALE_TOKEN` → stop at once. Never edit, commit, push,
  post messages, or call another command; one command per Bash call (D6).

### 3. The flows

```text
orchestrator (6a, later):  cp.py tool review --key task:R1:global:<n> --args-file {kind: global, run: R1, trigger} --token <run>
   authorize → reserve (scope · skip · join · BUSY if deferred · row launching) → prepare (base/head · model · dir · agent copy)
   → launch → identify → running

daemon tick → review_pilot (in-process):
   reap children → close dead reviews (guarded) → queue + rules → request_locked (scope · join · defer)
   → row requested + grant → review_dir · args.json
   → Popen(cp.py tool review --key pilot:<event>:<n> --args-file <dir>/args.json --token review:V<n>.0.<grant>)   [detached]
        → authorize (key = tool_key) → reserve (requested → launching, session nonce) → prepare → launch → identify → running

review session (cwd = <review dir>, dontAsk):
   snapshot · task show · ledger show · review read …  →  finding open (scope, its source, --token) …
   →  review finish (outcomes · blast_radius (global) · finished · review_done to each run)  →  stop
```

## Acceptance criteria

1. **Launcher.** `tool review` launches `claude --bg` with the resolver's
   model and `effortLevel`, `dontAsk` and the pinned allowlist, in the
   review's private directory with the agent copied; records `reviews`,
   `review_tasks` (base and head per task), `review_triggers` and
   `tool_calls`; skips a global review of fewer than 2 tasks; a replayed key
   never launches; a failed launch frees its coalesce key; a review never
   counts against the node cap.
2. **Principal.** A review session token writes findings on its scope only,
   with its source, across runs; `review finish` records each task's
   outcome (and, in a global review, `blast_radius`) with the reviewed head
   sha and posts `review_done` to each open run; a closed review's session
   token, a grant on a write or on another key, a session token on `tool
   review`, a foreign task and a review token on any other command are
   refused.
3. **Reads.** `review read` runs only its fixed git argv on hex shas and
   refuses every other option and revision.
4. **Coalescing and deferral.** A trigger joins an in-flight review of its
   key whose heads are not captured yet; after that it is deferred (`BUSY`
   for `tool review`, queued for the pilot) and one new review starts once
   the running one closes.
5. **Pilot.** `review_pilot` is registered on child 14's point (both
   lists), fires on `overlap_cross_run`, `duplicate_task_cross_run` and a
   merge that touches another run (not on `dependency_cycle_cross_run`),
   once per event (one retry after a failed launch, merge events included;
   an abandoned review is not retried),
   through a detached, reaped `cp.py tool review` process that never blocks
   the tick; it closes dead reviews (guarded) with `review_failed`; the
   findings reach each run touched.
6. **Reader.** `reviews.outcome` returns the latest finished outcome for
   that task, kind and head only.
7. **Agents.** Both templates render on both harnesses and are pinned in
   `tests/qs`.
8. **Gates.** 100% coverage of the Control Plane in `tests/qs`;
   `docs/workflow/control-plane.md` updated; `docs/epics/QS-369.md` amended
   (T11b, text only, its SVGs fresh); `check_doc_drift.py` clean;
   `quality_gate.py --impacted` and `--quick tests/qs` pass.
