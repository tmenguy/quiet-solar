# QS-379 — Arm the zero-power charger alert from the first start launch

- Issue: https://github.com/tmenguy/quiet-solar/issues/379
- Lane: feature × product (`area:car`, `area:charger`, `kind:feature`,
  `target:product`, `scale:task`)
- Branch: `QS_379`
- Follow-up 1 of QS-376 (`docs/stories/QS-376.story.md` → "Decisions" →
  Follow-ups, and "Iceberg check").

## Problem

The "There is no power being delivered to the car (<car>) while charging was
expected" alert lives in `QSChargerGeneric.constraint_update_value_callback_soc`
(`ha_model/charger.py`), which `constraint_update_value_callback_percent_soc`
delegates to with `is_target_percent=True`. The alert block is guarded by
`is_target_percent`, a ≥ 5 % SOC gap to the target
(`CHARGER_CHECK_REAL_POWER_MIN_SOC_DIFF_PERCENT`) and
`not car.is_soc_sensor_distrusted()`, and only runs when

```python
self._expected_charge_state.value is True
and self._expected_charge_state.last_ping_time_success is not None
and (time - last_ping_time_success).total_seconds() > CHARGER_CHECK_REAL_POWER_WINDOW_S  # 600 s
```

`QSStateCmd.last_ping_time_success` is set **only** by `QSStateCmd.success()`
(first success) and cleared by `QSStateCmd.reset()`, which `set(True)` calls on
a value change. A start that never succeeds therefore never arms the alert: the
charger keeps `value is True`, `last_ping_time_success is None`, and the
household gets no signal.

QS-376 contained this for OCPP (an unavailable `charge_control` is a fault,
with an alert and a StatusNotification nudge) and made a start-stuck charger
isolate and re-arm through the group for every charger type (F1/F2). But a
**non-OCPP** charger whose start silently never takes effect (the switch
accepts `turn_on`, the charger just never reports enabled) still gives the
user nothing.

## Goal

Arm the zero-power alert from the **first start launch**
(`QSStateCmd.register_launch`), so a start that never succeeds raises the
existing alert once the usual 600 s window has passed — with **no change** for
starts that are confirmed within that window (their reference point stays the
success time).

## Design

### The change (a 3-line addition)

In `QSStateCmd.register_launch(value, time)`, after `self.set(value, time)`
and the counter bump:

```python
# QS-379: arm the zero-power alert from the first launch, so a start that
# never succeeds still gets checked; the first success() overwrites it.
if self.last_ping_time_success is None:
    self.last_ping_time_success = time
```

**Why reuse the field (vs a separate `first_launch_time`).** The alert block
already uses `last_ping_time_success` as its *last check* reference (it writes
`last_ping_time_success = time` after each check, so it re-checks every
600 s). Reusing it keeps the reference and the re-check cadence in one field
and leaves the alert guard untouched; a separate field would need the guard to
read `last_ping_time_success or first_launch_time` and would still have to be
advanced by the alert block. The generic placement in `register_launch` is the
hook the issue names and the smallest diff; the wider arming (every
`QSStateCmd`, every launch value) is **deliberate and accepted**, justified by
the invariant and the reader inventory below, and pinned by AC2.

### Invariant

`last_ping_time_success is None` ⇒ `first_time_success is None`: `reset()`
clears both; `success()` sets both together on the first success; the only
other writers (alert block, amperage ping) write a non-`None` time. So whenever
`register_launch` arms `last_ping_time_success`, the **first** `success()` that
follows still takes its `first_time_success is None` branch and **overwrites**
`last_ping_time_success` with the success time. `success()` is not modified.

### Reader / caller inventory (whole `custom_components/`)

`QSStateCmd` is used only in `ha_model/charger.py` (three per-charger
instances).

- **Callers of `register_launch`:** charge state — `stop_charge` (`False`) and
  `start_charge` (`True`); amperage — `set_max_charging_current`
  (`for_default_when_unplugged is False` only); phases —
  `set_charging_num_phases` (two sites, the second followed by `success()`).
- **Readers of `last_ping_time_success`:**
  - charge state — only the zero-power alert block (the target of this change);
  - amperage — only in the *charging and want to charge* branch of
    `_ensure_correct_state`, right **after**
    `await self._expected_amperage.success(time)`, which overwrites an armed
    value on a first success (invariant) → no behavior change;
  - phases — **no reader** → no behavior change.
- **Readers of `first_time_success`:** amperage only (the
  `last_ping == first_time_success` comparison, same branch, after `success()`).

### Behavior per case

- **Normal start, confirmed within 600 s:** the steady-state branch calls
  `success()` → reference = success time, as today.
- **Stuck start** (never succeeds): reference = first launch time `T0`.
  Retries (`register_launch` at `T0+91/182/273` on the QS-376 7 s grid) do
  **not** move it (same-value `set()` does not reset, and the field is no
  longer `None`). Between the 4th launch and the F2 re-arm the charger is
  isolated from the group budget (QS-376 F1) but **not** faulted:
  `_expected_charge_state.value` stays `True` (only F2 sets `False`), and
  `is_load_active(time)` stays `True` (only `is_charger_faulted` flips it), so
  `Home` keeps calling `update_live_constraints` → the SOC update callback every
  load-management cycle. The alert block becomes eligible at the first cycle
  `> T0 + 600 s` (`T0 + 602` on the 7 s grid), before the F2 re-arm at
  `T0 + 1176 s` (4th launch + `CHARGER_START_RETRY_REARM_S`).
- **Retarget during launches** (`register_launch` with a different value):
  `set()` resets first, so the new command is re-armed at its own first launch.
- **F2 re-arm** (`set(False)` + `success()`): the target leaves `True`, the
  block is not entered while idle; the next budgeted start (`apply_budgets` →
  `set(True)` → `QSStateCmd.reset()`) re-arms from its own first launch.
- **Stop launches** (`register_launch(False)`): arms on a `False` target; the
  alert requires `value is True` → no effect; a later `set(True)` resets it.
- **OCPP charger flagged faulted** (QS-376 F3): `is_load_active` is `False`, so
  `Home` skips `update_live_constraints` → the SOC callback (and the zero-power
  block) never runs → only the QS-346 fault alert is sent, no double alert.
  An OCPP stuck start that is **not** faulted gets the zero-power alert, like a
  generic charger.

### Notifications and the car card (decided)

The existing block notifies only when `possible_charge_error_start_time` is
`None` and sets it. That attribute lives on the charger (not on `QSStateCmd`),
so it survives `QSStateCmd.reset()`, the F2 re-arm and a new stuck round. It is
cleared only by a power-OK check with target `True`, or by
`QSChargerGeneric.reset()` (reset button / disable / unplug path).

- **One notification per stuck episode**, however many F2 rounds follow.
- The car card keeps showing `CAR_CHARGE_NO_POWER_ERROR` between the re-arm and
  the next start — **deliberate**: the last start did fail, and the error clears
  at the next check that sees power. Pinned by AC3.

### Out of scope

- Energy-mode (non-SOC) constraints: the alert block is SOC-only; not extended.
- Clearing `possible_charge_error_start_time` on the F2 re-arm (kept visible,
  see above).
- QS-376 follow-ups 2 and 3.

## Acceptance criteria

1. **AC1 — arm at first launch.** On a fresh `QSStateCmd` (via
   `tests/factories.py::create_state_cmd()`):
   (a) `register_launch(True, t0)` → `last_ping_time_success == t0`;
   (b) `register_launch(True, t1)` → still `t0`;
   (c) `register_launch(False, t2)` (retarget) → `t2`; then `set(True, t3)` →
   `None`; then `register_launch(True, t4)` → `t4`.
2. **AC2 — success still wins (regression pin).** After
   `register_launch(v, t0)` then `success(t1)`:
   `first_time_success == last_ping_time_success == t1`.
3. **AC3 — stuck start raises the alert once per episode.** On the QS-376
   V-generic stuck state (`_build_stuck_charger(switch_state="off")`, the OCPP
   fixture, not faulted), driving `stuck.ensure_correct_state(t)` then the
   callback at the same `t` on the 7 s grid from `T0`:
   - after `T0`, `_expected_charge_state.last_ping_time_success == T0` and stays
     `T0` through the 4 launches; `stuck.is_load_active(t) is True` and
     `_expected_charge_state.value is True` until `REARM`;
   - no alert at any `t ≤ T0 + 600 s`;
   - at the first cycle `> T0 + 600 s` (`T0 + 602`, `< REARM`):
     `possible_charge_error_start_time` is set, `on_device_state_change` awaited
     once with `device_change_type=DEVICE_STATUS_CHANGE_ERROR` and a message
     containing the car name, `get_charge_type()[0] == CAR_CHARGE_NO_POWER_ERROR`,
     and `last_ping_time_success` advanced to that cycle;
   - after `REARM` + `group.apply_budgets` (second stuck round, as in
     `test_stuck_start_rearms_through_the_group`): the new first launch re-arms
     `last_ping_time_success` at `t_apply`; the round-2 check at the first cycle

     **not** notify again (`on_device_state_change.await_count == 1`);

## Risks

- **New alerts where there were none** (the feature): any charger whose start
  never takes effect for > 10 min on a SOC car ≥ 5 % from its target alerts,
  with the existing text.
- **Late confirmation**: a start that is confirmed only after 600 s (slow
  charger, lagging state sensor), or that stays behind a gate of
  `_ensure_correct_state` that skips the charge-state `success()` (state reset,
  pending reboot, phase mismatch) for > 600 s with zero power, now alerts once.
  Accepted: zero power for 10 min with the target `True` is a real
  non-delivery; the error clears at the next check that sees power (the first
  `success()` moves the reference to the success time).
- **Timing**: one ~574 s alert window per stuck round (T0+602 … REARM); AC3
  pins it.
