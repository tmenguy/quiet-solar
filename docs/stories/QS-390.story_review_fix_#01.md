## Findings to fix

### [should-fix] S1 — F1 margin skip drops a user override's runtime
- File: `custom_components/quiet_solar/ha_model/bistate_duration.py:1130-1132`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: before the PR, `saved_runtime = max(current_value)` over ALL
  constraints, and the code comment says an override counts toward the daily
  target. The new `end_of_constraint <= cycle_end_limit` skip also applies to
  USER_OVERRIDE constraints. Example: pool in auto, an override ends at 14:00
  with 1h58 run, and the user switches the mode string at 13:57. The override
  is skipped, `saved_runtime` is 0, and the pump runs up to the override
  duration longer than it did before the PR. While an override runs, its
  runtime is not mirrored in the auto constraint (`update_live_constraints`
  only updates the first active constraint).
- Proposed fix: do not apply the margin skip to override-originated
  constraints. Reuse the override predicate already used in this block; a small
  local helper is fine if it keeps the code clear, but no refactor beyond that.
  The #390 rollover is unaffected: at rollover `mode_changed` is False unless
  the mode string also changed, so overrides never feed `saved_runtime` there.
- Test: a regression test in `tests/test_coverage_bistate_duration.py` for an
  override that ends within the margin, a mode-string switch, and the override
  runtime carried (`saved_runtime == override current_value`, capped as the code
  already caps it). Write it red first against the current PR head, record the
  verbatim red, then fix.

### [nice-to-have → fix] N1 — margin skip drops same-cycle runtime on a same-end mode switch
- File: `custom_components/quiet_solar/ha_model/bistate_duration.py:1130-1132`
- Severity: nice-to-have (fixed: this PR introduced the regression)
- Source: qs-review-edge-case-hunter
- Description: the skip also removes a constraint whose `end_of_constraint` is
  in `new_ends`, i.e. the CURRENT cycle, not the finished previous one. Example:
  finish 00:00, auto 12h target with 5h run, and the user switches to winter
  (4h, same 00:00 end) at 23:57. Before the PR the carry `min(5h, 4h)` made the
  new constraint met. Now it starts at 0 and forces the pump ON for the last
  ≤5 min, so the cycle ends unmet.
- Proposed fix: narrow the skip to
  `c.end_of_constraint <= cycle_end_limit and c.end_of_constraint not in new_ends`
  (plus the S1 override exemption). This still covers the #390 rollover (the old
  end is never in the next day's `new_ends`) and T1b (the ON-mode end is the
  next midnight, not 07:00). Also update the QS-390 comment on
  `_CYCLE_END_MARGIN` / at the skip site so it describes the narrowed rule.
- Test: a regression test for the same-end, mode-string switch within the margin
  (runtime carried, new constraint met). Red first, then fix. All existing T1*
  tests must stay green.

### [nice-to-have → fix] N2 — F2 fallback can pick a step above the minimum
- File: `custom_components/quiet_solar/home_model/constraints.py:2262-2269`
- Severity: nice-to-have (fixed: new code in this PR, conservative clamp)
- Source: qs-review-edge-case-hunter
- Description: after the headroom-free recompute, `j` comes from
  `available_power` with no headroom cap. A multi-step `num_max_on_off` load in
  a forced-ON hold slot could get a higher step than the exhausted headroom
  allows, not just the minimum needed to keep the hold.
- Proposed fix: in the F2 fallback branch only, keep just the smallest command
  (`power_sorted_cmds = power_sorted_cmds[:1]`, after checking the list is
  sorted ascending, which `_get_lower_consign_idx_for_power` implies) so the
  hold is kept at the minimum step. Only when the recompute returned a
  non-empty list.
- Test: a test in `tests/test_solver.py` (or the existing constraints test
  module used by T2) with a multi-step, `num_max_on_off` load, `support_auto`
  False, exhausted headroom and solar surplus in a forced-ON slot. Assert the
  slot command is the minimum step. Red first, then fix.
