## Findings to fix

### [should-fix] R3-S1 — the CodeRabbit skip rule contradicts itself (template and docs)
- File: `scripts/qs/agent_templates/qs-node.md.j2:555-579` ("Between loop calls" and the end-of-wait sentence),
  `:370-373` (the catch-up paragraph); `docs/workflow/control-plane.md:676`
- Severity: should-fix
- Source: qs-review-blind-hunter and qs-review-edge-case-hunter, merged. The acceptance auditor raised the catch-up
  sentence as a nice-to-have.
- Description: the bullet says "**only** an answer still `BUSY` past [[ crwait ]] s since `cr_from`" skips. The
  end-of-wait clause skips a `BUSY` `cr: trigger` as soon as CI is terminal, whatever the time. The wait also ends
  on "CI terminal and `cr` no longer `pending`", so a `trigger` does not hold the wait at all. A node gets two rules;
  following the doc leaves `cr: trigger` unresolved when the round moves on. Fix plan #02's wording introduced this.
- Proposed fix — **one rule everywhere, the window applies to `trigger` too**:
  - The wait ends when CI is terminal **and `cr` is neither `trigger` nor `pending`**.
  - In `cr: trigger` / `cr: pending`, the tool is always re-called first. A still-`BUSY` answer turns `cr` into
    `skipped` only past [[ crwait ]] s since `cr_from`:
    - "CodeRabbit trigger failed" for `trigger`;
    - "CodeRabbit skipped: no review in time" for `pending`.
  - The other skip paths are unchanged: "any other error" and "head moved".
  - Drop the CI-terminal special case.
  - In the catch-up paragraph (~:370-373), say the same: "…until it settles, or a re-call past [[ crwait ]] s since
    `cr_from` still answers `BUSY`".
  - Bound: "each window is checked between loop calls, so a round waits about 2×`CR_WAIT_S` for CodeRabbit (plus at
    most one loop cap per window)". This also covers the edge-case hunter's poll-gap nice-to-have.
  - Mirror the rule in `control-plane.md:676`.
- Tests (`tests/qs/test_render_agents.py`):
  - update `test_node_bounds_an_unanswered_trigger_by_the_coderabbit_wait`,
    `test_node_re_calls_the_coderabbit_tool_before_skipping_it` and
    `test_node_says_the_coderabbit_wait_is_at_most_two_windows`;
  - pin the new end condition ("neither `trigger` nor `pending`");
  - assert the CI-terminal skip sentence ("whose re-call still answers `BUSY` becomes") is gone;
  - pin the catch-up wording.

### [should-fix] R3-S2 — plan-concrete's "a create-target that already exists" misfires on a re-plan during build
- File: `scripts/qs/agent_templates/qs-node-plan-concrete.md.j2:65-67`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: the reviewer is also launched in a plan loop that runs after build has started:
  - a plan-level `fix` during build (qs-node.md.j2 ~:673-679);
  - a split with code already written (~:622-627).

  It receives the full plan. By then every file the plan creates exists on the branch, so each one gets a false
  `should_fix` and the re-plan cannot converge. Fix plan #02's polish introduced this.
- Proposed fix: limit the rule to files that already exist **at the task's base** (`git merge-base origin/main HEAD`),
  not files this task's own commits created. Suggested wording: "A create-target that already exists at the task's
  base (`git merge-base origin/main HEAD`) — not one this task's own commits created —: `should_fix` (the plan must
  say "modify")". Pin it in `test_plan_concrete_file_specificity_agrees_with_create_targets`.
