## Findings to fix

### [should-fix] S1 — `sync_body` split-block fix fails when the owned block comes first
- File: `scripts/qs/epic_doc.py` (~739–758, `sync_body`)
- Source: qs-review-edge-case-hunter (reproduced)
- Description: if the `(not filed)` block sits directly under
  `## Children` and the task-line block follows after a blank line, the
  anchor is the second block. `_owned_by_heading(anchor)` then returns
  False, so nothing is stripped and `owned=[]`.
  - Repro body: `"Intro\n\n## Children\n\n- (not filed) B\n- (not filed) C\n\n- [ ] #371 — A\n"`
  - Repro rows: A=#371, B=#380, C unfiled.
  - Effect: B ends up listed both as unfiled and as filed, and the state
    never self-heals.
- Proposed fix: decide ownership for the whole section. When the anchor is
  one of the section's blocks, set
  `is_owned = any(_owned_by_heading(content, s) for s, _ in section_blocks)`.
  Add the reversed-order body as a test and assert the second run is a no-op.

### [should-fix] S2 — `land` preflight skips the issue's own doc when it lacks an exact `## Decomposition` heading

### [should-fix] S3 — A branch mismatch still force-removes the worktree
- File: `scripts/qs/cleanup_worktree.py` (~266–282)
- Source: qs-review-edge-case-hunter + qs-review-blind-hunter (deduplicated)
- Description: fix #01 S3(d) detects that the worktree is on a branch other
  than `QS_<issue>`, but it only skips the branch delete. The wrong worktree
  is still removed with `--force` and an `rmtree` fallback. In the worst
  case, a `--work-dir` pointing at the main checkout gets rmtree'd.
  Separately, when `_current_branch` returns `None`, the guard is skipped
  and the branch is deleted anyway.
- Proposed fix:
  - On a mismatch, return `status: "error"` with the mismatch detail
    **before** `remove_worktree`. Touch nothing.
  - Treat detached `HEAD` or a `None` branch as "unknown":
    - Confirm ownership through
      `git -C <main_wt> worktree list --porcelain`. The entry whose
      `worktree` path equals `work_dir` must carry
      `branch refs/heads/QS_<issue>`, or be detached.
    - If ownership is confirmed or the entry is detached, proceed with
      removal but keep the branch when it is unknown.
    - If the entry names another branch, refuse.
  - Add tests for a mismatch (worktree survives), detached HEAD, and an
    unreadable HEAD.

### [should-fix] S4 — The dir-gone retry path bypasses the safety guards, and a missing branch is reported as "kept"
- File: `scripts/qs/cleanup_worktree.py` (~145–177 `_retry_branch_delete`,
  ~163–168, ~287–296)
- Source: qs-review-acceptance-auditor (reproduced) + qs-review-blind-hunter
  + qs-review-edge-case-hunter (deduplicated)
- Description:
  - (a) With the directory gone, `--issue 78` deletes an unrelated `QS_78`
    branch. There is no mismatch check, and `--force` is not required.
  - (b) If `branch -D` fails with "not found" (the branch is already gone,
    e.g. on a re-run after a fully successful first run), the result is
    `removed-branch-kept`, which is false.
  - (c) If the work dir is a typo while the real worktree is still alive,
    `branch -D` fails with "checked out at…", yet the status is reported as
    "worktree already gone".
- Proposed fix:
  - The retry path requires `--force`. Without it, keep the old
    "does not exist" error.
  - Before `git worktree prune`, find the porcelain registration for
    `work_dir`:
    - If it names a branch other than `QS_<issue>`, refuse.
    - If there is no registration at all, refuse the delete. Nothing proves
      the dir belonged to `QS_<issue>`. Report
      `removed-branch-kept` with an explanatory `branch_delete_error`.
  - Before `branch -D`, check
    `git rev-parse --verify --quiet refs/heads/QS_<N>`. If the branch is
    absent, report `branch_deleted: true` and `branch_absent: true` with
    status `removed`.
  - When `QS_<N>` is checked out in another worktree, return a distinct
    status `branch-checked-out-elsewhere`, and handle it in the finish
    template.
  - Drop the unused `issue` parameter.
  - Add tests: gone-dir mismatch, gone-dir without `--force`, gone-dir with
    no registration, branch already absent, and branch checked out
    elsewhere.

### [should-fix] S5 — The finish-task epic status probe doesn't handle a refusal
- Files: `scripts/qs/agent_templates/qs-finish-task.md.j2` (~101–108),
  `docs/workflow/lanes/epic-factory.md` (~232, same rule)
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter (deduplicated)
- Description: the template only branches on `safe_to_discard: true` versus
  "otherwise ask Force-delete". A refusal such as `git-error` (offline),
  `undecodable`, or `lookup-failed` carries none of those fields. The user
  is asked to force-delete without seeing what would be lost, and could
  lose an unlanded draft.
- Proposed fix: add a bullet saying that if the probe JSON `status` is not
  `ok`, the agent must STOP, show the JSON, and never offer force-delete
  without a successful probe. Restrict "Otherwise" to `status: ok` with
  `safe_to_discard: false`. Mirror this in the lane doc. Pin the rule in
  `tests/qs/agents/test_lane_steps_parity.py`
  (`test_finish_task_case_a_has_the_epic_variant`, or a sibling test), and
  also pin the `removed-branch-kept` / `branch-checked-out-elsewhere`
  handling.

### [should-fix] S6 — The setup-task parent-epic backfill can overwrite the issue body
- File: `scripts/qs/agent_templates/qs-setup-task.md.j2` (~141–143)
- Source: qs-review-coderabbit
- Description: the template says "`### Parent epic` … appended to the body
  via `gh issue edit {{N}} --body ...`". But `--body` replaces the whole
  body, so an agent following this literally can wipe the issue text.
- Proposed fix: spell the procedure out:
  - Fetch the current body with `gh issue view {{N}} --json body --jq .body`.
  - Append `\n\n### Parent epic\n#{{epic}}\n`.
  - Write the result to a temp file outside the worktree.
  - Run `gh issue edit {{N}} --body-file <tmp>`.
  - Remove the temp file.

  Re-render the agents, then run `--quick tests/qs`.
