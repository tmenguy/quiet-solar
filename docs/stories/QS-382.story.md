# QS-382 — Spike: prove the mechanisms an orchestrator over parallel sessions needs

Issue: [#382](https://github.com/tmenguy/quiet-solar/issues/382) ·
Lane: feature × factory · Target: factory ·
Parent epic: [#369](https://github.com/tmenguy/quiet-solar/issues/369) —
[`docs/epics/QS-369.md`](../epics/QS-369.md) ("The orchestrator session",
"Mechanisms available", "Child scopes" → 4)

## Problem

Epic #369 plans a second pipeline: **one orchestrator GUI session** that
drives one background session ("node") per deliverable, each in its own
worktree, in parallel.

Several of the Claude Code features that design needs are **not verified**
(epic, "Mechanisms available → Not verified"):

- whether a `--bg` session can be brought into the desktop app;
- whether `SendMessage` reaches a running `--bg` session, or wakes a
  reopened GUI session;
- whether `--model` at spawn beats an agent's frontmatter model.

Others are documented but untested on this repo:

- `SessionStart` hooks in the GUI;
- a GUI session spawning `claude --bg` through Bash;
- a background task's exit waking an idle GUI session;
- background sessions under a permission mode;
- CI remediation with no human relay.

Children 5–13 are built on these assumptions. If one fails, the epic has to
be re-planned before any of that work starts.

## Goal

Run the orchestrator-over-nodes pattern **for real, once**, with throwaway
prototypes, on two real product deliverables in parallel on Claude Code.
For each of the 8 mechanisms in the table below, record what works, what
needs a workaround, and what fails.

**No threshold is set in advance: the maintainer judges go / no-go on the
results.** The spike proves **mechanisms, not the design**.

## Mechanisms (the issue's numbering)

| # | question | exercised in | "works" means |
|---|---|---|---|
| **1** | Can a GUI orchestrator on the hand-pinned main checkout launch one `claude --bg --agent` node per deliverable, each in its own worktree, with no tracked change on main? | R1, R2 | Both nodes run with their worktree as cwd. The evidence is the `claude agents --json` field recorded in P5; the fallback evidence is each node's `start` event `pwd`. `git -C <main> status --porcelain` is empty while they run |
| **2** | Does a node run its own sub-agents and return a compact result? | R3 | The node transcript shows parallel reviewer sub-agent calls, and a compact result arrives |
| **3** | Do messages go both ways? | R3, R4, R5, R9 | **3a** node → orchestrator; **3b** orchestrator → idle node; **3c** orchestrator → node **mid-turn** (pass criterion in R4); **3d** a node's `SendMessage` wakes a reopened GUI orchestrator with no human prompt. "Delivered" always means a receiver-side `received` event with the sender's `msg_id` and `via: sendmessage` |
| **4** | Is a CI failure the spike injects — a real Linux-only defect whose fix is a code change — read from the log, fixed and pushed with no maintainer input? | R6–R8 | Red run → the node reads `--log-failed` → an allowed fix → green run, with zero maintainer messages between the red and the green. The allowed fixes are correcting the path, or renaming the fixture to match. A skip, a deletion or a revert is recorded as an evasion. If the watcher's exit does not wake the idle GUI (see P7) and a maintainer nudge is needed, the score is `works with workaround` / `manual-per-round` |
| **5** | Does a killed orchestrator resume from its state, with a `SessionStart` hook injecting a summary? | R9 | A **new** GUI session on main gets the summary. It rebuilds the run from the state store alone: nodes, PRs, CI, open questions. It restarts `watch.py`, and acts on every event emitted between the kill and its start. A node's next message reaches **this** session |
| **6** | Closed mid-run and reopened: do the nodes keep working until they need the orchestrator, and does it pick up with nothing lost? | R5 | The nodes progressed while it was closed, and every node event emitted during the close is acted on after the reopen |
| **7** | Can a node session be brought into the desktop app (`/resume`, `/desktop` from `claude attach`)? | P6 (probe session) | Recorded either way |
| **8** | Measured, no threshold | P5, R10 | **8a** the orchestrator's context over the run; **8b** the total token cost; **8c** the node result sizes; **8d** whether `--model` at spawn beats the frontmatter |

**Outcomes:** `works` / `works with workaround` / `fails` /
`not tested — <why>`.

**Workaround tags** (exactly one per workaround):

- `hand-off` — a new session is needed to continue;
- `file-relay` — the maintainer carries a plan or file between sessions;
- `manual-per-round` — a human step is needed for each round or event;
- `one-time` — setup only;
- `none`.

Only the first three count against the design (issue: "reported as such").

**Optional extras** — not mechanism rows. If skipped or aborted they are
simply absent, never `not tested`:

- `/resume` of the killed session after R9;
- whether CodeRabbit reviews a draft PR, if noticed.

**Also observed** — one line each in the results, not acceptance criteria:

- the permission mode the nodes actually needed;
- `setup_task.py`'s side effects in the new worktrees (see R2);
- the permissions Claude Code added to main's `settings.local.json` during
  the run (`settings-drift.diff`);
- the orchestrator copying the node agent itself: the issue says "by hand",
  and a failed copy falls back to a hand copy tagged `one-time`;
- the `charger.py` catch-up after the first merge (F3).

## Design

### Actors and sessions

**Operator** — this task's implement session (`qs-implement-setup-task`), in
worktree `QS_382`.

- It writes the kit, runs the read-only checks (`gh`, and `git -C <main>`
  status and ref reads), keeps `RUNLOG.md`, runs `measure.py`, writes the
  results and opens this PR.
- It **edits only its own worktree**.
- Every command that runs on the main checkout, in another worktree, or
  starts a Claude session, it **prints for the maintainer**.

**Maintainer** — GUI and terminal. He:

- runs the printed commands: the pin, the agent copies, the probe sessions
  and `inject.sh`;
- opens, closes, reopens and kills the GUI;
- approves the plans in the orchestrator;
- triggers R4;
- tests `attach` / `/desktop`;
- decides the abort, the cut-off, the go / no-go and the merges.

**Orchestrator** — a true GUI session on the main checkout, pinned by hand
to `qs-spike-orchestrator`; "one voice".

**Nodes ×2** — `claude --bg --agent qs-spike-node`, one per deliverable, in
worktrees `QS_379` and `QS_381`.

The operator is **experiment scaffolding**, not part of the pipeline under
test:

- The maintainer's R-steps are setup, fault injection (R4 trigger,
  `inject.sh`), fault simulation (close, kill) or measurement.
- None of them relays plans, fix plans or files between the orchestrator and
  the nodes.
- If a per-round step does need a human, it is tagged `manual-per-round`.

**How the implement phase spans the run.** The operator's work spreads over
several `qs-implement-setup-task` sessions, which the maintainer relaunches
whenever the run needs them: session A, logging during the live run, and
session B.

- Each session resumes from `$KIT/RUNLOG.md` (the checklist of P-, R-, F- and
  B-steps with evidence and times), `$KIT/ARTEFACTS.md` and the state store.
- **No review handoff is emitted until B4.**

### The kit — `$KIT = <QS_382>/var/qs-spike-382/`

This is throwaway, out-of-PR scaffolding: removed after the run, never
committed.

- `var/` is gitignored (`.gitignore` l.21), so nothing under
  `var/qs-spike-382/**` can reach this PR's diff.
- Everything the kit holds is **experiment scaffolding**, authorised by this
  plan in the operator's own worktree.
- **The main checkout gets only two things,** both written by the maintainer
  from printed commands:
  - `<main>/.claude/agents/qs-spike-orchestrator.md` (covered by
    `.claude/agents/*.md`);
  - edits to `<main>/.claude/settings.local.json`.
- `render_all` only writes the files it renders and never deletes anything
  (`render_agents.py` l.404-432), so hand-copied agents survive every
  re-render.
- **Size bound:** each script is a single file, standard library only, with
  no CLI framework, no config and no retries beyond what its step needs.
  Anything larger means the spike has started building the pipeline instead
  of probing it.

| file | role |
|---|---|
| `agents/qs-spike-orchestrator.md`, `agents/qs-spike-node.md` | The prototype agent sources (frontmatter below). |
| `emit.py` | **The only writer of `events.jsonl`.** It appends one JSON line `{ts, msg_id, from, deliverable, kind, channel, payload}`, opened with `O_APPEND` and held under `fcntl.flock`. It prints the `msg_id` (a uuid4). Both agents are told never to write the file any other way. |
| `state.json` | The orchestrator's view: deliverables, node ids and names, phase, PR, CI head and status, open questions, and `orchestrator.session_id` (the **current** target for node messages) with its history. Written **only by the orchestrator** and its `SessionStart` hook. |
| `events.jsonl` | Append-only evidence, and the fallback channel (see "Messaging"). |
| `summary.py` | The `SessionStart` hook command. It reads the hook's stdin JSON (`session_id`, `source`), sets `orchestrator.session_id` in `state.json` (appending the old id to the history), and emits `orch-start`. It prints a summary: the state, the events since the last `orch-turn` marker, and **always** the last 20 events, so a stale marker after a kill loses nothing. |
| `watch.py` | Run by the orchestrator with `run_in_background`. It snapshots a baseline, polls every 60 s, and exits with a one-line reason on either: (a) a new head SHA on a watched PR, or a watched check reaching a **terminal** state (success / failure / cancelled); or (b) new lines in `events.jsonl` past the baseline. A move from pending to in-progress does not wake it. For a failure it prints the run id, parsed from `gh pr checks <PR> --json name,state,link` (`/actions/runs/<id>/`). |
| `inject.sh` | The maintainer-run CI-defect injection (see below). |
| `measure.py` | Written in **P8**, after P5 has shown the transcript format (see "Measurements"). |
| `pr-body-<N>.md` | Draft-PR bodies, written by the orchestrator. |
| `settings.local.json.bak`, `settings-drift.diff` | The backup of main's pin file, and its diff taken just before the restore. |
| `ARTEFACTS.md`, `RUNLOG.md` | The cleanup checklist and the run log. |

**Why no tests.** These prototypes are never committed: they live in ignored
paths and are deleted after the run.

- TDD and the 100% coverage rule apply to committed code (coverage is scored
  on `custom_components/quiet_solar`), and this PR commits only docs.
- **The operator writes no red test for the kit scripts.** This is the
  explicit exemption for this story.
- The deliverables' code is written by the nodes under the frozen rules:
  TDD, and `--impacted` before every push.

**Outside the template / model policy on purpose.** The two prototype agents
are hand-written `.md` files, never rendered from `agent_templates/*.j2`, and
their frontmatter model is hand-set. This is deliberate: they are throwaway,
and `render_agents.py` neither renders them nor needs a `models.py` row for
them.

### Main's pin (written by the maintainer, removed at R11)

1. Back up the file:

   ```bash
   cp <main>/.claude/settings.local.json <KIT>/settings.local.json.bak
   ```

2. Merge these keys into `<main>/.claude/settings.local.json` (absolute
   paths, because `$KIT` is not expanded in settings). The existing
   `permissions.allow` entries stay as they are:

   ```json
   {
     "agent": "qs-spike-orchestrator",
     "hooks": {"SessionStart": [{"hooks": [{"type": "command",
       "command": "python3 <QS_382>/var/qs-spike-382/summary.py"}]}]},
     "permissions": {"additionalDirectories": ["<worktrees root>"]}
   }
   ```

   The hook runs the system `python3` (the scripts are standard library
   only). `additionalDirectories` lets the orchestrator `cd` into the
   deliverable worktrees and reach `$KIT`; it is tagged `one-time`.

**While the pin is on (R1 → R11), every bare session on main boots as the
orchestrator and runs the hook.** So no other work happens on main in that
window. R11 removes the pin before the frozen path, which works on main.

### Prototype agents (the operator writes them in P4)

**Frontmatter.** Both omit `tools:`, so every tool is inherited, including
`SendMessage` and `Agent`. The frozen agents' `tools:` line has no
`SendMessage`; copying it would break mechanism 3 through setup, not the
harness.

```yaml
---
name: qs-spike-orchestrator
description: QS-382 spike orchestrator (throwaway; main checkout, GUI).
---
```

The GUI picker decides the orchestrator's model, so there is no `model:`
line.

```yaml
---
name: qs-spike-node
description: QS-382 spike node (throwaway; one deliverable worktree, background).
model: claude-opus-5-5
---
```

#### `qs-spike-orchestrator` (main checkout, GUI)

**Every turn** starts by reading `state.json` and the new `events.jsonl`
lines. It ends with `emit.py --kind orch-turn`.

**Writes.** It never writes a tracked file on main. Its only writes are:

- `$KIT` (state, events, PR bodies);
- the node agent copies;
- `setup_task.py` runs;
- the draft PRs.

**Launch.** For each deliverable:

1. From main:

   ```bash
   python scripts/qs/setup_task.py <N> --title "$(gh issue view <N> --json title -q .title)" --next-cmd /create-plan
   ```

   Record its JSON, including the launch-script paths (`new_context`,
   `pycharm_context`, `pycharm_applescript_context`, under `$TMPDIR`).
   `setup_task.py` only **writes** these scripts; it never starts a session.
2. Copy `$KIT/agents/qs-spike-node.md` into `<wt>/.claude/agents/`.
3. Spawn the node:

   ```bash
   cd <wt> && claude --bg --agent qs-spike-node --permission-mode auto --add-dir <KIT> -n qs-spike-<N> "<spawn prompt>"
   ```

4. Record the printed id in `state.json`.

The spawn prompt carries the issue number, the lane, and the absolute `$KIT`
path. It tells the node to **re-read `orchestrator.session_id` from
`state.json` before every `SendMessage`**.

**Fallback** (maintainer decision): if `auto` blocks the node on a prompt it
cannot pass (visible in `claude logs <id>`), `claude stop` it and respawn it
with `--permission-mode bypassPermissions`. This is recorded.

**Relay only.** It forwards node plans and questions to the maintainer and
sends back his answers.

- The gate and triage are **pre-approved** in the spawn prompt, so the only
  relays are plan approvals and true exceptions.
- It makes no design judgement of its own in this spike.

**Draft PRs.** When a node reports "pushed, local gate green", the
orchestrator:

1. Writes `$KIT/pr-body-<N>.md` in `create_pr.py`'s shape:
   - a summary from the node's result;
   - `Fixes #<N>`, plus `Refs #<epic>` if `targets.parse_parent_epic` finds
     one;
   - the Testing / Code quality / Risk checkboxes, from the node's gate
     result;
   - the Lane note;
   - a `## Doc maintenance` justification when the node's `doc_drift` says
     drift.
2. Opens the PR:

   ```bash
   gh pr create --draft --base main --head QS_<N> --title "QS-<N>: <issue title>" --body-file <KIT>/pr-body-<N>.md
   ```

   `QS_<N>` is already on origin (`worktree-setup.sh` pushes it at
   creation).

The PR is a draft from its first second. pr-quality runs on `opened`,
`synchronize` and `reopened` with no draft filter (`pr-quality.yml` l.3-6).
`ready_for_review` re-runs nothing.

**CI and wake-ups.** It restarts `watch.py` after each PR it opens and each
node push report. When the watcher exits:

- on a **red check**, it sends the node the PR number, the failing run id
  and "read the log, fix with a code change, gate, push" (emits `ci-red`);
- on a **head move with no node event** (for example the `inject.sh` push),
  it emits `head-moved` and sends nothing;
- on an **event line**, it acts on the event;
- in every case, it restarts the watcher.

**Mid-turn message (R4).** On the maintainer's request, it sends one
harmless message to a working node: "emit a `progress` event with your
current step".

#### `qs-spike-node` (each deliverable worktree, background)

It reads the frozen agents rendered in its own worktree
(`qs-create-plan.md`, then `qs-implement-task.md`) and follows them, with
these changes.

**Keeps:**

- `context.py`;
- the analysis;
- `check_doc_drift.py`, in the plan and in implement;
- one review round with the 4 `qs-plan-*` global reviewers **in parallel**
  as its own sub-agents (mechanism 2);
- the story file committed on its branch;
- TDD;
- `python scripts/qs/quality_gate.py --impacted` before **every** push;
- the implement commit (`git add custom_components/quiet_solar/ tests/ docs/stories/`);
- `git push -u origin QS_<N>`.

**Replaces with a pre-approved "yes":**

- "write it";
- triage ("fix all valid findings");
- "Ready to run the quality gate?".

**Replaces with a plan summary, then waits for approval:**

- FINALIZE. It then goes **straight to implement**; create-plan's
  "Determine NEXT_PHASE" step is dropped.

**Replaces with a `question` event, then waits:**

- every other "ask the user" turn;
- the lane-FAIL path;
- create-plan's target-label stop.

**Never runs:**

- `next_step.py`, `render_agents.py`, `setup_task.py`,
  `cleanup_worktree.py`, `create_pr.py`;
- `quality_gate.py --seed-testmon`;
- `gh issue edit`;
- any launcher;
- a terminal or any other session.

**Compact result**, sent by `SendMessage` and mirrored with
`emit.py --kind result`:
`{deliverable, phase, status, branch, head_sha, story, gate, doc_drift, questions[], notes}`.
"≤ 15 lines" is a prompt constraint, not a threshold; the real size is
measured (8c). Its first event is `start`, carrying its `pwd` and session id.

**On "CI red":**

1. `gh run view <run> --log-failed`;
2. diagnose;
3. make a **code change**;
4. `--impacted`, push, compact result.

### Messaging

- **Primary channel:** `SendMessage`, to the id currently in `state.json`.
- **Mirrored in `events.jsonl`:** only results, questions and CI events,
  each with a `msg_id`, and with `channel` set to `sendmessage-attempted` or
  `log-only`.
- **Delivery is proven by the receiver, not the sender.** On acting on a
  message, the receiver emits `received {msg_id, via: sendmessage|log}`. So
  a lost `SendMessage` shows up as `via: log` or as no `received` line at
  all.
- **If `SendMessage` cannot address a `--bg` session or the GUI session,**
  these fallbacks are recorded:
  - orchestrator → idle node: `claude --bg --resume <id> "<msg>"`;
  - node → orchestrator: the log alone, woken by `watch.py`.

### The run

#### Operator session A — preflight and kit

**P1 — CLI.** `claude --version` is at least 2.1.280
(`models.CLAUDE_CLI_FLOOR`). The permission modes in `claude --help` include
`auto` and `bypassPermissions`. `claude-opus-5-5` and `claude-sonnet-5` are
in `models.HARNESS_MODELS["claude"]`.

**P2 — Main clean.** `git -C <main> status --porcelain` is empty, and after
`git -C <main> fetch`, `git -C <main> status -sb` is neither behind nor
ahead.

**P3 — Deliverables**, for each N:

- `gh issue view N --json state,labels`: `OPEN`, exactly one `kind:*`,
  `target:product`, not `scale:epic`;
- `grep -rlnE "QS-<N>|qs<N>" <main>/custom_components <main>/tests <main>/docs/stories`
  is empty (the check that caught #352);
- no `QS_<N>` worktree exists;
- `git -C <main> show-ref --verify refs/heads/QS_<N>` fails;
- `git ls-remote --heads origin QS_<N>` is empty.

**P4 — Write the kit** (without `measure.py`), then dry-run it:

- `summary.py` on an empty store, and on fake events plus a fake stdin JSON;
- `watch.py` against the merged PR #384, with a short timeout.

**P5 — Probe session** (maintainer, in a terminal, from printed commands):

1. Set up the probe folder:

   ```bash
   PROBE=$(mktemp -d) && mkdir -p $PROBE/.claude/agents && cp <KIT>/agents/qs-spike-node.md $PROBE/.claude/agents/
   ```

2. Run 1, the control (frontmatter only):

   ```bash
   cd $PROBE && claude --bg --agent qs-spike-node --permission-mode auto --add-dir <KIT> -n qs-spike-probe "Run python3 <KIT>/emit.py --from probe --kind dry. Say whether the SendMessage tool is available to you. Reply done."
   ```

3. Run 2 is the same with `--model claude-sonnet-5 -n qs-spike-probe-model`.

The operator records:

- whether `auto` let the append through;
- whether `SendMessage` is available;
- the `claude agents --json` schema (the field names for id, cwd and busy /
  idle);
- where each `--bg` transcript lands, and its `usage` and `model` fields;
- **8d**, from the two `model` fields.

**P6 — Mechanism 7** (maintainer), on `qs-spike-probe`, never on a live
node: `claude attach <id>`, then `/desktop`; separately, the desktop app's
`/resume` picker. The result is recorded, then `claude stop`.

**P7 — GUI wake probe** (maintainer):

1. In a throwaway GUI session (any folder that is not main), ask it to run

2. Record whether a turn starts with no input.

This scores the watcher's role in mechanisms 4, 5 and 6 up front.

**P8 — `measure.py`.** Write it from P5's findings, and dry-run it on the

**P9 — Pin and agent copy.** The maintainer runs the printed pin-backup,

#### Live run (maintainer + orchestrator + nodes; the operator logs evidence into `RUNLOG.md`)

**R1 — GUI boot** (maintainer; mechanisms 1 and 5). He opens a **new GUI
session on the main checkout**, with the app's worktree isolation **off**
(isolation drops the pin; see harness.md, "GUI self-isolation"), and picks
the GUI model. Checks:

- it boots as `qs-spike-orchestrator`;
- the hook summary is injected;
- `state.json` holds its session id;
- `which claude && claude --version` works from **its** Bash.

If the GUI's Bash cannot start `claude --bg`, that is a mechanism-1 result.
The workaround — the maintainer spawns the nodes from a terminal — is
tagged `manual-per-round`.

**R2 — Launch** (orchestrator; mechanism 1). It launches both nodes. The
evidence:

- `git -C <main> status --porcelain`, empty while both run;
- the P5 cwd field from `claude agents --json`, or the nodes' `start` events;
- `setup_task.py`'s side effects, one line each:
  - the `QS_<N>` branch pushed to origin;
  - the `venv`, `config/*` and `custom_components/*` symlinks;
  - the copied `.mypy_cache` and `.testmondata`;
  - both agent directories rendered;
  - the pin plus `effortLevel`;
  - the launch-script paths.

**R3 — Plans** (nodes → orchestrator → maintainer; mechanisms 2, 3a, 3b).
Each node analyses, runs its reviewer sub-agents and sends a plan summary.
The maintainer approves in the orchestrator, which sends "approved".

**R4 — Mid-turn message** (maintainer triggers, orchestrator sends;
mechanism 3c). When `claude agents --json` shows a node busy (the P5
field), the maintainer asks the orchestrator to send the mid-turn message.
That request is fault injection, not a relay.

**Pass:** in the node transcript, the message shows up **before** the final
assistant message of the turn that was running when it was sent. The send
timestamp is earlier than a later tool call in the same turn, and the
`progress` event's timestamp falls inside that turn. The transcript markers
used are recorded.

**R5 — Close and reopen** (maintainer; mechanisms 6 and 3d).

1. He **closes** the orchestrator window, not killing it, while both nodes
   implement.
2. He watches `tail -f events.jsonl` until a `result` or `question` has been
   emitted during the close, **or 60 minutes pass**.
3. He reopens the **same** session.

Records:

- did the nodes progress?
- did the GUI wake on its own (3d)?
