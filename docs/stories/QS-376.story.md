## Symptom

After an HA restart at 14:02:55 on 2026-09-27, **no car charged for the
rest of the afternoon** despite ~4–7 kW of solar surplus (the home battery
absorbed ~6.9 kW instead):

1. **ID.buzz on `wallbox 2 parking`** — was charging at 13 A/3 ph (8.8 kW)
   before the restart; stopped at 14:03:49 and never restarted.
   `Ensure State: wallbox 2 parking expected charge=True, is_charge_enabled=False`
   ×3 471 (up to 16:20); `switch.charger_2_parking_charge_control` "missing
   or not currently available" at each of 4 start attempts; still
   unavailable at 18:35.
2. **Twingo on `wallbox 3 portail`** (82 % → 100 %, best effort) — solver
   planned 7.8–9.3 kW (`auto_green` / `auto_green_consign`) every 5 min
   from 14:08:50 (falling to 6.6 / 5.9 / 4.5 kW after 15:24), but **no
   `start_charge` was ever issued**; SOC flat 82 %.
3. **Zoe on `wallbox 1 maison`** (57 % → 100 %, best effort) — received a
   single `auto_green` command with `power_consign=0.0` at 14:08:50 (log
   line 2792), i.e. surplus-only charging; never started either. Whether it
   would have received amps without the stall depends on the surplus left
   after the Twingo.

## Root cause

Three chained links; the first is upstream, the other two are QS.

**L1 — trigger (upstream `lbbrhzn/ocpp` v0.12.0, not in this repo).**
`ChargePoint.on_meter_values` (`ocppv16.py`, "Restore missing per-connector
… active_transaction_id from HA") restores a missing
`(connector_id, transaction_id)` metric via
`ChargePoint.get_ha_metric(csess.transaction_id, connector_id)`
(`chargepoint.py:1531`), whose candidate list for `connector_id == 0` is
only the flattened `sensor.<cpid>_transaction_id` — i.e. connector 1's
running session on a single-connector charger — so the first connector-0
`MeterValues` after a `ChargePoint` is created mid-session sets
`_active_tx[0]` to connector 1's transaction id;
`_resolve_stop_connector` (`ocppv16.py:364`) then finds the id on two
connectors and returns `None`, `on_stop_transaction` holds `[0, 1]`
(#2128), and because the Wallbox sends `Finishing` **before**
`StopTransaction` (the only settling status has already been consumed) and
nothing until the car is unplugged, the hold never clears and the
transaction-bound `charge_control` switch stays unavailable.
Contributing facts: connector 0's hold can never be settled by any status
(`on_status_notification` only resolves `connector_id > 0`); the hold is
in-memory and survives charger reconnects (the `ChargePoint` is reused,
`post_connect` — which sends `TriggerMessage StatusNotification
connectorId 1` — runs once per object).

**L2 — QS never retries a start once its retry budget is spent.**
`QSChargerGeneric._ensure_correct_state`
([charger.py:5253](../../custom_components/quiet_solar/ha_model/charger.py))
gates `start_charge` on `QSStateCmd.is_ok_to_launch` → `can_launch()`
([charger.py:326](../../custom_components/quiet_solar/ha_model/charger.py),
`_num_launched <= STATE_CMD_RETRY_NUMBER (3)`). `_num_launched` is reset
only by: `set()` with a **different** value (`reset()`), `success()`, or
`_reset_state_machine()` (which rebuilds the `QSStateCmd`s — reached via
`execute_command`'s `DO RESET`
([charger.py:5778-5779](../../custom_components/quiet_solar/ha_model/charger.py))
and device reset / unplug
([charger.py:2914](../../custom_components/quiet_solar/ha_model/charger.py))).
None happens while the target stays `True`, the charger stays
not-charging, the car stays plugged and the command stays auto — so after 4
launches QS stops trying forever. `low_level_start_charge`
([charger.py:6083](../../custom_components/quiet_solar/ha_model/charger.py))
reports success although HA silently drops the call to the unavailable
switch. **No human signal:** the QS-346 fault path does not fire
(`Finishing` is not in `_unknown_state_vals`), and the zero-power alert is
disarmed for a start that never succeeds (see Evidence).

**L3 — one non-converging charger starves the whole budgeting group.**
`QSChargerGroup.ensure_correct_state`
([charger.py:866](../../custom_components/quiet_solar/ha_model/charger.py))
does `if res is False: return [], None` for any member that is not in its
expected state, with no bound on how long that may last, so while wallbox 2
is stuck `dyn_handle` never budgets wallbox 3 / wallbox 1 — no amps, no
`start_charge` — for the Twingo and the Zoe.

**L2 and L3 lock each other:** the only `set(False → True)` path that would
reset wallbox 2's counter is `apply_budgets` (charger.py:2235), which L3
blocks; and L3 lasts as long as L2 keeps wallbox 2 non-converging.

**One-sentence root cause (QS-owned):** a charger whose start can never
succeed (here: OCPP v0.12.0 holds `charge_control` unavailable because
connector 0 inherited connector 1's transaction id, so the stop could not
be attributed and both connectors were held) is never isolated — its start
retries silently run out in `_ensure_correct_state`/`QSStateCmd.can_launch`
and `QSChargerGroup.ensure_correct_state` keeps returning no actionable
chargers because of it — so every charger in the group stops being
budgeted indefinitely.

## Remediation of a stuck OCPP charger (what actually releases the hold)

Proven by the replay (E1–E4) against v0.12.0 and live (18:35:16):

| Remedy | Releases? | Notes |
|---|---|---|
| Unplug (→ `Available`) and replug | **yes** (E1) | manual; later sessions clean |
| `StatusNotification` for **connector 1** | **yes** (E2) | `ocpp.trigger_custom_message` (v0.12.0) has no `connector_id` field → QS can only send a connector-less trigger (next row) |
| Connector-less `ocpp.trigger_custom_message StatusNotification` | **yes — verified live on the Pulsar** | 18:35:16: Wallbox answered conn 0 `Available` + conn 1 `Finishing` → `connector 1 reports no transaction; ending the one it held` (Live check result) |
| Reload the charger's OCPP config entry (or HA restart) while not charging | **yes** (E4) | new `ChargePoint`, in-memory hold gone; out of scope for QS |
| Charger reboot (`Reset`) | **no / uncertain** | `ChargePoint` reused on reconnect, hold kept; post-reboot status may be `Preparing` (keeps the hold) |
| QS not stopping a running session at boot | **no** (E5) | only postpones the stall to the session's end |

**Rejected QS-side prevention (review C9):** "do not send a connector-less
`TriggerMessage MeterValues` in the cycle that issues an OCPP stop". S2
shows that removing the one 14:03:50.516 sample avoids *this* hold, but
connector 0 is poisoned by **any** connector-0 sample after a
`ChargePoint` is created mid-session — QS's `update_data_request` sends
such triggers every ~21–42 s in the ensure loop, and the Wallbox sends its
own `Sample.Clock` on conn 0 every 15 min — so any later stop of the
session holds anyway (E5/E6). Prevention is only possible upstream (L1).

## Fix plan (decided)

Scope: QS containment of L2 + L3 (+ OCPP containment of L1's effect); the
L1 fix itself lives in the fork (D3).

**Layering:** in the observed OCPP scenario, **F3 + F4** (with the existing
QS-346 plumbing) are the primary containment — the charger leaves the group
and the solver immediately, is nudged, and resumes on recovery. **F1 + F2**
are the generic safety net for any charger whose start never takes effect
while its control stays available (any charger type).

- **F1 (L3) — isolate a start-stuck charger from the group, keep its amps
  reserved.** New method `QSChargerGeneric.is_start_stuck(time) -> bool` =
  `_expected_charge_state.value is True and self.is_charge_enabled(time) is
  not True and not _expected_charge_state.can_launch()` (no new state). In
  `QSChargerGroup.ensure_correct_state`, in the `res is False` branch
  (charger.py:866), a member with `is_start_stuck(time)` is skipped
  (`continue`) **before** `get_stable_dynamic_charge_status`
