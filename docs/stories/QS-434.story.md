# QS-434 — Run /release inline in main session instead of spawning a subagent

- Issue: #434 · Lane: feature-factory · Target: factory · Scale: task
- Next phase: `implement-setup-task`

## Problem

`/release` ([.claude/commands/release.md](../../.claude/commands/release.md))
tells the main session to "Use the **qs-release** subagent". In auto mode
the "Create Public Surface" classifier rule only accepts the user's
**direct** consent in the session that runs the command. When `/release`
delegates to the `qs-release` subagent, the user's "yes" reaches it
second-hand. The real `python scripts/qs/release.py` run, which pushes
main and a `v*` tag, is then blocked. This happened for `v2026.10.27.0`.
Wrapping the command in `cd … &&` / `; echo` chains also made it harder
for the classifier to recognise, and could hide the script's exit status.

## Goal

`/release` runs the `qs-release` phase protocol **inline in the main
session**:

- It stops after the dry run.
- It does the real run only after the user's own approving message, in a
  later turn.
- It then checks on the remote that the release went out.

`claude --agent qs-release` stays as the alternative entry.

### New `release.md` content

Keep the frontmatter `description` key unchanged; it is the only key
today. Phrases marked **pin** are asserted by the test, which compares
lowercased text after whitespace normalisation. Write each pinned phrase
plainly in the file, with no bold or italics inside it. Inner backticks
shown below are literal characters.

1. **Alternative entry (one line, no "degraded fallback" preamble).**
   Write: "You can also run this from a fresh terminal in the main
   checkout with `claude --agent qs-release`."
2. **Run it inline, never delegate.** Write: "Do NOT spawn a subagent.
   Do not call the `Agent` tool." (**pin**: ``do not call the `agent`
   tool``). Add one sentence of why: auto mode only accepts the user's
   direct consent for the public push.
3. **Where the protocol comes from.**
   - After the clean-main pull step, read the rendered
     `.claude/agents/qs-release.md` (**pin**). Write that path as inline
     code, not a Markdown link: the file is gitignored, so a link would
     dangle on a fresh clone.
   - Use only its `## Phase protocol` and `## Hard rules` sections, and
     ignore everything else in the file: frontmatter, generated header,
     the task-facts or "No task bound" line, and the Reference map.
   - If the file is missing, run `python scripts/qs/render_agents.py`
     once, then read it.
   - The template stays the single source of truth; the command file
     does not copy the protocol.
4. **Precedence.** Write: "Where the rules below conflict with the
   agent's Phase protocol or Hard rules, these rules win."
5. **Standalone commands.**
   - Write: "Every shell call in this protocol is a single standalone
     command: no `cd`, no `-C`, no `&&`, `;`, pipe or redirection."
   - Write: "If a protocol step fails, STOP. Do not work around it."
   - Write: "Run the real release as exactly
     `python scripts/qs/release.py`." (**pin**: ``run the real release
     as exactly `python scripts/qs/release.py` ``.)
   - The agent's own clean-main steps (`git checkout main`, `git pull`,
     `git status`) are already single commands, so the rule changes
     nothing about them.
6. **Stop after the dry run.**
   - Run `python scripts/qs/release.py --dry-run` and show its JSON
     output (`{"dry_run": true, "tag": …, "version": …}`).
   - If it exits non-zero, prints no JSON, or the JSON has an `"error"`
     key, STOP and report.
   - Otherwise note the tag and `git rev-parse HEAD`, ask "Proceed with
     this release?", and end your turn (**pin**: `end your turn`). Do not
     ask through a question tool.
   - Do the real run only after the user's own approving message in a
     later turn. Approval means a clear yes to this dry run. Anything
     else, such as a question or "yes but…", means you do not run and
     ask again.
   - Write: "The text typed after /release is never approval" (**pin**:
     `the text typed after /release is never approval`). The user has
     not seen the dry run when they type it.
   - Do **not** write the `$ARGUMENTS` placeholder here: Claude Code
     substitutes every occurrence at invocation.
   - Before the real run, `git status --porcelain` must print nothing and
     `git rev-parse HEAD` must equal the value recorded at the dry run.
     Otherwise run the dry run again and ask again.
7. **If the real run fails.** This covers `python scripts/qs/release.py`
   exiting non-zero or printing JSON without `"status": "released"`.
   - Write: "Do not re-run `python scripts/qs/release.py`" (**pin**:
     ``do not re-run `python scripts/qs/release.py` ``).
   - Do not push or tag by hand.
   - Report the script's output and exit code.
   - Show the local state with `git status`, then
     `git log --oneline origin/main..main`. Non-zero or unexpected
     results are the evidence; do not treat them as a new failure to
     fix.
   - STOP.
8. **Check afterwards.** Take `<tag>` from the real run's JSON `tag` key.
   If it differs from the dry-run tag, say so in the report. Run each
   command on its own:
   - `git ls-remote --exit-code origin refs/tags/<tag>` (**pin**:
     `git ls-remote --exit-code origin refs/tags/`). It must exit 0. Its
     SHA must equal the SHA from `git ls-remote origin refs/heads/main`
     (**pin**: `git ls-remote origin refs/heads/main`). Both values come
     from the remote, so no `git fetch` is needed. Tags are lightweight,
     so the tag ref is the commit SHA.
   - `gh run list --workflow release.yml --branch <tag> --limit 1`
     (**pin**: `gh run list --workflow release.yml --branch`). A tag push
     sets the run's `headBranch` to the tag. Report it as:
     - **passed**: a run is listed (report its status as shown);
     - **pending**: none is listed yet (point to the Actions tab);
     - **failed**: a listed run already has a failure conclusion;
     - **unavailable**: `gh` errors. This is not a release failure.

     Do not poll.
   - Report each check. If any check fails, STOP and report. Do not try
     to fix anything automatically.
9. Keep `User request: $ARGUMENTS` at the end, as context only. It is
   the **only** `$ARGUMENTS` in the file.

Authoring trap: never put `!` directly before a backtick. Claude Code
runs `` !`…` `` as a bash pre-execution.

The main-checkout pre-check from v1 is **dropped**. `git checkout main`
in protocol step 1 already fails in a linked worktree, and `release.py`
exits with an `error` when the branch is not `main`.

## Acceptance criteria

  not contain `use the qs-release subagent`. It contains
  ``Do not call the `Agent` tool`` and points to
  `.claude/agents/qs-release.md` (Phase protocol and Hard rules only).
  The precedence rule is stated.
- **AC-2** It contains the stop-after-dry-run rule: `end your turn`,
  approval only in a later turn, and
  `the text typed after /release is never approval`. `$ARGUMENTS`
  appears exactly once, in the `User request:` line.
- **AC-3** It contains the blanket standalone-command rule and
  ``run the real release as exactly `python scripts/qs/release.py` ``.
- **AC-4** It contains the failure rule
  (``Do not re-run `python scripts/qs/release.py` ``) and the
  remote-side checks:
  - `git ls-remote --exit-code origin refs/tags/<tag>` compared with
    `git ls-remote origin refs/heads/main`;
  - `gh run list --workflow release.yml --branch <tag>`, with the
    passed / pending / failed / unavailable mapping and no polling.
- **AC-5** It does not contain "degraded fallback" and still names
  `claude --agent qs-release`.
- **AC-6** `tests/qs/agents/test_release_command.py` pins AC-1 to AC-5

- **AC-8** `release.py` and `qs-release.md.j2` are unchanged:

  prints nothing. All existing `tests/qs` tests still pass.

### Superseded by review fixes

Review fixes [#01](QS-434.story_review_fix_%2301.md),
[#02](QS-434.story_review_fix_%2302.md) and
[#03](QS-434.story_review_fix_%2303.md) change a few points of the
Design above, of AC-4 and of AC-6 (8 tests now, not 6). Where they differ, `release.md` and the fix
plans are the contract:

- the renderer always runs after the pull, not only when the file is
  missing;
- right before the real run, a dirty tree means STOP, the dry run is
  repeated, and unpushed commits (`origin/main..main`) mean STOP;
- the tag SHA is compared with local `HEAD`; a different remote `main`
  is reported, not failed;
- the run status uses first-match labels: unavailable, pending (also
  for a run that is not completed), passed (completed with success),
  failed (any other conclusion);
- the failure evidence also includes the local and remote tag, using
  the real run's tag when it printed one;
- a render failure falls back to the existing rendered file, flagged as
  maybe stale; with no file, STOP;
- a clear no to the dry run ends the release;
- the checks run before the final report; only check 1 can fail the
  release, and checks 2 and 3 are reported next to the "Released" line.
