### [should-fix] F4 — "Waking": reaping wording too absolute, early `tool resume` cost unstated
- File: `docs/workflow/control-plane.md:661`
- Severity: should-fix
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter (nice-to-have "within 30 s")
- Description: "The daemon's liveness watchdog does the reaping" omits that
  `_reserve_prelude` (tools.py) runs `nodes.refresh` on every `tool spawn` /
  passing `tool resume`; a row within `LAUNCH_SETTLE_S` of launch is never
  reaped; an unknown listing reaps nothing. "about 30 s" reads as a
  guaranteed delay (it was the first 30 s poll). An early `tool resume` is
  refused `INVALID_STATE` (hint "wake it with SendMessage", wrong for an
  ended session) and spends its key.
- Proposed fix: "A node is reaped by the next `nodes.refresh` — the
  watchdog's, every `LIVENESS_EVERY_S`, or any `tool spawn` / `tool resume`
  reserve — never within `LAUNCH_SETTLE_S` of its launch, nor under an
  unknown listing; `tool resume` cannot reap its own node (its guard runs
  first). Call it only once the row reads `reaped` (or `node_dead` fired):
  an earlier call is refused `INVALID_STATE` and spends its key, so retry
  with a new key. Seen live on 2026-10-29 (Claude Code 2.1.312, #437):
  `reaped` at the first poll, within 30 s of `claude stop`." Verify every
  name (`_reserve_prelude`, `LIVENESS_EVERY_S`, `LAUNCH_SETTLE_S`,
  `_resume_guard`, the refusal code/hint, key spending) in
  `scripts/qs/control_plane/{tools,nodes,liveness}.py`; drop any clause the
  code does not support.
