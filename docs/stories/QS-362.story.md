## Symptom

First production boot of the `2026.09.22.0` release together with
`lbbrhzn/ocpp` v0.12.0 (first v0.12.0 boot — the OCPP config migration
2.2 → 2.3 runs at 11:35:03):

1. **276 identical ERROR tracebacks** in ~32 minutes, one per
   load-management cycle (7 s) per OCPP charger (3 Wallbox Pulsar):
   `check_amps_delivery raised for wallbox N …` →
   `KeyError: 'sensor.charger_N_…_current_offered'`.
2. The Twingo on `wallbox 1 maison` did not charge for the rest of the
   run (`Ensure State: expected charge=True, is_charge_enabled=False`
   ×186; `switch.charger_1_maison_charge_control are missing or not
   currently available` at each `start_charge` retry).

Symptom 2 turned out **not** to be a QS defect (see Evidence E5/E6); it
is recorded here because it is what made the regression visible.

## Root cause

`QSChargerOCPP.__init__` ([charger.py:6252](../../custom_components/quiet_solar/ha_model/charger.py))
binds `self.charger_ocpp_current_offered` (and lists it in
`get_probable_entities()`) but never calls
`attach_ha_state_to_probe()` on it, while the QS-359 clip detector
(`check_amps_delivery` → `_ocpp_read_current_offered`,
[charger.py:6594](../../custom_components/quiet_solar/ha_model/charger.py))
reads it every cycle through the probe cache, whose lookup
([device.py:841](../../custom_components/quiet_solar/ha_model/device.py))
indexes `_entity_probed_last_valid_state[entity_id]` without a default —
so on every OCPP device that exposes `sensor.<cpid>_current_offered`
(all of them under v0.12.0) each load-management cycle raises
`KeyError`.

Why it "changed with #359": before #359 `_current_offered` was only
referenced in the dead `use_ocpp_custom_charging_profile=True` branch
and read via `hass.states.get`; #359 added a new per-cycle consumer that
reads it via the probe cache.

Symptom 2 (car not charging) is **not** a QS defect: a one-shot
artefact of the OCPP v0.11.4 → v0.12.0 upgrade (#2128 hold on the last
v0.11.4-born transaction), consumed on the first v0.12.0 boot and
cleared by any subsequent HA restart. It cannot recur.

## Decision (product, taken in-session)

Three fixes were on the table:

- (a) register the probe (one line) and keep #359;
- (b) remove the clip detector only, keep the #2131 fallback;
- (c) **revert all #359 product code**.

**Chosen: (c).** Rationale: on the owner's hardware the #2131 fallback
can only be a no-op (E3: the Pulsar accepts `ChargePointMaxProfile`) or
degrade the ack loop into a sticky, blind optimistic mode on a false
positive (two transient rejections > 10 s apart); the clip detector is
the only part of #359 with an observed production effect, and that
effect is this bug. Both guard against populations (chargers rejecting
the station profile, stack-level clips) with no reported occurrence.
Keeping them "in case a future charger / another user needs them" is
dead code until that day; it will be rebuilt then, against real
evidence.

## Iceberg check

Not an iceberg — the cause is local to #359's own additions and the fix
removes them.

Two things noted, deliberately **not** done here:

- `device.py:841` indexes `_entity_probed_last_valid_state[entity_id]`
  raw. Softening it to `.get()` would have hidden this very bug behind a
  silently-dead feature; keeping the hard `KeyError` on an unregistered
  entity is the better contract. Left as is.
- Process: #359's tests mocked the probe read (`_seed()`), which is how
  a per-cycle `KeyError` shipped with "100 % coverage". The regression
  test here goes through the real cycle for that reason. Worth
  remembering when reviewing future charger tests; no pipeline change
  proposed in this bug.

Symptom 2 (OCPP v0.12.0 #2128 one-shot hold after upgrade) is upstream
behaviour and cannot recur for this installation. An optional follow-up
— a README/upgrade note ("after upgrading lbbrhzn/ocpp to v0.12.0 with a
charge in progress, restart HA once after that session ends") — is
**out of scope** for this PR; open a `kind:feature` issue if wanted.
