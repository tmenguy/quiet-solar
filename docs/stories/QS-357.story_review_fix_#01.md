## Findings to fix

### [should-fix] Handoff render never warns on `facts_state == "unbound"`
- File: `scripts/qs/next_step.py:217`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: In the handoff render block (`main`, ~lines 217-228),
  `build_render_context(args.work_dir)` re-derives task-boundness solely
  from the worktree's current branch via `_current_branch` — it ignores
  `args.issue` / `args.title`. When the branch cannot be parsed to an
  issue (detached HEAD mid-rebase/bisect, or a worktree moved onto a
  non-`QS_<N>` branch), `issue` resolves to `None` and `bound_task`
  collapses to `False`. The warn-block only emits on
  `facts_state == "lookup_failed"` or `lane_protocol_state ==
  "file_missing"` — it never warns on `facts_state == "unbound"`. Result:
  the handoff silently ships agents whose Task-facts section reads
  "No task bound… run context.py" even though `next_step` was invoked
  with a known `--issue` / `--title`. No operator signal is produced.
- Proposed fix: Emit a warning when `facts_state == "unbound"` at handoff
  time so the operator is told the rendered agents are task-agnostic
  despite a known issue. Related (and worth folding in while editing the
  same block): the existing `if lookup_failed … elif file_missing`
  structure suppresses the second warning when both conditions hold —
  prefer independent `if`s so each render-degradation reason surfaces
  independently. Add/extend a test in
  `tests/qs/launchers/test_next_step_cli.py` that drives the handoff
  render on a worktree whose branch does not resolve to an issue and
  asserts the `unbound` warning is printed (and that both warnings can
  co-occur).
