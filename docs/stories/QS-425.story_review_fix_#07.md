## Root cause

Three review rounds in a row (6, 7, and the R6-S1 fix) found gaps in the catch-up section. A catch-up spans several
side effects: a counter, a merge, a gate, a resolution review, a push and a write. `round.json` records none of
them except `step: catchup` and, after the push, `head`. So every resume, rotation or unblock has to re-derive what
was done, and each derivation leaves a hole.

## The design

### New `round.json` field: `catchup`
Add to the field list (~:176-193):

> "catchup" (`null`, or `{"from": "conflict"|"done", "merge": <sha>|null, "clean": true|false|null,
> "reviewed": true|false}` — the catch-up in progress or last pushed: why it started, its merge commit, whether
> the merge was clean, whether its resolution review ran; kept until the next build round's push write
> consumes `merge` as `--base`, or until step 8)

### Step 7, rewritten around that field
1. **Entering step 7** (either trigger): if `catchups` is already 3 → blocked (cause `catchups`), with no merge. This
   is the bound, now checked **before** every merge (R7 S4). Otherwise write, **in one `round.json` write**:
   `step: catchup`, `catchups` + 1, `catchup = {"from": <trigger>, "merge": null, "clean": null, "reviewed":
   false}`. The counter therefore can't be lost, or counted twice, around the merge (R7 nice-to-have).
2. `git fetch origin main`. If `origin/main` is an ancestor of `HEAD` and `catchup.from` is `done` → nothing to
   merge: `catchup` = `null`, step 8. If it is an ancestor and `from` is `conflict` (a stale `mergeable` answer) →
   `catchup` = `null`, `step: wait` (back to the wait; CI must still go green). Otherwise `git merge origin/main`.
3. Once the merge commit exists (clean, or once the implementer has committed the resolution), record
   `catchup.merge` = the merge commit and `catchup.clean` in one write.
4. The implementer invocation:
   - **clean** → "gate only; fix on top of the merge if red";
   - **conflicts** → "resolve the merge conflicts".

   Both are given **the code-level fixes in `pending.json`** (R7 S3). A fix that unblocked a `catchups` block now
   reaches the implementer that can apply it. Applied fixes are resolved after its commit, as in "The `fix`
   protocol".

   The red-gate rule is unchanged: one more invocation; still red → blocked (cause `catchups`), with the merge left
   committed.
5. **Resolution review**, when `catchup.clean` is false or commits sit on top of the merge: `qs-node-edge-case` on
   `git show --remerge-diff <catchup.merge>` plus the fix diff, then triage, then `catchup.reviewed` = true.
6. Push, then the catch-up push write, unchanged except that `catchup` stays as it is. CodeRabbit handling is
   unchanged.
7. After the catch-up wait: green with nothing blocking → step 8; findings left blocking → the round's `continuing`
   report (unless already posted), then the next build round. **Remove** the old "`catchups` reaching 3 → blocked"
   clause here, because the bound is now step 7.1.

### Build step 2 `--base` (R7 S1)
Replace "after a catch-up, `--base <merge commit>`" with "`--base <catchup.merge>` when `catchup.merge` is set".
Step 2's one push write sets `catchup` = `null` (consumed). *(Superseded: the implementation clears it in the write after `round start`; fix plan #08 then moves the merge to `base_merge`.)* A rotation or resume between the catch-up and the next
round then still has the merge commit. Do the same in the post-wait sentence: "the next build round (`--base` =
`catchup.merge`)".

### Start-up rule 5, `catchup` (R7 S2 and the "gate if not yet green" nice-to-have)
Replace the two current `catchup` clauses with one ordered rule, driven by `catchup`:
- `MERGE_HEAD` exists → the implementer finishes the open merge (never start a new merge over it), then go on from
  item 3.
- `catchup.merge` is `null`, no `MERGE_HEAD` → resume at step 7 item 2 (the counter is already written; never
  increment it again).
- `catchup.merge` is set and `HEAD` ≠ `round.json`'s `head` → finish the remaining sub-steps **in order**:
  - the gate: a gate-only implementer invocation with the pending code fixes, as a new `inv`. Re-running it is
    always safe;
  - the resolution review (item 5), if needed and `catchup.reviewed` is false;
  - `tool push` (its key replays);
  - the catch-up push write.

  Never re-decide whether to merge, and never go to done from here.

### Step 8
`catchups` = 0 and `catchup` = `null` in step 8's first write. Then both the in-session path and the
resume-at-`wait` path reset them (R7 nice-to-have). Remove the "`catchups` reset to 0" phrase from step 7's
post-wait sentence.

### Unchanged
- Clearing a `catchups` block still sets `catchups` = 0 (~:677).
- The blocked-then-unblocked catch-up resumes at `step: catchup` and is now handled by rule 5 above.
