# QS-349 — Minimum battery discharge safety for CMD_GREEN_CHARGE_ONLY during grid outage

- **Issue**: #349
- **Branch**: `QS_349`
- **Lane**: feature × product (`area:battery`, `area:solver`, `area:car` —
  car is indirect: chargers consume `battery_can_discharge()`, see
  Design §3 blast-radius note)
- **Story version**: v6 (review round 2: all 20 findings accepted and
  folded; D1 universal floor confirmed, D2 force-charge residual
  accepted)

## Problem

When the solver decides grid power is cheaper than battery power, it
issues `CMD_GREEN_CHARGE_ONLY` to the home battery. That command writes
`max_discharging_power = 0` to the inverter
(ha_model/battery.py:71) — the battery may still charge from solar
excess but must not discharge. `CMD_FORCE_CHARGE` writes the same 0
(ha_model/battery.py:73).

If a grid outage strikes while that 0 is pinned in the inverter, and
the inverter honours the max-discharge limit in island mode, the
battery cannot power the house — blackout despite a full battery. How
bad it gets depends on the setup:

- **Setups without backup power for HA/network** (the generic case
  quiet-solar must protect): the house going dark takes down the very
  controller that could lift the 0 — a **latched** blackout.
- **Setups where HA + network/EMMA survive on their own backup**
  (the reporter's case, settled decision Q4): the restore path lifts
  the 0 within seconds — the floor's job is to cover the
  **detection + reaction window** so the house rides through it.

The floor value should be sized per that purpose (small ride-through
allowance vs. enough to run essential loads unattended).

### What already exists (do not rebuild)

- **Outage detection**: `CONF_OFF_GRID_ENTITY` (+ state value /
  inverted flags) with an event-driven state-change listener, mode
  select (`AUTO` / `FORCE_OFF_GRID` / `FORCE_ON_GRID`), mobile alarm
  broadcast (ha_model/home.py).
- **Restore on detection**: `async_set_off_grid_mode` sends the battery
  `CMD_GREEN_CHARGE_AND_DISCHARGE`, restoring
  `max_discharging_power = max` (home.py:1066-1071), then forces a
  re-solve.
- **QS-264 decision** ([docs/agents/concepts/off-grid-mode.md](../agents/concepts/off-grid-mode.md)):
  the outage *SOC reserve* is a native inverter concern (Huawei
  `Backup power SOC` vs `End-of-discharge SOC`; released in hardware,
  sub-second). QS's residual obligation: "do not pin the battery at
  max-discharge = 0 longer than necessary while on-grid".

### The actual gap

The window between grid loss and QS's restore is not survivable when
`max_discharging_power = 0` is honoured in island mode. The hardware
SOC-reserve pair does not help — it governs *how deep* the battery may
discharge, not *whether* discharge power is allowed at all.

Additionally, code inspection found the post-detection reaction path
is slower than it needs to be — two ordering flaws:

- **Flaw A — notifications block the safety path.** In
  `_off_grid_entity_state_changed` (home.py:1180-1214) the mobile-app
  broadcast runs **before** `_compute_and_apply_off_grid_state`
  (called at home.py:1214), and `async_notify_all_mobile_apps` awaits
  each notify service sequentially with `blocking=True`
  (home.py:1159-1167). Push notifications route through cloud
  services — exactly what may hang during an outage — so the battery
  restore waits behind them.
- **Flaw B — battery restored last.** In `async_set_off_grid_mode`
  (home.py:1055-1071) every load is idled first (each an awaited
  probe + service call) and the battery
  `CMD_GREEN_CHARGE_AND_DISCHARGE` restore comes after all of them —
  the one command that keeps the house alive is at the back of the
  queue.

## Goal

Give the user a way to guarantee that quiet-solar never writes a
discharge limit so low that a grid outage becomes unrecoverable (the
guarantee is opt-in — the default keeps today's behaviour), and make
the detect→restore reaction as fast as the signal allows. Residual
risk stays honest: with instantaneous island demand above the
configured floor, the inverter's native overload protection decides
the outcome — the floor bounds the damage, it does not run an
arbitrary house.

1. **Floor**: a user-configurable **minimum discharge power floor**
   for the battery: commands that today write
   `max_discharging_power = 0` write the floor instead. Default 0 W
   (opt-in) — existing behaviour and the QS-264 stance are unchanged
   unless the user asks for the safety floor.
2. **Reaction latency**: on the off-grid transition, restore the
   battery **first**, shed loads **second**, and never let
   notifications sit in the critical path (fixes for flaws A and B).

The two compound: the floor covers the pre-detection window; the
reordering shrinks the post-detection window.

## Non-goals

- No new outage detection, no new restore path — both exist.
- No SOC-reserve management (QS-264: native inverter concern; on EMMA
  setups the SOC setpoints are read-only anyway).
- No Huawei-specific code — quiet-solar stays hardware-agnostic
  (generic `number`/`switch` entities).
- No notification-delivery machinery: fix A is a pure reordering — no
  retry, no queue, no delivery-status abstraction; exception handling
  is log-only.
- No fix for the pre-existing single-pass allocation heuristic or the
  pre-existing complete-cover branch bug (solver.py:1337-1338), and no
  fix for the pre-existing pre-flip `consumption_power` staleness —
  all three exist today at F = 0 and changing them would break the
  F = 0 regression guarantee (see Design §4).
- No hardware probing of whether a given inverter honours
  max-discharge in island mode (manual validation on the reporter's
  hardware is post-merge validation, not a merge gate — Acceptance
  §Manual).

## Design

### 1. Config (`const.py`, `config_flow.py`, `strings.json`)

- New key `CONF_BATTERY_MIN_DISCHARGE_POWER_VALUE` in `const.py`
  (mirrors `CONF_BATTERY_MAX_DISCHARGE_POWER_VALUE`, const.py:146),
  default `0`.
- **Config-flow field** in `async_step_battery` (config_flow.py:1102):
  mirror the `CONF_BATTERY_MAX_DISCHARGE_POWER_VALUE` block
  (config_flow.py:1174-1185) — `vol.Required(...)` with
  `suggested_value` (default 0), `NumberSelector` `min=0`, BOX mode,
  W unit. No artificial upper cap in the UI — the effective value is
  clamped to `[0, max_discharging_power]` in the domain model
  (Design §2). A floor equal to max is a legitimate choice (it makes
  `CMD_GREEN_CHARGE_ONLY` behave like `CMD_GREEN_CHARGE_AND_DISCHARGE`,
  and the solver models that correctly per Design §4).
- **Both flows**: `async_step_battery` lives in `QSFlowHandlerMixin`
  (config_flow.py:305), shared by `QSFlowHandler` (:2235) and
  `QSOptionsFlowHandler` (:2312) — both paths are structurally
  guaranteed. **Re-init mechanism**: an options-flow save updates the
  config entry, which reloads the device and re-runs the
  `Battery.__init__` clamp; if implement-time verification finds the
  battery is *not* re-inited on options save, fall back to a live
  clamp (min of floor and current max at emission time) — do not ship
  a floor that can silently exceed a lowered max. **Migration**:
  entries without the key behave as floor = 0; the single owner of
  that default is `Battery.__init__`
  (`kwargs.pop(CONF_BATTERY_MIN_DISCHARGE_POWER_VALUE, 0.0)`,
  mirroring `max_discharging_power` at home_model/battery.py:21) —
  the bridge passes the raw entry value or omits the kwarg, never
  defaults it itself.
- **`strings.json` — two insertion points**: the config step data
  block (~line 89, next to `battery_max_discharge_power_value`) and
  the options step `[%key:...]` reference (~line 498). The battery
  steps have **no `data_description` block today** — create one in
  the config-section battery step and a `[%key:...]`-mirrored one in
  the options section (pattern: strings.json:638-650). Label copy
  (honest about the residual risk): "outage safety floor — minimum
  discharge power the battery always keeps available so a grid outage
  during a grid-charge phase cannot lock the battery at zero
  discharge; if the outage-time house demand exceeds this floor, the
  inverter's own overload protection decides the outcome".
  `translations/en.json` regenerated via
  `bash scripts/generate-translations.sh` (never hand-edited).

### 2. Domain model (`home_model/battery.py`)

- `min_discharging_power` (today hardcoded `0.0` at line 33) becomes a
  `Battery.__init__` kwarg populated from the new config key **via the
  same path as `max_discharging_power`** (`kwargs.pop(CONF_..., 1500)`
  at home_model/battery.py:21 — popped before line 33, so the clamp
  can reference it; `max_discharging_power` always has a value, its
  kwarg default is 1500).
- **Clamp at init** (one-time), integer-normalized: effective value =
  `float(round(min(max(0.0, configured), max_discharging_power)))`
  (`round()`, not truncation — a safety minimum must not be silently
  lowered; review-fix #01 N1). The normalization matters: the write path
  maps the value to the entity unit/step/range via `_number_entity_target`
  and the read path is `int(round(...))`, while `probe_if_command_set`
  reuses the **same** `_number_entity_target` for its expected value — so a
  non-integer / kW / stepped floor still confirms (no eternal retry). (A
  corrupt `null`/string/non-finite floor or max is coerced via
  `_coerce_float` to a finite default, and a negative max is clamped to 0
  so it can't drag the floor negative — review-fix #01 R6 / #02 R6, #03
  T6.) If the user later lowers
  `max_discharging_power` below the floor via reconfigure, the device
  re-init re-clamps — no live property clamp (see Design §1 for the
  fallback if re-init is not triggered).

- The existing write-clamp in `set_max_discharging_power`

  `[min_discharging_power, max_discharging_power]` and becomes

  ha_model/home.py:1253, 1802, 1859, 1899-1904) see up to F of battery

  none — re-confirm before appending the tuple element).

### 4. Solver (`home_model/solver.py`) — model the floor (user decision)

The solver must model the real hardware behaviour: during
`CMD_GREEN_CHARGE_ONLY` slots the battery discharges up to the floor F
whenever house demand exceeds solar. Changes live in
`_battery_get_charging_power` (solver.py:389-488) and the allocation
pass (solver.py:1298-1363); F is read from
`self._battery.min_discharging_power` (the attribute travels with the
battery object). The leak buckets are a **new pass-1 output** that
crosses to the allocation pass (see "Data flow" below).

**Sign conventions (single source of truth for all formulas):**

| Symbol | Unit | Sign |
| --- | --- | --- |
| `available_power` | W | > 0 = house demand the battery may serve; < 0 = surplus it may absorb |
| `charging_power` | W | > 0 = charging; < 0 = discharging |
| `charged_energy` | Wh | `charging_power × duration_h`; < 0 = discharge |
| `d_i` | Wh ≥ 0 | slot discharge magnitude = `−charged_energy` when `charged_energy < 0`, else 0 |
| `leak_i` | Wh ≥ 0 | `min(d_i, F × duration_h)`; 0 when the slot does not discharge |
| `limit_discharge` / budgets | Wh ≥ 0 | remaining **compressible** discharge budget per price |
| `F` | W ≥ 0 | the floor |

**Core insight — incompressible vs compressible discharge.** A
discharging slot's energy splits into an **incompressible leak**
`leak_i` that flows regardless of which *discharge-limiting* command
the slot ends up with (a flipped `CMD_GREEN_CHARGE_ONLY` slot still
leaks it), and a **compressible remainder** `d_i − leak_i` — the only
energy the price-bucket optimizer can move between buckets.

**Why `CMD_FORCE_CHARGE` is leak-free (recorded assumption + accepted
residual):** during force-charge the battery is *actively charging
from grid* (`available_power = −power_consign`); pack-level charge and
discharge are mutually exclusive, so no discharge flows while the
charge executes. ("Unconditional" above is scoped to slots not
actively commanded to charge from grid.) **Accepted residual drift
(user decision, round-2 D2)**: if the battery saturates (100%) or the
inverter derates *mid* force-charge slot, hardware permits discharge
up to F for the slot's remainder — unmodelled, bounded by
`F × saturated-remainder duration` per slot (worst case F/4 Wh per
15-min slot). Modelling it would require predicting the saturation
point inside a slot; the bound is documented here and in
`solver.md` instead.

**The changed sites:**

- **Pre-set `CMD_GREEN_CHARGE_ONLY` slots** (solver.py:424-425): the
  clamp `available_power = min(0.0, available_power_list[i])` becomes
  `available_power = min(float(available_power_list[i]), F)` — surplus
  slots unchanged (min picks the negative surplus), demand slots capped
  at F instead of 0. `get_charger_power` then applies SOC limits and
  battery max-discharge as usual.
- **Pass 1 bucket accumulation** (solver.py:461-464): alongside
  `prices_discharged_energy_buckets`, accumulate
  `prices_leak_energy_buckets[price] += leak_i` for each discharging
  slot. `leak_i = min(−charged_energy, F × duration_h) if
  charged_energy < 0 else 0.0`, computed immediately after the
  `charged_energy` computation (solver.py:441), **before** the
  `limited_discharge_per_price` block (the value is idempotent under
  the later flip clamp).
- **Pass 2 flip site** (solver.py:443-454): flip when the
  *compressible* budget is exhausted —
  `limit_discharge + min(0.0, charged_energy + leak_i) <= 0.0`
  (evaluated with the **pre-clamp** `charged_energy`); on flip, clamp
  `charging_power = max(charging_power, −F)` and
  `charged_energy = max(charged_energy, −leak_i)`.
  **Debit is evaluated POST-clamp** (review-fix #01 M1) —
  `limited_discharge_per_price[price] = max(0.0,
  limit_discharge + min(0.0, charged_energy + leak_i))` with the clamped
  `charged_energy`. On a flipped slot `charged_energy + leak_i == 0`, so
  the debit is 0: **a flipped slot consumes no budget and the residual
  stays available for later same-price slots**. This is the pre-QS-349
  behaviour, so at F = 0 the whole flip site reduces algebraically to
  today's code (the earlier pre-clamp draft debited the whole
  compressible part on flip, which silently changed F = 0 behaviour and
  broke the AC 3 no-op guarantee — M1). A non-flip slot debits its
  compressible discharge (`charged_energy + leak_i < 0`). The flip stays
  **binary** (leak only or full discharge), never a partial
  `leak + residual`.
- **Allocation pass** (solver.py:1307-1352) — **one-time
  normalization, no per-line edits**. The inner loop restarts at
  `sub_price_idx = 0` on every outer iteration, so cheap buckets are
  **revisited** with 3+ price levels; subtracting the leak inside the
  loop would double-subtract on revisits. Instead, immediately before
  the loop (after solver.py:1307):
  ```python
  for p, leak in prices_leak_energy_buckets.items():
      prices_discharged_energy_buckets[p] = max(
          0.0, prices_discharged_energy_buckets.get(p, 0.0) - leak
      )
  ```
  Lines 1322, 1342-1346, and 1348 then stay **textually unchanged**
  (the bucket already holds the compressible total), revisit semantics
  are exactly today's, and F = 0 reduction is trivial (empty/zero leak
  buckets → no-op). Line 1348 keeps its expression but now stores the
  remaining *compressible* budget, consistent with the pass-2 debit.
- **SOC trajectory follows**: `battery_charge[i] = prev +
  charged_energy` carries the exact leak of flipped slots.

**Data flow — return-signature change:** `prices_leak_energy_buckets`
is **appended as the last element** (index 8) of
`_battery_get_charging_power`'s return tuple, so the existing
index-based accesses (`[7]` at solver.py:146, 1052; `[1]` at 837 and
1428; `refreshed[...]` at 942-946, indices 1 and 7) stay valid — no
negative indexing or star-unpacks exist among consumers (round-2
grep-verified; re-confirm at implement time, Design §3 audit item b).
The 5 full-tuple unpack sites to update: solver.py:671, 1191, 1291,
1363, 1622. **Test-side arity impact** (carved out of AC 3): the
8-tuple shape test `test_battery_get_charging_power_returns_eight_tuple`
(tests/test_solver.py:2423-2451) and the mocked 8-tuple `ret` fixtures
(tests/test_solver.py:2197/2199, 2240, 2283-2285;
tests/test_solver_2.py:1630/1632, 1669) must be extended with an empty
leak dict — arity edits only, never expected-value edits.

**Exactness scope (honest statement):** the floor accounting is exact
**within today's accounting semantics**. Pre-existing at F = 0 and
deliberately unchanged: (a) the flip site's `consumption_power` /
`grid_nrj` use the pre-flip value (solver.py:438, 466) — a flipped
slot's cheap-bucket grid residual already reflects pre-flip discharge
today; (b) the single-pass allocation heuristic; (c) the
complete-cover branch bug (solver.py:1337-1338: zeroing before
subtracting). Fixing any of them would change F = 0 output and break
the regression guarantee — out of scope.

- **F = 0 reduces algebraically to today's code**: every `leak_i` term
  is 0; all changed sites collapse to the current expressions.
- **Off-grid solves unaffected**: off-grid tariffs are flat 0.0 →
  single price bucket → the allocation short-circuits
  (solver.py:1299-1303) — no `CMD_GREEN_CHARGE_ONLY` issued off-grid.

### 4bis. Reaction-latency fixes (`ha_model/home.py`)

- **Fix A — notifications off the critical path, alarm off the apply
  path.** In `_off_grid_entity_state_changed` (home.py:1180-1214):
  1. **schedule** the mobile broadcast as a fire-and-forget background
     task first (`hass.async_create_task(...)` — production precedent:
     ha_model/device.py:406, ha_model/car.py:397). `async_create_task`
     returns immediately, so this delays nothing; because it is
     scheduled *before* the apply, a **hung** apply (e.g. a cloud-load
     `CMD_IDLE` hanging in the shedding loop during the outage) cannot
     delay the alarm either — the cloud-hang argument cuts both ways.
     The task body is wrapped in a log-only `except Exception` (lazy
     `%s`, no trailing period; **rule basis**: the background-task
     allowance in project rules). No retry/queue/delivery abstraction
     (non-goal).
  2. then `await self._compute_and_apply_off_grid_state(for_init=False)`,
     wrapped in `except Exception` + lazy `%s` error log (**rule
     basis**: this listener is an event-loop-dispatched callback on
     the safety path — treated under the background-task allowance;
     recorded here so implement and review make the same call). The
     alarm is already scheduled, so AC 11 holds trivially; the guard
     exists so the listener never dies half-way.
  Broadcast content and conditions unchanged (including the
  `FORCE_ON_GRID` override variants). Notification delivery and the
  battery restore are now **concurrent** — neither waits for the
  other; the safety requirement is only that the restore is never
  *delayed by* notification delivery (AC 10), not that it precedes
  it. The recovery path (off-grid → on-grid) inherits the same handler
  structure as an incidental consequence — **no dedicated
  recovery-symmetry behaviour or test obligation**.
- **Fix B — battery restore first.** In `async_set_off_grid_mode`
  (off-grid branch, home.py:1055-1071), send the battery
  `CMD_GREEN_CHARGE_AND_DISCHARGE` restore **before** the
  load-shedding loop. The battery is not in `_all_loads` (only
  `AbstractLoad` instances are appended, home.py:2003-2005), so this
  is a pure reorder. Load shedding, the
  `_switch_to_off_grid_launched` gate, and `force_next_solve()` are
  otherwise unchanged.
  **Risk analysis (why battery-first is safe):** the reorder adds
  *supply*, not load. During the shedding interval the island serves
  the same pre-outage loads either way; with battery-last it does so
  with *less* available power (strictly worse). Overload beyond the
  inverter's island capacity is handled by the inverter/SmartGuard's
  native protection in both orderings — QS cannot and does not manage
  it.
- Non-goal here: no change to the detection mechanism itself — the
  entity listener is already event-driven (~ms); upstream sensor
  latency belongs to the source integration, outside this repo.

## Acceptance criteria

1. With the floor configured (e.g. 300 W), `CMD_GREEN_CHARGE_ONLY`
   results in `number.set_value(max_discharge_number, 300)` — never 0.
2. Same for `CMD_FORCE_CHARGE`.
3. With the floor left at its default 0, behaviour is today's —
   operationally defined: **the existing solver and battery test
   suites pass with no expected-value edits** (any expected-value
   edit = regression). Sole carve-out: **arity/shape edits** forced by
   the 9-tuple (the sites enumerated in Design §4 "Data flow" — extend
   with an empty leak dict, nothing else). Plus explicit F = 0 tests
   on the changed sites.
4. `probe_if_command_set` confirms `CMD_GREEN_CHARGE_ONLY` when the
   entity reads the floor value (no eternal-retry regression) —
   including a **non-integer configured floor** (e.g. 300.7 → 301
   after the init `round()` normalization; write, read, and probe agree).
5. Floor is clamped at init: configured value above
   `max_discharging_power` is capped to it; negative → 0 (protects
   YAML/import/legacy-entry paths, not reachable from the UI).
6. Restore path still lifts to max: on the off-grid transition the
   battery command becomes `CMD_GREEN_CHARGE_AND_DISCHARGE` and writes
   `max_discharging_power = max`.
7. Config flow: the battery step accepts the new field in **both**
   initial and options/reconfigure paths, persists it, and the value
   reaches `Battery.min_discharging_power`; a pre-existing entry
   without the key behaves as floor = 0.
8. **Solver models the floor** — for a `CMD_GREEN_CHARGE_ONLY` slot
   with floor F and house demand D > solar: modelled discharge is
   `min(D − solar, F, battery max discharge, SOC-limited available
   power)` (not 0) and the SOC trajectory reflects it; the F-focused
   tests pin the fixture SOC comfortably above empty so the F bound is
   the binding one (a separate case may pin SOC as the binding bound).
9. **Leak-aware price-bucket accounting** (no phantom savings),
   asserted in a **two-price** scenario (the pre-existing
   complete-cover bug at solver.py:1337-1338 makes 3+-bucket
   plan-vs-recompute equality fail even at F = 0 — do not
   "strengthen" the test):
   - the allocation moves only compressible energy (buckets
     leak-normalized once before the loop); the expensive-bucket grid
     residual matches the plan (no `F × flipped-duration` shortfall);
   - a flipped slot models discharge clamped to its leak (not
     zeroed), `power_consign` consistent, budget debited by the
     compressible part only — the scenario includes **at least one
     flipped slot with `leak_i > 0`** (pins the compressible-budget
     reinterpretation of the stored buckets);
   - a **3-price** companion test asserts the normalization is applied
     exactly once (no bucket ever goes negative on revisits) —
     structured to avoid plan-vs-recompute equality so it survives
     the pre-existing solver.py:1337-1338 bug;
   - exactness is scoped to today's accounting semantics (the
