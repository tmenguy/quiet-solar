# QS-358 — Per-phase model policy by lane (rides on the templated agents of #357)

- Issue: [#358](https://github.com/tmenguy/quiet-solar/issues/358) · Lane: `feature-factory` · Parent epic: #321 (wave 3 — "Speed: per-phase model selection")
- Branch: `QS_358` · Depends on #357 (merged 2026-09-21, PR #360)
- Plan version: **v6** (v1 2026-09-22 · v2 after review round 1 + OpenCode in scope · v3 after round 2 · v4 after round 3 · v5: D16, the GUI pin writes `model` — from the user's workflow question · v6 after round 4)

## Problem

Every pipeline session runs on the same model, chosen by a hardcoded
`--model opus` in `scripts/qs/launchers/claude.py::CLAUDE_LAUNCH_OPTS`.
Sub-agents inherit whatever the parent runs. Three concrete costs:

1. **Wrong model for the phase.** A mechanical phase (`finish-task`,
   the CodeRabbit wrapper) burns Opus tokens and latency; a discovery
   phase (`create-plan`) gets no say either. There is no per-agent
   knob at all — the launcher flag wins over everything.
2. **Opus 5 over-reaches against our prompts.** Observed in this repo
   on implement, review *and* plan: unrequested fixes, unrequested
   verification, plans reinterpreted without asking. Anthropic's own
   4.8→5 migration guide documents this interaction with prompts
   "tuned for earlier models" (see "Research basis"); our 21 prompts
   are exactly that.
3. **No uniformity across surfaces.** The Claude GUI never runs the
   launcher script (so `CLAUDE_LAUNCH_OPTS` is invisible to it), and
   OpenCode has its own `model:` field that today renders a
   commented-out placeholder. The same phase can already run on three
   different models depending on how it was opened.

#357 reserved the plumbing: `render_agents.build_render_context(...,
model=...)` and a `model` frontmatter slot in every template (Claude:
`model: [[ model ]]`; OpenCode: `model: <value>` when the value is not
`inherit`, else the placeholder comment) — but nothing fills it.

## Goal

Choose the model per **lane × agent** at render time, so the
orchestrator *and* its sub-agents run on the right model for the phase,
identically on **Claude CLI, Claude GUI and OpenCode** — same phase,
same model *version*, whichever harness opened it. Decide each alias's
version in one place (`models._VERSIONS`) and keep every downstream
statement of a version in lockstep by test.

## Decisions taken in the planning session

Recorded with the reasoning so a later reader can flip them knowingly.

- **D1 — Two independent axes, not a 6-lane matrix.** Only the planning
  orchestrator's model depends on the lane (kind `bug` vs
  `feature`/`epic`). Everything else is a flat `agent → alias` map.
  The `lane × agent` contract of the issue survives as the
  `resolve(lane, stem)` signature — the lever for a later factory-lane
  cost downgrade — not as a 6-row table we don't believe in.
- **D2 — Reviewers are assigned by role, lane-invariant, deliberately
  mixed.** Four reviewers on one model share one set of blind spots; a
  mix of `opus`/`fable`/`sonnet` gives the fan-out independent failure
  modes. Model diversity is part of the adversarial design.
- **D3 — Every `opus` slot is Opus 4.8.** Rationale in "Research
  basis". Flipping it is one entry in `models._VERSIONS` plus the
  config value(s) the lockstep test then names (two for `opus`, one
  for any other family).
- **D4 — One version source, two harness forms.** `models._VERSIONS`
  (alias → version) is the only place a version is *decided*. From it:
  the Claude IDs (`claude-opus-4-8`, …) that `.claude/settings.json`
  must carry in its `env.ANTHROPIC_DEFAULT_<ALIAS>_MODEL` entries, and
  the OpenCode literals (`github-copilot/claude-opus-4.8`, …) rendered
  straight into `.opencode/agents/*.md`. Claude frontmatter carries
  **aliases only** — a full model ID in *subagent* frontmatter is
  silently ignored on current Claude Code (anthropics/claude-code#91890),
  whereas the `ANTHROPIC_DEFAULT_*_MODEL` env vars (all four families,
  `FABLE` included, are documented) are the documented way to say what
  an alias means for the main session *and* sub-agents, settable in a
  settings `env` block. A test asserts the two config files agree with
  `_VERSIONS`.
- **D5 — Both harnesses, one policy.** (Reverses v1's Claude-only
  stance at the user's request: *"ça doit être cohérent et marcher
  dans OpenCode"*.) The renderer picks the form per harness; the
  OpenCode placeholder comment disappears from every rendered agent.
- **D6 — `setup-task` → `sonnet`, `release` → `haiku`.** This replaces
  the issue's "default row applies" for the two main-checkout agents
  with explicit rows (the no-lane fallback now exists only for the
  planning row — D10). `setup-task` makes the one decision everything
  downstream depends on (the lane labels, which select the phase
  protocol *and* this policy); `haiku` is the model we'd least trust
  with that. `release` is fully scripted behind a dry-run +
  confirmation gate.
- **D7 — Review orchestrator → `fable`.** Its real job is
  consolidation: dedupe four reviewers, decide *invalid*, rank
  severity, write a fix plan precise enough to execute blind. Too much
  judgment for `sonnet`; too interactive (latency) for `opus`.
- **D8 — Fail loud on a template without a policy row, before any
  file is written.** A new `qs-*.md.j2` with no entry in `models.py`
  is a `RenderError` raised in a pre-pass over all stems — never a
  half-rendered agent set, never a silent `inherit` (repo convention:
  no silent fallback — cf. `UnknownPhaseError`). Surfaces as fatal at
  worktree birth (`setup_task.py`) and warn-and-continue at handoff
  (`next_step.py`) — the hooks' existing `(ImportError, RenderError)`
  handling, unchanged and intended. A test pins policy stems ==
  discovered templates so this is caught in CI first.
- **D9 — Drop `--model opus` from the launcher; no `--model` flag comes
  back.** The model reaches the main session through the agent's
  frontmatter **and** the worktree pin's `model` key (D16); sub-agents
  through frontmatter. **Deviation from the issue text** ("keep
  `--model` as an explicit override path" in the launcher): no launcher
  code carries an *override*; the override paths are per surface —
  Claude CLI `claude --model …` (flag beats frontmatter — S6 checks,
  non-blocking; on S6 `FAIL` the §3 comment and §7 docs drop that
  claim before task 6), Claude GUI `/model <x>` mid-session (the
  documented top-priority path — effectively **session-scoped** in a
  pinned worktree, because `/model` saves to `~/.claude/settings.json`
  — documented: *"Claude Code writes it to your user settings file"* —
  and the worktree's `settings.local.json` `model` written by the pin
  (D16) beats it at the next session start; S4 is the empirical
  check), OpenCode: edit the agent's `model:` / `opencode.json`.
  Durable change = edit the table.
- **D10 — Unknown/empty lane deviates from the issue sketch.** Issue:
  "today's behaviour (`opus` orchestrator / `inherit` sub-agents)".
  Plan: the flat table applies regardless of lane; only the planning
  row needs a lane and falls back to `opus`. `resolve()` never returns
  `inherit`. Reason: the flat rows are per-agent judgments, not lane
  judgments — a legacy unlabelled worktree should still get `haiku`
  for `finish-task`.
- **D11 — No CLI in `models.py`.** The rendered frontmatter *is* the
  visible resolved table:
  `grep -h '^model:' .claude/agents/*.md .opencode/agents/*.md`.
- **D12 — The verification spike is user-run, and a blocking FAIL
  means re-plan.** The cases need a GUI session, a `fable` main
  session and an OpenCode TUI — not agent-executable. No pre-authorised
  code fallback: a blocking FAIL halts implementation; the implementer
  commits the recorded results (story only — commit A's config stands,
  it is harmless on its own), tells the user, and does **not** run
  `next_step.py`; the user reopens `claude --agent qs-create-plan`.
- **D13 — `opencode.json` default follows the pin.** Today
  `github-copilot/claude-opus-4.6`; becomes `…/claude-opus-4.8` so an
  agent-less OpenCode session is coherent with the policy. A downstream
  consumer of `_VERSIONS`, covered by the lockstep test. (Not in the
  issue — one line, kept for coherence. **Open for the user's veto at
  FINALIZE**; the implementer proceeds and notes it in the PR body.)
- **D14 — All four families are pinned, per harness.** OpenCode
  necessarily pins literals for `fable`/`sonnet`/`haiku` too; leaving
  the Claude aliases floating would let the same phase run different
  versions across harnesses — the incoherence D5 exists to prevent.
  Cost: three more `env` lines, zero code; upgrades become a deliberate
  `_VERSIONS` edit plus the config value(s) the test names. **Verified
  by the spike for `opus` only** (the other three pins equal today's
  alias defaults, so S1/S5/S6 pass whether or not those env vars are
  honoured) — harmless by construction today; recorded in Risks.
- **D15 — S4b is informational, not blocking.** The documented
  main-session precedence list contains settings `model` and not
  `--agent` frontmatter, so whether the agent's frontmatter alone
  would beat a user-level `model` is unknown. With D16 the answer no
  longer decides correctness — it only tells us whether D16 was
  necessary or belt-and-braces, and is recorded in `harness.md`.
- **D16 — The GUI pin writes `model` next to `agent`.** The user's
  primary workflow is: open the Claude GUI on the worktree and rely on
  `settings.local.json` `"agent"` (written by the launcher's pin
  writer at every handoff). Facts established in-session: the user's
  `~/.claude/settings.json` carries `"model": "fable"` (that is where
  `/model` persists — documented); the documented settings precedence
  is project-local > shared project > user; the desktop app reads the
  same files; and no doc states whether an agent's frontmatter `model`
  beats a settings `model` for the main session. So the **documented**
  way to make the policy hold in the GUI is for the pin writer to
  write `"model": models.resolve(lane, agent)` alongside `"agent"` —
  project-local beats the user's default on every surface (the CLI
  launcher runs in the same worktree, so it benefits too), without
  relying on the undocumented precedence. Frontmatter stays the
  mechanism for sub-agents (documented) and as redundancy for the main
  session. The writer thereby **owns two keys** in the worktree's
  local file, `agent` and `model`; it still never touches any other
  key. `lane` reaches the launcher as a new `build_payload(...,
  lane=None)` kwarg — accepted-and-ignored by the codex/opencode
  launchers exactly like `caller` (`del lane`, the file's existing
  `del caller` idiom).
  **Deviation from the issue text** ("the frontmatter now decides"):
  for the *main* session the pin's `model` is the load-bearing,
  documented mechanism and frontmatter is redundancy; for sub-agents
  frontmatter decides, as the issue says. Listed in the PR body next to
  D9/D13. **Not the round-1 "Fallback B"** (C2): that was a
  spike-conditioned contingency emitting a `--model` *flag* from the
  launcher; D16 is a mechanism decided now, on a documented settings
  path, with no flag — D12's "no pre-authorised code fallback" stands.
  Scope: the pin writer is guarded to real worktrees, so the
  main-checkout agents (`qs-setup-task`, `qs-release`) and the
  post-merge render on `main` get **no** pin — their main-session model
  rests on frontmatter alone (Risks). Sub-agents without frontmatter
  (Claude Code's built-ins, e.g. `Explore`) inherit the main
  conversation's model, i.e. the pinned alias — unchanged from today;
  all 21 pipeline agents carry frontmatter. `ANTHROPIC_MODEL` exported
  in the user's shell would beat any settings `model` (documented) —
  not our case; noted in Risks.

## Design

### 1. Policy module — `scripts/qs/models.py` (new)

Sibling top-level module under `scripts/qs/`, `from __future__ import
annotations` header like its siblings. Imports: `targets` (bare
`import targets  # type: ignore[import-not-found]`, same idiom as
`render_agents.py`). **Must not** import `render_agents` — the renderer
imports this module; the dependency is one-way. No `re`.

```python
# What resolve() may return. Matches the issue's test spec exactly.
# ("inherit" is a renderer/template concern and never appears here.)
ALIASES: frozenset[str] = frozenset({"fable", "opus", "sonnet", "haiku"})

# Six lanes, derived from targets.py (both are tuples → stable order):
# f"{k}-{t}" for k in KINDS for t in TARGETS, plus f"epic-{t}" for t in TARGETS.
LANES: tuple[str, ...]

# --- versions: the ONE place a model version is decided (D4/D14) -----------
_VERSIONS: dict[str, str] = {"opus": "4.8", "fable": "5.1", "sonnet": "5", "haiku": "4.5"}
OPENCODE_PROVIDER = "github-copilot"

def _claude_id(alias: str) -> str:   # "claude-opus-4-8"
    return f"claude-{alias}-{_VERSIONS[alias].replace('.', '-')}"
def _opencode_id(alias: str) -> str: # "github-copilot/claude-opus-4.8"
    return f"{OPENCODE_PROVIDER}/claude-{alias}-{_VERSIONS[alias]}"

CLAUDE_MODEL_IDS: dict[str, str] = {a: _claude_id(a) for a in ALIASES}
OPENCODE_MODELS: dict[str, str] = {a: _opencode_id(a) for a in ALIASES}
# (all four OpenCode literals are in `opencode models` on OpenCode 1.14.31 — re-checked by spike S0)

# --- the table -------------------------------------------------------------
_PLANNING: frozenset[str] = frozenset({"qs-create-plan", "qs-diagnose-task"})

_FLAT: dict[str, str] = {                    # 19 lane-invariant rows
    "qs-plan-critic": "opus",
    "qs-plan-concrete-planner": "opus",
    "qs-plan-dev-proxy": "fable",
    "qs-plan-scope-guardian": "fable",
    "qs-plan-delta-auditor": "sonnet",
    "qs-diag-root-cause-skeptic": "opus",
    "qs-diag-fix-minimalist": "fable",
    "qs-implement-task": "opus",
    "qs-implement-setup-task": "opus",
    "qs-review-task": "fable",
    "qs-verify-task": "fable",
    "qs-review-blind-hunter": "opus",
    "qs-review-edge-case-hunter": "opus",
    "qs-review-acceptance-auditor": "fable",
    "qs-review-regression-proof": "fable",
    "qs-review-coderabbit": "haiku",
    "qs-finish-task": "haiku",
    "qs-setup-task": "sonnet",
    "qs-release": "haiku",
}

STEMS: frozenset[str] = frozenset(_FLAT) | _PLANNING   # 21

class ModelPolicyError(ValueError): ...      # unknown stem only

def _planning_alias(lane: str | None) -> str:
    """Exact membership in LANES: a `bug-*` lane → "opus"; any other LANES
    member (`feature-*`, `epic-*`) → "fable"; anything else (None, "",
    "feature-nope", …) → "opus". A lane label is data and never raises
    (same stance as targets.parse_axes)."""

def resolve(lane: str | None, stem: str) -> str:
    """Alias for ``stem`` under ``lane`` — always a member of ALIASES.
    Unknown ``stem`` → ModelPolicyError (a stem is code, not data)."""

def to_opencode(alias: str) -> str:
    """``OPENCODE_MODELS[alias]``. Plain dict lookup — an unknown alias
    (including "inherit") is a programmer error and raises KeyError."""
```

Reading the table by role — fan-out diversity (D2): plan round =
`opus, opus, fable, fable` (+ `sonnet` delta-auditor from round 2);
review round = `opus, opus, fable, fable` (+ `haiku` wrapper); diag
round = `opus, fable`. Planning orchestrators: `bug` → `opus` (causal
chain), else `fable` (conversation). Implement: `opus` both.

### 2. Renderer — `scripts/qs/render_agents.py`

- `import models  # type: ignore[import-not-found]` at module top
  (sibling block with `targets`).
- `build_render_context(..., model: str | Mapping[str, str] | None = None)`.
  The default is now `None`; the returned context still carries the
  `model` key (**value `None` means "policy"**). No new key — the
  "always returns every key" contract is unchanged. Docstring states:
  an explicit `str` / `Mapping` is an override; an override value that
  is an alias is translated per harness, any other value (a provider
  literal, `"inherit"`) is emitted verbatim on both.
- `render_all` — **pre-pass, right after `model_spec =
  context.get("model", "inherit")` (~L363) and before the stem loop**:
  build `claude_model: dict[str, str]` for every discovered stem, then
  derive the OpenCode value per stem from it. Nothing is written until
  every stem has a value (D8 / AC4):
  - **`model_spec is None`** → `claude_model[stem] =
    models.resolve(context.get("lane"), stem)`, inside its own
    `try/except models.ModelPolicyError as exc: raise RenderError(f"no
    model policy row for agent {stem!r}; add it to
    scripts/qs/models.py") from exc` (the existing `try` blocks wrap
    only `get_template` and `render`, so this needs its own).
  - otherwise → `claude_model[stem] = _resolve_model(model_spec, stem)`
    exactly as today (returns `str`; `"inherit"` default for a partial
    Mapping is legal and unchanged; `_resolve_model`'s annotation is
    untouched because `None` never reaches it).
  - `opencode_model[stem] = models.to_opencode(v) if v in
    models.ALIASES else v` where `v = claude_model[stem]` — an alias is
    translated (this is what makes an explicit `model="opus"` valid on
    OpenCode); a provider literal (`github-copilot/x`) or `"inherit"`
    is emitted verbatim (the template prints its placeholder for
    `inherit`). `to_opencode` can therefore never raise from here.
- Inside the existing per-harness loop, `render_ctx["model"]` (the key
  the templates read as `[[ model ]]`, built per `(stem, harness)` at
  ~L382-390) becomes `claude_model[stem]` for `claude` and
  `opencode_model[stem]` for `opencode`.
- Docstring of `render_all` (~L334, "`context=None` means
  `build_render_context(work_dir)` with defaults") gains: "…which now
  resolves the model per agent from `models.py`".
- No template change: the OpenCode expression already prints
  `model: <value>` when the value is not `inherit`, on its own line
  (valid YAML either way — verified).
- Both callers (`setup_task.py` ~L223, `next_step.py` ~L215) already
  omit `model=` — they move onto the policy path with no edit.

### 3. Launcher — `scripts/qs/launchers/claude.py`

- `CLAUDE_LAUNCH_OPTS = "--dangerously-skip-permissions"` (D9).

  - `import models  # type: ignore[import-not-found]` placed above
    `from utils import is_worktree` in the same block (plain `import`

    "``utils`` is a sibling top-level module" to "``models`` and

  failure the handoff therefore pins `resolve(None, agent)` (`opus` for

  re-render, and the next handoff repairs both. `setup_task.py` —
  `lane = targets.parse_axes(labels)["lane"] or None` (labels are
  bound at L182, before the `--no-worktree` branch; `targets` is

### 5. Verification spike — **task 2**, user-run

The design rests on runtime claims not proven on the installed
versions (Claude Code `2.1.270`, OpenCode `1.14.31`; the relevant
upstream reports are on Claude Code `2.1.220`–`2.1.275`).

**Mechanics.** The implementer prints, in one message and in table
order S0→S7, one script block per case (file to edit, exact `model:`
line, command, oracle path), then **ends its turn and waits** — no
polling. The user runs the cases and pastes results back; the
implementer records them under `## Spike results` (new section
**between "Risks" and "Adversarial Review Notes"**) with both tool
versions. Cases S1, S2, S4, S4b, S4c, S5, S6 all edit
`.claude/agents/qs-finish-task.md` in turn — the table order is the
edit order. Two kinds of hand-edits, both on gitignored files: the
*rendered* agent files (`model:` line), and — for the Claude cases —
the worktree's `.claude/settings.local.json`, **edited by key only**
(`agent`, `model`; never replace the file — it carries the user's
accumulated `permissions`). That file currently pins *this* session's
agent (`qs-implement-setup-task`): every case that sets `"agent":
"qs-finish-task"` must **restore it, and remove the `model` key,
before the next case** — the "local pin" column below is the required
state per case. **Do not run `next_step.py` or `render_agents.py`
during the spike** (they re-render over the edits; nothing else does —
no `SessionStart` hook exists). Every case runs with **task 1
committed** (commit A), the user's `~/.claude/settings.json` left as
is (`"model": "fable"` — that is part of what is under test), and **no
shell export** of any `ANTHROPIC_*` variable.

Why the local pin is set for the blocking CLI cases too: under D16 the
*shipped* configuration always carries `model` in the local pin, so
S1/S2/S5 must test that configuration. S4b is the one case that
measures "frontmatter alone" — informational (D15).

### Research basis (why D3 — recorded for the reversal)

Honest framing first: the sources below support *"same pass rate,
smaller footprint, fewer unasked changes"* on 4.8 — not *"Opus 5 is a
worse model"* (it is the more capable one). Anthropic's documented
remedy is **prompt edits**; we chose the pin over that remedy because
re-tuning 21 prompts is a project of its own, and the pin is one
`_VERSIONS` entry (plus the test-named config values) to undo.

- **Anthropic, "Migrating to Claude Opus 5" (from 4.8), Recommended
  changes 5–6:** *"Default visible responses and written deliverables
  run longer on Claude Opus 5 than on Claude Opus 4.8"*; *"Claude Opus
  5 verifies its own work without being told to, so remove explicit
  verification or self-check instructions carried over from prompts
  tuned for earlier models; leaving them in causes over-verification.
  For narrow tasks, constrain the task scope explicitly… Claude Opus 5
  delegates more readily than earlier models."*
- **stet.sh, "Opus 4.8 vs Opus 5 on 25 tasks — same score, different
  routes" (2026-08-26):** 9/25 strict passes each; 4.8 smaller patch
  footprint on **20/25**; Opus 5 touched more files, added an unasked
  141-line e2e test, and on one task *"renamed one required test, and
  omitted another"* where 4.8 passed. Recommendation: *"Opus 4.8 on
  contained work where the owner is known and patch surface is
  expensive"* — our implement/review phases; discovery-heavy planning
  runs on `fable` here.
- **Community (asked for by the user):** "Why does Opus 5 feel worse to
  work with?" (HN, 993 pts) — fewer clarifying questions,
  *"reinterpret[s] or update[s] my plans without asking"*; in this
  pipeline the plan is the contract.
- **Practicalities:** Opus 4.8 is *Active (legacy)*, same price as
  Opus 5, same 1M context, retirement *not sooner than 2027-05-28*;
  available on `github-copilot` in OpenCode.
- **Mechanism (D4):** claude-code#91890 (open) — full ID in subagent
  frontmatter ignored; claude-code#82359 (controlled experiment) —
  alias frontmatter honoured; Claude Code model-config docs —
  `ANTHROPIC_DEFAULT_<FAMILY>_MODEL` (OPUS/FABLE/SONNET/HAIKU) sets
  what an alias means, settable in a settings `env` block.

## Risks

- **Upstream model-resolution flakiness — accepted, undetectable by
  us, no mitigation.** claude-code#95550: runs that start on
  `claude-opus-4-8` self-correct to `claude-opus-5` mid-execution;
  #95303: `--model` ignored in ~50% of runs on 2.1.275. The spike's
  single-turn oracle cannot see mid-run drift; nothing in this plan
  claims otherwise.
- **Main-session frontmatter precedence is undocumented** (the
  documented list is `/model`, `--model`, `ANTHROPIC_MODEL`, settings
  `model`, `ANTHROPIC_DEFAULT_MODEL` — `--agent` frontmatter is not in
  it). D16 routes the GUI through the *documented* settings `model`
  path so correctness no longer hangs on it; S1/S4/S4c still verify
  the shipped configuration (blocking), S4b/S6 refine the wording only
  (D15/D9). A blocking bad answer is a re-plan, not a patch (D12).
- **The pin now overrides a user's per-worktree `model`.** By design
  (that *is* the policy), and the user's `/model` default lives at
  user level, untouched. Documented in `harness.md`; a one-off
  override is `/model` for the session (and `claude --model`, if S6
  confirms it).
- **Main-checkout agents get no pin.** The writer is guarded to real
  worktrees, so `qs-setup-task` / `qs-release` (and any session on
  `main`) rely on frontmatter alone for the main-session model — the
  undocumented precedence D16 sidesteps elsewhere. Low stakes: both are
  short, user-driven phases; S4b tells us whether frontmatter suffices.
- **`ANTHROPIC_MODEL` in the user's shell would beat every settings
  `model`** (documented). Not set on this machine; a one-line note in
  `harness.md`.
- **The `fable`/`sonnet`/`haiku` env pins are unverified at runtime**
  (D14): they equal today's alias defaults, so no spike case can tell
  "pin honoured" from "default happened to match". Harmless today; the
  first time one of them is bumped away from the default, that bump is
  the test.
- **The pins govern the user's own `/model opus` (etc.)** in this repo
  and the agent-less OpenCode default. Intended; documented in
  `harness.md`.
- **Pinned versions retire** (Opus 4.8 not before 2027-05-28) → loud
  failure at launch; the lockstep test names every place to bump.
- **OpenCode sub-agent model is only best-effort observable**
  (S7-note). OpenCode's docs: a sub-agent uses its own `model:` when
