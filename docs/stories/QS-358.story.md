## Problem

Every pipeline session runs on the same model, chosen by a hardcoded
`--model opus` in `scripts/qs/launchers/claude.py::CLAUDE_LAUNCH_OPTS`.
Sub-agents inherit whatever the parent runs. Three concrete costs:

1. **Wrong model for the phase.** A mechanical phase (`finish-task`,
   the CodeRabbit wrapper) burns Opus tokens and latency; a discovery
   phase (`create-plan`) gets no say either. There is no per-agent
   knob at all — the launcher flag wins over everything.
2. **Opus 5 over-reaches against our prompts.** Observed in this repo
   on implement, review *and* plan: unrequested fixes, unrequested
   verification, plans reinterpreted without asking. Anthropic's own
   4.8→5 migration guide documents this interaction with prompts
   "tuned for earlier models" (see "Research basis"); our 21 prompts
   are exactly that.
3. **No uniformity across surfaces.** The Claude GUI never runs the
   launcher script (so `CLAUDE_LAUNCH_OPTS` is invisible to it), and
   OpenCode has its own `model:` field that today renders a
   commented-out placeholder. The same phase can already run on three
   different models depending on how it was opened.

#357 reserved the plumbing: `render_agents.build_render_context(...,
model=...)` and a `model` frontmatter slot in every template (Claude:
`model: [[ model ]]`; OpenCode: `model: <value>` when the value is not
`inherit`, else the placeholder comment) — but nothing fills it.

## Goal

Choose the model per **lane × agent** at render time, so the
orchestrator *and* its sub-agents run on the right model for the phase,
identically on **Claude CLI, Claude GUI and OpenCode** — same phase,
same model *class*, whichever harness opened it, and the same model
*version* wherever both harnesses offer that model. One
harness-agnostic **class** per agent; one complete **class → exact
model ID** row per harness (D18/D20), rendered straight into every
agent's frontmatter; `opencode.json` kept in lockstep by test.

## Decisions taken in the planning session

Recorded with the reasoning so a later reader can flip them knowingly.

- **D1 — Two independent axes, not a 6-lane matrix.** Only the planning
  orchestrator's model depends on the lane (kind `bug` vs
  `feature`/`epic`). Everything else is a flat `agent → class` map.
  The `lane × agent` contract of the issue survives as the
  `resolve(lane, stem)` signature — the lever for a later factory-lane
  cost downgrade — not as a 6-row table we don't believe in.
- **D2 — Reviewers are assigned by role, lane-invariant, deliberately
  mixed.** Four reviewers on one model share one set of blind spots; a
  mix of `deep`/`frontier`/`light` classes gives the fan-out
  independent failure modes. Model diversity is part of the
  adversarial design.
- **D3 — The `deep` class is Opus 4.8, on both harnesses.** Rationale
  in "Research basis". Flipping it is the two `deep` cells of
  `HARNESS_MODELS` plus `opencode.json`, which the lockstep test then
  names.
- **D4 — Per-harness model rows, both in exact model IDs.** (v8
  replaced v4–v7's "one version source, derived forms" — spike S0
  disproved the same-family assumption for `fable` on `github-copilot`;
  **v11 replaces v8–v10's "Claude row = aliases + `env` pins"** — spike
  Run 2 disproved the pin, D20.) `HARNESS_MODELS["claude"]` maps each
  class to a **full Claude model ID** (`claude-opus-4-8`,
  `claude-fable-5-1`, `claude-sonnet-5`, `claude-haiku-4-5`) rendered
  straight into frontmatter — proven on Claude Code 2.1.278 for
  sub-agents, `--agent` CLI sessions and settings-pinned (GUI-path)

## Design

### 1. Policy module — `scripts/qs/models.py` (new)

Sibling top-level module under `scripts/qs/`, `from __future__ import
annotations` header like its siblings. Imports: `targets` (bare
`import targets  # type: ignore[import-not-found]`, same idiom as
`render_agents.py`). **Must not** import `render_agents` — the renderer
imports this module; the dependency is one-way. No `re`.

```python
# --- classes (D18): the policy's own, harness-agnostic vocabulary ----------
# deep     — the best code-grounded model: implement, concrete-planner, hunters, root-cause
# frontier — the best general reasoner: planning conversation, consolidation, judgment
# light    — checklists: delta-auditor, setup-task
# fast     — mechanical: finish, CodeRabbit wrapper, release
CLASSES: frozenset[str] = frozenset({"deep", "frontier", "light", "fast"})
# ("inherit" is a renderer/template concern and never appears here.)

# Six lanes, derived from targets.py (both are tuples → stable order):
# f"{k}-{t}" for k in KINDS for t in TARGETS, plus f"epic-{t}" for t in TARGETS.
LANES: tuple[str, ...]

# --- one complete class → model row per harness (D4/D17/D18/D20) ------------
# Keys mirror render_agents._HARNESSES (test-enforced). Each row speaks the
# harness's own vocabulary, and BOTH rows name exact versions: Claude Code
# takes full model IDs in frontmatter (proven on 2.1.278 for sub-agents,
# --agent sessions and settings-pinned sessions — spike Run 2; aliases
# would float to the provider default because the settings `env` pin is
```

### Research basis (why D3 — recorded for the reversal)

Honest framing first: the sources below support *"same pass rate,
smaller footprint, fewer unasked changes"* on 4.8 — not *"Opus 5 is a
worse model"* (it is the more capable one). Anthropic's documented
remedy is **prompt edits**; we chose the pin over that remedy because
re-tuning 21 prompts is a project of its own, and the pin is two
`HARNESS_MODELS` cells (plus `opencode.json`, test-named) to undo.

- **Anthropic, "Migrating to Claude Opus 5" (from 4.8), Recommended
  changes 5–6:** *"Default visible responses and written deliverables
  run longer on Claude Opus 5 than on Claude Opus 4.8"*; *"Claude Opus
  5 verifies its own work without being told to, so remove explicit
  verification or self-check instructions carried over from prompts
  tuned for earlier models; leaving them in causes over-verification.
  For narrow tasks, constrain the task scope explicitly… Claude Opus 5
  delegates more readily than earlier models."*
- **stet.sh, "Opus 4.8 vs Opus 5 on 25 tasks — same score, different
  routes" (2026-08-26):** 9/25 strict passes each; 4.8 smaller patch
  footprint on **20/25**; Opus 5 touched more files, added an unasked
  141-line e2e test, and on one task *"renamed one required test, and
  omitted another"* where 4.8 passed. Recommendation: *"Opus 4.8 on
  contained work where the owner is known and patch surface is
  expensive"* — our implement/review phases; discovery-heavy planning
  runs on the `frontier` class here (Fable 5.1 on Claude).
- **Community (asked for by the user):** "Why does Opus 5 feel worse to
  work with?" (HN, 993 pts) — fewer clarifying questions,
  *"reinterpret[s] or update[s] my plans without asking"*; in this
  pipeline the plan is the contract.
- **Practicalities:** Opus 4.8 is *Active (legacy)*, same price as
  Opus 5, same 1M context, retirement *not sooner than 2027-05-28*;
  available on `github-copilot` in OpenCode.
- **Opus 5.5 (2026-09-22, D21):** cheaper ($4 / $20), faster, fewer
  tokens per task, stronger code review per Anthropic — but no
  documented change on scope discipline, Opus-5 prompting patterns
  still "a reasonable starting point", release-day evidence only, and
  Claude Code ≥ 2.1.280 required. Not adopted in this story; revisit
  trigger and path recorded in D21.
- **Mechanism (D4 → D20):** the plan first relied on aliases +
  `ANTHROPIC_DEFAULT_<FAMILY>_MODEL` in a settings `env` block (Claude
  Code docs: documented, "any file", "for every session"), avoiding
  full IDs because claude-code#91890 reported them ignored in subagent
  frontmatter on 2.1.259. **Spike Run 2 on 2.1.278 inverted both
  facts:** the `env` block is not applied to the process (alias
  floats to Opus 5 — reproduced independently by the planner), and a
  full ID in frontmatter works on every Claude surface. The plan now
  follows the measured behaviour, and the post-render smoke (task 7)
  re-measures it on every upgrade.

## Risks

- **Upstream model-resolution flakiness — accepted, undetectable by
  us, no mitigation.** claude-code#95550: runs that start on
  `claude-opus-4-8` self-correct to `claude-opus-5` mid-execution;
  #95303: `--model` ignored in ~50% of runs on 2.1.275. The spike's
  single-turn oracle cannot see mid-run drift; nothing in this plan
  claims otherwise.
- **Main-session frontmatter precedence is undocumented — but now
  measured** (Run 2): an agent's frontmatter `model` beats a settings
  `model` on every surface, on 2.1.278. Version-dependent by nature
  (#91890 said the opposite for sub-agents on 2.1.259); the
  post-render smoke (task 7) re-measures the shipped agents, and any
  upgrade that flips it shows up there before it shows up in a phase.
- **The documented settings `env` block does nothing on 2.1.278**
  (D20). If a later Claude Code applies it, nothing breaks — the
  frontmatter IDs still win; the `"env" not in settings.json` test just
  documents that we don't rely on it. Worth an upstream report.
- **No repo-wide alias pin.** A hand-typed `/model opus` or `--model
  opus` is the provider default — Opus 5 today, Opus 5.5 once Claude
  Code moves the alias; the pipeline agents are pinned by their
  frontmatter. Documented in `harness.md`. (`claude --model
  claude-opus-4-8` still works for a one-off.)
- **A pinned ID that the installed Claude Code does not know fails
  loudly** — `400 … version X or newer is required` (observed for
  `claude-opus-5-5` on 2.1.278). Good failure mode for a deliberate
  pin; it also means a future `deep` → 5.5 flip (D21) requires the CLI
  upgrade first, and the task-7 smoke is the check.
- **Main-checkout agents get no pin.** The writer is guarded to real
  worktrees, so `qs-setup-task` / `qs-release` (and any session on
  `main`) get their **model** from frontmatter — which Run 2 proved
  sufficient (S4b) — but their **effort** stays the user's default
  (frontmatter `effort` does not reach the main session, S8, and there
  is no pin on `main`). Low stakes: both are short, user-driven phases.
- **`ANTHROPIC_MODEL` in the user's shell would beat every settings
  `model`** (documented). Not set on this machine; a one-line note in
  `harness.md`.
- **The `frontier` class on OpenCode is a non-Claude model (D17).** Eight
  slots — including both review orchestrators and the feature-lane
  planning orchestrators — run GPT-6 Astra there, with prompts tuned
  on Claude models. Quality unvalidated; OpenCode is the secondary
  surface; one dict entry to revert.
- **Effort levels "depend on the model"** (D19). A level the pinned
  model rejects might error at launch or be silently clamped; today's
  values (`high`/`medium`) are within every current Claude model's
  range (which is why the spike probes with `medium`, not `low`), and
  `fast` (Haiku 4.5) sets none. S8b is the blocking check (documented
  settings key, GUI); S8/S8c only record — sub-agent `effort` is the
  documented path.
- **`opencode run --agent` and the raw OpenCode API ignore the agent's
  `model`** (Run 2, source-verified at v2.0.14): they use the project
  default (`opencode.json`, = `deep`). The policy holds in the TUI and
  for task-tool sub-agents (S7-note). Documented in `harness.md`; the
  pipeline does not use `opencode run`.
- **The OpenCode catalogue drifts under our feet** — `fable` was listed
  at plan time (1.14.31) and gone by the spike (v2.0.14). The literal
  tests pin what *we* say, not what the provider serves; only S0 at
  spike time checks the catalogue. A later disappearance surfaces as
  an OpenCode launch error, not as a red test.
- **Full-ID frontmatter was proven at runtime for `claude-opus-4-8`
  (T1/T3/S3-control) but S1/S5/S6 sent *aliases* whose defaults
  happened to equal the pinned IDs** — `claude-fable-5-1`,
  `claude-sonnet-5`, `claude-haiku-4-5` as literal frontmatter values
  were not sent in Run 2. The task-7 smoke sends two of them
  (`claude-sonnet-5`, `claude-fable-5-1`); `claude-haiku-4-5` stays
  unsmoked (no read-only `fast` agent). Low risk: same ID scheme,
  documented as accepted by `--model`.
- **Pinned versions retire** (Opus 4.8 not before 2027-05-28) → loud
  failure at launch; the flip is two `HARNESS_MODELS` cells (+
  `opencode.json` for `deep`, which the lockstep test names).
- **OpenCode sub-agent model is only best-effort observable**
  (S7-note). OpenCode's docs: a sub-agent uses its own `model:` when
  set, else the invoking primary's — we rely on the docs if the TUI
  shows nothing.
- **`frontier` on the review orchestrator** (D7) is a judgment call
  (Fable 5.1 on Claude, GPT-6 Astra on OpenCode); reversible in one
  cell.
- **Cost**: factory lanes run `deep` (Opus 4.8) for implement and two
  reviewers per fan-out. Accepted for depth; the lane axis is the
  reserved lever.
