# QS-406 — The Control Plane's active loop: tick hooks, restart and self-check, detectors, CI watcher, liveness and watchdog, backups

Issue: [#406](https://github.com/tmenguy/quiet-solar/issues/406) · epic
[#369](https://github.com/tmenguy/quiet-solar/issues/369) child 14 · lane
feature × factory · target `factory` → `implement-setup-task` · built on the
frozen pipeline.

Status: **v11 (final; reviewed through round 9; decisions settled with the
maintainer on 2026-10-09, see "Decisions settled with the maintainer")**.

## Problem

#399 shipped the Control Plane's daemon as a **skeleton**:

- a singleton `flock`;
- migration on start;
- a lease (holding the schema version);
- a heartbeat;
- an idle exit;
- `daemon.run(…, tick_hooks=…)`.

But `cli._daemon` passes no hooks, and there is no registration point. So
nothing *watches* the runs:

- a red CI, a dead node, a stalled orchestrator, or two tasks editing the
  same files go unnoticed until a session happens to look;
- new Control Plane code merged on `main` keeps running in the old daemon
  until it idles out, and nothing checks the new code before automatic
  merges continue;
- the DB is backed up only before a migration, so a lost or corrupt
  `harness_state.db` loses every run.

Child 15 (the cross-run pilot), #375 (red CI as a ledger finding) and child 7
(merge conditions) need this loop's outputs: the registration point, the
alert kinds, the alert read path and `tasks.ci_state`.

## Goal

The daemon becomes the **active loop** of epic view 7. It is one Python
process for all runs, and it **watches and alerts but never decides**.

1. **A tick-hook registration point** in a module the CLI imports. Child 15
   registers its pilot on it.
2. **Alerts:**
   - the alert kinds, as constants;
   - `ROUNDS_ALERT` (5);
   - a fingerprint helper;
   - an occurrence engine: an alert is raised once per occurrence, and again
     when it recurs;
   - a **read path**: `alerts` in `snapshot`.
3. **The lifecycle:**
   - restart on any new Control Plane code, cleanly while runs are in flight;
   - a post-merge self-check. Automatic merges are refused until the
     self-check has passed for the code on disk:
     - while it is pending, `tool merge` gets a retryable `BUSY`;
     - when it has failed, every run is alerted;
   - the state lives in the DB, and `tool merge` checks it before the merge
     policy;
   - a passing self-check opens the gate, and so does the maintainer, through
     the orchestrator, after approving a prompt in the app.
4. **Detectors**, in every run and across runs:
   - overlap;
   - a stalled node;
   - too many rounds;
   - state anomalies;
   - dependency cycles;
   - the same task discovered twice.
5. **Hook-event routing:** the `hook_events` alerts reach their run's
   orchestrator queue through a cursor kept in the DB.
6. **A CI watcher** for every open PR, within GitHub's API budget:
   - it writes `tasks.ci_state` / `ci_sha` (`pending | green | red`);
   - a red check becomes a must-fix alert.
7. **Liveness** of nodes and orchestrators, and a **watchdog** that wakes a
   stalled orchestrator. It tries, in order:
   1. the inbox socket, when T1 establishes it (D1);
   2. a one-shot `--bg` messenger;
   3. "orchestrator not listening".

   The socket token is a secret.
8. **Periodic backups** with rotation, a `backup_failed` alert (an
   addition, under "watches and alerts"), and a **restore** command.

## Decisions

These are proposals unless marked otherwise. Items marked **(open)** are the
maintainer's to confirm; each has a default the implementation follows.

- **D1 — the inbox socket (open).**
  - **What the docs say** (code.claude.com/docs/en/cross-session-messaging,
    read 2026-10-09):
    - the transport is a Unix socket at `$CLAUDE_CODE_MESSAGING_SOCKET`;
    - an optional first line, `{"type":"auth","token":"<CLAUDE_CODE_MESSAGING_TOKEN>"}`;
    - a connection with no complete line within 30 s is closed;
    - an idle CLI session that receives a delivered message starts a new
      turn;
    - `crossSessionInbound` is `accept | hold | refuse`;
    - a sender that does not prove its identity "asserts no permission class".
  - **Not documented:**
    - the payload schema;
    - the response;
    - whether the path changes across an engine restart;
    - whether a post wakes an idle *desktop* session;
    - whether the token is needed on macOS.

    Reading the format out of the Claude Code binary was refused by the
    auto-mode classifier in the plan session. No workaround was tried.
  - **Default:**
    - **T1** (manual, with the maintainer) runs **before T11a**. It is the
      only task that waits on him; T2–T10 do not depend on it.
    - **If T1 establishes the format,** the whole "socket bundle" ships as
      the first rung, enabled. The bundle is:
      - `inbox.py`;
      - the `session_inbox` table: a statement appended to migration v2,
        which is still unmerged at that point;
      - `hook session-start`;
      - `run open` recording the inbox;
      - the `hooks_settings` additions;
      - the socket bullets of AC 12 and the inbox bullets of AC 14.
    - **If it does not,** the bundle is **not built**. It moves to a
      follow-up issue whose body is T1's record, and the ladder is
      messenger → "not listening". The issue's "verified once and recorded"
      Done-when bullet is then met by T1's negative record.
    - **The maintainer runs T1** (maintainer, 2026-10-09: "I'll be available
      to do T1"). T1 is a required step before T11a, never skipped.
    - **The follow-up issue:** the implement agent writes its ready-to-paste
      body (T1's record plus `Refs #369`, labels `target:factory`,
      `kind:feature`, `scale:task`) into "Implementation notes". The
      maintainer files it at review or finish: issue creation stays
      outside the implement phase.
- **D2 — who opens a closed gate, and who restores (maintainer,
  2026-10-09).**
  - The maintainer does not use a terminal. He asks the **orchestrator**,
    which runs `cp.py halt clear --reason TEXT` (or `cp.py restore
    --confirm`).
  - The `PreToolUse` hook answers **`ask`** (`hookSpecificOutput.
    permissionDecision: "ask"`) for any Bash segment that invokes `cp.py
    halt clear` or `cp.py restore`. The app then shows the maintainer an
    approval prompt, and nothing runs until he approves it. That prompt is
    the guard.
  - Both commands are exempt and take no token: the DB may have no open
    run, or be lost (restore).
  - The guard covers agent *mistakes*, which is #399's threat model, not
    adversaries. A command that slips past the Bash-segment matcher (a
    wrapper, `bash -c '…'`) is not caught, like #399's other matchers;
    this is written down as a convention.
  - **The prompt depends on the permission mode.** `maintainer_confirm`
    reads `permission_mode` from the hook's input. It answers `ask` only in
    the modes listed in `hooks.ASK_MODES`: the modes where T1 saw a real
    approval prompt. The default before T1 is `{"default", "acceptEdits"}`.
    T1 tests `default`, `auto` and `bypassPermissions`, and adds each mode
    that prompts.
  - **In any other mode it answers `deny`**, with the hint "switch this
    session to default mode in the app, then ask again". So an orchestrator
    in `auto` or full-permission mode can never clear a halt or restore by
    mistake.
  - **If no mode prompts at all,** T1 records it. Until child 8's board
    button exists, the fallback is the maintainer running the command in the
    app's shell-command prefix (`!`), if T1 confirms the desktop app
    supports it; T14 documents whichever applies.
  - A later **board button** (child 8) calls the same functions
    (`mergegate.override`, `restore.restore`); that is child 8's to wire.
  - A clear is an **override for the current code version only**. For that
    version, the self-check stops retrying and stops raising
    `selfcheck_failed`. The override is keyed on the version, so it does not
    apply to other code. If the code later returns to that exact version (a
    revert), the override applies again, by design: same code, same
    decision.
  - The `tool merge` refusal never names the command. It says "ask the
    maintainer", so the orchestrator escalates instead of clearing on its
    own; the `ask` prompt backs this up.
- **D3 — the self-check's content (open).** Default (§4.3):
  - `schema`: the schema version and `PRAGMA quick_check`;
  - `entry`: one subprocess, `<MAIN>/venv/bin/python cp.py version`, which
    runs the code on disk;
  - `registry`: the built-in tools, commands and tick hooks are present.

  It runs only while the daemon's loaded code **is** the code on disk.
  Failures are retried (D18).

  v2's second subprocess (`hooks-settings --role orchestrator`) is dropped:
  - `entry` already imports `hooks` through `cli`;
  - `test_hooks.py::TestHooksSettings` proves the settings' content.
- **D4 — thresholds (open).** Default: §4.4.
- **D5 — the alert read path is a table.**
  - A new `alerts` table holds one row per (run, occurrence), for detector
    alerts and routed hook alerts alike.
  - `snapshot["alerts"]` lists every open row plus the `ALERTS_LIMIT` newest
    cleared ones.
  - The raw `hook_events` alerts move to `snapshot["hook_alerts"]`, so
    unroutable ones stay visible.
  - This is the issue's "join `alerts` (and its golden) or get a table"
    fork, taken deliberately. Only tests consume the old key (§11): no agent
    template or workflow doc reads it (checked 2026-10-09).
- **D6 — fingerprints.**
  - The format is `"<kind>:<sha256(subject)[:16]>:<n>"`, where `n` is the
    occurrence counter: 1 plus the number of earlier `alerts` rows for the
    same (run, kind, subject).
  - The fingerprint is the message `dedupe_key`. `messages` is
    `UNIQUE (run_id, dedupe_key)` (schema v1), so posting to two runs gives
    two messages.
  - A condition that should be raised again per value puts that value in its
    **subject**: the CI sha, the round, a lock's `acquired_at`.
  - Every clear → recur cycle gets a new `n`, so the alert is raised again,
    and two occurrences at the same instant never collide.
- **D7 — restart = exit + respawn.**
  1. The daemon finishes its tick and leaves its loop with `exit:
     "new_code"`.
  2. Its lease is cleared and its `flock` released.
  3. `cli._daemon` calls `ensure`, which starts the new code from disk.

  If the new daemon never starts, no pass is recorded for its version, so
  merges stay closed (§4.2). The trigger is debounced: the new version must
  read the same on two consecutive ticks, and no git operation may be in
  progress in the main checkout (`index.lock`, `MERGE_HEAD`, `rebase-merge`
  or `rebase-apply` under `.git/`).
- **D8 — the code version.**
  - It is a sha256 over the sorted relative paths and contents of
    `scripts/qs/control_plane/**/*.py`, `scripts/qs/cp.py`,
    `scripts/qs/models.py` and `scripts/qs/targets.py`. The messenger
    imports `models`, which imports `targets`.
  - **A test pins the set.** It runs in a **real subprocess** (`python -I -c
    …`), because an xdist worker's `sys.modules` also holds the modules of
    sibling tests.
    - The subprocess inserts `scripts/qs` into `sys.path` the way `cp.py`
      does, then runs `import control_plane.cli; from control_plane import
      activeloop; activeloop.register_builtin()`. It computes **both** sets
      itself and prints them as JSON for the parent to assert on (the
      parent's `paths` are patched to `fake_main`).
    - It asserts that every loaded module file under `scripts/qs` is in
      `codever.hashed_files(paths.code_root())` (the function `code_version`
      is built on), comparing paths relative to `scripts/qs`. The test is
      therefore correct from a linked worktree too.
    - It asserts that the hashed set's members outside `control_plane/` are
      exactly `{cp.py, models.py, targets.py}`. `cp.py` is the entry script
      and is never loaded as a module. `models` is imported lazily in
      `watchdog._messenger_model()` (see "Implementation notes": the purity
      test allows only that lazy import), so the pin subprocess calls it
      before listing the loaded modules.
    - If the subprocess finds a loaded `scripts/qs` module outside the set,
      add it to `hashed_files` **and** to the "exactly" set together: the
      loaded modules are authoritative.
  - The hash is cached on a (path, `mtime_ns`, size) signature. A missing
    file is hashed as absent and never raises: a bare `fake_main` has no
    `cp.py`.
  - **The version the daemon has loaded** is `codever.loaded_version()`.
    - It is computed once and cached, as **the first statement of
      `cli._daemon`**, before `daemon.run` and its migration. The value is
      passed as `daemon.run(..., loaded_version=…)`, so a pull that lands
      while the daemon migrates is never mistaken for loaded code.
    - It is not computed at import, so no other `cp.py` call (a hook, a
      read) pays for the hash.
    - It never raises: a `CpError` from `paths.main()` gives `None`.
    - **The import window.** In `control_plane/__init__.py`, `import time` and
      `IMPORTED_AT_NS = time.time_ns()` come before `from .migrations import
      SCHEMA_VERSION` (E402 is ignored repo-wide), at no cost.
      - If any hashed file has `IMPORTED_AT_NS <= mtime_ns <= now` (`now`
        read inside `loaded_version()`), the function returns
        `"unverified:" + <hash>`, which no disk hash can equal. A pull
        landing between the imports and `_daemon` is therefore caught by
        the normal debounce, which restarts the daemon.
      - A file whose mtime is in the **future** (a clock stepped back, `touch
        -d`, an extracted archive) is logged once and ignored, never a
        restart loop.
      - `codever` reads the stamp at call time as
        `sys.modules[__package__].IMPORTED_AT_NS` (never `from . import
        IMPORTED_AT_NS`, which would bind the value at import), so tests
        patch the package attribute. The conftest's files postdate the session's
        import, so the AC 4 tests of the real function either patch the
        stamp to `time.time_ns()` after building `fake_main`, or
        `os.utime` the files into the past, for the plain-hash case.
    - `loaded_version=None` (the default of `daemon.run`) makes the
      `code_version` hook inert and the self-check skip.
    - The tests' autouse fixture monkeypatches `codever.loaded_version` to
      return `codever.code_version(fake_main)`, so the loaded and disk
      versions agree under the fake checkout.
  - It is computed on **`paths.main()`**, the main checkout, for the daemon,
    for `tool merge` and for `halt clear`, whichever copy of `cp.py` runs. A
    worktree copy cannot reach the live DB anyway (`PATH_GUARD`).
  - It is never stored in a lease: the lease keeps the schema version.
- **D9 — hooks build their own seams.**
  - A tick hook is called with `(conn, clock)`; `conn` is the daemon's
    **single long-lived connection**.
  - It takes its seams from `activeloop.seams()`: `make_seams()`, cached once
    per daemon.
  - The tests' autouse fixture replaces `activeloop.make_seams` with fakes
    built on the test `Deps`. One named test covers the real `make_seams`.
- **D10 — the inbox is recorded in two places** (socket bundle):
  - the `SessionStart` hook, on every source;
  - `run open`. It is the one command that creates the DB: on the very
    first start-up, `SessionStart` fires before the DB exists, and hooks
    never create it.

  #399's rule "the CLI never reads a token from the environment" is about
  run tokens. This exception is written down.
- **D11 — the orchestrator's settings** (socket bundle):
  - `hooks-settings --role orchestrator` gains the `SessionStart` hook and
    the top-level `"crossSessionInbound": "accept"`;
  - the contract with child 9: it merges the whole JSON fragment into the
    pin, not only `hooks`;
  - 6a proves it.
- **D12 — the messenger.**

  ```text
  claude --bg -n qs-wake-<run>-m<msg> --model <models.model_for("claude", "fast")>
    --permission-mode auto --allowedTools SendMessage "<prompt>"
  ```

  - **Working directory:** `paths.messenger_dir()`, created 0700 before the
    launch. The default is `~/.local/state/quiet-solar/cp-messenger/`, or
    `QS_CP_MESSENGER_DIR`. On the pinned main checkout a bare `claude` boots
    as the orchestrator.
  - **Permission mode:** `auto` is a prompting class, so the message is never
    held (spike row 5a).
  - **Model:** `models` is imported in `watchdog._messenger_model()`, at call
    time (as shipped: see "Implementation notes"), as a plain
    `import models`. `scripts/qs` is on `sys.path` (from `cp.py`, and from
    the conftest in tests), and mypy's `ignore_missing_imports = true` needs
    no suppression. If 6c's resolver merges first, the catch-up switches to
    it.
  - **Record:** a `tool_calls` row, `watchdog-messenger` / `msg:<id>`, so it
    is idempotent.
  - **Cap:** 1, of its own.
  - **The accepted limit:** `claude --bg` returns at once, so a `succeeded`
    row holds the cap for `MESSENGER_TTL_S`. With N runs stalled at the same
    time, the last gets its messenger after about (N-1) × `MESSENGER_TTL_S`.
    So the TTL equals `WAKE_RETRY_S` (300 s). The issue fixes the cap at 1,
    and T14 documents this.
  - **Exception:** this is the one documented, tested exception to "only a
    task's node is spawned".
- **D13 — "outside any checkout"** is one helper, `paths.state_dir(env,
  default)`.
  - It refuses the code root, the main checkout, and every linked worktree
    registered under `<main>/.git/worktrees/*/gitdir` (read without a
    subprocess).
  - It does not refuse other `.git` ancestors, such as a dotfiles `~`.
  - A refusal is `POLICY_REFUSED`, with a hint naming the variable.
  - A refused migration backup fails the migration loudly, through the
    `migrate-error` sidecar.
  - Used by `backup_dir()` and `messenger_dir()`.
  - **Defaults:**
    - `backup_dir()`: `~/.local/state/quiet-solar/cp-backups/`, or
      `QS_CP_BACKUP_DIR` (both #399's, unchanged);
    - `messenger_dir()`: `~/.local/state/quiet-solar/cp-messenger/`, or
      `QS_CP_MESSENGER_DIR`.

    Neither is inside a checkout. A T3 test asserts that both defaults pass
    `state_dir`. The conftest points them at `tmp_path / "backups"` and
    `tmp_path / "messenger"`, outside `fake_main = tmp_path / "main"`.
  - **Directory permissions** (`paths.ensure_private_dir(d)`, used by
    `write_copy` and by the messenger):
    - a missing directory is created 0700, its parents with the default
      mode;
    - an existing directory **owned by the current user** is `chmod`ed to
      0700. These are this code's own state directories by contract, and
      #399 created `cp-backups` with the umask (0755), so the v2 migration's
      own backup must not be refused;
    - an existing directory owned by someone else → `POLICY_REFUSED`.
      Ownership is `os.stat(d).st_uid != os.getuid()`, and tests monkeypatch
      `os.getuid`.
- **D14 — restore copies the backup into the live file, in place.**
  `cp.py restore --confirm` is exempt, for the maintainer, with no token.
  - It uses SQLite's backup API, so the file is never replaced and its WAL
    never deleted:
    - every open connection stays coherent and sees the restored content;
    - a concurrent writer meets the busy timeout and writes afterwards, so
      nothing is lost silently.
  - A `<db>.restoring` marker, `{pid, pid_start, at}`, is honoured by
    `ensure` and by the daemon, so no daemon starts mid-restore.
    - It is honoured only while that pid is not proven dead. A marker left
      behind by a killed `restore` is unlinked by the next `ensure`.
    - No signal handler is installed: if `restore` is killed (a closed
      terminal), the OS frees its `flock` and migrate lock, the copy into
      the live DB is transactional, and the dead pid's marker is ignored and
      unlinked by the next `ensure`. Only the immediate `ensure` is lost,
      and the next `wait` or command issues it anyway.
  - The daemon is stopped, and the locks are held for the whole restore.
  - A live tool call refuses the restore (`BUSY`).
  - Every exit path removes the marker, releases the locks and calls
    `ensure`.
  - A pre-v2 backup is restored as it is. The daemon that `ensure` starts
    then migrates it.
- **D15 — a dependent task starts only after its dependency has merged
  (maintainer, 2026-10-09: "if B depends on A, it should start AFTER A
  merge").** Dependencies here are **task** dependencies (`task_deps`, "B
  depends on A" in a run's task tree), not code or work items. The detector
  looks at **started, non-terminal** dependents: a task in `planning`,
  `contracted`, `building` or `ready_to_merge`, or `blocked` with a
  `blocked_from` other than `proposed` / `ready`. It flags such a task B
  when a dependency A is:
  - neither `merged` nor `validated` (it started too early);
  - or `dropped`.

  A terminal task (`tasks.TERMINAL`: `merged`, `validated`, `dropped`) is
  never flagged, so a finished task never keeps an alert that nothing can
  clear. The subject is `"<dependent>-><dependency>"`, one condition per
  subject even when both cases hit.

  It alerts the orchestrator, and never blocks anything (a detector never
  decides). Enforcing the order when nodes are spawned is 6a's.
- **D16 — the socket token** (socket bundle).
  - **The threat model** is #399's: agent mistakes, not adversarial
    same-user processes. Nodes could read the live DB; that is accepted and
    written down.
  - **Storage:** a table of its own, never read by `snapshot`, `task show`,
    `export-summary` or the board.
  - **Backups:** every copy erases it:
    1. `PRAGMA secure_delete = ON` on the copy (whose `journal_mode` is
       always set to `DELETE`, §10);
    2. `DELETE FROM session_inbox`;
    3. `VACUUM`.

    So no backup file ever contains the token's bytes. This goes beyond the
    issue's "dropped on a restore": a restore has nothing left to drop.
    Backups are also 0600, in a 0700 directory.
  - **Environment:** `daemon.strip_env(environ) -> dict` drops every
    `CLAUDE_CODE_MESSAGING_*` name, `CLAUDE_CODE_SESSION_ID`, `CLAUDECODE` and
    `CLAUDE_CODE_ENTRYPOINT`. The daemon is never a Claude session, and a
    nested-session marker could make the messenger's `claude --bg` refuse to
    launch. T1 may **add** names, never remove them; any addition updates
    `strip_env`, D16 and the AC 4 bullet (T6a's test) in a T11b commit. It
    has **one call site**:
    `ensure` passes `env=strip_env(os.environ)` to its `Popen`. The
    messenger inherits the cleaned environment from the daemon.
    - The daemon, and every child it spawns (`Runner` copies `os.environ`),
      never carries the spawning session's secret or identity.
    - `runner.py` is unchanged.
    - A daemon started by hand (`cp.py daemon` in a terminal) keeps its own
      environment; the maintainer's shell is not a session.
    - The env strip applies whether or not the socket bundle is built.
- **D17 — modules are split to avoid import cycles.**
  - The leaves are `codever.py`, `mergegate.py` and `backups.py`. `daemon`,
    `tools` and `migrations` import only these leaves among the new modules.
    `cli` may also import `ticks`, `activeloop`, `alerts`, `restore` and,
    with the socket bundle, `inbox`. None of those imports `cli` at module
    level, so there is no cycle.
  - `selfcheck.py` imports `cli`, `tools` and `ticks` lazily.
  - `restore.py` imports `daemon` and `backups`.
  - `ticks.py` (the registry) is separate from `activeloop.py` (the seams and
    `register_builtin`), because the hook modules import `ticks`.
  - The hook modules import `activeloop` at the top, for `seams()`; they
    annotate `Seams` under `TYPE_CHECKING`. `activeloop` imports the hook
    modules **lazily**, inside `register_builtin()` and `_reset_for_tests()`,
    so there is no cycle.
- **D18 — when the self-check runs, and its retries.**
  - It runs on the first tick of a daemon whose loaded version
    (`daemon.started_code_version()`) equals the disk version, unless
    `meta.selfcheck` already records a pass, or an override exists, for that
    version.
  - **A failure is retried indefinitely,** never before `meta.selfcheck.at +
    SELFCHECK_RETRY_S`. The check reads the DB, not an in-memory throttle, so
    a new daemon does not retry early. A failing check costs about 1 s every
    10 minutes.
  - **`tries`** counts consecutive failures for one version, across daemons.
    It resets with a new version.
  - **Escalation of the merge verdict:** the gate refuses (`POLICY_REFUSED`)
    only after `SELFCHECK_ESCALATE_AFTER` (3) consecutive failures, so a
    transient first failure (for example, a cold venv) keeps merges `BUSY`
    (D19). **The alert does not wait:** an alert that clears on the next pass
    costs nothing, and the issue says "every run alerted".
  - **The `selfcheck_failed` set on each tick**, keyed on the **disk**
    version `v`:
    - active = `[Condition("selfcheck_failed", v, every open run)]` iff
      `meta.selfcheck` is `ok: false` for `v` (from the first failure) and no
      override exists for `v`;
    - otherwise `[]`.

    So it clears on a pass, on an override and on a version change, and a
    run opened later still sees it.
- **D19 — a gate still pending is retryable.**
  - **Pending** → `BUSY` ("self-check pending for <v12>; replay the same key
    shortly"). A Control Plane merge on `main` closes the gate for about a
    minute (the debounce, the restart, the self-check), so this is routine.
    `BUSY` releases the claim.
  - **Pending for too long** (`stuck`) → `POLICY_REFUSED` ("the self-check
    has not run for <v12> in N min; the daemon may not start (a git
    operation has been in progress in the main checkout since <t>: <file>);
    ask the maintainer". The `git_busy` clause appears only when
    `codever.git_busy(main)` names a file, so a leftover `index.lock` is
    named as the cause):
    - `tool merge` records `meta.selfcheck_pending = {code_version, since}`
      the first time it sees a version pending, and commits it before it
      raises (§4.2);
    - past `PENDING_ESCALATE_S` (600 s), that version refuses.

    This is the case where new code cannot even start the daemon. Nothing
    else would ever tell anyone, and it is exactly the case `halt clear`
    exists for.
  - **Failed fewer than `SELFCHECK_ESCALATE_AFTER` times** (`retrying`) →
    `BUSY` too, with the next retry time. The `selfcheck_failed` alert is
    already raised (D18).
  - **Failed `SELFCHECK_ESCALATE_AFTER` or more times** (`failed`) →
    `POLICY_REFUSED` ("automatic merges are halted: self-check failed for
    <v12>; ask the maintainer").
  - **Why:** this deliberately refines the issue's "halted when it fails"
    into "open only after a pass". Without it, merges would run on new,
    unchecked code until the check finished.

### 2. The registration point — `ticks.py`

```python
Hook = Callable[[sqlite3.Connection, Clock], None]

def register(name: str, fn: Hook) -> None   # ValueError on a duplicate name
def registered() -> tuple[tuple[str, Hook], ...]
def hooks() -> list[Hook]                    # each wrapped in a closure named after its hook (the daemon's log; a bound method's __name__ cannot be set)
def _reset_for_tests() -> None               # clears the registry and every Throttle in _THROTTLES

class Throttle:                              # in memory; a new daemon is due at once; adds itself to _THROTTLES
    def __init__(self, every_s: float): ...
    def due(self, clock: Clock) -> bool      # True and re-arms when every_s has passed since the last True
```

- `cli` calls `activeloop.register_builtin()` at import and at the top of
  `cli.main`. The call is idempotent.
  - **The cost:** every `cp.py` call, the `PreToolUse` hook included, then
    imports the hook modules (small, stdlib-only, plus `models` /
    `targets`). T4 measures it with `python -X importtime`. If it adds more
    than 30 ms per call, registration moves to the paths that need the
    registry (`_daemon`, `version`, the self-check), and `main`'s call
    stays.
- `_daemon` passes `tick_hooks=ticks.hooks()`.
- **Child 15** adds its hook to `register_builtin()`'s explicit list and to
  `BUILTIN_NAMES`, from its own module, so a test reset makes the registry
  whole again and the self-check sees a missing pilot.
- **The contract**, written on `register`:
  - never let `daemon.STALE_AFTER_S` (30 s) pass without a beat;
  - give every subprocess a timeout of at most `HOOK_SUBPROCESS_S` (20 s);
  - call `daemon.beat(conn, clock)` **after every subprocess call**;
  - run subprocesses and `beat` **outside any `db.write`**: read, release,
    call, beat, write;
  - bound the work done per tick (the overlap detector does at most
    `OVERLAP_MAX_CALLS` git calls per tick, §6);
  - never launch a long job in-process;
  - throttle with a `Throttle`, or with a DB timestamp.
- **`daemon.run`** checks `_stop` after **each** hook, not only at the end
  of the tick, so a SIGTERM is honoured within one hook. The restart flag is
  checked only at the end of the tick.
- A hook that raises is logged and skipped (#399, kept). The daemon already
  beats before and after each hook.

### 4. Lifecycle

#### 4.1 Restart on new code — `selfcheck.py`, the `code_version` hook

- **The loaded version.** `cli._daemon` calls `codever.loaded_version()`
  first and passes it to `daemon.run(…, loaded_version=…)`, which stores it.
  `started_code_version()` returns it. With `None`, the hook does nothing.
  The **candidate** is held in `daemon`, next to the restart flag. `run()`
  clears both at start, and so does `_reset_for_tests()`.
- **The hook,** each tick, recomputes the version (cached):
  - unchanged → nothing;
  - changed while `git_busy` → nothing;
  - changed, seen once → this is the candidate;
  - the same candidate on the next tick → `daemon.request_restart("new_code")`.
- **The loop.** `run()` clears the restart flag at start. The loop checks it
  at the **end of the tick**, next to the existing `_stop.is_set()`, so the
  daemon finishes its tick (D7), and then returns `{"exit": "new_code", …}`.
  Only `_stop` (SIGTERM) is also checked after each hook. A tick cut short
  that way still counts (`ticks += 1`, then break), so
  `test_daemon.py:84-95`'s `ticks == 1` holds. The existing `finally` clears the lease, and leaving the
  `with db.file_lock(...)` block closes the `flock` file descriptor, all
  **before** `run()` returns, so the `ensure` that follows finds the
  singleton free.
- **The respawn.**
  - When `result.get("exit") == "new_code"` (a `held_elsewhere` result has
    no `exit` key), `cli._daemon` calls `ensure_daemon(io)` and returns
    `{…, "respawn": <status>}`.
  - An exception from that `ensure` is caught and reported as `"respawn":
    "error"` with `respawn_error`, like `_daemon_status`. The next `wait`
    retries.
- **The first deploy (bootstrap).** The daemon running when this PR merges
  is #399's skeleton, with no `code_version` hook. Migration v2 raises the
  code's schema to 2, so the next `ensure` (any `wait`) sees a lease of a
  lower schema. It stops that daemon through #399's existing
  older-schema path, and starts the new code, which migrates and runs its
  self-check. AC 4 covers it.
- **What updates the code on disk:** today, the frozen `finish-task`'s `git
  pull` on the main checkout; later, child 7's fast-forward. The gate tracks
  the checkout, not `origin/main`.
- **Runs in flight:**
  - commands and hooks are per-call processes, so they load the new code at
    their next call;
  - a running `wait` keeps its old code: it is a loop over the queue, and a
    schema change stops it (#399);
  - the quality gate and CI run per call.
- **The import-failure case:** a version that cannot start records no pass.
  Merges are `BUSY`, and after `PENDING_ESCALATE_S` they are `POLICY_REFUSED`
  ("stuck … ask the maintainer"), so the case is never silent.
  - **The accepted limit:** if that version also carries a migration, the DB
    stays at the older schema. Every write command, `tool merge` included,
    then answers #399's `SCHEMA_PENDING`, with the migrate-error sidecar's
    content when there is one, before reaching the gate. `halt clear` answers
    the same. That is visible, but it is not the `stuck` text. The fix is to
    revert the code, and T14 documents it.
  - **Who keeps a daemon alive:** #399's idle exit fires only when **no run
    is open** for `IDLE_EXIT_S`. While a run is open, the daemon never idles
    out, and the orchestrator's `wait` re-ensures it on a stale heartbeat. So
    `pending` / `stuck` with an open run means the daemon really cannot run
    its check.

#### 4.2 The merge gate — `mergegate.py`

- **State** (`meta` keys):
  - `selfcheck` = `{code_version, ok, at, tries, failures}`;
  - `selfcheck_override` = `{code_version, reason, at}`.
- **`merge_allowed(conn, version, clock) -> Verdict(state, reason)`.** It
  writes `selfcheck_pending = {version, now}` when the key is absent **or
  holds another `code_version`**, and otherwise leaves it, keeping `since`.
  So it runs inside the caller's `db.write`, and that `db.write` **commits
  before any refusal is raised**. Its states:
  - `open`: a pass, or an override, is recorded for `version`;
  - `failed`: the record is `ok: false` for `version`, with `tries >=
    SELFCHECK_ESCALATE_AFTER`;
  - `retrying`: the record is `ok: false` with fewer tries;
  - `stuck`: pending, and `selfcheck_pending.since` for this version is
    older than `PENDING_ESCALATE_S`;
  - `pending`: anything else.
- **`tool merge`.** The `policy` step:
  1. computes `version = codever.code_version(ctx.main)` (the step's own
     seam, which is already `paths.main()`) **before** `with ctx.write() as
     conn`, so no file is hashed under the writer lock;
  2. computes the verdict with `with ctx.write() as conn: verdict =
     mergegate.merge_allowed(conn, version, ctx.clock)`. It calls the gate
     through the module attribute, never a `from` import, so the conftest's
     monkeypatch applies. The block **exits and commits** (so
     `selfcheck_pending.since` is stored) before anything is raised;
  3. **after** the block, maps the verdict:
     - `pending` / `retrying` → `BUSY` (D19);
     - `failed` / `stuck` → `POLICY_REFUSED`, in a text that never names the
       command. For `stuck`, `tool merge` calls `codever.git_busy(ctx.main)`
       here, after the `db.write` block, so no file is read under the writer
       lock, and names the file when there is one;
     - `open` → `merge_policy.check`, as today.

  The probe still runs `gh pr view --json state,mergeCommit` first (#399),
  so the refusal comes before `gh pr view --json headRefOid` and `gh pr
  merge`. Both refusals release the claim. A PR the probe finds already
  merged skips the `policy` step, as today.
- **`cp.py halt clear --reason TEXT`** (exempt). Its checks, in order:
  1. no `--reason` → `USAGE`;
  2. `db.check_schema(wait=False)`: newer → `SCHEMA_TOO_NEW`, older →
     `SCHEMA_PENDING`;
  3. a missing DB → `NOT_FOUND`;
  4. `db.connect(path)` (read-write), then one `db.write`: write
     `selfcheck_override` for the current version, delete
     `selfcheck_pending`, and call
     `alerts.sync_locked(kinds={"selfcheck_failed"}, active=[])`, all in that
     one `db.write`.

  It returns `{"override": …, "previous": <selfcheck record>}`, and never
  prompts.

#### 4.3 The self-check — `selfcheck.py`, the `selfcheck` hook

**The hook's body, in order, on each tick:**

1. Sync D18's `selfcheck_failed` active set, computed from `meta` for the
   **disk** version. This runs first, so a version change or a stuck daemon
   never leaves a stale alert behind.
2. Return when any of these holds:
   - `daemon.started_code_version()` is `None`, or differs from
     `codever.code_version(paths.main())` (a restart is pending);
   - a pass or an override exists for the version;
   - the record is for this version, `ok: false`, and its next retry is not
     yet due (`meta.selfcheck.at + SELFCHECK_RETRY_S`). A new version is
     checked on its first tick, whatever the previous version's record.
3. Run the steps below.
4. Record the result.

Each step runs under the per-step broad guard, followed by `daemon.beat`:

1. **`schema`:** `user_version == current_schema_version()`, and `PRAGMA
   quick_check` returns `ok`.
2. **`entry`:** `seams.runner.run([python, <main>/scripts/qs/cp.py,
   "version"], timeout=HOOK_SUBPROCESS_S)`.
   - It must exit 0 and print JSON with:
     - `schema_version == current`;
     - `tools ⊇ tools.BUILTIN_NAMES | {s.name for s in items.SPECS}`;
     - `tick_hooks ⊇ activeloop.BUILTIN_NAMES`.
   - `python` is `<main>/venv/bin/python`, else `sys.executable`.
   - This runs the code on disk, through the entry every session uses.
3. **`registry`:** the same two inclusions, checked in-process (lazy
   imports), and `cli.build_parser()` succeeds. The two steps check
   different things:
   - `entry` checks the code on disk, through the venv entry point that
     every session uses;
   - `registry` checks the modules the daemon itself runs.

**Recording.** The result is recorded for `started_code_version()`, and only
if the disk version still equals it after the steps.

- **Pass:** record `ok: true`, delete `meta.selfcheck_pending`, and call
  `alerts.sync_locked(kinds={"selfcheck_failed"}, active=[])`, all in one
  transaction.
- **Fail:** record `ok: false` with `tries + 1` and `at = now`, and delete
  `meta.selfcheck_pending` in the same transaction (the version is no longer
  pending; it is `retrying` or `failed`). Then
  `selfcheck_failed` follows D18's active-set rule, which the hook syncs on
  every tick.

The subprocess takes about 1 s and at most 20 s, within `STALE_AFTER_S`.

```python
def fingerprint(kind: str, subject: str, n: int) -> str

@dataclass(frozen=True)
class Condition:
    kind: str
    subject: str
    run_ids: tuple[str | None, ...]   # None and closed runs are dropped in sync_locked
    payload: Mapping[str, Any]

def sync_locked(conn, clock, *, kinds: Collection[str], active: Iterable[Condition]) -> dict
def sync(conn, clock, **kw) -> dict      # db.write + sync_locked
def event_locked(conn, clock, *, kind, subject, run_id, payload) -> dict | None
```

- **`sync_locked`** runs inside the caller's transaction. For each (open run,
  kind, subject):
  - **an open row exists:** set `last_seen = now` and refresh `payload`;
  - **otherwise:**
    1. compute `n`;
    2. insert the row (`first_seen = now`);
    3. call `messages.post_locked(recipient="orchestrator", kind,
       sender="cp:daemon", payload={**payload, alert_id, fingerprint,
       severity}, dedupe_key=fingerprint)`;
    4. store `message_id`.
- **Clearing:** every open row of a kind in `kinds` that is absent from
  `active` gets `cleared_at = now`, with no message.
- **Unknown input:** a detector whose input is unknown this tick leaves its
  kinds out of `kinds`, so nothing is cleared or raised.
- **Cold state counts as unknown.** A new daemon (after every Control Plane
  merge, D7) starts with empty memory, and a restart is not a recurrence. So
  a hook whose conditions depend on in-memory state leaves its kinds out of
  `kinds` until that state is warm, or rebuilds the state from the DB:
  - **overlap:** both kinds are omitted until this daemon has completed one
    full recomputation. After that, a truncated walk re-emits the last
    *complete* result;
  - **`node_dead` / `orchestrator_dead`:** each sighting counter is
    **seeded from the open `alerts` rows**, so an already-open subject counts
    as confirmed. The kinds are omitted until this daemon has taken
    `LIVENESS_CONFIRM` successful listings;
  - **`orchestrator_not_listening`:** the ladder is rebuilt from the head
    message's `watchdog-messenger` row (§9.2), so an open row stays active
    while the run is still stalled on the same head;
  - **`backup_failed`:** derived from `meta.last_backup_error` (set on a
    failure, cleared on a success), not from memory.
- **`event_locked`** inserts a one-shot alert with `cleared_at = first_seen`,
  and posts it once.
- **Severity:** `must-fix` for `ci_red`; `alert` for the rest.

### 6. Detectors — `detectors.py`

Each detector is `detect_<x>(conn, clock, seams) -> tuple[kinds,
list[Condition]]`. The `detectors` hook runs them all, then calls
`alerts.sync` once per detector.

1. **Overlap.**
   - **Active branches:** non-terminal tasks with a `branch` whose local
     `refs/heads/<branch>` resolves. Local `QS_<N>_<k>` refs are included.
   - **Base:**
     - for a deliverable, the newer of `refs/heads/main` and
       `refs/remotes/origin/main`, by `merge-base --is-ancestor`; if they
       diverge, `origin/main`. A stale `origin/main` would otherwise make a
       branch show `main`'s own commits;
     - for a work item, `refs/heads/QS_<N>`.
   - **Files:** `git diff --name-only <base>...<tip>`, cached per (base sha,
     tip sha), so a moved base is recomputed.
     The issue's "via `git merge-tree`" is kept for `conflicts`, because
     `merge-tree` reports conflicts, not changed files.
   - **Pairs:** every pair, except an item with its own deliverable. Two
     items of one deliverable do form a pair.
   - **Payload:**
     - `files`: sorted, at most 50, plus `truncated`;
     - `conflicts`: from `git merge-tree --write-tree --name-only
       --no-messages <tipA> <tipB>`, cached per (tipA sha, tipB sha). Exit 1 → the lines
       after the first one (the tree OID). Exit 0 → `[]`. Any other exit is
       a git failure.
   - **Git:** `merge-tree` needs git ≥ 2.38; the maintainer has 2.51, and
     this is documented. It writes loose tree objects into the main
     repository, also documented.
   - **Kind:** `overlap`, or `overlap_cross_run` when the two runs differ.
   - **Robustness:**
     - recomputation is skipped while `git_busy`, and the cached conditions
       are re-emitted instead;
     - a recomputation makes at most `OVERLAP_MAX_CALLS` git calls per tick.
       **Every** git subprocess counts: `rev-parse`, `merge-base
       --is-ancestor`, `diff`, `merge-tree`. Then it stops and re-emits the
       last *complete* result (or omits the kinds if there is none yet:
       cold state, §5). An incomplete walk continues on **every**
       `detectors` run until it completes; the pairs already computed hit
       the per-tip cache at no cost, so the cache is the only state, and
       there is no cursor. `OVERLAP_EVERY_S` counts from the last complete
       walk;
     - any git failure drops both kinds;
     - every git call has a 20 s timeout and is followed by a beat.
2. **A stalled node.**
   - **Who:** a node in `running`, with no `started` `tool_calls` row by
     actor `node:<task>`, whose last activity is older than `STALL_S`. The
     actor string is #399's `Principal.actor`: `node:<task_id>`, keyed on
     the **task** id (for example `node:T7`), and the same value is used as
     `messages.sender`.
   - **Activity** is the newest of:
     - `launch_at` and `spawned_at`;
     - the task's `reports.at`;
     - `messages.created_at` where `sender = 'node:<task>'`;
     - that actor's `tool_calls.started_at` and `finished_at`.
3. **Too many rounds.** Per (non-terminal task, phase), `max(reports.round)
   > ROUNDS_ALERT`. A new round is a new subject. This detector is **the only
   raiser** of the alert.
4. **State anomalies.**
   - **`task_without_node`:** a task in `planning`, `contracted` or
     `building` with no node in `nodes.LIVE_STATES`, whose last
     `task_history.at` (and newest node's `launch_at`, if any) is older than
     `ORPHAN_GRACE_S`. `tasks.update_fields` (the CI watcher's writes)
     writes no history, so it never restarts this grace.
   - **`dependency_violated`:** D15.
   - **`lock_held_long`:** a `locks` row older than its `LOCK_HELD_S` entry.
     It is routed to the run of `token_subject`, else to every open run.
     `token_subject` is #399's `Token.subject_ref`: `run:R<n>` (the run id)
     or `node:N<n>`, keyed on the **node** id and resolved through
     `nodes.run_id`.
   - **`gate_slot_held_long`:** a `gates` `cap_slots` row older than
     `GATE_SLOT_HELD_S`. It is routed to the run of a `started` `tool_calls`
     row with the same `holder_pid`, else to every open run.
   - **`leftover_item`:** a work item whose `worktree` is not NULL while its
     deliverable is `validated` or `dropped`.
   - **`leftover_scratch`:** a `git worktree list --porcelain` entry whose
     path basename is `QS_<N>_<k>_integration`, for an item whose deliverable
     is `validated` or `dropped`.
5. **Dependency cycles.**
   - Tarjan's algorithm over every `task_deps` row, across runs.
   - Every strongly connected component with more than one task is a cycle.
     It is `dependency_cycle_cross_run` when it spans several runs.
   - Tested on a two-run SQL fixture: `R1.T1 → X → R2.T2 → Y → R1.T1`.
6. **The same task discovered twice.**
   - **Normalisation:**
     1. NFKC, then `casefold`;
     2. `re.sub(r"^\s*qs[-_ ]?\d+\s*[:\-–—]?\s*", "", t)`;
     3. `re.sub(r"[\W_]+", " ", t).strip()`.
   - Two or more non-terminal tasks with the same non-empty normalised title
     are a duplicate (`duplicate_task`, or `duplicate_task_cross_run`).

### 7. Hook events — `hookroute.py`

- **The cursor:** `meta.hook_events_cursor`. Migration v2 seeds it to
  `COALESCE(max(id), 0)`, so history is never replayed.
- **Each tick**, in one `db.write`:
  1. read `SELECT … FROM hook_events WHERE id > cursor ORDER BY id LIMIT 500`;
  2. for each `alert` row, find the run: `detail.run_id`, else the run of
     `detail.task_id`, else none. A row with no run, or whose run is closed,
     is unroutable and stays only in `hook_alerts`. This is why
     `hook_alerts` exists;
  3. call `alerts.event_locked(kind=detail["kind"], subject="hook:<id>", …)`;
  4. move the cursor to the last id read.
- SQLite serialises writers, so ids commit in order. `hook_events.id` is
  `AUTOINCREMENT` (schema v1), so ids never go back.

### 8. CI watcher — `ciwatch.py`

- **The `GitHub` seam,** on `seams.runner`:
  - **`repo()`** parses `git remote get-url origin` once per daemon. It
    accepts three forms: `https://github.com/o/r(.git)`,
    `git@github.com:o/r(.git)` and `ssh://git@github.com/o/r(.git)`.
    Anything else is a permanent `CiFailure`, logged once.
  - **`prs(numbers) -> (dict[int, PrCi | None], Rate)`** makes one `gh api
    graphql` call per `CI_BATCH` PRs, with a 20 s timeout. Each PR is an
    alias inside the repository:

    ```text
    query { rateLimit { remaining resetAt }
      repository(owner: "<o>", name: "<r>") {
        p<n>: pullRequest(number: <n>) { state headRefOid
          commits(last:1){ nodes{ commit{ statusCheckRollup{ state
            contexts(first:100){ pageInfo{hasNextPage}
              nodes{ __typename
                ... on CheckRun{ name conclusion detailsUrl }
                ... on StatusContext{ context state targetUrl } } } } } } } } } }
    ```

  - **Partial errors:** GraphQL may return `errors` together with partial
    `data`, and `gh` then exits non-zero. The stdout is parsed anyway:
    - a `null` alias with a `NOT_FOUND` error means that PR is unknown
      (`None`), skipped this poll with no write;
    - every other alias is valid;
    - only a transport, auth or rate failure (no parseable `data`) is a
      `CiFailure`.
  - **`PrCi`** = `(state, head, rollup, failing, truncated)`.
  - **Failures:** a non-zero exit with no parseable `data` (`Runner`
    reports a missing `gh` as exit 127 and a timeout as 124), an
    unauthenticated `gh`, bad JSON or a missing key → `CiFailure`.
- **Watched PRs:** deliverables with a `pr_number`, not terminal, in an open
  run.
  - Work items are skipped.
  - A PR reported `MERGED` or `CLOSED` gets `ci_state = NULL, ci_sha = NULL`
    written once, on a change. This clears any `ci_red` (a PR closed so that
    a new one can be opened leaves no stale must-fix). It stays in the batch
    and counts as settled (`CI_SLOW_S`), so a reopened PR is picked up by
    the next slow poll. There is no skip set.
- **Mapping:**
  - `SUCCESS` → `green`;
  - `FAILURE` / `ERROR` → `red`;
  - `PENDING` / `EXPECTED` / no rollup → `pending`. No rollup counts as
    settled for the schedule.
- **`failing`** lists the `CheckRun`s concluded `FAILURE`, `TIMED_OUT`,
  `CANCELLED`, `ACTION_REQUIRED` or `STARTUP_FAILURE`, and the
  `StatusContext`s in `FAILURE` or `ERROR`. Red means the rollup is red;
  required checks are child 7's.
- **A poll is all-or-nothing for transport failures.** Only when every batch
  returns parseable data are `ci_state` / `ci_sha` written, through
  `tasks.update_fields` (existing schema-v1 columns, `SETTABLE`), and only on
  a change. A `CiFailure` in any batch writes nothing. One unknown PR (a
  `NOT_FOUND` alias) never blocks the others.
- **`ci_red` is derived from the stored rows on every tick,** whether or not
  a poll ran: one condition per watched task with `ci_state = 'red'`. Its
  payload is `{task_id, pr_number, sha, failing, truncated, severity:
  "must-fix"}`.
- **The schedule.** `CiWatcher` is a module singleton, reset by
  `_reset_for_tests`.
  - The next poll comes `CI_FAST_S` after a poll that saw a `pending` rollup
    or a moved head, else `CI_SLOW_S`.
  - Failures back off from `CI_BACKOFF_MIN_S` to `CI_BACKOFF_MAX_S`.
  - `rate.remaining < CI_RATE_FLOOR` → no poll before `resetAt`.
  - It catches only `CiFailure`, and logs it.
  - A new daemon polls at once: that is the re-sync after a restart or a
    restore.

### 9. Liveness and the watchdog — `watchdog.py`, `inbox.py`

The `liveness_watchdog` hook runs every 30 s:

- it takes one listing, `claude.try_agents(timeout=HOOK_SUBPROCESS_S)`;
  `None` means unknown;
- it beats right after.

The listing's `Agent` carries `session_id`, `name`, `status`, `state` and
`started_at_ms` (#399).

- **What the listing covers:** `claude agents --json` lists interactive
  sessions as well as `--bg` ones. This is recorded in the issue and the
  epic (the maintainer, 2026-10-03), and spike T2/T3 used it for GUI
  sessions. T1 re-checks that a desktop orchestrator appears with its idle
  status.
  - **A negative T1 check** removes `orchestrator_dead` and the ladder's
    idle gate in T11b, and moves both to the D1 follow-up issue. There is no
    runtime switch.
- **Idle and busy:** a session is **idle** iff `"idle" in (agent.status,
  agent.state)`, the rule `nodes.refresh` uses. A listed session that is not
  idle is busy. An absent session is absent.
- **Stale messenger rows:** at the start of each run of the hook, a
  `started` `watchdog-messenger` row whose holder fails
  `probe.holder_alive(holder_pid, holder_pid_start, None)` becomes `failed`.

#### 9.1 Liveness

- **Nodes:** `nodes.refresh(conn, clock, listing)`.
- **`node_dead`:** a task's current generation is `reaped` while the task is
  in `tasks.NODE_RANGE`. It is raised after `LIVENESS_CONFIRM` sightings,
  counted in memory.
- **`orchestrator_dead`:** an open run whose lease `session_id` is absent
  from `LIVENESS_CONFIRM` consecutive successful listings.
- **A `None` listing** leaves `node_dead`, `orchestrator_dead` **and
  `orchestrator_not_listening`** out of `sync`, and keeps the counters and
  the ladders.

#### 9.2 The stalled-orchestrator ladder (in memory)

A run is **stalled** when all of these hold:

- the listing is known;
- the run has no open `orchestrator_dead`;
- the head message (`messages.head_id`) has been visible for at least
  `WATCHDOG_S`;
- `wait.live_waiter` is false;
- the lease session is **listed idle**. An absent session is
  `orchestrator_dead`'s case; a busy one drains through its `Stop` hook.

The ladder state lives in memory, per (run, head id). A new daemon starts it
over, and the messenger stays idempotent through `tool_calls`.

1. **`socket`** (socket bundle). It applies when a `session_inbox` row for
   the lease session has `stale_at IS NULL`. The hook calls
   `seams.inbox.post(socket, token, wake_text)`:
   - `delivered` → wait `WAKE_RETRY_S`;
   - `refused` / `error` → set `stale_at = now`, then rung 2 in the same
     tick.
2. **`messenger`:**
   - **Adopt an existing row first.** If a `('watchdog-messenger',
     'msg:<id>')` row exists for this head (a previous daemon, or an earlier
     tick), the ladder takes over its outcome and launches nothing:
     - `succeeded` → treated as launched at its `started_at`; rung 3 once
       `started_at + WAKE_RETRY_S` has passed;
     - `failed` → rung 3 now;
     - `started` with a live holder → wait.
   - **Cap** (only for a new claim): a `watchdog-messenger` row in `started`
     or `succeeded`, younger than `MESSENGER_TTL_S` by its `started_at`, takes
     the cap. Cap taken → retry on the next tick.
   - **Name:** a run whose name is not bound to its lease session
     (`name_bound_session_id != session_id`; `run bind-name`, #399) cannot be
     addressed, so it goes to rung 3.
   - **Claim,** in one `db.write`, re-checking that no row exists (another
     tick may have raced it), then insert:

     ```sql
     INSERT INTO tool_calls (tool, key, args_hash, run_id, task_id, actor,
                             args, state, holder_pid, holder_pid_start, started_at)
     VALUES ('watchdog-messenger', 'msg:<id>', '-', <run>, NULL, 'cp:daemon',
             <args json>, 'started', <daemon pid>, <start>, now)
     ```

     While `started`, the row shows in `snapshot.tool_calls_in_flight`, as
     intended. A `started` row whose holder is dead is marked `failed` at the
     start of the hook (§9).
   - **Launch:**
     1. `paths.ensure_private_dir(messenger_dir())`;
     2. `seams.claude.spawn_bg([...], cwd=messenger_dir(),
        timeout=HOOK_SUBPROCESS_S)` (`spawn_bg` is a `ClaudeCli` method);
     3. a beat;
     4. `UPDATE … state = 'succeeded' | 'failed', finished_at, exit_code,
        result = {stdout tail}`.
   - **Then:** a launch → wait `WAKE_RETRY_S`. A failed launch → rung 3.
3. **`not_listening`:** the condition `orchestrator_not_listening` is synced
   while the run stays stalled after rung 2, or once rung 2 failed. It is
   visible in `snapshot.alerts`.

A new head starts a new ladder.

**The texts.** Neither ever contains a token.

- `wake_text`: "Run <R> has <N> message(s) waiting in the Control Plane.
  Pop the next with `<cp> msg pop --run <R> --as orchestrator --token
  <your run token>`, handle it, ack it; then restart `wait`."
- The messenger prompt: "You are a one-shot messenger. Call the SendMessage
  tool exactly once, to the session named `<runs.name>`, with this message:
  <wake_text>. Do nothing else, then stop."

#### 9.3 The inbox (socket bundle)

- **`session_inbox`** `(session_id PK, socket, token, source, recorded_at,
  stale_at)`. Nothing but the watchdog reads it, and backups erase it (D16).
- **`inbox.record(conn, clock, session_id, source)`** reads
  `CLAUDE_CODE_MESSAGING_SOCKET` / `_TOKEN` and upserts the row, with
  `stale_at = NULL`. Missing variables → nothing is written.
- **`cp.py hook session-start`** (exempt, stdin = the hook JSON):
  - it records with `source = payload["source"]`, through
    `hooks._db_if_current`;
  - it fails open and prints nothing (6a owns the summary).
- **`run open`** records with `source = "run-open"`, for its session id.
- **`Inbox.post(path, token, text, timeout=5)`:**
  1. `AF_UNIX` connect;
  2. send the auth line;
  3. send `frame(text)` (T1's format);
  4. read one line.

  It returns `delivered | refused | error`. `ECONNREFUSED`, `ENOENT` and
  `ENOTSOCK` count as `refused`.
- **`hooks_settings("orchestrator")`** gains:
  - `"SessionStart": [{"hooks": [{"type": "command", "command":
    _hook_command(main_dir, "session-start"), "timeout": HOOK_TIMEOUT_S}]}]`;
  - `"crossSessionInbound": "accept"`.

### 10. Backups and restore — `backups.py`, `restore.py`

- **Where backups go:** every file `write_copy` writes (periodic, migration,
  replaced) goes under **`backups.db_dir(db_path) = backup_dir() /
  sha256(str(db_path.resolve()))[:8]`**.
  - A temporary DB's daemon (through `QS_CP_DB`) therefore never mixes its
    backups with the live DB's.
  - `choose_source` reads only that subdirectory.
  - #399's top-level files are left alone. To make one restorable, move it
    into the subdirectory by hand (T14 doc note).
- **The DB path:** `migrations._backup(conn, db_path, version)` gains the
  path. The hook gets it from the `main` row of `PRAGMA database_list`,
  which equals `db_path.resolve()` (`db.connect` opens the resolved path).
- **`write_copy(src_conn, dest)`:**
  1. `paths.ensure_private_dir(paths.backup_dir())`, then
     `paths.ensure_private_dir(dest.parent)` (D13). Both directories end up
     0700, a user-owned one is tightened (`cp-backups` as #399 left it), and
     a foreign one is refused.
  2. `os.open(<dest>.partial, O_CREAT | O_EXCL | O_WRONLY, 0o600)`, then
     close.
  3. `copy = sqlite3.connect(partial)`, then `src_conn.backup(copy)`. Then
     one read (`PRAGMA user_version`), so the copy's connection re-reads
     page 1. Then **always** `PRAGMA journal_mode = DELETE`, asserting that
     it returns `"delete"`. The source is in WAL mode, a backup copies its
     header as-is, and without the read the pragma would be a no-op.
  4. When `session_inbox` exists (T11a): `PRAGMA secure_delete = ON`,
     `DELETE FROM session_inbox`, `COMMIT`, `VACUUM`.
  5. `copy.close()`, `fsync`, then `os.replace(partial, dest)`.

  Any exception closes the copy and unlinks the `.partial`. Migration backups
  use `write_copy` too, as `harness_state.v<N>.<stamp>.db`, with the same
  `%Y%m%dT%H%M%S%fZ` stamp as today. `rotate` and `choose_source` match only
  the exact pattern `harness_state\.(periodic|v\d+)\.\d{8}T\d{12}Z\.db`, so
  `.partial`, `-wal` and `replaced` files never match.
- **`take(conn, clock, db_path)`** writes
  `db_dir(db_path)/harness_state.periodic.<stamp>.db`, with the stamp taken
  from the clock.
- **The `backup` hook** runs when a run is open, `meta.last_backup_at` is
  missing or at least `BACKUP_EVERY_S` old, and `meta.last_backup_error` is
  absent or its `at` is at least `BACKUP_EVERY_S` old. It calls `take`,
  then `rotate`, then writes `last_backup_at`.
  - **On a failure** (`CpError`, `OSError`, `sqlite3.Error`), it logs once and
    writes `meta.last_backup_error = {at, error}`. `backup_failed` is synced
    to every open run while that key exists, and the next attempt waits
    until `last_backup_error.at + BACKUP_EVERY_S`. A success deletes the
    key. A full disk or a refused directory is never silent, never retried
    every tick, and survives a restart.
  - **Footprint:** the time-based rotation bounds the directory to about
    100 files (96 for the last day, 7 dailies) × the DB's size, a few MB per
    copy. `v<N>` and `replaced` files are never deleted by code: a `replaced`
    copy is the maintainer's undo of a restore, and T14's doc note says to
    delete old ones by hand. No size cap (scope round 6).
- **`rotate(dir, now)`** applies to `periodic` files only, keyed on the stamp
  in the filename:
  - everything younger than 24 h is kept;
  - between 24 h and 7 days, the newest per UTC day is kept;
  - anything older is deleted.
- **`choose_source(dir)`:** the newest `periodic` or `v<N>` file in the
  DB's subdirectory, by stamp. Never a `replaced` or `.partial` file.
  Restoring an older backup means moving the newer files aside by hand (doc
  note in T14); `--from` stays cut.
- **`restore.restore(db_path, *, clock, probe, kill, popen,
  lock_wait_s=RESTORE_LOCK_WAIT_S)`**, behind `cp.py restore --confirm`
  (exempt; no `--confirm` → `USAGE`; guarded, like `halt clear`, by the
  `PreToolUse` `ask` prompt, since a restore discards everything since the
  backup):
  1. **Check, before stopping anything.** A refusal here writes no marker
     and calls no `ensure`. The checks, in order:
     1. the live DB's state, through `restore._live_state(path) -> (version,
        page_size) | None | "corrupt"` (it catches `sqlite3.DatabaseError`).
        Newer than the code → `SCHEMA_TOO_NEW`. `None` means missing, and so
        does a file with `user_version == 0` (a restore or first migration
        that failed earlier), which is then reused with `connect(mode="rwc")`
        so a retry is never stuck; `"corrupt"` goes on to step 5;
     2. `choose_source` finds nothing → `NOT_FOUND`;
     3. the source, opened **read-only** (`db.connect(src, mode="ro")`, so
        it is never rewritten), fails `quick_check`, has `user_version >
        current`, or has a `page_size` different from the live DB's (only
        compared when the live DB is readable; a new live DB gets the default
        4096, like every backup this code writes) → `CONFLICT`;
     4. only when `_live_state` returned a readable state: a live `started` tool call
        exists (`probe.holder_alive`) → `BUSY`.
  2. **Write the marker** `<db>.restoring` (`{pid, pid_start, at}`). From
     now on `ensure` answers
     `restoring` and spawns nothing, and a starting daemon exits at once.
     Steps 3–7 run under `try/finally`. `_stop_old` already takes
     `pending=` (#399), so `ensure` is untouched.
  3. **Stop the daemon.** `daemon.stop(db_path, *, clock, probe, kill,
     restart_wait_s, stale_after_s=STALE_AFTER_S) -> {"status": "stopped" |
     "not_running" | "signalled"}`:
     - a missing lease, or `pid IS NULL` → `not_running`;
     - otherwise it calls `_stop_old(lease, alive=probe.alive(…),
       fresh=_fresh(…), pending="signalled", …)`, and `None` → `stopped`.

     `ensure` keeps calling `_stop_old` directly and is unchanged. A
     `signalled` daemon is healthy, but still finishing its hook; it is
     left to step 4's `flock` wait rather than refused.
  4. **Take the locks:** the singleton `flock`, then the migrate lock, each
     waiting up to `lock_wait_s` (a parameter, so tests use 0). Still held →
     `BUSY`. Then, only when step 1's state was readable, check the live
     tool calls again → `BUSY`. The `BUSY` hint reads "the daemon may be
     finishing a tick; retry".
  5. **Keep the current DB:**
     - live DB present and readable → `write_copy` it to
       `db_dir(db_path)/harness_state.replaced.<stamp>.db`;
     - live DB missing → `db.connect(mode="rwc")`, and `replaced: null`;
     - live DB `"corrupt"` (random bytes, an invalid header), or
       `DatabaseError` from `db.connect` / `write_copy` → `CONFLICT`, with
       the hint "move it aside, then retry".
  6. **Restore:**
     1. read the live `waiters` rows, with their ids, and the live `meta`
        keys `selfcheck`, `selfcheck_override` and `selfcheck_pending` (`[]`
        and none when the live DB was missing). These keys describe the code
        on disk, not the restored data. Carrying them keeps a maintainer's
        `halt clear`, and also stops a backup's stale `ok: false, tries >= 3`
        record for the current version from re-closing a gate the live code
        has since passed;
     2. `src.backup(live_conn)`. The `page_size`s were checked equal in
        step 1;
     3. in one `db.begin(conn, "BEGIN IMMEDIATE")` (not `db.write`, since
        the version may be older), with `try/except BaseException: if
        conn.in_transaction: ROLLBACK; raise` (as `migrations` does):
        - replace `waiters` with the live rows, keeping their original
          `id` (a running `wait` deletes its row by id);
        - clear the daemon lease's `pid` / `heartbeat_at`;
        - replace `meta` `selfcheck`, `selfcheck_override` and
          `selfcheck_pending` with the live values read before (deleted when
          there were none), so the backup's stale copies never apply;
        - `COMMIT`.

     Why `waiters` are kept: a `wait` whose run token predates the backup
     keeps blocking after the restore, so dropping its row would make the
     watchdog wake a session that is waiting. A `wait` whose token is newer
     exits on its next poll (`STALE_TOKEN`) and deletes its own row.
  7. **Finally:** remove the marker, release the locks, call `ensure`.
     - On success the output is `{restored_from, backup_at, replaced,
       message}`.
     - The message reads: "Everything recorded after <backup_at> is lost.
       Run tokens issued since then are stale: each orchestrator must `run
       claim` again. The next ticks re-sync CI and liveness."
- **After a restore:**
  - an older-schema backup is migrated by the daemon that `ensure` starts,
    and any open `wait` stops on the schema change (#399);
  - restored `locks`, `cap_slots` and `tool_calls` are reaped by their
    holders' liveness, as always;
  - the re-sync: CI polls at once, and liveness refreshes the nodes. The
    self-check record is the live one, carried over.
- **No change-detection skip on the `backup` hook:** `PRAGMA data_version`
  misses the daemon's own writes, so a backup is taken every 15 minutes while
  a run is open.
- **The marker's placement:**
  - `daemon.run` checks it right after taking the `flock`, before
    `_me_with_start` / `_migrate`, and returns `{"ticks": 0, "exit":
    "restoring"}`. `_daemon` does not respawn on that exit;
  - `ensure` checks it right after the path guard, before `read_lease`,
    and returns `{"status": "restoring"}`;
  - `wait` keeps polling on `restoring`.

  While restore holds the migrate lock, read commands and hooks see
  `SCHEMA_PENDING`, or fail open. This is documented.

## Acceptance criteria

Each criterion maps to an automated test in `tests/qs/control_plane/`,
unless it is marked **manual**, **doc** or **socket bundle** (built only if
T1 succeeds). Tests run on a fake clock, fake liveness, a fake GitHub, a
fake socket and a fake `ClaudeCli`. Coverage stays at 100%.

1. **Registration:**
   - a hook registered through `ticks.register`, from a module imported by
     `cli`, runs under `cp.py daemon`;
   - a duplicate name raises `ValueError`;
   - `Throttle` respects its period;
   - a hook that raises is logged, and the loop goes on;
   - the guard test: no real subprocess or socket under `cp.py daemon`;
   - the real `make_seams` is covered.
2. **Kinds:**
   - every `KINDS` entry is 1–32 characters;
   - `CROSS_RUN_KINDS ⊂ KINDS`;
   - `ROUNDS_ALERT == 5`;
   - `fingerprint` changes with `n`;
   - in a real `python -I` subprocess: the `scripts/qs` modules loaded after
     `import control_plane.cli` plus `register_builtin()` are a subset of the
     D8 set, and the D8 set's members outside `control_plane/` are exactly
     `{cp.py, models.py, targets.py}`;
   - a missing D8 file is hashed as absent and never raises.
3. **Occurrences:**
   - a condition gives one row and one message per run; a two-run condition
     gives two messages;
   - the next tick raises nothing and refreshes the payload;
   - a clear then a recurrence, **at the same fake instant too**, gives a
     second row with `n = 2`;
   - omitted kinds neither clear nor raise;
   - **a daemon restart is not a recurrence:** T5 tests the engine (after
     `_reset_for_tests`, an open row and the same active set post nothing and
     clear nothing). Each later task adds its own restart test for its hook's
     cold state: T7 overlap, T10 `node_dead` / `orchestrator_dead`, T11b
     `orchestrator_not_listening` (AC 12), T12 `backup_failed` (AC 15);
   - closed runs get no message;
   - `snapshot["alerts"]` holds the open rows plus the newest cleared ones,
     and `--run` filters them.
4. **Restart:**
   - with a run open, a CP file change seen on two ticks makes `daemon.run`
     exit `new_code`, with its lease cleared;
   - `cli._daemon` then calls `ensure`;
   - a change seen once, or while `MERGE_HEAD` exists, triggers nothing;
   - a second `run()` in the same process does not exit at once;
   - with `IMPORTED_AT_NS` patched to `stamp = time.time_ns() - 10**9`, a
     hashed file whose mtime is set explicitly to `stamp + 10**6`
     (`os.utime(f, ns=(stamp + 10**6, stamp + 10**6))`, safely inside `[stamp,
     now]` at any timestamp resolution) makes `loaded_version()` return
     `unverified:…`, and the daemon exits `new_code` two ticks later;
   - **bootstrap:** a lease at schema 1 with the code at schema 2 → `ensure`
     stops the old daemon and starts the new one (T6b's AC 7 adds: its first
     tick records a `meta.selfcheck`);
   - a hashed file with an mtime in the future does not make
     `loaded_version()` unverified;
   - an exception from the respawn's `ensure` is reported as `"respawn":
     "error"`;
   - after `run()` returns `new_code`, a real `db.file_lock` on the
     daemon's `flock` is taken at once (singleton free before `ensure`);
   - a SIGTERM set during a hook ends the loop after that hook;
   - a restart requested mid-tick takes effect at the end of that tick;
   - with `loaded_version=None`, the `code_version` hook never restarts;
   - `ensure`'s `Popen` env holds no `CLAUDE_CODE_MESSAGING_*`,
     `CLAUDE_CODE_SESSION_ID`, `CLAUDECODE` or `CLAUDE_CODE_ENTRYPOINT`;
   - `started_code_version()` is the value `codever.loaded_version()`
     returned at `_daemon` entry, even when a file changes during
     `_migrate`. The test monkeypatches `loaded_version` to a sentinel; there
     is no reload;
   - `codever.loaded_version()` returns `None`, without raising, when
     `paths.main()` raises.
5. **Killed during `wait`:**
   - the lease's pid is a real child process (`sleep 60`);
   - while `wait` blocks, it is killed with `proc.kill(); proc.wait()`, so it
     is reaped and no zombie remains;
   - with the real `liveness.ProcessProbe()`, `wait` calls `ensure`
     (`started`) and returns on the next posted message.
6. **The merge gate** (`real_gate`, an accept-all `merge_policy`):
   - no record → `BUSY` ("pending"), raised before `gh pr view --json
     headRefOid` and `gh pr merge`, with the claim released;
   - **end to end, with no seeded `meta`:** a real `tool merge` at t0 gives
     `BUSY`; the fake clock moves `PENDING_ESCALATE_S + 1`; the same key then
     gives `POLICY_REFUSED` ("stuck"), proving `selfcheck_pending` was
     committed despite the `BUSY`;
   - one or two failures → `BUSY`, with `next_retry_at`;
   - `stuck` with a leftover `.git/index.lock` names that file in the
     refusal;
   - `SELFCHECK_ESCALATE_AFTER` failures → `POLICY_REFUSED`, in a text
     without `halt clear`;
   - a pass → the same key merges;
   - **after a revert:** vA seen pending by a `tool merge` at t0, then
     passed; vB's pass seeded **without** a `tool merge` while vB was
     pending; the fake clock moved past `t0 + PENDING_ESCALATE_S`; then back
     to vA → the first `tool merge` gives `BUSY`, not `POLICY_REFUSED` (a
     pass or a failure deletes `selfcheck_pending`);
   - vC recorded pending, then vD on disk → `BUSY` with a fresh `since`, not
     `stuck` (another version's record is replaced);
   - a CP file change → `BUSY` again;
   - `halt clear --reason r` opens the gate for this version only;
   - a newer DB → `SCHEMA_TOO_NEW`;
   - a missing DB → `NOT_FOUND`;
   - the `PreToolUse` hook answers `ask` (not deny, not allow) for a Bash
     `cp.py halt clear` segment in a mode in `ASK_MODES`, `deny` with the
     "switch to default mode" hint in any other mode, and still denies a
     DB-access segment.
7. **Self-check:**
   - each step fails on its own fixture:
     - `schema`: a wrong `user_version`;
     - `entry`: a failing `cp.py version`, or a tool or hook name missing
       from its output;
     - `registry`: a plain `TypeError` and an `ImportError`, each recorded as
       a failure, never escaping;
   - each failure → `ok: false` and `tries + 1`, and `selfcheck_failed`
     reaches every open run **from the first failure**;
   - a retry never comes before `meta.selfcheck.at + SELFCHECK_RETRY_S`,
     **including after a daemon restart**, and retries never stop;
   - a run opened later still gets an active alert;
   - a pass, an override or a version change clears the alert;
   - a recorded pass, or an override, is not re-run;
   - a new version after a failed one is checked on its first tick, not
     after `SELFCHECK_RETRY_S`;
   - **bootstrap (with T6a's AC 4):** the new daemon's first tick records a
     `meta.selfcheck`;
   - while the loaded version differs from the disk version, the check is
     skipped and records nothing.
8. **Detectors.** Each fires on its fixture and clears when the fixture is
   fixed.

     - two runs' deliverables → `overlap_cross_run`, with `conflicts`;

      `.partial`, and `choose_source` never picks a `.partial`;

### Deviations and notes so far

- **T7 overlap:** the refs resolved during an overlap walk (tips, the base,
  ancestry) are kept until the walk completes or fails. Without it, a walk
  over 10 branches spends its whole `OVERLAP_MAX_CALLS` budget on
  `rev-parse` every tick and never completes. The diff / merge-tree caches
  stay the only cross-walk state.
- **T9:** a `null` GraphQL alias is an unknown PR (`None`) whether or not its
  `NOT_FOUND` error is present.
- **T4 / T13 — the import cost:** with every hook module registered, the new
  Control Plane modules cost ~3.4 ms of self import time per `cp.py` call,
  plus ~0.3 ms for `models` (`python -X importtime cp.py version`, three
  runs) — well under the 30 ms budget, so registration stays at import.
- **T11b:** the ladder keeps no state in memory. It is derived each tick from
  the head message's `watchdog-messenger` row (none → claim and launch;
  `failed` → rung 3; `succeeded` → rung 3 once `started_at + WAKE_RETRY_S`

  rebuild anyway. A run that is busy, absent, waiting or `orchestrator_dead`
  keeps its open `orchestrator_not_listening` as is (re-emitted, neither
  raised nor cleared); a drained or fresh head clears it.
