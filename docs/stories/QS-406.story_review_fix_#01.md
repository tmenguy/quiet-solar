## Findings to fix

### [must-fix] F1 — Watchdog messenger claim row can stay `started` for the life of the daemon
- File: `watchdog.py:242-269` (`_launch`), `watchdog.py:317` (`_ladder`)
- Severity: must-fix
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter
- Description: `_launch` commits the `tool_calls` claim row (`state='started'`,
  with the live daemon's own pid as holder) **before** these calls:
  `paths.ensure_private_dir(paths.messenger_dir())`, `spawn_bg`,
  `daemon.beat` and the second `db.write`. If any of them raises
  (`CpError POLICY_REFUSED` on a bad `QS_CP_MESSENGER_DIR`, `OSError`, or
  `BUSY`), the row is never closed. `_fail_stale_messengers` only reaps rows
  whose holder is dead, so `_ladder` returns `None` ("launch in progress")
  forever:
  - no wake-up is sent;
  - `orchestrator_not_listening` is never raised;
  - the global messenger cap stays taken for every run.
- Proposed fix:
  1. Resolve and create the messenger dir **before** the claim.
  2. Wrap everything after the claim in `try/except Exception`. On failure,
     mark the row `failed` (with exit_code/result carrying the exception
     text, and no secrets) so the next tick's ladder escalates to
     `orchestrator_not_listening`.
  3. Belt and braces: `_fail_stale_messengers` also fails a `started`
     messenger row older than `MESSENGER_TTL_S`, even when its holder is
     alive.

  Tests:
  - a bad messenger dir → no row left `started`, and the next tick gives
    `orchestrator_not_listening`;
  - `spawn_bg` raises → the row is `failed`, then escalation;
  - an aged `started` row with a live holder is reaped.

### [should-fix] F2 — One bad hook event stops hook routing permanently
- File: `hookroute.py:60-71` (`route_locked`)
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: the batch and the cursor move in one transaction. If
  `alerts.event_locked` raises for one event, everything rolls back, the
  cursor stays put, and every later tick fails on the same row.
- Proposed fix: route each event inside a SAVEPOINT. On an exception, roll
  back to the savepoint, log once (event id + error), and treat the event as
  unroutable so the cursor still advances past it.
  - Test: a poisoned event (force `event_locked` to raise for one id) is
    skipped, later events are routed, and the cursor moves past both.

### [should-fix] F3 — A routed hook event can claim a built-in alert kind

### [should-fix] F4 — A restore that fails after the copy leaves a half-restored DB and drops the `replaced` path
- File: `restore.py:191-216`
- Severity: should-fix
- Source: qs-review-blind-hunter + qs-review-edge-case-hunter
- Description: `source.backup(conn)` has already overwritten the live DB by
  the time the fix-up transaction runs (waiters, `daemon_lease`, carried
  selfcheck meta). If the fix-up fails, the live DB is half-restored and the
  lease is not cleared. The `CONFLICT` error ("move it aside") drops the
  `replaced=<path>` pointer.
- Proposed fix:
  1. Before the copy, check that the source has the tables `_restore_into`
     writes to (`waiters`, `daemon_lease`, `meta`). If one is missing, raise
     `CONFLICT` with nothing touched.
  2. Catch a failure *after* the copy separately. Raise a distinct error
     that says the data was restored but the fix-up failed, and carry
     `replaced=<path>` (the pre-restore copy) in the message or hint.

  Tests:
  - a source missing `waiters` → refused, with the live DB byte-identical;
  - an injected fix-up failure → the error names the replaced path.

### [should-fix] F5 — `detect_stalled` never reports a node whose `started` tool call has a dead holder
- File: `detectors.py:244-245`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: a SIGKILLed `cp.py` tool call stays `state='started'`, and the
  node is skipped forever.
- Proposed fix: skip the node only when the started call's holder is alive

### [should-fix] F6 — A stale `.git/index.lock` silently freezes overlap detection and the restart-on-new-code
- File: `codever.py:120-126` (`git_busy`), used at `detectors.py:212` and
  `selfcheck.py:47`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: a crashed git leaves `index.lock`. As a result:
  - `detect_overlap` serves `_cached_overlap()` forever;
  - `code_version_hook` never restarts the daemon;
  - nothing alerts.
- Proposed fix: ignore an `index.lock` whose mtime is older than a named
  constant (for example `GIT_LOCK_STALE_S = 600`), and log once that it was
  ignored as stale. `MERGE_HEAD` / `rebase-*` stay "busy" (a legitimate
  long operation), and the merge gate's existing STUCK clause already covers
  them. Add the constant to the docs' constants table.
  - Tests: a fresh lock → busy; an aged lock → not busy, logged.

## Skipped this round (recorded, not fixed)
- A PR that permanently returns `null` keeps a stored `red` (ciwatch). It
  needs a policy decision about how many polls to wait.
- Restore fallback to an older valid backup. This is a behaviour change to a
  maintainer-confirmed command, so it is better as its own story.
- A dead restore marker whose `pid_start` is None. The pid-reuse case is
  rare, and a staleness rule needs design.
- Relative `gitdir` (`worktree.useRelativePaths`) and a main checkout whose
  `.git` is a file. The repo doesn't use either today.
- A clock going backwards (negative ages).
- `codever.loaded_version()` hashes `paths.main()` rather than the import
  root. That matches the design: the daemon always runs main's code.
- `maintainer_confirm` with a global flag before the subcommand. This limit
  is already accepted in the docstring.
- D1 socket-bundle follow-up issue: the maintainer files it at finish (a
  process item, outside the diff).
