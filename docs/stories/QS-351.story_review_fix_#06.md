### [should-fix] SF-1 — Stated aggregate bound is `(n-1)·M`; the correct bound (and what the code uses) is `n·M`
- File: `custom_components/quiet_solar/const.py:497-501` (relation (i));
  `custom_components/quiet_solar/ha_model/home.py:2703` (pass-2 comment);
  `docs/stories/QS-351.story.md:856, :863`; `tests/test_person_car_allocation.py:996`
  (pin docstring); PR #354 body `## Review-fix #05`.
- Severity: should-fix
- Source: qs-review-regression-proof + qs-review-edge-case-hunter (found independently)
- Description: The rewritten comment says two assignments whose preferred count
  differs by one "can differ in base cost by up to `(n-1)*(max_base - min_base)`"
  and derives the shipped offset from it. Two perfect matchings can differ in
  **all n** cells, so the correct bound is `n·M` with `M = E_max + 1.0 + PLUGGED`
  — exactly what the code ships (`n·M + eps`, margin = eps = 1.0 Wh for all n,
  E_max). The text is off by one factor of M and evaluates to 0 at n == 1.
  Counterexample to `(n-1)·M` (regression-proof): n = 2, E_max = 0, A = {p0→c0
  plugged sentinel 1.25, p1→c1 plugged sentinel 1.25}, B = {p0→c1 covered 0,
  p1→c0 covered 0}, p0 prefers c0 → base gap = 2·1.25 = n·M; A wins only if
  offset > 2.5. Edge-case-hunter: `(n-1)·M + 1.0` fails 221/6000 sweep cases;
  smallest witness n=1, m=4, E_max=879.27, row `[-1.0, 879.27, -2.0, 0.0]`,
  plugged `[F,F,T,F]`, preferred c2 → solver picks c1 (0 preferred) over c2
  (1 preferred, the max). **The new pin does not catch this**: forcing the
  multiplier to `(n-1)` leaves `test_pass2_offset_dominates_aggregate_spread`
  green. Risk: a reader "tightens" the constant to its own stated bound.
- Proposed fix: (a) Replace `(n-1)*(max_base - min_base)` with
  `n*(max_base - min_base)` in const.py relation (i), home.py:2703, the story
  #05 progress note (:856/:863), the pin docstring and the PR body; state the
  margin directly: `PASS2_offset − n·(E_max + 1.0 + PLUGGED) = eps = 1.0 > 0`
  for all n ≥ 1, E_max ≥ 0. (b) Pin the multiplier: add the n == 1 witness
  above as a second test (or parametrisation) in `TestSentinelAndPass2Ordering`,
  asserting the preferred car (c2) is chosen and the preferred pass adopted via
  `caplog`; run it red first with the multiplier forced to `(n-1)` (baseline
  `9735f46d` + local mutation — state how the red state was produced) and record
  the full verbatim `pytest tests/...::Class::test -v` transcript (progress line,
  FAILED line, assertion block, `path:line: AssertionError`, `1 failed in …s`) in
  the story progress note and PR body. No production behaviour change.

### [nice-to-have] N-2 — maxi_val argument is per-cell; the guarantee actually rests on the `1e12` floor
- File: `custom_components/quiet_solar/const.py:505-508`; `custom_components/quiet_solar/ha_model/home.py:2542`
- Severity: nice-to-have
- Source: qs-review-regression-proof (edge-case-hunter confirms the conclusion holds)
- Description: The comment compares maxi_val to "the largest legitimate pass-2
  cell"; the correct comparison is against a whole assignment (n × largest
  legitimate cell). The second `max(...)` branch `(E_max + 1.0)·(1 + max(m, n))`
  is always below the largest legitimate pass-2 cell, so the forbidden-pair
  guarantee rests solely on the `1e12` floor — still ~5–6 orders of margin for
  realistic n, E_max (break point ≈ 5e11 Wh per car). Conclusion correct,
  reasoning loose.
- Proposed fix: State it as "an assignment using a forbidden cell costs ≥ 1e12,
  while any fully legitimate assignment costs ≤ n·((n+1)·(E_max + 1.25) + 1.0)
  ≪ 1e12 for realistic n, E_max; the `1e12` floor is what carries the
  guarantee". Comment-only.
