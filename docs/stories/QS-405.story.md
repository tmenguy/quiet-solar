# QS-405 — Rendering and models for the new pipeline's agents

**Issue**: [#405](https://github.com/tmenguy/quiet-solar/issues/405) ·
**Lane of this task**: feature-factory (`target:factory`) ·
**Parent epic**: #369 (child 6c, wave 4)

Status: planned (story v4 — converged after 3 review rounds)

## Problem

The second pipeline (epic #369) needs a frame for its agents before the
children that write their prompts (6a, 6b, 13, 15) can start. Today:

1. **`render_agents.py` knows only the frozen pipeline.** Its registry is
   `ORCHESTRATORS` (10, the values of `PHASE_TO_AGENT`), `LANE_AWARE` (7)
   and `SUBAGENTS` (12). Two test files pin that these 22 are the whole
   world:
   - `tests/qs/test_render_agents.py`: the `== 22` file counts, and the
     glob `== ORCHESTRATORS | SUBAGENTS`;
   - `tests/qs/test_models.py`: `len(STEMS) == 22`, `STEMS ==
     ORCHESTRATORS | SUBAGENTS`, the discovered templates `== STEMS`, and
     the flat rows `== STEMS` minus the planning stems.

   A new template under any other stem breaks them.
2. **A bound render puts task facts into every agent.** `render_all`
   resolves each stem's model with the worktree's lane, and `_base.md.j2`
   writes `lane=… issue=…` in the GENERATED comment. The new pipeline's
   agents must be task-agnostic: the facts travel in the launch prompt and
   the Control Plane (epic, "Agent prompts: rendering").
3. **`models.py` has no rows for the new roles.** Its decision D1 says
   only the two planning orchestrators are lane-dependent.
4. **`tool spawn` never reads the policy.** It passes `--model` only when
   its caller gives one, and never passes an effort. Frontmatter
   `effort:` does not reach a main session.

## Goal

The frame the new pipeline's agents plug into, with no prompt:

- a new agent set with the **five role names** fixed by the epic;
- their **policy rows**, and the rule for the rows 6b adds;
- the set renders **wherever `render_all` runs**, with **no task facts**,
  and **never in an integration scratch**;
- **`tool spawn` takes its model and effort from the policy** when its
  caller gives no model, with the lane coming from the task.

The frozen agents, their rendering and their counts are unchanged.

## Terms

- **Claim**: a tool call's `tool_calls` row, written under `(tool, key)`
  before any effect.
  - A `USAGE` (or `BUSY`, …) raised while the call has no recorded step
    output **releases** the claim, so the same key works again.
  - The same codes after an output, and any `INTERNAL`, leave the claim
    `started`. A same-key call takes it over once this process has
    exited.
  - A `StepFailed` records the call `failed` (`TOOL_FAILED`), and the key
    is spent.
- **Probe**: the tool function that runs when a call is replayed or taken
  over, and rebuilds the step outputs from the real world. For `spawn`,
  `_launch_probe` rewrites `outputs["reserve"]` to `{node_id, name}`. A
  value computed in `reserve` therefore cannot reach `launch` through the
  step outputs.
- **Render sites**, the places where `render_all` runs:
  - **Worktree birth, `setup_task.py`.** A deliverable gets a bound
    render. An item gets a `bound=False` render, through `--item`, which
    `tool item-create` reaches. `tool worktree-create` runs
    `setup_task.py` too, so a second-pipeline deliverable worktree gets
    the same bound render as a frozen-pipeline worktree.
  - **The handoff, `next_step.py`:** bound, with the same context
    builder as birth.
  - **The post-merge render on `main`** (`qs-finish-task`) and the manual
    `python scripts/qs/render_agents.py`: unbound, on branch `main`.

  The integration scratch is made by `worktree-setup.sh --integration`,
  which renders nothing. Its checkout still has the tracked
  `.claude/settings.json` and `.claude/commands/`, but no `agents/`.

## Decisions

- **D1 — The set is `SECOND_PIPELINE`** in `render_agents.py`:
  `{"qs-orchestrator", "qs-node", "qs-global-review",
  "qs-cross-run-review", "qs-final-review"}`.
  - It is disjoint from the three frozen sets and is not in
    `PHASE_TO_AGENT`.
  - Child 6b adds the node's sub-agents to it.
  - No real template is added here, and a stem may have its policy row
    before its template exists.
  - `render_all` iterates over the **discovered templates**, not over
    `models.STEMS`, so a row without a template renders nothing and does
    not fail.
- **D2 — A second-pipeline agent renders with no task facts (an
  allowlist).**
  - **The constant.** `_TASK_AGNOSTIC_FACTS` holds every key
    `build_render_context` returns except `model`: `branch`, `issue`,
    `title`, `labels`, `lane`, `worktree`, `story_file` and
    `lane_protocol` are `None`, `facts_state` is `"unbound"`, and
    `lane_protocol_state` is `"no_lane"`.
  - **The per-stem loop.** A stem in `SECOND_PIPELINE` gets the
    **replacement** base context `{**_TASK_AGNOSTIC_FACTS, "model":
    context.get("model")}`. Nothing else from `context` reaches it. Every
    other stem gets `context`, as today.
  - **A key-set test** asserts `set(_TASK_AGNOSTIC_FACTS) | {"model"} ==
    set(build_render_context(...))`. A key that a later child adds to the
    context then forces a decision.
  - **The pre-pass** resolves the stem's model with `lane = None if stem
    in SECOND_PIPELINE else context.get("lane")`.
  - **What the template sees.** The flags `orchestrator` and
    `lane_aware` stay false for the set, so `_base.md.j2` writes no "Task
    facts" and no "Reference map". The GENERATED line is built from
    `[[ template ]]` (= `f"{stem}.md.j2"`) under a constant
    `scripts/qs/agent_templates/` prefix, and from the existing
    `lane or "none"` / `issue or "none"`. It reads:

    `<!-- GENERATED by scripts/qs/render_agents.py from scripts/qs/agent_templates/qs-node.md.j2 — harness=claude lane=none issue=none. DO NOT EDIT; edit the template and re-render. -->`

    The line does not depend on the templates dir (`render_all`'s
    `templates_dir=` parameter).
  - **Byte-identical.** For the same tree, and absent an explicit
    `model=` override (no production render site passes one), the
    rendered file is byte-identical at every render site.
  - **A worktree may still differ from main.** Its `models.py` can differ
    from main's (an unmerged branch), so its frontmatter can name a model
    that main's policy does not. That is harmless for a spawned session,
    because the spawn's `--model` comes from main's policy and wins over
    the frontmatter.
- **D3 — The classes of the five roles.**
  - These are this child's choice (maintainer, 2026-10-03). They are a
    starting point, and the maintainer may retune them later. A retune is
    a one-row edit in `models.py` plus its line in
    `tests/qs/test_models.py`.

  | role | class | why |
  |---|---|---|
  | `qs-orchestrator` | `frontier` (flat) | the run's planning conversation and judgment |
  | `qs-node` | **by lane**: `bug-*` → `deep`, other lanes → `frontier`, no lane → `deep` | a mini-orchestrator that plans and triages; the planning orchestrators' rule |
  | `qs-global-review` | `frontier` (flat) | coherence judgment over one run |
  | `qs-cross-run-review` | `deep` (flat) | code-grounded overlap between runs; mixed with the global review on purpose |
  | `qs-final-review` | `frontier` (flat) | the run's readable verdict |

  - The GUI orchestrator's model comes from the picker, and its effort
    from child 9's pin. The `qs-orchestrator` row is what that pin reads.
- **D4 — The rule for the rows 6b adds (this rewrites models.py's D1).**
  - **The rule.** Besides the two planning orchestrators (`_PLANNING`), a
    row may depend on the lane **only** for a stem that a Control Plane
    tool launches. `models.py` states this in its rewritten D1 comment.
  - **The allowed domain.** It is the test-local set `CP_LAUNCHED =
    {"qs-node", "qs-global-review", "qs-cross-run-review",
    "qs-final-review"}` in `tests/qs/test_models.py`, next to the D4 rule
    test. No production code needs it, so `models.py` carries no such
    constant.
  - **Growing it.** Adding a stem to the domain is a deliberate edit of
    that test.
  - **Today.** Only `qs-node` actually depends on the lane. Child 15
    decides whether a review is launched with a lane; a cross-run review
    never has one.
  - **Every other new row is flat**, the node's sub-agents included. They
    render with no task facts, so their frontmatter cannot know a lane.
  - **Classes keep their meaning:** implementer `build`, reviewers spread
    across classes, mechanical `fast`.
- **D5 — The resolver is `models.spawn_policy(stem, lane) -> tuple[str,
  str | None]`.**
  - It returns `(model_for("claude", cls), effort_for(cls))` with
    `cls = resolve(lane, stem)`. It covers the `claude` harness only,
    because the spawn is `claude --bg`.
  - It raises `ModelPolicyError` for an unknown stem. That class already
    subclasses `ValueError` (`models.py`, test-pinned).
  - It raises a plain `ValueError("lane 'x' is not one of models.LANES")`
    for a lane that is neither `None` nor in `LANES`. There is no new
    exception class.
  - `resolve` itself still never raises on lane data.
  - `effort_for` returns only `high`, `medium` or `None`. `high` and
    `medium` are the `effortLevel` values the GUI pin already writes.
- **D6 — The wiring: one lazy import, in `control_plane/cli.py`, run only
  when a spawn calls the resolver.**
  - **The alias.** `tools.py` defines `ResolveModel =
    Callable[[str, str | None], tuple[str, str | None]]`.
  - **`cli.Deps`** gets a required field `resolve_model:
    tools.ResolveModel`. `Deps` has no defaulted fields today, and it is
    built only in `make_deps` and in the `deps` fixture.
  - **The resolver.** `make_deps` stores `cli._policy_resolver`, which
    runs `import models` **at call time** and returns
    `models.spawn_policy(stem, lane)`, through a typed local
    (`result: tuple[str, str | None] = …; return result`), so mypy never
    sees an `Any` return. It catches nothing. An exception
    raised by the import (an `ImportError`, or a `SyntaxError` from a
    half-edited file) propagates, and `cli.main` already maps every
    unexpected exception to `INTERNAL`. The claim is then left `started`
    for a takeover (Terms).
  - **What stays free of the policy.** Calling `make_deps` never imports
    `models`, so the hooks (the fail-closed `pre-push` included), `wait`
    and the daemon never touch the policy.
  - **Which tree the policy comes from.** `cp.py` runs as a script, so
    `sys.path[0]` is its own `scripts/qs`. `models` therefore comes from
    the same tree as the running Control Plane, and control-plane.md
    says that tree is always `<MAIN>`. A test asserts
    `Path(models.__file__).parent == Path(cli.__file__).parents[1]`.
    Under pytest both load from the same `scripts/qs`, so this test is a
    cheap regression pin, not proof of the production path. What
    guarantees the production path is that `cp.py` runs as a script.
  - **Consequence.** A stem whose row exists only on an unmerged branch is
    `USAGE` at spawn. This is documented.
  - **Lint and types.** ruff selects no `PL` rules, and mypy has
    `ignore_missing_imports = true`, so the lazy import needs no config
    change.
  - **`tools.Ctx`** gets `resolve_model: ResolveModel | None = None`, a
    defaulted last field. The three positional `tools.Ctx(...)` calls in
    `test_tools.py` never spawn and stay valid.
  - **Reaching the resolver.** `_tool_handler` passes `d.resolve_model`,
    and the steps reach it as `ctx._call.ctx.resolve_model`, the
    tools.py-internal path that `_reserve_prelude` already uses. The
    frozen `StepCtx` API is unchanged.
  - **`default_ctx()`** has no resolver, on purpose. A spawn through
    `invoke(ctx=None)` with no caller model is `USAGE`, so child 15 must
    pass a `Ctx` that carries the resolver.
  - **The purity test.**
    `tests/qs/control_plane/test_import_purity.py::test_control_plane_imports_only_stdlib_and_itself`
    applies the issue's rule, "the Control Plane imports only the standard
    library and itself". It is about twenty lines; the precedent is the
    AST scan in `tests/qs/test_mermaid_svg.py`. It walks every
    `scripts/qs/control_plane/*.py` (the package is flat) with
    `ast.walk`, and allows:
    - `ImportFrom` with `level >= 1`;
    - `__future__`;
    - a top-level name in `sys.stdlib_module_names`;
    - and the single `Import(models)` whose enclosing `FunctionDef` is
      `_policy_resolver` in `cli.py`.

    Today's tree passes it; this was checked.
- **D7 — The lane of a spawn.**
  - **`nodes.lane_of(conn, task_id) -> str | None`** reads
    `nodes.deliverable_of(conn, task_id)`. That returns the task itself
    for a deliverable or a standalone task, and the `deliverable_id` row
    for an item. An item's own `lane` column is ignored.
  - **The value.** It returns the deliverable's `lane` if non-empty, else
    `tasks.derive_lane(kind, target)`.
  - **`derive_lane`** returns `None` when `target` is `None` or `""`, and
    `f"{kind}-{target}"` otherwise. A single formula is enough, because
    `kind = "epic"` gives `epic-<target>`.
  - **The cases that cannot arise.**
    - An unknown task: `run_recorded` raises `NOT_FOUND` before the steps
      run.
    - An empty or unknown kind: `kind` is `NOT NULL` with a `CHECK` over
      `{epic, feature, bug}`.
    - A missing deliverable: `deliverable_id` is an enforced foreign key.
  - **Refusals.** A free-text target such as `nope` derives to
    `feature-nope`, which the resolver refuses (D5). So does a free-text
    `lane`, since `task add --lane` does not validate it.
  - **The columns are fixed.** `lane`, `kind` and `target` are set once
    at `task add`; they are not in `tasks.SETTABLE`.
  - **Parity with the render.** The derivation mirrors
    `targets.parse_axes`: the task `kind = "epic"` corresponds to the
    label `scale:epic`. So **when `lane` is unset**, a node's lane equals
    the lane of the bound render of the same worktree, which the parity
    grid tests. No epic deliverable is spawned in this child.
- **D8 — How `tool spawn` behaves.**
  - **A caller's `model` wins.** It is passed as `--model <model>`
    verbatim, and the spawn adds **no `effortLevel`**. This is this
    child's decision, not the issue's.
  - **No caller model.** `_spawn_policy(ctx) -> tuple[str, str | None]`
    reads the lane with `with ctx.write() as conn: lane =
    nodes.lane_of(conn, ctx.task["id"])`. It then calls the resolver
    **after the block**, so no DB lock is held across an import. It runs
    at two points:
    The error contract: `_spawn_policy` raises `ValueError` for a
    missing resolver (`"no model policy resolver"`), and lets the
    resolver's own `ValueError` propagate unchanged (an unknown agent, an
    invalid lane). `CpError` is not a `ValueError`, so the two never
    catch each other.
    1. **First in `reserve`, before `_reserve_prelude`, as a
       pre-check.** `reserve` turns a `ValueError` into
       `CpError("USAGE", <its message>)`. Nothing is recorded yet, so the
       claim is released and no `nodes` row is written.
       *(Review fixes #01 and #02.)* The refusal — and any other failure
       of the pre-check, re-raised unchanged (`INTERNAL`, D6) — is raised
       inside the reservation transaction, after the adopt branch and
       before a re-take or a new row: adopting a late launch launches
       nothing and needs no policy.
    2. **In `launch`, after `prompt = arg_file_text(...)` and before
       `_launch` stamps `launch_at`.** This value is authoritative, and
       the `start` closure captures it. The probe rewrites `reserve`'s
       output (Terms), which is why the policy is resolved again here
       rather than carried over.
  - **Why the two resolutions can differ.** Inside one process the
    module is cached, so they can differ only on a takeover in a new
    process, after main's `models.py` changed in between.
  - **If the launch resolution fails** (any `ValueError`, a missing
    resolver included, for example when a takeover goes through a `Ctx`
    without one), `launch` raises `StepFailed`: the call is recorded
    `failed` (`TOOL_FAILED`), and the key is spent. That is exactly what a failed `claude --bg` does today.
    Nothing is launched, and the row stays `spawning` with no `launch_at`.
    The next admission reaps it once the holder has exited, as
    `locks.admit_node` already does. Recovery is the same as for any
    failed launch:
    - the same key → `TOOL_FAILED` (spent);
    - a new key without `--replace` → `CONFLICT` (the `spawning` row
      counts as live);
    - `tool resume` → `INVALID_STATE` ("is spawning" until the row is
      reaped, then "never launched");
    - a new key **with `--replace`** supersedes the stuck row directly
      (`spawning → superseded` is allowed) and launches.
  - **The argv.** `--model <model>` stays in its slot after `-n <name>`.
    The settings become `json.dumps({**hooks.hooks_settings("node",
    ctx.main), **({"effortLevel": effort} if effort else {})},
    sort_keys=True)`. `sort_keys=True` and the inline JSON are already
    today's serialization, and the existing test compares parsed JSON.
    `hooks.hooks_settings` is unchanged, because it also feeds child 9's
    pin.
  - **Where the effort comes from.** Claude Code's settings precedence
    puts command-line `--settings` above the local, project and user
    files, so a spawn's `effortLevel` wins. **When the spawn sends none**
    (a caller model, or a class with no effort), the session takes its
    effort from those files: in a `tool worktree-create` worktree, the
    phase pin that the launcher writes into `.claude/settings.local.json`
    (typically `high`), else the user's settings. The spawn cannot clear
    a pinned effort. This is an accepted limitation, written in the
    spawn row of control-plane.md so child 15 does not assume otherwise.
  - **Nothing new is recorded in `tool_calls`.** The model is visible in
    the argv, and the spawn's result is unchanged.
- **D9 — `resume` is unchanged, and two points are recorded as
  unverified.**
  - **Why `resume` is untouched.** A bare `claude --bg --resume` takes no
    flag: any extra flag forks a copy.
  - **Who records what.** The issue says the check "is checked together
    with child 6b's resume check. This child records the result." This
    child cannot run that check, because 6b builds the resumed node. It
    records the open points next to the hooks item, and 6b writes the
    result there.
  - **The two points:**
    - whether a resumed node keeps its model and effort, which 6b's
      resume check answers;
    - whether `effortLevel` through `--settings` takes effect on a `--bg`
      session, which the first real node spawn (6b) can observe.
  - **Where the answers go.** 6b writes the results into control-plane.md
    and, for the effort path, into harness.md's new bullet.

## Design

### `scripts/qs/models.py`

- `_PLANNING` stays the two planning orchestrators, for the D4 test.
- A new `_BY_LANE = _PLANNING | {"qs-node"}`.
- `resolve` checks `stem in _BY_LANE`, and those stems use
  `_planning_class`.
- `STEMS = frozenset(_FLAT) | _BY_LANE`.
- `_FLAT` gains:
  - `qs-orchestrator: frontier`;
  - `qs-global-review: frontier`;
  - `qs-cross-run-review: deep`;
  - `qs-final-review: frontier`.
- New, with docstrings and type hints: `spawn_policy` (D5). The D4 rule
  goes into the D1 comment; there is no constant for it.
- Rewrite the D1 comment, and the module docstring, which names the
  consumers: the Control Plane's spawn now reads the policy. `models.py`
  still imports nothing from the renderer.

### `scripts/qs/render_agents.py`

- `SECOND_PIPELINE` (D1) lands in task 2, with `models.py`, because
  `test_models.py` imports it.
- The rest lands in task 4:
  - `_TASK_AGNOSTIC_FACTS` (D2);
  - the pre-pass lane and the replacement base context in `render_all`
    (D2);
  - the module docstring.

### Control Plane (`scripts/qs/control_plane/`)

- `tasks.py`: `derive_lane(kind, target) -> str | None` (D7).
- `nodes.py`: `lane_of(conn, task_id) -> str | None` (D7).
- `tools.py`:
  - the `ResolveModel` alias (task 5's structural step) and
    `Ctx.resolve_model` (D6);
  - `_spawn_policy` (D8);
  - `reserve` and `launch` per D8, with the settings merge.
- `cli.py`:
  - `Deps.resolve_model` and `_policy_resolver`;
  - the `make_deps` wiring;
  - `_tool_handler` passing the resolver to `tools.Ctx` (D6).

## Acceptance criteria

1. **AC1 — The set.**
   - `render_agents.SECOND_PIPELINE` is exactly the five role names.
   - It is disjoint from `ORCHESTRATORS | SUBAGENTS`, and absent from the
     values of `PHASE_TO_AGENT`.
   - The frozen counts still hold: `len(ORCHESTRATORS) == 10`,
     `len(SUBAGENTS) == 12`, `len(ORCHESTRATORS | SUBAGENTS) == 22`.
2. **AC2 — Renders at every site, with no task facts**
   (`test_second_pipeline_renders_task_agnostic`, in
   `tests/qs/test_render_agents.py`).
   - **Fixture.** A templates dir in `tmp_path` holds copies of the real
     `*.md.j2`, plus a fixture `qs-node.md.j2`. The fixture extends
     `_base.md.j2`, with `name: qs-node` / `model: [[ model ]]` in both
     frontmatter blocks.
   - **Three contexts,** each rendered with
     `render_all(..., templates_dir=<fixture>)`, its own `out_root`
     (`tmp_path/"main"`, `/"deliverable"`, `/"item"`), and
     `lanes_dir=LANES_DIR`, with `r._current_branch` monkeypatched:
     - **main:** branch `"main"`, the default `build_render_context`
       with `fetch=False`;
