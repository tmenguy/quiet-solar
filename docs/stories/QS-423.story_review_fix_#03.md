## Findings to fix

### [should-fix] The stop backoff is anchored after the listing, so a slow listing delays every retry by a tick
- File: `scripts/qs/control_plane/reviewpilot.py` (`_backoff`, `stop_closed`: `started`, `retry_at`); `docs/workflow/control-plane.md` (step 4 "Backoff" bullet)
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-edge-case-hunter (both raised it independently); also clears qs-review-edge-case-hunter's nice-to-have (unclamped `2 ** (attempts - 1)` can raise `OverflowError` as a float) and qs-review-acceptance-auditor's nice-to-have (`test_fewest_attempts_first` passes only because `HOOK_SUBPROCESS_S > PILOT_EVERY_S / 2`)
- Description: `retry_at = started + _backoff(rid)`. `started` is read **after** `try_agents`, which can take up to `HOOK_SUBPROCESS_S`, while the next tick compares against its own `now`, read before its listing. The half-tick slack (15 s) cannot absorb a listing longer than ~15 s plus the jitter of steps 1–3. So a stopped review's confirmation, and every retry, slips one throttled tick: 60/90/150 s instead of the documented 30/60/120 s. Wall-clock arithmetic also needs the slack fudge in the first place.
- Proposed fix: count the backoff in **pilot ticks**, not wall time.
  - Replace `_State.retry_at: dict[str, datetime]` with `_State.tick: int = 0` and `_State.retry_tick: dict[str, int]`, pruned to the window like the other fields.
  - `stop_closed` increments `_state.tick` once on entry. It runs once per due `PILOT_EVERY_S` tick, and each direct call in the tests counts as one tick.
  - After a tick sends stops to `rid`, set `retry_tick[rid] = _state.tick + min(2 ** min(attempts[rid] - 1, 16), STOP_BACKOFF_MAX_S // PILOT_EVERY_S)`. This is int arithmetic with the exponent clamped, so it cannot overflow, and `STOP_BACKOFF_MAX_S` becomes an int (3600).
  - A candidate is eligible when `_state.tick >= retry_tick.get(rid, 0)`. Drop the `- PILOT_EVERY_S / 2` slack and its docstring wording.
  - The first retry is the next tick (delay 1), then 2, 4, … ticks, capped at 120 ticks (1 h at `PILOT_EVERY_S = 30`).
  - The clock is no longer read for the backoff. The clock-step-back guard on the stop budget (fix #01) stays.
  - Tests:
    - Rework the always-124 backoff test to count ticks: stops on ticks 1, 2, 4, 8, … and on no tick in between, with no listing on a skipped tick when it is the only candidate, and the cap at 120 ticks.
    - Add a test where the listing itself advances the fake clock by `HOOK_SUBPROCESS_S` (a slow listing). The retry still comes on the next tick.
    - The `later()` helper may stay, but no test should depend on clock advances for the backoff any more. In particular, `test_fewest_attempts_first` must pass even with `HOOK_SUBPROCESS_S` patched below `PILOT_EVERY_S / 2`: monkeypatch it in that test, or assert directly.
  - Docs: step 4's "Backoff" bullet and the module docstring speak in pilot ticks ("the next pilot tick, then after 2, 4, … ticks, at most `STOP_BACKOFF_MAX_S / PILOT_EVERY_S` (120) ticks, 1 h"). Keep the constants row (`STOP_BACKOFF_MAX_S` 3600).

### [should-fix] Within one review, a fork whose stop hangs starves its sibling fork
- File: `scripts/qs/control_plane/reviewpilot.py:~620-626` (`stop_closed`, the loop over `matches[r["id"]]`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: fewest-attempts-first orders reviews, but inside a review the matches always run in listing order. Take a review with two listed agents (its session plus an L5 same-named fork) where `claude stop` on the first always times out (124 after 20 s). The budget then breaks before the second agent on every due tick for 7 days, so the second session is never stopped, even though its stop would succeed.
- Proposed fix: rotate a review's matches by its attempt count before stopping: `found = matches[rid]; k = attempts.get(rid, 0) % len(found); found = found[k:] + found[:k]`. This needs no new state. Test: two same-named agents, the first one's stop "hangs" (advances the clock by `HOOK_SUBPROCESS_S` and exits 124). Over two eligible ticks, both targets get a stop.

### [nice-to-have] "claude stop exited 0 but the session is still listed" can be logged for an agent that never got a stop
- File: `scripts/qs/control_plane/reviewpilot.py:575-581, ~616-617` (`_log_still_listed` and its call)
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter, qs-review-acceptance-auditor, qs-review-blind-hunter (the `any(...)` clause silences a flapping stop)
- Description: the condition is "matched, `attempts >= 1`, no non-zero exit logged". It does not check that the still-listed agent is one that got an exit-0 stop. Two false positives: a fork the budget cut off never got a stop, and a fork created later by hand-resume. Also, once any non-zero exit was logged for the review, a later genuine exit-0-still-listed is never logged.
- Proposed fix: record the targets whose stop exited 0, `_State.stopped_ok: dict[str, set[str]]` (pruned to the window). Log once per review (key `(rid, 0)` in `stop_logged`) only when a listed match's target (`id or session_id`) is in `stopped_ok[rid]`. Drop the `any(... c != 0 ...)` clause. Tests:
  - A budget-cut fork (the second fork never stopped) is listed next tick: no line.
  - A target that exited 0 and is still listed: one line.
  - A review that first logged exit 124 and later has an exit-0 target still listed: the exit-0 line is logged too.
