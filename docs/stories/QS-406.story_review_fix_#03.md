## Findings to fix

### [should-fix] H1 — Restore: a staging failure gets the wrong error, and a hint that can lose data (G1 follow-up)
- File: `restore.py:265-305` (`_restore_into`, the `_staged_copy` call at about :271, the outer `except sqlite3.DatabaseError` at about :297)
- Severity: should-fix
- Source: qs-review-blind-hunter, qs-review-edge-case-hunter, qs-review-acceptance-auditor (N2)
- Description: `_staged_copy` sits inside the outer `except sqlite3.DatabaseError`.
  - A staging failure, such as `OperationalError("database or disk is full")`
    during `source.backup(stage)`, is reported as `CONFLICT` "the live DB
    cannot be kept or restored — move it aside". The live DB was never
    touched. If the maintainer follows that hint, the retry runs with no
    live DB, so the waiters and the selfcheck meta are not carried.
  - An `OSError` from `os.open(O_EXCL)` / ENOSPC, or a `CpError` from
    `ensure_private_dir`, escapes without the `replaced` pointer.
  - This is the likeliest failure, because a restore now needs about twice
    the DB size free.
- Proposed fix:
  1. Wrap the `_staged_copy` call in its own
     `try/except (sqlite3.Error, OSError, errors.CpError)`. Raise the same
     "nothing was restored; the live DB was not touched" refusal the
     fix-up branch uses, with `**kept()`. Make sure the hint never says
     "move it aside".
  2. Also catch `OSError` next to `sqlite3.DatabaseError` around
     `backups.write_copy` (the `replaced` copy).

  Tests:
  - `_staged_copy` raises `OperationalError("disk full")` → the live DB is
    logically identical, the hint doesn't say "move it aside", and the
    error carries `replaced`;
  - `os.open` raises `OSError` → the same.

### [should-fix] H2 — Backups: a failed directory fsync after a successful rename counts as a failed copy (G6 regression)
- File: `backups.py:59` (`write_copy`)
- Severity: should-fix
- Source: qs-review-edge-case-hunter, qs-review-acceptance-auditor (N1)
- Description: `_fsync(dest.parent)` runs inside the
  `try … except BaseException` cleanup, so it re-raises after `os.replace`
  has already succeeded. On filesystems where a directory fsync returns
  EINVAL/ENOTSUP (FUSE, 9p, SMB…), this fails every time:
  - `backup_failed` is raised on every attempt;
  - rotation never runs, so copies pile up;
  - migrations can never back up, so they can never run;
  - restore can never keep its `replaced` copy.
- Proposed fix:
  - Move the directory fsync out of the cleanup block. The copy is complete
    once `os.replace` returns.
  - Make it best-effort: catch `OSError`, log it once, and still return
    `dest`.

  Test: monkeypatch `os.fsync` to raise `OSError(EINVAL)` only for the
  directory fd → `write_copy` returns `dest`, and `backup_hook` runs
  `rotate` without `backup_failed`.

### [nice-to-have] H3 — Overlap: the walk state is not reset when an unexpected exception escapes `_walk`
- File: `detectors.py:313-322` (`detect_overlap`)
- Source: qs-review-edge-case-hunter
- Proposed fix: handle `except OutOfBudget` (resume) as now, and add
  `except BaseException: _end_walk(); raise`. This keeps a stale
  `failed_diffs` / `failed_conflicts` / `refs` from leaking into the next
  walk.
  - Test: a non-BUSY `CpError` from the beat in the middle of a walk → the
    next walk retries the previously failed keys.
