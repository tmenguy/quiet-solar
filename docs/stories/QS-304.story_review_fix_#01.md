### [must-fix] 3 — rung 6 survives supersede-with-no-successor; throttle burnt on intent
- File: `custom_components/quiet_solar/home_model/load.py:741-773`
  (also `:782`, `:791`)
- Severity: must-fix
- Source: qs-review-edge-case-hunter (must-fix 1 + should-fix 3)
- Description: `launch_command` commits `_last_supersede_time = time`
  and calls `abandon_running_command` (which deliberately preserves
  `running_command_num_relaunch`) **before** the two remaining gates:
  `is_command_suppressed_by_override` (`:782`) and
  `current_command == command` (`:791`). Either returns with the slot
  empty and the rung still at 6. The "empty slot implies rung 0" repair
  lives only in `_escalate_or_recover` (`:943`), i.e. one cycle later —
  but `update_loads` calls `launch_command` twice per cycle for the same
  load (`ha_model/home.py:3008` upload loop, then `:3027` idle-forcing
  loop) and buttons call it too (`ha_model/load.py:1962`, `:1981`).
  Reproduced against `tests/factories.NeverAcksLoad`:

  ```text
  after no-op supersede:      rung=6 running=None unresponsive_since set? True
  brand new command in flight: rung=6 is_uncontrollable=True delay=300.0s (expected 50)
  ```

  So a brand-new command is declared uncontrollable with zero relaunches
  of its own and gets a 300 s first retry instead of 50 s. This is
  exactly the defect class "Implementation findings (v8)" item 1 claims
  to have closed — the fix does not cover the paths the diff itself
  added.

  Second half of the same defect: because `_last_supersede_time` is
  written before those gates, a supersede that issues **zero** service
  calls still burns the 300 s window, contradicting the contract stated
  at `load.py:62-66` ("a disobedient device never sees more than one
  service call per 300 s"). Reproduced:
  `=> running=None stacked=None last_supersede BURNT` with no
  `execute_command` call made.
- Proposed fix: move both the `_last_supersede_time = time` assignment
  and the `abandon_running_command` call **down** next to
  `self.running_command = command`, so they commit only when a successor
  is actually launched. Per the edge-case-hunter, this single move fixes
  both halves. Pin with two tests that fail if reverted: one for the
  override-suppression path, one for the `current_command == command`
  path, each asserting rung 0, `is_uncontrollable is False`, a 50 s
  first retry, and an unburnt throttle window.

### [must-fix] 4 — ownerless lost-control clock after a full command wipe
- File: `custom_components/quiet_solar/home_model/load.py:349-364`
  (clock non-reset justified at `:181-184`; re-arm gate at `:945`)
- Severity: must-fix
- Source: qs-review-edge-case-hunter (must-fix 2), corroborated by
  qs-review-acceptance-auditor (AC3 test near-vacuous)
- Description: `constraint_reset_and_reset_commands_if_needed(keep_commands=False)`
  nulls **both** `current_command` and `running_command` but keeps
  `unresponsive_since` / `_last_supersede_time`. The only re-arm path
  (`_escalate_or_recover`, `:945`) is gated on
  `current_command is not None`, so after a full wipe the clock is
  permanently ownerless and the first command launched afterwards flips
  `is_uncontrollable` True on its very first cycle. The docstring at
  `:181-184` justifies the non-reset with "an unmet command survives a
  constraint reset" — true for `keep_commands=True`, false for
  `keep_commands=False`, which destroys the very command the clock
  describes. Story §6's reasoning covers only the disable direction, not
  re-enable or the reset button. Triggers: the load's reset button
  (`AbstractLoad.user_clean_and_reset` → `reset()` →
  `launch_command(CMD_IDLE)`, `load.py:1968-1981`) and toggling
  `qs_enable_device` off then on. Reproduced:

  ```text
  lost control:              uncontrollable=True rung=6 current=CMD_IDLE
  after user reset:          unresponsive_since=<kept> current=None running=None
  first command after reset: uncontrollable=True rung=0 (zero relaunches!)
  differing command:         running=CMD_ON(1000) stacked=None  # superseded, not stacked
  ```

  Critically this fires for a **healthy** load too:
  `QSBiStateDuration.execute_command` returns falsy on a normal service
  call (`ha_model/bistate_duration.py:584`), so the command sits in
  flight for one ~7 s cycle — long enough for `qs_load_uncontrollable`
  to flash PROBLEM immediately after the user's own remediation action.
  Distinct from #308: the trigger is the reset path and it happens even
  when `current_command` was a real acked command right before the reset.
- Proposed fix: clear `unresponsive_since` and `_last_supersede_time` in
  `constraint_reset_and_reset_commands_if_needed` when
  `keep_commands is False` (the wipe destroys the clock's subject, so the
  clock must go with it) — routed through `_clear_unresponsive` to keep
  the "single writer / one line out" guarantee. Then correct the
  `:181-184` docstring to say the clock survives `keep_commands=True`
  only. Also fix the AC3 test: `tests/test_bug_304_command_deadlock.py:118`
  currently calls `keep_commands=True`, the branch that touches **no**
  command state (`load.py:353` guards everything behind
  `keep_commands is False`), so it is near-vacuous. Re-assert with
  `keep_commands=False`, and add the healthy-load reset-button
  regression: after `user_clean_and_reset`, `is_uncontrollable` must be
  False on the next cycle.

### [should-fix] 7 — throttled `_stacked_command` is starved forever
- File: `custom_components/quiet_solar/home_model/load.py:~760`
  (`launch_command` throttled-supersede branch), `:903-911`
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: a throttled command becomes `_stacked_command`, but
  `check_commands` promotes the stack only when `running_command is None`
  — and for an uncontrollable load the slot never empties. So once the
  solver goes quiet, the newest desired command is never sent while the
  **stale** one is retried every 300 s forever.
- Proposed fix: make `_relaunch_stale_command` prefer `_stacked_command`
  over the stale `running_command` once the supersede window has opened
  (i.e. relaunch the newest intent, not the one we know is being
  ignored). Pin with a test: supersede, stack a newer command inside the
  window, stop the solver, advance past the window, assert the newer
  command is what gets executed.

### [should-fix] 8 — equal-command absorb discards a throttle-parked stacked command
- File: `custom_components/quiet_solar/home_model/load.py:744-748`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: the equal-command absorb branch unconditionally clears
  `_stacked_command`, discarding a newer command the new 300 s throttle
  had just parked there, in favour of the stale command QS already knows
  the device is ignoring. The branch is pre-existing, but nothing used


  in-flight one. Overlaps with finding 7 — fix both together and pin with
  one jitter scenario.
