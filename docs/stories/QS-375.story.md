# QS-375 — The loop engine on the Control Plane: finding ledger, convergence rules, flip-flop detection with `settled` decisions, focused-reviewer contract, red CI as a ledger finding

**Issue**: [#375](https://github.com/tmenguy/quiet-solar/issues/375) ·
**Lane of this task**: feature-factory (`target:factory`) ·
**Parent epic**: #369 (child 3, wave 4 — in parallel with children 14 and 6c)

Status: planned (story v10 — converged after 8 review rounds; the maintainer's decisions of 2026-10-09 included)

## Problem

Review has no memory between rounds. A rejected finding comes back in the
next round. Nothing says when a loop has converged, and nothing notices a
flip-flop: a finding that undoes the fix of an earlier one. A story takes
about 4.3 review rounds on average, and up to 10.

The second pipeline's nodes (child 6b) run two loops, plan and build. Both
need a shared, durable record of the findings. The Control Plane (#399,
#400) has none of that yet. What it has:

- `reports` (phase, round, status, free JSON fields);
- `tasks.ci_state` / `ci_sha`;
- `integrations`.

Nothing is reserved in schema v1, and `export.LEDGER_SECTIONS` is an empty
seam.

## Goal

A **finding ledger** on the Control Plane, used by the new nodes in both
loops. It **recognises, records and flags by code**, and refuses nothing
to force convergence (maintainer, 2026-10-06). Its only refusals are:

- malformed input;
- a token used out of its scope;
- the CI rule the issue asks for.

What it holds:

- **Rows:** one per finding, with its fingerprint, `source`, task, round,
  the node's classification and its state.
- **Matches:** a finding raised again is matched to the earlier one and
  flagged with that one's state and reason.
- **Flip-flop candidates:** a finding on the same code as an earlier fix
  is flagged.
- **Convergence:** declared by the node, with the evidence (`blocking`,
  `consistent`) computed from the ledger (D14, the maintainer's refinement
  of the issue's "computed from the ledger").
- **What child 17's analysis needs** (§7).
- **`blast_radius`** per task, with the head sha it reviewed.
- **The focused-reviewer contract**, written down.

Out of scope, as the issue says:

- the nodes and loops (6b);
- the frozen `review-task` / `create-plan`;
- the global review and the review sessions' principal (15);
- the merge's read of `blast_radius` (7);
- the CI watcher and the rounds detector (14).

## Decisions

Answers to the issue's open points, and this plan's choices. The
maintainer confirmed D7, D8 (family), D11, D12 and D14 on 2026-10-09,
refining D9, D11 and D14 on the way (marked **(confirmed)**).

- **D1 — Four new tables, apart from `reports`:** `rounds`, `findings`,
  `finding_events` and `blast_radius`, through one new migration.
  - **Why not inside `reports`:** a round starts **before** its report
    exists, because its base and head go to the reviewers first. A node
    may also post several reports in one round, at each blocker.
  - **The link:** a `rounds` row and its `reports` rows share the natural
    key `(task_id, phase, round)`, with no foreign key. The node takes the
    round number from `round start` and posts its report with it.
  - **Child 14** keeps reading `reports.round`.
- **D2 — No `CHECK` of schema v1 is widened.** `reports.status` is
  enough, and no table is rebuilt.
- **D3 — A round is one `round start` call:** one review pass of one
  phase of one task. The CP numbers rounds `1, 2, …` per `(task, phase)`.
  - **Back to the plan loop:** a plan-level fix sends the node back there,
    and the plan counter continues ("the round counters go on").
  - **Catch-up with `main`:** its conflict-resolution delta is not a
    round, so the node calls no `round start` for it.
  - **Restarts:** every call is a new round. A restarted node reads
    `latest_round` and its head through `ledger show` before starting
    another.
- **D4 — "The diff" of a round is `base..head`.**
  - **`--head`** is required for `build` rounds (`USAGE` without it), and
    optional for `plan`.
  - **Round 1:** the node gives the base; a NULL base is allowed.
    - deliverable `QS_<N>`: `git merge-base origin/main QS_<N>`;
    - work item `QS_<N>_<k>`: `git merge-base QS_<N> QS_<N>_<k>`, its fork
      point on the local `QS_<N>`.
  - **Later rounds:** the base defaults to the previous round's head ("the
    last reviewed commit"). `--base` overrides it.
  - **After a catch-up with `main`:** the node passes `--base <the catch-up
    merge commit>`, so `main`'s changes stay out of the reviewers' delta.
- **D5 — A reviewer sub-agent writes with the node's token, passed in its
  prompt.**
  - **Why:** the CLI never reads a token from the environment (#399).
    Sub-agents run inside the node's session (same hooks, same fencing),
    so a superseded node's reviewers get `STALE_TOKEN` too.
  - **What it receives:** `--token`, `--task`, `--phase` and `--round`.
  - **How it writes:** through stdin (`--input -`, a heredoc), since it has
    no Write tool.
  - **Accepted risk:** the token would also let the reviewer call `finding
    state` or `finding classify` on its own task. Mitigations:
    - the contract forbids it;
    - 6b's reviewer templates allow `Bash` only for `cp.py finding open`;
    - every write records its actor.

    A reviewer-scoped token is left to 6b / 15.
- **D6 — States, and free transitions.** The states are `open`,
  `resolved`, `rejected`, `deferred` and `settled`. Any state may move to
  any other; the code never forces a path.
  - **Required arguments, by target:**
    - `resolved` needs `--commit`;
    - `rejected` and `settled` need `--reason`;
    - `open` (a reopen) and `deferred` take an optional `--reason`;
    - `--commit` with any other target is `USAGE`.
  - **`--cause <id>`:** optional on any target, `NOT_FOUND` if unknown. It
    records why, e.g. the red CI finding that reopened a settled decision.
  - **Same state:** a noop (`changed: false`, no event), checked after the
    argument and `--cause` validation. To change a settled rationale, the
    node reopens and settles again, which leaves two honest events.
  - **Every change** writes a `state` event, including a move caused by
    `finding classify` (D7).
  - **The row's columns** hold only the latest state:
    - `reason` becomes the new `--reason` (NULL when none is given);
    - `resolved_sha` is set on `resolved` and cleared on any other target.

    The history lives in the events.
- **D7 — Classification drives open ⇄ deferred (confirmed).** `finding
  classify` sets `classification` in any state and writes a `classify`
  event.
  - **Who:** any writer of the task: its node (own token) or the
    orchestrator (run token); the maintainer acts through the
    orchestrator. Reviewers do not, by contract (§5). The same writers
    may also use `finding state --to deferred` / `--to open` directly.
    Every change records its actor.
  - **Where deferred rows live:** in `findings` itself, with state
    `deferred` and their class; their history is in `finding_events`.
    They show in `ledger show --state deferred`, `task show`, `snapshot`
    and the exported summary that lands with the PR. The run's final
    review (child 13) reads every deferred row across the run's tasks.
  - **Open row, `nice_to_have` or `out_of_scope`:** the row moves to
    `deferred`.
  - **Deferred row, `must_fix` or `should_fix`:** the row moves back to
    `open`, so a promoted finding blocks convergence again.
  - **Other states:** the class is recorded and the state is unchanged.
  - **Same class:** a noop (`changed: false`, no event).
  - **A classify-driven move** writes the `classify` event (its reason is
    `--note`), then a `state` event with the reason `classified <class>`.
    The row's `reason` becomes `classified <class>` too. So a promotion
    from deferred to open is counted as a reopening (§7).
  - **At birth**, `classification` is NULL, except for `ci` / `gate` rows
    (`must_fix`). This rule runs only on `finding classify`, never at
    birth.
  - `out_of_scope` is the epic's fourth finding class ("out of scope:
    deferred to the final review"). How the final review shows deferred
    rows is 6b's / 13's to decide.
- **D8 — Fingerprint and matching: code recognises, the node judges.**
  - **`norm(text)`:** lower-case; every run of non-alphanumerics becomes
    one space; trimmed.
  - **`file`** is stored normalised: a leading `./` is stripped. An
    absolute path or a `..` segment is `USAGE`. **`symbol`** is stored
    trimmed.
  - **`category`:** one of `CATEGORIES`: `correctness`, `edge-case`,
    `test`, `security`, `performance`, `design`, `scope`, `docs`, `style`,
    `ci`, `gate`, `other` (the fallback). It is checked in Python, not by
    an SQL `CHECK`, so 6b can extend the list without a migration.
  - **Fingerprint:** `sha256` over `file␟symbol␟category`. `␟` is U+001F
    and NULL is encoded as an empty string. When both `file` and `symbol`
    are empty, `␟norm(title)` is appended. The task and the line numbers
    are left out.
  - **Family (confirmed):** matching looks across a task's family:
    - `root = tasks.deliverable_id` if set, else the task itself;
    - the family is `{root} ∪ (SELECT id FROM tasks WHERE deliverable_id =
      root)`.

    So a finding rejected on a work item is recognised when the global
    review raises it on the deliverable. Such a cross-task match is
    flagged, never closed (D9): the deliverable's wider context deserves a
    re-assessment. Matching crosses phases. Inside
    a batch, item 2 can match item 1: rows are written in order.
  - **Flags** are computed at open and stored on the row, as a JSON list
    of `{"kind", "id", "state", "reason", "commit", "source", "strong",
    "cross_task", "escalated"}`:
    - `cross_task` is true when the flagged row is on another task, for
      every kind;
    - `strong` and `escalated` are computed for `matches` only, and are
      false for the other kinds;
    - `escalated` is true on a strong `matches` flag when the item is
      `must_fix` and the flagged row's effective class is not, whether the
      row is born open or closed;
    - each flag's own `reason` field carries the flagged row's rationale.
      This is distinct from the new row's `reason` column (D9).

    Flags record what was true at open; `ledger show` also returns each
    flagged row's current state.
  - **"Latest" means the most recent state decision:** among candidate
    rows, the one with the highest `decided_seq`. This is a monotonic
    number drawn from the `counters` table (kind `finding_decision`; the
    table has no `CHECK` on `kind`), inside the write transaction,
    through a new `db.next_seq(conn, kind) -> int`. It holds today's body
    of `db.next_id`, which then returns `f"{prefix}{next_seq(conn,
    kind)}"`, with a `test_db.py` case. A row gets one at birth and a new one at every state
    change: `finding state`, or a classify that moves the state (D7). A
    classify that leaves the state alone, a noop and a replay do not
    touch it. There are no timestamps, so no ties and no clock
    dependence. So a node that reopens and resolves the original row
    overrides an older born-closed copy of it, even if that copy was
    classified since.
    - `kind: "matches"`: earlier family rows with the same fingerprint.
      `strong: true` when `norm(title)` is equal too.
    - `kind: "overlaps_fix"`: earlier family rows, `resolved` or
      `settled`, with the same `file` and the same non-empty `symbol` but
      another fingerprint. These are the code-detected flip-flop
      candidates.
    - `kind: "relates_to"` (a plan choice, not asked by the issue: a cheap
      flag): the earlier rows the item names in its optional `relates_to:
      [ids]` (`NOT_FOUND` if one is unknown). This is
      how a reviewer holding the ledger excerpt, or the orchestrator
      opening a CI finding, points at the settled or resolved row that a
      finding touches. Plan-loop findings, docs findings and CI failures
      in test files have no shared symbol for `overlaps_fix` to see.
  - **`matched_id`:** the first hit, in this order: the latest same-task
    strong match, the latest strong match of the family, the latest weak
    match. NULL when there is none. For a born-closed row, it is the row
    whose state and reason it took.
  - **The node judges** whether a match is the same finding and whether an
    overlap or a relation is a flip-flop. Then it settles the finding,
    with a rationale, or does the work.
- **D9 — The born state of a new row.** A row is **born closed**, in the
  state of its latest **same-task** strong match (same task, same
  fingerprint, same title), when both hold:
  - its source is reviewer-type: `reviewer`, `coderabbit`,
    `global_review` or `cross_run_review`;
  - that same-task strong match is `rejected` or `settled`.

  The task's own decision wins, whatever a sibling raised since. A
  born-closed row stays closed whatever its severity, because the issue
  says it "stays closed unless the node reopens it".

  **Cross-task (maintainer, 2026-10-09):** when the task has **no**
  same-task strong match but the family has one (e.g. rejected on a work
  item and raised for the first time on the deliverable), the row is born
  `open`, flagged `strong` and `cross_task` with the earlier rationale,
  so the node re-assesses it in the wider context. Once the node decides
  it, that decision is the task's own, and later re-raises follow it.
  - **Reason:** `matches #<id>: <reason of #id>`, with one exception: when
    `#id`'s reason already starts with `matches #`, it is reused verbatim.
    It then names the root and never nests. The test is on the text only,
    so it is deterministic. A row that was reopened and re-settled with a
    fresh rationale is prefixed normally.
  - **Born `open`:** every other case, with its `reason` column NULL (the
    earlier rationale stays in the flag). That covers a
    weak match (same fingerprint, another title, so possibly a different
    finding), a cross-task strong match with no same-task one, a same-task
    strong match that is `open`, `deferred` or `resolved`, and an
    `overlaps_fix` or `relates_to` flag alone. Each is flagged.
  - **Always born `open`:** sources `ci`, `gate`, `orchestrator`,
    `maintainer` and `detector`. They speak with authority (the
    maintainer, a correction) or mechanically (a red check, a detector),
    and a red CI check reopens a settled decision, never the reverse.
    Their matches are flagged like any other.
- **D10 — Exact replay, through a unique `replay_key`.**
  - **The key:** a `sha256` with the D8 encoding (`␟`, NULL as an empty
    string) over task, phase, round, source, `reviewer`, the fingerprint,
    `norm(title)`, `line_start`, `line_end`, `ci_sha` and
    `integration_id`. For `ci` and `gate` the round is left out:
    `ci_sha` and `integration_id` already identify them, so a retry after
    a new round started stays a replay.
  - **The insert:** `INSERT … ON CONFLICT(replay_key) DO NOTHING`, then
    `SELECT id … WHERE replay_key = ?`. Never `INSERT OR IGNORE`, which
    would also swallow `CHECK` and `NOT NULL` errors.
  - **Order:** the replay lookup runs **before** the `ci` / `gate` checks,
    so a CI retry after `ci_state` turned green gets its existing id back.
  - **What a replay keeps:** its non-key fields (`severity`, `body`) are
    ignored, so the first write wins (documented).
  - **What is never merged:** two different findings on the same symbol, a
    second reviewer, or a red CI on a new sha.
- **D11 — Flip-flops: flagged, never refused (confirmed).** This confirms
  the 2026-09-24 proposal. A flip-flop is a fix/break loop: a fix made in
  one round is undone or reworked by a later finding (fix A breaks B, fix
  B breaks A). A finding that would revert or rework an earlier fix, or
  re-raise a resolved or rejected one, is flagged by code (`matches`,
  `overlaps_fix`, `relates_to`).
  - **The node decides once** and marks it `settled`, with its rationale.
  - **A later exact re-raise on the same task** is born `settled` and
    flagged with that rationale (D9).
  - **A later weak match, overlap or relation** is born `open`, with the
    rationale in its flag.
  - **None of these is refused.**
  - **A red CI finding** that relates to or overlaps a settled row carries
    the settled rationale. The node may reopen the settled row (`--cause
    <ci finding>`).
  - **Escalation:** whether fixing CI "would reverse the settled
    trade-off", and so escalates through a question, is the node's
    judgement (6b). The ledger records the reopen and its cause.
  - **Another perspective (maintainer, 2026-10-09):** on a flip-flop the
    node may ask for a decision from another viewpoint instead of
    deciding alone.
    What the ledger sees:
    1. the node asks the orchestrator (`question open` or `msg post`;
       both accept a node token);
    2. the decision lands as `finding state --to settled`, with its
       rationale, written with the run token. `tokens.Principal.actor`
       maps a run token to `orchestrator` (and a node token to
       `node:<task>`), so the event's actor shows who decided.

    How the orchestrator reaches its decision (alone, or through a global
    review) is 6a's and 15's. The ledger launches nothing. The epic prose
    records the maintainer's intent.
- **D12 — `unchanged_lines` is recorded as given (confirmed — changed
  from v1).** The issue asks to record it, not to compute it.
  - **The field:** each item may carry `unchanged_lines` (bool), set by
    the reviewer or the node, who both hold the round's diff.
  - **Storage:** `1` / `0` / NULL when absent.
  - **Nothing is refused** on it.
  - **No git in the CP:** that keeps one plain write transaction. A
    CP-side check is a follow-up, if child 17 finds the reported values
    unreliable.
- **D13 — Who writes: `ledger.writer(conn, token, task_id, *,
  kinds=frozenset({"run", "node"}))`.** It is the one point child 15
  extends.
  - **The token check:** it calls `tokens.require(kinds=kinds,
    task_id=task_id)`. A node token writes on its own task, a run token on
    any task of its run. A run token on another run's task, or a node
    token on another task, is `CONFLICT`. `kinds={"run"}` with a node
    token is `CONFLICT`.
  - **ID-taking commands** (`finding classify`, `finding state`) check the
    token first (`tokens.require(kinds=…)`), then look the finding up
    (`NOT_FOUND`), then check the task scope (`writer(…, row.task_id)`).
    So a stale token always gets `STALE_TOKEN`, as in
    `messages.ack`.
  - **The `source`** is recorded as given, with the writer's `actor`; the
    two are not paired.
  - **`run_id`:** the task's (`tasks.run_id`, nullable) or, for a task with
    no run, the principal's. In practice a task with no run is written
    with a run token: `tokens.require` accepts a task whose `run_id` is
    NULL, and `tool spawn` binds a node to a task of its run.
  - **`ci` findings:**
    - they need `sha` equal to `tasks.ci_sha` while `tasks.ci_state =
      'red'` (`INVALID_STATE` otherwise);
    - the vocabulary `pending | green | red` is child 14's contract (epic,
      "Assistant choices" 9), not checked by schema v1;
    - they are stored with `ci_sha`, and with `severity` and
      `classification` both `must_fix`.
  - **`gate` findings** need `integration_id`, an `integrations` row whose
    `item_task_id` or `deliverable_id` is the task (`NOT_FOUND` /
    `CONFLICT`). They are stored `must_fix` / `must_fix`, with the tail of
    `integrate-finish` in `body`.
  - **Corrections:** the orchestrator opens the CI, gate and detector
    findings it acts on, then sends `msg post --kind fix` with
    `finding_id` in the payload. That is a documented convention;
    `messages.py` is not changed.
  - **`blast-radius set`** uses `kinds={"run"}`. A node must not rate its
    own blast radius, which feeds the merge's second human gate.
- **D14 — Convergence: the node declares it; the ledger shows the
  evidence (confirmed, maintainer 2026-10-09).** `ledger.convergence(conn,
  task_id, phase)`:
  - **Converged** means the node has declared it: `latest_round >= 1`, and
    the **latest** `reports` row (highest id) of `(task, phase,
    latest_round)` has `status = 'converged'`. A round still in review
    never reads as converged, and a later non-converged report in the same
    round withdraws the declaration. A report posted with the run token
    counts too: the orchestrator is the authority above the node.
    - `reports.phase` is free text in schema v1, so a report counts only
      when its `phase` is exactly `plan` or `build`;
    - `reports.status`'s `CHECK` already includes `converged`.
  - **`blocking`:** the rows of that task and phase that are `open` with
    an effective class (`classification`, else `severity`) of `must_fix`
    or `should_fix`. Round-0 rows count. An unclassified should-fix
    counts until the node classifies it. An open nice-to-have, or an open
    `out_of_scope` row (reopened by hand), never counts.
  - **`consistent`:** `blocking == []`. A node that declares convergence
    with blocking rows still open is **converged** and **not
    consistent**. Nothing overrides the node: a flip-flop it chose to
    leave open (for example while waiting for another perspective, D11)
    never stalls the loop by code.
  - **The answer:** `{converged, consistent, blocking: [ids],
    latest_round, counts: {state: n}}`, with `latest_round = 0` without a
    round.
  - **Who reads the discrepancy:** the orchestrator, child 7's merge
    conditions (which may require `consistent`) and child 17's analysis.
  - **The node's flow:** after triage it reads `blocking`, settles or
    defers what it decides to (D11), then posts its report with
    `converged`.
  - **Rounds:** no hard stop. `ROUNDS_ALERT` stays child 14's, at 5; this
    rule needs no other value.
- **D15 — `blast_radius`, append-only.** Each row holds:
  - `task_id`;
  - `value` (`ok | doubt | too_large`);
  - `head_sha`;
  - `review`: the id of the review it came from, free text that 15 fills;
  - `reason` (optional): the explanation a human reads at gate (b);
  - `actor`;
  - `at`.

  The reader is `ledger.blast_radius(conn, task_id, head_sha=None)`: the
  latest row, or the latest for that sha, else `None`.
- **D16 — One JSON write for findings; only ids come back.**
  - **The call:** `finding open --task T --phase P --source S [--round R]
    --input F|-` reads one JSON object or a list (schema in §2) and opens
    it in one transaction.
  - **The answer:** `{"ok": true, "ids": [...]}`, one id per item in
    order; a replayed item repeats its id.
  - **`--round`** defaults to the latest round of that phase, or `0`
    before any round (e.g. a CI finding before the first review). Round `0`
    is a default only: a given `--round` must be `>= 1` and exist
    (`NOT_FOUND`).
  - **Phase:** `ci`, `gate` and `detector` findings are opened in `build`
    by convention; a plan-level correction is opened in `plan`.
  - **Cross-run:** a cross-run review opens one batch per task touched.
    Writing across runs waits on child 15's `writer` extension: a run token
    is `CONFLICT` on another run's task today.

## Design

### 1. Schema: `Migration(2, "the finding ledger (#375)", schema_ledger.STATEMENTS)`

**`scripts/qs/control_plane/schema_ledger.py`** holds `STATEMENTS`,
`TABLES` and the vocabularies (`PHASES`, `SOURCES`, `SEVERITIES`,
`CLASSES`, `STATES`, `CATEGORIES`, `BLAST_VALUES`).

- It imports nothing from the package, like `schema_v1.py`.
- It is named by what it holds, so a renumbering at catch-up leaves no
  wrong name.
- It cannot live in `ledger.py`, which imports `db`, because `db →
  migrations → ledger → db` would be a cycle.

**The import rules:**

- `ledger` imports only `clock`, `db`, `errors`, `export`, `tasks`,
  `tokens` and `schema_ledger`. It never imports `messages`, `reports`,
  `nodes`, `questions`, `hooks`, `wait` or `snapshot`.
- `snapshot` imports `ledger` (for `convergence`), and `cli` imports
  `ledger`.
- No cycle results: `tasks` and `export` do not import `ledger`.

```sql
CREATE TABLE rounds (
    task_id TEXT NOT NULL REFERENCES tasks(id),
    phase TEXT NOT NULL CHECK (phase IN ('plan', 'build')),
    round INTEGER NOT NULL CHECK (round >= 1),
    base_sha TEXT, head_sha TEXT,
    actor TEXT NOT NULL, started_at TEXT NOT NULL,
    PRIMARY KEY (task_id, phase, round)
)
CREATE TABLE findings (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id TEXT REFERENCES runs(id),
    task_id TEXT NOT NULL REFERENCES tasks(id),
    phase TEXT NOT NULL CHECK (phase IN ('plan', 'build')),
    round INTEGER NOT NULL CHECK (round >= 0),
    source TEXT NOT NULL CHECK (source IN ('reviewer', 'coderabbit', 'global_review', 'cross_run_review',
                                           'ci', 'gate', 'detector', 'orchestrator', 'maintainer')),
    reviewer TEXT,
    severity TEXT NOT NULL CHECK (severity IN ('must_fix', 'should_fix', 'nice_to_have')),
    classification TEXT CHECK (classification IN ('must_fix', 'should_fix', 'nice_to_have', 'out_of_scope')),
    category TEXT NOT NULL,                   -- CATEGORIES, checked in Python
    title TEXT NOT NULL,
    body TEXT NOT NULL,                       -- not `detail`: snapshot._rows JSON-parses `detail`
    file TEXT, symbol TEXT, line_start INTEGER, line_end INTEGER,
    fingerprint TEXT NOT NULL,
    title_norm TEXT NOT NULL,
    replay_key TEXT NOT NULL UNIQUE,
    matched_id INTEGER REFERENCES findings(id),
    flags TEXT NOT NULL DEFAULT '[]',
    unchanged_lines INTEGER CHECK (unchanged_lines IN (0, 1)),
    state TEXT NOT NULL CHECK (state IN ('open', 'resolved', 'rejected', 'deferred', 'settled')),
    decided_seq INTEGER NOT NULL,             -- D8's "latest": birth and every state change
    reason TEXT, resolved_sha TEXT, ci_sha TEXT,
    integration_id INTEGER REFERENCES integrations(id),
    actor TEXT NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL
)
CREATE INDEX findings_fingerprint ON findings (fingerprint)
CREATE INDEX findings_task ON findings (task_id, phase, state)
CREATE TABLE finding_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    finding_id INTEGER NOT NULL REFERENCES findings(id),
    at TEXT NOT NULL, actor TEXT NOT NULL,
    round INTEGER NOT NULL,                   -- the phase's latest round at the time
    kind TEXT NOT NULL CHECK (kind IN ('classify', 'state')),
    from_value TEXT, to_value TEXT,           -- states, or classes
    reason TEXT, commit_sha TEXT,
    cause_id INTEGER REFERENCES findings(id)
)
CREATE TABLE blast_radius (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL REFERENCES tasks(id),
    value TEXT NOT NULL CHECK (value IN ('ok', 'doubt', 'too_large')),
    head_sha TEXT NOT NULL, review TEXT NOT NULL, reason TEXT,
    actor TEXT NOT NULL, at TEXT NOT NULL
)
```

**Notes on the statements:**

- Each is a single statement, run with `execute`.
- A finding's opening is its row (`created_at`, `round`), so there is no
  `open` event.
- **Why `finding_events` exists:** the issue requires the reopenings,
  which are `state` events to `open`.
- **Why `classify` events too:** the plan keeps them so the triage itself
  (who classified what, when) can be audited. They are cheap, and the
  issue does not require them.

### 2. `ledger.py`: the Python API (for 6b, 7, 15 and 17)

```python
@dataclass(frozen=True)
class Writer: principal: tokens.Principal; actor: str; run_id: str | None
def writer(conn, token, task_id, *, kinds=frozenset({"run", "node"})) -> Writer   # inside db.write; 15 extends it
def norm(text) -> str
def norm_path(file) -> str | None                               # USAGE on an absolute path or `..`
def fingerprint(*, file, symbol, category, title) -> str
def family(conn, task_id) -> list[str]
def start_round(conn, clock, *, token, task_id, phase, head, base) -> dict        # {round, base_sha, head_sha}
def open_findings(conn, clock, *, token, task_id, phase, source, round_, items) -> dict  # {"ids": [...]}
def classify(conn, clock, *, token, finding_id, cls, note) -> dict                # {finding_id, state, classification, changed}
def set_state(conn, clock, *, token, finding_id, to, reason, commit, cause) -> dict # {finding_id, state, changed}
def set_blast_radius(conn, clock, *, token, task_id, value, head_sha, review, reason) -> dict

def blast_radius(conn, task_id, head_sha=None) -> dict | None   # child 7's reader
def show(conn, task_id, *, phase=None, states=None, include_family=False) -> dict     # rounds, findings (+ current state of flagged rows),
                                                                #   events, blast_radius, convergence {plan, build}
def register_export() -> None                                   # appends each of the 3 sections if its title is absent
```

- **Transactions:** every write function runs in one `db.write`
  (`BEGIN IMMEDIATE` plus the version re-check), through `cli._write`,
  like `reports.post_report`.
- **`open_findings`'s order:**
  1. validate every item (`USAGE`, before the transaction);
  2. check the writer;
  3. resolve `--round`;
  4. for each item in order:
     - compute the fingerprint and the replay key;
     - look the key up (a replay reuses the id);
     - apply the `ci` / `gate` checks;
     - compute the flags and the born state;
     - `INSERT … ON CONFLICT(replay_key) DO NOTHING`, then `SELECT id`.

**The item schema** (`finding open --input`). Each of these is `USAGE`:
an unknown key, a wrong type, a value outside its vocabulary, `line_start
> line_end`, `line_end` without `line_start`, a bad path, input that is
not JSON, and an object or list that is empty.

| key | type | required |
|---|---|---|
| `severity` | `must_fix \| should_fix \| nice_to_have` | yes, except `ci` / `gate`: optional there, and overridden to `must_fix` if given |
| `category` | one of `CATEGORIES` | yes |
| `title` | non-empty string | yes |
| `body` | string | yes |
| `file`, `symbol` | string (`file` relative, normalised) | no |
| `line_start`, `line_end` | int ≥ 1 (`line_end` defaults to `line_start`) | no |
| `reviewer` | string (the lens, e.g. `qs-review-blind-hunter`) | no |
| `unchanged_lines` | bool | no |
| `relates_to` | list of finding ids (`NOT_FOUND` if one is unknown) | no |
| `sha` | string | `ci` only, required there; `USAGE` elsewhere |
| `integration_id` | int | `gate` only, required there; `USAGE` elsewhere |

### 5. The focused-reviewer contract (written into `control-plane.md`)

**What a reviewer receives** in its prompt from the node:

- **The diff:** `git diff <base>..<head>` from `round start`'s answer.
  Round 1 is the full integrated diff; later rounds are the delta.
- **The acceptance criteria:** `task show` → `criteria`.
- **The ledger excerpt:** for example `ledger show --task T --phase P
  --family --state open,rejected,settled,deferred` (6b may tune the
  filter), so it does not raise them again. `--family` (`dest=
  "include_family"`) widens only `findings` and their events to the task's
  family (D8); `rounds`, `blast_radius` and `convergence` stay per task.
  So a deliverable's reviewer sees what its work items already closed. A
  re-raise of one of those is born `open`, `cross_task` (D9): it counts in
  `blocking` until the node triages it.
- **The write coordinates:** `--task`, `--phase`, `--round`, and the
  node's `--token`.
- **Its instructions:**
  - apply a relevance-to-this-task test;
  - suggest no refactor outside the scope;
  - in a later round, raise no finding on lines the round did not change
    (a red CI is the exception);
  - set `unchanged_lines` from the diff;
  - put the ids of the excerpt rows a finding touches in `relates_to`.

  These are instructions only: the ledger records and refuses nothing for
  them.

**What it writes:** one heredoc call, `finding open --source reviewer
--input -`, with the items of §2.

**What it returns** to the node: only the ids from `{"ok": true, "ids":
[...]}`. It calls no other ledger command.

**Then the node:**

1. reads the rows and flags with `ledger show`, and the `escalated`,
   `cross_task` and weak-match flags first;
2. triages them (`finding classify`, `finding state`). On a flip-flop it
   may ask the orchestrator for another perspective (D11) instead of
   deciding alone;
3. reads `convergence.blocking`;
4. posts its report with the round number, `converged` when it judges the
   loop done (D14), with its `blocking` ids in the report's fields. The
   orchestrator does the same when it declares with the run token.

**A correction from the orchestrator:** `finding open` (`ci`, `gate`,
`detector`, `orchestrator` or `maintainer`, with `relates_to` when it
touches a settled row), then `msg post --kind fix` with `{"finding_id":
<id>, …}`.

2. **Replay** (`test_ledger.py`):
   - the same item twice gives one row, in two calls (`[n]` then `[n]`)
     and in one batch (`[n, n]`);
   - items differing only in title, lines or `reviewer` give separate
     rows, and the second carries a `matches` flag on the first, in the
     same batch too. The fixtures carry a `file` or `symbol`; otherwise the
     title is part of the fingerprint;
   - two red-CI items on different `ci_sha` give two rows;
   - a CI item replayed after a new round started returns its id, and so
     does one replayed after `ci_state` turned green.
3. **Exact re-raise of a rejected or settled finding:**
   - a reviewer item with the same fingerprint and title as a `rejected`
     (resp. `settled`) row of the same task is born in that state;
   - it carries `matched_id`, a strong `matches` flag and the reason;
   - it stays so until `finding state --to open`, which writes an event;
   - a `must_fix` item matching a `should_fix` row is still born closed,
     with `escalated: true`;
   - a reason inherited twice names the root once;
   - "latest" is the most recent state decision (`decided_seq`). When #5
     is rejected, #8 is born rejected from it, the node then reopens and
     resolves #5, and then classifies #8 without moving its state, the
     next re-raise follows #5 (born `open`), not #8's stale rejection.
     This holds with the frozen `fake_clock`, since no timestamp is
     involved;
   - `decided_seq` grows at birth and on each state change, and not on a
     state-preserving classify, a noop or a replay;
   - rows seeded by hand with `sql` (`world`, `busy_world`) supply a
     `decided_seq` and seed the `finding_decision` counter above it, so a
     later allocation never ties with a seeded value;
   - when a newer weak match also exists, `matched_id` is still the strong
     match.
4. **Weak match and flip-flop**, all exit 0:
   - same fingerprint with another title as a rejected row: born `open`,
     weak `matches`;
   - same file and symbol as a `resolved` row with another category: born
     `open`, `overlaps_fix`;
   - a re-raise of a `resolved` row: born `open`, `matches`;
   - settling it stores the rationale, and the next exact re-raise is
     born `settled`, flagged;
   - an item with `relates_to: [settled id]`: born `open`, the rationale
     in its flag;
   - an unknown `relates_to` id is `NOT_FOUND`.

     by a `global_review` item on its deliverable, is born `open`, with a
