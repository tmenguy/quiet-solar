# QS-436 — Pin requirements to Home Assistant 2026.10.4 (CI out of sync with local dev venv)

- Issue: #436 · Lane: bug × product · Branch: `QS_436`
- Status: diagnosis (story v4)

## Symptom

The shared local dev venv (`venv` → `quiet-solar/venv314`, Python 3.14.3)
runs Home Assistant **2026.10.4**, after a manual upgrade. But
`requirements.txt` still pins `homeassistant==2026.8.1`, and
`requirements_test.txt` still pins the matching
`pytest-homeassistant-custom-component==0.13.355`.

So every CI job that installs the requirements runs an **older** stack
than local dev. These are `pr-quality.yml`'s lint, typecheck and 4 test
shards, `release.yml`'s quality gate, and `auto-bmad.yml`, all via
`pip install -r requirements.txt -r requirements_test.txt`.
`lane-check` and `hacs-validate` install no requirements, so they are
unaffected. Separately, the `pr-quality.yml` aggregation job installs
a twin `coverage==` literal, and that literal has drifted too. This
breaks the stated guarantee: "Pinned to exact versions so CI is
reproducible against the local dev env."

A second, previously hidden symptom: under the local venv (HA 2026.10.4)
the full suite is **not** green. 2 tests fail, and CI cannot see them
because it still runs 2026.8.1:

```text
FAILED tests/test_config_jinja_rendering.py::test_notification_fires_when_cloud_write_raises[turn_on]
FAILED tests/test_config_jinja_rendering.py::test_notification_fires_when_cloud_write_raises[turn_off]
E       Failed: DID NOT RAISE <class 'tests.test_config_jinja_rendering._CloudApiError'>
tests/test_config_jinja_rendering.py:708: Failed
2 failed, 11379 passed, 2 skipped — coverage 100% (17258 stmts)
```

They fail deterministically when re-run on their own.

- **The HA behaviour change behind the 2 failures.** A diff of
  `homeassistant/helpers/script.py` between 2026.8.1 (wheel downloaded to
  scratch) and 2026.10.4 shows that `_ScriptRun._async_step_call_service`
  now wraps the service call (2026.10.4 l.1096–1101):

  ```python
  except (*CONFIGURATION_ERRORS, exceptions.HomeAssistantError):
      raise
  except Exception as ex:
      if not self._action.get(CONF_CONTINUE_ON_ERROR, False):
          raise
      raise exceptions.HomeAssistantError(ex) from ex
  ```

  Walked through on 2026.10.4 (the round-2 skeptic verified it against
  the source):
  - With `continue_on_error` set, the wrapped `HomeAssistantError` is
    swallowed by `_handle_exception` (l.614–641): it is not a
    `_StopScript` and not in `CONFIGURATION_ERRORS`. The script helper
    logs it at ERROR (`log_exceptions=True`).
  - Without the flag, the raw exception propagates.
  - `_async_step_parallel` (l.714–730) is unchanged from 2026.8.1: it
    gathers with `return_exceptions=True`, then re-raises.

  In 2026.8.1 a plain `Exception` always propagated ("Only Home
  Assistant errors can be ignored", then `raise`).
- The cloud step in `config/configuration.jinja` (`switch.turn_on` at
  l.364 and `switch.turn_off` at l.399, each inside the `parallel:`
  block) carries `continue_on_error: true`. On 2026.10.4 the
  `_CloudApiError` is swallowed, the script completes normally, and the
  test's `with pytest.raises(_CloudApiError)`
  (`tests/test_config_jinja_rendering.py:708`) fails with DID NOT RAISE.
- **The behaviour the test guards still holds.** Throwaway probes (an
  uncommitted copy of the test module with extra cases, deleted
  afterwards) pass on 2026.10.4 for both directions (4/4):
  - **(a) As rendered:** the cloud handler is called exactly once, the
    diagnostic `persistent_notification.create` fires once, and
    `429 throttled` appears in the ERROR log. This positively confirms
    the wrap-and-swallow path.
  - **(b) Mutation, `continue_on_error` deleted from the cloud step in
    the deep-copied sequence:** `pytest.raises(_CloudApiError)` holds
    (the exception propagates out of `parallel:`), and the notification
    still fires once. So the `parallel:` isolation still works against
    a propagating exception.
- **Production observability change (not a defect).** QS-305 review fix
  #03 (`docs/stories/QS-305.story_review_fix_#03.md` l.212–223) relied
  on the raw pyatmo `ApiError` escaping `switch.turn_on/off` as the
  trace of a failing cloud channel. On HA ≥ 2026.10 that failure shows
  up instead as one script-helper ERROR log line
  (`… Error executing script … 429 throttled`, no traceback). The
  diagnostic notification is unaffected.

## Root cause

Two parts. Both come from the manual venv upgrade to HA 2026.10.4 /
phcc 0.13.375, which neither the pins nor the tests followed:

1. **Stale pins.** `requirements.txt:1` (`homeassistant==2026.8.1`) and
   `requirements_test.txt` lines 15/18/20 (`coverage==7.15.2`,
   `pytest-homeassistant-custom-component==0.13.355`, `syrupy==5.5.3`)
   are out of date, and so is their CI twin
   `.github/workflows/pr-quality.yml:226` (`pip install coverage==7.15.2`).
   As a result every requirements-installing CI job resolves an older
   environment than local dev.
2. **A test that is wrong for the HA version the bump brings in.**
   `tests/test_config_jinja_rendering.py::test_notification_fires_when_cloud_write_raises`
   asserts `pytest.raises(_CloudApiError)` around `Script.async_run`. That
   encodes HA ≤ 2026.8 semantics. Since 2026.10,
   `homeassistant.helpers.script._ScriptRun._async_step_call_service`
   wraps non-HA exceptions in `HomeAssistantError` on a
   `continue_on_error` step, so the exception is swallowed. Bumping the
   pins alone would turn CI red.

There is no product-code defect. `custom_components/quiet_solar/` passes
at 100% coverage, and mypy is clean on 2026.10.4. The rendered
`config/configuration.jinja` behaviour is correct on both HA versions:
the diagnostic fires either way. Only how a cloud failure surfaces
changes (see the observability note in Evidence).

## Repro strategy

**Part 2 has a real red test.** It already exists:
`tests/test_config_jinja_rendering.py::test_notification_fires_when_cloud_write_raises[turn_on]`
and `[turn_off]`. Both are red **today** in the local venv, which is
already the target environment, so they are red before any pin edit
too. The pins only decide whether CI sees them.

```bash
venv/bin/python -m pytest "tests/test_config_jinja_rendering.py::test_notification_fires_when_cloud_write_raises" -v -p no:testmon
```

They fail with `DID NOT RAISE <class 'tests.test_config_jinja_rendering._CloudApiError'>`,
which is the diagnosed reason, not an import or collection error.

**Part 1, the coverage twin: an in-fix lockstep guard, not a repro.**
`tests/test_quality_gate.py::TestCiWorkflowConfig::test_coverage_pin_matches_requirements`
is green before the fix and green after it. It goes red only in the
half-edited state (one side of the twin bumped), so it guards against a
partial fix rather than reproducing the stale pins. Implement still
induces and records that red (see Fix plan) as proof the twin moved
together.

**Part 1, the pins vs the local venv: a unit test cannot reproduce
this.** The bug is a mismatch between a dependency manifest and an
external, machine-local venv, and no pytest running *inside* one
environment can see the other. The discriminating alternative proof,
red today and green after the fix, is the combined dry-run against the
local venv:

```bash
set -o pipefail; venv/bin/python -m pip install --dry-run --quiet --report - -r requirements.txt -r requirements_test.txt | venv/bin/python -c 'import json,sys; r=json.load(sys.stdin); i=[(p["metadata"]["name"],p["metadata"]["version"]) for p in r["install"]]; assert i==[], i; print("OK: pins satisfied by local venv")'
```

How to read the result:
- **Red today:** an `AssertionError` listing HA 2026.8.1, phcc 0.13.355,
  ….
- **Green after the fix:** it prints `OK`.
- **Also red:** a missed lockstep pin makes pip fail the combined
  resolve with `ResolutionImpossible`. You then see pip's error on
  stderr, plus a `JSONDecodeError` from the empty stdout, and
  `pipefail` keeps the exit status non-zero.

**Regression check, not discriminating:** `pr-quality.yml` green on the
fix PR (4 shards on HA 2026.10.4, coverage aggregation, ruff, mypy,
translations). It shows that nothing regresses on the new stack.

Fallback accepted: the remaining pin-vs-local-venv drift is invisible to any unit test running inside a single environment; proof = the combined pip dry-run assertion above going red→green, plus green pr-quality CI as a regression check (accepted by the human in-session, 2026-10-27).
