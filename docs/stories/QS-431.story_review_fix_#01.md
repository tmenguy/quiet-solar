### [should-fix] S1 — unplug while HA is down leaves the car frozen
- File: `custom_components/quiet_solar/ha_model/charger.py:3645` (`_lift_boot_user_pin_if_car_unplugged`), related `charger.py:4336-4350` (unplug branch)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: the only store wipe on unplug is `self.car.clear_all_user_originated()`
  inside `if self.car:`. After a restart `self.car` is None in the unplug branch, so
  nothing is cleared. The QS-416 boot guard proves the unplug (`_car_unplugged_since`)
  but only lifts the two pin keys, leaving `user_frozen` set. Scenario: pin Thomas on
  the Zoe (frozen) → HA down 07:00–07:30, Zoe unplugged at 07:15 → on boot the guard
  lifts the pins only → Zoe plugged in that evening is still frozen → no person
  constraint for the whole session. Before this PR the leak was harmless (pin only);
  now it silently disables trip charging, contradicting "freeze lasts until unplug".
- Proposed fix: when the boot guard proves the unplug, treat it as the physical unplug
  it is for the car's user store: clear the car's whole user-originated store
  (`car.clear_all_user_originated()`, which removes `user_frozen` along with the pins
  it already clears), mirroring the live-unplug branch. Check whether the live branch's
  companion clears (`_clear_leaked_person_target_if_needed` equivalent for that car,
  `clear_system_person_hold`) must follow too, and justify the choice in the progress
  note. Red test: a frozen car with a persisted pin, plug sensor history on→off after
  the pin's save time, boot → after the guard fires `car.is_user_frozen()` is False and
  a person constraint is pushed at the next plug. Update `user-override.md` /
  `person-trip-prediction.md` freeze-lifetime wording if needed.

### [should-fix] S2 — the charger-card reset does not unfreeze the car
- File: `custom_components/quiet_solar/ha_model/charger.py:2691` (`QSChargerGeneric.user_clean_and_reset`), `home_model/load.py:455-463`
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: charger-card bump / "charge now" / timed-charge buttons call the car's
  user methods and freeze the car, but the charger-card reset only clears the charger's
  own store and runs `reset()` → `detach_car()`, never touching `car._user_originated`.
  Scenario: "charge now" on the Wallbox card (car frozen) → reset on the same Wallbox
  card → car re-attaches next cycle still frozen → no person constraint until a
  physical unplug or a car-card reset.
- Proposed fix: in `QSChargerGeneric.user_clean_and_reset`, capture the attached car
  before `super().user_clean_and_reset()` detaches it and clear its user-originated
  store (same effect as the car-card reset for the freeze). Red test: charger-card
  "charge now" then charger-card reset → `car.is_user_frozen()` is False and the person
  constraint is pushed again. Make the docs ("the reset button") name both cards.

### [nice-to-have] N2 — rounded-% compare has no hysteresis
- File: `custom_components/quiet_solar/ha_model/charger.py:4923`
- Severity: nice-to-have
- Source: qs-review-edge-case-hunter
- Description: a person need jittering around a .5 boundary (44.49 ↔ 44.51 …) flips
  `int(round(...))` on each poll → rewrite + `stable_name` change + notification each
  time — a slower residual of the same storm.
- Proposed fix: add a half-percent hysteresis — rewrite only when the rounded % changes
  **and** `abs(new - current) >= 0.5`. Red test: needs 44.49 → 44.51 → 44.48 → 44.52 →
  no rewrite after the first; a genuine move (44.49 → 45.2) still rewrites. Keep
  `test_person_target_sub_percent_drift_does_not_rewrite` green. Mention it in the
  charger-budgeting doc's Fix B sentence.
