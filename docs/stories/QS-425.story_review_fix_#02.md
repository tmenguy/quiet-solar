## Findings to fix

### [should-fix] R2-S1 — a re-run attempt of the same workflow run can keep the verdict FAILURE
- File: `scripts/qs/control_plane/ciwatch.py`: `_PR_FIELDS`, `_run_of` / `_latest_per_workflow`, the `ids[1] > latest[ids[0]][0]` comparison
- Severity: should-fix
- Source: qs-review-blind-hunter
- Description: "Re-run failed jobs" / "Re-run all jobs" keeps the same `workflowRun.databaseId` (it bumps
  `run_attempt`), and each attempt gets its own check suite. Two suites then share `(workflow id, run id)`. The strict
  `>` keeps the first one in iteration order; if that is the failed attempt 1, a flaky job that was re-run green
  stays red.
- Proposed fix: add the suite's own `databaseId` to the `checkSuites` node selection. Keep the latest suite per
  workflow by the key `(run databaseId, suite databaseId)`; suite ids grow monotonically. Tests: two suites with the
  same run id — old FAILURE, newer SUCCESS → green, in either list order; the reverse → red.

### [should-fix] R2-S2 — `checkSuites(first:20)` counts every app's suites (raised by 3 reviewers)
- File: `scripts/qs/control_plane/ciwatch.py:66-73` (`_PR_FIELDS`)
- Severity: should-fix
- Source: qs-review-coderabbit (Major), qs-review-blind-hunter and qs-review-edge-case-hunter (round 1 nice-to-have),
  merged
- Description: suites from other apps (coderabbitai, cursor — cursor stays `QUEUED` with 0 runs) take up the 20-suite
  page. Actions suites can then fall off it: the verdict sits `PENDING` behind `hasNextPage`, or a failing or newer
  suite is never seen.
- Proposed fix: `checkSuites(first:20, filterBy:{appId:15368})`. The orchestrator checked this live on PR #435: it
  returns only the two `github-actions` suites, `hasNextPage: false`. Add a module constant (e.g. `CI_APP_ID = 15368`)
  next to `CI_APP`, and keep the client-side slug filter as a backstop. Update the query-text test. Add the constant
  to the module-constants table in `docs/workflow/control-plane.md`, and change the CI-watcher paragraph's 20-suite
  assumption to "20 Actions suites".

### [should-fix] R2-S3 — a null `checkSuites` raises in `_verdict`
- File: `scripts/qs/control_plane/ciwatch.py` (`_pr` → `_verdict(commit["checkSuites"])`, ~:169)
- Severity: should-fix
- Source: qs-review-coderabbit (Major). It was a round-1 nice-to-have; it is promoted because the fix is two lines.
- Description: `commit["checkSuites"]` = `null` → `TypeError`, so the poll can't store that PR's state.
- Proposed fix: treat `None` as no suites: `_verdict` accepts `dict | None` and returns `("PENDING", 0)` for `None`.
  Add a test.

### [should-fix] R2-S4 — a resumed node can skip CodeRabbit without making a single call
- File: `scripts/qs/agent_templates/qs-node.md.j2`: "Between loop calls" (~:552-561) and the end-of-wait sentence
  (~:568-570)
- Severity: should-fix
- Source: qs-review-edge-case-hunter
- Description: `cr_from` lives in `round.json`. The bullets don't order "re-call the tool" against "past
  [[ crwait ]] s since `cr_from` → skipped", and the CI-terminal clause is unconditional. A node resumed more than 900 s
  later, or one that finds CI already terminal, can mark `cr: skipped` without one call. The review is then never
  requested, or a finished review is never ingested.
- Proposed fix: make the rule explicit. In `cr: trigger` / `cr: pending`, always re-call the tool first. Only an
  answer that is still `BUSY`, and comes after [[ crwait ]] s since `cr_from`, turns `cr` into `skipped`. Phrase the
  CI-terminal clause the same way: "once CI is terminal, a `cr: trigger` whose re-call still answers `BUSY` becomes
  `cr: skipped`". Pin the wording in `test_node_bounds_an_unanswered_trigger_by_the_coderabbit_wait` (or a sibling
  test).

### [should-fix] R2-S5 — the CodeRabbit wait bound: the docs say one window, the template allows two
- File: `scripts/qs/agent_templates/qs-node.md.j2:182-184` (the `cr_from` description) and `:307-309`;
  `docs/workflow/control-plane.md:676`
- Severity: should-fix (raised by 3 reviewers)
- Source: qs-review-blind-hunter, qs-review-edge-case-hunter, qs-review-acceptance-auditor (nice-to-have each),
  merged
- Description: `cr_from` is set on entering `cr: trigger` and set again on `triggered` / `already`. The worst case is
  therefore 2×`CR_WAIT_S`, but `control-plane.md` describes a single window "counted from the request being owed".
- Proposed fix: keep the behaviour, because a review needs its own full window after it is requested, and say so in
  both places. For example: "`cr_from` is set on entering `cr: trigger` and reset when the request is answered
  (`triggered` / `already`), so a round waits at most 2×`CR_WAIT_S` for CodeRabbit". Add the "(superseded by review
  fix #01 S3/#02)" pointer at the story's D2 wait-loop text (~:209, ~:338).
