## Findings to fix

### [should-fix] R6-S1 — a resume during the catch-up wait can reach `done` without the catch-up head's CI being green
- File: `scripts/qs/agent_templates/qs-node.md.j2`:
  - the catch-up push write in step 7 (~:374-377);
  - start-up rule 5 (~:214-223).
- Severity: should-fix
- Source: qs-review-edge-case-hunter. The orchestrator checked it against the template.
- Description: the catch-up push write sets `head`, `pushed_at` and `wait_from` (and skips a `cr: trigger`), but
  leaves `step` at `catchup`. So the whole catch-up wait and the triage after it run under `step: catchup`. Start-up
  rule 5 treats `catchup` specially only when `MERGE_HEAD` exists. Otherwise a resume restarts step 7 from the top:
  `origin/main` is already an ancestor of `HEAD`, and the PR's `conflict` bit is not kept, so nothing is merged and
  the "before done" path goes on to step 8. That posts `converged` and `task state --to ready_to_merge` without
  step 6's "CI green on the current head" check ever running for the catch-up head. Nothing in the Control Plane
  refuses this.
- Reproduces when: the catch-up head's CI stays pending past `CI_WAIT_MAX_S`, so the node blocks with `ci_wait`. An
  `info` "go on" then unblocks it, and it resumes at `step: catchup` and goes straight to done. The same happens on
  any reap or rotation during the catch-up wait.
- Proposed fix (template only; keep the wording tight):
  1. **Catch-up push write:** in the same one write, also set `step: wait`. The resumed node then re-enters the wait
     loop and the triage after it (step 6, which checks CI green on the current head). It then reaches step 7's
     "before done" catch-up again, finds nothing to merge, and goes to step 8 only after green CI. Say so in one
     clause, e.g. "(`step: wait`: a resume re-enters this wait and its triage, never step 8 directly)".
  2. **Start-up rule 5,** extending the existing `catchup` clause: "`catchup` with no `MERGE_HEAD` and `git rev-parse
     HEAD` ≠ `round.json`'s `head` (a catch-up merge committed, maybe pushed) → finish that catch-up: the gate if not
     yet green, `tool push` (its key replays), then the catch-up push write; never re-decide whether to merge, never
     go to done from here."
  3. Check that "wait" in the `step` enum, and the step 6 / 7 / 8 flow, still read correctly with this. In particular,
     the "When the wait ends, triage runs again over the build phase…" sentence must stay true when the resume is at
     `step: wait` after a catch-up push.
- Tests (`tests/qs/test_render_agents.py`):
  - pin `step: wait` in the catch-up push write (extend `test_node_catch_up_push_skips_an_owed_trigger`, or add a
    sibling test);
  - pin the new start-up `catchup` clause ("never go to done from here", or equivalent).
