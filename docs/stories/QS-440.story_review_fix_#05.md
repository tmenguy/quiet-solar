### [nice-to-have] Z1 — Git's real full-disk lock message is still read as `BUSY`
- File: `scripts/qs/control_plane/catchup.py:83` (`_REF_LOCK`), `tests/qs/control_plane/test_catchup.py:1908-1916` (`test_only_a_ref_lock_on_fetch_is_busy`), `docs/workflow/control-plane.md:686`
- Source: qs-review-edge-case-hunter (round 5, reproduced with git 2.51)
- Description:
  - Git's ref transaction always puts `cannot lock ref '<ref>': ` in
    front of the lock error. A full disk therefore reads
    `error: cannot lock ref 'refs/remotes/origin/main': Unable to create '…/main.lock': No space left on device`.
  - The bare `cannot lock ref` alternative matches that, so the answer
    is `BUSY` and costs 6 × 60 s of replays.
  - The test row for a full disk on a `.lock` path has no prefix, so it
    passes without covering git's real message.
- Proposed fix:
  - `BUSY` only when the lock really exists: `Unable to create
    '….lock': File exists`, or `cannot lock ref '…': ` followed by
    anything other than an `Unable to create` (for example
    `is at X but expected Y`).
  - Suggested pattern:
    `r"Unable to create '[^'\n]*\.lock': File exists|cannot lock ref '[^'\n]*': (?!Unable to create)"`.
  - Add test rows using git's real prefixed forms:
    - `cannot lock ref '…': Unable to create '….lock': File exists.` → BUSY
    - `cannot lock ref '…': Unable to create '….lock': No space left on device` → TOOL_FAILED
    - `cannot lock ref '…': is at … but expected …` → BUSY
  - Reproduce at least the `File exists` case on a real temporary repo
    if that is practical. Otherwise use the parametrised rows.
  - Fix the "never a full disk" comment and the doc line so they match.

### [nice-to-have] Z2 — A merge that newly conflicts gets `finish` after any miss; the doc says `resolve`
- File: `scripts/qs/control_plane/catchup.py:678` and `:707` (`progress`), `docs/workflow/control-plane.md:716`, test `test_a_merge_over_uncommitted_changes_is_an_error` (it pins `"finish"` for a fresh merge)
- Source: qs-review-edge-case-hunter, qs-review-blind-hunter (round 5)
- Description:
  - `resolve = "resolve" if not cu["misses"] else "finish"` is also
    used for conflicts that this call's own `git merge` just opened.
  - After a miss, for example once the implementer has run
    `git merge --abort` and reported red, the next re-merge conflicts
    and is answered `finish`. `finish` gives the implementer neither
    side's intents; `resolve` does.
  - The doc says conflicts → `resolve`, and limits `finish` to a
    `MERGE_HEAD` that was already open.
- Proposed fix:
  - When this call's own merge opens the conflicts, answer
    `self.resolve("resolve")`.
  - Keep `finish` only for the branch where `MERGE_HEAD` was already
    open when the call began, after a miss.
  - Update the pinned test, and add one: a miss, then a fresh
    conflicting re-merge, answers `resolve`.
  - Make the doc and the template's mode text match.
