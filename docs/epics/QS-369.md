## Goal

Build a **second pipeline next to today's**, which is frozen. Its single entry
point is **one orchestrator session**:

1. it discusses the work with the maintainer and turns it into a **task
   graph** — deliverables made of work items;
2. after **one review** of the global plan and the deliverable plans, it runs
   the graph **autonomously**: one session per work item, each in its own
   worktree, in parallel where the graph allows;
3. it integrates each deliverable, drives its review loop to convergence with
   CI green, and **merges it itself**, without waiting for the maintainer (for
   now);
4. once everything is merged, **one interactive review guide** takes the
   maintainer through every deliverable to a **final validation — or a
   reopened discussion** on the ones that need it.

The maintainer steps in for the discussion, the plan review, the final
validation and the exceptions — never to carry fix plans or files between
sessions.

## Evidence

### Recorded 2026-09-24

- **Review does not converge.** Across the last 15 stories: 64 review-fix
  plans, about 4.3 rounds per story; QS-335 and QS-349 took 10 each. Findings
  per round stay flat (QS-335: 10, 10, 10, 6, 10, 6, 8, 6, 6, 1) instead of
  shrinking.
- **No stopping rule.** `qs-review-task` loops "until no must-fix/should-fix
  remains". The inexhaustible lenses dominate: blind-hunter ≈ 710 findings,
  edge-case-hunter ≈ 600, of ≈ 1,900 total.
- **Code review has no memory.** Plan review has finding states (open /
  resolved / rejected) and a delta-auditor; code review re-reviews the whole
  PR from scratch each round and can re-raise rejected findings.
- **Flip-flop between rounds.** Review raises X, implement fixes it, a later
  round asks to revert or change that fix, implement reverts it, then review
  raises X again. Nothing detects this.
- **Late rounds find things that belong elsewhere.** A refactor filed as
  should-fix in QS-349 round 9 belongs in the plan. A red CI `ruff format`
  check in the same round should have been caught at implement (fixed by
  #371). Implement also has no pre-PR self-check against the acceptance
  criteria; the acceptance-auditor has logged ≈ 260 findings.
- **The human is the relay.** Every fix round costs two new sessions, plus a
  fix-plan file committed to `docs/stories/`. Today a task takes 5+
  maintainer touchpoints: setup, plan finalize, "Ready to run the quality
  gate?" in implement, the review triage, the merge authorization.
- **The lanes haven't split for implement and review.** 5 of 6 lane files
  were byte-identical to `phase-protocols.md` (4 of 6 since #340).
- **Leftover path-based routing** and **template bloat** — both fixed by
  #372.
- **Bug fixes can grow silently.** Diagnose checks bug scope at plan time,
  but the diagnose template lets implement "extend the list with a reasoned
  progress note". Nothing checks scope at build time.

### Mechanisms available (checked 2026-09-28)

- **Claude Code 2.1.281** (`claude --help`): `claude --bg` starts a
  background session; `claude agents` lists sessions (it also lists the
  maintainer's interactive sessions on this machine); `claude attach <id>`
  opens a background session in a terminal; `claude logs <id>`;
  `--bg --resume <id>` continues a session in the background under the same
  id, or starts a copy when it is already running; `--agent` always wins over
  a pin.
- **Cross-session messaging** (Claude Code docs): `SendMessage` delivers a
  message to another local session between its tool calls, or starts a new
  turn when it is idle.
- **Claude desktop app** (Claude Code docs): `/resume` picks up a session
  started in the terminal; `/desktop` in the terminal moves a CLI session to
  the desktop app; several sessions run side by side as sidebar tabs. It has
  **no view of background sessions** (the agent view is terminal-only) and is
  **not** a Remote Control client (Remote Control reaches claude.ai/code and
  the mobile apps). It has **no agent picker**; it honours an `agent` key in
  `.claude/settings.local.json`, which today's launcher writes only into
  linked worktrees — the main checkout is refused by design (guard 2,
  [harness.md](../workflow/harness.md) → "GUI launch surface").
- **Hooks:** `SessionStart` fires on start and on resume and can inject
  context.
- **OpenCode — a known limitation:** `spawn_session.py` creates a session and
  sends it a message over the HTTP API, but only inside the server's own
  workspace; a new worktree is another workspace (`launchers/opencode.py`).
  Agents are discovered at server start.
- **Not verified:** whether a `--bg` session can be brought into the desktop
  app (`/resume`, `/desktop`); whether `SendMessage` reaches a running `--bg`
  session, or wakes a reopened GUI session; whether `--model` at spawn beats
  an agent's frontmatter model.
- **How other harnesses store state** (survey): plans in markdown tracked in
  git; runtime state outside the tracked tree, mostly SQLite (vibe-kanban,
  Conductor, mcp_agent_mail) or a DB server (beads and Gas Town on Dolt).
  Tracked state files led to merge conflicts and lost updates; claims are
  leases with a TTL; crash recovery replays an append-only event log.

## Principles and decisions

### Two pipelines side by side

- **Today's pipeline is frozen — lightly** (maintainer: "the freeze is
  light, I will probably never work again on the previous way of working if
  the new one works; if you need to do stuff on those to help us, do it, but
  I doubt it"). It stays reachable (CLI `claude --agent qs-<phase>`, slash
  commands). Retiring it is a later decision.
- **The new pipeline** is built next to it, child by child.

### Units: deliverables and work items

- **A deliverable is a GitHub issue:** a unit that on its own brings
  something measurable and testable to the system — something a release note
  would list (maintainer). It gets its own worktree, branch and PR, and a lane
  (`kind` × `target`, hence its rigor profile).
- **A work item is a part of a deliverable.** Several work items of one
  deliverable can run in parallel and land in the same PR (maintainer).
- **The task graph** holds the deliverables, their work items and their
  dependencies. A small bug is one deliverable with one work item; an epic is
  several deliverables.

### The flow

1. **Entry.** The maintainer opens the orchestrator: a **true session in the
   Claude GUI** on the pinned main checkout (maintainer), or
   `claude --agent qs-orchestrator`.
2. **Discussion → graph.** Every piece of work starts the same way; the
   discussion decides the graph's shape (maintainer). The orchestrator
   proposes each deliverable's lane.
3. **The plan review** — the global plan plus each deliverable's plan, in one
   review before anything is launched (working position; the maintainer said
   "maybe").
4. **Refinement.** Plan agents refine each deliverable plan; their questions
   come back to the orchestrator (maintainer). A refinement that changes a
   deliverable's scope or acceptance criteria goes back to the maintainer
   (assistant proposal).
5. **Execution.** One background session per work item, in its worktree.
   Each node session spawns its own implementer and helpers.
6. **Integration inside a deliverable,** very regularly (see "Parallel
   work").
7. **The deliverable's review loop,** CI included (see "The build loop").
8. **Automatic merge** (maintainer, for now), when CI is green, the review
   has converged and no escalation is open — **the orchestrator never pauses
   to ask before a merge**. Dependent deliverables start from the updated
   `main`.
9. **The review guide and the final validation, at the end** (see below). A
   merged deliverable **keeps its worktree, branch and state until the final
   validation**, and cleanup happens **only at the final stage** (maintainer).

### The orchestrator session

- **A true session in the Claude GUI — nothing more** (maintainer, 2026-09-28:
  "better to have the orchestrator simply in the Claude Code GUI as a true
  session"). No separate "voice" front end.
- **While it is open,** it orchestrates. The node sessions are separate
  background sessions, so they keep running when the GUI is not looking.
- **When it is closed (or the app quits), orchestration pauses:** nodes carry
  on until they need the orchestrator, then wait; nothing is lost — the state
  is in the database. Leaving the app open (with its keep-awake option) lets a
  run go on while the maintainer is away.
- **When it is reopened,** it picks up from the database (maintainer liked
  this, 2026-09-28): it reads the run's state at every turn, so any message
  resumes it; a `SessionStart` hook injects a summary of what happened while
  it was closed; and, if the spike shows it works, a node's `SendMessage`
  wakes it without the maintainer.

### Parallel work inside one deliverable

Principle (maintainer): parallel work items must be split so they **do not
step on each other**, and **integrate very regularly** — like two engineers
on the same branch for the same PR. How overlaps are prevented is child 6's
choice (assistant proposal: by code, not by the prompt, with a work item that
needs another's part of the code going through the orchestrator).

### One voice, and a board

- **One voice** (maintainer, "ok one voice"). The maintainer only talks to
  the orchestrator; node sessions never address the maintainer, they ask the
  orchestrator, which answers when the plan covers the case and escalates
  only the exceptions.
- **Open doors** (assistant proposal): any node session can be opened in a
  terminal (`claude attach`) to watch it or take over.
- **The board is a web page** (maintainer, "would love it"): the graph with
  each deliverable and work item, its state, PR and CI.
- **Communication** (assistant proposal): through the state database, plus a
  wake-up message from the harness; work items never negotiate with each
  other directly.

### The state database

**Our own, a SQLite file** (maintainer): `harness_state.db` at the root of the
main checkout, gitignored, used by every worktree; its path is passed to
every session. One machine for now; a new machine creates its own. Losing it
loses only runtime state — plans, code, PRs, issues, the per-deliverable
summaries and the review guide are durable, in git and GitHub. Each
deliverable leaves a summary of what was done in `docs/stories/`
(maintainer).

### The build loop of a deliverable

1. **Implement** in the node sessions: TDD, local gate.
2. **Review:** the lane's reviewers in parallel, with no implementer context;
   round 1 on the full integrated diff, later rounds on the changes since the
   last reviewed commit, with the ledger as context.
3. **Triage by policy, recorded in the ledger.** must-fix is fixed
   automatically. **should-fix is fixed in every round** — in scope by
   definition — with flip-flops handled properly and a **strict scope
   check**: a "should-fix" that would expand the scope is out of scope and
   deferred (maintainer). nice-to-have is only recorded. Rejected findings
   keep their reason and cannot be re-raised.
4. **CI is the definition of done** (maintainer's brief): CI green on the PR,
   not the local gate. A red check is a must-fix finding, handled
   autonomously and watched during the loop.
5. **Converge. Aim for 2 rounds, no hard stop; after about 5 rounds without
   converging, alert the maintainer and ask** (maintainer: "after 5 for
   example"; the exact number is child 3's to set).
6. **Deferred findings** go to the review guide; at the final validation the
   maintainer decides which ones become issues.

**Finding classes** (proposed by the assistant, accepted by the maintainer as
the starting point):

- **must-fix:** the deliverable is wrong without it — an acceptance criterion
  unmet, a bug or regression, a red CI check or failing test, a violated
  project rule.
- **should-fix:** a real weakness inside the deliverable's scope — e.g. an
  unhandled edge case in the changed code, a missing test for a changed path —
  fixable without adding behaviour or touching code outside the plan.
- **nice-to-have:** optional polish; recorded only.
- **out of scope:** refactors, new behaviour, code outside the plan —
  deferred to the review guide, whatever the reviewer called it.

**Flip-flops.** "Proper flip-flop handling" (maintainer). The mechanism —
recorded 2026-09-24, not revisited: a finding that would revert or rework a
change made to resolve an earlier finding, or that re-raises a fixed or
rejected one, is decided once with a recorded rationale and marked `settled`;
later contradictions are rejected automatically. **A red CI check or a
failing test reopens a settled decision** (maintainer: "ok"); it escalates
only if fixing CI would reverse the settled trade-off (assistant proposal).
The deterministic part is enforced by code (#375).

**Focused reviewers** (recorded 2026-09-24, not revisited): only the diff and
the plan's acceptance criteria, a relevance-to-this-task test, no refactor
suggestions outside the scope.

### When it asks the maintainer

- A plan defect: a plan is contradictory or incomplete, or a refinement or a
  finding needs a change to a deliverable's scope or acceptance criteria.
- A big decision with no clear rationale, including an oscillation the
  orchestrator cannot settle.
- No convergence after about 5 rounds, or a gate stuck after K attempts.
- A node or an integration it cannot unblock.
- Actions the rules reserve for the maintainer (`pragma: no cover`, a
  cross-target warning, irreversible actions). Merges run without waiting,
  for now; an escalation blocks the merge it concerns.

### The review guide and the final validation

**Why merges do not wait:** the maintainer accepted it on a condition —
"if I can come back and revert things easily, then you're right, do
everything at the end so you can work without interruption" — and expects to
reopen a discussion more often than to revert a whole deliverable.

**What he gets in return:** "a very well-made artifact that guides me
progressively through the deliverables … up to a final validation", which
**must be very fluid** (maintainer). It fills in as deliverables merge,
without asking anything (reading it along the way is optional); **once
everything is merged, the maintainer goes through it in one sitting** and
gives each deliverable a verdict: **validated, or reopen the discussion**.

For each deliverable — the maintainer's list: a nice summary with **diagrams
if needed**; the **bug or feature recalled for the end user, how it was
before and what it does now**; the **confidence level**; the **blast
radius**; the **attention points**. Assistant additions: the basis of the
confidence level, what was deferred, how to revert it, and the deliverables
merged after it that it may affect.

For the run: the graph and merge order, and the interactions between
deliverables. After a reopened discussion **the maintainer decides what
follows** — a follow-up fix, a new deliverable, a revert only if needed. A
follow-up starts from the deliverable's kept worktree, brought up to date
with `main`, goes out as a **new PR** through the same loop, and its guide
entry is updated. **The run closes** when every deliverable is validated or
its follow-up settled; cleanup happens then.

### Lanes become rigor profiles

A lane sets the rigor of one deliverable (maintainer's brief): plan template,
gates, reviewer set, definition of done, checkpoints — a plain profile file
the orchestrator reads on demand. The table below is a **starting point
carried over from the 2026-09-24 text**, decided when each profile's child is
filed:

| profile | plan | gates | done means | reviewers |
|---|---|---|---|---|
| **feature × product** | spec with acceptance criteria | today's product gate | every acceptance criterion met and tested; CI green | today's four, focused |
| **bug × product** (copies the content of `diagnose-task` and `verify-task`) | diagnosis with a red-test spec | product gate, red test first | cause removed, regression pinned by a red test that failed for the diagnosed reason; CI green | regression-proof, code-level fix-minimalist, edge-case limited to the fix, CodeRabbit |
| **feature × factory** | spec with acceptance criteria | `tests/qs` always, harness-sync check, prompt cost (from #338) | criteria met; dogfood criterion written before merge; CI green | adds parity and prompt-cost lenses |
| **bug × factory** | diagnosis, plus the substitute oracle for prompt fixes (from #336) | as feature × factory, red test or oracle first | as bug × product, plus observe-after-merge for prompt fixes (from #336) | as bug × product, plus parity |
| **epic × factory** (mode) | the decomposition; no build loop, no PR | `epic_doc.py land` checks | document landed, children filed | the plan reviewers |

**The bug profile fixes only the bug** (recorded 2026-09-24, not revisited):
the diagnosis sets the allowed scope, the red test fails for the diagnosed
reason, and a size tripwire stops the loop with three options — a minimal fix
plus a separate refactor, back to diagnosis, or accept the wider fix.

### GUI and entry

- **The main checkout is pinned to the orchestrator** (maintainer): a new GUI
  session on `quiet-solar` is the orchestrator.
- **A small command** (working name `/setup-gui`) re-pins the orchestrator for
  the next session opened (maintainer).
- **The frozen pipeline** stays reachable from the CLI and its slash
  commands.

### Agent prompts: rendering

**Jinja stays as a build step, with no task facts** (maintainer): harness
frontmatter, model and effort from `models.py`, shared partials. The facts
travel in the launch prompt and the state database; profiles are files read
on demand. The frozen pipeline keeps its rendering unchanged.

### Multi-harness

**Kept** (maintainer). Assistant proposal: target Claude Code and OpenCode
first, with the harness-specific parts behind the launcher layer; Codex stays
as it is for today's pipeline. OpenCode cannot yet create a session in
another workspace — child 10's first question; if no fallback works (nodes in
the server's workspace, one server per worktree), the multi-harness decision
is revisited with the maintainer.

### Success measures (assistant proposal)

The state database records rounds, escalations, reopened discussions and
merges per deliverable, so the new pipeline can be compared with the evidence
above (about 4.3 rounds per story, 5+ touchpoints, red CI persisting across
rounds) after its first deliverables.

### Risks

1. **Token and session cost** of many parallel sessions.
2. **Parallel work items stepping on each other.**
3. **Dead or duplicated nodes** (a lease expiring during a long gate run).
4. **Orchestration pausing** while the orchestrator session is closed.
5. **A bad automatic merge** — mitigated by CI, the review loop, the review
   guide, and a revert when needed.
6. **The orchestrator's context** growing with the discussion and the number
   of deliverables.
7. **Unverified mechanics** (listed under "Mechanisms available").

### Rejected alternatives

- **Script-driven orchestration** (a script chaining headless `claude -p`
  sessions): the core is continuous judgement, which needs an LLM.
- **A separate `qs-build-task` after the plan** (2026-09-24): it loses the
  intent the planning session holds, and keeps a hand-off.
- **One interactive session per task, from setup to merge** (first redesign):
  its context grows with every round, it cannot parallelise, and under the
  one-level sub-agent limit it cannot give each part of the work its own
  implementer.
- **A "voice" GUI session in front of a background orchestrator:** it would
  only relay messages (maintainer, 2026-09-28).
- **beads for the state:** an external binary and Dolt database, touching
  agent files, with a memory feature that clashes with the no-auto-memory
  rule. Its ideas (ready / claim, hash ids, `supersedes` links) are borrowed.
- **State in tracked files:** merge conflicts and lost updates across
  branches.

## Requirements per child

Problems found in review that each child must solve. The mechanism is the
child's choice.

- **Item worktrees (child 12):**
  - `utils.get_issue_from_branch` (`utils.py` ≈ l.94-96) does
    `int(branch[3:])`, and Python's `int()` accepts underscores, so a
    sub-branch `QS_369_1` parses as issue **3691**; `quality_gate.py`
    (≈ l.1930-1934) already fixed this, `utils` did not — callers include
    `render_agents.py`, `context.py`, `create_pr.py`;
  - naming, creation and cleanup of item worktrees: today everything knows
    only `QS_<N>` — `worktree-setup.sh` (numeric issue only, `push -u origin`
    for every branch), `setup_task.py` (render and pin at worktree birth),
    `utils.get_worktree_dir`, `cleanup_worktree.py`, the lane check in
    `quality_gate.py`; the venv and cache seeding of a new worktree; whether
    item branches are pushed; tests in `tests/qs`.
- **State database (child 5):**
  - the **graph schema** — deliverables, work items, dependencies, state, PR,
    CI — which the orchestrator writes and the board reads, plus a schema seam
    for #375's ledger tables;
  - liveness from the process (e.g. `claude agents --json`), not only from
    LLM heartbeats, plus a **fencing token** so a superseded session cannot
    commit, push or post; the old session is killed before a respawn;
  - a cap on concurrent node sessions and concurrent gate runs;
  - a take-over / hand-back state so an opened node is not reclaimed;
  - a lock that serialises integrations;
  - `harness_state.db` and its `-wal` / `-shm` files gitignored;
  - a clear split between runtime state (may be lost) and durable context
    (exported to git: the `docs/stories/` summaries, the review guide) so the
    no-auto-memory rule of `CLAUDE.md` still holds;
  - done: every CLI command covered at 100% in `tests/qs`, including a
    concurrent-claim test.
- **Loop engine (#375, child 3):** its ledger tables on child 5's schema;
  finding identity (a fingerprint) and the finding schema first; what counts
  as a round, K, and the alert threshold (maintainer's example: 5); red CI
  checks turned into must-fix findings; the code / judgement split.
- **Orchestrator core (child 6):**
  - it is a true GUI session: it reads the run's state at every turn; a
    `SessionStart` hook injects a summary of what happened while it was
    closed; closing it pauses orchestration without losing anything;
  - rendering: a **third registry** in `render_agents.py` for new-pipeline
    agents — no task facts, not in `PHASE_TO_AGENT` (being an orchestrator
    there turns on the task-facts block of `_base.md.j2`); `models.STEMS`
    extended, `tests/qs/test_models.py` and `tests/qs/test_render_agents.py`
    updated; task-agnostic agents present in every worktree the orchestrator
    creates; new templates pinned in `tests/qs` (`--quick tests/qs` before
    commit);
  - the lane-dependent model: `models.py` stays the single policy source and
    exposes a lane → model mapping that the launcher applies at spawn;
  - integration inside a deliverable: serialised; each merge in a scratch
    worktree, the deliverable branch moved only if the gate is green; overlap
    prevention re-checked at integration (which also catches `--no-verify`),
    with merge commits exempt;
  - deliverable issues filed at the plan review with the approved lane's
    labels (target declared by approval, not inferred); a dependent
    deliverable's worktree created when its dependencies have merged;
  - catching up with `main` after a sibling's merge (re-run CI; the
    conflict-resolution delta does not count as a round);
  - frozen agents are copied, never moved.
- **Review loop and automatic merge (child 7):**
  - it owns the reviewer fan-out: which session hosts a review round, and
    reviewers writing their findings to the database and returning only ids;
    how CodeRabbit joins a round;
  - the automatic merge repeats what `finish-task` does on the main checkout

    the feature-product, feature-factory, bug-factory and epic-product lane

    `.claude/commands/finish-task.md`.
- **Review guide (child 13):** its format and location (durable, in git);
  the per-deliverable verdicts at the end; the follow-up path; the run's
  close and cleanup; built on the database, testable with fixture data.
- **Board web page (child 8):** a local page served from the state database,
  read-only to start with, on child 5's graph schema.
- **GUI entry (child 9):** pinning the main checkout needs a new writer —
