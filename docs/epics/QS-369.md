## Goal

Replace the manual relay `implement → review → fix plan → implement → review …`
with an **autonomous build loop** that runs implementation and review
together, **converges quickly**, and asks the maintainer only when a decision
truly cannot be made from the story and the rules. The maintainer should no
longer carry fix plans between sessions.

**All six lanes** end up following this approach, but the build is **not the
same agent behaviour in every lane**: a feature build and a bug build have
different goals, scope rules and reviewers (see "Lanes plug in as policy").

## Evidence (verified 2026-09-24)

- **Review does not converge.** Across the last 15 stories: 64 review-fix
  plans, about 4.3 rounds per story; QS-335 and QS-349 took 10 each. Findings
  per round stay flat (QS-335: 10, 10, 10, 6, 10, 6, 8, 6, 6, 1) instead of
  shrinking.
- **No stopping rule.** `qs-review-task` loops "until no must-fix/should-fix
  remains". The inexhaustible lenses dominate: blind-hunter ≈ 710 findings,
  edge-case-hunter ≈ 600, of ≈ 1,900 total.
- **Code review has no memory.** Plan review has finding states (open /
  resolved / rejected) and a delta-auditor; code review re-reviews the whole
  PR from scratch each round and can re-raise rejected findings.
- **Flip-flop between rounds.** Review raises X, implement fixes it, a later
  round asks to revert or change that fix, implement reverts it, then review
  raises X again. Nothing detects this.
- **Late rounds find things that belong elsewhere.** A refactor filed as
  should-fix in QS-349 round 9 belongs in the plan. A red CI `ruff format`
  check in the same round should have been caught at implement:
  `check_impacted()` runs only the testmon-selected tests and changed-line
  coverage, never `ruff check`, `ruff format --check` or `mypy`, which CI runs
  (#371). Implement also has no pre-PR self-check against the acceptance
  criteria; the acceptance-auditor has logged ≈ 260 findings.
- **The human is the relay.** Every fix round costs two new sessions, plus a
  fix-plan file committed to `docs/stories/`.
- **The lanes haven't split for implement and review.** 5 of 6 lane files are
  byte-identical to `phase-protocols.md`; feature-factory runs the
  product-code reviewers on markdown prompts.
- **Leftover path-based routing.** `qs-review-task` picks implement vs
  implement-setup from a hardcoded path list, which contradicts QS-321 (target
  is declared, never inferred) (#372).
- **Template bloat.** About half of `qs-review-task.md.j2` (≈ 290 of 560
  lines) is launcher and handoff plumbing, repeated 3–6 times per phase
  template (#372).
- **Bug fixes can grow silently.** Diagnose checks bug scope at plan time (the
  iceberg check; `qs-diag-fix-minimalist` rejects over-scoped plans with
  `redesign`), but the diagnose template lets implement "extend the list with
  a reasoned progress note". Nothing checks scope at build time.

## Design

### One orchestrator, thin, top-level

A single build orchestrator (working name `qs-build-task`) replaces the
implement ↔ review relay. It holds the loop state and spawns sub-agents, so
its own context does not fill up over many rounds. It must be the top-level
session, because Claude Code sub-agents cannot spawn sub-agents. OpenCode and
Codex need an equivalent, or a documented fallback.

1. **Implement.** An implementer sub-agent with a fresh context reads the story
   plus the open ledger findings, does TDD, and runs a gate that matches CI.
2. **Review.** The lane's reviewers run in parallel. Round 1 reviews the full
   diff; round 2+ reviews **only the changes since the last round**, with the
   ledger as context.
3. **Triage by policy, not by the maintainer.** must-fix is fixed
   automatically. **should-fix is fixed automatically when in scope**;
   refactors and scope growth go to the deferred list. nice-to-have is only
   recorded. Rejected findings are recorded with a reason and cannot be
   re-raised.
4. **Converge.** **Round budget = 3.** After round 1 the bar rises: only
   must-fix issues in the new changes, or regressions, can keep the loop going.
5. **Finish.** One summary (fixed / deferred / rejected, with reasons). The
   maintainer approves before finish.

### Finding ledger (replaces fix-plan files)

One state file per story. Each finding is `open`, `fixed`, `rejected`,
`deferred` or `settled`, with the round it came from and the change that
resolved it. The loop resumes from it if a session dies.

### Flip-flop detection (required)

The ledger links each fix to the finding it resolved. A new finding that would
**revert or rework a change made to resolve an earlier finding**, or that
**re-raises a fixed or rejected finding**, is flagged as an oscillation. The
orchestrator **decides it once**, picks a side with a recorded rationale, and
marks it `settled`. Any later finding that contradicts a settled decision is
rejected automatically. It escalates to the maintainer only when there is no
clear rationale either way.

### Focused reviewers

Reviewer prompts are tuned to stay on the task: only the diff and the story's
acceptance criteria, no open-ended exploration, a relevance-to-this-task test
before a finding is reported, and no refactor suggestions outside the story's
scope (those are deferred at most).

### When it asks the maintainer (the exception, not the norm)

The default is **autonomous until the pre-finish approval**. The loop stops
mid-flight only for:

- **A plan defect.** The story is contradictory or incomplete, or needs a
  change to scope or acceptance criteria. The loop writes a short plan
  amendment; the maintainer chooses amend and continue, back to create-plan
  (or diagnose), or accept as-is. Small clarifications are written into the
  story and the loop continues.
- **A big decision with no clear rationale**, including an oscillation the
  orchestrator cannot settle.
- **The round budget runs out** without converging, or **the gate is stuck**
  after K attempts.
- **Actions the rules already reserve for the maintainer:** `pragma: no
  cover`, a cross-target warning (product vs factory), irreversible actions,
  and the merge.

### Lanes plug in as policy; the loop is shared

From the maintainer's side each lane's `qs-build-task` behaves like a
different agent; underneath, the loop mechanics are written once. Each lane
supplies a reviewer set, a gate profile and a definition of done:

| lane | done means | should-fix rule | reviewers |
|---|---|---|---|
| **feature × product** | every acceptance criterion met and tested | fix automatically when in scope | today's four, focused |
| **bug × product** | cause removed, regression pinned by a red test that failed for the diagnosed reason | only what the bug needs; the rest becomes a follow-up issue | regression-proof, code-level fix-minimalist, edge-case limited to the fix's reach, CodeRabbit |
| **feature × factory** | criteria met; dogfood pass/fail criterion written before merge | fix automatically when in scope | adds harness-sync (parity) and prompt-cost lenses |
| **bug × factory** | bug × product discipline, plus the substitute oracle for prompt fixes (recorded transcript, pass/fail criterion, verification tail) | as bug × product | as bug × product, plus parity |
| **epic × {product, factory}** | no build step — the decompose agent (#340) reuses the engine to review the epic document | — | plan reviewers |

### The bug build fixes only the bug

- **The diagnosis fix plan sets the allowed scope.** Every round checks the
  diff against it; a change outside the plan is a finding against the build
  itself.
- **The red test comes first** and must fail for the diagnosed reason, not
  just fail.
- **A size tripwire stops the loop.** It trips when the fix touches files or
  functions the plan didn't list, needs a refactor, or reviewers say the cause
  is wider than diagnosed. It offers three choices: (a) a minimal fix now,
  with the refactor filed as a separate feature × product task; (b) back to
  diagnose (the iceberg path); (c) explicitly accept the wider fix. This is
  one of the legitimate stop cases.

## Decisions (maintainer, 2026-09-24)

- Autonomous until the pre-finish approval; mid-flight questions only for a
  plan change or a big decision with no clear rationale — the exception, not
  the norm.
- should-fix fixed automatically when in scope.
- Round budget 3; reviewers tuned to stay focused on the task.
- Flip-flops are detected and decided by the system so the loop converges.
- In the bug lanes the fix covers only the bug; if it turns out to need a
  refactor, the diagnosis or the build says so and stops.
